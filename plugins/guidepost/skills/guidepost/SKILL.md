# Guidepost

このスキルはメインセッションで実行する。`git`、`gh`、`node` はすべて Bash ツール経由で実行し、ユーザーに CLI 操作を要求しない。

`[guidepost]` で始まる注入を受けた場合は、ツアーを生成せず「9. 回答時の作法」だけを実行する。それ以外は次の手順を順番どおりに実行する。必須処理に失敗した場合は成功として扱わず、指定された中断条件に従う。

## 1. 引数を解釈する

- 引数がない場合はコミット範囲 `HEAD~1..HEAD` を使う。
- `#` に続く数字だけの引数は PR モードとして扱う。`#42` の PR 番号は `42` として `gh` に渡す。
- それ以外はコミット範囲モードとして扱う。範囲は `<base>..<head>` のように両端を明示した形式で受け取る。
- 解釈できない引数では処理を中断し、`/guidepost HEAD~3..HEAD` または `/guidepost #42` の形式を案内する。

## 2. diff と SHA を取得する

作業開始時のカレントディレクトリを対象プロジェクトのルートとして固定する。diff は一時ファイルへ保存し、以降は同じ内容だけを分析する。

### コミット範囲モード

1. 入力範囲を `<base>` と `<head>` に分ける。
2. `git rev-parse "<base>^{commit}"` と `git rev-parse "<head>^{commit}"` を実行し、完全な `baseSha` と `headSha` を取得する。
3. `git diff --no-ext-diff --unified=3 <range>` を実行し、出力全体を一時ファイルへ保存する。
4. `source` は `{ "type": "range", "value": "<入力範囲>" }` とする。省略時の value は `HEAD~1..HEAD` とする。

### PR モード

1. `gh` の存在を確認する。
2. `gh pr view <番号> --json baseRefOid,headRefOid` を実行する。
3. 応答から完全な `baseRefOid` を `baseSha`、完全な `headRefOid` を `headSha` として取得する。base ブランチを `main` などに固定しない。
4. `git diff --no-ext-diff --unified=3 <baseSha>..<headSha>` を実行し、出力全体を一時ファイルへ保存する。
5. `source` は `{ "type": "pr", "value": "#<番号>" }` とする。

`gh` がない、PR 情報を取得できない、SHA が空、または PR の diff を取得できない場合は、`/guidepost HEAD~3..HEAD` のようなコミット範囲モードを案内して中断する。取得できた一部分からツアーを作らない。

コミット範囲モードでも SHA または diff の取得に失敗した場合は中断する。diff が空の場合も 1 件以上のストップを作れないため、ツアーを書き出さずに中断する。

## 3. サイズを検査する

保存した diff の行数を `wc -l` で数える。10,000 行を超える場合は、diff が大きすぎることを警告し、コミット範囲を複数の小さい範囲へ分割するよう提案して中断する。ストップを省略した不完全なツアーは作らない。

## 4. 変更を依存順へ並べ替える

各ファイルと各 hunk の役割を確認し、次の順序で並べる。

1. 型・データモデル定義
2. コアロジック
3. 呼び出し側・配線
4. テスト
5. 設定・雑務

同じ区分では、依存される変更を依存する変更より前に置く。並べ替えが確定するまで stop ID を付けない。

## 5. hunk をストップ化する

- 原則として unified diff の hunk 1 個をストップ 1 個にする。同じファイルの別 hunk を結合しない。
- hunk ヘッダー `@@ -oldStart[,oldLines] +newStart[,newLines] @@` を読み、`hunk.oldStart`、`hunk.oldLines`、`hunk.newStart`、`hunk.newLines` を有限の数値で埋める。行数が省略されている側は `1` とする。
- `diffText` には、その hunk の `@@` ヘッダーと、その hunk に属するコンテキスト行・削除行・追加行を改変せずに含める。ファイル全体、`diff --git` メタデータ、別 hunk は含めない。
- `file` はリポジトリルートからのパスにする。通常と新規ファイルは `+++ b/<path>`、削除ファイルは `--- a/<path>`、rename は変更後のパスを使い、`/dev/null` は使わない。
- hunk を持たないバイナリ変更、rename-only、mode-only の変更は概要ストップへ畳む。
- 全変更が hunk を持たない場合は、全変更をまとめた概要ストップを 1 件作る。
- 詳細ストップと概要ストップの合計を必ず 1 件以上 20 件以下にする。
- 概要ストップが不要で hunk が 20 個以下なら、各 hunk を詳細ストップにする。
- hunk が 20 個を超える場合、または hunk を持たない変更を加えると 20 件を超える場合は、依存順の先頭から詳細ストップを最大 19 件作り、残りを末尾の概要ストップ 1 件へ畳む。
- 概要ストップには `hunk` と `diffText` を含めない。`what` に、畳んだすべてのファイルパスと各ファイルの変更概要を 1 行ずつ列挙する。`file` には畳んだ先頭ファイルのパスを入れる。
- 並べ替えと畳み込みが確定した後、先頭から `stop-01`、`stop-02` のように 2 桁で連番を付ける。ID は重複させず、最大を `stop-20` とする。

## 6. 各ストップを解説する

各ストップに、すべて空でない文字列として次を記述する。

- `title`: 変更の要点を示す短い見出し。
- `what`: 何を変更しているか。
- `why`: なぜその変更または設計が必要か。diff から確認できる事実と周辺コードに基づいて書き、根拠のない意図を断定しない。
- `ifBroken`: この変更が欠ける、または壊れた場合に起きる問題。

各詳細ストップの `file` にはリポジトリルートからの変更ファイルパスを空でない文字列として入れる。

## 7. tour.json を書き出す

ローカル時刻と `headSha` の先頭 7 文字から、`YYYYMMDD-HHmmss-短縮SHA` 形式の `tourId` を作る。使用できる文字は英数字とハイフンだけにする。

変更全体を表す空でない `title` を付け、次のフィールドを持つ JSON を `.guidepost/tours/<tourId>/tour.json` へ新規に書き出す。

```json
{
  "version": 1,
  "tourId": "YYYYMMDD-HHmmss-abcdef0",
  "title": "変更全体を表すタイトル",
  "baseSha": "完全な base SHA",
  "headSha": "完全な head SHA",
  "source": {
    "type": "range または pr",
    "value": "入力範囲または #付きPR番号"
  },
  "stops": [
    {
      "id": "stop-01",
      "file": "リポジトリルートからのパス",
      "hunk": {
        "oldStart": 1,
        "oldLines": 1,
        "newStart": 1,
        "newLines": 1
      },
      "diffText": "@@ から始まる該当 hunk 単体の unified diff",
      "title": "ストップの見出し",
      "what": "何をしているか",
      "why": "なぜこの設計か",
      "ifBroken": "壊すと何が起きるか"
    }
  ]
}
```

次の条件をすべて確認してから書き出す。

- `version` は数値の `1`。
- `tourId`、`title`、`baseSha`、`headSha` は空でない文字列。
- `source.type` は文字列の `range` または `pr`、`source.value` は空でない文字列。
- `stops` は 1〜20 件。
- 全ストップの `id`、`file`、`title`、`what`、`why`、`ifBroken` は空でない文字列で、ID は `stop-NN` 形式かつ重複なし。
- 詳細ストップは `hunk` の 4 数値と文字列の `diffText` を持つ。
- 概要ストップは `hunk` と `diffText` を持たない。
- JSON として構文エラーがない。

書き出しに失敗した場合は中断し、成功と報告しない。一時 diff は処理終了時に削除する。

ツアー生成後、`.guidepost/` が `.gitignore` に含まれていなければ、追加を推奨する。ただし実際の追記はユーザーの判断に委ね、このスキルでは `.gitignore` を編集しない。

## 8. ビューアを提示する

1. `curl -s -o /dev/null http://127.0.0.1:4870/` で既存サーバーを確認する。
2. 起動済みなら `http://127.0.0.1:4870/` をユーザーへ提示する。
3. 起動していなければ、Bash ツールで `node "${CLAUDE_PLUGIN_ROOT}/scripts/serve.mjs" --dir "$(pwd)"` を `run_in_background: true` で起動する。
4. バックグラウンドコマンドの標準出力から実際の URL を読み、その URL をユーザーへ提示する。ポート番号を推測しない。
5. 起動に失敗した場合、または URL を取得できない場合はその事実を報告し、ビューアを提示できたと報告しない。

## 9. 回答時の作法

`[guidepost]` で始まる注入に含まれる tour、stop、質問、回答先の指定を確認する。

1. 注入で指定された `tour.json` を読む。
2. 指定された stop ID と一致するストップを読み、その `file`、`hunk`、`diffText`、`what`、`why`、`ifBroken` を確認する。
3. 注入された質問へ、そのストップの内容に即して回答する。
4. 注入で指定された回答先パスへ、回答本文を新規ファイルとして書く。親ディレクトリがなければ作成する。
5. 回答先が既に存在する場合は追記も上書きもせず、中断して衝突を報告する。
6. 回答処理では既存の answers ファイルへ追記せず、指定された新規回答ファイル以外の `.guidepost/` 配下を編集しない。
7. tour、stop、質問、回答先の指定が欠けている、対象ストップがない、または指定ファイルを読めない場合は回答ファイルを作らず中断する。
