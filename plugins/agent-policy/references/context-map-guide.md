# context-map 作成ガイド

## context-map とは

セッションの探索成果物。現在の構造・関連モジュール・既存パターン・影響範囲・既存契約・未解決事項・テスト方法を、オーケストレーターが生探索を避けられる小さな状態へ圧縮したもの。
map を小さく(蒸留された状態に)保つことが最優先の規律である。

## 用語

| 用語 | 意味 |
| --- | --- |
| オーケストレーター | セッションを主導し、dispatch・要件確定・承認・最終レビューを行う役割 |
| 所在通知 | dispatch の依頼文や報告に map の**ファイルパスを含める**こと(map 本文ではない) |
| (全文)参照 | **蒸留済み map の全セクションを読む**こと(生コードの全文ではない) |
| 蒸留 | 生探索の結果を、判断に要る最小限へ要約・構造化して map に落とすこと。ダンプの反対 |
| 要約(上流報告) | map の **§未解決事項(とその差分)だけ**をオーケストレーターへの報告に載せること |

## 作成契機

- コードベース探索を伴う設計・実装タスクの着手時のみ作成する。判断基準は「着手前にコードベースを探索して構造・依存・影響範囲を把握する必要があるか」。
- 作成する: 新機能の設計、複数ファイルにまたがる改修、影響範囲が不明な変更。作成しない: 単発質問、typo 級の軽微修正、1 ファイルで完結する定型変更、雑談。
- 同一セッション(1 会話)内の追加タスクは新規作成せず同じファイルを更新する。別セッションは新規ファイルとし、必要なら前回の map を参照する。

## 生産側の規律

- 探索担当が生ファイルを読み、map 作成者が結果を蒸留して map 化する。
- map が大きくなったら、共有先を減らす前に、判断に不要な生データ・重複・長い引用を除いて再蒸留する。
- Serena の探索ツールが使えるときは、シンボルの定義・参照・実装をたどる用途にそれらを使う。
- Grep は自由文字列の検索に充てる。
- Grep でコードを探すときは、ビルド生成物とバンドル出力のディレクトリを対象から外す。
- git worktree に隔離されて作業するときは、Serena の編集ツールを使わず、Edit と Write で書き換える。

## 消費側の読む深さ

| 対象 | 読む深さ |
| --- | --- |
| オーケストレーター | 圧縮された map を読む(= 生探索の代替)。チェックポイントごとの深さは次表に従う |
| 設計担当 | 蒸留済み map の全文を参照。多くは作成者と同一なので追加ロード不要 |
| 実装担当 | map 全体は渡さず、必要セクションの断片のみブリーフに転記 |
| map 作成者 | 自己共有は不要。作成者 ≠ 下流設計者になった場合だけ、次の dispatch にパスを渡す |

## オーケストレーターの3チェックポイント

チェックポイントを明示宣言しない。

| チェックポイント | 主に読むセクション | 深さ |
| --- | --- | --- |
| ① 要件精緻化(map 作成直後) | §未解決事項(最重要)・§既存契約・§影響範囲 | 探索実働が §未解決事項を要約で必ず上げ、作成者が map に統合する。オーケストレーターは要約で判断し、必要なときだけ該当セクションを参照 |
| ② 計画承認(設計書/WBS 完成時。`orchestration-discipline` §設計・実装計画の規律 の Approve と同一の瞬間) | 要約(§未解決事項を前面に) | 所在通知＋オンデマンド全文(承認判断に必要なときだけ map 全文を読む) |
| ③ 最終レビュー | §影響範囲・§既存契約・§未解決事項・§テスト方法 | 能動参照。作業フェーズ最終段の 1 回だけとし、dispatch ごとに繰り返さない |

- 上流へ伝わる本体は §未解決事項である。設計担当が map を更新して未解決事項が動いた場合は、その差分だけを要約(上流報告)で上げ、map 全文を再送しない。

## 実装担当への断片転記例

```markdown
Context-map 所在: `.claude/context-maps/2026-07-20-auth-middleware.md`
参照断片:

- §5 変更の影響範囲: `src/auth/middleware.ts` とログイン統合テストが直接影響。
- §6 守るべき既存契約: 未認証時は HTTP 401 と `{"code":"UNAUTHORIZED"}` を返す。
```

このブリーフだけで担当作業を開始できるようにし、全体構造が必要になった場合だけ map の該当セクションを追加参照させる。

## §未解決事項の差分通知例

直前の上流報告から変わった項目だけを書く。changelog にしない。

```markdown
§未解決事項の差分:

- 解消: #1 既存 API の 401 応答形式は維持することで確定。
- 追加: #4 監査ログ保持期間は最上位オーケストレーターの判断待ち。
```

## 出力先とテンプレート

- 出力先: `.claude/context-maps/YYYY-MM-DD-<タスク名スラッグ>.md`(kebab-case、日付は作成日。同一会話が日をまたいでも最初の作成日を維持)。
- テンプレート: プラグイン同梱の `assets/context-map-template.md` を上記パスへコピーし、各セクション(1〜11)を可能な範囲で埋める。「作成者」欄は map を実際に作ったモデル名を記入する。
- `.claude/context-maps/` を git 追跡するかはプロジェクト判断。追跡したくない場合は `.gitignore` への追記例を案内する(自動で書き換えない)。

## シークレット非記録

context-map に API キー・トークン・パスワードなどの機密情報を記録しない。
リポジトリ固有ポリシー(例: 特定ディレクトリを読まない等)を context-map が上書きしない。
