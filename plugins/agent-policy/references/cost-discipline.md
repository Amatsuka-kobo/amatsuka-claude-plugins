# コスト規律

`agent-policy` の各方針が共有する、サブエージェント運用における入力トークンとオーケストレーターターンを抑制する共通規律である。各方針 Skill と GPT Agent テンプレートはこの文書に従う。

設計根拠の詳細は `docs/design/2026-07-21-agent-policy-cost-discipline-design.md` を参照する。実測では、巨大スキルのロードにより GPT Luna の input が 11.80M、cache_read が 0.73M となり、スキル未ロード時の見込み約 2.5M に対して約 5 倍に増幅した。また、個別 dispatch により Fable の約 26 ターン(約 $52)が発生した。以下の規律はこの実測に基づく。

## スキルロード規律

> サブエージェントは、ブリーフで明示的に指定されたスキル以外を Skill ツールでロードしない。スキル側のトリガー定義(「〜に言及したら必ず読め」等)は、サブエージェントにおいてはブリーフの明示指定に劣後する。

- スキル本文はロード時だけでなく、そのエージェントの以後全ターンで再送される。巨大スキルを無自覚にロードしてはならない。
- 巨大スキルの目安は 10k トークン級以上、または本文が数百行を超えるものとする。迷った場合はロードさせず、オーケストレーターが必要な節だけを確認する。
- 巨大スキルの知識が必要なタスクでは、オーケストレーターが必要断片をブリーフへ転記する。出典(スキル名)と必要な節・手順・制約だけを「参照断片」として区別し、ブリーフが自己完結する最小限に留める。
- サブエージェントが追加スキルの必要性に気づいた場合は、ロードせずその旨を報告して差し戻す。

## 委譲の損益分岐

> 委譲が得なのは、サブ側でしか消化できないターン数が十分多いときだけである。オーケストレーターの 1 ターンは文脈サイズに比例して高価であり、dispatch と受取で最低 2 ターンを消費する。

| 作業の性質 | 正しい配分 |
|---|---|
| 転記(完成形が全指定済み・サブ側の判断ターンほぼゼロ) | オーケストレーターが直接 Write する。複数ファイルは並列ツールコールで 1 ターンにまとめる |
| 探索・反復(サブが自前で多数ターンを消化) | バッチ委譲する。N 件を 1 dispatch に束ね、オーケストレーターの関与を dispatch + 受取の約 2 ターンに固定する |
| 独立した複数 dispatch | 同一ターンに並列で束ねる。逐次 dispatch でターンを分割しない |

- dispatch + 受取のオーケストレーター 2 ターン(実測目安: 約 $4)を、サブ側で置き換わるターンの差額で回収できるかで判断する。
- サブ 1 ターンをオーケストレーター 1 ターンの 1/20〜1/50 のコストとみなす。サブ側で 3 ターン以上の自律作業が見込めるなら委譲し、2 ターン以下の転記級なら直接実行する。境界例は直接実行に倒す。
- 転記級のタスクをタスクごとに個別 dispatch してはならない。

### 検証・コミットの寄せ

サブエージェントに毎タスクの git commit・広域 grep 検証をさせない。バッチの最後にオーケストレーター側、または 1 回の検証専用 dispatch へ寄せる。

### GPT 経路の重み補正

GPT 経路は、現時点ではプロンプトキャッシュがほぼ不成立であり、文脈再送が全額課金される前提で損益分岐を判断する。事件実測では GPT Luna input の 94% が非キャッシュであった。Claude 系経路は cache_read が入力単価の約 1/10 で済むため、同じ判断表を用いつつ損益分岐はこの分だけ緩い。キャッシュ不成立が解消された場合は、この補正と分岐の数値を見直す。

## コスト計測の注意

- `/cost` のドル換算はカスタムエイリアスに対して不正確になりうる。実測では実単価約 $12 に対して $56.15 と表示された。プロキシ経由モデルのコスト判断はトークン数を一次情報とし、実単価は自ら掛ける。
- usage 形式を混同しない。Anthropic 形式は `input_tokens`(非キャッシュ)と `cache_read_input_tokens` が別建てであり、OpenAI 形式は `input_tokens` が全量、`cached_tokens` がその内数である。
- input が数 M あるだけでは異常と断定しない。非キャッシュ input、1 ターンあたりの文脈サイズ、ターン数の 3 点に分解して判断する。

## オーケストレーター文脈軽量化チェックリスト

- セッション開始時に `/context` で常駐カタログ(MCP tools・custom agents・skills・memory)のサイズを把握する。
- 使わない MCP サーバー・プラグインはプロジェクト設定で無効化する。オーケストレーターの 1 ターン単価は文脈サイズに比例する。参考実測では MCP tools 約 15k、custom agents 約 20k、skills 約 5k が常駐していた。
- CLAUDE.md・メモリファイルの肥大を防ぐ。これらは毎ターン再送される。

## GPT 経路でプロンプトキャッシュが効かない原因(調査済み)

2026-07-21 調査完了。CLIProxyAPI の上流リクエストログの実測により、原因は **CLIProxyAPI の Anthropic→Codex(Responses API)変換が、暗号化 reasoning アイテムを会話履歴の先頭付近に注入すること**と特定した。

- プロキシは `prompt_cache_key` と `session_id` を安定して送出しており、継続性キーは壊れていない(既知 issue #2373 の症状とは別)。
- しかし変換後の `input` 配列では、直前応答の `reasoning`(`encrypted_content`)が履歴の**2番目**(luna 実測)に置かれ、この暗号化ブロブは**ターンごとに内容が変わる**。OpenAI のプレフィックスキャッシュは先頭からの完全一致で効くため、キャッシュ可能なプレフィックスが「システムプロンプト+ツール定義の途中」(実測 cached_tokens 2,560〜24,576)で頭打ちになり、会話履歴の大部分(94%)が毎ターン全額課金で再送される。
- Claude 系経路はこの変換を通らないため正常にキャッシュされる(対照実測: Haiku cache_read 25.3M / input 0.03M)。

対処の選択肢(いずれも本プラグインの外):

1. CLIProxyAPI のアップデートを追う(reasoning 注入位置の改善や continuity 修正 PR の後継が入る可能性)。
2. プロキシの `codex-reasoning-replay` 相当の挙動を無効化できる設定があるか、使用中のバージョンで確認する(reasoning を注入しなければプレフィックスが安定するが、推論品質とのトレードオフになりうる)。

解消が確認できたら「GPT 経路の重み補正」(約10倍重い前提)と委譲の損益分岐の数値を見直す。それまでは現行規律をそのまま適用する。
