# オーケストレーション共通規律

この文書の読者はオーケストレーターである。「サブエージェントは〜」で始まる条項は、依頼文への転記と、生成した定義の本文でサブエージェントへ届ける。

以下で「担当表」とは、読み込んだ方針の §モデル別役割 の表を指す。帯の名前は担当表の行名で参照する。

## モデル別役割の運用

- 各モデルは担当表に従い、その役割タスクのみを担当する。
- 複数コンポーネントにまたがる実装、または非自明な設計判断を含む実装は「複雑または重要な実装」とする。
- 単一コンポーネントに閉じ、設計判断を伴わない実装は「通常の実装」とする。
- 既存パターンの機械的な反復・一括適用は「軽量な実装」とする。
- サブエージェントを起動するとき、対象に「あなたはサブエージェントである」ことを明示する。
- オーケストレーターは、複数の context-map・設計書・実装差分・並列サブエージェントの全レポートを分割せず一度に読んで突き合わせる。要約の要約では判断しない。
- オーケストレーターは、独立したタスクが複数あるとき、それらを 1 メッセージ内で可能な限り並列に dispatch する。
- オーケストレーターは、担当表の「軽量な実装」と「設計・計画・実装のアドバイザー」の帯以外のサブエージェントに Agent Tool を許可する。
- オーケストレーターは、サブエージェントに方針スキルをロードさせない。必要な規律は依頼文へ転記する。
- サブエージェントは、アドバイザーとして相談する相手を、役割マーカーの対応表にある「設計・計画・実装のアドバイザー」の帯の定義にする。対応表に無いときは `Fable` にし、`Fable` が利用できないときは `Opus` にする。
- サブエージェントは、Agent Tool が許可されていないときの迷いを、相談ではなく差し戻しで解決する。
- サブエージェントは、自身が起動したアドバイザーサブエージェントに Agent Tool を許可せず、依頼文に「助言のみを返し、作業はしない」と明記する。
- サブエージェントは、依頼文で指定されたスキルだけをロードする。方針スキルも、指定が無ければロードしない。
- サブエージェントは、スキルの指定がなければどのスキルもロードせず、依頼文の記述だけで作業する。
- SessionStart フックが役割マーカーの対応表を注入したときは、その帯の委譲先を担当表より優先してその定義とする。同じ帯に複数あるときは依頼内容に近いものを選ぶ。

## 委譲先の実行モデルの確定

Agent を名指しで dispatch するたびに、起動形態を次の 3 種から選ぶ。帯に対して委譲先を選ぶ役割ベースの dispatch にはこの節を当てず、方針の「実行帯の解決順」に従って実務タスクの着手前に一度だけ確定させる。

- そのまま起動 — `subagent_type`・モデル・tools のいずれにも触れない。
- モデル注入起動 — `subagent_type`・tools・本文を元定義のまま使い、`model` param だけを注入する。注入するのは `model` 未宣言・`inherit` の定義に対する帯モデルであり、帯モデルが Claude 以外のときは担当表の同じ帯の Claude モデルへ読み替える。
- 合成 — 帯の定義をホストとして `subagent_type` に指定し、外部定義の本文を依頼文へ同梱する。

上から順に評価し、最初に該当した行で確定する。

| 順 | 条件 | 起動形態 |
| --- | --- | --- |
| 1 | フックの注入文が `subagent_type` や起動様式を指定している | そのまま起動 |
| 2 | 原本定義を特定できない | そのまま起動 |
| 3 | frontmatter が `name` / `description` / `model` / `tools` / `color` / `agent-policy-role` 以外のフィールドを持つ、または本文が `${CLAUDE_PLUGIN_ROOT}` などの展開値に依存する | そのまま起動 |
| 4 | `model` 宣言が `sonnet` / `opus` / `haiku` / `fable` のどれでもない | そのまま起動 |
| 5 | 作業種別が合成対象の帯に合致しない | そのまま起動 |
| 6 | 帯に対応表の定義が無い、外部定義固有の MCP tool が作業の本体で未付与、または外部本文の義務条項がホスト本文の禁止条項と衝突する | モデル注入起動 |
| 7 | 上記以外で `model` が未宣言・`inherit` | 合成する。モデルはホストの frontmatter に従う |
| 8 | 上記以外で `model` が enum で宣言されている | 合成し、`model` param で宣言値を適用する |

合成の対象とする帯は、「複雑または重要な実装」「通常の実装」「軽量な実装」「コードベース探索実働」「リアルタイム情報調査」「設計書・実装計画書の独立レビュー」「設計書・実装計画書のレビュー」「コードレビュー」「設計・計画・実装のアドバイザー」の 9 帯とする。「その他のタスク」と、担当表に帯を持たない作業(調査・分析、設計書・実装計画書の作成、コードベース探索統括)は合成しない。

判定に迷ったときは合成せず、より上の行へ倒す。

### 原本の確認

- 委譲先の原本は、プロジェクトの `.claude/agents/` → ユーザーの `~/.claude/agents/` → プラグイン実体の `agents/` の順で探す。
- dispatch に使われる実体と同一の定義を読めた確証が無いときは、そのまま起動する。
- 確認は原本に対して行い、複製・改変版は作らない。
- ビルトイン Agents(`Explore` / `Plan` / `general-purpose` 等)は `model` 未宣言として扱う。
- ビルトイン Agents は本文を読めないため合成せず、帯が定まるならモデル注入起動にする。

### 合成の手順

- ホストは、役割マーカーの対応表でその帯に解決された定義から選ぶ。同じ帯に複数あるときは依頼内容に近いものを選ぶ。
- 同梱プリセットはプロジェクト最適化を持たないため、ホストに使わない。
- 依頼文の冒頭で、ホストが担う役割名を明示する。
- 外部定義の本文(frontmatter より後の全文)を、その作業の役割定義として依頼文へ同梱する。
- 外部本文の禁止条項・制約条項がホスト本文の同種規定より優先することを、依頼文に明記する。
- 外部本文の義務条項がホスト本文の禁止条項と衝突するときは、合成せずモデル注入起動にする。

### 合成したときの tools

- built-in の tools は外部定義の tools を上限とし、外部定義に無い `Write` / `Edit` / `Bash` は使わない。
- ホスト frontmatter の `mcp__*` は、外部定義の tools に無くても使う。
- 外部本文が明示的に禁じる操作は、`mcp__*` の規則より優先して行わない。
- 読み取りの帯で合成するときは、依頼文に「ファイルを変更しない」「報告のみを返す」を重ねる。

### 外部定義固有の MCP tool

外部定義の固有 MCP tool が作業の本体であるときは、次の順で扱う。

1. ホスト定義へその MCP サーバーを許可することをユーザーへ提案する。提案文には、付与が永続の変更であること、サーバー単位の許可は外部定義のツール単位 allowlist より広くなること、付与に使う CLI へ既存の MCP サーバーを含めた全集合を渡さないと既存分が脱落することを書く。
2. 付与を dispatch の副作用として自分で実行しない。
3. 付与が行われないときは、モデル注入起動にする。

## コードベース探索

- ファイル探索・コードベース探索が必要なときだけ、この文書と同じディレクトリの `context-map-guide.md` を読み、これに従う。
- コードベース探索は担当表の「コードベース探索統括」の帯が統括する。grep/read の反復など短命な探索実働は、担当表の「コードベース探索実働」の帯へバッチ委譲する。
- context-map の執筆・§未解決事項の判断・要件確定への接続は、担当表の「コードベース探索統括」の帯が行う。
- 作成した context-map の所在(パス)は、次の dispatch または上流報告で必ず通知する。

## コスト規律

- 委譲先にロードさせるスキルは、`wc -c` で本文と参照文書の合計を測る。30KB を超えるものは、指定があってもロードさせず、必要な節・手順・制約だけを参照断片として依頼文へ転記する。
- サブエージェントに毎タスクの git commit・広域 grep 検証はさせない。バッチの最後にオーケストレーター側で行うか、1 回の検証専用 dispatch へ寄せる。

## 設計・実装計画の規律

- コードベース探索を伴う設計・実装は、context-map の作成後に着手する。
- 出力した設計書・実装計画書は、まず担当表の「設計書・実装計画書のレビュー」の帯にレビュー(理解+暗黙知・矛盾抽出)させ、オーケストレーターが補足修正を加える。
- 補足修正を終えた設計書・実装計画書は、ユーザーへ提示して承認を得る。
- オーケストレーターの Approve(計画が全体要件を満たすことの確認)はユーザー承認の後に置く。Approve を経てから実装へ移行する。
