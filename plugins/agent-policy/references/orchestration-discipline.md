# オーケストレーション共通規律


## 担当表

| 役割名                                   | RoleId                  | 種別       | Claude モデル | effort    |
| ---------------------------------------- | ----------------------- | ---------- | ------------- | --------- |
| 複雑または重要な実装                     | `complex-impl`          | `impl`     | `Opus`        | `medium`  |
| 通常の実装                               | `normal-impl`           | `impl`     | `Sonnet`      | `medium`  |
| 軽量な実装                               | `light-impl`            | `impl`     | `Haiku`       | `medium`  |
| 行き詰まり時のエスカレーション           | `escalation`            | `impl`     | `Fable`       | `high`    |
| その他のタスク                           | `general`               | `impl`     | `Sonnet`      | `medium`  |
| コードベース探索                         | `explore`               | `readonly` | `Sonnet`      | `high`    |
| リアルタイム情報調査                     | `realtime-research`     | `readonly` | `Sonnet`      | `high`    |
| E2E 動作検証・ブラウザ/GUI 操作          | `e2e-verify`            | `impl`     | `Sonnet`      | `high`    |
| 設計書・実装計画書のレビュー             | `design-review`         | `readonly` | `Opus`        | `high`    |
| 暗黙知の抽出・理解レビュー               | `knowledge-elicitation` | `readonly` | `Haiku`       | `low`     |
| コードレビュー                           | `code-review`           | `readonly` | `Sonnet`      | `high`    |
| 重要な実装・高リスク設計書の最終レビュー | `complex-review`        | `readonly` | `Fable`       | `high`    |
| 敵対的レビュー                           | `adversarial-review`    | `readonly` | `Opus`        | `high`    |

- 「RoleId」は Agent 定義の `agent-policy-role` マーカーに書く値であり、役割マーカーの対応表の各行にも `[general]` の形で載る。担当表の行と対応表の行は RoleId で対応づく。
- 「種別」は `impl` が成果物ファイルを書く役割、`readonly` が読み取りと報告だけの役割である。
- 「Claude モデル」は、その役割を Claude のモデルだけで実行するときのモデルである。`claude-model-policy` の運用では役割モデルそのものであり、`custom-policy` の運用では委譲先が決まらない役割の読み替え先である。
- 「effort」は、その役割を「Claude モデル」列のモデルで実行するときの effort である。

## 委譲先の解決

### 委譲先の候補

- 委譲先の候補は、プロジェクトの `.claude/agents/` にある Agent 定義のうち、`model` が Claude のモデルで実行されるものである。`model` が `sonnet` / `opus` / `haiku` / `fable` のいずれか、`inherit`、または未宣言の定義が該当する。`agent-policy-vendor` は未宣言・`claude`・`none` のいずれかであることを要する。
- custom 構成では、これに加えて外部ベンダーのモデルを指定した定義も候補に含める。どちらの構成かは、役割マーカーの対応表の 2 行目が示す。
- 候補の範囲は、対応表にある役割にも、対応表に無い役割にも、同じように当てる。
- 候補に入らない定義は、役割に対する委譲先として選ばない。名指しで起動するよう指示されたときだけ使う。
- ユーザーの `~/.claude/agents/` と、他プラグインが同梱する定義は候補に含めない。

### 解決順

上から順に評価し、最初に該当した行で確定する。claude と custom のどちらの構成でも同じである。

| 優先順位 | 条件                                                                 | 委譲先                                                                                                |
| --- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 1   | 役割マーカーの対応表にその役割がある                                 | その役割の候補集合。集合内の選び方は §同じ役割の候補から選ぶ に従う                                            |
| 2   | 対応表に無く、候補のうちに担当範囲が合うものがある                   | その定義。`description` と本文が示す担当範囲に、委譲する作業が含まれるものを選ぶ。複数あるときは担当範囲が最も狭いものを選ぶ |
| 3   | 上記のいずれにも該当しない                                           | ビルトイン Agents。担当表の「種別」が `readonly` の役割は `Explore`、`impl` の役割は `general-purpose`  |

- 実務タスクへ着手する前に、役割ごとの委譲先(対応表にある役割では候補集合)を一度確定し、以後タスクごとに確定し直さない。候補集合から 1 件を選ぶことと、その起動形態を決めることは、委譲のたびに行う。
- 表の 1 行目と 2 行目に該当があるかぎりビルトインへ委譲しない。例外は §同じ役割の候補から選ぶ のステップ 4 だけである。
- 委譲先の `model` の扱いは §委譲先の実行モデルの確定 に従う。
- 名指しで Agent を起動するときはこの節を当てず、§委譲先の実行モデルの確定 に従う。

### 同じ役割の候補から選ぶ

役割マーカーの対応表で、1 つの役割に 2 件以上の定義があるときに当てる。1 件のときはその定義へ委譲する。

委譲のたびに、上から順に評価し、最初に該当したステップで確定する。

1. 同じ役割の特化定義のうち、担当に作業が含まれるもの。複数当たるときは担当範囲が最も狭いものを選ぶ。
2. 同じ役割の汎用定義。複数あるときは対応表で先に載っているものを選ぶ。
3. 「その他のタスク」の役割。その役割の候補に、件数を問わずこの節のステップ 1 とステップ 2 を当てる。
4. ビルトイン Agents。元の役割の種別が `readonly` なら `Explore`、`impl` なら `general-purpose` とする。

- 特化定義は、`description` か本文が担当をディレクトリ・技術領域・機能領域のいずれかに限っている定義である。
- 汎用定義は、その限定が無い定義である。
- 「その他のタスク」の役割そのものへ委譲するときは、ステップ 3 を飛ばす。
- ステップ 3 は種別を問わず当てる。
- ステップ 3 で回した作業は、起動形態の判定でも「その他のタスク」の役割として扱う。
- 元の役割の種別が `readonly` で、ステップ 3 の委譲先が `Write` / `Edit` を持つときは、§モデル別役割の運用 の `readonly` の明記を依頼文に入れる。
- ステップ 4 のビルトインへ注入するモデルは、担当表の「Claude モデル」列で元の役割に当たる値とする。

### ビルトイン Agents へ委譲するとき

§解決順 の 3 行目、または §同じ役割の候補から選ぶ のステップ 4 でビルトイン Agents へ委譲するときは、元の役割の役割断片の本文(frontmatter より後の全文)を、その作業の役割定義として依頼文へ転記する。

- 役割断片は、プロジェクトの `.claude/agent-policy/roles/<RoleId>.md` があればそれを使い、無ければこの文書から見て `../assets/roles/<言語>/<RoleId>.md` を使う。
- `<言語>` は、会話の使用言語が日本語なら `ja`、それ以外なら `en` とする。
- Agent tool の `effort` param に、担当表の「effort」列で元の役割に当たる値を指定する。

## オーケストレーターが自ら担う作業

オーケストレーターはサブエージェントの起動・要件確定・採否判断・承認・分析を担う。ファイルとして残す文書は自分で書いてよい。担当表の全役割はサブエージェントが担い、オーケストレーターはそのどれも自ら実行しない。コマンドで起動したスキルの手順(スキル駆動のワークフロー)がこの規律のオーケストレーター条項と衝突するときは、ワークフローの手順を優先する。

### 分析

分析は次の3つを含む。実働(読む・探す・再現する)はサブエージェントへ委譲してよいが、結論と判断はオーケストレーターが出す。

- 報告の突き合わせ・判断。複数の設計書・レビュー・実装差分・並列サブエージェントの全レポートを分割せず一度に読んで突き合わせ、採否と要件を決める。要約の要約では判断しない。
- 要件分析。ユーザーの要望を要件と受け入れ基準へ落とす。
- 原因分析・調査。バグの原因究明・現状把握など「調べて結論を出す」作業。実働は「コードベース探索」などの役割へ委譲し、「その他のタスク」の役割へ丸投げしない。

レビューの指摘が対立し採否の軸を自分で言葉にできないとき、または要件確定で選択肢が複数あり判断軸を立てられないときは、`AskUserQuestion` でユーザーへ選択肢を示して質問する。

### 文書の執筆を委譲するとき

- 文書の執筆を委譲する依頼文に載せる内容は、オーケストレーターが決めて渡す。
- 文書の執筆を委譲する依頼文には、対象ファイルのパス・事実・決定事項・制約・受け入れ基準・章立て・用語・参照先のパスだけを、箇条書き・表・キーワードの形で書く。
- 文書の執筆を委譲する依頼文には、対象ファイルの文体で書かれた段落や、そのまま貼り付けられる完成文を載せない。
- 文書の執筆を委譲する依頼文では、成果物の本文に載せる語や文の例にだけ「本文に載せる」と添える。
- 文書の執筆を委譲する依頼文で成果物の本文に載せる例を示すときは、成果物で閉じた列挙にしないことを明記する。
- AI が読む文書の項目を書き換える依頼には、判断の軸を書く。軸だけで伝わらないときだけ例を添える。判断の軸を言葉にできないときは、委譲しない。
- 要件分析と報告の突き合わせの成果(要件と受け入れ基準の箇条書き、判断のメモ)は、文書の執筆を委譲する依頼文に書くものであり、ファイルとして残す文書ではない。この規律の対象外である。

## モデル別役割の運用

- 各モデルは担当表に従い、その役割タスクのみを担当する。
- `escalation`・`complex-impl`・`normal-impl`・`light-impl` の4役割への振り分けは、次の5軸で判断する。
  - 仕様確定度: 何を作るかが明確か
  - 設計新規性: 新しい設計判断が要るか
  - 変更影響度: 失敗したときの影響範囲
  - 検証困難度: テストなどで正解を容易に判定できるか
  - 分解可能性: 難しい判断の部分と単純な実装の部分を分けられるか
- 4役割の条件を上から順に評価し、最初に該当した役割へ委譲する。
- 各役割は、列挙した条件のいずれか1つに当たれば該当する。
- 変更量(コンポーネント数、公開インターフェース変更の有無)は条件に使わない。

- `escalation`: 原因不明 / 前提崩壊 / 再設計 / 行き詰まりの解消。
- `complex-impl`: 非自明な設計判断 / 複雑または曖昧な仕様 / 検証困難。
- `normal-impl`: 仕様と設計が済んだ大半の実装 / テスト作成。
- `light-impl`: 定型変更 / 一括変更 / 明確な小変更 / 機械的に検証できる。

- 分解できる作業は、難しい判断の部分を `complex-impl` へ、単純な部分を `normal-impl` または `light-impl` へ分けて委譲する。
- 分けるのは、判断部分の成果を型・関数シグネチャ・ファイル配置・変更箇所の列挙などの形で文書に固定でき、下位の役割が追加の判断なしに実装できるときだけとする。
- 分けるときは判断部分を先に完了させ、その成果を下位の役割の依頼文に渡す。
- 成果を固定できないとき、または分割で委譲の回数が増えて効果に見合わないときは、分けずに全体を `complex-impl` に任せる。
- 変更影響度だけでは役割を決めず、検証困難度と組み合わせる。
- 影響が広く、失敗を機械的に検出できない作業は `complex-impl` へ寄せる。影響が広くても機械的に検証できる作業は、役割を上げない。
- 「機械的に検証できる」根拠(変更する全箇所の正誤を、どの型検査・テスト・lint・grep が判定するか)は、着手前の「コードベース探索」の依頼に含めて調べさせる。根拠を示せなければ検証困難として扱う。
- 実装役割への依頼文には、完了報告に変更した各箇所を判定した検査とその結果を添えるよう書く。
- 全セッションに作用する設定(hooks など)・保護パス・データ移行は、検証の可否にかかわらず `light-impl` へ委譲しない。
- `light-impl` または `normal-impl` から差し戻された作業と、完了報告に検査結果を添えられない箇所がある作業は、`complex-impl` へ再委譲する。
- `complex-impl` でも解けない作業は `escalation` へ委譲する。

- `escalation` の条件に当たったら、オーケストレーターは自分で原因を追わず `escalation` へ委譲する。
- 依頼文には試行履歴(誰に何を頼み、何が返ったか)・失敗出力の原文・未解決の制約を載せる。
- 初回の作業は `escalation` へ委譲しない。
- サブエージェントを起動するとき、対象に「あなたはサブエージェントである」ことを明示する。
- 独立したタスクが複数あるとき、それらを並列に起動する。
- サブエージェントに Agent Tool を許可しない。
- 委譲の依頼文の冒頭で、その委譲が担う役割を明示する。
- その役割の Output Format を依頼文で指定する。
- 担当表の「種別」が `readonly` の役割を `Write` / `Edit` を持つ定義へ委譲するとき、依頼文に次を明記する。合成して起動するときも同じである。
  - 使用してよい tools を読み取り系に限定すること(`Read` / `Grep` / `Glob`、読み取りに限った `Bash`、依頼に調査が含まれるときは `WebSearch` / `WebFetch`)
  - ファイルを変更しないこと
  - 報告のみを返すこと
- サブエージェントを起動するとき、この文書の「サブエージェントは〜」で始まる条項をすべて依頼文へ転記する。
- SessionStart が custom から claude へのフォールバックを通知したとき、依頼文に「役割マーカーの対応表のうち、外部ベンダーのモデルを指定した定義は委譲先にしない」と明記する。

### サブエージェントの規律

- サブエージェントは、依頼文に無い判断が必要で選択肢が複数あり選択により成果物の構造(インターフェース・ファイル配置・依存関係)が変わるとき、依頼文と実コードの食い違いを依頼文から解決できないとき、またはテスト・型検査の失敗を再現しても複数の原因候補を 1 つに絞れないときに、作業を止めて差し戻す。
- サブエージェントは、依頼文に書かれた事項を依頼文から確認する。
- サブエージェントは、Read・Grep で確かめられる事実を自分で確かめる。
- サブエージェントは、命名・表記・並び順を既存パターンに合わせる。
- サブエージェントは、作業範囲の拡大が要る判断を差し戻す。
- サブエージェントは、依頼文で指定されたスキルだけをロードする。指定が無ければ、方針スキルを含めどのスキルもロードせず、依頼文の記述だけで作業する。
- サブエージェントは、依頼文にある語や文の例のうち「本文に載せる」と添えられていないものを、依頼の説明として扱う。成果物の本文には書かず、自分で選んだ言葉を書く。
- サブエージェントは、「本文に載せる」と添えられた例を成果物へ書くとき、閉じた列挙にせず、判断の軸とともに書く。

## 委譲先の実行モデルの確定

Agent を名指しで起動するたびに、起動形態を次の 3 種から選ぶ。

- そのまま起動 — `subagent_type`・モデル・tools のいずれにも触れない。
- モデル注入起動 — `subagent_type`・tools・本文を元定義のまま使い、`model` param だけを注入する。注入するのは `model` 未宣言・`inherit` の定義に対する役割モデルである。`claude-model-policy` の運用では、役割モデルは担当表の「Claude モデル」列である。`custom-policy` の運用では、役割モデルは §同じ役割の候補から選ぶ でそのタスクに選んだ定義の `model` である。委譲先がビルトインのときは、担当表の「Claude モデル」列で元の役割に当たる値とする。役割モデルが Claude 以外のときは、担当表の「Claude モデル」列へ読み替える。
- 合成 — 役割の定義をホストとして `subagent_type` に指定し、外部定義の本文を依頼文へ同梱する。

上から順に評価し、最初に該当した行で確定する。

| 優先順位 | 条件                                                                                                                                                                                                  | 起動形態                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 1   | フックの注入文が `subagent_type` や起動様式を指定している                                                                                                                                             | そのまま起動                                  |
| 2   | 原本定義を特定できない、または dispatch に使われる実体と同一の定義を読めた確証が無い                                                                                                                  | そのまま起動                                  |
| 3   | frontmatter が `name` / `description` / `model` / `tools` / `color` / `agent-policy-role` / `agent-policy-vendor` / `agent-policy-description-hash` / `agent-policy-preamble-hash` / `effort` 以外のフィールドを持つ、または本文が `${CLAUDE_PLUGIN_ROOT}` などの展開値に依存する | そのまま起動                                  |
| 4   | `model` 宣言が `sonnet` / `opus` / `haiku` / `fable` のどれでもない                                                                                                                                   | そのまま起動                                  |
| 5   | 作業種別が合成対象の役割に合致しない                                                                                                                                                                  | そのまま起動                                  |
| 6   | 役割に対応表の定義が無い、外部定義固有の MCP tool が作業の本体で未付与、または外部本文の義務条項がホスト本文の禁止条項と衝突する                                                                      | モデル注入起動                                |
| 7   | 上記以外で `model` が未宣言・`inherit`                                                                                                                                                                | 合成する。モデルはホストの frontmatter に従う |
| 8   | 上記以外で `model` が enum で宣言されている                                                                                                                                                           | 合成し、`model` param で宣言値を適用する      |

合成の対象とする役割は、担当表のうち「その他のタスク」を除く全役割とする。

判定に迷ったときは合成せず、より上の行へ倒す。

### 原本の確認

- 委譲先の原本は、プロジェクトの `.claude/agents/` → ユーザーの `~/.claude/agents/` → Agent 定義を同梱する他プラグインの実体にある `agents/` の順で探す。このプラグインは Agent 定義を同梱しない。
- 確認は原本に対して行い、複製・改変版は作らない。
- ビルトイン Agents(`Explore` / `Plan` / `general-purpose` 等)は `model` 未宣言として扱う。
- ビルトイン Agents は本文を読めないため合成せず、役割が定まるならモデル注入起動にする。

### 合成の手順

- ホストは、§同じ役割の候補から選ぶ でそのタスクに選んだ定義とする。
- プラグインが同梱する汎用定義はプロジェクト最適化を持たないため、ホストに使わない。
- 依頼文の冒頭で、ホストが担う役割名を明示する。
- 外部定義の本文(frontmatter より後の全文)を、その作業の役割定義として依頼文へ同梱する。
- 外部本文の禁止条項・制約条項がホスト本文の同種規定より優先することを、依頼文に明記する。

### 合成したときの tools

- built-in の tools は外部定義の tools を上限とし、外部定義に無い `Write` / `Edit` / `Bash` は使わない。
- ホスト frontmatter の `mcp__*` は、外部定義の tools に無くても使う。
- 外部本文が明示的に禁じる操作は、`mcp__*` の規則より優先して行わない。

### 外部定義固有の MCP tool

外部定義の固有 MCP tool が作業の本体であるときは、次の順で扱う。

1. ホスト定義へその MCP サーバーを許可することをユーザーへ提案する。提案文には、付与が永続の変更であること、サーバー単位の許可は外部定義のツール単位 allowlist より広くなること、付与に使う CLI へ既存の MCP サーバーを含めた全集合を渡さないと既存分が脱落することを書く。
2. 付与を dispatch の副作用として自分で実行しない。
3. 付与が行われないときは、モデル注入起動にする。

## コードベース探索

- コードベース探索は担当表の「コードベース探索」の役割へ委譲する。
- grep/read の反復が 3 ターン以上見込まれる探索は、1 回の dispatch にまとめる。

## コスト規律

- 委譲先にロードさせるスキルは、`wc -c` で本文と参照文書の合計を測る。30KB を超えるものは、指定があってもロードさせず、必要な節・手順・制約だけを参照断片として依頼文へ転記する。
- サブエージェントに毎タスクの git commit・広域 grep 検証はさせない。バッチの最後にオーケストレーター側で行うか、1 回の検証専用 dispatch へ寄せる。

## 設計・実装計画の規律

- 設計書・実装計画書は、探索で確定した事実(パス・行番号・現況)と、確定した要件・受け入れ基準を踏まえてオーケストレーターが書く。
- 出力された設計書・実装計画書は、まず担当表の「暗黙知の抽出・理解レビュー」の役割にレビュー(理解+暗黙知・矛盾抽出)させる。
- 続いて担当表の「設計書・実装計画書のレビュー」の役割へ、原本のみを渡して dispatch する。他のレビューの指摘は渡さない。依頼文に「反証の提示までを担い、採否はオーケストレーターが判断する」と明記する。この役割の委譲先の解決は §委譲先の解決 に従う。
- オーケストレーターが両レビューの指摘の採否を判断し、補足修正を加えてからユーザーへ提示して承認を得る。
- オーケストレーターの Approve(計画が全体要件を満たすことの確認)はユーザー承認の後に置く。Approve を経てから実装へ移行する。
