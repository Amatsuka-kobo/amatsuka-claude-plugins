# オーケストレーション共通規律


## 担当表

| 役割名                           | RoleId               | 種別       | Agent Tool | Claude モデル |
| -------------------------------- | -------------------- | ---------- | ---------- | ------------- |
| 複雑または重要な実装             | `complex-impl`       | `impl`     | 可         | `Opus`        |
| 通常の実装                       | `normal-impl`        | `impl`     | 可         | `Sonnet`      |

- 「RoleId」は Agent 定義の `agent-policy-role` マーカーに書く値であり、役割マーカーの対応表の各行にも `[general]` の形で載る。担当表の行と対応表の行は RoleId で対応づく。
- 「種別」は `impl` が成果物ファイルを書く役割、`readonly` が読み取りと報告だけの役割である。
- 「Agent Tool」は、その役割として起動したサブエージェントに Agent Tool を許可してよいかである。
- 「Claude モデル」は、その役割を Claude のモデルだけで実行するときのモデルである。`claude-model-policy` の運用では役割モデルそのものであり、`custom-policy` の運用では委譲先が決まらない役割の読み替え先である。

## 委譲先の解決

### 委譲先の候補

- 委譲先の候補は、プロジェクトの `.claude/agents/` にある Agent 定義のうち、`model` が Claude のモデルで実行されるものである。`model` が `sonnet` / `opus` / `haiku` / `fable` のいずれか、`inherit`、または未宣言の定義が該当する。`agent-policy-vendor` は未宣言・`claude`・`none` のいずれかであることを要する。
- custom 構成では、これに加えて外部ベンダーのモデルを指定した定義も候補に含める。どちらの構成かは、役割マーカーの対応表の 2 行目が示す。
- 候補の範囲は、対応表にある役割にも、対応表に無い役割にも、同じように当てる。
- 候補に入らない定義は、役割に対する委譲先として選ばない。名指しで起動するよう指示されたときだけ使う。
- ユーザーの `~/.claude/agents/` と、他プラグインが同梱する定義は候補に含めない。

### 解決順

上から順に評価し、最初に該当した行で確定する。claude と custom のどちらの構成でも同じである。

| 順  | 条件                                                                 | 委譲先                                                                                                |
| --- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 1   | 役割マーカーの対応表にその役割がある                                 | その定義。同じ役割に複数あるときは依頼内容に近いものを選ぶ                                            |
| 2   | 対応表に無く、候補のうちに担当範囲が合うものがある                   | その定義。`description` と本文が示す担当範囲に、委譲する作業が含まれるものを選ぶ。複数あるときは依頼内容に近いものを選ぶ |
| 3   | 上記のいずれにも該当しない                                           | ビルトイン Agents。担当表の「種別」が `readonly` の役割は `Explore`、`impl` の役割は `general-purpose`  |

- 実務タスクへ着手する前に一度確定し、以後はタスクごとに再判定しない。
- ビルトインは最後の受け皿である。順 1 と順 2 に該当があるかぎりビルトインへ委譲しない。
- 委譲先の `model` の扱いは §委譲先の実行モデルの確定 に従う。
- 名指しで Agent を起動するときはこの節を当てず、§委譲先の実行モデルの確定 に従う。
- 「設計書・実装計画書の独立レビュー」の役割は順 2 と順 3 へ進めず、対応表に無ければ独立レビューを省略する。他の役割で代行しない。同じベンダーのモデルによるレビューは独立性を持たないためである。

## オーケストレーターが自ら担う作業

オーケストレーターはサブエージェントの起動・要件確定・採否判断・承認・分析を担う。ファイルとして残す文書は自分で書いてよい。担当表の全役割はサブエージェントが担い、オーケストレーターはそのどれも自ら実行しない。

- コマンドで起動したスキルの手順(スキル駆動のワークフロー)がこの規律のオーケストレーター条項と衝突するときは、ワークフローの手順を優先する。

### 分析

分析は次の3つを含む。実働(読む・探す・再現する)はサブエージェントへ委譲してよいが、結論と判断はオーケストレーターが出す。分析全体を1つの役割へ渡して結論まで受け取ることはしない。

- 報告の突き合わせ・判断。複数の設計書・レビュー・実装差分・並列サブエージェントの全レポートを分割せず一度に読んで突き合わせ、採否と要件を決める。要約の要約では判断しない。
- 要件分析。ユーザーの要望を要件と受け入れ基準へ落とす。
- 原因分析・調査。バグの原因究明・現状把握など「調べて結論を出す」作業。grep/read の反復や再現の実働は「コードベース探索」などの役割へ委譲してよいが、結論はオーケストレーターが出す。「その他のタスク」の役割へ丸投げしない。

### 文書の執筆

- 使用する言語の文脈と文法に従い、訳語が文脈に合うか確かめる。
- 簡潔でわかりやすい文章にし、難しい言い回しや回りくどい表現を避ける。
- 引用と出典は必要な分に絞り、読み手を混乱させる背景や根拠を加えない。
- 英語以外で書くときは直訳せず、対象言語の慣用に合わせて意訳する。日本語では文脈に応じて次のように言い換える。
  - Version は単に「版」とせず、「確定版」「新しいバージョン」などから選ぶ。
  - テスト結果の Green / Red は「緑」「赤」とせず、「パス」「失敗」と書く。
  - Frozen Document は「凍結文書」とせず、「確定版の文書」と書く。
  - Ledger は用途に応じて「一覧」「管理表」「ログ」と書き分ける。
  - Step は「段」とせず、「Step」または「ステップ」と書く。

### 文書の執筆を委譲するとき

- 文書の執筆を委譲する依頼文には、確定した内容・対象ファイルのパス・参照すべき既存文書を渡す。内容の決定はオーケストレーターが担う。
- 文書の執筆を委譲する依頼文には、事実・決定事項・制約・受け入れ基準・章立て・用語・参照先のパスだけを、箇条書き・表・キーワードの形で書く。
- 文書の執筆を委譲する依頼文には、対象ファイルの文体で書かれた段落や、そのまま貼り付けられる完成文を載せない。
- 文書の執筆を委譲する依頼文では、成果物の本文に載せる語や文の例にだけ「本文に載せる」と添える。
- 文書の執筆を委譲する依頼文で成果物の本文に載せる例を示すときは、成果物で閉じた列挙にしないことを明記する。
- AI が読む文書の項目を書き換える依頼には、判断の軸を書く。軸だけで伝わらないときだけ例を添える。判断の軸を言葉にできないときは、委譲しない。
- 要件分析と報告の突き合わせの成果(要件と受け入れ基準の箇条書き、判断のメモ)は、文書の執筆を委譲する依頼文に書くものであり、ファイルとして残す文書ではない。この規律の対象外である。

## モデル別役割の運用

- 各モデルは担当表に従い、その役割タスクのみを担当する。
- 複数コンポーネントにまたがる実装、または非自明な設計判断を含む実装は「複雑または重要な実装」とする。
- 単一コンポーネントが対象で、設計判断を伴わない実装は「通常の実装」とする。
- 既存パターンの機械的な反復・一括適用は「軽量な実装」とする。
- サブエージェントを起動するとき、対象に「あなたはサブエージェントである」ことを明示する。
- 独立したタスクが複数あるとき、それらを可能な限り並列に起動する。
- 担当表の「Agent Tool」列が「可」の役割のサブエージェントにだけ Agent Tool を許可する。
- 委譲の依頼文の冒頭でその委譲が担う役割を明示し、その役割の Output Format を指定する。
- 担当表の「種別」が `readonly` の役割を `Write` / `Edit` を持つ定義へ委譲するとき、依頼文に次を明記する。合成して起動するときも同じである。
  - 使用してよい tools を読み取り系に限定すること(`Read` / `Grep` / `Glob`、読み取りに限った `Bash`、必要なら `WebSearch` / `WebFetch`)
  - ファイルを変更しないこと、報告のみを返すこと
- サブエージェントに方針スキルをロードさせない。
- サブエージェントを起動するとき、この文書の「サブエージェントは〜」で始まる条項をすべて依頼文へ転記する。
- 役割マーカーの対応表が注入されているとき、その役割の委譲先を担当表より優先してその定義とする。同じ役割に複数あるときは依頼内容に近いものを選ぶ。
- SessionStart が custom から claude へのフォールバックを通知したとき、依頼文に「役割マーカーの対応表のうち、外部ベンダーのモデルを指定した定義は委譲先にしない」と明記する。

### サブエージェントの規律

- サブエージェントは、タスクを再委譲するとき、依頼文で受け取った「サブエージェントは〜」で始まる条項をすべて、再委譲先の依頼文へ転記する。
- サブエージェントは、タスクを再委譲するとき、委譲先に「あなたはサブエージェントである」ことを明示する。
- サブエージェントは、タスクを再委譲するとき、役割マーカーの対応表にある役割の委譲先を優先する。同じ役割に複数あるときは依頼内容に近いものを選ぶ。
- サブエージェントは、読み取りだけの作業を `Write` / `Edit` を持つ定義へ再委譲するとき、依頼文に「使用してよい tools を読み取り系に限定すること(`Read` / `Grep` / `Glob`、読み取りに限った `Bash`、必要なら `WebSearch` / `WebFetch`)」「ファイルを変更しないこと」「報告のみを返すこと」を明記する。
- サブエージェントは、アドバイザーとして相談する相手を、役割マーカーの対応表の `advisor`(設計・計画・実装のアドバイザー)の行にある定義にする。対応表に無いときは `Fable` にする。`Fable` が起動できないときは相談せず、差し戻しで解決する。
- サブエージェントは、Agent Tool が許可されていないときの迷いを、相談ではなく差し戻しで解決する。
- サブエージェントは、自身が起動したアドバイザーサブエージェントに Agent Tool を許可せず、依頼文に「助言のみを返し、作業はしない」と明記する。
- サブエージェントは、依頼文で指定されたスキルだけをロードする。方針スキルも、指定が無ければロードしない。
- サブエージェントは、スキルの指定がなければどのスキルもロードせず、依頼文の記述だけで作業する。
- サブエージェントは、依頼文にある語や文の例のうち「本文に載せる」と添えられていないものを、依頼の説明として扱う。成果物の本文には書かず、自分で選んだ言葉を書く。
- サブエージェントは、「本文に載せる」と添えられた例を成果物へ書くとき、閉じた列挙にせず、判断の軸とともに書く。

## 委譲先の実行モデルの確定

Agent を名指しで起動するたびに、起動形態を次の 3 種から選ぶ。役割に対して委譲先を選ぶときはこの節を当てず、§委譲先の解決 に従って実務タスクの着手前に一度だけ確定させる。

- そのまま起動 — `subagent_type`・モデル・tools のいずれにも触れない。
- モデル注入起動 — `subagent_type`・tools・本文を元定義のまま使い、`model` param だけを注入する。注入するのは `model` 未宣言・`inherit` の定義に対する役割モデルである。`claude-model-policy` の運用では、役割モデルは担当表の「Claude モデル」列である。`custom-policy` の運用では、役割モデルは役割マーカーの対応表でその役割に解決された定義の `model` である。役割モデルが Claude 以外のときは、担当表の「Claude モデル」列へ読み替える。
- 合成 — 役割の定義をホストとして `subagent_type` に指定し、外部定義の本文を依頼文へ同梱する。

上から順に評価し、最初に該当した行で確定する。

| 順  | 条件                                                                                                                                                                                                  | 起動形態                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 1   | フックの注入文が `subagent_type` や起動様式を指定している                                                                                                                                             | そのまま起動                                  |
| 2   | 原本定義を特定できない                                                                                                                                                                                | そのまま起動                                  |
| 3   | frontmatter が `name` / `description` / `model` / `tools` / `color` / `agent-policy-role` / `agent-policy-vendor` 以外のフィールドを持つ、または本文が `${CLAUDE_PLUGIN_ROOT}` などの展開値に依存する | そのまま起動                                  |
| 4   | `model` 宣言が `sonnet` / `opus` / `haiku` / `fable` のどれでもない                                                                                                                                   | そのまま起動                                  |
| 5   | 作業種別が合成対象の役割に合致しない                                                                                                                                                                  | そのまま起動                                  |
| 6   | 役割に対応表の定義が無い、外部定義固有の MCP tool が作業の本体で未付与、または外部本文の義務条項がホスト本文の禁止条項と衝突する                                                                      | モデル注入起動                                |
| 7   | 上記以外で `model` が未宣言・`inherit`                                                                                                                                                                | 合成する。モデルはホストの frontmatter に従う |
| 8   | 上記以外で `model` が enum で宣言されている                                                                                                                                                           | 合成し、`model` param で宣言値を適用する      |

合成の対象とする役割は、担当表のうち「その他のタスク」を除く全役割とする。「その他のタスク」は合成しない。

判定に迷ったときは合成せず、より上の行へ倒す。

### 原本の確認

- 委譲先の原本は、プロジェクトの `.claude/agents/` → ユーザーの `~/.claude/agents/` → Agent 定義を同梱する他プラグインの実体にある `agents/` の順で探す。このプラグインは Agent 定義を同梱しない。
- dispatch に使われる実体と同一の定義を読めた確証が無いときは、そのまま起動する。
- 確認は原本に対して行い、複製・改変版は作らない。
- ビルトイン Agents(`Explore` / `Plan` / `general-purpose` 等)は `model` 未宣言として扱う。
- ビルトイン Agents は本文を読めないため合成せず、役割が定まるならモデル注入起動にする。

### 合成の手順

- ホストは、役割マーカーの対応表でその役割に解決された定義から選ぶ。同じ役割に複数あるときは依頼内容に近いものを選ぶ。
- プラグインが同梱する汎用定義はプロジェクト最適化を持たないため、ホストに使わない。
- 依頼文の冒頭で、ホストが担う役割名を明示する。
- 外部定義の本文(frontmatter より後の全文)を、その作業の役割定義として依頼文へ同梱する。
- 外部本文の禁止条項・制約条項がホスト本文の同種規定より優先することを、依頼文に明記する。
- 外部本文の義務条項がホスト本文の禁止条項と衝突するときは、合成せずモデル注入起動にする。

### 合成したときの tools

- built-in の tools は外部定義の tools を上限とし、外部定義に無い `Write` / `Edit` / `Bash` は使わない。
- ホスト frontmatter の `mcp__*` は、外部定義の tools に無くても使う。
- 外部本文が明示的に禁じる操作は、`mcp__*` の規則より優先して行わない。

### 外部定義固有の MCP tool

外部定義の固有 MCP tool が作業の本体であるときは、次の順で扱う。

1. ホスト定義へその MCP サーバーを許可することをユーザーへ提案する。提案文には、付与が永続の変更であること、サーバー単位の許可は外部定義のツール単位 allowlist より広くなること、付与に使う CLI へ既存の MCP サーバーを含めた全集合を渡さないと既存分が脱落することを書く。
2. 付与を dispatch の副作用として自分で実行しない。
3. 付与が行われないときは、モデル注入起動にする。

## コードベース探索

- コードベース探索は担当表の「コードベース探索」の役割へ委譲する。
- grep/read の反復が 3 ターン以上見込まれる探索は、1 回の dispatch にまとめる。
- 探索結果の突き合わせ・未解決事項の判断・要件の確定は、オーケストレーターが担う。

## コスト規律

- 委譲先にロードさせるスキルは、`wc -c` で本文と参照文書の合計を測る。30KB を超えるものは、指定があってもロードさせず、必要な節・手順・制約だけを参照断片として依頼文へ転記する。
- サブエージェントに毎タスクの git commit・広域 grep 検証はさせない。バッチの最後にオーケストレーター側で行うか、1 回の検証専用 dispatch へ寄せる。

## 設計・実装計画の規律

- 設計書の執筆を委譲する前に、探索で確定した事実(パス・行番号・現況)を要件・受け入れ基準とともに依頼文へ渡す。
- 設計書・実装計画書の執筆は、担当表の「設計書・実装計画書(WBS)の作成」の役割へ委譲する。オーケストレーターは確定した要件・受け入れ基準を依頼文で渡し、自ら執筆しない。
- 出力された設計書・実装計画書は、まず担当表の「設計書・実装計画書のレビュー」の役割にレビュー(理解+暗黙知・矛盾抽出)させる。
- 続いて担当表の「設計書・実装計画書の独立レビュー」の役割へ、原本のみを渡して dispatch する。他のレビューの指摘は渡さない。依頼文に「反証の提示までを担い、採否はオーケストレーターが判断する」と明記する。この役割の委譲先の解決は §委譲先の解決 に従う。
- オーケストレーターが両レビューの指摘の採否を判断し、補足修正を加えてからユーザーへ提示して承認を得る。
