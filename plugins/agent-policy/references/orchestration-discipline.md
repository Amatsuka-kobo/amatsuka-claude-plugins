# オーケストレーション共通規律

この文書の読者はオーケストレーターである。「サブエージェントは〜」で始まる条項は、依頼文への転記と、生成した定義の本文でサブエージェントへ届ける。

以下で「担当表」とは、この文書の §役割 の表を指す。役割は担当表の「役割名」列の値で参照する。

## 役割

| 役割名 | RoleId | 種別 | Agent Tool | Claude モデル |
| --- | --- | --- | --- | --- |
| 複雑または重要な実装 | `complex-impl` | `impl` | 可 | `Opus` |
| 通常の実装 | `normal-impl` | `impl` | 可 | `Sonnet` |
| 軽量な実装 | `light-impl` | `impl` | 否 | `Haiku` |
| 行き詰まり時のエスカレーション | `escalation` | `impl` | 可 | `Fable` |
| その他のタスク | `general` | `impl` | 可 | `Sonnet` |
| 設計書・実装計画書(WBS)の作成 | `design-plan` | `impl` | 可 | `Opus` |
| コードベース探索統括 | `explore-lead` | `impl` | 可 | `Opus` |
| コードベース探索実働 | `explore` | `readonly` | 可 | `Sonnet` |
| リアルタイム情報調査 | `realtime-research` | `readonly` | 可 | `Sonnet` |
| E2E 動作検証・ブラウザ/GUI 操作 | `e2e-verify` | `readonly` | 可 | `Sonnet` |
| 設計書・実装計画書の独立レビュー | `independent-review` | `readonly` | 可 | `Sonnet` |
| 設計書・実装計画書のレビュー | `doc-review` | `readonly` | 否 | `Haiku` |
| コードレビュー | `code-review` | `readonly` | 否 | `Sonnet` |
| 重要な実装の最終レビュー | `final-review` | `readonly` | 否 | `Fable` |

| 設計・計画・実装のアドバイザー | `advisor` | `readonly` | 否 | `Fable` |

- 「RoleId」は Agent 定義の `agent-policy-role` マーカーに書く値である。
- 「種別」は `impl` が成果物ファイルを書く役割、`readonly` が読み取りと報告だけの役割である。
- 「Agent Tool」は、その役割として起動したサブエージェントに Agent Tool を許可してよいかである。
- 「Claude モデル」は、その役割を Claude のモデルだけで実行するときのモデルである。`claude-model-policy` の運用では役割モデルそのものであり、`custom-policy` の運用では委譲先が決まらない役割の読み替え先である。

## オーケストレーターが自ら担う作業

オーケストレーターが担うのは dispatch・要件確定・採否判断・承認・分析である。担当表の全役割はサブエージェントが担う。オーケストレーターはそのどれも自ら実行しない。

分析は次の 3 つを含む。実働(読む・探す・再現する)は役割へ委譲してよいが、結論と判断はオーケストレーターが出す。分析全体を 1 つの役割へ渡して結論まで受け取ることはしない。

- 報告の突き合わせ・判断。複数の context-map・設計書・レビュー・実装差分・並列サブエージェントの全レポートを分割せず一度に読んで突き合わせ、採否と要件を決める。要約の要約では判断しない。
- 要件分析。ユーザーの要望を要件と受け入れ基準へ落とす。
- 原因分析・調査。バグの原因究明・現状把握など「調べて結論を出す」作業。grep/read の反復や再現の実働は「コードベース探索実働」などの役割へ委譲してよいが、結論はオーケストレーターが出す。「その他のタスク」の役割へ丸投げしない。

## モデル別役割の運用

- 各モデルは担当表に従い、その役割タスクのみを担当する。
- 複数コンポーネントにまたがる実装、または非自明な設計判断を含む実装は「複雑または重要な実装」とする。
- 単一コンポーネントに閉じ、設計判断を伴わない実装は「通常の実装」とする。
- 既存パターンの機械的な反復・一括適用は「軽量な実装」とする。
- サブエージェントを起動するとき、対象に「あなたはサブエージェントである」ことを明示する。
- オーケストレーターは、独立したタスクが複数あるとき、それらを 1 メッセージ内で可能な限り並列に dispatch する。
- オーケストレーターは、担当表の「Agent Tool」列が「可」の役割のサブエージェントにだけ Agent Tool を許可する。
- オーケストレーターは、委譲の依頼文の冒頭でその委譲が担う役割を明示し、その役割の Output Format を指定する。
- オーケストレーターは、担当表の「種別」が `readonly` の役割を `Write` / `Edit` を持つ定義へ委譲するとき、依頼文に次を明記する。合成して起動するときも同じである。
  - 使用してよい tools を読み取り系に限定すること(`Read` / `Grep` / `Glob`、読み取りに限った `Bash`、必要なら `WebSearch` / `WebFetch`)
  - ファイルを変更しないこと、報告のみを返すこと
- オーケストレーターは、サブエージェントに方針スキルをロードさせない。必要な規律は依頼文へ転記する。
- サブエージェントは、アドバイザーとして相談する相手を、役割マーカーの対応表にある「設計・計画・実装のアドバイザー」の役割の定義にする。対応表に無いときは `Fable` にする。`Fable` が起動できないときは相談せず、差し戻しで解決する。
- サブエージェントは、Agent Tool が許可されていないときの迷いを、相談ではなく差し戻しで解決する。
- サブエージェントは、自身が起動したアドバイザーサブエージェントに Agent Tool を許可せず、依頼文に「助言のみを返し、作業はしない」と明記する。
- サブエージェントは、依頼文で指定されたスキルだけをロードする。方針スキルも、指定が無ければロードしない。
- サブエージェントは、スキルの指定がなければどのスキルもロードせず、依頼文の記述だけで作業する。
- SessionStart フックが役割マーカーの対応表を注入したときは、その役割の委譲先を担当表より優先してその定義とする。同じ役割に複数あるときは依頼内容に近いものを選ぶ。

## 委譲先の実行モデルの確定

Agent を名指しで dispatch するたびに、起動形態を次の 3 種から選ぶ。役割に対して委譲先を選ぶ dispatch にはこの節を当てず、方針の「実行役割の解決順」に従って実務タスクの着手前に一度だけ確定させる。

- そのまま起動 — `subagent_type`・モデル・tools のいずれにも触れない。
- モデル注入起動 — `subagent_type`・tools・本文を元定義のまま使い、`model` param だけを注入する。注入するのは `model` 未宣言・`inherit` の定義に対する役割モデルである。`claude-model-policy` の運用では、役割モデルは担当表の「Claude モデル」列である。`custom-policy` の運用では、役割モデルは役割マーカーの対応表でその役割に解決された定義の `model` である。役割モデルが Claude 以外のときは、担当表の「Claude モデル」列へ読み替える。
- 合成 — 役割の定義をホストとして `subagent_type` に指定し、外部定義の本文を依頼文へ同梱する。

上から順に評価し、最初に該当した行で確定する。

| 順 | 条件 | 起動形態 |
| --- | --- | --- |
| 1 | フックの注入文が `subagent_type` や起動様式を指定している | そのまま起動 |
| 2 | 原本定義を特定できない | そのまま起動 |
| 3 | frontmatter が `name` / `description` / `model` / `tools` / `color` / `agent-policy-role` / `agent-policy-vendor` 以外のフィールドを持つ、または本文が `${CLAUDE_PLUGIN_ROOT}` などの展開値に依存する | そのまま起動 |
| 4 | `model` 宣言が `sonnet` / `opus` / `haiku` / `fable` のどれでもない | そのまま起動 |
| 5 | 作業種別が合成対象の役割に合致しない | そのまま起動 |
| 6 | 役割に対応表の定義が無い、外部定義固有の MCP tool が作業の本体で未付与、または外部本文の義務条項がホスト本文の禁止条項と衝突する | モデル注入起動 |
| 7 | 上記以外で `model` が未宣言・`inherit` | 合成する。モデルはホストの frontmatter に従う |
| 8 | 上記以外で `model` が enum で宣言されている | 合成し、`model` param で宣言値を適用する |

合成の対象とする役割は、担当表のうち「その他のタスク」を除く全役割とする。「その他のタスク」は合成しない。

判定に迷ったときは合成せず、より上の行へ倒す。

### 原本の確認

- 委譲先の原本は、プロジェクトの `.claude/agents/` → ユーザーの `~/.claude/agents/` → Agent 定義を同梱する他プラグインの実体にある `agents/` の順で探す。このプラグインは Agent 定義を同梱しない。
- dispatch に使われる実体と同一の定義を読めた確証が無いときは、そのまま起動する。
- 確認は原本に対して行い、複製・改変版は作らない。
- ビルトイン Agents(`Explore` / `Plan` / `general-purpose` 等)は `model` 未宣言として扱う。
- ビルトイン Agents は本文を読めないため合成せず、役割が定まるならモデル注入起動にする。

### 合成の手順

- ホストは、役割マーカーの対応表でその役割に解決された定義から選ぶ。同じ役割に複数あるときは依頼内容に近いものを選ぶ。
- プラグインが同梱する汎用定義はプロジェクト最適化を持たないため、ホストに使わない。
- 依頼文の冒頭で、ホストが担う役割名を明示する。
- 外部定義の本文(frontmatter より後の全文)を、その作業の役割定義として依頼文へ同梱する。
- 外部本文の禁止条項・制約条項がホスト本文の同種規定より優先することを、依頼文に明記する。
- 外部本文の義務条項がホスト本文の禁止条項と衝突するときは、合成せずモデル注入起動にする。

### 合成したときの tools

- built-in の tools は外部定義の tools を上限とし、外部定義に無い `Write` / `Edit` / `Bash` は使わない。
- ホスト frontmatter の `mcp__*` は、外部定義の tools に無くても使う。
- 外部本文が明示的に禁じる操作は、`mcp__*` の規則より優先して行わない。

### 外部定義固有の MCP tool

外部定義の固有 MCP tool が作業の本体であるときは、次の順で扱う。

1. ホスト定義へその MCP サーバーを許可することをユーザーへ提案する。提案文には、付与が永続の変更であること、サーバー単位の許可は外部定義のツール単位 allowlist より広くなること、付与に使う CLI へ既存の MCP サーバーを含めた全集合を渡さないと既存分が脱落することを書く。
2. 付与を dispatch の副作用として自分で実行しない。
3. 付与が行われないときは、モデル注入起動にする。

## コードベース探索

- ファイル探索・コードベース探索が必要なときだけ、この文書と同じディレクトリの `context-map-guide.md` を読み、これに従う。
- コードベース探索は担当表の「コードベース探索統括」の役割へ委譲する。grep/read の反復など短命な探索実働は、統括の役割が「コードベース探索実働」の役割へバッチで再委譲する。
- context-map の執筆は「コードベース探索統括」の役割が行う。
- context-map の §未解決事項の判断と、そこから要件を確定させる接続は、オーケストレーターが行う。統括の役割は §未解決事項を報告に載せるところまでを担う。
- 作成した context-map の所在(パス)は、次の dispatch または上流報告で必ず通知する。

## コスト規律

- 委譲先にロードさせるスキルは、`wc -c` で本文と参照文書の合計を測る。30KB を超えるものは、指定があってもロードさせず、必要な節・手順・制約だけを参照断片として依頼文へ転記する。
- サブエージェントに毎タスクの git commit・広域 grep 検証はさせない。バッチの最後にオーケストレーター側で行うか、1 回の検証専用 dispatch へ寄せる。

## 設計・実装計画の規律

- コードベース探索を伴う設計・実装は、context-map の作成後に着手する。
- 設計書・実装計画書の執筆は、担当表の「設計書・実装計画書(WBS)の作成」の役割へ委譲する。オーケストレーターは確定した要件・受け入れ基準・context-map の所在を依頼文で渡し、自ら執筆しない。
- 出力された設計書・実装計画書は、まず担当表の「設計書・実装計画書のレビュー」の役割にレビュー(理解+暗黙知・矛盾抽出)させる。
- 続いて担当表の「設計書・実装計画書の独立レビュー」の役割へ、原本のみを渡して dispatch する。他のレビューの指摘は渡さない。依頼文に「反証の提示までを担い、採否はオーケストレーターが判断する」と明記する。この役割の委譲先の解決は方針の「実行役割の解決順」に従う。
- オーケストレーターが両レビューの指摘の採否を判断し、補足修正を加えてからユーザーへ提示して承認を得る。
- オーケストレーターの Approve(計画が全体要件を満たすことの確認)はユーザー承認の後に置く。Approve を経てから実装へ移行する。
