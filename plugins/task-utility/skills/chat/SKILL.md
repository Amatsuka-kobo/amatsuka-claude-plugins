# Chat — 会話の記録

## 目的

`docs/chat/` はリポジトリにコミットされる**唯一の永続的な会話記録**である(生ログはローカル限定で消える)。将来のAIと人間が「何をして、何を決め、なぜそう決め、何がうまくいかなかったか」を検証するための一次資料として書く。とくに、要約した瞬間に永久に失われる情報 — **ユーザーの発言の原文**と**失敗・やり直しの経緯** — を守ることがこの記録の最優先の責務である。

## 保存場所

- パス: `docs/chat/YYYY/MMDD/<内容を表すケバブケース名>.md`
- 同じ作業の続きを記録するときは、新規ファイルを作らず既存ファイルにセッション見出しを増やして追記する

## ファイルの構成(この順で書く)

1. **ヘッダー**: タイトル(`# <題名>`)と箇条書きのメタ情報
   - 日付
   - 参加者(ユーザーは GitHub ユーザー名。不明なら必ず本人に確認する)
   - 成果物(作成・変更したファイルのパス、コミットハッシュ)
   - 前提(参照した設計書・過去のチャット記録)
2. **本文**: `## セッション N: <要旨>` で区切り、各ターンを `# <ユーザー名>` / `# AI` の見出しで記録する
3. **末尾**: 注意事項と次の作業(未コミットの変更、持ち越した課題)

## 本文の粒度契約(非対称)

ユーザー側とAI側で粒度を変える。**ユーザーの発言は原文、AIの発言は構造化された要約。**

### ユーザーの発言 = 原文

発言を引用ブロック(`>`)で**原文のまま**載せる。原文が長い場合は、原文引用の後に要旨を地の文で添える(原文を削って要旨だけにすることはしない)。

ユーザーの発言は要件の一次資料である。AIの解釈で置き換えて記録すると、AIが要件を誤解していた場合に「AIの誤解」が「ユーザーの要求」として歴史に残り、後から検証する手段が失われる。発言は会話全体のごく一部であり、原文保存のコストはほぼゼロで済む。

### AIの発言 = 構造化された要約

逐語ではなく、次のスロットを埋める形で要約する:

- **何をしたか**: 調査・実装・提案の内容
- **決定と理由**: 何を選び、なぜか
- **却下された選択肢**: 提示したが採用されなかった案と、その理由
- **失敗・やり直し・誤った前提**: 何を試み、どう失敗し、何が原因で、どう方針転換したか。**調査と発見の道筋ごと書く**(結論1行に圧縮しない)。失敗の経緯はこのリポジトリで最も価値の高い記録であり、成功より優先して残す

### 網羅性の明記

複数のタスク・項目のうち一部だけを詳述するときは、**残りがどうだったかを一文で明記する**(例: 「残り3エンドポイントは指摘なくそのまま移行」「Task 5, 6, 9〜11 は一発通過」)。これにより「記録がない」=「何もなかった」と読めるようになり、無記録と無風が区別できる。

### 表記規約

- 引用ブロック(`>`)= 発言の原文
- 地の文 = 要約・言い換え

この対応を崩さない。読み手が「これは本人の言葉か、AIの解釈か」を常に判別できることが目的である。
