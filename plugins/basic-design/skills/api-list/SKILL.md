# API List — API/IF 一覧の作成

## 目的

ユーザーから与えられた情報を出発点に、ブレインストーミングでシステムのエンドポイントを洗い出し、API/IF 一覧として Markdown で保存する。

## 大原則

- **ディスカッションはユーザーが使用する言語を厳守する**
- **ユーザーの明示的な承認を得るまで生成・保存しない**
- STOP するときは必ず「理由+次にユーザーがすべきこと」を伝えて終了する

## 手順

### 1. 最初の確認

AskUserQuestion で次を確認する:

- **保存先**: `docs/design/api/` を既定として提案し、変更希望を確認する
- **対象範囲**: システム全体か、特定の機能・サブシステムか

すでに入口スキル(basic-design)から引き継いでいる場合、**保存先の確認は省略**する(入口スキルの手順 2 で確認済みの値を使う)。**対象範囲**は、会話ですでに明らかなら聞き直さず、不明なときだけ確認する(単独呼び出し時も同じ判断でよい)。

### 2. ブレインストーミング

自由対話で進めつつ、次の観点がすべて埋まるまで、**不足している観点だけを 1 問ずつ**質問する。選択式で聞ける場面では AskUserQuestion を使う。

| 観点 | 埋まる状態 |
| --- | --- |
| エンドポイント一覧 | 対象範囲の API が列挙され、それぞれの役割を一言で説明できる |
| メソッドとパス | 各 API の HTTP メソッドと URL パス(パスパラメータ含む) |
| 認証 | 各 API の認証要否と方式(例: Bearer トークン / セッション / 不要) |
| リクエスト概要 | 主要な入力(パスパラメータ・クエリ・ボディの主要フィールド)。**フル JSON 定義は書かない** |
| レスポンス概要 | 正常時の主要な出力フィールドとステータスコード。**フル JSON 定義は書かない** |

先行する成果物・用語集(入口スキルの概要ブレストなど)がある場合、リソース名・エンティティ名はそれに従う(例: ER図の `orders` エンティティに対応する API は `/orders`)。

画面遷移図や ER図が先に存在する場合は、画面・エンティティごとに必要な API を洗い出す問いかけをすると漏れが減る(例: 「注文一覧画面はどの API からデータを取得しますか?」)。

### 3. ドラフト提示 → 明示承認

`references/template.md` の形式で一覧表の**全文**を提示し、ユーザーの承認を得る。

### 4. 保存

承認された内容を `docs/design/api/<名前>.md` に保存する。ファイル名はケバブケース(例: `order-api.md`)。git コミットはユーザーの指示があったときのみ行う。

ローカル保存の完了後、`${CLAUDE_PLUGIN_ROOT}/skills/shared/drive-upload.md` の手順で Google Drive へのアップロードを確認する(設定が無ければ何も起きない)。

## 既存一覧の更新

同名のファイルが既にある場合は、それを読み込んで現状を把握し、差分(追加・変更・廃止エンドポイント)をブレストしてから全文を更新する。
