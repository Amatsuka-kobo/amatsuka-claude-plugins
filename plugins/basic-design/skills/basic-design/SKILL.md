# Basic Design — 基本設計オーケストレーション

## 目的

対象システムの概要を短いブレインストーミングで固め、必要な成果物を選択し、各専用スキルを順に実行して基本設計ドキュメント一式を作る。

## 大原則

- **ディスカッションはユーザーが使用する言語を厳守する**
- **ユーザーの明示的な承認を得るまで生成・保存しない**(各成果物のドラフト承認は各スキルの規律に従う)
- STOP するときは必ず「理由+次にユーザーがすべきこと」を伝えて終了する
- **成果物は 1 つずつ逐次で作る**。並列にしない(ブレストは 1 本の対話であり、用語の整合は逐次実行に依存する)

## 手順

### 1. 概要ブレスト

対象システムについて、次の 3 点を軽い対話で確認する(まとめて聞いてよい。既に会話に出ていれば聞き直さない):

- **システム名と一言サマリ**(何をするシステムか)
- **主要ユースケース 2〜3 個**(誰が・何をする)
- **登場する主な概念**(画面になりそうなもの・データになりそうなもの・連携する外部システム)

### 2. 全体設定の確認(1 回だけ)

AskUserQuestion で次を確認し、**以降の全成果物に引き継ぐ**(各スキルでの再確認はしない):

- **出力形式**(図系スキル用): Draw.io / インタラクティブ HTML / 両方。Markdown 系スキル(api-list / nfr-checklist)には適用しない(常に Markdown)
- **保存先ルート**: `docs/design/` を既定として提案(各成果物は `docs/design/<種別>/` に入る)

ここで引き継ぐのは**出力形式と保存先だけ**。各スキルが必要とするそれ以外の情報(対象範囲、システムの性質など)は、概要ブレストと会話の文脈から判断し、不明なときだけ各スキルの手順で確認する。

### 3. 成果物の選択

AskUserQuestion(multiSelect)で作る成果物を選んでもらう:

- ER図(er-diagram)
- 画面遷移図(screen-flow)
- システム構成図(system-architecture)
- シーケンス図(sequence-diagram)
- API/IF 一覧(api-list)
- 非機能要件チェックリスト(nfr-checklist)

推奨順を添えて提示する: **画面遷移 → ER → シーケンス → 構成図 → API一覧 → 非機能**(画面とデータが決まると後続の粒度が定まりやすい)。ユーザーの希望があればその順に従う。

### 4. 用語集の確立

手順 1 で出た用語を**用語集としてディスカッション中に明示的にまとめて提示する**。形式は次の箇条書き(会話メッセージとして出力する。ファイルには書かない):

```
【用語集】
- 画面: ログイン画面, ホーム画面, ...      ← 画面遷移図・API一覧が参照
- エンティティ: users, orders, ...          ← ER図・API一覧が参照
- アクター/外部システム: ユーザー, 決済API, ... ← シーケンス図・構成図が参照
```

以降の各スキルのブレストではこの用語集に従い、同じ概念に別名を付けない。新しい用語が生まれたら用語集に追記して提示し直す。ファイルやパラメータでの受け渡しは行わない(同一コンテキストの対話が用語集のすべて)。

### 5. 各スキルの逐次実行

選択された成果物を順に、対応するスキルの手順で作成する:

- 各スキルの「最初の確認」(出力形式・保存先)は手順 2 で確認済みのため省略し、その値を使う
- 各スキルのブレスト・ドラフト承認・生成・保存の規律はそのまま従う
- 1 つの成果物が完了するたびに、次の成果物に移る前に「次は<成果物名>に進みます」と一言告げる。ユーザーが中断・順序変更を求めたら従う

### 6. 最終報告

全成果物の完了後、次を報告する:

- 生成ファイルの一覧(パス)
- 開き方(.drawio → app.diagrams.net、.html → ブラウザで直接、.md → そのまま)
- 未選択の成果物(あれば「後から各スキルで個別に追加できる」ことを添える)

## 途中で中断した場合

どこまで完了したか(成果物と保存先の一覧)と、残りの成果物を報告して終了する。再開時は完了済みの成果物を読み込めば用語集を復元できる。
