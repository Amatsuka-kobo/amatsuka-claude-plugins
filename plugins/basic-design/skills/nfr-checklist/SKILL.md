# NFR Checklist — 非機能要件チェックリストの作成

## 目的

観点カタログ(`references/catalog.md`)を網羅的にたどりながら、対象システムの非機能要件の「要否と目標値」をブレインストーミングで埋め、チェックリストとして Markdown で保存する。

## 大原則

- **ディスカッションはユーザーが使用する言語を厳守する**
- **ユーザーの明示的な承認を得るまで生成・保存しない**
- STOP するときは必ず「理由+次にユーザーがすべきこと」を伝えて終了する
- **観点を勝手にスキップしない**。対象外とする場合も「対象外」という判断を明示的にユーザーと確認して記録する

## 手順

### 1. 最初の確認

AskUserQuestion で次を確認する:

- **保存先**: `docs/design/nfr/` を既定として提案し、変更希望を確認する
- **システムの性質**: 社内システム / 一般公開サービス / 組み込み等(カタログのどの観点を重点的に扱うかの判断材料)

すでに入口スキル(basic-design)から引き継いでいる場合、**保存先の確認は省略**する(手順 2 の値を使う)。**システムの性質**は、会話ですでに明らかなら聞き直さず、不明なときだけ確認する(単独呼び出し時も同じ判断でよい)。

### 2. ブレインストーミング(カタログ巡回)

`references/catalog.md` の 8 分類を**分類ごとに**たどる。分類単位で現状の想定を要約提示し、不足している下位観点だけを 1 問ずつ質問する。選択式で聞ける場面では AskUserQuestion を使う。

各観点で埋めるのは次の 3 点:

1. **要否**: 必要 / 対象外(理由付き)
2. **目標値・方針**: 数値目標(例: 応答 1 秒以内、稼働率 99.9%)または方針(例: 日次バックアップ)
3. **備考**: 前提や補足があれば

すべての分類を巡回し終えるまで保存に進まない。ユーザーが「残りはまとめて対象外でよい」と明示した場合はその旨を記録して先へ進む。

### 4. 保存

承認された内容を `docs/design/nfr/<名前>.md` に保存する。ファイル名はケバブケース(例: `order-system-nfr.md`)。git コミットはユーザーの指示があったときのみ行う。

## 既存チェックリストの更新

同名のファイルが既にある場合は、それを読み込んで現状を把握し、変更のある分類だけを再ブレストして全文を更新する。
