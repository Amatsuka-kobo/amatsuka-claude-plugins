# better-agentics の設計の根拠

設計の正本は `harness-docs/design/2026-10-26-better-agentics-design.md` にある。ここには、スキル本文と参照文書から外した根拠・不採用案・リスクを置く。

## オーケストレーターが自分で働く理由

先行する運用方針では、オーケストレーターは調査も実装もサブエージェントへ委譲した。better-agentics はこの配分を逆にし、オーケストレーターが作業の大半を自分で行う。委譲するのは、別の目が要るレビュー、並列化か文脈の保護で得をする分担、自分で解けない行き詰まりの 3 つに限る。

## 選択基準をオーケストレーターに持たせない理由

Claude Code がオーケストレーターの Agent 一覧に載せるのは、定義の `description` だけである。基準を本文の `## When to invoke` に置き、委譲先決定スクリプトだけが読めば、基準はオーケストレーターの文脈に入らない。オーケストレーターは「いつ委譲するか」だけを判断し、「どこへ委譲するか」は Jev が基準と作業内容から決める。

`description` に基準を書く案は、Agent 一覧に基準が載るため採らなかった。同じ理由で、生成する定義の `description` は基準を含まない短い句にしてある。

## サブエージェントの規律を hook で注入する理由

規律を定義本文に埋め込むと、規律を変えるたびに定義を作り直す必要がある。依頼文へ書き写す方式は、書き写し漏れが起きる。SubagentStart で注入すれば、プラグインの更新だけで全定義に効く。

注入は環境変数が有効なときだけ行う。別の運用方針のプラグインは、マーカーの無い定義も委譲先の候補にするため、better-agentics の定義がそちらで選ばれうる。そのときに規律が二重にならないようにするためである。

## 不採用案

- Jev を MCP ツールとしてオーケストレーターに呼ばせる案。ツールの引数に基準を組むため、オーケストレーターが基準を読むことになる。
- PreToolUse hook で Agent の `subagent_type` を書き換える案。選択が会話記録に残らずデバッグしにくい。権限確認への副作用もある。
- 基準を専用ファイルに置く案。定義の追加・削除との同期が要る。
- 同梱の役割断片を役割 ID で引いて基準にする案。利用者が定義を編集しても基準が変わらない。
- キーが無いときに、理由ごとの既定先へ回す案と、オーケストレーターが自分で選ぶ案。判断の経路が 2 つになり、後者は基準を持たせない方針にも反する。
- マーカーのキーを別の運用方針のプラグインと共用する案。2 つのプラグインの仕様が結びつく。
- エスカレーションを分担の候補に含める案。行き詰まりは分担とは別の場面で、試行の履歴を載せる規律も別に要る。
- worktree で切り離して並列にする案。取り込みの手間が増え、プロジェクトごとのブランチ運用の決まりを配布物から判定できない。
- setup の非対話モード。対話モードで推奨のまま全部作れば同じ結果になる。
- レビューの順序を固定する案。どのレビュアーに回すかは Jev が決め、返った全員を並列に起動する。順序を固定すると、オーケストレーターがレビュアーの組を知っている必要がある。
- 断片のプロジェクト独自の層。基準と本文の調整は、生成した定義を直接編集し、再生成で保持する形で足りる。

## リスク

- Jev の選択の質。基準の書き方しだいで、委譲先が偏る。出力に確率を含め、`## When to invoke` を定義の編集で調整できるようにしている。
- 並列の衝突。書き込むファイルの集合の見積もりを誤ると、同じファイルを 2 者が書き換える。サブエージェントの規律で範囲外の変更を禁じ、最後にオーケストレーターが差分を突き合わせる。
- 定義を名指しで起動したときの規律の欠落。環境変数が無効なセッションでは、better-agentics の定義を名指しで起動しても、サブエージェントの規律が届かない。
- キーの入手。TypeSafe AI は 2026-09-22 から新規サインアップを停止している。
