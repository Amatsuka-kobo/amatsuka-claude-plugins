# better-agentics の設計の根拠

設計の正本は `harness-docs/design/2026-10-26-better-agentics-design.md` にある。ここには、スキル本文と参照文書から外した根拠・不採用案・リスクを置く。

## オーケストレーターが自分で働く理由

先行する運用方針では、オーケストレーターは調査も実装もサブエージェントへ委譲した。better-agentics はこの配分を逆にし、オーケストレーターが作業の大半を自分で行う。委譲するのは、別の目が要るレビュー、並列化か文脈の保護で得をする分担、自分で解けない行き詰まりの 3 つに限る。

## 選択基準をオーケストレーターに持たせない理由

Claude Code がオーケストレーターの Agent 一覧に載せるのは、定義の `description` だけである。基準を本文の `## When to invoke` に置き、委譲先決定スクリプトだけが読めば、基準はオーケストレーターの文脈に入らない。オーケストレーターは「いつ委譲するか」だけを判断し、「どこへ委譲するか」は Jev が基準と作業内容から決める。

`description` に基準を書く案は、Agent 一覧に基準が載るため採らなかった。同じ理由で、生成する定義の `description` は基準を含まない短い句にしてある。

## サブエージェントの規律を hook で注入する理由

規律を定義本文に埋め込むと、規律を変えるたびに定義を作り直す必要がある。依頼文へ書き写す方式は、書き写し漏れが起きる。SubagentStart で注入すれば、プラグインの更新だけで全定義に効く。

注入は環境変数が有効なときだけ行う。別の運用方針のプラグインは、マーカーの無い定義も委譲先の候補にするため、better-agentics の定義がそちらで選ばれうる。そのときに規律が二重にならないようにするためである。

## 不採用案

- Jev を MCP ツールとしてオーケストレーターに呼ばせる案。ツールの引数に基準を組むため、オーケストレーターが基準を読むことになる。
- PreToolUse hook で Agent の `subagent_type` を書き換える案。選択が会話記録に残らずデバッグしにくい。権限確認への副作用もある。
- 基準を専用ファイルに置く案。定義の追加・削除との同期が要る。
- キーが無いときに、理由ごとの既定先へ回す案と、オーケストレーターが自分で選ぶ案。判断の経路が 2 つになり、後者は基準を持たせない方針にも反する。
- マーカーのキーを別の運用方針のプラグインと共用する案。2 つのプラグインの仕様が結びつく。
- エスカレーションを分担の候補に含める案。行き詰まりは分担とは別の場面で、試行の履歴を載せる規律も別に要る。
- worktree で切り離して並列にする案。取り込みの手間が増え、プロジェクトごとのブランチ運用の決まりを配布物から判定できない。
- setup の非対話モード。対話モードで推奨のまま全部作れば同じ結果になる。
- レビューの順序を固定する案。どのレビュアーに回すかは Jev が決め、返った全員を並列に起動する。順序を固定すると、オーケストレーターがレビュアーの組を知っている必要がある。
- 断片のプロジェクト独自の層。基準と本文の調整は、生成した定義を直接編集し、再生成で保持する形で足りる。

## リスク

- Jev の選択の質。基準の書き方しだいで、委譲先が偏る。出力に確率を含め、`## When to invoke` を定義の編集で調整できるようにしている。
- 並列の衝突。書き込むファイルの集合の見積もりを誤ると、同じファイルを 2 者が書き換える。サブエージェントの規律で範囲外の変更を禁じ、最後にオーケストレーターが差分を突き合わせる。
- 定義を名指しで起動したときの規律の欠落。環境変数が無効なセッションでは、better-agentics の定義を名指しで起動しても、サブエージェントの規律が届かない。
- キーの入手。TypeSafe AI は 2026-09-22 から新規サインアップを停止している。

## 起動モード改修(2026-11-11)で覆した判断と採らなかった案

出典は `harness-docs/design/2026-11-10-better-agentics-launch-modes-and-subagent-performance-design.md` の 12 章である。表の中の番号(D・J・セクション)は、その設計書を指す。

### 覆した判断

| 元の判断 | 出どころ | 覆した理由 |
| --- | --- | --- |
| 起動形態の判定(モデル注入起動・合成)は対象外 | 現行の設計書の 2-2 | Standard Agent モードで、定義を作らずに役割ごとのモデルと effort で委譲するため |
| 同梱の役割断片を役割 ID で引いて基準にする案を採らない | rationale.md の不採用案 | 不採用の理由は「利用者が定義を編集しても基準が変わらない」だった。断片の基準を使うのは定義の無い役割だけで、定義があればその基準を使うので、理由が当たらない |
| 定義は 1 役割に 1 つで、model と effort を frontmatter に固定する | 現行の設計書の 1-3 | Custom Agent モードでは保つ。Standard Agent モードでは `roles.ts` の推奨値を呼び出しで渡す |
| 定義の無い役割は委譲先にならない | 現行の setup の「この役割は作らない」 | 定義の無い役割は Standard Agent モードで委譲する。外したい役割は D18 の設定で外す |

### 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| 委譲先をバックグラウンドのメインセッションにする | 理由は次の 6 つ。codiel の stop-guard が委譲先の終了を止める【推定】。書き込みに worktree が要り、codiel 1.1 の D8 とぶつかる。codiel の待ちの仕組みは、サブエージェントの完了の通知を前提にしている。Workflow の `agent()` では起動できない。他のプラグインの hook がすべて委譲先で動く。規律の注入を SessionStart の分岐へ作り直す必要がある |
| 書き込む委譲先を worktree で、または `worktree.bgIsolation: "none"` で動かす | 上の案を採らないので不要 |
| 役割の定義をプラグインに同梱し、Standard Agent モードで使う | 置き場所による守られ方の差に根拠が無い(D7)。定義の説明文は常にエージェントの一覧に載る。プラグイン同梱の定義では `mcpServers` が無視される |
| knowledge-elicitation の effort を medium に上げる | medium では役割を果たせない(D9) |
| fork を 3 役割以外にも使う。effort を fork の条件に含める | 4.5 のとおり |
| 委譲先への文脈の受け渡しに context-map を使う | agent-policy で 2026-09-24 に廃止された(コミット 202955e8) |
| Standard Agent モードの読み取りの役割に、組み込みの Explore を使う | Explore は再開できず(D5 が使えない)、CLAUDE.md も読まない |
| 外した役割を、定義のファイル(役割マーカーだけの定義など)で表す | 定義の一覧と Agent ツールの一覧に、使わない定義が載る |
| レビューの差分をファイルに保存して渡す | 保護パス(`.git`・`.claude`)への書き込みか、プロジェクトの外の読み取りで許可の確認が出うる |
| レビューの対象をスナップショットのコミットで固定する | 実装のレビューをコミットの後に移した(D25)ので要らない(J14) |
| 実装を委譲している間に、受け入れ検査を自分で書く | テストを書く時点は運用方針のスコープの外とした(D27) |
| 30KB を超えるスキルの要る部分を依頼文へ書き写す | スキルの渡し方を codiel 1.2 の形にそろえた(D26) |
| 外側の手順に従う条項を、事項ごとの置き換えの表として規律に書く | 想定していない対立に当てられない。一般の原則として書く(D22) |
| 依頼文の優先の条項を、役割断片の「引き受けない」にも当てる | 安全弁がいつも外れる(J16) |
