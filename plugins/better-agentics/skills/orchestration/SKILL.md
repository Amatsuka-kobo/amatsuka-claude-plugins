# オーケストレーターの規律

## 自分で行う作業と委譲する場面

- 調査・分析・要件確定・設計書と計画書の執筆・実装・検証は、自分で行う。
- 委譲するのは、次の 3 つの理由のどれかに当たるときだけとする。

| 理由 | 場面 |
| --- | --- |
| `review` | 自分の成果物を、自分以外の目で確かめる必要があるとき |
| `split` | 作業の一部を委譲先に進めさせるとき |
| `stuck` | 自分で原因を追っても解決しないとき |

- 委譲先は自分で選ばず、`pick-delegate` が返した委譲先で起動する。
- 並列化やコストのために分担する `split` では、委譲している間も自分の分担を進める。自分の分担が無く待つだけになる委譲は、長く機械的な作業(多数のファイルへの一括変更など)に限る。
- `review`・`stuck` と、文脈の保護のための探索の `split` は、待つだけになってもよい。
- `pick-delegate` が `ok: false` を返したら、理由を問わず委譲も作業の続行もせず、`error` の種別と `message` をユーザーへ報告して指示を待つ。外側の手順に従っている間の扱いは「外側の手順」のセクションによる。
- 必須のレビューの前に `ok: false` が返ったときは、ユーザーへの提示・完了の報告・push にも進まない。
- `pick-delegate` に渡す作業内容(`summary`)は英語で書く。

## pick-delegate の呼び出し

標準入力で JSON を渡す。出力は JSON の 1 行で、終了コードは常に 0 である。次は例示であり、値は実際の内容に置き換える。

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/pick-delegate.mjs" --dir "$PWD" <<'EOF'
{"reason": "review", "task": {"summary": "Review the design doc for the cache layer", "artifacts": ["docs/design/cache.md"]}, "parentModel": "opus", "lang": "ja"}
EOF
```

| reason | 入力 |
| --- | --- |
| `review` | `{"reason": "review", "task": {"summary": string, "artifacts": string[]}}` |
| `split` | `{"reason": "split", "tasks": [{"id": string, "summary": string, "needsContext"?: boolean}]}`。`id` は配列内で一意にする。会話の文脈が無いと仕様を書き切れない作業にだけ `needsContext: true` を付ける。外側の手順に従って作業している間は付けない |
| `stuck` | `{"reason": "stuck", "task": {"summary": string}}` |

どの理由にも、最上位に `parentModel` と `lang` を付ける。`excludeRoles` は、委譲先を選び直すときだけ付ける。

| 項目 | 値 |
| --- | --- |
| `parentModel` | 自分のモデルの別名(`fable` / `opus` / `sonnet` / `haiku`)。システムプロンプトの環境の欄にあるモデル名から書く |
| `lang` | 会話の言語のコード(`ja`・`en` など)。省くと `en` |
| `excludeRoles` | その呼び出しだけ候補から外す役割 ID の配列 |

- `review` と `stuck` の出力は `agents`、`split` の出力は `assignments` に委譲先を持つ。
- `split` の `assignments` は、入力の `id` ごとに委譲先を 1 つ持つ。
- 委譲先は `role`・`mode`・`agentType` を持ち、`mode` で Agent ツールへの渡し方が決まる。

| `mode` | Agent ツールへの渡し方 |
| --- | --- |
| `custom` | `agentType` を `subagent_type` に渡す。`model` と `effort` は渡さない |
| `standard` | `agentType` を `subagent_type` に、`model`・`effort` を同名の引数に渡す。`preamble` を依頼文の冒頭にそのまま置く |
| `fork` | `subagent_type: "fork"` で起動し、`preamble` を依頼文の冒頭にそのまま置く。起動が拒否されたら、その作業を自分で行う |
| `self` | `split` だけで返る。その作業は委譲せず、自分で行う |

- 委譲先は、`run_in_background: true` で起動する。
- 待つだけでよい場面では、ターンを終えて完了の通知を待つ。通知で始まる次のターンで、委譲先の結果を読む。
- 委譲先の起動がエラーになったときは、別のモデルで起動し直さず、エラーをユーザーへ報告する。報告では、その役割を better-agentics:setup で外すか、別のモデルで定義を作るよう案内する。

| `error` | 意味 |
| --- | --- |
| `invalid-input` | 入力が JSON として読めない、必須の項目が欠ける、`split` の `id` が重複する、任意の項目の値が不正 |
| `invalid-config` | `.claude/better-agentics/config.json` が読めないか、形が違う |
| `no-candidates` | 理由に当たる役割を、設定ですべて外しているか、`excludeRoles` で候補がすべて外れた |
| `duplicate-role` | 同じ役割を 2 件以上の定義が持つ、または候補の定義の名前が重なる |
| `no-api-key` | Jev を呼ぶ必要があるのに `TYPESAFE_API_KEY` が無い |
| `jev-failed` | Jev の呼び出しが失敗した、または応答の形が想定外だった |

## review

次の時点で、必ずレビューを依頼する。

1. 設計書・実装計画書を書き終え、ユーザーへ示す前。
2. 実装をコミットした後。
3. 次のどれかに変更を加えてコミットした後。変更の大きさは問わない。
   - 全セッションに効く設定(hooks など)
   - プロジェクトの指示(CLAUDE.md・rules など)が、変更を禁じているか、確認や手順を求めているパス
   - データ移行

2 のコードレビューは、次の条件を両方満たすときだけ省ける。

- 変更した全箇所の正誤を、型検査・テスト・lint・grep のいずれかで判定できる。
- 3 に当たらない。

コードレビューを省いたときは、判定に使った検査とその結果を報告に書く。判定に使う検査を示せない変更は検証困難として扱い、レビューを省かない。

レビューを終えるまで、ユーザーへの提示・完了の報告・push に進まない。レビューを終えるとは、critical・high の指摘が残らなくなり、残った medium 以下の指摘について判断を仰いで答えを得たことを指す。

### 依頼の仕方

- レビュアーには、原本と満たすべき要件だけを渡す。自分の結論と、別のレビューの指摘は渡さない。
  - 文書のレビューでは、文書のパスを渡す。レビューを終えるまで、その文書を編集しない。
  - コードのレビューでは、コミットの範囲の差分を取るコマンド `git diff <base>..<head>` を渡す。base は作業を始める前の HEAD、head はレビューを頼む時点の HEAD とし、実際のコミットに置き換える。
- `pick-delegate` が複数のレビュアーを返したら、全員を 1 つのメッセージで並列に起動する。
- 出力に `fallback: true` が付いていたら(Jev がどの候補も選ばなかった)、そのレビュアーで進め、ユーザーへの報告にその旨を添える。

### 指摘への対応と再レビュー

- 指摘の採否は自分で決める。
- critical・high の指摘がある巡では、medium 以下を含めすべての指摘に対応する。対応とは、採る指摘を直し、採らない指摘は理由を記録することを指す。
- 直した変更はコミットしてから再レビューに回す。critical・high の指摘が出なくなるまで、回数の上限を置かずに回す。
- 再レビューは、前の巡のレビュアーへ SendMessage で続きを頼む。送るのは、直した後の差分を取るコマンドと満たすべき要件だけとし、自分の反論や結論は送らない。
- 再開できなかったときは、前の巡と同じ委譲先を新しく起動する。どちらの場合も `pick-delegate` を呼ばない。
- critical・high の指摘が無い巡が来たら、再レビューを止める。その巡の medium 以下の指摘は直さず、直すかどうかを含めて判断を仰ぎ、答えを待つ。1 巡目に critical・high が無いときも同じとする。
- 答えが「直す」なら、直した変更をコミットしてから再レビューに回し、同じ回し方を続ける。この修正はラウンドに数えない。

### 修正の担い手

critical・high のある巡の指摘を直して再レビューに回すまでを、1 ラウンドと数える。ラウンドの番号は、critical・high のあった巡を順に数えた番号とする。

- 1〜3 ラウンドは、変更を書いた担い手が同じ文脈で直す。
  - 自分で行った変更は、自分で直す。
  - `split` の委譲先が書いた変更は、その委譲先を SendMessage で再開して直させる。指摘が複数の担い手の変更にまたがるときは、担い手ごとに分けて頼む。
  - 再開できなかったときは、前と同じ委譲先を新しく起動し、それまでの修正の履歴を依頼文に載せる。
- 4 ラウンド目以降の、文書以外(実装・設定・データ移行)の修正は、`stuck` で `pick-delegate` を呼び、返った委譲先に直させる。
  - 依頼文には、試行の履歴としてこれまでのラウンドの修正の履歴を、失敗出力の原文として残っている指摘の原文を載せる。未解決の制約も載せ、無ければ無いと書く。
  - 2 ラウンドごとに新しく起動し直す。4・5 ラウンドは 1 体目が担い、5 ラウンド目は SendMessage で再開する。6 ラウンド目に同じ委譲先を新しく起動し、6・7 ラウンドはその 2 体目が担う。以降も同じとする。
  - 起動し直すときは `pick-delegate` を呼ばず、前の委譲先の試行を含めた履歴を依頼文に載せる。
  - 各委譲先の 2 ラウンド目に再開できなかったときは、同じ委譲先を新しく起動し、その 2 ラウンドの残りとして数える。
  - 委譲先が断ったときは、「委譲先が断ったとき」のセクションに従う。候補が尽きて自分で直すときは、2 ラウンドごとに原因の調べ直しから始める。
  - `excludeRoles` を付けない `stuck` の呼び出しで `no-candidates` が返ったら(行き詰まりの役割を設定で外している)、委譲せずに自分で直す。2 ラウンドごとに、それまでの修正の方針を捨て、原因の調べ直しから始める。自分で直したことを完了の報告に書く。
- 委譲先に直させるときは、依頼文でコミットまで指示する。
- 文書の修正は、書き手と種類を問わず `stuck` に回さない。文書とは、実行やテストで正しさを確かめられない成果物を指す。設計書・計画書・README のほか、CLAUDE.md・rules・SKILL.md・Agent 定義などの AI 向けの指示書も含む。
  - 1〜3 ラウンドは、上の規則のとおり書いた担い手が直す。
  - 4 ラウンド目からは、書いたのが委譲先でも自分で引き継いで直す。前の担い手の文脈は引き継がず、文書とこれまでの指摘と修正の履歴から直す。
  - 4・6・8 ラウンド目のように 2 ラウンドごとに、指摘の出た箇所を前の直し方によらずに書き直す。文書の全体は書き直さない。
- 1 つの巡の指摘が文書と文書以外にまたがるときは、指摘ごとに分けて規則を当てる。ラウンドの番号は巡ごとに 1 つとし、どちらの指摘にも同じ番号を当てる。
- レビューの修正の中では、「stuck」のセクションの 3 つの条件を当てず、ラウンドの規則で `stuck` に回す。

## split

### 着手前の見積もり

依頼を受けたら、作業に入る前に、情報を集める部分の規模を見積もる。

1. 依頼のうち、ファイルを読んで事実を集める部分(探索・調査・一覧の作成など)を書き出す。依頼文に「探索」「調査」の語が無くても対象にする。
2. その部分で読むファイルの数を、`ls`・`grep -l`・`wc` などで数える。
   - 数えるのは 1 ターンで済ませる。
   - ファイルの中身は読まない。
3. 次のどちらかに当たれば、grep/read の反復が 3 ターン以上見込まれると判断する。自分で始めずに、`split` で委譲する。
   - 読むファイルが 5 件以上ある。
   - 読む対象が複数のディレクトリにまたがる。
4. 見積もった数と判断を、最初の報告に 1 行で書く。

### 分担の範囲

分担してよいのは、次のどちらかに当たる部分である。

- 並列化: 自分の作業と同時に進められ、状態を共有しない部分。
- 文脈の保護: 結論だけが要り、過程を手元に置く必要が無い部分。grep/read の反復が 3 ターン以上見込まれる探索と、多数のファイルへの機械的な一括変更が該当する。

分担の前提:

- 切り出す部分の仕様は、型・関数シグネチャ・ファイル配置・変更箇所の列挙の形で書いて渡す。
- 会話の文脈が無いと仕様を書き切れない部分は、`needsContext: true` を付けて渡す。`fork` が返れば fork に委譲し、`self` が返れば自分で行う。
- 全体の設計判断、部品の結合、最終検証は、自分の手元に残す。

手順:

1. 分担する作業を洗い出し、作業ごとに書き込むファイルの集合と、他の作業の成果を待つかを書き出す。
2. 次の条件を両方満たす作業同士を、同じ並列グループに入れる。
   - 書き込むファイルの集合が重ならない。自分の分担とも比べる。
   - どちらも相手の成果を入力にしない。
3. グループ内の全作業を、1 回の `pick-delegate` 呼び出しに渡す。
4. 返った委譲先を、1 つのメッセージで全員バックグラウンド起動する。その間に自分の分担を進める。
5. 全員が戻ったら差分を突き合わせ、型検査・テスト・ビルドを自分で 1 回実行する。
6. 依存がある作業は次のグループに回し、前のグループの成果を依頼文に載せる。

補足:

- 同じ委譲先が複数の作業に選ばれたら、同じ委譲先を複数起動する。
- 書き込むファイルの集合が重なる作業は、並列にせず順に委譲する。
- 並列化と文脈の保護のどちらで切り出した作業も、手順 1〜6 で扱う。探索のように書き込みの無い作業は書き込みの集合が空なので、他の作業と同じグループに入れられる。
- 並列中の委譲先に実行させてよい検査は、対象のファイルを指定して範囲を絞れるもの(対象を指定したテスト、対象を指定した lint など)に限る。依頼文には、使ってよい検査のコマンドを書く。
- プロジェクト全体が対象の検査(型検査・ビルド)と、ビルド出力・lockfile・lint の自動修正は、手順 5 で自分だけが行う。
- 依頼文には「変更範囲の外が原因の失敗は直さず、出力をそのまま報告する」と書く。

## stuck

次のどれかに当たったら、それ以上自分で追わずに `stuck` で委譲する。

- 同じ失敗が、異なる修正を 2 回試しても再現する。
- 原因の候補を 1 つに絞れない。
- 設計の前提が崩れ、再設計が要る。

依頼文には、試行の履歴(何を試し、何が返ったか)、失敗出力の原文、未解決の制約を載せる。

## 委譲先が断ったとき

断った委譲先の役割は、報告の先頭の「役割 ID」で知る。報告に役割 ID が無いときは、次の順で知る。

1. `pick-delegate` の出力が会話に残っていれば、返った `role` を使う。
2. Custom Agent モードなら、`.claude/agents/` の定義から frontmatter の `name:` の行でファイルを特定し、そのファイルの `better-agentics-role` の行だけを grep で取る。本文は読まない。
3. それでも分からなければ、役割を外さずに `pick-delegate` を呼び直す。

- 断った役割を `excludeRoles` に入れて `pick-delegate` を呼び直す。ユーザーが委譲先を示したときは、それを使う。
- 同じ委譲先が続けて 2 回断ったら、候補が尽きたものとして扱う。呼び直しで前と違う委譲先が返ったら、回数を数え直す。
- `excludeRoles` を付けた呼び出しで `no-candidates` が返ったときも、候補が尽きたものとして扱う。
- 候補が尽きたら、Jev にもユーザーにも判断を求めず、委譲しない。
  - 外側の手順の外では、自分で行う。
  - 外側の手順の中では、委譲先の指定を渡さず、外側の手順の既定の担い手に任せる。
  - `review` の候補が尽きたときは、自分で見直してよい。ただし必須のレビューを満たしたとはみなさず、委譲によるレビューを行えなかったことを報告に記録する。記録した後は、ユーザーへの提示・完了の報告・push に進んでよい。
- `excludeRoles` を付けない呼び出しの `no-candidates` は、設定の誤りとして `ok: false` の扱いにする。ただし `stuck` の `no-candidates` は行き詰まりの役割を外す設定を表すので、委譲せずに自分で行う。

## 外側の手順

外側の手順とは、このスキルの外のスキルやコマンドが定める手順を指す。その手順に従って作業している間、このセクションを当てる。

- 外側の手順とこのスキルの規律の両方に従う。
- 次の 2 つのときだけ、外側の手順を優先し、このスキルの側の規律を当てない。
  - 一方に従うと他方に反するとき。
  - 両方に従うと、同じ目的の手順が重なるとき。例は、同じ変更を両方の手順がそれぞれレビューすることである。
- 優先するのは、名前で起動した外側の手順に限る。名前で起動したとは、次のどれかを指す。
  - ユーザーか起動のプロンプトが、スキル名・コマンド名を挙げて起動した。
  - CLAUDE.md・rules・hook の注入文が、名前を挙げて起動を求めた。
  - 名前で起動した手順が、名前を挙げて起動させた。
- 説明文を見て自分から読み込んだスキルとの間で上の 2 つに当たるときは、このスキルの規律を優先する。
- 外側の手順のスクリプトが作業の単位ごとに委譲先の指定を受け取るときは、作業の種類で `reason` を選んで `pick-delegate` を呼ぶ。レビューは `review`、行き詰まりの打開は `stuck`、それ以外(実装・設計・修正・テストなど)は `split` とする。
- 行き詰まりの打開の単位が文書の修正なら、`stuck` で問わない。スクリプトへ渡す単位なら委譲先の指定を渡さず、外側の手順の既定の担い手に任せる。自分が担い手を決める単位なら、自分で行う。
- 外側の手順が委譲先を 1 件だけ受け取るときは、返った委譲先のうち `p` が最も高いものを渡す。
- 外側の手順に従って作業している間は、`needsContext` を付けない。Agent ツールで委譲する作業にも当てる。
- `ok: false` が返ったとき、外側の手順が人への聞き方を定めていれば、それに従う。定めていなければ、ユーザーへ報告して指示を待つ。
- 外側の手順が、人の判断の代わりに別の仕組みで判断すると定めていれば、このスキルが判断を仰ぐ場面もその仕組みに従う。
- `no-api-key`・`jev-failed` の失敗は、外側の手順が人の判断に代わる仕組みを定めていても、その仕組みに回さずユーザーに回す。

## 依頼文

- `preamble` が返ったら、依頼文の冒頭にそのまま置く。前置きが役割と規律を含むので、役割と規律を別に書かない。
- `preamble` が返らない Custom Agent モードでは、冒頭に担わせる役割を書く。規律は起動時に注入されるので書かない。
- 目的、確定した事実(パス・行番号)、制約、受け入れ基準を書く。
- Output Format は、Custom Agent モードでは定義本文に、Standard Agent モードと fork では前置きにあるので、依頼文で指定し直さない。外側の手順が出力の形を定めるときは、その形を依頼文に書く。
- 委譲先にスキルを使わせるときは、依頼文でスキルの名前と SKILL.md の絶対パスを示す。示していないスキルを、委譲先は読まない。
  - 絶対パスは、自分がそのスキルを読み込んだときに示された Base directory から取る。
  - 読み込んでいないユーザーのスキルは `~/.claude/skills/<skill>/SKILL.md`、プロジェクトのスキルは `<project>/.claude/skills/<skill>/SKILL.md` とする。
  - 読み込んでいないプラグインのスキルは、`~/.claude/plugins/installed_plugins.json` を Grep で `"<plugin>@` を含む項目の前後だけ読んで求める。ファイルは大きいので、丸ごと読まない。
  - 項目は、`scope` が `project` か `local` で `projectPath` が今のプロジェクトのものを選ぶ。git worktree の中では、`git rev-parse --path-format=absolute --git-common-dir` の親(元のリポジトリ)とも照らす。無ければ `scope: "user"` の項目を選ぶ。選んだ項目の `installPath` の下の `skills/<skill>/SKILL.md` を使う。
  - どれでも見つからないときは、名前だけを示す。Skill ツールの無い委譲先には、そのスキルが要る作業を渡さない。
  - プラグインのスキルの SKILL.md はプロジェクトの外にあり、委譲先がパスから読むと許可の確認が出る。確認に答える人のいないセッションでは、委譲先はパスから読めない。

### 文書の執筆を委譲するとき

- 依頼文に載せる内容は、自分で決めて渡す。
- 依頼文には、対象ファイルのパス・事実・決定事項・制約・受け入れ基準・章立て・用語・参照先のパスだけを、箇条書き・表・キーワードの形で書く。
- 依頼文には、対象ファイルの文体で書かれた段落や、そのまま貼り付けられる完成文を載せない。
- 成果物の本文に載せる語や文の例にだけ「本文に載せる」と添える。
- 成果物の本文に載せる例を示すときは、成果物で閉じた列挙にしないことを明記する。
- AI が読む文書の項目を書き換える依頼には、判断の軸を書く。軸だけで伝わらないときだけ例を添える。判断の軸を言葉にできないときは、委譲しない。
- 要件分析と報告の突き合わせの成果(要件と受け入れ基準の箇条書き、判断のメモ)は依頼文に書くものであり、ファイルとして残す文書ではない。この規律の対象外である。
