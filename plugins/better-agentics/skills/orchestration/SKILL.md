# オーケストレーターの規律

## 自分で行う作業と委譲する場面

- 調査・分析・要件確定・設計書と計画書の執筆・実装・テスト・検証は、自分で行う。
- 委譲するのは、次の 3 つの理由のどれかに当たるときだけとする。

| 理由 | 場面 |
| --- | --- |
| `review` | 自分の成果物を、自分以外の目で確かめる必要があるとき |
| `split` | 大きな作業を、自分と分担して進めるとき |
| `stuck` | 自分で原因を追っても解決しないとき |

- 委譲先は自分で選ばず、`pick-delegate` が返した定義で起動する。
- `pick-delegate` が `ok: false` を返したら、理由を問わず委譲も作業の続行もせず、`error` の種別と `message` をユーザーへ報告して指示を待つ。
- 必須のレビューの前に `ok: false` が返ったときは、ユーザーへの提示とコミットにも進まない。
- `pick-delegate` に渡す作業内容(`summary`)は英語で書く。

## pick-delegate の呼び出し

標準入力で JSON を渡す。出力は JSON の 1 行で、終了コードは常に 0 である。次は例示であり、値は実際の内容に置き換える。

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/pick-delegate.mjs" --dir "$PWD" <<'EOF'
{"reason": "review", "task": {"summary": "Review the design doc for the cache layer", "artifacts": ["docs/design/cache.md"]}}
EOF
```

| reason | 入力 |
| --- | --- |
| `review` | `{"reason": "review", "task": {"summary": string, "artifacts": string[]}}` |
| `split` | `{"reason": "split", "tasks": [{"id": string, "summary": string}]}`。`id` は配列内で一意にする |
| `stuck` | `{"reason": "stuck", "task": {"summary": string}}` |

- `review` と `stuck` の出力は `agents`、`split` の出力は `assignments` に委譲先を持つ。
- 各要素の `agent` を、Agent ツールの `subagent_type` にそのまま渡す。
- `split` の `assignments` は、入力の `id` ごとに委譲先を 1 つ持つ。

| `error` | 意味 |
| --- | --- |
| `invalid-input` | 入力が JSON として読めない、必須の項目が欠ける、`split` の `id` が重複する |
| `no-candidates` | 理由に対応する役割の定義が 1 つも無い |
| `duplicate-role` | 同じ役割を 2 件以上の定義が持つ、または候補の定義の名前が重なる |
| `no-api-key` | Jev を呼ぶ必要があるのに `TYPESAFE_API_KEY` が無い |
| `jev-failed` | Jev の呼び出しが失敗した、または応答の形が想定外だった |

## review

次の時点で、必ずレビューを依頼する。

1. 設計書・実装計画書を書き終え、ユーザーへ示す前。
2. 実装を終え、コミットする前。
3. 次のどれかに変更を加えたとき。変更の大きさは問わない。
   - 全セッションに効く設定(hooks など)
   - プロジェクトの指示(CLAUDE.md・rules など)が、変更を禁じているか、確認や手順を求めているパス
   - データ移行

2 のコードレビューは、次の条件を両方満たすときだけ省ける。

- 変更した全箇所の正誤を、型検査・テスト・lint・grep のいずれかで判定できる。
- 3 に当たらない。

コードレビューを省いたときは、判定に使った検査とその結果を報告に書く。判定に使う検査を示せない変更は検証困難として扱い、レビューを省かない。

進め方:

- レビュアーには、原本と満たすべき要件だけを渡す。自分の結論と、別のレビューの指摘は渡さない。
  - 文書のレビューでは、文書のパスを渡す。
  - コードのレビューでは、差分を取るコマンドを渡す(例: コミット前なら `git diff HEAD`、コミット済みの範囲なら `git diff <base>..<head>`)。値は実際の範囲に置き換える。
- `pick-delegate` が複数のレビュアーを返したら、全員を 1 つのメッセージで並列に起動する。
- 出力に `fallback: true` が付いていたら(Jev がどの候補も選ばなかった)、そのレビュアーで進め、ユーザーへの報告にその旨を添える。
- 再レビューは、前の巡と同じ定義を、`pick-delegate` を呼ばずに起動する。巡の数はこの組で数える。
- 指摘の採否は自分で決める。指摘が対立して採否の軸を言葉にできないときは、`AskUserQuestion` でユーザーへ聞く。
- critical・high・medium の指摘を直したときは、再レビューを依頼する。low だけを直したときは再レビューしない。
- 再レビューを 2 巡しても critical・high・medium の指摘が残るなら、ユーザーへ判断を仰ぐ。

## split

分担してよいのは、次のどちらかに当たる部分である。

- 並列化: 自分の作業と同時に進められ、状態を共有しない部分。
- 文脈の保護: 結論だけが要り、過程を手元に置く必要が無い部分。grep/read の反復が 3 ターン以上見込まれる探索と、多数のファイルへの機械的な一括変更が該当する。

分担の前提:

- 切り出す部分の仕様は、型・関数シグネチャ・ファイル配置・変更箇所の列挙の形で書いて渡す。
- 委譲先が追加の判断なしに進められる形にできない部分は、切り出さずに自分で行う。
- 全体の設計判断、部品の結合、最終検証は、自分の手元に残す。

手順:

1. 分担する作業を洗い出し、作業ごとに書き込むファイルの集合と、他の作業の成果を待つかを書き出す。
2. 次の条件を両方満たす作業同士を、同じ並列グループに入れる。
   - 書き込むファイルの集合が重ならない。自分の分担とも比べる。
   - どちらも相手の成果を入力にしない。
3. グループ内の全作業を、1 回の `pick-delegate` 呼び出しに渡す。
4. 返った委譲先を、1 つのメッセージで全員バックグラウンド起動する。その間に自分の分担を進める。
5. 全員が戻ったら差分を突き合わせ、型検査・テスト・ビルドを自分で 1 回実行する。
6. 依存がある作業は次のグループに回し、前のグループの成果を依頼文に載せる。

補足:

- 同じ定義が複数の作業に選ばれたら、同じ定義を複数起動する。
- 書き込むファイルの集合が重なる作業は、並列にせず順に委譲する。
- 並列化と文脈の保護のどちらで切り出した作業も、手順 1〜6 で扱う。探索のように書き込みの無い作業は書き込みの集合が空なので、他の作業と同じグループに入れられる。
- 並列中の委譲先に実行させてよい検査は、対象のファイルを指定して範囲を絞れるもの(対象を指定したテスト、対象を指定した lint など)に限る。依頼文には、使ってよい検査のコマンドを書く。
- プロジェクト全体が対象の検査(型検査・ビルド)と、ビルド出力・lockfile・lint の自動修正・git commit は、手順 5 で自分だけが行う。
- 依頼文には「変更範囲の外が原因の失敗は直さず、出力をそのまま報告する」と書く。

## stuck

次のどれかに当たったら、それ以上自分で追わずに `stuck` で委譲する。

- 同じ失敗が、異なる修正を 2 回試しても再現する。
- 原因の候補を 1 つに絞れない。
- 設計の前提が崩れ、再設計が要る。

依頼文には、試行の履歴(何を試し、何が返ったか)、失敗出力の原文、未解決の制約を載せる。

## 依頼文

- 冒頭に、担わせる役割を書く。
- 目的、確定した事実(パス・行番号)、制約、受け入れ基準を書く。
- 「サブエージェントである」旨とサブエージェントの規律は、起動時に自動で注入されるので書かない。
- Output Format は定義本文にあるので、依頼文で指定し直さない。
- 委譲先にスキルを使わせるときは、依頼文でスキル名を名指しする。名指しが無いスキルを、サブエージェントはロードしない。ロードには Skill ツールを使う。
- スキルを名指しできるのは、`tools` に `Skill` を持つ定義に限る。それ以外の定義には、要るセクション・手順・制約を依頼文へ書き写す。
- 名指しする前に、`wc -c` で本文と参照文書の合計を測る。30KB を超えるものは名指しせず、要るセクション・手順・制約だけを依頼文へ書き写す。

### 文書の執筆を委譲するとき

- 依頼文に載せる内容は、自分で決めて渡す。
- 依頼文には、対象ファイルのパス・事実・決定事項・制約・受け入れ基準・章立て・用語・参照先のパスだけを、箇条書き・表・キーワードの形で書く。
- 依頼文には、対象ファイルの文体で書かれた段落や、そのまま貼り付けられる完成文を載せない。
- 成果物の本文に載せる語や文の例にだけ「本文に載せる」と添える。
- 成果物の本文に載せる例を示すときは、成果物で閉じた列挙にしないことを明記する。
- AI が読む文書の項目を書き換える依頼には、判断の軸を書く。軸だけで伝わらないときだけ例を添える。判断の軸を言葉にできないときは、委譲しない。
- 要件分析と報告の突き合わせの成果(要件と受け入れ基準の箇条書き、判断のメモ)は依頼文に書くものであり、ファイルとして残す文書ではない。この規律の対象外である。
