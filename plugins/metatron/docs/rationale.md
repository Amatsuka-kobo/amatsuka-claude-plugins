# metatron の設計根拠

実装後も参照する必要のある判断の由来をまとめる。出典は `harness-docs/design/2026-08-16-metatron-design.md` と、
書式・パス解決の正本である `harness-docs/design/2026-08-16-file-contract-freeze.md` である。

## MCP サーバー化を撤回した経緯

当初は ARCHITECTURE / GOTCHAS の読み書きを MCP サーバーのツールとして提供する案だった。
`read_architecture` / `stage_architecture` / `commit_architecture` / `append_gotcha` 等をツールとして定義し、
サーバーを常駐させる。同じリポジトリに raguel-mcp の前例があり、ツール一覧に現れる発見性の高さが利点だった。

独立レビューでの反証を受けてこれを撤回し、**共有ライブラリ + 決定的 CLI + deny hook + 注入 hook**
(常駐プロセスなし)の構成を採った。撤回の根拠は 4 点である。

1. **読み経路がすべて MCP を迂回する。** SessionStart 注入はファイル直読、Codiel の hooks もファイル直読、
   セッション中の参照は Read ツールで足りる。読みで MCP を通る経路がひとつも無く、
   MCP の存在理由が「低頻度の書き込み検証」だけに縮退する。常駐プロセスを 1 つ増やす対価に釣り合わない。
2. **MCP でも強制にはならない。** ツールの呼び出しは任意であり、呼ばずに Write で直接書けば素通りする。
   この点で CLI と同じである。「MCP にすれば守られる」というのは誤りで、守らせるのは deny hook である。
   同じ強制力なら、常駐プロセスを持たない CLI のほうが軽い。
3. **検証ロジックが二重実装になる。** deny hook は MCP を呼べない実行文脈で動く
   (hook は独立プロセスであり、MCP クライアントを持たない)。検証をサーバー内に閉じると
   hook 側にも同等の判定を書くことになり、同じ規則の実装が 2 つできる。
   共有 TypeScript ライブラリに 1 本化し、CLI と 2 つの hook がそれを取り込む構成なら実装は 1 つで済む。
4. **raguel-mcp は前例にならない。** raguel-mcp は run の各フェーズで必ず通る高頻度ゲートであり、
   常駐のコストが呼び出し回数で償却される。metatron の書き込みは初回生成と時々の記録・更新だけで、
   頻度プロファイルがまったく異なる。同じリポジトリに MCP サーバーがある事実は、
   metatron を MCP にする根拠にならない。

MCP の唯一の明確な利点である発見性は、2 経路で代替する。SessionStart 注入文の先頭に置く CLI 案内は
毎セッション必ずコンテキストに載り、deny hook の拒否メッセージは間違えた瞬間に正しい窓口を教える。
どちらも CLI の絶対パスを含むため、AI は metatron のインストール位置を知らなくても呼べる。

将来 MCP へ昇格する余地は残っている(サブコマンド体系はツール名に 1 対 1 で写せる)。
昇格を判断する材料が出たときに、設計書へ差し戻して決める。

## 真の強制点は deny hook だけである

metatron の目的は、現行 Codiel が「AI に守らせる指示」で保っていた品質
(承認なしに書き込まない・既存記述を削除しない・追記のみ)を、指示より強い形へ移すことにある。
移す先の候補は 3 つあり、強制力は次のとおりだった。

| 手段 | 強制力 |
| --- | --- |
| MCP ツール | 呼び出しは任意。呼ばずに Write で直接書けば素通り |
| CLI | 呼び出しは任意。同上 |
| PreToolUse deny hook | Edit / Write / NotebookEdit 経由の直接編集を、hook が正常動作する限り拒否する |

**真の強制点は deny hook だけである。** MCP ツールも CLI も、それ単体では
「行儀よく使えば安全な窓口」でしかない。したがって設計の中心を deny hook に置き、
「正本ファイルへの直接編集を拒否し、正しい窓口へ誘導する」構造にした。

CLI に価値が無いという意味ではない。deny hook は「直接書かせない」ことしかできず、
書式検証・採番・追記のみの規律・差分提示の強制は CLI が担う。両者は役割が違い、どちらも欠かせない。

## 保証範囲は限定的である

deny hook が守るのは「**Edit / Write / NotebookEdit 経由の直接編集を、hook が正常動作する限り拒否する**」
ところまでである。次の 3 つは対象外であり、「破りようがない」とは主張しない。

- **Bash リダイレクトによる書き込み。** `echo >> docs/GOTCHAS.md` は matcher に掛からない。
  捕捉するにはシェルコマンドの構文解析が必要で、誤検知と実装コストが釣り合わない。
- **人間のエディタでの編集。** hook は AI のツール呼び出しにのみ介在する。
  これは正しい挙動である。人間が特別なツール無しに読み書きできることは Markdown 保存の目的そのものだ。
  なお CLI のロックは CLI 同士の相互排除しか担わないため、人間がエディタで開いている最中に
  CLI が先頭挿入すると、人間側の保存で CLI の書き込みが消えうる。これは受け入れる
  —— 文書は git 管理下にあり、失われた変更は差分で気づけるためである。
- **hook 自身が失敗したとき。** 素通しする(後述のフェイル方針)。

この位置づけは「回避しようとする AI を止める設計」ではなく
「知らずに直接編集する AI を正しい窓口へ導く設計」である。

## なぜ SessionStart 注入なのか

現行、ARCHITECTURE / GOTCHAS は「サブエージェントが作業前に必ず読む」という**指示**で運用されている。
これには 2 つの弱点がある。

1. **Codiel の run の中でしか効かない。** 通常のセッションで人間が「このバグを直して」と頼んだとき、
   AI は GOTCHAS を読まない。過去に記録した罠を、記録した本人(のプラグイン)以外は踏み続ける。
2. **読むかどうかが AI の判断に委ねられる。** 「今回は関係なさそう」と判断されれば読まれない。
   GOTCHAS は「関係あると気づいていない罠」を伝える台帳であり、読む判断を読み手に委ねると、
   最も必要な場面で読まれない。

SessionStart hook で決定的に注入すればこの両方が解決する。
同じ理由で、「metatron の CLI で前提を確認せよ」という 1 行だけを注入する案も採らなかった。
それでは「呼ぶかどうか」が AI の判断に戻り、解決したはずの問題がそのまま残る。

## なぜサブエージェントにも注入するのか

SessionStart の `additionalContext` がサブエージェントへ継承される保証は、公式文書に無い。
一方、SubagentStart hook の `additionalContext` は、サブエージェントのコンテキストに足せる。
これは Claude Code の hooks の公式文書(Context7 の `/websites/code_claude`)で確かめた。

当初は、サブエージェントへ依頼文に実パスを埋めて必読させる運用を考えていた。
この運用では、読むかどうかが依頼を書く AI の判断に戻る。
依頼文に原文や要約を写すと、原文とずれても気づけない。
SubagentStart で決定的に注入すれば、メインセッションと同じ前提でサブエージェントが動く。

注入の中身は、サブエージェントが読むだけで足りる範囲に絞る。
CLI の案内と記録のタイミングは載せない。記録と文書の更新はメインセッションが行うためである。
載せきれない部分は、`node M ...` の代わりに文書のパスを Read する案内にする。サブエージェントには `M` が何か伝わらない。

SessionStart の注入文には、委譲の依頼文へ両文書の原文も要約も書き写さないよう書く。
この一文は、SubagentStart を登録した後でなければ事実に合わないので、登録と同じコミットで足した。

除外の設定キーは足さない。metatron の注入を切りたい利用者は `injection.enabled` で SessionStart と SubagentStart の両方を止める。

## なぜ記録のタイミングを hook でなく注入文に置いたのか

記録の要否は、依頼された作業を終えて完了を報告する前に確かめるのが最も良い。
hook は、この「作業の完了」を検出できない。Stop など、ターンの終わりに発火する hook は、ターンの終わりと作業の完了を見分けられない。
途中のターンでも発火するので、毎回通知するか、状態ファイルで抑止するかになる。

そこで検出を諦め、SessionStart の注入文に確かめる時点を書いた。
削れない部分に置くので、縮退してもプレビューに残る。文書が無いうちは記録先が無いので、`/metatron:init` の案内には入れない。

検討して採らなかった案は次のとおりである。

| 案 | 採らなかった理由 |
| --- | --- |
| Stop hook でこのセッションのコミット(reflog)と codiel の run の終了を合図にする | 途中のコミットでも通知する。コミットしない作業は拾えない。状態ファイルによる抑止が要る |
| 合図が出たときだけ `claude -p` で完了かを判定する | 子の Claude Code への hook の再帰、時間切れへの対処が要る |
| prompt 型の Stop hook で毎回判定する | 毎ターン LLM を呼ぶ |
| 作業ツリーが clean に戻ったときを合図にする | 未コミットのまま残すパス(このリポジトリの `docs/chat/` など)があると発火しない |
| TaskCompleted を合図にする | TaskUpdate ツールでしか発火しない |
| PreCompact で促す | 注入ができない(`decision` しか返せない) |

codiel の run の候補は、finalize が「結果レポートを出したら終了する」と定めているので、run の中では確かめない。
注入文は、結果レポートの候補を次のターンの初めに確かめるよう伝える。

## なぜ台帳へ移した GOTCHAS 候補を参照形に縮めず消すのか

ADR 候補は、ADR へ移した後に持続層のエントリを参照形(ADR の番号を指す短い形)へ縮める。
GOTCHAS 候補は同じ形にせず、台帳へ移したものも、移さないと決めたものも、エントリごと消す。

失敗の全文は、台帳の 1 か所だけに残す。参照形に縮めると、領域ファイルに失敗の索引がたまっていく。
索引は台帳の目次と二重になり、台帳側のタグ付けや統合に追随しない。

候補 ID が無いので、二重移行は台帳の同じタイトルで検出する。
`scan-gotcha-candidates` は候補ごとに `ledgerMatches`(同じタイトルの台帳エントリの ID)を返す。
台帳へ移した後の削除に失敗した候補は、次の走査で ID が出るので、人が同じ失敗かを確かめて消すだけを選べる。
タイトルの一致だけでは同じ失敗とは限らないため、機械では判定しない。

## なぜ Markdown ファイルに保存するのか

ARCHITECTURE / GOTCHAS を SQLite 等の内部 DB に持ち、ファイルを出力形式の 1 つとする案は採らなかった。
構造化クエリが自然になり、検索が速く、書式の破損が起きない、という利点はある。

不採用の理由は、**チーム資産としての性質を失う**ことである。DB では git でコミットできず、
PR でレビューできず、GitHub 上で読めず、metatron を入れていない人が読めない。
ARCHITECTURE は「新しく入った人が最初に読む文書」であり、その価値は
「特別なツール無しに読める」ことに強く依存する。DB はマシンローカルになりがちで、
チーム間で内容が同期しない。検索性能の懸念は、GOTCHAS が数百件規模に収まる想定では問題にならない。

## なぜ環境変数でパスを設定しないのか

`METATRON_ARCHITECTURE_PATH` 等でパスを指定する案は、実装が最も簡単で、設定ファイルの探索も解析も要らない。

不採用の理由は、**チーム内で位置が乱立する**ことである。環境変数は各自のシェル設定に書かれ、
リポジトリにコミットされない。A の環境では `docs/ARCHITECTURE.md`、B の環境では別の場所を見る、
という状態が容易に発生し、しかも**その食い違いは誰の目にも見えない**。
共有資産の位置は、共有された場所で宣言されなければならない。

設定ファイルとの併用(環境変数が優先)も採らない。優先順位を持つ設定は
「なぜ自分の環境だけ違う挙動なのか」の調査コストを恒常的に発生させる。

## なぜ ADR と GOTCHAS の記録を既定で無効にするのか

ADR と GOTCHAS の記録は、注入文の分量と、完了報告の前に記録の要否を確かめる手間をセッションごとに増やす。
ARCHITECTURE と rules だけで足りるプロジェクトや、記録の運用を決めていないチームには、その負担だけが残る。
そこで、2 つの記録を環境変数でオプトインにし、既定を無効にした。
ADR と GOTCHAS は独立に使えるので、変数も 2 つに分けた。

「なぜ環境変数でパスを設定しないのか」で挙げた「設定の食い違いが誰の目にも見えない」問題は、この変数にも当てはまる。
答えは置き場所にある。プロジェクトの `.claude/settings.json` の `env` に置けばリポジトリにコミットされ、チーム全員が同じ値で動く。
各自のシェル設定に置く運用は推奨しない。
パスと違い、この変数は有効・無効の 2 値だけを選び、値の食い違いが起きても、記録が止まるだけでファイルは壊れない。
そのため、設定ファイル(`metatron.config.json`)の契約には載せず、環境変数のままにしている。

変数はセッションの起動時に決まる。注入は SessionStart の値を使い、CLI は実行ごとの値を使うため、変数を変えたら新しいセッションを始める。

## フェイル方針が 2 層に分かれる

metatron のフェイル方針は 2 層に分かれる。層を混同しないことが重要である。

| 層 | 対象 | 方針 |
| --- | --- | --- |
| 第 1 層: 内容の検証 | CLI の書き込み系(検証・ハッシュ照合・採番) | **フェイルクローズド** |
| 第 2 層: 機構自身の動作 | 注入 hook・deny hook・設定の読み取り | **フェイルオープン** |

言い換えると、「書く内容が正しいか」は厳しく、「metatron が動いているか」は緩く判定する。
壊れた内容を書けば正本が壊れるので、書かずに止まるほうが常に安い。
一方、機構側で止めると、metatron の不具合がセッション開始やユーザーのあらゆる編集を妨げる。
拒否できなかった結果は「直接編集が 1 回通る」ことであり、
拒否機構の故障で全編集が止まることに比べれば桁違いに小さい損害である。

**codiel の PreToolUse hook はフェイルクローズド(catch で `ask` を出す)であり、方針が逆になる。**
これは矛盾ではなく、「止めたときの損害」の大きさが違うことによる。
codiel の hook が守るのは run の state であり、そこを取り違えたまま進むと run 全体が壊れる。
metatron の hook が守るのは 1 回の直接編集であり、見逃しても git の差分で気づける。
同じ形の機構でも、守っている対象の損害の非対称がフェイル方針を分ける。
