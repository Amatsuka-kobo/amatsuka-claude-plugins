# GOTCHAS

このプロジェクトで AI が実際にやってしまった失敗のパターンを蓄積する。
発見された失敗を、下記のフォーマットで追記していく。

## 運用ルール

- 新しいものを上に追加する。
- 同じパターンが 5 件以上蓄積されたら、スキルまたは Hook への昇格を検討する。
- 解決済みの項目は `[解決済み]` タグを付けて残す。削除しない。
- 陳腐化した項目は `[対象外]` タグを付けて残す。削除しない。

## 失敗パターン一覧

### [2026-08-14] GOTCHA-002: 他部署のタスクが見えるクエリを書いた

**タスク**: タスク一覧 API に「担当者が未設定のタスクだけを返す」フィルタを追加する。
**失敗内容**: `prisma.task.findMany` に `tenantId` の条件を書かず、全部署のタスクを対象にするクエリを実装した。RLS が有効な検証環境では 0 件になり、RLS を切っている開発環境では他部署のタスクが返った。
**原因 (推測)**: 同じディレクトリの既存クエリが `withTenant()` を経由していることに気づかず、`prisma` を直接呼ぶ形で書き足した。
**対策**: `src/server/**` から Prisma を呼ぶときは `src/server/db/with-tenant.ts` の `withTenant()` を経由する。`prisma.` で始まる呼び出しを書く前に、同じディレクトリの既存クエリを Read してヘルパの有無を確認する。
**昇格候補**: Yes

### [2026-07-22] GOTCHA-001: [解決済み] マイグレーションを手書きの SQL で追加した

**タスク**: `Task` テーブルに `archivedAt` 列を追加する。
**失敗内容**: `prisma/migrations/` に手書きの SQL ファイルを置いて適用し、`schema.prisma` を更新しなかった。次に実行された `prisma migrate dev` が差分を検出し、追加した列を落とすマイグレーションを生成した。
**原因 (推測)**: SQL を直接書くほうが速いと判断し、`schema.prisma` が正本であることを確認しなかった。
**対策**: スキーマを変更するときは `prisma/schema.prisma` を編集してから `pnpm exec prisma migrate dev --name <変更内容>` を実行する。`prisma/migrations/` に手でファイルを作らない。
**昇格候補**: Yes

**[解決済み] (2026-08-05)**: `prisma/migrations/**` を ARCHITECTURE の `## 保護パス` に追加し、直接編集を人間への確認事項にしたため。
