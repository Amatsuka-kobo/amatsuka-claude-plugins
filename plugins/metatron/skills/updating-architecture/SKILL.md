# ARCHITECTURE の更新

## 共通規律

- CLI の絶対パスは、SessionStart の hook が出す案内文、または直接編集の拒否メッセージに現れたものを使う。`get config` の `cli.path` も同じ値を返す。
- 案内が無いときはユーザーに絶対パスを尋ねる。インストール先を推測して組み立てない。
- 入力の渡し方・出力の読み方・失敗時の扱いは `../../references/cli-usage.md` を読む。
- 長い入力は Write ツールで一時ファイルへ書き、`--input <path>` で渡す。
- 引数へ本文を直接埋め込まず、一時ファイルのパスだけを渡す。
- ARCHITECTURE の更新は CLI だけで行う。Edit / Write で直接書き換えない。
- CLAUDE.md への @メンションの追記は `link-claude-md` だけで行う。
- ARCHITECTURE と CLAUDE.md のどちらに書くかは `../../references/document-boundary.md` に従う。

## 起点と手順の省略

更新のきっかけが何であっても、手順 1 から順に進める。

- きっかけには、乖離の検出の依頼、監査の依頼、1 セクションの修正、実装計画書に書かれた CLI の手順、自分の作業で気づいた変更を含む。
- 監査の依頼(`/metatron:audit` など)では、手順 3 の後に「監査」の手順を行い、その候補も手順 4 に並べる。
- 監査の依頼は「依頼された変更」に当たらない。監査の候補は、ほかの候補と同じく手順 4 で 1 件ずつ選ばせる。
- ユーザーが依頼した変更は、手順 4 の一覧に「依頼された変更」として並べる。承認済みの計画書に書かれた変更も含む。
- 依頼された変更は、依頼の時点で更新が選ばれたものとして扱う。更新するかどうかを手順 4 で選び直させない。
- 依頼された変更と同じ内容の候補が手順 2 と 3 で見つかったときは、依頼された変更として 1 件にまとめる。
- 依頼や計画書の承認は、手順 9 の diff の承認に代えない。
- 自分の作業で気づいた変更は、手順 2 と 3 の候補と同じく手順 4 で選ばせる。
- 対象が 1 件だけ・数行だけのときも、手順を省かない。
- 手順を飛ばすのは次の場合だけとする。
  - 手順 4 で選ばれた対象が無く、手順 5〜10 で扱うものが無い場合
  - 監査だけの依頼で、手順 2 の `diff-architecture` を飛ばす場合(手順 2 の `get architecture` は行う)
  - 手順 4 で旧構成の移行が選ばれず、手順 11 で扱うものが無い場合
  - 手順 4 で @メンションの追記が選ばれず、手順 12 の対象も無い場合
  - 手順 4 で CLAUDE.md から消す候補と CLAUDE.md へ移す候補がどちらも選ばれず、「CLAUDE.md の変更」で扱うものが無い場合

## 1. 設定の確認

`get config` を 1 回実行し、ARCHITECTURE の解決先パスと存在の有無を確かめる。

## 2. 乖離の検出

- `diff-architecture` を実行し、`findings` と `skipped` を取る。
- `get architecture` で現行の本文を取る。手順 4 で候補に併記する「現行の記述」にも使う。
- 依頼された変更と自分で気づいた変更が、ARCHITECTURE の他の部分を古くしていないかを確かめる。確かめるときは、この結果と現行の本文を使う。
- `diff-architecture` が返すのは決定的に検出できる乖離だけである。対象はドメインマップの穴、死んだ glob、セクションの欠落、残った旧見出し(`legacy_section`)とする。技術スタック・コマンド定義の突き合わせ、ディレクトリ構成の突き合わせは `skipped` で返る。
- `findings` に `ADR 一覧` の `legacy_section` があれば、1 件の候補(種別「旧 ADR 一覧」)に加える。`detail` には ADR 機能を廃止したことと、削除できることが載っている。
- それ以外の `legacy_section` は、手順 3 の「旧構成の移行」で扱う。
- 書かれていないディレクトリは乖離として扱わない。置き場を迷うディレクトリが新しくできたときだけ候補に加える。
- ディレクトリの消失は CLI が断定しない。`skipped` の「ディレクトリの実在の未確認」に並ぶのは、インラインコードで書いた `/` を含むパスのうち、ルートから実在を確かめられなかったものである。パッケージ内の相対パスやリンクの先など、どこを指すかを読んで確かめ、消えていたものだけを候補に加える。
- ツリー(コードフェンスの中)と 1 語(`legacy/` など)で書いたディレクトリは、未確認の一覧にも並ばない。実在するかを自分で確かめる。
- `skipped` の「ドメインマップの死んだ glob の未確認」に並んだ glob は、走査が入らない除外ディレクトリやシンボリックリンクの中に一致しうるため判定されていない。一致するファイルがあるかを確かめ、無いものだけを候補に加える。
- `## 技術スタック` と `## コマンド定義` は、`diff-architecture` の `sources` に並んだファイルを読んで確かめる。書かれた技術とバージョン、書かれたコマンドが消えたと確かめられたものだけを候補に加える。
- `sources` は読む起点であり、網羅していない。ランタイムのバージョン定義(`.nvmrc` など)・ビルド設定・ツールに組み込みのコマンド(`go test` など)は `sources` の外にある。`sources` に見当たらないだけでは候補にせず、該当しそうなファイルを探して確かめる。
- `sources` にあってセクションに書かれていない依存とコマンドは、乖離として扱わない。セクションに載せる粒度は `../../references/architecture-format.md` に従う。
- `skipped` に理由付きで返った項目は、その実行では検出していない。判断が要るときは該当ファイルを読んで自分で確かめ、結果を候補に加える。
- 散文の内容が実装と食い違うといった意味的な乖離は検出されない。実装 diff を見て気づいた点は、`findings` に無くても候補に加える。
- `findings` が 0 件でも、気づいた意味的な乖離があれば候補に加える。「乖離なし」で終えない。

## 3. 旧構成と @メンションの確認

- 旧 rules の置き場は、`metatron.config.json` に旧版の `paths.rulesDir` があればその場所、無ければ docRoot の `.claude/rules/metatron/` である。
- 置き場に `conventions.md`・`protected-paths.md`・`testing-policy.md` のどれかが残っているかを確かめる。置き場に他のファイルしか無いときは旧 rules として扱わない。
- 次のどちらかがあれば、「旧構成の移行」を 1 件の候補に加える。
  - `ADR 一覧` 以外の `legacy_section`(`## レイヤー構造`・`## ディレクトリ構成と責務`・`## 保護パス`)
  - 旧 rules のファイル
- 「旧構成の移行」を候補にしたときは、`## ディレクトリ構成`・`## 禁止事項`・`## 変更時の追随`・`## テスト方針` の欠落のうち、旧見出しか旧 rules に移す元があるものをこの候補にまとめ、別の候補にしない。移す元が無い欠落は通常の欠落の候補に残す。
- 「旧構成の移行」の候補には、移行しないと旧見出しのセクションは本文を直せず、削除しかできないことを添える。
- 旧見出しの本文に当たる候補は、別の候補にせず「旧構成の移行」に合流させ、手順 11 の a で移し先のセクションに反映する。移行が選ばれなかったときは、反映できなかった候補として手順 13 で報告する。
- 依頼された変更が旧見出しの本文に当たるときは、旧見出しには書けないため、「旧構成の移行」も依頼されたものとして扱う。手順 4 で移行を選び直させず、手順 11 の a で依頼された変更を移し先のセクションに反映する。
- docRoot の `CLAUDE.md` と `.claude/CLAUDE.md` のコードの外に、`get config` の `architecture.relative` を指す `@<相対パス>` があるかを確かめる。`.claude/CLAUDE.md` の行は `../` を付けたパスで書かれている。
- 欠けている @メンションがあるか、`get config` の `configExists` が `false` のときは、「@メンションの追記」を 1 件の候補に加える。設定ファイルは手順 12 の `link-claude-md` が作る。旧構成の移行で旧 rules を移すときは、移行の中で追記するので別の候補にしない。
- どちらも `diff-architecture` では検出されない。SessionStart の案内文が移行や追記を促していても、ここで自分で確かめる。

## 削れる内容の確認

監査の依頼でも、監査でない更新でも行う。

- `../../references/writing-discipline.md` の「削れる内容」と `../../references/document-boundary.md` を読む。
- 手順 2 で取った全文を、「削れる内容」の 4 種類で読み、当たる箇所を候補に加える。旧見出しの本文には候補を作らず、手順 11 の a の起草で当てる。
- 重複を判定するため、docRoot の `CLAUDE.md` と `.claude/CLAUDE.md` を読む。`CLAUDE.local.md` と、CLAUDE.md が @ で取り込む他の文書は読まない。どちらも無いときは、CLAUDE.md との重複を 0 件として他の観点だけで進める。
- CLAUDE.md との重複は、`document-boundary.md` で置き場を決める。ARCHITECTURE が置き場でなければ ARCHITECTURE から消す候補に、CLAUDE.md が置き場でなければ CLAUDE.md から消す候補にする。
- 古くなった記述は、手順 2 の `findings`・`skipped` と、本文に出てくるパスの実在で判定する。監査だけの依頼で `diff-architecture` を飛ばしたときは、本文のパスの実在を自分で確かめる。
- 手順 4 では、これらの候補を種別「削れる内容」としてまとめる。各候補に、当たった種類と根拠の事実(重複の相手の箇所、写しの元のファイルと項目、実在しないパス)を併記する。

## 監査

書式と執筆規律の現行の規定に、既存の文書が合っているかを確かめる。監査の依頼のときだけ行う。

- `../../references/architecture-format.md`・`../../references/writing-discipline.md`・`../../references/document-boundary.md` を読む。
- ARCHITECTURE の各セクションを規定と照らし、合わない箇所を候補に加える。
- 書式の表に無い見出しは候補に加える。旧見出しは「旧構成の移行」の候補に、`## ADR 一覧` は「旧 ADR 一覧」の候補に回し、監査の候補と二重にしない。監査だけの依頼でも、旧見出しの有無は `get architecture` の本文で確かめる。
- 旧見出しの本文には監査の候補を作らない。書き方は移行の起草で直す。
- CLAUDE.md に書く内容(`document-boundary.md` の作業の進め方)が ARCHITECTURE にあれば、CLAUDE.md へ移す候補に加える。CLAUDE.md に同じ内容が既にあるときは「削れる内容」の候補で扱い、二重にしない。
- 候補には、当たった規定の文書名と項目を添える。
- 監査の候補は書き方だけを直す。書かれた事実が実装と食い違うときは、監査ではなく乖離の候補として扱う。「削れる内容」の候補はこの限定を受けない。
- 手順 4 では、監査の候補を種別「監査」としてまとめる。

## 4. 候補の提示と選択

- 依頼された変更、手順 2 と 3 の候補、削れる内容の候補、監査の候補を 1 つの一覧に並べる。
- `get architecture` の `lineCount` が `lineLimit` を超えているときは、一覧の先頭に行数と目安を書き、「削れる内容」の候補を他の種別より先に並べる。削っても超えるときの分割は、ユーザーと検討する事項として伝え、このスキルでは行わない。
- 候補は種別ごとにまとめ、1 件を 1 行で示す。
- 各候補に、現行の記述と実装側の事実を併記する。監査の候補には、実装側の事実の代わりに当たった規定を併記する。
- 依頼された変更のほかに候補が無いときも、乖離・削れる内容・旧構成の移行・@メンションの追記の候補が 0 件だったことを一覧に書く。
- 依頼された変更を除く候補は、更新するかしないかを 1 件ずつ選ばせる。全件を一括で更新に倒さない。
- 更新しないと選ばれた候補は、その回では扱わない。

## 5. 起草

- 文面は `../../references/writing-discipline.md` の執筆規律に従って書く。
- セクションごとに書く内容は `../../references/architecture-format.md` に合わせる。
- 欠けているセクションを足すときは `scan` を実行し、その事実で埋まる範囲だけを草案にする。埋まらない箇所は推測せずユーザーに聞く。
- `## 禁止事項`・`## 変更時の追随`・`## テスト方針` の草案を `scan` の事実から起こさない。移す元が無く、セクションが欠けているときは `../../docs/ARCHITECTURE.example.md` の該当セクションの記入例を型にし、既存の設定ファイルと文書から既定の草案を作る。
- `## 禁止事項` の起草では、`../../references/check-format.md` の `no-import` で判定できる禁止(import の方向)に、`json metatron:checks` の定義の案を添える。定義を書いたら、手順 10 の書き込みの後に `check` を実行し、違反と終了コードを手順 13 で報告する。
- `document-boundary.md` で CLAUDE.md に当たる内容は ARCHITECTURE に書かない。起草中に気づいたとき(依頼された変更に含まれるときを含む)は、起草から外し、CLAUDE.md へ移す候補として手順 4 の一覧に戻して選ばせる。依頼された変更を選び直させない規定の例外である。書き込み先が ARCHITECTURE から CLAUDE.md に変わるので、改めて選ばせる。
- `## ADR 一覧` を削除する候補を選ばれたときは、種別(「旧 ADR 一覧」「監査」)を問わず、本文を退避するかをユーザーに確かめる。
  - 退避するときは、ユーザーが選んだパスへ `## ADR 一覧` の本文を Write で写す。決まった置き場が無いときは、移動先を提案してから写す。
  - 写し終えてから、手順 8 で `{ "heading": "ADR 一覧", "remove": true }` を stage する。
  - 退避しないと決まったときは、写さずに削除する。

## 6. サブエージェントによる簡潔化

- 手順 5 の草案をすべてサブエージェントに渡し、`writing-discipline.md` の規律を守った上でより簡潔にさせる。
- コードフェンスの中身(`metatron:domains` のブロックなど)は、簡潔化の対象から外すよう依頼文に書く。
- 返った文面で、事実が変わっていないことと、対象から外した部分が手順 5 の草案と一字一句同じことを確かめてから、手順 7 で使う。

## 7. 草案の提示

- 1 セクションにつき、草案と確認してほしい点 1〜3 個を 1 メッセージで示す。
- 残す部分と差し替える部分を、提示の時点で分けて示す。

## CLAUDE.md の変更

手順 4 で CLAUDE.md から消す候補か、CLAUDE.md へ移す候補が選ばれたときだけ、手順 7 の後、手順 8 の stage より前に行う。CLAUDE.md へ先に書くので、否認されても内容は ARCHITECTURE に残る。

- 書き換える先は、docRoot の `CLAUDE.md` とする。それが無く `.claude/CLAUDE.md` だけがあるときは `.claude/CLAUDE.md` とする。どちらも無いときに移す候補が選ばれたら、承認を得てから Write で `CLAUDE.md` を作る。
- 消す候補は、消す行とパスを示す。移す候補は、追記する文面と追記する位置を示す。移す文面の見出しは CLAUDE.md の見出しの階層に合わせ、既存の行と重なる部分は外す。
- 書き換えてよいかの明示的な承認を得てから、Edit で書き換える。示した行の他は書き換えない。
- 移す候補の ARCHITECTURE 側の削除は、CLAUDE.md へ追記した後に、手順 8〜10 の stage と承認で行う。追記を否認された候補は、ARCHITECTURE 側の削除を stage に含めない。
- 消した行と追記した行を手順 13 の報告に使う。

## 8. stage

- ARCHITECTURE のセクションは `stage-architecture` で渡す。
- `stage-architecture` に `規約` の見出しを渡さない。指定すると `unknown_heading` で返る。既存の ARCHITECTURE に `## 規約` が残っているときは、`{ "heading": "規約", "remove": true }` で消す。

## 9. diff の提示と承認

- 返った diff を提示し、書き込んでよいかの明示的な承認を得る。
- `stage-architecture` の `lineCount` が `lineLimit` を超えているときは、diff と併せて行数と目安を示す。
- `stage-architecture` が exit 0 で返ったことを承認と読み替えない。
- 承認は stage 1 回につき 1 回得る。複数の stage を 1 回の承認でまとめない。
- 提示の前に `diff.truncated` を見る。省略の有無を `diff.unified` の文面から判断しない。
- `diff.truncated` が `false` のときは `diff.unified` を要約せず全文提示する。長いときは分割して提示する。
- `diff.truncated` が `true` のときは `diff.unified` を提示に使わず、`diff.sections` の `before` / `after` をセクション単位で全文提示する。
- セクション単位でも一度に提示しきれないときは、`diff.sections` の `heading` を一覧で示し、どのセクションから見るかをユーザーに尋ねる。
- 承認の後に文面を足さない。足すときは手順 8 からやり直して承認を取り直す。

## 10. 書き込み

- 手順 9 で承認を得た staging だけを `commit-architecture --staging-id <id>` で書き込む。
- staging の期限切れや `file_changed` で commit が失敗したときは、現行を読み直して手順 8 からやり直す。

## 11. 旧構成の移行

手順 4 で旧構成の移行が選ばれたときだけ行う。a から d の順に進め、承認は段階ごとに得る。複数の段階を 1 回の承認でまとめない。

- a. 新しい見出しの草案を起こし、旧見出しを消す。旧見出しが無く、旧 rules の `protected-paths.md`・`testing-policy.md` も無いときは a を飛ばす。
  - 材料は、旧見出しの本文と、旧 rules の `protected-paths.md`・`testing-policy.md` の本文である。旧 rules は 1 行目の `# 見出し` と、`> この文書は metatron の管理下にある。` で始まる管理者表示の行を除いて使う。
  - 移し先は `../../references/architecture-format.md` の旧見出しの表に従う。`protected-paths.md` は旧見出しの `## 保護パス` と同じく、触らないパスを `## 禁止事項` へ、変更に慎重を要するパスを `## 変更時の追随` へ分ける。`testing-policy.md` は `## テスト方針` へ移す。
  - 草案は手順 5〜7 の起草・簡潔化・提示を通す。起草では `writing-discipline.md` の「削れる内容」の 4 種類を当て、同じ決まりが 2 か所にあれば書式の規定で持ち主のセクションに寄せる。
  - ARCHITECTURE に同じセクションが既にあるときは、現行の本文と移す本文を並べて示し、どちらを残すか、合わせた文面にするかをユーザーに決めてもらう。
  - 新しい見出しの `body` と、旧見出しの `{ "heading": "<旧見出し>", "remove": true }` を 1 回の `stage-architecture` に入れる。diff の提示と承認、書き込みは手順 9 と 10 に従って `commit-architecture` で行う。
- b. `conventions.md` の本文(1 行目の `# 見出し` と管理者表示の行を除く)を CLAUDE.md へ移す。
  - 移す先は手順 12 の追記先と同じ CLAUDE.md とする。どちらの CLAUDE.md も無いときは、承認を得てから Write で作る。
  - `conventions.md` が無いときは b を飛ばす。
  - CLAUDE.md の既存の内容と重なる行は移す文面から外す。
  - 移す文面と追記する位置を示し、承認を得てから Edit で追記する。移す文面の中の見出しは CLAUDE.md の見出しの階層に合わせる。
- c. 手順 12 に従って `link-claude-md` で @メンションを追記する。旧 rules が無いときは c を飛ばし、@メンションの欠落は手順 3 の候補で扱う。
- d. 旧 rules の 3 ファイルを削除する。
  - 旧 rules の本文を a と b のそれぞれで書き込んだか、移さずに捨てるとユーザーが決めた後に行う。旧 rules が無ければ d を飛ばす。
  - 削除するのは置き場の `conventions.md`・`protected-paths.md`・`testing-policy.md` だけとする。置き場の他のファイルとディレクトリそのものは消さない。ただし既定の置き場 `.claude/rules/metatron/` が 3 ファイルを消して空になったときは、そのディレクトリも消す。
  - 削除するファイルの絶対パスの一覧を示し、承認を得てから Bash で削除する。
  - Bash の削除が拒否されたときは、ユーザーに `! rm <絶対パス>` の実行を依頼する。
- 否認された段階は書き込まずに次の段階へ進み、手順 13 で報告する。旧 rules の本文を a か b で移しておらず、捨てるとも決まっていないときは、d を行わない。

## 12. CLAUDE.md への @メンションの追記

手順 4 で @メンションの追記が選ばれたとき(設定ファイルが無いときを含む)と、手順 11 の c のときに行う。

- 追記する行は、`get config` の `architecture.relative` から `@<相対パス>` の形で組み立てる。
- 追記先は docRoot の `CLAUDE.md` とする。それが無く `.claude/CLAUDE.md` だけがあるときは `.claude/CLAUDE.md` とし、各行のパスに `../` を付ける。どちらも無ければ `CLAUDE.md` が新しく作られる。
- どちらかの CLAUDE.md のコードの外に既にある @メンションは、追記する行から外す。
- `metatron.config.json` が無いときは、`link-claude-md` が `{ "version": 1 }` の設定ファイルも作る。承認を求めるときに、作られる設定ファイルのパスも併せて示す。
- 追記先のパスと追記する行を示し、追記してよいかの明示的な承認を得る。
- 承認を得てから `link-claude-md` を実行する。入力もオプションも取らない。
- 返った `added` と `present` を手順 13 の報告に使う。

## 13. 報告

- 更新したセクション名を列挙する。
- 旧構成の移行では、段階ごとに行ったこと・否認されたこと・削除したパスと見出しを列挙する。
- 旧 ADR 一覧を削除したときは、退避したパス、または退避しないと決めたことを報告する。
- CLAUDE.md に追記した行と、既にあった行を列挙する。
- CLAUDE.md から消した行と、CLAUDE.md へ移して追記した行を列挙する。
- 「<更新したファイルのパス> を更新した(未コミット)。コミットするか」を 1 行添える。
- run の文脈から呼ばれたときは、この確認を添えない。呼び出し元のコミット規約が働く。
