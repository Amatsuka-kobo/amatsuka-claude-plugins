# GOTCHAS の記録

## 共通規律

- CLI の呼び出しは `../../references/cli-usage.md` に従う。
- 台帳の書式・記録の判断・タグの規則・昇格の基準は `../../references/gotchas-format.md` に従う。
- エントリ本文の文体は `../../references/writing-discipline.md` の執筆規律に従い草案を書いたのち、サブエージェントに同じ規律で検査させる。

## CLI の呼び出し

- 実行するコマンド行は `node <CLI の絶対パス> <サブコマンド>` の形にする。
- CLI の絶対パスは、セッション開始時に注入された案内か、文書の直接編集が拒否されたときのメッセージに現れる。コンテキストに現れたものをそのまま使う。
- 現れていないときはユーザーに絶対パスを尋ねる。インストール先を推測して組み立てない。
- `--input <path>` に渡す JSON は Write ツールで一時ファイルへ書いてから渡す。
- 引数へ本文を直接埋め込まず、一時ファイルのパスだけを渡す。
- ヒアドキュメントで stdin へ流さず、`--input` でパスを渡す。
- GOTCHAS の書き込みは CLI 経由だけで行う。Edit / Write で直接書き換えない。

## 手順

- [ ] 1. 記録の可否を判断する
- [ ] 2. 台帳の現状を確認する
- [ ] 3. エントリを起草する
- [ ] 4. `append-gotcha` で追記する
- [ ] 5. 状態が変わったエントリにタグを付ける
- [ ] 6. 昇格を検討する
- [ ] 7. 完了報告

## 1. 記録の可否

判断は `../../references/gotchas-format.md` の記録の判断に従い、1 問で行う。GOTCHAS と Raphael の抗体のどちらに記録するかは、同ファイルの `## Raphael の抗体との棲み分け` の節が判定する。

- No のときは記録せず、判断の結果と理由を報告する。理由を伝えたうえでユーザーがなお記録を指示したときは記録する。
- 「たぶん二度と起きない」のような推測で No にしない。判断はこの 1 問への Yes / No で行う。
- 記録を依頼されたこと自体は Yes の根拠にならない。依頼されたときもこの 1 問で判断する。
- 記録するかどうかに失敗の内容の恥ずかしさを持ち込まない。

## 2. 台帳の現状確認

- `get config` で GOTCHAS の解決先パスを確認する。
- `get gotchas --query <失敗を表す語>` で同じ事実が既に記録されていないかを確認する。
- 同じ事実が既にあるときは追記せず、既存の ID を報告する。同じ内容の重複エントリを作らない。
- `error: "not_created"` は台帳が未作成という事実であって異常ではない。`/metatron:init` を経ていないプロジェクトと、台帳が手で消されたプロジェクトで起きる。
- 台帳が無いときも `append-gotcha` が雛形ごと作る。記録を止めて初期化を案内しない。自前でファイルを作らない。
- 記録の途中で `init-gotchas` を呼ばない。台帳の生成は承認を要する操作であり、失敗の記録はその承認を待たない。

## 3. エントリの起草

- フィールドの構成と各フィールドに書く内容は `../../references/gotchas-format.md` に従う。
- `date` は省略する。省略時に当日日付が入る。過去に起きた失敗を後から記録するときだけ明示する。

## 4. append-gotcha

- 起草した JSON を一時ファイルへ書き、`append-gotcha --input <path>` で追記する。
- **追記に承認は求めない。** 誤って記録したものは手順 5 のタグで打ち消す。
- `countermeasure` が定型句だけだという警告が返ったときは、追記は完了している。本文は書き換えられないため、警告の内容を完了報告に載せる。
- `lock_timeout` が返ったときは、同じ文書へ書く別プロセスの完了を待って再実行する。ロックファイルを手で消さない。
- 非 0 で終わったときは `error` を読んで入力を直し、実行し直す。拒否を握り潰して先へ進まない。

## 5. タグ付け

状態が変わったエントリには `tag-gotcha --id <ID> --tag <解決済み|対象外> --reason <理由>` でタグを付ける。タグの値域と選び分けは `../../references/gotchas-format.md` に従う。

- `--reason` は必須とする。理由なしでタグを付けない。
- **エントリ本文を書き換えない。削除しない。** 状態の変化はタグと理由の追記だけで表す。
- 過去のエントリと矛盾する事実が分かったときは、新しいエントリを追記したうえで、古いエントリへ `対象外` のタグを理由付きで付ける。古いエントリを直さない。

## 6. 昇格の検討

- 昇格候補の基準と 5 件ルールは `../../references/gotchas-format.md` に従う。
- 集計は `get gotchas --promotion-candidates --exclude-tagged` で行う。件数を数えるために台帳を通読しない。
- どれが同種かの判定は人間とモデルが行う。CLI が返すのは候補の絞り込みまでである。
- 自動で昇格させない。検討を提案するところで止め、昇格先の設計はユーザーと決める。

## 7. 完了報告

- 追記したエントリの ID とタイトル、書き込んだファイルのパスを報告する。
- タグを付けたときは対象の ID とタグと理由を報告する。
- 記録しないと判断したときは、その理由を報告する。
- 「更新した(未コミット)。コミットするか」の確認を 1 行添える。
- 呼び出し元のフローがコミットまでを担っているとき(ハーネスの run の一部として起動されたとき)は、この確認を添えない。
