# ARCHITECTURE / GOTCHAS / rules の執筆規律

ARCHITECTURE の本文、ADR のエントリ、GOTCHAS のエントリ、rules の本文を書くときと更新するときに従う。

## 削る基準

- 実測値など、指示を正当化するための根拠は削る。
- 出典・引用・経緯は削る。
- 重複は削る。同じ内容の言い換え、要約と本文の重なりは一方だけを残す。
- 判断基準のない修飾(「適宜」「必要に応じて」「できるだけ」)は基準に置き換える。置き換えられないなら修飾ごと削る。
- 文書自身の構成や意図の説明は削る。
- 例は、性質が同じものだけを 1 つに絞る。性質の違う例は削らない。
- 引くために置かれた記述には、重複・例・出典の基準を当てない。範囲は「## 引くための記述の例外」に従う。

## 引くための記述の例外

引くための記述とは、開いた者が値を引く先になるブロック(技術スタックの表、ドメインマップ、コマンド定義など)であり、重複・例・出典の基準を当てない。

- 判定の単位は見出し配下のブロックとする。表・その表を導入する文・表の直後の補足は 1 ブロックとして同じ扱いにする。
- ブロック内で判定が割れるときは、そのブロックが「開いた者が値を引く先」か「読んだ者の動きを変える文」かで決める。前者は例外、後者は通常適用とする。
- 迷ったブロックは通常適用に倒す。
- 書き方の基準・残す基準は、引くための記述にも当てる。
- 例外が効くのは ARCHITECTURE と rules の、値を引く先のブロックだけである。GOTCHAS エントリには当てない。

## 残す基準

- 読んだ後にエージェントの振る舞いが変わる文は残す。
- 誤読を防ぐ制約(順序・範囲・例外・優先順位)は残す。
- 判断基準そのものは残す。
- 適用範囲や優先順位を判断する材料になる理由は、短く 1 か所にまとめて残す。
- 削る基準と残す基準の両方に当たる文は、残す基準を優先する。

## 書き方の基準

- 残す基準に当たる内容を保てる範囲で、最も短い文で書く。
- 望ましい動きの言い切り(「〜する」「〜しない」)で書く。命令形にしない。
- やむを得ず禁止を書くときは、「〜にせず、〜する」のように代わりに取る動きを併記する。
- 太字・`IMPORTANT`・「絶対に」で強調せず、条件と範囲で指示の重さを伝える。
- 出力の形を示す例を置くときは、例示であることと、値を実際の内容に置き換えることを明記する。
- 判断を示す例は、性質の違うものを 2 つ以上置く。
- 1 文に 1 指示だけを書く。
- 見出し毎の概要や 1 文だけの指示は、その見出しの直下に書く。
- 本文は箇条書きで書く。
- 構造体の補足・見出しの概要・1 文だけの指示は、箇条書きにせず散文で書く。
- 箇条書きにすると文脈が破綻する箇所は、散文で書く。

## 図の基準

- Mermaid 図は、全体の層と主要コンポーネントの関係が読める範囲に絞る。
- ノードとエッジを網羅目的で増やさない。網羅性が要るときは、図ではなく表で書く。
- 図に載せるのは、知らないと全体像を誤解する要素に限る。個々のクラス・関数・テーブルは図に載せず、`## ディレクトリ構成と責務` と `## ドメインマップ` に書く。
- 図は常時注入される。ノードを 1 つ足すたびに毎セッションのコストが増えるため、載せるか迷ったノードは載せない。
- rules では「常時注入される」を「起動時に読み込まれ、サブエージェントにも渡る」と読み替える。この基準は ARCHITECTURE 向けであり、rules に Mermaid 図は置かない。

## 適用の強さ

| 区分 | 対象 | 適用 |
| --- | --- | --- |
| 削る基準を強く適用 | `## システム概要` / `## 技術スタック` / `## レイヤー構造` / `## ディレクトリ構成と責務` / `## コマンド定義`、rules の 3 ファイル | 全文が常時読み込まれる。根拠・経緯・言い換えを残さない |
| 根拠系フィールドのみ例外 | `## ADR 一覧` の `背景` / `検討した選択肢` / `理由`、GOTCHAS の `原因 (推測)` | 削る基準のうち「実測値など、指示を正当化するための根拠は削る」だけを当てない |

## 例外の範囲

例外とは、根拠系フィールドを削らずに残すことである。冗長に書いてよいという意味ではない。

例外の範囲でも、次はすべて当てる。

- 書き方の基準。
- 残す基準。
- 削る基準のうち根拠以外(重複・言い換え・性質が同じ例を 1 つに絞ること・判断基準のない修飾)。

## GOTCHAS エントリ

- 直近 N 件は全文が毎セッション注入される。簡潔化を全面適用する。
- 各フィールドは 1 から 3 文に収める。
- 例示と重複を削る。
- 「引くための記述だから通読させない」を理由に簡潔化を外さない。

## ADR エントリ

- 注入されるのはタイトルと状態だけであり、長さの自由度は GOTCHAS エントリより高い。
- 自由度が高いのは長さだけである。書き方の基準と、根拠以外の削る基準は同じく当てる。

## 何を ADR にするか

次の 3 つをすべて満たすものだけを ADR にする。

- 覆すコストが大きい。後から変えると複数コンポーネントに波及する、またはデータ移行を伴う。
- 選択肢が実在した。比較した代替を具体的に挙げられる。
- 理由が自明でない。コードや設定を読んだだけでは、なぜそうしたかが分からない。

満たさないもの(ライブラリのバージョン選定、命名規約、ディレクトリの分け方)は ADR にせず、該当するセクションの本文に書く。

## ADR の書き方

ADR エントリの各欄は、次を満たすように書く。

- 背景には、なぜその決定が要ったか(解きたい問題、反していた考え)を書く。誰が何を担っていたかという現状の事実だけでは書かず、決定に至った問題を書く。
- 各欄は、事実と決定を落とさない範囲で最も短い文と最も少ない文数にする。削っても判断が変わらない語句は削る。
- 影響範囲には、その決定から直接生じる変化だけを 1 項目 1 文で書く。結論の繰り返しと、別の決定の帰結は書かない。
- 本文を書き換えないほかの ADR の記述が古くなるときは、その置き換えを影響範囲に 1 文で書く。ほかの ADR の一部を上書きするときは、上書きする範囲を結論に書く。
- 検討した選択肢は、互いに食い違わない書き方にする。前の選択肢を土台にするときは、「2 と同じだが、…」のように差分を書く。
- 理由には、採用した結論が背景の問題をどう解くかと選んだ根拠を書く。背景の文を繰り返さない。
