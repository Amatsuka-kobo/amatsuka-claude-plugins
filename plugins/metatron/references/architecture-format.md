## セクション構成

見出し名と順序を次に固定する。CLI の `heading` キーは `## ` を除いた見出し名をそのまま使う。

| # | 見出し | 機械可読 |
| --- | --- | --- |
| 1 | `## システム概要` | — |
| 2 | `## 技術スタック` | — |
| 3 | `## レイヤー構造` | — |
| 4 | `## ディレクトリ構成と責務` | — |
| 5 | `## ドメインマップ` | ○ |
| 6 | `## コマンド定義` | — |
| 7 | `## テスト方針` | — |
| 8 | `## 保護パス` | — |
| 9 | `## 規約` | — |
| 10 | `## ADR 一覧` | 採番のみ |

- すべてのセクションは任意である。欠けているセクションがあってもエラーにしない。
- `## ドメインマップ` だけを持つ最小ファイルも、正当な ARCHITECTURE として扱う。
- この表に無い見出しは書き込み経路が拒否する。書きたい内容は既存のセクションの本文に入れる。
- 同名の見出しが複数あるときは最初のものを採る。書き込み経路は重複を警告する(拒否はしない)。
- `# ARCHITECTURE` と最初の `##` の間に本文を置かない。冒頭の概要は `## システム概要` に書く。そこに本文があるファイルは、書き込み経路が警告を返す(拒否はしない)。
- ADR の追加と状態変更は `stage-adr` で行う。`heading` に `ADR 一覧` を渡すとエラーになる。

## システム概要
- プロジェクトの目的・利用者・主要な技術的制約を、散文 1 段落で書く。
- 全体アーキテクチャ図を Mermaid で置き、主要コンポーネントとその間のデータ・制御の流れを表す。
- 図に載せるのは全体像の把握に要る要素だけとする。個々のクラス・関数・テーブルは載せない。
- Mermaid の構文は検証しない。壊れた図はレンダリングされないだけで、他セクションの機械処理は動く。

## 技術スタック
- 言語・フレームワーク・主要ライブラリを表で並べ、各行にバージョン方針を書く。
- 併用を禁じるツールがあるときは、代わりに使うものを同じ行に併記する。

## レイヤー構造
- レイヤーを上から下へ列挙し、各レイヤーの責務を 1 行で書く。
- 依存の許される方向を明記する。
- 禁止される依存方向を明記する。書かれていない方向を読み手に推測させない。
- 禁止は「〜しない」で終えず、代わりに取る手段を併記する。例:「ドメイン層は UI 層を参照しない。UI へ値を渡すときは、ドメイン層がインタフェースを定義し UI 側が実装する」

## ディレクトリ構成と責務
- 主要ディレクトリをツリーで示し、各領域の責務を 1 行で書く。
- ツリーのパスを `## ドメインマップ` の glob と矛盾させない。
- 実装エージェントが置き場を迷うディレクトリに絞る。全ディレクトリを網羅しない。

## ドメインマップ
ドメイン名から、そのドメインに属するパスの glob への写像を、次のマーカーで始まるフェンスに書く。

````
```json metatron:domains
{ "frontend": ["src/app/**", "src/components/**"], "backend": ["src/server/**"] }
```
````

- データ形式は `{ "<ドメイン名>": ["<glob>", ...] }`。ドメイン名は任意の文字列で、固定語彙ではない。
- 分割が馴染まないプロジェクトは `{ "generic": ["**"] }` に縮退させる。
- ブロックが同一ファイル内に 2 個以上あるときは、最初のものを採る。
- 書き込み時に次の 4 項目を確認し、1 つでも反すれば書き込まない。読み取り時に反していれば「読めない」として扱い、例外を投げない。
  1. ブロック内が有効な JSON である。
  2. トップレベルがオブジェクトで、配列でない。
  3. 各値が 1 要素以上の文字列配列である。
  4. キーが 1 個以上ある。

このブロックを機械的に読むのは次の 4 つである。

| 読み手 | 与える解釈 |
| --- | --- |
| codiel `initializing-harness` | run 開始の前提条件(読めなければ run を開始しない) |
| codiel `orchestrating-runs` | 実装ステップのディスパッチ先の選択 |
| sandalphon `check-intent-env` | ASIS 探索のスコープ決定 |
| metatron の CLI と hook | `get domains` の応答と SessionStart 注入 |

codiel の `guard-write` hook はこのブロックを読まない。書き込み境界の強制をこのブロックに期待せず、必要なら各エージェントの担当範囲として書く。

## コマンド定義
- test / lint / typecheck / build / e2e の実行コマンドを表で並べる。
- コマンドは実行できる形そのままで書く。省略形・別名を書かない。
- 実行に前提(依存のインストール、環境変数)が要るときは、その前提を同じ行に書く。

## テスト方針
- ユニットテストと E2E の役割分担を書く。
- テストファイルの配置規約と命名規約を書く。
- 新規テストをどこへ足すかが、読んだだけで決まる粒度にする。

## 保護パス
- 触らないパスと、変更に慎重を要するパスを分けて列挙する。
- 触らないパスには、変更が必要になったときに取る手順(誰に確認するか)を併記する。
- 慎重を要するパスには、変更してよい条件(何を確認するか、どのテストを通すか)を書く。

## 規約
- コーディング規約・ブランチ運用・DoD を書く。
- 言語やフォーマッタの既定と同じ内容は書かない。
- 禁止事項には代わりに取る手段を併記する。

## ADR 一覧
- アーキテクチャ上の重要な設計判断を `### ADR-NNN: タイトル` のエントリで並べる。
- 追加と状態変更は `stage-adr` で行う。この節を直接編集しない。
- エントリを削除しない。覆した判断は `廃止` の状態で残す。
