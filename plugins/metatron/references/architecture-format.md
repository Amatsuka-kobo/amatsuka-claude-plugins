# ARCHITECTURE の書式

## セクション構成

見出し名と順序を次に固定する。CLI の `heading` キーは `## ` を除いた見出し名をそのまま使う。

| # | 見出し | 機械可読 |
| --- | --- | --- |
| 1 | `## システム概要` | — |
| 2 | `## 技術スタック` | — |
| 3 | `## ディレクトリ構成` | — |
| 4 | `## ドメインマップ` | ○ |
| 5 | `## コマンド定義` | — |
| 6 | `## テスト方針` | — |
| 7 | `## 禁止事項` | — |
| 8 | `## 変更時の追随` | — |

- すべてのセクションは任意である。欠けているセクションがあってもエラーにしない。
- `## ドメインマップ` だけを持つ最小ファイルも、正当な ARCHITECTURE として扱う。
- この表に無い見出しは書き込み経路が拒否する。書きたい内容は既存のセクションの本文に入れる。
- 同名の見出しが複数あるときは最初のものを採る。書き込み経路は重複を警告する(拒否はしない)。
- `# ARCHITECTURE` と最初の `##` の間に本文を置かない。冒頭の概要は `## システム概要` に書く。そこに本文があるファイルは、書き込み経路が警告を返す(拒否はしない)。
- 書き込み経路は、差し替えた後の全文を読み直してから保存する。次のどれかに当たれば書き込まない。
  - 閉じていないコードフェンスがある(`unclosed_fence`)。`body` の中のフェンスは `body` の中で閉じる。
  - `metatron:domains` のブロックが読めない(`invalid_domains`)。ドメインマップ以外のセクションに置いたブロックも対象になる。変更前からブロックが読めない文書では拒否しない。

- ARCHITECTURE と CLAUDE.md のどちらに書くかは `document-boundary.md` に従う。
- 同じ決まりを 2 つのセクションに書かない。どのセクションに書くかは、各セクションの規定に従う。
- 表に無い見出しのセクションが既存の ARCHITECTURE に残っているときは、`stage-architecture` の `{ heading, remove: true }` で消す。削除は見出し許可リストを参照しない。
- 旧見出し `## レイヤー構造`・`## ディレクトリ構成と責務`・`## 保護パス` は、次の移し先へ本文を移してから消す。

| 旧見出し | 移し先 |
| --- | --- |
| `## レイヤー構造` | レイヤーと許される依存方向は `## ディレクトリ構成`、禁止する依存方向は `## 禁止事項` |
| `## ディレクトリ構成と責務` | `## ディレクトリ構成` |
| `## 保護パス` | 触らないパスは `## 禁止事項`、変更に慎重を要するパスは `## 変更時の追随` |

## システム概要
- プロジェクトの目的・利用者・主要な技術的制約を、散文 1 段落で書く。
- 全体アーキテクチャ図は任意とする。図がないと全体像を誤解するときだけ Mermaid で置き、主要コンポーネントとその間のデータ・制御の流れを表す。
- 図に載せるのは全体像の把握に要る要素だけとする。個々のクラス・関数・テーブルは載せない。
- Mermaid の構文は検証しない。壊れた図はレンダリングされないだけで、他セクションの機械処理は動く。

## 技術スタック
- 表は言語・ランタイム・フレームワーク・データ層の 4 つの役割だけを持つ。1 行に 1 つの役割を書き、その役割を担う技術名とバージョンを同じセルに書く。
- Lint・テスト・バンドラ・パッケージマネージャなどの開発用ツールは表に載せない。併用を禁じるツール、バージョンを固定する方法、新しく足すときに揃える値のような方針があるときだけ、表の下の箇条書きに書く。
- バージョンはマイナーまで書く(例: `TypeScript 6.0`)。パッチと範囲指定(`^`・`~`)は書かない。
- 型定義・プラグイン・補助ライブラリのように、役割を担う技術に付随する依存は載せない。
- バージョン方針・更新の条件は、表の下の箇条書きに書く。表にカラムを足さない。
- 設定ファイルを開けば分かる個々の設定値は書かない。新しく足すときに揃える値だけを箇条書きに書く。
- 併用を禁じるツールがあるときは、代わりに使うものを表の下の箇条書きに併記する。

## ディレクトリ構成
- 主要ディレクトリをツリーで示し、各行に責務を 1 行で書く。
- 実装エージェントが置き場を迷うディレクトリに絞る。全ディレクトリを網羅しない。
- レイヤーがディレクトリに対応するときは、ツリーの行の責務の前に `[レイヤー名]` を付ける。レイヤーが 1 つしか無いプロジェクトは付けない。
- レイヤーがディレクトリに対応しないとき(ファイル名の接尾辞で層を分けるなど)は、ツリーの下にレイヤーの表を置き、上から下へ各レイヤーの責務を 1 行で書く。
- 許される依存方向をツリーの下に箇条書きで書く。禁止する方向は `## 禁止事項` に書く。
- ツリーのパスを `## ドメインマップ` の glob と矛盾させない。

## ドメインマップ
ドメイン名から、そのドメインに属するパスの glob への写像を、次のマーカーで始まるフェンスに書く。

````
```json metatron:domains
{ "frontend": ["src/app/**", "src/components/**"], "backend": ["src/server/**"] }
```
````

- データ形式は `{ "<ドメイン名>": ["<glob>", ...] }`。ドメイン名は任意の文字列で、固定語彙ではない。
- 分割が馴染まないプロジェクトは `{ "generic": ["**"] }` に縮退させる。
- ブロックが同一ファイル内に 2 個以上あるときは、最初のものを採る。
- 書き込み時に次の 4 項目を確認し、1 つでも反すれば書き込まない。読み取り時に反していれば「読めない」として扱い、例外を投げない。
  1. ブロック内が有効な JSON である。
  2. トップレベルがオブジェクトで、配列でない。
  3. 各値が 1 要素以上の文字列配列である。
  4. キーが 1 個以上ある。

このブロックを機械的に読むのは次の 4 つである。

| 読み手 | 与える解釈 |
| --- | --- |
| codiel `initializing-harness` | run 開始の前提条件(読めなければ run を開始しない) |
| codiel `orchestrating-runs` | 実装ステップのディスパッチ先の選択 |
| codiel `check-intent-env` | ASIS 探索のスコープ決定 |
| metatron の CLI | `get domains` の応答 |

codiel の `guard-write` hook はこのブロックを読まない。書き込み境界の強制をこのブロックに期待せず、必要なら各エージェントの担当範囲として書く。

## コマンド定義
- `scripts` などの定義から読めない使い方だけを表で並べる。候補が複数あるときの使い分け、実行の前提、引数の付け方が当たる。
- 定義の名前に実行コマンドを付けただけの行は載せない。
- 定義されていても使わないコマンドと、使えなくなったコマンドは載せない。
- コマンドは実行できる形そのままで書く。省略形・別名を書かない。
- 実行に前提(依存のインストール、環境変数)が要るときは、その前提を同じ行に書く。

## テスト方針
- ユニットテストと E2E の役割分担を書く。
- テストファイルの配置規約と命名規約を書く。
- 新規テストをどこへ追加するかが、読んだだけで決まる粒度にする。

## 禁止事項
- 禁止を 1 項目に 1 つ書き、代わりに取る手段を同じ項目に併記する。例:「ドメイン層は UI 層を参照しない。UI へ値を渡すときは、ドメイン層がインタフェースを定義し UI 側が実装する」
- 禁止する依存方向を明記する。書かれていない方向を読み手に推測させない。
- 触らないパスには、変更が必要になったときに取る手順(誰に確認するか)を併記する。
- 禁止する依存方向・触らないパス・読まないパスを含め、禁止はこのセクションにだけ書く。

## 変更時の追随
- パスまたは glob ごとに、変更したときに確かめること(通すテスト・確かめる条件)と、同時に直すものを書く。
- そのパスが何であるかは、`## ディレクトリ構成` に載っていれば書かない。載っていないパスは、何であるかを語句 1 つで添える。
- 禁止とその代わりの手段はこのセクションに書かず、`## 禁止事項` に書く。
