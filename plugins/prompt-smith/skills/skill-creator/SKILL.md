# スキルの作成

対象は SKILL.md、スキルの同梱物、`commands/*.md` のコマンド定義とする。
`../../references/description-guide.md` を併せて読み、description の共通基準に従う。

## 手順

1. 用途を聞く。
   - 何をするスキルかを聞く。
   - いつ発火すべきかを聞く。
   - 出力の形式を聞く。
   - テストケースの要否を判断する。
   - 会話に既に現れている情報は抽出し、埋まらない箇所だけを聞く。
2. 詳細を詰める。
   - edge case を聞く。
   - 入出力形式を聞く。
   - 例示ファイルの有無を聞く。
   - 成功条件を聞く。
   - 依存を聞く。
   - 使える MCP があるときは、先に調べてから質問する。
3. 配置を決める。
   - プラグイン同梱のスキルは `plugins/<plugin>/skills/<name>/` に置く。
   - プロジェクトのスキルは `.claude/skills/<name>/` に置く。
   - ユーザーのスキルは `~/.claude/skills/<name>/` に置く。
4. 構成を決める。
   - SKILL.md 単体で足りるかを判断する。
   - 決まりきった処理があるときは `scripts/` を加える。
   - 必要なときだけ読む文書があるときは `references/` を加える。
   - 出力に使う素材があるときは `assets/` を加える。
5. 本文を書く。
   - スキルの構造は「スキルの構造」に従う。
   - 文章は `prompt-smith:prompt-smith` の基準に従う。
6. description を書く。
   - 「description の規律」に従う。
   - `../../references/description-guide.md` の共通基準に従う。
7. 出力を評価する。
   - テストケースを作ると合意したときだけ「出力の評価」を行う。
8. eval セットの有無を確かめる。
   - eval セットが無いときは「eval セット」に従って作る。
9. eval セットの承認を得る。
   - 「eval セット」のレビュー手順に従う。
10. eval セットを保存する。
    - 承認済みの内容を「eval セット」の置き場へ保存する。
11. description の改善ループを回す。
    - `${CLAUDE_PLUGIN_ROOT}/scripts/run-loop.mjs` を使う。
12. 最良の description を適用する。
    - 出力の `best_description` を SKILL.md に書く。
    - 変更前後の description を示す。
    - 変更前後のスコアを示す。

既存スキルの description だけを直す依頼では、手順 1〜7 を飛ばして手順 8 から始める。

テストケースは、出力を客観的に検証できるときに作る。
ファイル変換・データ抽出・コード生成・決まった手順の実行では、テストケースを作る案を示す。
文体やデザインのように人の判断が要る出力では、テストケースを作らない。人の評価を使う案を示す。
どちらの案を採るかはユーザーが決める。

### 改善ループの実行

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-loop.mjs" \
  --eval-set "<eval セット JSON>" \
  --skill-path "<スキルディレクトリ>" \
  --model "<model-id>" \
  --max-iterations 5 \
  --holdout 0.4 \
  --runs-per-query 3 \
  --report auto
```

- `--skill-path` には SKILL.md ではなくスキルディレクトリを渡す。
- 反復せず発火だけを測るときは `${CLAUDE_PLUGIN_ROOT}/scripts/run-trigger-eval.mjs` を使う。
- 改善案を 1 回だけ得るときは `${CLAUDE_PLUGIN_ROOT}/scripts/improve-description.mjs` を使う。
- 並列数は `--num-workers` で変える。
- タイムアウトは `--timeout` で変える。
- 発火判定の閾値は `--trigger-threshold` で変える。
- 詳細ログは `--verbose` で出す。
- レポートの出力方法は `--report` で変える。
- 結果とログの保存先は `--results-dir` で指定する。
- `${CLAUDE_PLUGIN_ROOT}/scripts/generate-report.mjs` は直接実行しない。レポート生成は `run-loop.mjs` に任せる。

## スキルの構造

### 三層のロード

| 層 | 内容 | 読まれる時 |
| --- | --- | --- |
| メタデータ | `name` と `description` | 常時 |
| 本文 | SKILL.md の本体 | 発火した時 |
| 同梱物 | `scripts/`・`references/`・`assets/` | 必要になった時 |

- SKILL.md は 500 行以内を目安にする。
- SKILL.md が 500 行を超えるときは階層を足す。
- 階層を足したときは、どの文書を読むかの判断基準を本文に書く。
- `references/` の文書が 300 行を超えるときは目次を付ける。
- `scripts/` には決まりきった処理の実行体を置く。
- `references/` には必要なときだけ読む文書を置く。
- `assets/` には出力に使う素材を置く。
- 複数のドメインを扱うときは、ドメインごとに `references/` を分ける。
- ドメインごとに分けたときは、読む文書の選び方だけを本文に書く。

### 書き方のパターン

- 出力の形式が決まっているときはテンプレートで示す。
- 例は Input と Output の組で示す。
- 英語の本文は imperative で書く。
- 日本語の本文は `prompt-smith:prompt-smith` の文体基準に従う。

### 安全

- 悪意あるスキルは作らない。安全な範囲で代わりにできることを示す。
- 内容と description が食い違うスキルは作らない。両者の担当範囲を一致させる。

### 既存スキルを更新するとき

- `name` とディレクトリ名は維持する。
- 読み取り専用の場所にあるときは、書き込める場所へコピーしてから編集する。

### frontmatter

- SKILL.md のメタデータに `name` と `description` を書く。
- `compatibility` は必要なツールや依存があるときだけ書く。

## description の規律

- `description` は 1024 字以内にする。
- 100〜200 words 相当へ収める。
- 発火精度より 100〜200 words 相当の範囲を優先する。
- 上限に触れたときは、個別の記述を意図のまとまりへ言い換えて縮める。
- 発動する場面は「必ず使用する」と言い切る。
- 「役立つ」や「参照できる」のような控えめな表現は避け、発動する場面を断定する。
- ユーザーがスキル名や専門語を明示しない依頼も、発動する場面として書く。

## eval セット

### 形式

```json
[
  { "query": "ユーザーが実際に打ちそうな依頼文", "should_trigger": true },
  { "query": "近いが別の対応が要る依頼文", "should_trigger": false }
]
```

- eval セットは 20 問にする。
- `should_trigger: true` は 8〜10 問にする。
- `should_trigger: false` は 8〜10 問にする。
- クエリは具体的で現実的にする。
- クエリにはファイルパス・仕事や状況の背景・列名と値・会社名・URL・短い前置きのような手がかりを混ぜる。
- 小文字・略語・タイプミス・口語を混ぜる。
- クエリの長さを混ぜる。
- 明快な例ではなく境界事例を選ぶ。
- 1 手で終わる問は作らない。多段の作業や専門的な判断を要する問を作る。
- `should_trigger: false` は語や概念を共有する near-miss で埋める。
- 明らかに無関係な問は入れない。別の対応が要る問を入れる。

### 置き場

| 形態 | 置き場 |
| --- | --- |
| プラグイン同梱 | `plugins/<plugin>/evals/<skill-name>.json` |
| プロジェクトのスキル | `.claude/skills/<name>/evals/<name>.json` |
| ユーザーのスキル | `~/.claude/skills/<name>/evals/<name>.json` |

### 承認と回収

1. `${CLAUDE_PLUGIN_ROOT}/skills/skill-creator/assets/eval-review.html` を読む。
2. `__EVAL_DATA_PLACEHOLDER__` を eval セットの JSON 配列へ置換する。
3. `__SKILL_NAME_PLACEHOLDER__` をスキル名へ置換する。
4. `__SKILL_DESCRIPTION_PLACEHOLDER__` を現行の description へ置換する。
5. 置換した HTML を一時ファイルへ書き出す。
6. 一時ファイルをブラウザで開く。
7. ユーザーが編集して `Export Eval Set` を押すまで待つ。
8. ユーザーがエクスポートの完了を告げた後に `~/Downloads/` の `eval_set*.json` を探す。
9. 更新時刻が最も新しいファイルを回収する。
10. 回収した内容が 20 問、内訳、JSON 形式の条件を満たすかを確かめる。
11. 条件を満たさないときは、必要な修正を示してユーザーへ差し戻す。
12. 条件を満たすときは、承認済みの eval セットとして所定の置き場へ保存する。
13. 回収元のファイルは削除せず `~/Downloads/` に残す。

ダウンロードが見つからないときは保存先をユーザーに尋ねる。古いファイルを推測で選ばない。

## 出力の評価

### 手順

1. 現実的な試行プロンプトを 2〜3 個作る。試行プロンプトをユーザーに見せて合意する。
2. 各プロンプトについて、スキルを渡した実行と対照実行を同じターンでサブエージェントに起動する。
3. 実行中に assertion を起草する。客観的に検証できる合否条件としてユーザーに説明する。
4. 完了通知が届くたびにトークン数と所要時間を記録する。
5. 出力を採点する。2 構成の差を見る。
6. ユーザーに両方の出力を見せる。評価を聞く。
7. 本文を直す。
8. 手順 2 に戻る。

新規スキルの対照実行には、スキルを渡さない構成を使う。
既存スキルの対照実行には、編集前に控えた版を使う。

### 規律

- 2 構成の差でスキルの効果を判断する。
- 両構成とも合格する assertion は使わない。差を識別できる条件へ作り直す。
- 文体やデザインのような主観的な出力には assertion を付けない。人の判断に委ねる。
- 機械的に検証できる assertion はスクリプトで確かめる。
- 完了通知のトークン数と所要時間は、届いた順にその場で記録する。
- 個別の試行プロンプトに合わせて本文を細かくしない。失敗から意図のまとまりへ一般化する。
- 複数の試行で同じ補助スクリプトが作られたときは、そのスクリプトを同梱物にする。
- 効いていない記述は消して測り直す。指示を足すだけの改稿にしない。

## 測定の規律

- 1〜2 問の差で description や実装を疑わない。同条件で測り直す。
- 過去の測定と比べるときは `environment` の一致を確かめる。
- スコアは測定した環境に依存する。有効なプラグインやユーザースキルが変わった後の値を、変わる前の値と比べない。
- 全問が発火 0 で返ったときは、description ではなくタイムアウトを疑い、`--timeout` を伸ばして測り直す。
- 公式 `skill-creator` プラグインの `run_eval.py` / `run_loop.py` は使わない。代わりに `${CLAUDE_PLUGIN_ROOT}/scripts/` の移植版を使う。

## 相手に合わせた言葉選び

- 相手の習熟度は会話の手がかりから判断する。
- 「評価」と「ベンチマーク」は説明を添えずに使う。
- 「JSON」と「assertion」は、相手が知っていると分かるまで短い説明を添える。
