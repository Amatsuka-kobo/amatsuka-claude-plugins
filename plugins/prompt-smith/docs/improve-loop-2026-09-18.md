## 5. `buildImprovePrompt` の調査

- 失敗した問は query の全文と発火回数だけが提示される。合格した問は提示されないため、改善モデルには対照群がない。
- 移植元の tips は命令形と user intent を重視すると明示しており、規則の形は誘導していない。ただし、文の形は結果を動かさなかったため、この点は改修の根拠にしない。
- 長さを押し上げる経路は 3 つあった。
  1. 予算は最良案のバイト長に固定される。`run-loop.ts` は `Math.max(byteLength(best), LENGTH_FLOOR)` で算出するため、原文 1154 バイトが最良のままだった 3 反復では、予算も 1154 バイトだった。
  2. プロンプト本文は、長さと発火率の関係を伝えていなかった。
  3. 前回案を繰り返さず構造的に異なる案を試すことと、反復ごとに作風を変えることを促していた。
- 改修前のループが生成した案は、予算の 62%（712 バイト）と 96%（1106 バイト）を占めた。

## 9. バイト長は言語内の代理指標である

英語で書いた description を測った。英語は 1 バイト 1 文字である。

| UTF-8 バイト | passed | true 平均 | 案の作り方 |
| ---: | --- | ---: | --- |
| 415 | 20/20 | 0.97 | 人手 613 バイト案と同じ内容を英語で凝縮した |
| 565 | 12/20 | 0.20 | 707 バイト案から 2 つの節を削った |
| 650 | 12/20 | 0.20 | 707 バイト案から 1 つの節を削った |
| 707 | 12/20 | 0.20 | 同じ内容に節を足した |

- 英語の遷移は 415 バイトから 565 バイトの間にある。日本語の 717 バイトから 741 バイトより大幅に低い。
- したがって固定のバイト閾値は言語をまたいで成立しない。バイト長は言語内で比べるときの代理指標である。
- 英語の短い案は true 平均 0.97 だった。英語であること自体が大きく不利にはならない。
- 交絡がある。eval セットの 20 問のうち 17 問が日本語である。英語の description には言語をまたぐ不利が乗りうるため、英語側の遷移が低い理由を内容量だけに帰せない。
- `LENGTH_TARGET` の 600 は、日本語では遷移帯の十分下にあるが、英語では遷移帯より上にある。この定数を言語非依存とみなす前提は、この測定とは整合しない。予算の変更は本改修のスコープ外であり、行っていない。
