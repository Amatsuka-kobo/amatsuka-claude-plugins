- 不合格になるのは、毎回同じ 8 問だった。

## 5. `buildImprovePrompt` の調査

- 失敗した問は query の全文と発火回数だけが提示される。合格した問は提示されないため、改善モデルには対照群がない。
- 移植元の tips は命令形と user intent を重視すると明示しており、規則の形は誘導していない。ただし、文の形は結果を動かさなかったため、この点は改修の根拠にしない。
- 長さを押し上げる経路は 3 つあった。
  1. 予算は最良案のバイト長に固定される。`run-loop.ts` は `Math.max(byteLength(best), LENGTH_FLOOR)` で算出するため、原文 1154 バイトが最良のままだった 3 反復では、予算も 1154 バイトだった。
  2. プロンプト本文は、長さと発火率の関係を伝えていなかった。
  3. 前回案を繰り返さず構造的に異なる案を試すことと、反復ごとに作風を変えることを促していた。
- 改修前のループが生成した案は、予算の 62%（712 バイト）と 96%（1106 バイト）を占めた。

## 12. 予算を文字あたりバイト数で切り替える

分類は言語名ではなく、description の 1 文字あたりの UTF-8 バイト数で行う。実測した比は、多バイト文字を主とする description が 1.84 から 2.18、1 バイト文字だけの description が 1.00 だった。境目は 1.5 に置いた。

| 区分 | 遷移帯(実測) | target | floor |
| --- | ---: | ---: | ---: |
| 多バイト | 717〜741 | 600 | 680 |
| 1 バイト | 530〜565 | 450 | 500 |

- 多バイト側は従来の値を据え置いた。1 バイト側は新設した。どちらも予算の全域が、対応する遷移帯より下に収まる。
- コードパスや識別子が密な description は比が下がり、厳しい側の予算になる。予算が小さくなる方向であり、安全側である。
- `LENGTH_TARGET` と `LENGTH_FLOOR` を削除し、`bytesPerChar` と `lengthLimitsFor` へ置き換えた。`buildImprovePrompt` の target と、`run-loop` および `improve-description` の予算の床は、対象の description から解決される。プロンプト本文は target の数値以外を変えていない。
- バージョンを 0.5.0-dev へ上げた。コミットは `961d2b3` である。
- `pnpm run build`、`pnpm run lint`、`pnpm run typecheck`、`pnpm run test` はすべて終了コード 0 だった。テストは 2316 passed、失敗なしだった。
- バンドル経由の実機確認では、707 バイトの英語 description に対して改善プロンプトの target が 450 になった。
