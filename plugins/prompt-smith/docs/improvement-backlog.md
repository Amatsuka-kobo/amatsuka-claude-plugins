# prompt-smith 改修バックログ

2026-09-17 に metatron の 3 スキルを skill-creator で監査した際、測定スクリプトに見つかった欠陥と、運用で決めた方針を記録する。改修時の入力とする。

## 1. `callClaudeText` が作業ディレクトリを隔離しない

**場所**: `src/lib/claude-cli.ts` の `callClaudeText`

**症状**: `spawn("claude", args, { env: buildEnv() })` に `cwd` の指定がなく、呼び出し元プロセスの作業ディレクトリをそのまま継承する。プロジェクトルートから `run-loop.mjs` を起動すると、そのプロジェクトの hooks・CLAUDE.md・output style・有効化されたプラグインがすべて子プロセスに効く。

**実害**: 改善案生成が `<new_description>` タグを含む応答を返さず、`exit_reason: improve_failed (iteration 1)` で停止した。返ってきたのは、そのプロジェクトの SessionStart hook が注入した通知に対する応答だった。

実際に観測した応答:

```
既知の通知(蒸留完了は前ターンで報告済み)。追加対応不要。
```

**実証**: 同一プロンプト・同一モデル・同一環境変数で作業ディレクトリだけを変えた比較。

| cwd | 応答 |
| --- | --- |
| 中立な一時ディレクトリ | `<probe>OK</probe>`(正常) |
| プロジェクトルート | プロンプトと無関係な応答 |

**対処案**: 次のいずれか。

- `cwd` に一時ディレクトリを渡す。`runSingleQuery` が `cwd: sandbox.dir` を渡しているのと同じ考え方にする。
- `--bare` を付ける。CLI 2.1.274 で確認済み。hooks・LSP・plugin sync・auto-memory・CLAUDE.md auto-discovery を切る。skills は切らないため、サンドボックスに置いたスキルを読ませる発火測定にも使える。skills まで切るのは `--safe-mode` の方であり、こちらを使うと測定対象ごと消える。

**副作用**: 応答が汚染されるだけでなく、子プロセス側の hook が実際にファイルを書き込む。この監査では、測定用に起動した `claude -p` のセッションが会話記録の Stop hook を発火させ、`docs/chat/` 配下に 4 件の記録ファイルを作った。いずれも参加者が測定用モデル、セッション ID も本来の会話とは別物であり、内容は測定プロセス自身のやり取りだった。読み取り専用の測定のつもりでも、隔離しなければリポジトリが書き換わる。

**補足**: `buildEnv()` が落としているのは `CLAUDECODE` 環境変数 1 つだけである。設定ディレクトリもプラグインも hook も隔離していない。

## 2. `run-loop` が結果に `environment` を記録しない

**場所**: `src/run-loop.ts` の結果組み立て(`results.json` の出力)

**症状**: `run-trigger-eval` は `describeEnvironment()` の結果(`base_url` / `auth_source` / `model`)を結果 JSON に記録する。`run-loop` は記録しない。

**実害**: どの環境で測った数値かを後から照合できない。実際に、ベースラインを既定モデルで取り、改善ループを明示モデルで回したことに気づくのが遅れ、比較できない 2 系統の数値を作った。

**対処案**: `describeEnvironment()` の結果を `results.json` に含める。`run-trigger-eval` と同じ形にする。

## 3. `--model` の扱いが 2 つのスクリプトで揃っていない

**場所**: `src/run-loop.ts` の引数検証(`--model is required`)と `src/run-trigger-eval.ts` の引数定義

**症状**:

| スクリプト | `--model` |
| --- | --- |
| `run-trigger-eval` | 任意。未指定なら CLI の既定(`~/.claude/settings.json` の `model`)に委ねる |
| `run-loop` | 必須 |

**実害**: ベースラインを `run-trigger-eval` で既定モデルのまま取り、改善ループを `run-loop` で明示モデルを渡して回すと、環境が食い違う。実際にこれが起き、同じ description・同じクエリで発火率が 0/3 と 3/3 に割れた。

**対処案**: 次の 4 で決めた方針に合わせ、両者の既定を揃える。

## 4. 測定モデルは Sonnet に統一する

**方針**: 発火測定と改善ループのモデルを Sonnet に固定する。

**背景**: 既定モデル(`opus[1m]`)で測ると、能力の高さゆえに曖昧な description でも正しく判別してしまい、description の欠陥が数値に現れにくい。実際、capturing-architecture と updating-architecture の担当が重なっている問題は、Opus では顕在化せず Sonnet で顕在化した。

改善の対象は description の明確さであり、モデルの賢さで覆い隠されない条件で測る方が欠陥を拾える。加えて反復測定の回数が多く、コストの差も大きい。

**対処案**: 両スクリプトの `--model` の既定値を Sonnet にする。明示指定で上書きできる形は残す。既定を変えた時点で過去の測定値とは比較できなくなるため、変更後にベースラインを取り直す。

## 5. `--help` が無い

**症状**: `node scripts/run-trigger-eval.mjs --help` が `Unknown option '--help'` で終わる。`run-loop.mjs` も同様。

**実害**: 利用できるオプションと既定値を知るためにソースを読む必要がある。

**対処案**: `--help` でオプション一覧と既定値を出す。

## 6. holdout の分解能と採否の基準

**症状**: `--holdout 0.4` を 20 問の eval セットに当てると holdout は 8 問になる。1 問が 12.5% に相当し、train 側で明確な改善が出ても holdout が動かなければ採用されない。

**実際に起きたこと**: updating-architecture の改善ループで、反復 2 の案が train 6/12 から 8/12 へ 2 問改善した。holdout は 7/8 で元と同点だったため採用されず、`best_description` は元の description のままになった。

改善した 2 問は、実測で失敗していた「ADR の状態変更」と「保護パスの更新」であり、いずれも静的監査でも指摘した欠陥(description が rules の担当を覆っていない)に対応する。採る価値のある改善が、holdout の分解能不足で捨てられた形になる。

**対処案**: 次のいずれか、または組み合わせ。

- 採否を holdout 単独で決めず、train と holdout の両方を見る基準にする。
- holdout が同点のときの扱いを選べるようにする。
- eval セットを 20 問より増やせるようにし、holdout の問数を確保する。

## 7. description は長さで希釈される — 改善案生成が逆方向へ動く

**観測**: 同じ情報を含む description でも、長さによって発火率が大きく変わる。

updating-architecture の 2 クエリ(「更新しといて。他もズレてたら一緒に」「ADR に残して。前提だった方は廃止で」)で比較した結果。

| description | 字数 | 発火率 |
| --- | --- | --- |
| その 2 つの依頼だけに絞った極端な案 | 48 | 5/5 |
| 現行 | 302 | 0/5 |

同じクエリ文を収録した 400 字の案でも 0/7 であり、収録の有無ではなく密度が効いている。

3 スキルで現行・400 字案・200 字前後の案を比較した結果は次のとおり。

| スキル | 現行 | 400 字案 | 200 字前後の案 |
| --- | --- | --- | --- |
| capturing-architecture | 15/20(460 字) | 14/20(362 字) | 20/20(211 字) |
| updating-architecture | 13/20(302 字) | 13/20(390 字) | 20/20(223 字) |
| recording-gotchas | 15/20(448 字) | 15/20(390 字) | 20/20(188 字) |

短縮で直った問は 0.00〜0.29 から 1.00 へ完全に回復した。担当が重なっていたスキル間の誤発火も、境界を詳しく書くのではなく双方を短くすることで 1.00 から 0.00 へ解消した。

**改善ループへの影響**: `improve-description` が生成した 15 案はすべて現行より長く(400 字超)、すべて不採用に終わった。生成プロンプトは「100-200 words 以内」と指示しているが、失敗したクエリを列挙して渡す構造上、案は条件を足す方向へ膨らむ。短くする方向の探索が起きない。

**対処案**:

- 生成プロンプトに現行 description の字数を明示し、それを超えない案を求める。
- 案の字数に上限を設け、超えた案は測定せず再生成する。
- 失敗クエリを渡すときに、条件の追加ではなく既存の条件の言い換え・削除も選択肢だと明示する。
- 短縮方向の案を必ず 1 つ含める(例: 反復ごとに「条件を足した案」と「削った案」の 2 通りを測る)。

## 8. eval セットの作成基準に足すもの

`skills/skill-creator/SKILL.md` の「eval セット」節へ取り込む。現行の基準は、クエリを現実的にするために次を求めている。

- クエリは具体的で現実的にする
- ファイルパス・仕事や状況の背景・列名と値・会社名・URL・短い前置きのような手がかりを混ぜる
- 小文字・略語・タイプミス・口語を混ぜる
- クエリの長さを混ぜる
- 明快な例ではなく境界事例を選ぶ

これらを満たした eval セットでも、実運用で起きている発火失敗を再現できなかった。次の 5 つを足す。

### 1. 実運用の起動経路を作る前に確かめる

スキルの起動には 2 通りの経路がある。

- ユーザーが目的を明示して依頼する
- AI が提案し、ユーザーがそれに答える

どちらが主かはスキルごとに違う。eval を作る前にユーザーへ聞き、主な経路を true 問の構成へ反映する。

### 2. 提案への回答を true 問に入れる

提案への回答が主な経路であるスキルでは、その形を true 問に入れる。現行の基準だけで作ると、true 問がすべて「ユーザーが目的を明示した依頼」に偏る。

### 3. 人間は AI の発言を復唱しない

提案への回答を書くとき、AI の発言をなぞる形にしない。実際の返答は、対象を指す語が 1 つ残る程度の短さになる。

- 書かない: さっき指摘してもらった技術スタックの節のズレ、直してください
- 書く: 更新しといて。他もズレてたら一緒に

### 4. 短さの下限は対象語が 1 つ残るところ

測定は 1 クエリの単発実行であり、会話履歴を持たない。「お願いします」「はい」だけの返答は、どのスキルに向けた依頼か判定できないため測れない。対象を指す語を 1 つ残すところが下限になる。

- 測れない: お願いします
- 測れる: 残しといて。次も同じとこで止まると無駄

### 5. スキルが使う語彙と別の語彙を混ぜる

description が使う語だけで true 問を作ると、語の一致で発火する問ばかりになり、語彙の狭さを検出できない。同じ行為を指す別の語を混ぜる。

- description の語: 記録する・台帳・追記
- 混ぜる語: メモ残しといて・書いといて・忘れないようにして

### この基準で差し替えた結果

metatron の 2 スキルで true 問を 3 問ずつ差し替えた。新しく入れた 6 問のうち 5 問が、当時の description で失敗した。

| スキル | 差し替え前 | 差し替え後 |
| --- | --- | --- |
| updating-architecture | 18/20 | 16/20 |
| recording-gotchas | 20/20 | 17/20 |

差し替え前の eval では、欠陥が数値に現れていなかった。差し替え後に失敗した問は、description を短くする改修で 1.00 まで回復した。

なお、ユーザーからの明示的な指示が主な経路であるスキル(capturing-architecture)では差し替えを行わなかった。経路を確かめずに全スキルへ一律に適用すると、実態と違う形の問を増やすことになる。

## 参考: この監査で使った回避策

`run-loop.mjs` をプロジェクトの外(中立な一時ディレクトリ)から起動し、`--eval-set` と `--skill-path` を絶対パスで渡すことで、1 の欠陥を回避できる。コードを変えずに改善案生成が正常に動くことを確認した。
