# description の書き方

SKILL.md・コマンド定義(`commands/*.md`)・Agents 定義の frontmatter にある description の基準である。
output style・メモリの frontmatter にある description もこの基準に従う。

SKILL.md とコマンド定義の description は、`skill-creator` を使えない環境でこの基準を当てる。
使える環境では `skill-creator` へ委ね、この文書は読まない。
Agents 定義・output style・メモリの description は、環境によらずこの基準を当てる。

## 書く内容

- 何をするかと、どんなときに使うかの両方を書く。
- 「〜するスキルである」と説明せず、「〜のときに使う」と使用を促す形で書く。
- 実装の仕組みではなく、ユーザーが何を達成しようとしているかを書く。
- 個別の依頼文を列挙せず、ユーザーの意図のまとまりで書く。
- 隣接するスキルと並べたとき、どちらを選ぶかが 1 読で決まる語を選ぶ。
- 担当が近いスキルや Agents 定義があるときは、そちらが担当する場面を書いて境界を示す。
- 発動してほしくない場面があるときは、除外する場面と発動する場面を同じ改稿で書く。除外だけを足さない。
- 自律的に発動させないスキルは、明示的な依頼があったときだけ使う旨を末尾に置く。
- 「いつ使うか」は description にだけ書く。本文へ分散させない。
- 三人称で書く。「〜をお手伝いします」「あなたは〜できます」のような一人称・二人称にしない。

### 発火率を上げるための施策

- この施策は Agents 定義には適用しない。
- Agents 定義では、使用する場面を具体的に書き、「積極的に使用する」と書く。
- 「必ず使用する」と言い切る。「〜に役立つ」「〜のときに参照できる」のような控えめな表現にしない。
- ユーザーがその語を明示しない場面も、発動する場面として書く。

## 長さの上限

- 長さの上限は Agents 定義には適用せず、自由に記述する。
- SKILL.md とコマンド定義では、`description` を 1024 字以内にする。
- 100〜200 words 相当へ収める。発火精度を落としてでもこの範囲へ収める。
- 上限に触れたときは、個別の記述を意図のまとまりへ言い換えて縮める。

## 配布するスキル・Agents 定義の書き方

- 配布するスキル・Agents 定義では、開発リポジトリのファイル名・プラグイン名・エージェント名を書かない。
- 指す対象は、置き場所と種別で示す。`references/` 配下の文書・`commands/` 配下のコマンド定義・SKILL.md のように、どのリポジトリにもある形で書く。
- 固有名を書いてよいのは、そのリポジトリでしか使わないスキルに限る。

## 直したときの確かめ方

description を直したときは、発火を測ってから採否を決める。

- 発火を測る問を 20 問作る。発動してほしい問を 8〜10 問、発動してほしくない問を 8〜10 問にする。
- 問は、ユーザーが実際に打つ形で書く。ファイルパス・仕事の文脈・列名・会社名・URL・短い背景を混ぜる。
- 小文字だけの文・略語・タイプミス・口語を混ぜる。長さも揃えない。
- 判定が明確な問より、判定が割れる問を多く作る。
- 発動してほしくない問は、語や概念を共有しながら別の対応を要するものにする。明らかに無関係な問は作らない。
- 1 手で終わる問は作らない。多段の作業や専門的な判断を要する問を作る。
- 各問を 3 回実行し、発火率で判定する。1 回の結果で決めない。
- 問を 6 対 4 で分け、6 割で直し、4 割で採否を決める。直しに使った問の成績で採否を決めない。
- 改稿は 5 回までとする。
- 改稿しても落ちる問が残るときは、語を足さずに文構造と語の選び方を変える。
