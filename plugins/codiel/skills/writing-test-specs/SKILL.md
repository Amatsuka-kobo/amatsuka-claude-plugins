# テスト仕様書執筆規約

## 概要

test-spec フェーズでテスト仕様を書く委譲先が使うスキル。`design.md` の
「## 影響を受ける機能単位」と intent の受け入れ基準を入力に、仕様のディレクトリごとの
振る舞い仕様 `spec.md` と ID 付きテストケース表 `cases.md` を `<testsDir>/<ID>/` に
作成・更新する。`testsDir` の値はディスパッチプロンプトで渡される。

本フェーズが担当するのは `spec.md` と `cases.md` までで、テストコードは test-code フェーズが
書く。テストコードの置き場・実行は `scripting-tests` が担い、本スキルの範囲には含めない。

## 仕様のディレクトリの ID と置き場

仕様のディレクトリは `<testsDir>` 配下に置く。`testsDir` からの相対パスをそのディレクトリの
ID とし、`spec.md` と `cases.md` を置く。

| 系統 | 仕様のディレクトリ | 例(値は説明用) |
| --- | --- | --- |
| ユニットテスト | `units/<対象ファイルの repoRoot 相対パス>/` | `units/src/lib/foo.ts/` |
| E2E(画面) | `e2e/frontend/<画面名>/` | `e2e/frontend/login/` |
| E2E(API) | `e2e/backend/<API のルートパス>/` | `e2e/backend/api/users/{id}/` |
| E2E(画面でも API でもない入口) | `e2e/cli/<コマンド名>/` | `e2e/cli/codiel-state/` |

- 画面名とコマンド名は英小文字のケバブケースの 1 セグメントにする。CLI のコマンド・バッチ・
  hook などは `e2e/cli` に置き、サブコマンドは 1 つの仕様にまとめる。
- API のルートパスは、先頭の `/` を除いたパスをディレクトリの並びにする。パスのパラメータは
  フレームワークの書き方(`:id`・`[id]`・`<id>` など)によらず `{id}` の形にそろえ、ルート `/`
  は `e2e/backend/_root/` にする。HTTP メソッドはディレクトリに含めず、同じパスの全メソッドを
  1 つの仕様にまとめる。
- 対象ファイルを移す・消す変更では、仕様のディレクトリも同じく移す・消す。
- ID は `units/`・`e2e/frontend/`・`e2e/backend/`・`e2e/cli/` のいずれかで始まり、その後に
  1 つ以上のセグメントを持つ(`e2e/frontend/` と `e2e/cli/` の後はちょうど 1 セグメント)。
  空のセグメント・`.`・`..`・`:`・`\` は含めない。

## 画面名の決め方

コマンド名(`e2e/cli`)と API のルートパス(`e2e/backend`)はコードから決まるので、ユーザーに
聞かない。画面名だけ次のとおり決める。

- `<testsDir>/e2e/frontend/` に既にある画面の仕様を更新するときは、その名前をそのまま使う。
- まだ仕様のディレクトリが無い画面には、名前を決めず、ケバブケースの候補を 2〜3 個出す。候補は
  上記の画面名の規則(英小文字の 1 セグメント)に従い、報告に挙げる。ユーザーへの確認はオーケストレーターが行う。

## 作る仕様の規則

規約(docRoot 配下の `CLAUDE.md` と `.claude/rules/**/*.md` のテスト方針)に定めがあれば従う。
無ければ下表の基準で決める。

| 系統 | 規約に定めがあるとき | 定めが無いとき |
| --- | --- | --- |
| E2E | 従う | この変更でユーザーから観測できる振る舞いが変わるときだけ作る。画面の表示・操作が変わる画面ごとに `e2e/frontend`、API の応答が変わるルートごとに `e2e/backend`、コマンドの入出力が変わるコマンドごとに `e2e/cli` の仕様を置く。内部だけの変更には作らない |
| ユニットテスト | 従う | この変更で追加・変更するファイルのうち、分岐・計算・変換などのロジックを持つものに作る。設定・型定義・表示だけのファイルには作らない |

## 対象の一覧と同定

`design.md` が無い run(軽量)では、`design.md` の代わりに intent の `## 受け入れ基準` と `## 実装方針` を入力にする。仕様のディレクトリの一覧は、標準の run では `design.md` の「## 影響を受ける機能単位」、軽量の
run ではディスパッチプロンプトが渡す一覧を使う。どちらでも、渡された一覧だけを対象にする。
一覧に無い仕様のディレクトリが必要だと判断しても、自分では作らずオーケストレーターへ報告する。

## チェックリスト

1. 渡された一覧(標準では `design.md` の「## 影響を受ける機能単位」、軽量ではディスパッチ
   プロンプトの一覧)を読み、対象の仕様のディレクトリの ID を確定する。一覧に無いディレクトリは
   作らない。
2. intent の「## 受け入れ基準」を読み、各仕様のディレクトリがどの基準に対応するかを対応付ける。
3. 各仕様のディレクトリについて `<testsDir>/<ID>/` が既存かを Glob で確認する。
4. 新規: 書き込むのは `<testsDir>/<ID>/` の `spec.md` と `cases.md` だけにする。プロダクトコードとほかの領域には書かず、実装もせず、`Bash` は使わない。
   `spec.md` を作成する。先頭の frontmatter で `parallel` を決める。ポート・
   データベース・外部サービスのような共有資源を使う仕様は `parallel` を置かず直列のまま
   実行させる。続けて `cases.md` を新規に生成する。
5. 既存: 既存 `spec.md` を Read してから Edit で更新する(いきなり上書きしない)。
   `tests` の値は書かず、既存の値をそのまま保つ。更新後、`cases.md` を再生成する。既存
   ケース ID は挙動が変わらない限り維持し、挙動が変わるものは期待結果を更新し、消える機能の
   ケースは spec.md の `## 変更履歴` に削除理由を記録してから cases.md から取り除く。
6. cases.md の期待結果は intent の受け入れ基準から導出する。内部関数名・実装方式などの
   実装詳細ではなく、ユーザー視点で観測可能な振る舞いを書く。まだ実装されていない・これから変わる振る舞いも、
   受け入れ基準に基づく「あるべき」期待結果を書き、既存コードの現在の挙動を根拠にしない。
7. テストコードには一切触れない(作成もしない、既存があっても変更しない)。置き場と実装は
   test-code フェーズ(`scripting-tests`)が担う。
8. 自己チェック: 各ケースの期待結果について「intent のどの受け入れ基準が根拠か」を
   即答できるか確認する。答えられないケースは実装詳細の混入を疑う。
9. 完了報告(下記)を最終の返答に書く。

## spec.md の書式

先頭に `---` で囲む YAML の frontmatter を置ける。定義するキーは `parallel`(真偽値)と
`tests`(テストコードのパスの列)である。`tests` は test-code フェーズの委譲先が書く欄で、
本フェーズは書かない。既存の `spec.md` を更新するときも、既存の `tests` の値をそのまま保つ。

```markdown
---
parallel: true
tests:
  - src/lib/__test__/foo.test.ts
---

# spec: <ID>

## 概要

<この仕様が担う機能の一行要約>

## 振る舞い

- <ユーザー視点で観測可能な振る舞いを箇条書き。前提条件と結果をセットで書く>

## 受け入れ基準との対応

- intent「<受け入れ基準の文言>」 → 上記振る舞いの <該当箇所>

## 変更履歴

- <更新内容の要約>。削除したケースがあれば ID と削除理由を明記する。
```

`parallel: true` の仕様のディレクトリは、test-code・implement・test-loop・`/codiel:test` で
ほかのテストと同時に実行されうる。`parallel` が無ければ直列として扱う。

## cases.md の書式

各ケースの ID は `case-NNN`(3 桁ゼロ埋め、既存ケースの最大値の次から採番する)。ID は同じ
`cases.md` の中で一意であればよく、仕様のディレクトリをまたいで一意である必要はない。

```markdown
| ID | 前提 | 操作 | 期待結果 |
|---|---|---|---|
| case-001 | 未ログイン状態 | 正しい資格情報でログイン | ダッシュボードへ遷移 |
| case-002 | 未ログイン状態 | 誤った資格情報でログイン | エラーメッセージを表示しログイン画面に留まる |
```

## コミット責務

test-spec の委譲先は git 操作をしない。`orchestrating-runs` の成果物コミット規約により、
test-spec フェーズの成果物は Raguel の test-spec ゲート通過直後にオーケストレーター自身が
コミットする。委譲先の職務は spec.md / cases.md を書いて報告するところまでとする。

## 完了報告

報告のファイルは書かず、次の項目を最終の返答で返す。

- 作成・更新した仕様のディレクトリの ID ごとの `spec.md` と `cases.md` のパス
- 新しい画面の名前の候補(画面ごとに 2〜3 個)
- 一覧に無いが必要と判断した仕様のディレクトリと、その理由
- 削除したケースの ID と削除理由
