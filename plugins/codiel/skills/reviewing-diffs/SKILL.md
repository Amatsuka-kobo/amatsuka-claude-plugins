# diff レビュー規約

## 概要

レビューを担うサブエージェントが、依頼文で指定された観点で、review フェーズと fix-loop の再レビューに使うスキル。入力と手順はチェックリストに書く。受け入れ基準の出所は intent の `## 受け入れ基準` である。レビュー基準は常にこれらの文書との整合であり、レビュー担当個人の好みのコーディングスタイルは基準にしない。「自分ならこう書く」という指摘は、根拠が文書にない限り low 止まりとする。

fix-loop の再レビューでは、`fixing-review-findings` が申し送る「反論済み所見一覧」(所見の要約・反論根拠・記録先。記録先は github モードでは PR コメント URL、local モードでは本文ファイルのパス)が入力に含まれることがある。この一覧にある所見は原則再報告しない。再主張するのは、反論を覆す新たな根拠がある場合だけで、その根拠を所見書式の「根拠」欄に明記する。

レビューは両方向で行う。両方向チェックの原則は全観点共通である。

- 未達方向: intent の受け入れ基準 / design.md / spec.md にあるのに、diff に実装が見当たらない。
- 逸脱方向: intent / design.md / spec.md にない振る舞い・API・スキーマ変更が diff に追加されている。

観点ごとの確認項目は、依頼文で渡される観点ファイルにある。観点ファイルが依頼文にちょうど 1 件でないとき(なし、または 2 件以上)は、観点を推測せず、その旨を返答して差し戻す。統合と投稿はオーケストレーターが行う。担当は所見を返すだけで `gh pr review` を実行しない。

## チェックリスト

1. intent 文書(`docs/intents/**`)の `## 受け入れ基準` / `design.md` / `<testsDir>/**` の該当
   `spec.md`・`cases.md` と `tests` に記録されたテストコード / 関係する領域の持続層
   (`docs/intents/domains/<領域>.md`)の `## 意図的な制約` を読む。`design.md` が無い軽量の run では、
   intent と `dev-plan.md` を設計の代わりに読む。fix-loop の再レビューでは、申し送られた
   「反論済み所見一覧」も確認する。
2. `git diff <base>...<branch> -- ':(exclude,glob)<testsDir>/**/reports/**'` で diff を取得する。
   `<base>`・`<branch>` は依頼文の「## 前提」にある「diff の範囲」の行の値、`<testsDir>` は依頼文に書かれた値を使う(`codiel-state` は呼ばない)。「diff の範囲」の行が無いときは、範囲を推測せず、その旨を返答して差し戻す。E2E のレポートは diff から除く。
   diff が大きくても全ファイルに目を通し、サンプリングにせず全体を読む。
3. 自分の観点(依頼文で渡された観点ファイルの項目)に該当する変更点を洗い出す。
4. 各変更点について両方向チェックを行う:
   - 受け入れ基準・design.md にある振る舞いが diff で実現されているか(未達がないか)。
   - diff にある変更が design.md / spec.md のどこにも根拠を持たないものでないか(逸脱がないか)。
5. intent の原文のセクション(`## ASIS` / `## TOBE`)が語る要望を diff が満たすかも確認する。
   原文の要望の未達は severity high の所見にする。派生文(`## 現状調査` / `## 要求` /
   `## 受け入れ基準` / design.md)と原文が食い違うときは、原文を正とし、食い違いを所見に挙げる。
   人への確認はオーケストレーターが `mark-ask` の後に行う。
6. diff が受け入れ基準の振る舞いに触れるときは、テスト・型検査を読み取り実行して裏取りする(`npm test` / `npm run typecheck` 等。
   コンテキストに宣言があればそれに従い、無ければ `package.json` の `scripts` から取る)。実行結果は書き換えない。受け入れ基準に関わるテストの失敗は握り潰さず、severity high(未達)の所見に載せる。受け入れ基準と無関係な失敗は、根拠を書いたうえで low か medium の所見にする。スクリプトが無い・環境の失敗・タイムアウトで実行できないときは、所見にせず、完了報告の確認方法に実行できなかった旨と理由を書く。Bash は `git diff` とこの読み取り実行だけに使い、`gh pr review` の投稿・`git commit`・ファイルへの書き込みを伴う操作はしない。
7. 問題を見つけたら下記の所見書式でまとめる。severity は次のセクションの定義と基準文書に従って判定する。
   「反論済み所見一覧」に該当し、かつ反論を覆す新たな根拠がない場合は再報告しない。
8. 所見がゼロの観点があっても、確認した項目と確認方法を報告する(「完了報告」)。
9. 「完了報告」の項目をテキストで返す。ファイルへの書き込みは行わない。問題を見つけても自分で直さず、diff も書き換えず、所見として返す。修正は fix-loop の実装の委譲先が担う。

## 所見書式

見つけた問題は次の書式で 1 件ずつ書く。

```markdown
### [critical|high|medium|low] <一行要約>
- 観点: <渡された観点ファイルの名前(拡張子を除く)>
- 対象: `src/...:42`
- 抜粋: <該当行と前後 3 行の差分>
- 内容: <何が問題か>
- 根拠: <設計書・仕様書・Issue のどこと矛盾するか、またはどんな障害が起きるか>
- 提案: <修正の方向性>
```

## severity 定義

| severity | 定義 | 下流の扱い |
|---|---|---|
| critical | データ破壊・セキュリティ欠陥・主要機能の停止 | fix-loop で必ず修正 |
| high | 受け入れ基準の未達・設計との重大な乖離 | fix-loop で必ず修正 |
| medium | バグの温床・保守性の重大な問題 | triage フェーズでユーザーの指示のもと別 Issue 化 |
| low | 改善提案(スタイル・命名・軽微な最適化など) | triage フェーズでユーザーの指示のもと別 Issue 化 |

critical/high と medium/low で下流の扱いが分かれるため、判断に迷ったら基準文書に立ち返る。基準文書に照らしても severity が 2 つの間で決まらないときは、高いほうを採り、迷ったことと候補の 2 つを所見の「根拠」欄に書く。高いほうへ倒すのは、根拠があって段階だけで迷うときに限り、根拠のない指摘は冒頭のとおり low 止まりとする。security 観点の段階の基準は `references/security.md` に従う。持続層の意図的な制約に反する変更は high とする。

## 完了報告

最終の返答に、観点ごとに次の項目を書く。長さの上限は設けない。

- 観点の名前
- 確認した項目と確認方法(読んだファイル、実行したテスト・型検査のコマンドと結果)。所見がゼロでも書く
- 所見の一覧(上記の所見書式)。所見がゼロのときは「所見なし」と書く
- 各所見に付ける、該当する差分の抜粋(該当行と前後 3 行)と根拠
