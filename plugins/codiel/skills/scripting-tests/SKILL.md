# テストコード作成規約

## 概要

test-code フェーズの委譲先が、仕様のディレクトリ(`<testsDir>/<ID>/`)ごとに使うスキル。`cases.md` から実装より先にテストコード(ユニットテストと E2E)を書いて実行し、実装がまだ無いために失敗すること(Red)を確かめる。このスキルが書くのはテストコードだけで、`spec.md` と `cases.md` は書き換えない。

最初に、担当する仕様のディレクトリの `spec.md`・`cases.md`・`design.md`(軽量では intent の `## 受け入れ基準` と `## 実装方針`)・`dev-plan.md` を読む。

## worktree での作業

test-code の委譲は worktree(`.codiel/worktrees/<slug>/test-code-<k>`)で行う。依頼文が渡す brief ファイル(`.codiel/runs/<slug>/try-<n>/steps/test-code-<k>/brief.md`)の絶対パスを Read し、testsDir の値・担当する仕様のディレクトリの ID・入力のパスを、そこに書かれた値として確認する。委譲を出す順序と同時実行数は `../orchestrating-runs/references/delegation-env.md` の規律に従う。

worktree の中では、実装に入る前に依存をインストールする。コマンドは brief の `## 環境準備` の値を使う。「なし」のときは、その worktree の lockfile の種類から選ぶ既定のコマンドを使う。

## テストコードの置き場

置き場は codiel が決めず、プロジェクトの規約に従う。次の順で決める。

1. docRoot 配下の `CLAUDE.md` と `.claude/rules/**/*.md` の定め
2. 同じ種類の既存のテストの配置
3. フレームワークの既定の置き場。3 で決めたときは、根拠を報告に書く

フレームワークは、コンテキストの宣言・既存のテスト・`package.json` の `devDependencies` の順で決める。決まらなければテストを書かずに報告する。推定で決めたときは、その旨を報告に書く。既存のテストコードが有るかを Glob で確認し、有れば Read してから Edit で追随させる。

## テストコードの規約

- `cases.md` の 1 ケースを 1 テストにし、テスト名にケース ID を含める。
- 期待結果は `cases.md` の文言を変えずにアサーションへ写す。期待値の出所は `cases.md` だけであり、実装コードを読んで期待値を書き足したり調整したりしない。
- 置いたテストファイルのパスを、`spec.md` の frontmatter の `tests` に Edit で足す。既存の値は消さず、テストファイルを移したときだけ古いパスを新しいパスに置き換える。
- `cases.md`、`spec.md` の本文と `parallel`、プロダクトコードは書き換えない。

## Red の確認

Red の対象は、この run で追加・変更したケースであり、`git diff <base>...HEAD -- <cases.md のパス>` で決まる。実装の前なので、Red の対象のテストが失敗するのは期待どおりである。Red を消すために実装を書いたり期待結果を緩めたりしない。

- 失敗の理由が未実装(対象のモジュール・関数・画面・API・コマンドが無い、値や表示が期待と違う)なら Red とする。未実装のモジュールの import でファイル全体が失敗するときは、理由がその import であることを確かめ、そのファイルのケースをすべて Red とする。E2E で要素が見つからない失敗は、対象の画面が未実装なら Red とする。
- 失敗の理由が環境にある(下記「テストの実行環境と環境の失敗」)なら Red にせず、理由と出力の抜粋を報告に挙げる。
- テストの記述の誤り(構文、テスト自身の import、フレームワークの設定)で失敗したら、テストを直して再実行する。
- Red かテストの誤りか判断がつかないときは、書き換えず「cases.md の誤り」として報告する。
- 依頼文の実行モードの前提に「引き継いだ実装あり」と書かれているときは、追加・変更したケースが実装の前に通っても、cases.md の誤りとして報告しない。「引き継いだ実装で通る」として、ケース ID を報告に挙げる。
- 上の前提が無いとき、Red の対象のテストが通ったら、cases.md かテストの誤りを疑う。テストが期待結果を検出していない(アサーションの誤り、対象の取り違え)なら、テストを直して再実行する。テストが期待結果を検出していてなお通るなら、cases.md がこの run で変わる振る舞いを表していない。「cases.md の誤り」として報告に挙げ、cases.md は書き換えない。
- Red の対象でないケースのテストは、現行のコードで通ることを確かめる。失敗したら報告に挙げる。

## テストの実行環境と環境の失敗

E2E の実行に要る準備(サーバーの起動、データベースの用意など、依存のインストールを超えるもの)は、プロジェクトの規約とテストの設定に従う。準備の手順は codiel が持たない。理由が環境にある失敗は、未実装による Red にも「cases.md の誤り」にも数えず、環境の失敗として理由と出力の抜粋を報告に挙げる。

## E2E の実行とスクリーンショット

E2E の実行ごとのディレクトリへの出力と返答の項目は、`../../references/e2e-report-format.md` に従う。スクリーンショットの撮り方(フレームワークの設定、テストコードの後処理など)は、プロジェクトの規約とテストの設定に合わせて決め、決めた撮り方を返答に書く。

## ツール運用

- Playwright MCP が使えるときは、ブラウザ操作で失敗の原因(未実装の Red・テストの記述の誤り・環境の失敗)を切り分ける。使えないときは、コードリーディングとテストコマンドで代替する。
- 判定はテストの実行結果だけを根拠にする。手動操作の結果を判定の根拠にしない。

## コミット

区切りごとに 1 コミットとし、まとめて 1 回にしない。コミットは worktree の中で行う。

```
git add <テストファイル> <spec.md>
git commit -m "codiel(test-code): <内容> (<slug> try-<n>)"
```

報告の本文は最終の返答で返し、報告のファイルは Write で書かず、`git add` もしない。`codiel-state` は呼ばない。

## 完了報告

最終の返答に次の項目を書く。長さの上限は設けない。

- ケースごとの結果(Red・通過・環境の失敗・cases.md の誤り。「引き継いだ実装あり」の前提では、引き継いだ実装で通るケースも)と理由
- 置いたテストファイルのパスと `spec.md` の `tests` に足した値
- 置き場の根拠(フレームワークの既定の置き場で決めたときと、推定で決めたとき)
- 実行したコマンドと出力の抜粋
- E2E では、スクリーンショットの撮り方と、`e2e-report-format.md` の返答の項目
