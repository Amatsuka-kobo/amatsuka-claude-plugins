# テストコード作成規約

## 概要

test-code フェーズの委譲先が、仕様のディレクトリ(`<testsDir>/<ID>/`)ごとに使うスキル。`cases.md` から実装より先にテストコード(ユニットテストと E2E)を書いて実行し、実装がまだ無いために失敗すること(Red)を確かめる。

三層構造(`spec.md` → `cases.md` → テストコード、`docs/DESIGN.md` §4)のうち本スキルが担当するのはテストコードの作成と実行である。`spec.md` の本文・`parallel` と `cases.md` は test-spec フェーズの委譲(`writing-test-specs` に従って書く)が担当し、test-code の委譲先は書き換えない。期待結果を書く委譲(test-spec)とテストを書く委譲(test-code)、コードを直す委譲(implement・test-loop・fix-loop)を分けるのは、役割分担による捏造防止(同 §4)のためである。

## worktree での作業

test-code の委譲は仕様のディレクトリごとに worktree(`.codiel/worktrees/<slug>/test-code-<k>`)で行う。k は `testCode.units` にその ID を登録した順の番号であり、登録し直しても変わらない。依頼文が渡す brief ファイル(`.codiel/runs/<slug>/try-<n>/steps/test-code-<k>/brief.md`)の絶対パスを Read し、testsDir の値・担当する仕様のディレクトリの ID・入力のパスを、そこに書かれた値として確認する。報告の本文は最終の返答で返し、報告のファイルを Write で書かず、`git add` もしない。完了通知で返答を受けたオーケストレーターが `waits/<id>.md` と報告のファイルへ書く。委譲を出す順序と同時実行数は `orchestrating-runs` の規律に従う。

worktree の中では、実装に入る前に依存をインストールする。コマンドは brief の `## 環境準備` の値を使う。「なし」のときは、その worktree の lockfile の種類から選ぶ既定のコマンドを使う。

## テストコードの置き場

置き場は codiel が決めず、プロジェクトの規約に従う。次の順で決める。

1. docRoot 配下の `CLAUDE.md` と `.claude/rules/**/*.md` の定め
2. 同じ種類の既存のテストの配置
3. フレームワークの既定の置き場。3 で決めたときは、根拠を報告に書く

フレームワークは、コンテキストの宣言・既存のテスト・`package.json` の `devDependencies` の順で決める。決まらなければテストを書かずに報告する。

## テストコードの規約

- `cases.md` の 1 ケースを 1 テストにし、テスト名にケース ID を含める。
- 期待結果は `cases.md` の文言を変えずにアサーションへ写す。期待値の出所は `cases.md` だけであり、実装コードを読んで期待値を書き足したり調整したりしない。
- 置いたテストファイルのパスを、`spec.md` の frontmatter の `tests` に Edit で足す。既存の値は消さず、テストファイルを移したときだけ古いパスを新しいパスに置き換える。
- `cases.md`、`spec.md` の本文と `parallel`、プロダクトコードは書き換えない。

## Red の確認

Red の対象は、この run で追加・変更したケースであり、`git diff <base>...HEAD -- <cases.md のパス>` で決まる。実装の前なので、Red の対象のテストが失敗するのは期待どおりである。

- 失敗の理由が未実装(対象のモジュール・関数・画面・API・コマンドが無い、値や表示が期待と違う)なら Red とする。未実装のモジュールの import でファイル全体が失敗するときは、理由がその import であることを確かめ、そのファイルのケースをすべて Red とする。E2E で要素が見つからない失敗は、対象の画面が未実装なら Red とする。
- 失敗の理由が環境にある(下記「テストの実行環境と環境の失敗」)なら Red にせず、理由と出力の抜粋を報告に挙げる。
- テストの記述の誤り(構文、テスト自身の import、フレームワークの設定)で失敗したら、テストを直して再実行する。
- Red の対象のテストが通ったら、cases.md かテストの誤りを疑う。テストが期待結果を検出していない(アサーションの誤り、対象の取り違え)なら、テストを直して再実行する。テストが期待結果を検出していてなお通るなら、cases.md がこの run で変わる振る舞いを表していない。「cases.md の誤り」として報告に挙げ、cases.md は書き換えない。
- Red の対象でないケースのテストは、現行のコードで通ることを確かめる。失敗したら報告に挙げる。

## テストの実行環境と環境の失敗

E2E の実行に要る準備(サーバーの起動、データベースの用意など、依存のインストールを超えるもの)は、プロジェクトの規約とテストの設定に従う。準備の手順は codiel が持たない。

理由が環境にある失敗(サーバーが起動しない、接続が拒否される、ポートが使用中、必要なサービスが無い)は、環境の失敗として理由と出力の抜粋を報告に挙げる。未実装による Red にも「cases.md の誤り」にも数えない。

## E2E の実行とスクリーンショット

E2E は、仕様のディレクトリごとにテストフレームワークを 1 回起動する。
JSON の出力と、frontend では各ケースの最後の画面のスクリーンショットを、依頼文(worktree の委譲では brief)が指す実行ごとのディレクトリに出す。
スクリーンショットの撮り方(フレームワークの設定、テストコードの後処理など)は、プロジェクトの規約とテストの設定に合わせて決め、決めた撮り方を返答に書く。
返答に入れる項目は `../../references/e2e-report-format.md` に従う。

## ツール運用

- ライブラリ・フレームワークの仕様確認は Context7 の `resolve-library-id` → `query-docs` で行う。記憶で書かず、仕様を確認してから反映する。
- Playwright MCP が使えるときは、ブラウザ操作で失敗の原因を切り分ける。理由が未実装(Red)か、テストの記述の誤りか、環境の失敗かを見分けるために使う。
- Playwright MCP が使えないときは、コードリーディングとテストコマンドで切り分けを代替する。
- 判定はテストの実行結果だけを根拠にする。手動操作の結果を判定の根拠にしない。

## チェックリスト

1. 担当する仕様のディレクトリの `spec.md`・`cases.md`・`design.md`(軽量では intent の `## 受け入れ基準` と `## 実装方針`)・`dev-plan.md` を読む。
2. フレームワークと置き場を「テストコードの置き場」の順で決める。推定で決めたときは報告に書く。
3. 既存のテストコードが有るかを Glob で確認する。有れば Read してから Edit で追随させる。
4. worktree の中で依存をインストールする。
5. `cases.md` の全ケース ID にテストを 1 対 1 で対応させ、実行して「Red の確認」の判定を付ける。
6. `spec.md` の frontmatter の `tests` に、置いたテストファイルのパスを Edit で足す。
7. worktree の中でコミットする。
8. 最終の返答に、ケースごとの結果(Red・通過・環境の失敗・cases.md の誤り)と理由、置き場とその根拠、実行したコマンドと出力の抜粋を書く。`codiel-state` は呼ばない。

## コミット責務

```
git add <テストファイル> <spec.md>
git commit -m "codiel(test-code): <内容> (<slug> try-<n>)"
```

区切りごとに 1 コミットとする。まとめて 1 回にしない。

guard-write hook は、`<testsDir>/**/spec.md` と `<testsDir>/**/cases.md` への書き込みを implement・test-loop・fix-loop で ask にし、test-code は通す。hook は呼び出し元の委譲先を識別できないため、これ以外の境界は自身の規律で守る。

<HARD-GATE>
**`cases.md`・`spec.md` の本文と `parallel`・プロダクトコードを変更しない**。変更してよいのは、テストコードと `spec.md` の frontmatter の `tests` だけである。
**Red を消すための実装の先取りや期待値の緩和をしない**。Red の対象のテストを通すための実装や、期待結果に届かないテストの緩和で Red を消してはならない。
**判断がつかない場合は自己判断で書き換えない**。Red かテストの誤りか判断がつかないときは、書き換えず「cases.md の誤り」として報告する。
</HARD-GATE>

## Red Flags(合理化への反論)

| 思考 | 現実 |
|---|---|
| 「Red を早く消すために実装も少し書いてしまおう」 | 実装は implement フェーズの担当である。test-code がコードを先取りすると、Red が実装の追認になる。テストだけを書き、Red を確かめて報告する。 |
| 「cases.md の期待結果が厳しすぎるから、アサーションで緩めよう」 | 期待結果は test-spec フェーズの委譲が intent の受け入れ基準から導いたものであり、test-code に緩める権限はない。厳しすぎると思うなら書き換えず「cases.md の誤り」として報告する。 |
| 「テストが通ってしまったが、たぶんこのままで大丈夫だろう」 | Red の対象のテストが通るのは、テストの誤りか、cases.md がこの run の変更を表していないかのどちらかである。原因を切り分けずに放置すると、実装の後まで見過ごされる。 |
