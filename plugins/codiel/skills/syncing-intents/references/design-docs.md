# 設計資料の更新

intent-sync で、run の変更をシステムの今の姿として `docs/intents/design/<種別>.md` へ書く。領域ファイルへの取り込みの後に、intent の `domains` の有無によらず行う。書式の正本は `<plugin-root>/references/intent-format.md` の「設計資料」のセクションである。

## 入力

- 標準の run(`state.scale` が `standard`): `<runsDir>/<slug>/design.md` と、run の差分(`git diff <baseBranch>...<branch>`)。
- 軽量の run(`state.scale` が `light`): run の差分と、intent の `## 実装方針`。

intent-sync の時点では実装が済んでいる。`design.md` や `## 実装方針` と差分が食い違うときは、差分(実装された姿)を書く。

## 種別の判定

入力を読み、run の差分が次の変更を含む種別のファイルだけを更新する。

| 種別 | 当たる変更 |
| --- | --- |
| データモデル(`data-model.md`) | 永続化されるデータの構造の追加・変更・削除(スキーマ・マイグレーション・エンティティやモデルの定義) |
| API 一覧(`api.md`) | 外部から呼ばれる口の追加・変更・削除(ルーティング・ハンドラ・OpenAPI などの定義) |
| 画面遷移(`screen-flow.md`) | 画面の追加・削除と、画面間の遷移の変更 |
| システム構成(`architecture.md`) | コンポーネント・サービス・外部システム・インフラの構成と、それらの間の通信経路の変更 |
| シーケンス(`sequence.md`) | 複数のコンポーネントにまたがる処理の流れの追加・変更 |
| 非機能要件(`nfr.md`) | intent や `design.md` で決めた性能・可用性・セキュリティなどの目標値や方針の追加・変更 |

どの種別にも当たらない run(内部のリファクタリングなど)では、設計資料を更新しない。

## 手順

1. 上の表で、更新する種別を決める。当たる種別が無ければ、ここで終える。
2. 種別ごとに、ファイルがあれば読み、run の差分が変えた箇所だけを今の姿に書き換える。無ければ、書式の正本どおりに新しく作る。`docs/intents/design/` が無ければ作る。
3. 書くのは、run の差分と、差分を読むのに要る既存のコードの範囲から分かることだけにする。初めて作るファイルでも、既存のシステム全体を書き起こさない。
4. 変更の経緯は書かない。ファイルの末尾の `## 由来` に、今回の intent のパスを `- docs/intents/YYYY-MM-DD-<slug>.md(取り込み日 YYYY-MM-DD)` の形で 1 行加える。
5. 更新した設計資料のパスを、`.codiel/runs/<slug>/try-<n>/steps/intent-sync/report.md` に書き足す。更新しなかったときは、当たる種別が無かったことを書く。
