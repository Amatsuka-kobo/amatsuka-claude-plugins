# intent-sync 運転規約

## 概要

intent-sync フェーズで成果物を書く委譲が使うスキルである。実装中に承認された受け入れ基準の変更と、intent-sync より前のフェーズで原文(`## ASIS` / `## TOBE`)の末尾に追記された要望を、intent 文書の派生文のセクションへ書き戻し、`## 変更履歴` に 1 行加える。書き戻す内容は、ディスパッチプロンプトで渡された時点で人の確認を終えている。このスキル自身は内容を人に確認しない。

## 担い手の分担

state の操作、人への確認、書き戻し後のコミットはオーケストレーターが行う。次の作業はいずれもオーケストレーターが担い、この委譲では行わない。

- 承認済みの受け入れ基準の変更と、原文に追記された要望のうち、派生文セクションへ反映する範囲を洗い出す。
- `codiel-state mark-ask intent-sync --slug <slug> --kind confirm` で run を `awaiting_human` にし、反映内容をユーザーに確認する。
- 確認を終えたら `codiel-state resume --slug <slug>` で `in_progress` に戻す。
- 確認済みの反映内容(反映先のセクションと反映する文言)をディスパッチプロンプトに含めてこの委譲へ渡す。
- 書き戻し後の intent 文書をコミットする。

この委譲が担うのは、確認済みの反映内容を intent 文書へ書く作業だけである。`codiel-state` は呼ばない。ディスパッチプロンプトに無い内容を自分の判断で書き足さない。

## 共通規律

- intent 文書の書式は `../../references/intent-format.md` に従う。原文のセクションと派生文のセクションの区別、`## 変更履歴` の記録方法はここに従う。
- 派生文のセクションへ書く文は `../../references/intent-writing.md` の文の組み立ての規則に従う。原文のセクションには適用しない(このスキルは原文のセクションを書かない)。

## 手順

1. ディスパッチプロンプトから、intent 文書のパスと、確認済みの反映内容(受け入れ基準の変更点、反映する原文の追記の範囲、それぞれの反映先セクション)を読み取る。
2. 承認済みの受け入れ基準の変更を書き戻す。変更点を `## 受け入れ基準`(変更の性質によっては `## 要求` や `## 実装方針` など、関係する派生文のセクション)へ、確認済みの内容のとおりに反映する。要約や言い換えで内容を変えない。
3. intent-sync より前に原文へ追記された要望を派生文のセクションへ反映する。反映先は `## 現状調査` や `## 要求` など、追記の内容に対応するセクションである。反映する範囲はディスパッチプロンプトで確認済みの範囲に限り、それ以外の追記(まだ確認されていない追記)には触れない。
4. `## 変更履歴` に、変更した日付・変更したセクション・変更内容の要約・承認の経路(Raguel の evaluationId、`mark-ask --kind confirm` による確認である旨など、ディスパッチプロンプトに記載のもの)を 1 行加える。
5. 書き戻した箇所(ファイルパスとセクション名)を報告する。intent 文書のコミットはオーケストレーターの作業なので行わない。

## `## 変更履歴` の記録例

値は例であり、実際の日付・セクション名・内容・承認の経路に置き換える。

```markdown
## 変更履歴

- 2026-10-05 / `## 受け入れ基準` / 「保存状態を画面右上にも表示する」を追加 / `mark-ask --kind confirm` で確認済み
- 2026-10-05 / `## 要求` / fix-loop 中に追記された「一覧の並び順を保持する」要望を追加 / `mark-ask --kind confirm` で確認済み
```

<HARD-GATE>
- 原文のセクション(`## ASIS` / `## TOBE`)を書き換えない。この委譲は追記済みの原文を読むだけであり、原文への追記もオーケストレーターの作業である。
- intent の `status` を `done` にしない(`done` は finalize だけが判定して付ける値である)。
- ディスパッチプロンプトで確認済みと渡された内容だけを書く。確認が済んでいない受け入れ基準の変更や原文の追記に気づいたら、書かずにオーケストレーターへ報告する。
- `codiel-state` を呼ばない。state の操作はオーケストレーターの作業である。
</HARD-GATE>

## Red Flags(合理化への反論)

| 思考 | 現実 |
| --- | --- |
| 「追記された要望の反映先は明らかなので、確認を待たずに書いてよい」 | 反映先の判断が誤っていても、書いた時点で intent の派生文のセクションに残る。確認前に書くと、確認そのものの意味が失われる。 |
| 「受け入れ基準の変更は Raguel の ASK で既に承認済みだから、変更履歴は省いてよい」 | `## 変更履歴` は承認の経路を残す記録である。省くと、後から intent を読む人が変更の正当性を追えなくなる。 |
| 「まとめて分かりやすいので、原文の追記も要約して派生文のセクションに書こう」 | 要約は派生文のセクションの役割であり、原文のセクション自体を書き換える理由にはならない。要約は `## 要求` などの派生文のセクションにとどめ、`## ASIS` / `## TOBE` には手を入れない。 |
