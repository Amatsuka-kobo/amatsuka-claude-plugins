# intent-sync 運転規約

## 概要

intent-sync フェーズでオーケストレーターが使うスキルである。実装中に承認された受け入れ基準の変更と、intent-sync より前のフェーズで原文(`## ASIS` / `## TOBE`)の末尾に追記された要望を、intent 文書の派生文のセクションへ書き戻し、`## 変更履歴` に 1 行加える。書き戻す内容は、書く時点で人の確認を終えている。この確認はこのスキルの手順の前にオーケストレーターが行う。

intent-sync フェーズはもう 1 つ、承認済みの intent が持つ `## 目的` / `## 意図的な制約` / `## 非スコープ` を、領域ごとの持続層(`docs/intents/domains/<領域>.md`)へ取り込む作業も担う。取り込み先の見出しは `## 目的` / `## 意図的な制約` / `## 非ゴール` / `## 由来` / `## 出典` の 5 つで、intent の `## 非スコープ` は持続層の `## 非ゴール` へ移す。

## 担い手の分担

書き戻しと持続層への取り込みは、オーケストレーターが自分で書く。書く前の確認、state の操作、書き戻し後のコミットも同じオーケストレーターが行う。

- 承認済みの受け入れ基準の変更と、原文に追記された要望のうち、派生文セクションへ反映する範囲を洗い出す。
- `codiel-state mark-ask intent-sync --slug <slug> --kind confirm` で run を `awaiting_human` にし、反映内容をユーザーに確認する。
- 確認を終えたら `codiel-state resume --slug <slug>` で `in_progress` に戻す。
- 書き戻し後の intent 文書をコミットする。

書くのは、確認済みの反映内容だけである。確認の無い内容を自分の判断で書き足さない。

持続層への取り込みでも、既存の制約と矛盾する内容を見つけたら該当箇所を書かず、`codiel-state mark-ask intent-sync --slug <slug> --kind confirm` の後にユーザーへ確認する。確認の結果を受けてから書く。

候補 ID の採番は `codiel-state next-adr-candidate-id --file <領域ファイルのパス> --domain <正規化後の領域名>` を呼ぶ。このコマンドは領域ファイルを読んで連番を計算するだけで `state.json` を書き換えない。

## 共通規律

- intent 文書の書式は `../../references/intent-format.md` に従う。原文のセクションと派生文のセクションの区別、`## 変更履歴` の記録方法はここに従う。
- 派生文のセクションへ書く文は `../../references/intent-writing.md` の文の組み立ての規則に従う。原文のセクションには適用しない(このスキルは原文のセクションを書かない)。
- 領域ファイル(持続層)の書式は `../../references/intent-format.md` の「持続層」セクションに従う。5 つのセクションの構成、`[ADR 候補]` の書式、候補 ID の採番規則、参照形への縮約はここが正本である。

## 手順

1. intent 文書のパスと、確認済みの反映内容(受け入れ基準の変更点、反映する原文の追記の範囲、それぞれの反映先セクション)を読み取る。
2. 承認済みの受け入れ基準の変更を書き戻す。変更点を `## 受け入れ基準`(変更の性質によっては `## 要求` や `## 実装方針` など、関係する派生文のセクション)へ、確認済みの内容のとおりに反映する。要約や言い換えで内容を変えない。
3. intent-sync より前に原文へ追記された要望を派生文のセクションへ反映する。反映先は `## 現状調査` や `## 要求` など、追記の内容に対応するセクションである。反映する範囲は確認済みの範囲に限り、それ以外の追記(まだ確認されていない追記)には触れない。
4. `## 変更履歴` に 1 行加える。行には、日付・セクション名・変更内容の要約・承認の経路(Raguel の evaluationId、`mark-ask --kind confirm` による確認である旨など)を書く。
5. 書き戻した箇所(ファイルパスとセクション名)を確かめる。intent 文書のコミットは、ゲート通過直後に行う。

## `## 変更履歴` の記録例

値は例であり、実際の日付・セクション名・内容・承認の経路に置き換える。

```markdown
## 変更履歴

- 2026-10-05 / `## 受け入れ基準` / 「保存状態を画面右上にも表示する」を追加 / `mark-ask --kind confirm` で確認済み
- 2026-10-05 / `## 要求` / fix-loop 中に追記された「一覧の並び順を保持する」要望を追加 / `mark-ask --kind confirm` で確認済み
```

## 持続層への取り込み

承認済みの intent から、領域ごとの持続層(`docs/intents/domains/<領域>.md`)へ制約を取り込む手順である。上の受け入れ基準等の反映とは別の作業であり、intent の `domains` が領域を持つときに行う。

### 手順

1. intent 文書のパス、取り込み先の領域(intent の frontmatter `domains`)、`state.adrTarget` の値を読み取る。領域が複数あれば、領域ごとにこの手順を繰り返す。
   取り込み先の領域が空(intent の `domains` が空)のときは、取り込みを行わずに手順を終える。finalize の結果レポートに、取り込みを行わなかった理由(取り込み先の領域が空)と、intent の `## 意図的な制約` に行があったかを書く。
2. 領域ファイルが無ければ、書式の正本(`intent-format.md` の「持続層」セクション)どおりの見出しだけを持つ空のファイルを作る。
3. intent の `## 目的` を読み、領域ファイルの `## 目的` へ取り込む。
4. intent の `## 意図的な制約`(「制約 | 理由」の表)の行を、1 行を 1 件として、領域ファイルの `## 意図的な制約` へ取り込む。行の「制約」列を `- 制約:`、「理由」列を `- 理由:` に対応させる。
   - 既存の制約と同じ内容を別の intent が持ち込んだときは、制約を増やさず、その項目の `出典 intent` に今回の intent のパスを加える。
   - 既存の制約と矛盾する内容は、上書きせず、矛盾の内容を書かずにユーザーへ確認する。
   - 参照形のエントリは確定済みとして扱い、全文を書き戻さない(参照形とは `関連 ADR: ADR-NNN(候補 ID: <候補 ID>)` の 1 行だけを持つエントリである)。今回の変更がその制約を変える内容なら、書かずにユーザーへ確認する。
   - ADR の 3 条件(覆すコストが大きい・選択肢が実在した・理由が自明でない)を満たす新しい判断は、次項の `adrTarget` による書き分けに従う。
5. intent の `## 非スコープ` を読み、領域ファイルの `## 非ゴール` へ取り込む。
6. 領域ファイルの `## 由来` に、今回取り込んだ intent のパスを `- docs/intents/YYYY-MM-DD-<slug>.md(取り込み日 YYYY-MM-DD)` の形で 1 行加える。
7. 取り込みで引いた出典があれば、領域ファイルの `## 出典` へ追記する。`## 出典` は常に最後のセクションに保つ。
8. 取り込んだ領域ファイルのパス、書かずに終えた矛盾、finalize の結果レポートに挙げる ADR 候補をまとめて控える。領域ファイルのコミットは、ゲート通過直後に行う。

### `adrTarget` による書き分け

ADR の 3 条件を満たす判断は、`state.adrTarget` の値で `[ADR 候補]` の扱いを次のように書き分ける。

- `metatron` のとき: 持続層に本文を書かず、`関連 ADR` に番号だけを書く形を将来のために残す。判断の内容は領域ファイルへ書かず、finalize の結果レポートで ADR 候補として挙げる。内容は、タイトル・制約・背景・選択肢・結論・理由・影響範囲である。
- `intents` のとき: 該当する領域ファイルの `## 意図的な制約` に、`[ADR 候補: <候補 ID>]` の形で全文を書く。候補 ID は `codiel-state next-adr-candidate-id --file <領域ファイルのパス> --domain <正規化後の領域名>` を呼んで得る。出力の `candidateId`(`<領域名>-<n>` の形)を、そのまま `[ADR 候補: <候補 ID>]` の候補 ID に使う。

候補 ID は、領域ファイルに現れる候補 ID(印付きエントリと参照形の両方)の最大連番 + 1 になる。縮約済みの ID も数えるので、一度使った ID は再利用されない。数えるときは、印 `[ADR 候補: <候補 ID>]` と参照形の `(候補 ID: <候補 ID>)` を完全一致のトークンとして読み、`frontend-1` を数えるときに `frontend-10` の一部を拾わない。この計算は `next-adr-candidate-id` が行うので、結果をそのまま使う。

新しい ADR 級の判断を見つけたら、新しい候補 ID で新しいエントリとして書く。既存の参照形のエントリは書き換えず、候補 ID も使い回さない。

<HARD-GATE>
- 原文のセクション(`## ASIS` / `## TOBE`)を書き換えない。intent-sync は追記済みの原文を読むだけで、原文への追記は行わない。
- intent の `status` を `done` にしない(`done` は finalize だけが判定して付ける値である)。
- 確認済みの内容だけを書く。確認が済んでいない受け入れ基準の変更や原文の追記に気づいたら、書かずにユーザーへ確認する。
- 参照形のエントリは確定済みとして扱い、持続層に全文を書き戻さない。
- 持続層の既存の制約と矛盾する内容を、確認を待たずに上書きしない。矛盾に気づいたら書かずにユーザーへ確認する。
- `codiel-state` の操作は、確認のための `mark-ask` と `resume`、候補 ID を採番する読み取り専用の `next-adr-candidate-id` に限る。
</HARD-GATE>

## Red Flags(合理化への反論)

| 思考 | 現実 |
| --- | --- |
| 「追記された要望の反映先は明らかなので、確認を待たずに書いてよい」 | 反映先の判断が誤っていても、書いた時点で intent の派生文のセクションに残る。確認前に書くと、確認そのものの意味が失われる。 |
| 「受け入れ基準の変更は Raguel の ASK で既に承認済みだから、変更履歴は省いてよい」 | `## 変更履歴` は承認の経路を残す記録である。省くと、後から intent を読む人が変更の正当性を追えなくなる。 |
| 「まとめて分かりやすいので、原文の追記も要約して派生文のセクションに書こう」 | 要約は派生文のセクションの役割であり、原文のセクション自体を書き換える理由にはならない。要約は `## 要求` などの派生文のセクションにとどめ、`## ASIS` / `## TOBE` には手を入れない。 |
| 「今回の intent の方が新しいので、持続層の既存の制約を書き換えてよい」 | 矛盾の確認は `mark-ask --kind confirm` でユーザーに取る。確認を待たずに書き換えると、確認そのものの意味が失われる。 |
| 「参照形になった制約は情報が少ないので、全文を書き戻して見やすくしよう」 | 参照形は ADR へ移した後の確定済みの形である。全文を書き戻すと、ADR を正とする情報が持続層に重複し、どちらが正か分からなくなる。 |
