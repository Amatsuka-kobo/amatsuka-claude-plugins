# 開発手順書執筆規約

## 概要

オーケストレーターが dev-plan フェーズで使うスキル。`design.md`(目的・方針・変更対象・影響を受ける
機能単位)と、orchestrating-runs の §0 の実行モード・ドメインマップを入力に、
`design.md` の変更対象をドメイン単位の実行可能なステップ列へ分解し `dev-plan.md` として構造化する。

dev-plan は test-spec の委譲が動いている間に書きゲートするので、test-spec の出力(`cases.md`)を入力にしない。

本スキルの責務は「`design.md` の変更対象を、ドメイン単位に分割された実行可能なステップへ分解すること」
にある。コードを書くことではない。

## チェックリスト

1. `design.md` の `## 目的` `## 方針` `## 変更対象` `## 影響を受ける機能単位` を読む。
   `design.md` が無い run(軽量)では、代わりに intent の `## 受け入れ基準` と `## 実装方針`、
   関係する領域の持続層(`docs/intents/domains/<領域>.md`)の `## 意図的な制約` を読む。
   仕様のディレクトリの一覧は、標準では `design.md` の `## 影響を受ける機能単位`、軽量では
   オーケストレーターが同定した一覧を使う。どちらも、dev-plan を書く時点で一覧を変えずそのまま使う。
2. orchestrating-runs の §0 の実行モードとドメインマップを使う。
   `mapped` のとき、渡されたドメインマップが `{ "generic": ["**"] }` に縮退していれば、以降の
   domain タグはすべて `generic` を使う。
   `unscoped` のとき、全ステップに `[domain: generic]` を付け、ドメインによる分割を行わない。
   ステップの分割は依存関係だけで決める。
3. `mapped` のとき、`## 変更対象` の各行を、渡されたドメインマップの glob と突き合わせて
   所属ドメインごとにグルーピングする。
   1 件の変更が複数ドメインにまたがる場合(例: フロントエンドの型とバックエンドの API を同時に触る)は、
   その変更内容自体をドメインごとに分割し、別々のステップに割り振る。
4. グループを実行順に並べる。依存関係(例: スキーマ変更 → 生成コード → API 実装 → 画面反映)を踏まえて
   ステップの順序を決める。
5. 各ステップに下記の出力書式を適用し、`触るファイル / 前提ステップ / 内容 / 通すテスト / 完了条件 / 検証コマンド`
   を埋める。触るファイルは repoRoot 相対の glob の列とし、ディレクトリを含めて書く(`*.ts` や `**/*` のような
   固定部の無い glob だけでは書かない)。前提ステップは先に終わっている必要があるステップ番号の列とする。
6. 通すテストは、そのステップと前提ステップが終わった時点で通る仕様のディレクトリの ID
   (`writing-test-specs` の命名規則に従う)の列で書き、無ければ「なし」と書く。仕様のディレクトリ
   の一覧(ユニットと E2E のすべて)を、いずれかのステップの通すテストに割り当てる。
   E2E を除外しない。
7. 検証コマンドは、コンテキストに宣言があればそのコマンドをそのまま使う。宣言が無ければ、リポジトリの設定(`package.json` の scripts 等)で実在を確認した
   コマンドだけを使い、その出所をステップに書く。検証コマンドは、そのステップの通すテストだけを
   実行するものにする。全体のテストと型検査は test-loop が担うので、ここには書かない。
8. 完了条件は「〜が実装されている」のような曖昧な文ではなく、「`pnpm test` が該当ファイルでパスする」
   「エンドポイントが 201 を返す」のように機械的に yes/no 判定できる文にする。
9. 自己チェック: `design.md` の `## 変更対象`(軽量では対象ファイルの一覧)に列挙された全ファイル
   が、いずれかのステップの「触るファイル」に現れているか確認する。また、仕様のディレクトリの
   一覧の全 ID が、いずれかのステップの「通すテスト」に現れているか確認する。現れていないものが
   あれば、それを含む・割り当てるステップを追加する。
10. YAGNI: `design.md` に記載のない作業(ついでのリファクタ・関連しない改善)をステップに追加しない。
11. 文書の先頭に `## 環境準備` を書く。docRoot 配下の `CLAUDE.md` と `.claude/rules/**/*.md` を読み、
    worktree で依存をインストールするコマンド(lockfile を変更しないモード)を書く。書けなければ「なし」と書き、実装側は lockfile から既定のコマンドを選ぶ。
12. 文書の先頭に `## 生成物` を書く。同じ規約を読み、下記「生成物の方式」の表に従って方式 a か方式 b を選ぶ。
    規約に定めが無ければ方式 b にする。方式・生成コマンド・生成物のパス・根拠を書く。生成物が無ければ
    「なし」と書く。方式 b では、生成だけを行う最終 Step を dev-plan の最後の Step として書き、
    その前提ステップに全 Step の番号を並べる。
13. 出力書式どおりに `dev-plan.md` を作成する。コードは書かず変更もしない。成果物は `dev-plan.md` だけにする。

## 出力書式

後続フェーズ(implement)が機械的に読む書式。見出し名・箇条書きの項目名・`[domain: ...]` の位置を
変更せず、以下をそのまま使う。`## 環境準備` と `## 生成物` は Step の前、文書の先頭に置く。

```markdown
## 環境準備

<worktree で依存をインストールするコマンド(lockfile を変更しないモード)。書けなければ「なし」(実装側が lockfile から既定を選ぶ)>

## 生成物

- 方式: <a または b。生成物が無ければ「なし」>
- 生成コマンド: <生成物を作るコマンド。無ければ「なし」>
- 生成物のパス: <repoRoot 相対の glob。無ければ「なし」>
- 根拠(規約の出所): <方式を選んだ理由。無ければ「なし」>

## Step 1: <名称> [domain: backend]
- 触るファイル: `src/server/routes/**`
- 前提ステップ: なし
- 内容: <何をどう変えるか>
- 通すテスト: <このステップと前提ステップが終わった時点で通る仕様のディレクトリの ID の列。無ければ「なし」>
- 完了条件: <検証可能な条件>
- 検証コマンド: `pnpm test ...`(このステップの通すテストだけを実行する)

## Step 2: <名称> [domain: frontend]
- 触るファイル: `src/app/**`
- 前提ステップ: 1
- 内容: <何をどう変えるか>
- 通すテスト: <...>
- 完了条件: <...>
- 検証コマンド: <...>
```

ステップ番号は 1 から連番。`mapped` では渡されたドメインマップのキーから一つを選び、
`unscoped` では `generic` を使う。各ステップは単一ドメインにする。

## 生成物の方式

生成物の扱いは対象プロジェクトの規約に従う。規約は docRoot 配下の `CLAUDE.md` と
`.claude/rules/**/*.md` から読む。読んでも定めが無ければ方式 b にする。

| 方式 | 内容 | 選ぶ条件 |
| --- | --- | --- |
| a | 各 Step が自分の worktree で生成物を作り、ソースの変更と同じコミットに入れる。生成物のパスをそのステップの「触るファイル」に含める | 規約が、ソースの変更と生成物を同じコミットに入れることを求めるとき |
| b | どの Step も生成物をコミットせず、全 Step の後に生成だけを行う最終 Step を実行する | 規約に定めが無いとき(既定)、または規約が方式 b を求めるとき |

`## 環境準備` に書けず「なし」とした dev-plan は、worktree での依存のインストールに次の既定を使う。
下の表に無い lockfile だけのプロジェクトでは、インストールが省かれるため、`## 環境準備` にコマンドを書く。

| lockfile | 既定のコマンド |
| --- | --- |
| `pnpm-lock.yaml` | `pnpm install --frozen-lockfile` |
| `package-lock.json` / `npm-shrinkwrap.json` | `npm ci` |
| `yarn.lock` | `.yarnrc.yml` があれば `yarn install --immutable`、無ければ `yarn install --frozen-lockfile` |
| `bun.lockb` / `bun.lock` | `bun install --frozen-lockfile` |
| `uv.lock` | `uv sync --frozen` |

## ドメインタグと下流接続

どのドメイン glob にも一致しない共有コード(例: `src/lib/` のドメイン横断ユーティリティ)への変更は、
その変更を必要とする機能側のステップに含め、そのステップのドメインタグを付ける。複数ドメインが同じ
共有コード変更を必要とする場合は、共有コード変更だけを独立した先行ステップに切り出し、主たる利用側の
ドメインタグを 1 つ付ける(タグなし・複数タグのステップは作らない)。
`mapped` で主たる利用側が一意に決まらないときは、渡されたドメインマップのキーのうち、依存の起点になるものを選ぶ。

### どのドメインにも属さないパスの扱い

`guard-write` が glob に一致しない書き込みを `ask` で止めたときは、その判断を正当な合図として扱い、握り潰さない。
そのパスを担当ドメインの glob に含めるドメインマップの変更をユーザーへ提案するか、ステップを再計画して
glob 内に収まる形へ分割する。ドメインマップは書き換えない。

## コミット責務

`dev-plan.md` は `evaluate_plan` ゲート通過直後にオーケストレーターがコミットする。
