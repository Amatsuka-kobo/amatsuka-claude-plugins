# ディスカッション・アジェンダ作成規約

## 概要

オーケストレーターが discuss フェーズの前半で使うスキル。intent・ARCHITECTURE・GOTCHAS・
既存コードの調査結果を入力に、ユーザーとのディスカッションで扱う論点を
`agenda.md` に構造化する。

本スキルの責務は「設計に入る前に人間と合意すべき分岐点をすべて可視化すること」にある。
設計そのもの(design.md)を書くことではない。

## チェックリスト

1. intent の `## 要求` `## 受け入れ基準` `## 非スコープ` `## 未確定事項` `## 合意済み事項` `## 意図的な制約` を読む。
2. orchestrating-runs の §0 の結果から、実行モードとドメインマップを実行に使う値として確認する。
   - `mapped` では、渡されたドメインマップを使って論点の対象範囲を整理する。
   - `unscoped` では、ドメインマップが「なし」と渡されるため、ドメインマップを使わず、ドメインによる境界を設けない。
   - §0 で ARCHITECTURE のパスを解決した場合は、システム概要・レイヤー構造・技術スタックを読む読み物として参照してよい。
   - ARCHITECTURE を実行に使うドメインマップの取得元として読み直さない。
   - ARCHITECTURE の指定がない場合は使わず、既定パスへフォールバックしない。
   - §0 で解決した GOTCHAS のパスだけを使う。
   - GOTCHAS の指定がない場合は使わず、既定パスへフォールバックしない。
   - 指定された GOTCHAS ファイルが存在すれば必ず読み、存在しなければスキップする。
3. 影響しそうな既存コードを Read / Grep / Glob で調査する。選択肢とトレードオフは既存実装の
   現実に基づいて書く(想像で書かない)。
4. 論点を抽出する。論点は how(実現方法)に限る。what(達成すること・受け入れ基準)は
   intent の `## 受け入れ基準` で合意済みなので論点として立てない。少なくとも次の 3 種を検討する:
   - **方針の分岐**: 実現方法が複数あり、選択によって設計が大きく変わるもの
   - **未確定事項**: intent の `## 未確定事項` は**全件を必ず論点化する**(1 件も落とさない)
   - **スコープの線引き**: 今回の run でやるか後続 Issue に回すかが割れうるもの
5. 各論点に「背景 / 選択肢(2 つ以上)/ 各選択肢のトレードオフ / 推奨案と理由」を書く。
6. 出力書式(下記)どおりに `agenda.md` を作成する。
7. 自己チェック: 各論点について「intent / ARCHITECTURE / 既存コードのどれが根拠か」を
   即答できるか確認する。答えられない論点は削るか根拠を書き直す。逆に、design.md を書く際に
   選択を迫られるのに agenda に無い分岐が残っていないかも確認する。

## 出力書式

facilitating-design-discussions(オーケストレーター)がこの書式のまま論点を提示する。
見出し名・項目名を変更しない。

```markdown
# agenda: <intent のゴール>

## 論点 1: <論点名>

- 背景: <なぜこれが分岐点か。intent / ARCHITECTURE / 既存コードの根拠>
- 選択肢A: <概要> — トレードオフ: <...>
- 選択肢B: <概要> — トレードオフ: <...>
- 推奨: <A or B>。理由: <...>

## 論点 2: <intent の未確定事項由来の論点>

- 背景: intent の未確定事項「<原文>」
- 選択肢A: ...
```

## 論点の粒度

- ユーザーが選択できる形(選択肢の比較)まで落とす。「どう思いますか」だけの、答えの形が定まらない開いた問いにしない。
- 設計・スコープ・振る舞いに影響する分岐だけを論点にする。自明な実装詳細(変数名・
  ファイル配置など既存規約から一意に決まるもの)は論点にしない。
- 論点が 1 件も立たないときは `agenda.md` を作らず、その旨と根拠をユーザーに示す。続けて `discussion.md` に「論点なし」と根拠を書き、`complete-phase discuss` して design へ進む。

## 合意済み事項の継承

この継承は体験の強化であり、働かなくても discuss は成立する(合意事項は intent の本文に残る)。

intent の `## 合意済み事項`(「論点 | 決定 | 理由」の表)と `## 意図的な制約`(「制約 | 理由」の表)の
行は、discuss より前にユーザーと合意済みである。これらを論点として再提示しない。同じ分岐を二度議論
させると、前回と違う結論が出たときに intent 文書と discussion.md の内容が食い違う。

代わりに `agenda.md` の冒頭、`## 論点 1` より前に `## 合意済みとして継承` セクションを置き、`## 合意済み事項`
と `## 意図的な制約` の表の行を、1 行を 1 件として列挙する。

```markdown
## 合意済みとして継承

- <論点>: <採用済みの選択肢>(intent の合意済み事項。本 run では再議論しない)
- 制約: <intent の意図的な制約>(理由: <...>)
```

- 除外するのは合意済みの分岐と意図的な制約だけである。discuss フェーズ自体は省略しない。
- intent の `## 未確定事項` の論点と、既存コードの調査から新たに立つ論点は、通常どおり全件を
  論点化する。
- 例外: 既存コードの調査で、合意済みの選択肢が実現不能または重大な副作用を持つと判明したときは、
  論点として立て直す。その論点の「背景」に「intent で <選択肢> に合意済みだが、
  <根拠となる既存コードの事実> により再検討が必要」と明記する。合意の破棄はユーザーに
  気づかれる形でのみ行う。

## コミット責務

`agenda.md` はオーケストレーターがコミットする(`orchestrating-runs` の成果物コミット規約)。

<HARD-GATE>
- コードを書かない・変更しない。成果物は `agenda.md` のみ。
- intent の「## 未確定事項」を agenda から落とさない。
- `## 合意済み事項` にある分岐を、再検討が必要な根拠(「合意済み事項の継承」の例外)を示さずに
  論点として立てない。`## 合意済みとして継承` に 1 行で列挙する。
</HARD-GATE>

## Red Flags(合理化への反論)

| 思考 | 現実 |
|---|---|
| 「論点が多いとユーザーが面倒なので絞ろう」 | 絞られた論点はオーケストレーターの独断で決まる。テンポの調整は facilitating 側の「すべて推奨案で進める」ショートカットが担う。アジェンダ側で間引かない。 |
| 「推奨案だけ書けば十分、比較は冗長」 | 比較のない推奨は誘導になる。ユーザーは選択肢とトレードオフを見て初めて推奨に乗るかどうかを判断できる。 |
| 「この不明点は些細なので論点にしなくていい」 | 些細かどうかを決めるのはユーザー。ゼロコストで選べる形(推奨案つき選択肢)にして出せば、些細なら一瞬で決まる。 |
| 「既存コードを読まなくても選択肢は書ける」 | 現実の実装と乖離した選択肢は議論そのものを無駄にする。 |
