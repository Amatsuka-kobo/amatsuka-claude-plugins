# ADR 候補の書き残し

ADR の 3 条件(`<plugin-root>/references/intent-format.md` の「持続層」)を満たす判断を、ADR 候補として run の手元の記録に書き残す。書くかどうかは `knowledgeTarget` の値によらない。ADR へ移すのは metatron で、codiel は ADR を書かない。

| 判定する判断 | 判定して書く時点 |
| --- | --- |
| intent-sync で持続層へ取り込む intent の `## 意図的な制約` の行 | 取り込みの手順(`syncing-intents` の `references/persistent-layer.md`)の中 |
| fix-loop で採った、設計を変える修正 | fix-loop の pass-gate の後 |

- 3 条件をすべて満たす判断 1 件につき 1 件書く。満たさない判断は書かない。
- fix-loop では、直した所見ごとに、修正が設計を変えたかを確かめてから 3 条件を判定する。

## 手元の記録

- 候補は `.codiel/runs/<slug>/try-<n>/reports/adr-candidates.md` に追記する。
- ファイルが無ければ、先頭行を `# ADR 候補(<slug> try-<n>)` にして作る。
- 既存のエントリは消さず、書き換えるのは `写し先` の行を足すときだけにする。
- 見出しと `制約` が同じエントリが手元の記録にあれば、新しいエントリを足さない。見出しが同じでも `制約` が違えば、別のエントリとして足す。
- `.codiel/runs/` は git に載せないので、このファイルはコミットしない。

エントリは、持続層の `[ADR 候補]` のエントリから見出しの印を除き、`run` の行を足した形で書く。値は例であり、実際の内容に置き換える。

```markdown
### <判断のタイトル>
- 制約: <...>
- 決定日: YYYY-MM-DD
- 出典 intent: docs/intents/YYYY-MM-DD-<slug>.md
- 関連 ADR: なし(ADR 候補)
- run: <slug> try-<n>
#### 背景
#### 検討した選択肢
#### 採用した結論
#### 理由
#### 影響範囲
```

- `決定日` は、手元の記録に書いた日を、実行する機械のローカルのタイムゾーンで付ける。
- `出典 intent` は、run の intent のパス(state の `intent`)にする。
- 見出しに `[ADR 候補]` の印と候補 ID を付けない。候補 ID は、持続層へ写すときに採番する。
- 5 つの小見出しは省かず、内容が無い小見出しは「なし」と書く。
- エントリの範囲は、`###` 見出しから、次の `###` 見出しか `##` 見出しの直前までとする。

エントリの末尾の `- 写し先:` の行は、持続層へ写したか、写さないと決めたかを表す。`写し先` の行が無いエントリと、行があっても `references/gotcha-candidates.md` の「手元の記録」の判定(コミットの到達、または `<slug>` の run の完了)を満たさないエントリが、まだ扱いの決まっていない未写しの候補である。`写さない(<理由>)` は決まった扱いで、未写しに含めない。ADR 候補の値は `<領域ファイルのパス>(<slug>, 候補 ID: <候補 ID>, <コミット>)` の形とし、判定にはこの `<slug>` と `<コミット>` を使う。

## 持続層への写し(`knowledgeTarget` が `intents` のときだけ)

`metatron` のときは写さず、手元の記録と一覧だけにする。写す時点(intent-sync と finalize)、`写し先` の行を足す時点、写した領域ファイルを入れるコミットは、`references/gotcha-candidates.md` の「持続層への写し」と「手元の記録」に従い、ファイル名を `reports/adr-candidates.md` に読み替える。集める候補と写し先の領域は、次の規則で決める。

- 集めるのは、同じ slug のすべての try の手元の記録のうち、未写しのエントリである。
- この try の候補は、確かめずに写す。
- 前の try の候補は、写し先の領域が決まっているときだけ、写す前に人に確かめる。領域が決まらない候補は、確かめずに手元の記録に残して一覧に出す。`mark-ask <phase> --slug <slug> --kind confirm`(`<phase>` は今のフェーズにする。intent-sync の作業中は `intent-sync`、finalize の作業中は `finalize`)で待ち、該当する候補のタイトルと手元の記録のパスを一覧で示してから、AskUserQuestion で 1 件ずつ「写す」か「写さない」かを聞く。答えを得たら `resume` で戻す。
- 写さないと決めた候補には、答えを得た時点で、手元の記録のエントリへ `- 写し先: 写さない(<人が示した理由>)` を足す。この行を持つ候補は、コミットの到達と関係なく、以後の intent-sync と finalize で集めない。
- 写し先の領域は、その判断の出典になった `## 意図的な制約` の行を取り込んだ領域にする。出典の行が無い判断(fix-loop の修正など)や、領域が 1 つに決まらないときは、取り込み先の領域のうち intent の `domains` で最初に挙がっているものにする。
- 1 つの判断は 1 つの領域にだけ写す。同じ制約を複数の領域へ取り込んだときも、写し先は上の規則で 1 つに絞る。

写すエントリごとに、次の順で書く。

1. 写し先の領域ファイルの `## 意図的な制約` に、同じタイトルと同じ `制約` のエントリがあるかを確かめる。見出しだけが同じで `制約` が違うエントリは、同じとみなさない。`[ADR 候補: <候補 ID>]` の印を持つエントリと、metatron が縮めた参照形(印の無い見出しと `制約` の行と `関連 ADR` の行だけのエントリ)の両方を対象にする。あれば写さず、印のエントリなら印の候補 ID を、参照形なら `関連 ADR` の行の `(候補 ID: <候補 ID>)` を 4 で使う。
2. `codiel-state next-adr-candidate-id --file <領域ファイルのパス> --domain <正規化後の領域名>` を呼び、出力の `candidateId` を候補 ID に使う。採番はエントリごとに、前のエントリを書いた後で呼ぶ。
3. 見出しの末尾に ` [ADR 候補: <候補 ID>]` を付け、`run` と `写し先` の行を除いたエントリを、`## 意図的な制約` の末尾に新しいエントリとして書く。intent の表に同じ行があるかによらず、新しいエントリにする。
4. コミットの後、手元の記録のエントリに `- 写し先: <領域ファイルのパス>(<slug>, 候補 ID: <候補 ID>, <コミット>)` を足す。`<コミット>` は、領域ファイルを入れたコミットの後の `git rev-parse HEAD` の値にする。

既存の参照形のエントリは書き換えず、候補 ID も使い回さない。

## 一覧

- finalize の結果レポートには、この try の `reports/adr-candidates.md` のエントリと、前の try のエントリのうち未写しのものを一覧する。stop したときの完了報告の一覧は、`orchestrating-runs` 本文の 2.4 に従う。
- 一覧には、エントリごとのタイトルと `写し先` の値(未写しなら「未」)と、手元の記録のパスを書く。
- 未写しのエントリには、持続層へ写さなかった理由(`metatron` の run、または取り込んだ領域が無い)を添える。
- 候補が無ければ「なし」と書き、3 条件を満たす判断が無かったのか、取り込みを飛ばしたのかを添える。
