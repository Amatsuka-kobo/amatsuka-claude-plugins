# 設計書執筆規約

## 概要

オーケストレーターが design フェーズで使うスキル。intent(要求・受け入れ基準・非スコープ)と
`discussion.md`(discuss フェーズでユーザーと合意した決定の記録)を入力に、変更方針・変更対象・影響を受ける機能単位を
`design.md` として構造化する。

## チェックリスト

1. intent の `## 要求` `## 受け入れ基準` `## 非スコープ` `## 意図的な制約` を読む。
2. `discussion.md` の各論点(状態・決定・理由)を読む。「状態: 決定」の論点は設計を拘束し、黙って覆さない。
   合意から逸脱する必要があると判断したときは、逸脱した設計を書かず、`## 方針` に「discussion.md 論点 N の決定と衝突する事実と理由」を再協議事項として明記する(ウォークスルーでユーザーに再提示する)。
   「状態: 未決」の論点は、どの選択肢でも破綻しにくい設計を選び、その旨を `## 方針` に明記する。
   discussion.md が扱っていない未確定の点は、推測で埋めず、`## 方針` に未確定と明記する。
3. orchestrating-runs の §0 の結果から、実行モードとドメインマップを実行に使う値として確認する。
   - `mapped` では、渡されたドメインマップを使って `## 変更対象` の各行の所属ドメインを整理する。
   - `unscoped` では、ドメインマップが「なし」と渡されるため、ドメインマップを使わず、ドメインによる分割を行わない。
   - 持続層(`docs/intents/domains/<領域>.md`)のパスが分かっていれば読み、`## 意図的な制約` を設計の前提にする。指定がなければスキップする。
   - 持続層の制約に反する設計が要るときも、黙って進めず、`## 方針` に「持続層 <領域名> の制約と衝突する事実と理由」を再協議事項として明記する。
4. `## 変更対象` に挙げる既存ファイルは、設計を書く前に Read で中身を確認する(既存パターン踏襲)。
   読まずに「たぶんこう実装されているはず」で設計しない。
5. 受け入れ基準を一つずつ辿り、それぞれが `## 方針` `## 変更対象` のどの記述で満たされるかを
   対応付ける。満たされない基準が残っていないか確認する。
6. `## 方針` には代替案を最低 2 つ書き、採用理由・却下理由を明記する。単一案の正当化ではなく
   比較によって採用根拠を示す。採用案が `discussion.md` の決定に対応する場合は「discussion.md
   論点 N の決定に基づく」と出所を明記する。代替案が 1 つしか立たないときは、検討して却下した方向性とその理由を
   `## 方針` に書く。
7. `## 影響を受ける機能単位` に仕様のディレクトリの ID を列挙する。命名と、作る仕様を決める
   規則の正式な定義は `writing-test-specs` スキルにある(本スキルはそれを前提に一覧を作るのみ)。
   この一覧は test-spec フェーズが `<testsDir>/<ID>/` を作成・更新する入力になるため、既存の
   仕様の流用か新規かを判別できる粒度で書く。
   `<testsDir>/e2e/frontend/` に既にある画面は、その名前をそのまま ID に使う。
   仕様のディレクトリが無い新しい画面の行は、「候補の行の書式」で書き、ウォークスルーでも挙げる。
8. YAGNI: intent に書かれていない要求・受け入れ基準にない機能を設計に追加しない。
   「ついでに直せる」「将来役立つ」は追加理由にならない。`## 影響を受ける機能単位` の列挙にも同じ基準を当て、影響を受けない単位を多めに挙げない。
9. 出力書式(下記)どおりに `design.md` を作成する。コードは書かず変更もしない。成果物は `design.md` だけにする。
10. 自己チェック: `## 変更対象` の各行について「intent のどの要求が根拠か」を即答できるか
    確認する。答えられない行は YAGNI 違反の疑いがあるため設計から外す。

## 出力書式

後続フェーズ全員が読む書式。見出し名・順序を変更せず、以下をそのまま使う。

```markdown
# design: <intent のゴール>

## 目的

<intent の要求から導出した、この変更が達成すべきこと>

## 方針

- 案A: <概要> — 採用/却下。理由: <...>
- 案B: <概要> — 採用/却下。理由: <...>

採用案: <A or B> 。理由: <比較に基づく採用根拠>

## 変更対象

- `<既存/新規ファイルパス>` — <変更内容の概要>

## 影響を受ける機能単位

- `units/<repoRoot 相対パス>` — <影響内容>
- `e2e/frontend/<画面名>` — <影響内容>(名前が未定なら「候補の行の書式」に従う)
- `e2e/backend/<API のルートパス>` — <影響内容>

## データ・API の変更

- <スキーマ変更・エンドポイント変更・後方互換性への影響。なければ「なし」>

## リスクと可逆性

- <想定リスクと、問題が起きた場合に元に戻せるか・どう戻すか>
```

## 候補の行の書式

新しい画面で名前が未定のときは、`## 影響を受ける機能単位` の行を次の形で書く。ウォークスルーで名前が決まったら、`e2e/frontend/<決まった名前>` の通常の ID の行に書き換える。

```markdown
- `e2e/frontend/(候補: <候補1> / <候補2> / <候補3>)` — <影響内容>
```

## 既存パターン踏襲

既存パターンと衝突する設計を出す場合は、なぜ既存パターンから逸脱するのかを
`## 方針` に明記する。

## コミット責務

`design.md` は `evaluate_design` ゲート通過直後にオーケストレーターがコミットする。
