# 回帰テスト運転規約

## 概要

test-loop フェーズと `/codiel:test`(単独実行)で使うスキル。記録された全テストの回帰の確認を行い、判定(green / red / broken)を出す。テストを書く手順は持たない(test-code フェーズの `scripting-tests` が書く)。NG が残ったときの修正の委譲は `orchestrating-runs` が出す。

実行の担い手は ID で分かれる。プロジェクトの test コマンドと、ID が `units/` で始まる仕様のディレクトリのテストはオーケストレーターが実行する。ID が `e2e/` で始まる仕様のディレクトリのテストは、実行の委譲先が担う。

## プラグインルート参照規約

このスキル起動時に通知される「Base directory for this skill」は
`<plugin-root>/skills/running-regression-tests` である。**`<plugin-root>` はそのベース
ディレクトリの 2 階層上**。`codiel-state` は対象プロジェクトのルートで次の形で呼ぶ:

```
node <plugin-root>/scripts/codiel-state.mjs <command> [引数...] --slug <slug>
```

## 2 つの起動モード

- run 経由(test-loop フェーズ): `orchestrating-runs` が運転し、run ブランチ上で全テストの回帰を確認する。NG は仕様のディレクトリごとにまとめて報告するだけで、修正の委譲・`record-attempt`・state の更新はオーケストレーターが行う。`e2e/` の実行の委譲先は `codiel-state` を呼ばない。
- 単独実行モード(`/codiel:test`): run の有無に関係なく実行できる。state 遷移はせず、NG があってもディスパッチせず報告のみ行う。引数(testsDir からの相対パス)があればそのディレクトリのテストだけに絞り、無ければ testsDir 全体を対象にする。

`e2e/` の実行の委譲先は、レポートの本文を最終の返答で返す。報告のファイルを Write で書かず、`git add` もしない。run 経由ではオーケストレーターが、自分で実行した結果と委譲先の返答を合わせて `runs/<slug>/try-<n>/reports/test-run-<n>.md` へ書く。単独実行では、返答を受けた側が `.codiel/reports/test-run-<日時>.md` へ書く。

名前の `<日時>` は、実行する機械のローカルのタイムゾーンの時刻で、`YYYYMMDD-HHMMSS` の形にする。タイムゾーンは名前に含めない。Bash では `date +%Y%m%d-%H%M%S` で得る(`date -u` を使わない)。

E2E は、仕様のディレクトリごとにテストフレームワークを 1 回起動する。
JSON の出力と、frontend では各ケースの最後の画面のスクリーンショットを、依頼文が指す実行ごとのディレクトリに出す。
返答に入れる項目は `../../references/e2e-report-format.md` に従う。

単独実行モードでは、E2E のレポート(`results.json`・`summary.md` か `failure.md`・画像)を `.codiel/reports/test-run-<日時>/<仕様のディレクトリの ID>/` にだけ置き、testsDir の `reports/` に書かない。
`failure.md` の直し方は、修正をしないので「なし」と書き、理由に単独の実行は報告だけを行うことを添える。

以降のチェックリストは run 経由を基準に書く。単独実行モードとの差分は都度注記する。

## 回帰の範囲

`<testsDir>/**/spec.md` の `tests` に記録されたすべてのテストと、プロジェクトの test コマンドを対象にする。影響の有無で絞らない。test コマンドは、コンテキストに宣言があればそれに従い、無ければ `package.json` の `scripts` から取る。どちらでも見つからなければ対象から外す。

## 同時実行

`<testsDir>/**/spec.md` の frontmatter に `parallel: true` を持つ仕様のディレクトリのテストだけを同時に実行し、持たないものは直列に実行する。frontmatter やキーが無ければ直列とする。ポート・データベースなど共有資源を持つテストを守るためである。同時実行数の上限は 4 とする。

## テストの実行環境と環境の失敗

理由が環境にある失敗(サーバーが起動しない、接続が拒否される、ポートが使用中、必要なサービスが無い)は、broken にも NG にも数えず、環境の失敗として理由と出力の抜粋をレポートに挙げる。

run 経由では、オーケストレーターが自分で実行したもの(プロジェクトの test コマンドと `units/` のテスト)は自分で 1 回だけ実行し直す。`e2e/` の仕様のディレクトリは、動いている委譲が無いときに 1 回だけ単独で実行し直させる。単独実行モードでは、自分で 1 回だけ実行し直し、残れば報告に挙げてユーザーに示す。`mark-ask` は使わない。

broken の修正は、テストが保護されているため、オーケストレーターの `mark-ask test-loop --kind confirm` を経て人が承認してから行う。このスキルは判定と報告までを担い、修正はしない。

## チェックリスト

1. 起動モードを確認し、対象範囲(「回帰の範囲」の全体、単独実行で引数指定があればそのディレクトリのみ)を確定する。対象が 1 件も無いときは判定を出さず、その旨を報告して終了する。
2. `<testsDir>/**/spec.md` の `tests` を読み、記録されたテストファイルを洗い出す。
3. プロジェクトの test コマンドを確認する。
4. 「同時実行」の規則に従ってテストを実行し、broken・NG・環境の失敗を区別して記録する。
5. プロジェクトの test コマンドを実行し、結果(pass/fail の件数、失敗があれば出力抜粋)を控える。コマンドが無ければ実行を省き、レポートに「test コマンドなし」と書く。
6. 環境の失敗が残れば、「テストの実行環境と環境の失敗」に従って実行し直す。
7. 判定(green / red / broken)を決める(下記「判定基準」)。
8. レポート(下記書式)を作成し、実際の実行出力の抜粋を転記して、最終の返答に書く。
9. (run 経由のみ)NG があれば、仕様のディレクトリごとにまとめて報告する。修正のディスパッチはしない。

## 判定基準

- green: 全テストが OK で、test コマンドも成功している(コマンドが無ければテストの OK だけで判定する)。環境の失敗が残っていない。
- red: 判定が出て期待と違うもの(NG)が 1 件以上残っている、または test コマンドに失敗がある。
- broken: 判定が出ないケースが 1 件でも残っている状態。green / red のいずれとも判定できない。

## レポート書式(`test-run-<n>.md` / `test-run-<日時>.md`)

```markdown
## サマリ

- OK: <件数> / NG: <件数> / 異常終了(broken): <件数> / 環境の失敗: <件数>
- test コマンド: <pass 件数> pass / <fail 件数> fail

## ケース別結果

### <ケース ID>: <判定 OK|NG|broken|環境の失敗>

<OK の場合は実行出力の抜粋のみ。NG の場合は次の 4 項目を必須で書く>
- 再現手順: <手順>
- 期待結果: <cases.md の記載>
- 実際の結果: <実行出力の抜粋>

<broken の場合は「判定不能(ASK)」とその理由を書く>
<環境の失敗の場合は理由と出力の抜粋を書く>

## E2E のレポート

<E2E の仕様のディレクトリごとに 1 項目。その回の実行ごとのディレクトリの `summary.md` か `failure.md` への、リポジトリ相対のリンクを書く。E2E の仕様のディレクトリが無ければ「なし」>

## test コマンドの結果

<手順 3 で確認した test コマンドの実行結果。失敗があれば出力抜粋。
コマンドが無ければ「test コマンドなし」>

## 判定

<green | red | broken>
```

## 完了報告

レポート本文の書式とは別に、`e2e/` の実行の委譲先は完了時に次の項目を最終の返答でオーケストレーターへ返す。

- 実行したテストの件数
- OK・NG・broken・環境の失敗の内訳

## HARD-GATE

<HARD-GATE>
**出力を見ずに合格を主張しない**。レポートの各ケースには実際の実行出力の抜粋を必ず含める。「全部通ったはず」という推測でレポートを書くことは捏造と同じであり許されない。
**broken と NG を混同しない**。判定が出ない(broken)ケースと、判定が出て期待と違う(NG)ケースを取り違えない。判断がつかない場合は broken として ASK に挙げる。
**環境の失敗を broken にも NG にも数えない**。理由が環境にある失敗は、環境の失敗として別に報告する。
**単独実行モードでは NG があってもコード修正をディスパッチしない**。報告のみで終了する。
</HARD-GATE>

## Red Flags(合理化への反論)

| 思考 | 現実 |
|---|---|
| 「flaky なので 2 回目で通ったら OK 扱いにしよう」 | 2 回目にたまたま通った結果を採用するのはフレークの隠蔽であり、毎回同じ判定が出る状態を確かめるのが回帰の確認である。 |
| 「今回変更した仕様のディレクトリだけ確認すれば十分」 | 回帰の範囲は記録された全テストと test コマンドの合算であり、影響の有無で絞らない。今回変更していない箇所への副作用を見つけるためにこそ全件を確認する。 |
| 「NG は 1 件だけだからレポートの再現手順は省略していい」 | 再現手順・期待結果・実際の結果は修正の委譲への入力であり、1 つでも欠けると再現できない。件数の多寡は省略の理由にならない。 |
| 「broken か NG か迷うが、たぶん NG だろうから報告しよう」 | 判断がつかないものを NG として報告すると、再現できないバグ修正が委譲されてしまう。迷ったら broken として ASK に挙げる。 |
