# 回帰テスト運転規約

## 概要

test-loop フェーズと `/codiel:test`(単独実行)で使うスキル。記録された全テストの回帰の確認を行い、判定(green / red / broken)を出す。テストを書く手順は持たない(test-code フェーズの `scripting-tests` が書く)。NG が残ったときの修正の委譲は `orchestrating-runs` が出す。

実行の担い手は ID で分かれる。プロジェクトの test コマンドと、ID が `units/` で始まる仕様のディレクトリのテストはオーケストレーターが実行する。ID が `e2e/` で始まる仕様のディレクトリのテストは、実行の委譲先が担う。

## 起動モード

run 経由(test-loop フェーズ)は `orchestrating-runs` が運転し、run ブランチ上で全テストの回帰を確認する。NG は仕様のディレクトリごとにまとめて報告するだけで、修正の委譲・`record-attempt`・state の更新はオーケストレーターが行う。レポートは `runs/<slug>/try-<n>/reports/test-run-<n>.md` に書く。

単独実行モード(`/codiel:test`)は、run の有無に関係なく実行でき、run 経由との差分は次の 5 点である。

- state 遷移をせず、NG があっても修正をディスパッチせず報告だけを行う。
- 引数(testsDir からの相対パス)があれば、そのディレクトリのテストだけに絞り、プロジェクトの test コマンドは実行しない。引数が無ければ testsDir 全体と test コマンドを対象にする。
- active な run があるときは、委譲の待ちを `adhoc-` で始まる id で記録する(`orchestrating-runs` の §3)。
- レポートは `.codiel/reports/test-run-<日時>.md` に書き、E2E のレポートは `.codiel/reports/test-run-<日時>/<仕様のディレクトリの ID>/` にだけ置く。testsDir の `reports/` には書かない。
- `failure.md` の直し方は「なし」と書き、理由に単独の実行は報告だけを行うことを添える。

`e2e/` の実行の委譲先は、レポートの本文を最終の返答で返す。報告のファイルは Write で書かず、`git add` もしない。レポートを作るのはオーケストレーターで、自分で実行した結果と委譲先の返答を合わせて書く。run 経由では、委譲先の返答を `waits/<id>.md` へ書いてから、レポートへ合わせる。E2E は仕様のディレクトリごとにテストフレームワークを 1 回起動し、置き場・名前・日時の形・返答の項目は `../../references/e2e-report-format.md` に従う。

## 回帰の範囲

`<testsDir>/**/spec.md` の `tests` に記録されたすべてのテストと、プロジェクトの test コマンドを対象にする(単独実行でパスの指定があるときは、指定したディレクトリのテストだけで、test コマンドは対象にしない)。影響の有無で絞らない。test コマンドは、コンテキストに宣言があればそれに従い、無ければ `package.json` の `scripts` から取る。どちらでも見つからなければ対象から外す。

## 同時実行

同時実行の規則は `e2e/` の実行の委譲にだけ当てる。`spec.md` の frontmatter に `parallel: true` を持つ仕様のディレクトリの委譲だけを同時に出す(上限 4)。それ以外は直列に出す。詳細は `../orchestrating-runs/references/delegation-env.md` の「テストを実行する委譲の並べ方」を Read して従う。プロジェクトの test コマンドと `units/` のテストは、オーケストレーターが自分で直列に実行する。

## 環境の失敗と broken の修正

理由が環境にある失敗(サーバーが起動しない、接続が拒否される、ポートが使用中、必要なサービスが無い)は、broken にも NG にも数えず、環境の失敗として理由と出力の抜粋をレポートに挙げる。

実行し直しは環境の失敗にだけ、1 回行う。自分で実行したものは自分で、`e2e/` の仕様のディレクトリは動いている委譲が無いときに委譲先へ単独で実行し直させる。結果はレポートの `## 実行し直し` のセクションに書く。中断後の再開では、このセクションの有無で済んだかを判断する。それでも残れば、run 経由は `orchestrating-runs` の運転に従い、単独実行モードは報告に挙げてユーザーに示す(`mark-ask` は使わない)。環境の失敗以外の失敗は実行し直さず、出た判定のまま報告する。2 回目に通った結果だけを採用して OK にしない。

broken の修正は、テストが保護されているため、オーケストレーターの `mark-ask test-loop --kind confirm` を経て人が承認してから行う。このスキルは判定と報告までを担い、修正はしない。

## チェックリスト

1. 起動モードを確認し、対象範囲を確定する(「回帰の範囲」)。対象が 1 件も無いときは判定を出さず、その旨を報告して終了する。
2. `<testsDir>/**/spec.md` の `tests` を読み、記録されたテストファイルを洗い出す。
3. 自分で実行する分(プロジェクトの test コマンドと、ID が `units/` で始まる仕様のディレクトリのテスト)を直列に実行する。test コマンドの結果は pass/fail の件数と、失敗があれば出力の抜粋を控える。コマンドが無ければレポートに「test コマンドなし」と書く。`units/` は broken・NG・環境の失敗を区別して記録する。
4. ID が `e2e/` で始まる仕様のディレクトリの実行を、「同時実行」の規則に従って委譲し、完了通知で返答の完了報告とレポート本文を受ける。
5. 環境の失敗が残れば、「環境の失敗と broken の修正」に従って実行し直す。
6. 判定(green / red / broken)を決める(下記「判定基準」)。
7. オーケストレーターがレポート(下記書式)を作り、実際の実行出力の抜粋を転記して、最終の返答でサマリを報告する。run 経由で NG があれば、仕様のディレクトリごとにまとめて報告し、修正のディスパッチはしない。

## 判定基準

- green: 全テストが OK で、test コマンドも成功している(コマンドが無ければテストの OK だけで判定する)。環境の失敗が残っていない。
- red: 判定が出て期待と違うもの(NG)が 1 件以上残っている、または test コマンドに失敗がある。
- broken: 判定が出ないケースが 1 件でも残っている状態。green / red のいずれとも判定できない。NG か broken か判断がつかないケースは、NG として報告せず broken として ASK に挙げる。

## レポート書式(`test-run-<n>.md` / `test-run-<日時>.md`)

```markdown
## サマリ

- OK: <件数> / NG: <件数> / 異常終了(broken): <件数> / 環境の失敗: <件数>
- test コマンド: <pass 件数> pass / <fail 件数> fail

## ケース別結果

### <ケース ID>: <判定 OK|NG|broken|環境の失敗>

<OK の場合は実行出力の抜粋のみ。NG の場合は次の 3 項目を必須で書く>
- 再現手順: <手順>
- 期待結果: <cases.md の記載>
- 実際の結果: <実行出力の抜粋>

<broken の場合は「判定不能(ASK)」とその理由を書く>
<環境の失敗の場合は理由と出力の抜粋を書く>

## E2E のレポート

<E2E の仕様のディレクトリごとに 1 項目。その回の実行ごとのディレクトリの `summary.md` か `failure.md` への、リポジトリ相対のリンクを書く。E2E の仕様のディレクトリが無ければ「なし」>

## test コマンドの結果

<手順 3 で実行した test コマンドの結果。失敗があれば出力抜粋。
コマンドが無ければ「test コマンドなし」。パス指定の単独実行では「対象外」>

## 実行し直し

<環境の失敗を実行し直したときだけ置く。実行し直した対象と結果を書く>

## 判定

<green | red | broken>
```

## 完了報告

`e2e/` の実行の委譲先は、完了時に `../../references/e2e-report-format.md` の「委譲先が返答に入れる項目」を最終の返答でオーケストレーターへ返す。

オーケストレーターは、自分の実行結果と委譲先の返答を合わせて、最終の返答とレポートのサマリに次の項目を書く。長さの上限は設けない。

- OK・NG・broken・環境の失敗の件数(委譲先の内訳と、自分で実行した `units/` の結果の合計)
- test コマンドの pass・fail の件数
- 判定
- レポートのパス
