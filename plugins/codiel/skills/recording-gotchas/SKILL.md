# GOTCHAS 追記運用規約

実行者はオーケストレーター本体であり、サブエージェントへのディスパッチは発生しない。

## 台帳のパス

固定パスを前提にせず、次で解決したパスを台帳として扱う。

```
node -e 'import("<plugin-root>/scripts/lib.mjs").then(({ resolveDocPaths }) => console.log(resolveDocPaths(process.cwd()).gotchas))'
```

(`<plugin-root>` は絶対パスに展開して実行する)

## 記録の契機と担当

| 契機 | 担当 |
|---|---|
| Raguel が `STOP` verdict を出した | `raguel-gating` の STOP 手順から本スキルが起動され、オーケストレーターが追記する |
| test-loop / fix-loop がループ上限超過(`record-attempt` exit 3)で `ASK` に倒れた | 人間の裁定(中止)が確定した時点でオーケストレーターが本スキルを起動する |
| `mcp__raguel__record_outcome(outcome: "incident")` が記録された | incident 記録と同時にオーケストレーターが本スキルで追記する |
| レビューで設計時に想定していなかった仕様漏れ・考慮漏れが発覚した | fix-loop 完了時にオーケストレーターが記録要否を判定し、該当すれば追記する |

## 記録の判断

判断は 1 問だけとする。「次にこのプロジェクトを触るエージェントがこれを知らないと同じ失敗をするか?」が **Yes のときだけ記録する**。

- 別のリポジトリでも同じ対策が要るものは記録しない。一般的な AI の失敗パターンは判例ストアの領分とする。
- 一過性の凡ミス(タイポ、変数名の取り違え)は記録しない。
- 一般的な失敗とプロジェクト固有情報が混ざるときは、プロジェクト固有の部分だけを切り出して記録する。「型を確認せず存在しないメソッドを呼んだ」は記録せず、「このプロジェクトの ORM のこのバージョンにそのメソッドが無い」を記録する。
- 判断が割れるときは「次に同じプロジェクトファイルを触るエージェントの手がかりになるか」で判定する。

記録する例: 「このプロジェクトの ORM は `softDelete()` を持たず、`deletedAt` カラムへの `update` で論理削除する」。

## 手順

1. 「記録の契機と担当」で起点イベントの種別を確認する。
2. 台帳のパスを解決し、既存エントリを読む。
3. 「記録の判断」に照らし、Yes でなければここで終了する。判断結果は run の記録に残してよい。
4. 「エントリの書式」に従ってエントリを組み立てる。
5. 「書き込み手段」に従って追記する。
6. 台帳を `git add` し、`codiel(gotchas): <一行要約> (issue-N try-M)` の形式でコミットする。run が特定できないときだけ `(issue-N try-M)` を省く。

## 書き込み手段

- **metatron CLI の案内がコンテキストにあればそれを使い、なければ直接追記する。** 案内があるときは、エントリの JSON を一時ファイルへ書き、案内された絶対パスの CLI を `append-gotcha --input <一時ファイルのパス>` で実行する。
- **直接追記が hook に拒否されたら、拒否メッセージに示された CLI で実行し直す。** 拒否メッセージが CLI の絶対パスを載せているので、そこから読み取って使う。

metatron のインストール有無を検出しない。metatron のプラグインルート・ソース・CLI パスを推測しない。使ってよい CLI のパスは、コンテキストに現れた案内と拒否メッセージに載っていたものだけとする。

| 状態 | 経路 |
|---|---|
| CLI の案内がコンテキストにある | 案内された CLI の `append-gotcha` で追記する |
| CLI の案内がコンテキストから失われた | 直接追記し、拒否されたら拒否メッセージの CLI で実行し直す |
| metatron が無い | 直接追記する(拒否は起きない) |

CLI に渡す JSON は `{ title, date?, task, mistake, cause, countermeasure, promotionCandidate }` とする。`task` / `mistake` / `cause` / `countermeasure` / `promotionCandidate` が下記 5 フィールドに対応する。`date` を省くと当日日付になる。採番・挿入位置・雛形の作成は CLI が行う。

## エントリの書式

直接追記するときは、CLI を使わないだけで書式を同じにする。

```markdown
### [YYYY-MM-DD] GOTCHA-NNN: <失敗のタイトル>

**タスク**: <何をしようとしていたか>
**失敗内容**: <具体的に何を間違えたか>
**原因 (推測)**: <なぜそうなったか>
**対策**: <今後 AI はどう振る舞うべきか>
**昇格候補**: Yes / No
```

- 挿入位置は `## 失敗パターン一覧` の直下(先頭)とする。ファイル末尾に追記しない。
- 採番は `## 失敗パターン一覧` 配下の既存エントリを全件走査した最大値 + 1 とする。
- `対策` は精神論を書かず、次のエージェントがそのまま実行できる行動に落とす。「Prisma の API 名に注意する」ではなく「実装前に `node_modules/.prisma/client/index.d.ts` を Read し、実在するメソッド名であることを確認してから実装する」と書く。
- 関連ファイルの欄は持たない。パスを示す必要があれば `対策` の本文に書く。
- 関連する既存エントリの欄は持たない。触れる必要があれば `対策` の本文で `GOTCHA-00X` を挙げる。
- Codiel のフェーズ名の欄は持たない。フェーズの情報が要るときは `タスク` に自然文で含める。
- `昇格候補` は `Yes` か `No` だけを書く。対策が「特定の操作をするとき常に」効くものなら `Yes` とする。

### タグ

- 位置は `GOTCHA-NNN:` の直後、タイトルの直前とし、区切りは半角スペース 1 個とする。
- 使うリテラルは `[解決済み]` と `[対象外]` の 2 種だけとする。
- 見出しへのタグ挿入に加えて、エントリ末尾に理由を 1 行追記する(`**[解決済み] (2026-08-20)**: <理由>`)。
- 既にタグが付いているエントリへ付け直すときは、見出しのタグを差し替え、理由行は追記する。前の理由行は残す。

```
### [YYYY-MM-DD] GOTCHA-NNN: [解決済み] タイトル
```

### 台帳が無いとき

台帳または `## 失敗パターン一覧` 節が無ければ、次の雛形ごと作成してから新エントリを挿入する。初期化コマンドをユーザーへ案内して止めない。

```markdown
# GOTCHAS

このプロジェクトで AI が実際にやってしまった失敗のパターンを蓄積する。
発見された失敗を、下記のフォーマットで追記していく。

## 運用ルール

- 新しいものを上に追加する。
- 同じパターンが 5 件以上蓄積されたら、スキルまたは Hook への昇格を検討する。
- 解決済みの項目は `[解決済み]` タグを付けて残す。削除しない。
- 陳腐化した項目は `[対象外]` タグを付けて残す。削除しない。

## 記入テンプレート

### [YYYY-MM-DD] GOTCHA-NNN: 失敗のタイトル

**タスク**: (何をしようとしていたか)
**失敗内容**: (具体的に何を間違えたか)
**原因 (推測)**: (なぜそうなったか)
**対策**: (今後 AI はどう振る舞うべきか)
**昇格候補**: Yes / No (スキルや Hook にするべきか)

## 失敗パターン一覧
```

<HARD-GATE>
- **既存エントリの本文は書き換えず、削除もしない。** 追記だけを行う。
- **矛盾が判明したエントリは `[対象外]` タグの付与と理由行の追記で対応する。** 本文を消して書き直さない。
</HARD-GATE>

## Red Flags(合理化への反論)

| 思考 | 現実 |
|---|---|
| 「恥ずかしい失敗なので記録したくない」 | 台帳は次の run のための資産であり、恥の有無は記録可否と無関係。記録しなければ次の run が同じ失敗を再演する。 |
| 「たぶん二度と起きない」 | 「たぶん」は判断フローの Yes/No 判定を回避する推測。プロジェクト固有の罠は担当エージェントが変わっても環境・スキーマ・慣習が変わらない限り再発しうる。 |
| 「STOP の原因は自分の判断ミスだから記録は不要」 | STOP は最も学習価値の高い失敗であり、原因が判断ミスであっても「次回同じ判断をしないための手がかり」として記録する。 |
| 「対策は『注意する』でも書けば形式は満たせる」 | 精神論の対策は次のエージェントが実行できる手順にならず、再発防止効果がない。「〜する前に〜を確認する」の形に必ず落とす。 |
| 「hook に拒否されたので記録できなかった」 | 拒否メッセージが CLI の絶対パスを載せている。そのコマンドで実行し直す。 |
| 「台帳が無いので初期化を待つ」 | 記録の契機は失敗発生時であり、そこで止めれば学習機会を失う。雛形ごと作成して記録する。 |
