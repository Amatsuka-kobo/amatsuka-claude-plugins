# GOTCHAS

プロジェクト固有の落とし穴台帳。Codiel が「失敗を記録してプロジェクト毎に成長する」ための
生成側の資産(判定側の記憶は Raguel の判例ストアが担う)。

## 運用説明

- **何を書くか**: このプロジェクトで一度起きた、かつ再発しうる固有の失敗・注意点。
  一般論(「テストは書きましょう」等)や、他プロジェクトにも通用する汎用的な教訓は書かない。
  Raguel の判例ストアで扱うべき一般則と、ここで扱うべき「このプロジェクト固有の罠」は区別する。
- **いつ書くか**(記録の契機):
  1. Raguel が `STOP` verdict を出したとき
  2. test-loop / fix-loop がループ上限(既定 5 回)を超過して ASK に倒れたとき
  3. `record_outcome(incident)` が記録されたとき(PROCEED した変更が実害を出した)
  4. レビューで「設計時に想定していなかった仕様漏れ・考慮漏れ」が発覚したとき
- **誰が書くか**: `recording-gotchas` スキルに従い**オーケストレーター本体**が追記する
  (サブエージェントへのディスパッチは行わない)。人間が直接追記してもよい。
- **誰が読むか**: 全フェーズのサブエージェントが作業開始前に必読(ディスパッチプロンプトで
  「関連する GOTCHAS エントリを確認せよ」と明示的に指示される)。特に該当ファイル・該当フェーズの
  エントリは見落とさないこと。

## エントリ書式

新しいエントリは末尾に追記する(古いものを削除・改変しない。反証された場合も「無効化」の追記で
上書きし、履歴自体は残す)。連番 `GOTCHA-NNN` は既存の最大値 + 1 を採番する。

```markdown
## GOTCHA-001: <一行要約>
- **日付**: 2026-07-08
- **発生フェーズ**: test-loop
- **症状**: <何が起きたか>
- **根本原因**: <なぜ起きたか>
- **予防策**: <次回どうすれば防げるか(具体的な手順・チェック)>
- **関連ファイル**: `src/...`
```

- **発生フェーズ**は §2 のフェーズ名(init/design/test-spec/dev-plan/implement/test-loop/pr/
  review/fix-loop/triage/finalize)のいずれか、または `outcome`(incident 申告時)を書く。
- **予防策**は「気をつける」のような精神論ではなく、次に同じ状況に遭遇したエージェントが
  そのまま実行できるチェック・手順を書く。

## 記入例

## GOTCHA-001: 存在しない Prisma API を幻覚して実装した
- **日付**: 2026-06-14
- **発生フェーズ**: implement
- **症状**: `codiel-implementer-backend` がユーザーの論理削除機能を実装する際、
  `prisma.user.softDelete()` という存在しない API を呼び出すコードを生成し、TDD の RED フェーズで
  「メソッドが存在しない」という型エラーではなく `any` 型経由の実行時エラーとして検出が遅れた。
  結果として test-loop で 2 回分の試行を空費した。
- **根本原因**: 実装対象の Prisma バージョン(5.x)のドキュメントを参照せず、一般的な ORM の
  命名慣習(`softDelete` 等)から類推してコードを書いた。プロジェクトの `schema.prisma` には
  そもそも論理削除用カラム(`deletedAt`)しか存在せず、`update({ data: { deletedAt: new Date() } })`
  を使うのが正しい実装だった。
- **予防策**: Prisma のようなライブラリ API を使うステップでは、実装前に必ず
  `node_modules/.prisma/client/index.d.ts`(型定義)または `prisma/schema.prisma` を Read し、
  実在するメソッド・フィールド名であることを確認してから実装する。存在確認をせずに
  API 名を書いた場合は TDD の RED フェーズで「型エラーで失敗しているか、実行時エラーで
  失敗しているか」を区別し、後者であれば即座に API の実在を疑う。
- **関連ファイル**: `src/server/user-service.ts`, `prisma/schema.prisma`

## GOTCHA-002: E2E テストがタイムゾーン依存で不安定だった(flaky)
- **日付**: 2026-06-20
- **発生フェーズ**: test-loop
- **症状**: `screen-task-list` の E2E ケース(期限日の表示が「本日」「明日」等の相対表記になることを
  検証するケース)が、CI(UTC 実行)ではローカル(Asia/Tokyo 実行)と異なる判定結果になり、
  スクリプト安定化ループ(A)で「異常終了ではないが実行環境によって OK/NG が変わる」という
  想定外の状態に陥った。原因特定に試行上限(5 回)近くまで消費した。
- **根本原因**: テストスクリプトが `new Date()` を直接使って期待値を計算しており、実行環境の
  タイムゾーン設定(`TZ` 環境変数)に依存していた。プロダクトコード側も日付比較にサーバーの
  ローカルタイムゾーンを使っており、UTC 環境では日付境界を跨ぐタイミングがずれていた。
- **予防策**: E2E スクリプトで日時を扱う際は、テスト対象の「現在時刻」をモック・固定するか
  (例: Playwright の `page.clock` や環境変数での注入)、期待値の計算をプロダクトコードと
  同じタイムゾーン基準の関数(`src/lib/date.ts` の `toAppTimezone()`)を経由して行う。
  CI の実行環境変数に `TZ=Asia/Tokyo` を明示的に設定し、ローカルと CI で挙動を揃える。
  新規に日時判定を含むケースを書く際は、このプロジェクトが `TZ=Asia/Tokyo` を正としている前提を
  必ず確認する。
- **関連ファイル**: `.codiel/specs/screen-task-list/scripts/due-date.spec.ts`, `src/lib/date.ts`
