# E2E のレポートの書式

この書式は、run の中で E2E の仕様のディレクトリのテストを実行するたびに書くレポートと、`/codiel:test` の単独実行のレポートに適用する。ユニットテストの仕様のディレクトリ(`units/`)には適用しない。

## 置き場と名前

run の中のレポートは、仕様のディレクトリの `reports/` の下に、実行ごとのディレクトリを作って置く。

- 置き場は `<testsDir>/e2e/{frontend,backend,cli}/<名前>/reports/<実行ごとのディレクトリ>/` である。
- 実行ごとのディレクトリの名前は `<日時>-<slug>-try<n>` とする。`<slug>` は run の slug、`<n>` は try の番号である。
- 日時は、実行する機械のローカルのタイムゾーンの時刻を `YYYYMMDD-HHMMSS` で書く。タイムゾーンは名前に含めない。Bash では `date +%Y%m%d-%H%M%S` で得る。
- 実行は、仕様のディレクトリごとにテストフレームワークを 1 回起動する。複数の仕様のディレクトリを 1 回の起動で走らせない。
- 実行ごとのディレクトリの名前と、メインの作業ツリーの絶対パスは、オーケストレーターが実行の前に決め、依頼文(worktree の委譲では brief)に書く。worktree の中で実行する委譲も、出力はこの絶対パスの下に出す。

`/codiel:test` の単独実行は、`<testsDir>` の `reports/` に書かず、`.codiel/reports/test-run-<日時>/<仕様のディレクトリの ID>/` にだけ置く。`<日時>` は同じ実行の報告 `.codiel/reports/test-run-<日時>.md` と同じ値にする。

## ファイル

実行ごとのディレクトリに置くファイルは次の表のとおりである。

| ファイル | 書く者 | 内容 |
| --- | --- | --- |
| `results.json` | テストを実行した者 | テストフレームワークの JSON の出力をそのまま保存する。Playwright は JSON のレポーター(`--reporter=json`)を使い、出力先を環境変数 `PLAYWRIGHT_JSON_OUTPUT_NAME` で指す |
| `results.json`(JSON を出せないフレームワーク) | オーケストレーター | 最小の形で書く。ケースごとに `name`(ケース名)・`result`(結果の 5 つの値のどれか)・`durationMs`(時間)・`error`(エラーの文言。無ければ空文字列)を持つ配列を `cases` に置く。値は委譲先の返答から取る |
| `summary.md` | オーケストレーター | 成功した実行と、Red の確認の実行 |
| `failure.md` | オーケストレーター | 失敗した実行。Red の確認の実行は含めない |
| スクリーンショット | テストを実行した者 | frontend だけ。各ケースの最後の画面を、毎回、フレームワークの既定の形式(Playwright では png)で残す |

`summary.md` と `failure.md` は、テストを実行した委譲先の完了通知を受け、返答を `waits/<id>.md` に書いた直後に、その返答と `results.json` から書く。オーケストレーター自身が実行したときは、実行の直後に自分の実行の出力から書く。

## md の形

`summary.md` と `failure.md` は同じ見出しと項目で書く。`summary.md` に「## 失敗したケース」は置かない。

次の例は形の例である。値は実際の内容に置き換える。

```markdown
# E2E の実行: e2e/frontend/login

- 実行: 20261001-121500-add-login-try1
- 結果: 失敗(パス 3 / 失敗 1 / 全 4)
- フェーズ: test-loop(回帰の実行の委譲)
- コミット: 3f2a9c1
- コマンド: `npx playwright test tests/e2e/login.spec.ts --reporter=json`
- 時間: 12.4 秒

## ケース

| ケース | 結果 | 時間 | 画像 |
| --- | --- | --- | --- |
| LOGIN-01 | パス | 2.1 秒 | `login-01.png` |
| LOGIN-04 | NG | 3.0 秒 | `login-04.png` |

## 失敗したケース

### LOGIN-04

- 期待結果: パスワードを 5 回まちがえると、ロックの案内が出る
- 実際の結果: `expect(locator).toBeVisible()` がタイムアウトした
- 理由: NG。ロックの判定が 5 回目ではなく 6 回目で働く
- 直し方: `src/auth/lock.ts` の回数の比較を直す
```

ケースの結果は、次の 5 つのどれかで書く。

| 結果 | 意味 |
| --- | --- |
| パス | 期待どおりに動いた |
| NG | 実装が期待結果を満たさなかった |
| broken | テストのコードやデータが壊れていて、実装の良否を判定できなかった |
| 環境の失敗 | 環境の不調で実行できなかった。実行し直して判定する |
| Red | test-code の確認の実行で、実装の前にテストが失敗した |

## summary.md と failure.md の使い分け

test-code の Red の確認の実行は、ケースの結果にかかわらず失敗した実行に数えない。実行し直しも含めて、その実行ごとのディレクトリに `failure.md` を置かず `summary.md` を置く。結果の行に、実装の前の失敗を確かめた実行であることを書く。

それ以外の実行は、失敗したケースが 1 件でもあれば `failure.md`、無ければ `summary.md` を置く。

## failure.md の直し方

`failure.md` は、失敗した実行ごと(実行ごとのディレクトリごと)に 1 つ置く。失敗したケースの「直し方」は、その回の失敗を直した委譲の返答から書く。修正の委譲と、実装の委譲が自分の実行の失敗を直したときのその委譲が当たる。修正が複数回に分かれても、各回の `failure.md` には、その回の失敗を直した修正の直し方を書く。

`failure.md` を書く時点で直し方が分からなければ、「直し方」の項目に「未記入」と書く。書き換えは、次の 3 つの時点のどれかで行う。

- 直した委譲の完了通知を受け、返答を `waits/<id>.md` に書いた直後に、返答にある直し方を書く。
- 直した委譲が無いまま失敗が消えたとき(環境の失敗で実行し直して通った、別の変更で直った)は、同じ仕様のディレクトリの次の実行がパスした時点で、「なし」と理由を書く。
- 直す前に run が止まるときは、`codiel-state stop` の前に「なし」と理由を書く。

`/codiel:test` の単独実行は失敗を直さないので、`failure.md` の「直し方」に「なし」と、単独の実行は報告だけを行うことを書く。

## 委譲先が返答に入れる項目

テストを実行した委譲先は、次の項目を返答に入れる。

- ケースごとの結果(上の 5 つの値)と時間
- 失敗したケースごとの、期待結果・実際の結果・理由
- 実行したコマンド

失敗を直した委譲先は、次の項目を返答に入れる。

- 直した実行ごとのディレクトリの名前
- 失敗したケースごとの直し方
