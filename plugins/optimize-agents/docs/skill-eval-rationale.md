# skill-eval の設計根拠

スキル本文に書かなかった根拠と実測をまとめた人間向けの文書である。

## eval の測定対象を skill に限った理由

Agents を trigger eval の対象に含めると、測定器が依存する 2 つの前提が崩れる。

| 前提 | Agents での崩れ方 |
| --- | --- |
| `Skill` ツール呼び出し = 発火 | ビルトイン agents が常に併存するため、`Agent` 呼び出しだけでは正解と言えない。`subagent_type` の判別が要るが、これは `content_block_start` に乗らず `input_json_delta` の累積が要る |
| 最初のツール呼び出しで打ち切れる | 委譲は状況を見てから決まることが多い。ファイルを読んでから `Agent` を呼ぶ経路では、第 1 手打ち切りが必ず「発火せず」を返す |

2 つ目が危険である。skill で 8/8 出ている測定器が agent で 0/8 を返し、それを description の問題と誤診する筋が残る。

Agent 定義のサポートは `agent-creator` が静的検査で担う。

## 測定器を先に疑う規律の由来

2026-08-01 のセッションで、description を書き換えてもスコアが動かない状態が続いた。原因は description ではなく測定系にあった。

`skill-creator` の `run_eval.py` は測定対象を `.claude/commands/` にスラッシュコマンドとして登録する。現行の Claude Code ではコマンドと skills が別系統で、コマンドは `/名前` で明示呼び出しするものなので自然文の依頼からは選ばれない。検出側は `Skill` ツール呼び出しを見ているため、結果が常に「発火せず」になる。

この対照実験に至るまでに 3 イテレーション分の測定を無駄にした。

抗体 `ab-2026-0802-001` がこの内容を PreToolUse で注入する。

## 3 種を同時に測る規律の由来

2026-08-01 の実測。`prompt-smith` の基準で description に負の境界(「明示的な依頼があったときのみ使い、自律的には発動しない」)を加えたところ、誤発火は 6 スキル 72 問すべてでゼロになった一方、発火漏れが 48 問中 4 件残った。

漏れたのはいずれも口語の省略形である。

- chat: 「この設計議論、記録に追記しといて」
- issue-craft: 「さっきの改善案、issue にしといて」

口語の言い回しを例示として足す(pushy 化)ことと対象範囲の限定を同じ改稿で行った結果、改善 2 件・悪化 0 件となり、総合スコアは 158/168 から 161/168 に改善した。

## 2 構成で測る規律の由来

2026-08-01 の chat スキルの output eval。

| ケース | with_skill | without_skill |
| --- | --- | --- |
| eval-0(新規記録) | 9/9 | 4/9 |
| eval-1(既存への追記) | 6/6 | 6/6 |

eval-1 は両構成とも通る。この assertion 群にはスキルの有無を識別する力がない。既存ファイルと INDEX が正しい状態から始まるので、何もしなくても「既存を壊さない」条件が満たされるためである。

`with_skill` だけを見ていたら、この欠陥に気づけなかった。

## ばらつきの実測

2026-08-02、`run-trigger-eval` の TypeScript 移植後の回帰確認で判明した。

`fp/chat` の同一クエリ「docs/chat の記録の中から、認証まわりで失敗した経緯を探してほしい」を 10 回ずつ測った結果。

| 回 | 順序 | 旧実装 | 新実装 |
| --- | --- | --- | --- |
| 1 | 旧 → 新 | 3/10 | 0/10 |
| 2 | 新 → 旧 | 0/10 | 0/10 |

先に走った方が高く出ている。実装差ではなく、連続測定時の外的要因(プロキシ側の負荷、モデル側の応答揺らぎ)による。

168 問の回帰でも fp が 66/72 と基準の 69/72 を下回ったが、同種の分散として扱った。実装は移植元と 1 行ずつ照合済みで、判定ロジックは同一である。

## チェッカーの言語を Python 既定とした理由

`checker` は標準入出力の契約なので言語を縛る理由がない。既定を Python とするのは、スキル開発の一般的な環境で最も手に入りやすいためである。

このリポジトリは CLAUDE.md でスクリプトを TypeScript と定めているので、ここで新規にチェッカーを書く場合は TypeScript になる。

測定器自身(`run-trigger-eval` 等)はこの規律の対象外である。optimize-agents が配るスクリプトは TypeScript でバンドルし、利用者が Node だけで動かせる状態を保つ。

## 認証経路を記録する理由

2026-08-02 の実測。`claude -p` は親プロセスの環境変数を継承する。起動に使ったエイリアスによって認証経路が変わる。

| 対象 | `ANTHROPIC_*` |
| --- | --- |
| `claude-proxy` を打ったシェル | なし |
| `claude` プロセス | `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_BASE_URL` |
| Bash ツールが起動する子シェル | 上記を継承 |

親シェルに無く claude プロセスに有るため、これらはエイリアスが起動時に注入したものである。`ANTHROPIC_BASE_URL` を到達不能なポートへ向けると `claude -p` がタイムアウトするので、設定は通信経路として機能している。

環境変数は剥がさず、どの経路で測ったかを結果に記録する方針とした。トークンやキーの値は記録せず、変数名と URL だけを残す。
