# prompt-smith の対象範囲を references/ へ拡張する設計

2026-08-02 策定。`optimize-agents:prompt-smith` の適用範囲を、指示書の本文だけでなく
`references/` に置かれた文書へ広げる。人間向けの設計文書である。

## 背景

`prompt-smith` は適用範囲を「AI が読み手となる指示書の本文」と定義し、README・設計書・
チュートリアルを対象外としていた。この定義では、SKILL.md から必ず読まれる
`references/orchestration-discipline.md` のような文書の帰属が決まらない。SKILL.md の続きとして
機能するのに、本文ではないため対象に入らない。

拡張の障害は、参照先が AI 専用とは限らない点にあった。人間も読む文書に削る基準を当てると、
人間にとって必要な情報が失われうる。

## 決定

### 判定軸を置き場所へ移す

対象かどうかを、読み手の推測ではなく**置き場所**で決める。

CLAUDE.md の文書配置の運用方針は既に次を定めている。

> AI が必要なときにだけ読む文書(複数のスキル・エージェントで共有する規律、参照断片)は
> `plugins/<plugin>/references/` に置く。

この配置ルールをプラグイン独自の規定として `prompt-smith` に取り込み、`references/` 配下を
「AI の読み物」と定義する。人間が併読する内容であっても、そこに置かれていれば対象とする。

対象は `references/` というディレクトリ名で決まり、どのプラグインの配下かは問わない。
`optimize-agents` 自身の `references/` も、`task-utility` や `basic-design` の
`references/` も、利用者プロジェクトの `references/` も同じく対象とする。
配置ルールを他プラグインへ強制することはしないが、既にそこへ置かれた文書は評価できる。

### 参照関係はたどらない

指示書が参照している文書を再帰的に対象へ加えることはしない。判定は置き場所だけで閉じる。

codiel の Agent 定義は `design.md` / `dev-plan.md` / `docs/ARCHITECTURE.md` / `docs/GOTCHAS.md` を
参照するが、これらはランタイム生成物または利用者プロジェクトの文書である。参照関係で対象を
広げると、これらが巻き込まれる。置き場所で切れば追加の規定なしに対象外へ落ちる。

### 資料型の記述に例外を置く

`references/` 配下の文書は性格が一様ではない。

| 型 | 実例 | 読むと何が起きるか |
| --- | --- | --- |
| 規律型 | `orchestration-discipline.md` / `context-map-guide.md` / `description-guide.md` / `task-utility/references/github-issue-common.md` | エージェントの取る動きが変わる |
| 資料型 | `agent-definition-spec.md`(公式仕様の写し) / `basic-design/*/references/spec-schema.md`(JSON スキーマ) / `nfr-checklist/references/catalog.md`(観点カタログ) | 動きは変わらない。値を引くために開く |

資料型に現行の削る基準をそのまま当てると壊れる。

| 該当箇所 | 当たる基準 | 削ると起きること |
| --- | --- | --- |
| `agent-definition-spec.md` の「出典: https://code.claude.com/docs/...」 | 出典・引用・経緯は削る | 仕様の鮮度を確かめる手がかりが消える |
| `spec-schema.md` のフィールド表 | 重複は削る | 網羅性そのものが価値なのに欠ける |
| `catalog.md` の観点列挙 | 例は 1 つで伝わるなら 2 つ目以降を削る | 巡回漏れが出る |

これは description を対象外とした判断(`description-out-of-scope.md`)と同じ構造である。
description における「重複」や「例示」が一致の幅を作るのと同様、資料型における列挙の重複と
網羅は引く側の正確さを作る。

よって、削る基準に例外を 1 項置く。

### 例外はファイル単位ではなく記述の役割単位で判定する

例外の対象を「資料型のファイル」とはしない。`agent-definition-spec.md` は仕様表(例外対象)と
「仕様は変わる。この文書と実際の挙動が食い違うときは公式ドキュメントを正とする」という規律文
(通常適用)が同じファイルに同居している。ファイル単位の分類では両方を正しく扱えない。

例外がかかるのは重複・例・出典の 3 基準のみである。書き方の基準・残す基準・充足度は
資料型の記述にもそのまま当たる。

判定の単位は見出し配下のブロックとする。表・その表を導入する文・表の直後の補足は 1 ブロックとして
同じ扱いにする。ブロック内で判定が割れるときは、そのブロックが「この文書を開いた者が値を引く先」か
「読んだ者の動きを変える文」かで決める。前者なら例外、後者なら通常適用とする。迷ったブロックは
通常適用に倒す。例外を広げすぎると評価しない範囲が広がるが、狭すぎても指摘が出るだけで
ユーザーが却下できる。

### 判定はモデルが読んで行う

`prompt-smith` はスクリプトを持たない。基準を読んだモデルが判定する散文の規律である。
今回の変更もすべて散文で、`scripts/` 配下への追加・変更はない。
したがって例外の検出は正規表現やマークではなく、上記の判定手順に従うモデルの読解による。

### 評価の母数から除く

例外の当たる記述を冗長度の文の総数に数えると、スキーマ表 60 行のうち指摘 0 件という状態が
評点 5 として出力される。実際には評価していないものが高評価として読まれる。母数から除く。

除くのは比率を出すときの分母だけである。指摘リストの通し番号には影響しない。例外の当たる
記述からは冗長度の指摘が出ないため、番号が飛ぶことはない。

評点表には、除いた範囲を併記する。除いた事実が見えないと、文書の一部しか評価していない評点が
全体の評点として読まれる。表の直後に「例外(引くための記述)として除いた範囲: <見出し名>」を書く。

複数の指示書を一度に評価するときは、文の総数と評点を指示書ごとに出す。例外を除く操作も
指示書ごとに行い、合算しない。

## 変更内容

### skills/prompt-smith/SKILL.md

冒頭の適用範囲(現行 8-10 行目)を差し替える。

変更前:

```markdown
対象は CLAUDE.md・SKILL.md・output style・Agents 定義・メモリなど、AI が読み手となる指示書の本文である。
README・設計書・チュートリアルなど、人間が読み手の文書には適用しない。
frontmatter の description には適用しない。description を書くときは `../../references/description-guide.md` に従う。
```

変更後:

```markdown
対象は CLAUDE.md・SKILL.md・output style・Agents 定義・メモリの本文と、`references/` に置かれた文書である。
`references/` の文書は、人間も読む内容であっても対象とする。
README・設計書・チュートリアル・`docs/` の文書には適用しない。指示書がこれらを参照していても対象は広がらない。
frontmatter の description には適用しない。description を書くときは `../../references/description-guide.md` に従う。
```

「削る基準」節の末尾に 1 項を足す。

```markdown
- 引くために置かれた記述(外部仕様の写し、フィールドやスキーマの定義、網羅を要する列挙)には、
  重複・例・出典の基準を当てない。網羅と原典への追跡可能性がその記述の役割である。
```

「評価」節の評点の数え方に次を足す。

```markdown
引くために置かれた記述は、文の総数に数えない。除くのは分母だけで、指摘の通し番号には影響しない。
評点表の直後に、例外として除いた範囲の見出し名を書く。
表は、ヘッダ行と区切り行を除いた 1 行を 1 と数える。
```

現行の「評価」節は箇条書きの 1 項目と散文の 1 文をそれぞれ 1 と数えると定めるが、表の数え方を
書いていない。資料型は表が主体なので、ここで補う。

「退避」節の退避先から `references/` を外す。

現行は「references/ や設計書など毎回は読み込まれない置き場へ移す」と定めるが、`references/` を
対象範囲へ取り込んだことで、そこへ退避した根拠・経緯が次の評価で再び削る基準に当たる。退避が
循環するため、退避先を `docs/` の設計書に寄せ、`references/` を選ばないことを明示する。

これは適用範囲の拡張に伴う副作用であり、実装時に発見した。

### references/description-guide.md

変更しない。冒頭の 2 行が入れ子の区別を保つ。

```markdown
SKILL.md・Agents 定義の frontmatter にある description の基準である。
`prompt-smith` の削る基準・書き方の基準は、description には当てない。
```

この文書自体は `references/` 配下なので今回の拡張で対象になる(規律型であり当てて問題ない)。
一方この文書が定める description の基準は従来どおり対象外である。

### README.md

`optimize-agents:prompt-smith` の行で、対象を本文だけと書いている箇所を改める。

変更前: `AI が読み手となる指示書(CLAUDE.md・SKILL.md 等)の**本文**の基準と工程。`

変更後: `AI が読み手となる指示書(CLAUDE.md・SKILL.md 等)の**本文**と `references/` 配下の文書の基準と工程。`

### .claude-plugin/plugin.json

`0.11.0-dev` → `0.11.1-dev`。スキル 1 本の適用範囲拡張であり、マイナー相当と判断する。

## description の改稿と測定(2026-08-02)

本文の適用範囲を変えたことで、description が旧定義のままでは `references/` 配下の文書を渡されても
発火しない。`skill-eval` の基準に従って description を改稿し、3 種を各 8 問・2 runs で測った。
`prompt-smith` の eval セットは存在しなかったため新規に作成した。

| 版 | description 長 | substantive | short | fp | 合計 |
| --- | --- | --- | --- | --- | --- |
| 改稿前(旧定義のまま) | 194 字 | 4/8 | 5/8 | 7/8 | 16/24 |
| 1 回目の改稿 | 743 字 | 7/8 | 8/8 | 7/8 | 22/24 |
| 2 回目の改稿 | 853 字 | 1/8 | 1/8 | 8/8 | 10/24 |
| 2 回目を戻す(採用) | 743 字 | 8/8 | 8/8 | 8/8 | **24/24** |

測定環境: `claude-opus-5` / `ANTHROPIC_AUTH_TOKEN` / `http://127.0.0.1:8317`。

### 1 回目の改稿で直したもの

漏れ 7 件のうち 4 件が「ファイル名だけを挙げて評価・整形を頼む」形だった。`orchestration-discipline.md`
にパスを付けた依頼は通り、`agent-definition-spec.md` / `catalog.md` / `github-issue-common.md` を
ファイル名だけで挙げた依頼は落ちた。改稿前の description が対象を「`references/` に置かれた文書」と
場所で書いていたため、パスの見えない依頼が対象外と判断されていた。

「ファイル名だけを挙げて評価・整形・削減を頼まれたときも、それが references/ 配下または上記の
指示書なら使う」を足し、落ちた 4 系統の言い回しをそのまま例示に加えた。あわせて fp で誤発火した
subagent 定義の新規作成を `agent-creator` の担当として名指しした。

### 2 回目の改稿が失敗した理由

22/24 の残り 2 件を直そうとして、冒頭に「指示を正当化する根拠・出典・経緯・重複した言い換え・
判断基準のない修飾を削って指示だけを残し、望ましい動きの言い切りに揃える作業を担う」を足した。
110 字の追加で 22/24 が 10/24 へ落ちた。

`skill-eval` の「substantive が落ちる → 何をするスキルかを具体的に書く」を適用したつもりだったが、
「具体的に」をスキルの内部基準の列挙と解釈したのが誤りだった。依頼文に現れる語彙ではないため
一致に寄与せず、冒頭に置いたことで後続の例示群を相対的に埋もれさせた。

戻したところ 24/24 になり、10 runs で確定した漏れと判断していた CLAUDE.md の 1 件も通った。
`skill-eval` の「1〜2 問の差で description を直さない」を破った結果、24 問中 22 問を壊している。

### fp セットの設計

隣接スキル(`skill-eval` / `agent-creator`)が正解の依頼に加え、今回の拡張で新たに誤発火しうる
2 問を入れた。

- `plugins/optimize-agents/README.md` を読みやすく書き直してほしい(references 配下ではない)
- `references/description-guide.md` が定めている description の基準そのものを見直したい
  (ファイルは対象だが、そこに書かれた基準の見直しは `skill-eval` の担当)

後者は 2 runs で 1 度誤発火したが、10 runs では 0/10 だった。ばらつきの範囲である。

## スコープ外

- 既存 `references/` 6 ファイルへの遡及適用。基準の改定と実際の改稿は分ける。適用するかは
  基準確定後の別判断とする。
- 他プラグインへの配置ルールの強制。`basic-design` の `spec-schema.md` 等は現在の場所のままで、
  例外規定でカバーされる。
- `assets/` 配下(`context-map-template.md` / `gpt-*.template.md`)の扱い。テンプレートは
  埋めるための雛形であり、今回の対象に含めない。

## 不採用案

### 参照先を明示指定する方式

SKILL.md 側で「この参照先も対象」と書かれたものだけを対象にする案。判断をスキル作者へ委ねる
ため誤判定は減るが、既存の全 SKILL.md に指定を書き足す必要があり、書き忘れた参照先が
静かに対象外へ落ちる。置き場所による判定は書き足しなしで既存の全 `references/` を捕捉する。

### 文書側にマークを持たせる方式

各 references 文書の冒頭に対象/対象外のマークを置き、`prompt-smith` がそれを見て判定する案。
機械的に確実だが、既存文書の一括改修が要るうえ、他プロジェクトへ配布した先の `references/` では
マークが無いため機能しない。

### 資料型を assets/ へ移す方式

references/ を規律型だけにし、資料型は `assets/` へ移す案。判定が完全に置き場所だけで済む。
既存 6 ファイルの移動と CLAUDE.md の文書配置方針の改訂(人間確認必須)を伴うため見送った。
`assets/` は現状テンプレート置き場として使われており、参照資料と混在させると別の曖昧さを生む。
