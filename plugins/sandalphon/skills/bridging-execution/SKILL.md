# Bridging Execution — 起票と実行経路の決定

## 目的

承認済みの intent 文書を issue という外部化された形にして実行系へ渡す。渡さないと決めた場合も、
次に何が起きるかをユーザーと確定させてこのフェーズを閉じる。

## 共通規律

`../../references/sandalphon-common.md` を読み、これに従う。
intent 文書と intent-issue の書式の正本は `../../references/intent-format.md`、
外部スキルへの委譲に使う呼び出し契約の正本は `../../references/handoff-contract.md` である。
書式と契約をこの本文から推測せず、正本を読む。

## 起動条件

ゲート 1 を通過し `status: approved` で保存された intent 文書があるときにだけ実行する。
ドラフトのまま、または保存前の intent でこのフェーズに入らない。

入力は intent 文書のパスと、前フェーズが取得済みの環境 JSON である。環境 JSON を持っていないときだけ、
次を実行して取り直す。

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/check-intent-env.mjs"
```

## 手順

### 1. 起票可否と委譲可否を判定する

| 判定 | 見るもの | 扱い |
| --- | --- | --- |
| 起票できるか | `isGitRepo` / `repoSlug` / `ghInstalled` / `ghAuthenticated` | どれか 1 つでも欠ければ、起票を伴う選択肢を出さない |
| 委譲できるか | `/codiel:run` が自分の利用可能コマンド一覧にあるか、かつ `codielReady` | 両方を満たすときだけ委譲を選択肢に出す |
| Raguel MCP を確認できるか | 自分の利用可能ツール一覧に `mcp__raguel__` で始まるツールがあるか | 無くても選択肢は消さず、手順 2 の注記を添える |

- **プラグインと MCP の可用性はファイルシステムの事実ではない。** 環境 JSON では判定できないため、
  自分の利用可能なコマンド・スキル・ツールの一覧を見て判断する。
- **起票権限は事前検出しない。** `gh auth status` は認証の有無しか示さず、対象リポジトリへの
  issue 作成権限までは保証しない。403 等は起票時に判明したら手順 7 へ合流する。
- 畳んだ経路は必ず 1 行で理由を報告する(共通規律)。無言で選択肢を減らさない。

**委譲を選択肢に出すのは `codielReady` が true のときだけである。** false のときは選択肢に出さず、
1 行の案内に留める(選ばせても必ず失敗するため)。案内の文言は共通規律の「畳む経路の対応表」に従う。

- **`domainsReadable: false` の案内先は、`/metatron:init` が自分の利用可能コマンドにあるかで分岐する。**
  あれば `/metatron:init`(推奨)で ARCHITECTURE を整備するよう案内し、無ければ `/codiel:init` が
  ドメインマップだけの最小 ARCHITECTURE を生成できると案内する。
- `/codiel:run` が利用可能コマンド一覧に無いときは、案内も出さず委譲に言及しない。

### 2. 経路を 1 回の質問で決める

**質問は 1 回にまとめる。** 「起票するか」と「誰が実行するか」を別々に聞かない。選択肢は次の 4 つで、
手順 1 で畳んだものを除いて提示する。

- (a) issue を起票して `/codiel:run` へ渡す
- (b) 起票して sandalphon が実行する
- (c) 起票せず sandalphon が実行する
- (d) intent 文書だけ残して終了する

**質問文に品質差の 1 行を必ず添える。** これを書かないと、軽量経路を選んだ結果に重い経路の品質を
期待させてしまう。

```
(a) は設計・レビュー・PR まで含む重い経路、(b)(c) はテストと実装だけの軽量経路でレビューは付かない。
```

`mcp__raguel__` で始まるツールを確認できなかったときは、(a) を消さずに次の注記を添える。
引き渡し先は新しいセッションであり、そちらで接続済みの可能性があるため消さない。

```
※ /codiel:run は Raguel MCP 接続が無いと開始しない。現在このセッションからは接続を確認できていない。
```

規律:

- **issue 起票の提案はここで 1 回だけ行う。** 断られたら以降のフェーズで再提案しない。
- **(a) を選ぶなら起票は必須である。** `/codiel:run` は issue 番号を引数に取るため、起票しない (a) は
  成立しない。起票できない環境では (a) を選択肢に出さない。
- (b) と (c) の違いは記録を残すかどうかだけであり、実行内容は同じである。

### 3. intent-issue を組み立てる

`../../references/intent-format.md` の v1 仕様に従う。要点だけ再掲する。

- 1 行目にマーカー `<!-- intent:v1 -->` を置き、末尾に `<!-- intent-source: <リポジトリルートからの相対パス> -->` を置く。
- frontmatter は issue 本文へ転記しない。`## ASIS` 以降の見出しと本文をそのまま貼る。
- タイトルは intent 文書の `# intent: <...>` から `intent: ` の接頭辞を外したもの。
- **要約・整形・見出しの並べ替えをしない。** 転記は機械的作業であり、ここで加工すると
  ユーザーが承認した内容と issue の内容がずれる。

### 4. 起票する

**起票は外部公開行為であり、必ず承認を取る。** 承認はデグラデーションの対象にしない。

| 状況 | 経路 |
| --- | --- |
| `issue-craft` が自分の利用可能スキル一覧にある | `../../references/handoff-contract.md` の固定開始句で起動し、`title` / `body` / `labels` を渡す |
| 無い | 自前で `gh issue create --title <title> --body-file <一時ファイル>` を実行する |

- **どちらの経路でも、起票前の全文提示と明示承認を省略しない。** 委譲先が承認を取るからといって
  省かない。
- 本文は必ず一時ファイルに書き、`--body-file` で渡す。
- 起票に失敗したら生のエラーを報告して停止する。リトライも代替手段への切り替えもしない。
  そのうえで手順 7 へ進む。

### 5. intent 文書を更新する

起票が成功したら、Edit ツールで frontmatter の 2 キーだけを書き換える。

- `status` を `issued` にする。
- `issue` に issue の番号または URL を入れる。

本文と他のキーは書き換えない。環境検出スクリプトは intent 文書を読み取るだけで書き込まないため、
この更新はこのスキルの責務である。

### 6. 引き渡す

| 選んだ経路 | 行うこと |
| --- | --- |
| (a) | `/codiel:run <番号>` を提示してセッションを終える |
| (b)(c) | 実行フェーズのスキルへ進む |
| (d) | intent 文書の保存先を絶対パスで示し、後から `/sandalphon:run <intent 文書のパス>` で再開できる旨を添えて終える |

(a) の引き渡しには、**新しいセッションでの実行を推奨する 1 行を含める。**
intent は issue として外部化済みで、`/codiel:run` は issue 番号だけを入力に取るため、
セッションを跨いでも情報は失われない。

```
次は新しいセッションで /codiel:run 57 を実行することを推奨する(本セッションの文脈は issue #57 に外部化済み)。
```

**引き渡しはコマンド文字列の提示で行う。委譲先の内部スキルを Skill ツールで直接起動しない。**
理由は 3 つある。

1. 別プラグインの内部スキル名に結合すると、委譲先のリファクタで壊れる。コマンド名は利用者向けの
   公開インタフェースであり、内部スキル名より安定している。
2. `/codiel:run` は長く、独自のゲートを 10 個以上持つ。このセッションに抱え込むと、ヒアリング履歴と
   ASIS 探索の読み込み結果の上に全フェーズが積み上がる。
3. `/codiel:run` は未初期化時に案内して止まるフェイルクローズド設計であり、その入口を迂回すべきでない。

### 7. 起票できなかったとき

**黙って軽量経路へ落とさない。** ユーザーは委譲先の品質を期待して (a) を選んでいる。
理由を提示し、次の 3 つから選び直させる。

- (a) 環境を直して `/sandalphon:run <intent 文書のパス>` で再実行する
- (b) 軽量な自前実行へフォールバックする
- (c) intent 文書だけ残して終了する

(b) を選んだ場合、**同一セッションではゲート 1 を再実施せず、実行フェーズへ直進する。**
intent の内容は変わっておらず、再承認は同じ文書を二度承認させるだけになる。

## Red Flags(合理化への反論)

| 思考 | 現実 |
| --- | --- |
| 「起票は断られたが、実行の直前にもう一度勧めれば気が変わるかもしれない」 | 同じ提案の反復は情報を増やさず、体験だけを損ねる。判断材料が変わっていないのに再提示するのは、ユーザーの決定を尊重していないだけである。 |
| 「Raguel MCP が見えないので委譲は失敗する。選択肢から消しておくのが親切だ」 | 見えていないのは**このセッションから**であり、引き渡し先は新しいセッションである。消すと、実際には使える経路をユーザーが選べなくなる。注記を添えて残すのが正しい。 |
| 「委譲先のスキルを Skill ツールで直接起動すれば、ユーザーがコマンドを打つ手間が省ける」 | 内部スキル名への結合は委譲先のリファクタで静かに壊れ、フェイルクローズドな入口も迂回される。加えて 2 フェーズ分の文脈が同一セッションに積み上がる。手間 1 回と引き換えにするものが大きすぎる。 |
| 「起票に失敗したが、経路は決まっているのでそのまま自前実行を始めればよい」 | ユーザーが選んだのは「設計・レビュー・PR まで含む経路」である。黙って軽量経路に落とすと、レビューの無い成果物を重い経路の品質だと信じたまま受け取ることになる。 |
| 「本文に誤字がある。直してから起票したほうが良い issue になる」 | 起票する本文は全文提示して承認を得たものである。承認後の加工は、承認された内容と公開された内容をずらす。機械可読マーカーや見出し規約を善意の整形が壊すこともある。 |
| 「起票の承認は取ったので、経路の質問はまとめずに順に聞けばよい」 | 経路の質問を分けると、ユーザーは「起票するか」を実行主体が分からないまま答えることになる。2 つの軸は 1 回の質問で同時に見せたときだけ、比較して選べる。 |
