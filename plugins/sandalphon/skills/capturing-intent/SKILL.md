# intent の聞き取りと確定

## 目的

TOBE を聞き取り、intent に関係する範囲の ASIS と突き合わせ、分岐を合意したうえで intent 文書に固定する。

ASIS はユーザーに聞かず自分で読む。ユーザーに聞くのは、読んでも分からないこと(何を達成したいか、どうなったら完了か)だけである。

## 共通規律

- フェーズ間で共有する規律は `../../references/sandalphon-common.md` に従う。
- intent 文書の書式は `../../references/intent-format.md` に従う。書式の正本はそちらであり、この文書は手順だけを持つ。
- ディスカッションの言語はユーザーの使用言語に従う。intent 文書の言語は手順 6 で別に確認する。

## 手順

- [ ] 1. 環境検出
- [ ] 2. 既存 intent 文書との重複確認
- [ ] 3. TOBE のヒアリング
- [ ] 4. ASIS 探索
- [ ] 5. 分岐の提示と合意
- [ ] 6. ドラフトの全文提示
- [ ] 7. ゲート 1
- [ ] 8. 保存

## 1. 環境検出

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/check-intent-env.mjs"
```

- 最初に 1 回だけ実行する。以降のフェーズも同じ出力を使うため、再実行しない。
- 出力はファイルシステムの事実だけであり、判断は含まれない。畳む経路の判断はこのスキルが行う。
- ARCHITECTURE / GOTCHAS のパスは `projectDocs` と `contextDocs` の解決結果を使う。固定パスを前提にしない。
- `configWarnings` が空でないときは、その項目のパス設定が拒否されて既定値に落ちている。読めた文書だけで進み、警告の内容を完了報告に残す。
- 起動時の引数が既存 intent 文書のパスのときは、その文書を読み込み、記載済みの内容を確定済みとして手順 2 を飛ばして手順 3 から再開する。
- 引数が空のときは手順 3 の「何を達成したいか」から始める。

## 2. 既存 intent 文書との重複確認

- `existingIntents` のタイトル一覧を読み、今回の TOBE と重なるものがあるかを判断する。判断は意味で行い、slug の文字列一致だけで決めない。
- 重なるものがあれば「既存を更新するか、新規に起こすか」をユーザーに確認する。確認せずどちらかに決めない。
- `existingIntents` が空、または重なりが無いときはそのまま進む。一覧の提示だけを目的に会話を 1 往復増やさない。

## 3. TOBE のヒアリング

埋まるべき観点は次の 4 つである。

| 観点 | 何を得るか |
| --- | --- |
| 何を達成したいか | TOBE の中核 |
| 今それができない理由・困っている具体的な場面 | ASIS 側の課題 |
| どうなったら「できた」と言えるか | 受け入れ基準の種 |
| 今回やらないこと | 非スコープの種 |

- **不足している観点だけを 1 問ずつ聞く。** 起動時の引数と会話に既に現れている観点は聞き直さない。4 問を並べて一度に投げない。
- 選択式で聞ける場面は AskUserQuestion を使う。自由記述でしか答えられない問いだけを文章で聞く。
- ASIS 側の事実は聞かずに手順 4 で読む。「今はどう実装されているか」を質問にしない。
- 聞いても埋まらなかった観点は推測で埋めず、`## 未確定事項` に残す。

## 4. ASIS 探索

### 4-1. 既存文書を先に読む

優先順は **ARCHITECTURE → `CLAUDE.md` → GOTCHAS → `README.md`**。人間が書いた要約であり、コードを読むより桁で安い。

- パスは手順 1 の解決結果を使う。固定パスで開かない。
- **注入済みの内容は読み直さない。** セッション開始時に ARCHITECTURE や GOTCHAS 要約がコンテキストへ注入されている環境がある。既にコンテキストにある内容を Read で読み直すのは純粋な重複である。判定は「コンテキストに既にあるか」を見るだけでよく、どのプラグインが注入したかを調べる必要はない。
- **注入は縮退しうる。** 注入は文字数上限に収めるため、目次と要約に縮退することがある。縮退していて、かつ全文が判断に必要なら `contextDocs` のパスを Read する。「注入されていたから全部見た」と扱わない。
- **注入はサブエージェントに継承されない。** 探索を委譲するときは、解決済みの絶対パスを渡して委譲先に読ませる。「自分が読んだから委譲先も知っている」は成立しない。

### 4-2. 文書で埋まらない部分だけコードを読む

- 探索範囲は TOBE に登場する語から辿れる範囲に限定する。プロジェクト全体のスナップショットを作らない。
- Serena が利用可能なら優先して使う(`get_symbols_overview` / `find_symbol` / `find_referencing_symbols`)。利用できなければ Grep / Glob / Read で代替する。対象プロジェクトに Serena が導入されている前提を置かない。**有無で探索の深さは変えず、手段だけを切り替える。**
- `projectDocs.domainsReadable` が `true` で、TOBE が特定のドメインに閉じると判断できるときは、そのドメインの glob に絞ってよい。範囲の決定が推測でなくプロジェクト自身の宣言に基づく。ドメインマップが無い環境でも探索は成立するため、これは強化であって前提ではない。

### 4-3. 打ち切りと空振り

- **「受け入れ基準を書ける」かつ「実装方針の選択肢を 2 つ挙げられる」状態になったら止める。** それ以上は設計フェーズの仕事である。
- 対象が見つからないときは推測で ASIS を書かない。`## ASIS` に「該当する既存実装は見つからなかった(新規追加とみなす)」と明記する。

## 5. 分岐の提示と合意

- 実装方針が割れる論点は、選択肢を 2 つ以上と各々の帰結を示して合意を取る。自分で決めて先へ進まない。
- 合意した論点は `## 合意済み事項` へ `<論点>: <採用した選択肢>(理由: <...>)` の形で残す。ここに残した分岐は後続フェーズが再質問しないため、選択肢だけでなく理由まで書く。
- 決着しなかった論点は `## 未確定事項` へ残す。

## 6. ドラフトの全文提示

- ドラフトを書く前に、**intent 文書の言語と issue 本文の言語を 1 回で確認する。** リポジトリの既存文書から推定した言語を推奨として添える。両者を別々に聞かない。両者が食い違うと、issue への転記に翻訳という加工が入り、機械的に転記するという前提が崩れる。
- 書式は `../../references/intent-format.md` に従う。見出しの名称と順序を変えない。
- **提示はメッセージ本文で行う。** 先にファイルへ書いて「読んで確認してほしい」と依頼しない。保存は承認後である。
- `## 受け入れ基準` は機械的に YES/NO を判定できる文にする。「使いやすくなる」のような人が雰囲気で判定する文を書かない。
- `## 実装方針` も承認対象に含める。設計書ではなく、どの層をどう変えるかの方針として書く。
- slug は TOBE を表す英小文字ケバブケースにする。日本語のプロジェクトでも slug は英字にする。

## 7. ゲート 1

- 全文を提示したうえで、保存してよいかの明示的な承認を得る。
- 差し戻されたら手順 3 へ戻る。指摘された観点を聞き直してからドラフトを作り直す。指摘部分だけを直して再提示することを繰り返さない。

## 8. 保存

- 保存先は `repoRoot` 基準の `docs/intents/YYYY-MM-DD-<slug>.md`。ARCHITECTURE の解決に使う `docRoot` ではなく `repoRoot` を基準にする。両者が別ディレクトリを指すのは正常な状態である。
- `docs/intents/` が無ければ保存時に作る。ゲート 1 の前にディレクトリを作らない。
- 同日に同一 slug が既にあるときは `-2` を付す。既存ファイルを上書きしない。
- `isGitRepo: false` のときは基準にできる `repoRoot` が無い。カレントディレクトリ基準の `docs/intents/` を提案し、**保存前に絶対パスを提示して確認を取る。**
- frontmatter は `intent` / `slug` / `created` / `status` / `issue` の 5 キー平坦にする。`status` は `approved`、`issue` は空にする。
- 保存に失敗したときは、intent 文書の全文をセッション内に提示したうえで保存先をユーザーに確認する。文書を失わせない。
- 保存したパスを報告する。コミットはしない。「作成した(未コミット)」と明示する。
- 畳んだ経路があるときは、理由と使えるようにする方法を 1 行で報告する(例: `gh が未認証のため issue 起票は行わなかった(gh auth login で有効になる)`)。無言で選択肢を減らさない。
- 報告を終えたら `bridging-execution` へ進む。

<HARD-GATE>
- **承認なしに intent 文書を保存しない。** ドラフトへの相槌や部分的な感想は承認ではない。承認はユーザーの明示的な返答だけである。
- **ドラフトを全文提示せずに承認を求めない。** 要約・抜粋・差分の提示に置き換えない。
- **ASIS を推測で書かない。** 読んで確かめられなかったことは書かない。
- **ヒアリングで埋まらなかった観点を推測で埋めない。** `## 未確定事項` に残す。
- **ゲート 1 の前に `docs/intents/` を作らない。**
</HARD-GATE>
