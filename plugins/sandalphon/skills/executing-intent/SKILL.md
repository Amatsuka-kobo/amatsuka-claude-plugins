# intent の自前実行

## 概要

承認済みの intent 文書を入力に、受け入れ基準を満たす実装を作業ツリーへ残すまでを担う。
レビューフェーズもゲートも持たない軽量経路であり、承認ゲートはテスト仕様の 1 点だけである。

- フェーズ間で共有する規律は `../../references/sandalphon-common.md` に従う。
- intent 文書の frontmatter と各セクションの書式は `../../references/intent-format.md` に従う。
  `status` を書き換えるときはこの文書を読む。書式を記憶で書かない。

## チェックリスト

1. **併存チェック**: 環境 JSON の `codielHarness.runDirs` を読む。空なら 2 へ。
   空でなければ run ディレクトリ名の一覧をそのまま提示し、**未完了の run があるかをユーザーに確認する**。
   ある場合は本フェーズを開始せず、「その run を完了させる」「この intent も外部ハーネス側で扱う」の
   2 つを案内して停止する。
2. **テスト基盤の確認**: 環境 JSON の `testRunner` を読む。`evidence` と推定した実行コマンドを
   1 行で示す。訂正があればそれに従う。`detected: false` のときは「テスト基盤が無い場合」に従う。
3. **テスト仕様の作成**: intent 文書の `## 受け入れ基準` を 1 対 1 でテストケースへ写像する。
   基準 1 件に対してケースが 0 件になってはならない。各ケースに「対象」「前提」「操作」「期待結果」を
   書く。**期待結果は受け入れ基準の文言をそのまま使う**(言い換えない)。
   出力先は、自動テストなら実際のテストファイル(未実装のまま Red になる状態)、手動検証手順なら
   intent 文書と同じディレクトリの `YYYY-MM-DD-<slug>-verify.md`。
4. **ゲート 2**: 下記 3 点をまとめて提示し、一括で承認を得る。差し戻されたら 3 へ戻る。
5. **TDD 実装**: 受け入れ基準 1 件を 1 サイクルとして Red → Green → Refactor を回す。
6. **ドキュメント更新**: 下記の判定基準に該当する文書だけを更新する。
7. **結果報告**: 下記の項目を報告し、intent 文書の `status` を `done` に更新する。

## ゲート 2: テスト仕様の承認

次の 3 点を 1 回でまとめて提示し、一括で承認を得る。分割して 3 回聞かない。

1. テストケースの一覧(**全文**。件数や要約に置き換えない)
2. テスト実行コマンド(`testRunner.command` の推定値と `evidence`)
3. 作業ブランチ

**承認後は完了までユーザーへ問いかけない。** ただし判断が必要な状況に至ったときは、勝手に決めず
**作業を止めて報告する**。問いかけないことと勝手に決めることは別である。

## 作業ブランチ

- git リポジトリでは**既定でブランチを切る**。名前は intent の slug を流用した `sandalphon/<slug>`。
- 現行ブランチのまま作業するのは、ユーザーがゲート 2 の承認の場で明示的にそれを選んだときだけとする。
- 対象プロジェクトにブランチ運用の規約があるときは、承認の場で選び直させる。
- git 管理下でないときはブランチを作らず、その旨を承認の場で 1 行示す。

## テスト基盤がある場合

既存の基盤に**合わせる**。次を行わない。

- テストランナーの変更・追加
- テストディレクトリ構成の変更
- アサーションライブラリの追加

既存テストファイルを 1 つ読み、命名・配置・記述スタイルを揃えてから書き始める。

## テスト基盤が無い場合

**テスト基盤を勝手に導入しない。** intent の `## TOBE` に「テストを整備する」旨が明記されている
場合のみ導入し、その場合は導入自体が実装対象になる。明記が無ければ次のとおり縮退する。

- テスト仕様の代わりに**手動検証手順**を作る。各項目は「何を実行し、何が見えれば OK か」を
  ユーザーが再現できる粒度で書く(コマンド・入力・期待出力)。
- ゲート 2 の承認対象はこの手動検証手順になる。
- TDD の代わりに「実装 → 手動検証手順を自分で実行 → 結果を記録」を受け入れ基準単位で回す。
- 自分で実行できない項目(ブラウザ操作、外部サービス連携など)はその旨を記し、報告でユーザーに
  実行を依頼する。
- 報告に**「このプロジェクトには自動テスト基盤が無いため手動検証で確認した」と明記する**。

## TDD の回し方

- 受け入れ基準 1 件を 1 サイクルとし、Red → Green → Refactor を回す。全基準が Green になるまで続ける。
- 既存テストも毎サイクル走らせる。回帰が出たら**そのサイクル内で直す**。次のサイクルへ持ち越さない。
- 実装がテスト仕様と食い違う必要が出たときは、**テスト仕様を先に直し**、その差分を最終報告に含める。

## 自律実行の安全境界

ゲート 2 の承認は、リポジトリに対する任意の操作の白紙委任ではない。次は承認後であっても
自律実行せず、その場で確認する。確認は 1 操作 1 回、何を・なぜ行うかを 2 行以内で示す。

| 操作 | 具体例 |
| --- | --- |
| secrets への接触 | `.env` / `.env.*` / 認証情報を含む設定ファイルの読み取り・作成・変更 |
| DB マイグレーション | マイグレーションファイルの追加・適用、スキーマ変更コマンドの実行 |
| 破壊的操作 | ファイル・ディレクトリの削除、`git reset --hard` / `git clean`、既存ブランチの強制更新、外部サービスへの書き込み |
| 依存パッケージの追加 | `package.json` 等への依存追加、ロックファイルの更新 |

判断基準は「**その操作は作業ブランチを捨てれば元に戻るか**」である。戻るなら自律実行してよく、
戻らないなら確認する。表に無い操作もこの 1 本で判断する。

## ドキュメント更新の判定

**「今回の変更で記述が事実と食い違うようになった文書」だけを更新する。** 該当が無ければ
「更新対象なし」と報告する。文書を増やすこと自体を目的にしない。

## 結果報告

次の 5 点を報告する。

1. 受け入れ基準ごとの達成状況(達成 / 未達成 / 仕様変更)
2. 変更したファイルの一覧
3. テスト実行結果(手動検証の場合はその結果と、自分で実行できなかった項目)
4. 更新したドキュメント(無ければ「更新対象なし」)
5. 残った未確定事項

報告に合わせて intent 文書の `status` を `done` に更新する。

**コミットはしない。** 変更は作業ツリーに残し、報告でその旨を明示する。

<HARD-GATE>
- 未完了の run があるとユーザーが答えた状態で本フェーズを開始しない。
- ゲート 2 の承認を得ずにプロダクトコードへ書き込まない。
- 受け入れ基準に対応するテストケースが 0 件のまま実装へ進まない。
- テストを skip 化・削除して Green にしない。テスト仕様の変更が要るなら仕様を先に直して報告する。
- 安全境界の 4 操作を、承認後であっても無確認で実行しない。
- 変更をコミットしない。
</HARD-GATE>

## Red Flags(合理化への反論)

| 思考 | 現実 |
|---|---|
| 「run ディレクトリの state を読めば未完了かどうか分かる」 | 外部ハーネスの state 形式に結合すると、その内部変更で静かに誤判定するようになる。一覧という事実の提示までが本スキルの責務で、判断はユーザーと当のハーネスが持つ。 |
| 「run は残っているが古そうなので進めてよい」 | 同じ作業ツリーを 2 つのフローが同時に触ると、ハーネスの state と実際の変更が食い違う。古さは完了の証拠ではない。 |
| 「期待結果は受け入れ基準を要約したほうが読みやすい」 | 言い換えた時点で、承認された文言と検証される内容がずれる。読みやすさは「対象」「前提」「操作」の側で作る。 |
| 「ゲート 2 を通ったのだから、依存を 1 つ足すくらいは含意されている」 | 承認されたのはテスト仕様であって供給網とライセンスの意思決定ではない。作業ブランチを捨てても戻らないものは承認の範囲外。 |
| 「テスト基盤が無いのでこの機会に vitest を入れておく」 | 基盤の導入は依存追加・CI 設定・既存コードへの波及を伴う独立した意思決定であり、intent に無い変更を持ち込むことになる。intent に明記が無ければ手動検証へ縮退する。 |
| 「テストがおかしいので直しながら実装を進める」 | 仕様を黙って動かすと、承認された完了の定義が消える。テスト仕様を先に直し、その差分を最終報告に載せる。 |
| 「承認後は問いかけない規律なので、迷ったところは自分で決めてよい」 | 問いかけないのは設計判断についてであり、判断材料が足りない状況では止めて報告する。勝手に決めることは自律実行ではない。 |
| 「作業ブランチを切るとリポジトリの規約に反するかもしれない」 | 既定はブランチを切る。規約があるかどうかはユーザーがゲート 2 の承認の場で選び直す。無言で現行ブランチへ書き込まない。 |
| 「ドキュメントも一通り整えておいたほうが親切」 | 更新対象は今回の変更で事実と食い違うようになった記述だけである。無関係な文書を触ると、レビューの無い経路で差分だけが膨らむ。 |
| 「完了したのでコミットまで済ませておく」 | 対象リポジトリのコミット運用は本スキルから見えない。作業ツリーに残して報告するところまでが職務。 |
