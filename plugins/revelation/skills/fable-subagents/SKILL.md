# Fable Subagents — サブエージェントの使い方

これは Fable 5 が実際にサブエージェントを運用するときの内部規律を、明示的な手順として書き下したものだ。

原則は一つに要約できる:

> **サブエージェントは「手足」ではなく「使者」だ。**
> 君の代わりに遠くへ行き、**結論だけ**を持ち帰らせる。丸投げの装置でも、自分の仕事の分身でもない。
> 使者が役に立つかどうかは、送り出すときの**指示文の質**でほぼ決まる。

---

## 0. 委任判断 — 投げるべきか、自分でやるべきか

起動する前に10秒考える。委任には固定コストがある(起動、文脈ゼロからの立ち上がり、結果の受け渡し)。そのコストを上回るときだけ投げる。

### 投げる場面

- **広い探索。** 複数ディレクトリ・命名規則が不明・「どこにあるか」から分からない検索。ファイルダンプで君のコンテキストを埋める代わりに、結論だけ受け取る。
- **独立した作業が複数ある。** 互いに依存しない調査・検証は、並列に投げれば壁時計時間が縮む。
- **「読む量は多いが、要るのは要約」な仕事。** 複数ファイルを横断して仕様を把握する、ログを漁って原因候補を絞る、など。
- **専用エージェントがある仕事。** 利用可能なエージェント一覧に合致するタイプ(Explore、Plan、その他プロジェクト定義のもの)があるなら、汎用より先にそれを使う。

### 投げない場面

- **単発の事実確認。** ファイル名・シンボル名・設定値が分かっていて grep や Read で10秒で引けるもの。使者を仕立てるより自分で歩いた方が速い。
- **君の会話文脈が濃く必要な仕事。** サブエージェントは会話を見ていない。文脈を全部指示文に書き写すコストが作業自体より大きいなら、自分でやる。
- **逐次的にしか進まない仕事。** 各ステップの結果を見て次を決める作業は、分割しても直列のまま。委任の旨味がない。

### 鉄則:二重作業をするな

**投げた検索を自分でも走らせるな。** 委任した瞬間、その仕事は使者のものだ。待っている間にやるのは**別の**独立した作業。同じ調査を自分でもやるのは、コストを倍払って結果を1つ得る行為だ。

## 1. エージェントの選択 — 権限は最小に

- **読むだけの仕事に、書けるエージェントを使うな。** 探索なら Explore(読み取り専用)。設計なら Plan。読み取り専用のエージェントは事故を構造的に起こせない。
- 汎用エージェント(general-purpose / claude)は「編集・実行まで任せる」ときだけ。
- **モデルの階層は仕事の質で選ぶ。** 調査・分析・設計など考える仕事は上位モデルに、機械的・定型的な作業は軽いモデルに投げる。**迷ったら model を指定せず継承する** — セッションのモデルがほぼ常に正しい選択で、根拠なき指定は事故のもと。
- 複数のエージェントが**同じファイルを並列に触る**構図になったら、それは設計ミスの兆候。直列化するか、worktree 分離を使うか、そもそも1エージェントにまとめる。

## 2. 指示文 — ここで9割決まる

サブエージェントは**この会話を一切見ていない**。君が当然と思っている文脈(ユーザーの依頼、これまでの発見、試して駄目だったこと)は、書かなければ存在しない。

**「会話を見ていない新入りへの引き継ぎメモ」として書け。** 含めるべき要素:

1. **背景を1〜2文。** なぜこの調査/作業が必要か。目的を知らない使者は、境界事例で必ず間違った判断をする。
2. **具体的な出発点。** 分かっているファイルパス・シンボル名・エラーメッセージ・再現手順は全部渡す。「認証まわりを調べて」は最悪の指示。「`src/auth/` 配下と、`validateToken` の呼び出し元を調べて」が指示。
3. **完了条件。** 何が分かれば/できれば終わりか。オープンエンドな指示は、オープンエンドな長さの作業と曖昧な報告を返してくる。
4. **返答フォーマットの指定。** これが最重要。君が受け取るのは**エージェントの最後のメッセージだけ**だ。欲しい形を明示的に指定する:
   - ❌ 「調べて報告して」
   - ✅ 「`ファイルパス:行番号` のリストと、各箇所の1行説明で返せ。該当なしなら『なし』と、探した場所を列挙して返せ」
5. **やってはいけないことの明示。** 「ファイルを編集するな」「コミットするな」「調査だけで修正はするな」。書かなければ、気を利かせたつもりの使者が勝手に直す。
6. **既に試して駄目だったこと。** 書かないと、使者は君の失敗をゼロから再演する。

### 一使者一任務

1つのエージェントに「Aを調べて、ついでにBも直して、Cも確認して」と積むな。任務が濁ると報告も濁る。独立した任務なら、独立したエージェントを並列に出す方が速くて正確。

## 3. 並列化 — 独立なら同時に、依存なら順に

- **互いに依存しない複数のエージェントは、1つのメッセージで同時に起動する。** 1つずつ起動して待つのは、並列化できる仕事を直列にやる無駄。
- 依存がある(Aの結果がBの指示文に要る)なら、素直に直列。Aの結果を**見てから**Bの指示を書く。
- 結果が出るまで次に進めないなら同期実行(バックグラウンドにしない)。他の作業を進められるならバックグラウンドで走らせ、通知を待つ。**バックグラウンドに投げた後、ポーリングでそわそわするな** — 完了すれば知らされる。

## 4. 結果の受け取り — 使者の報告を疑え

サブエージェントの報告は**主張であって事実ではない**。fable-method の検証規律はここにも適用される。

1. **「見つからなかった」を鵜呑みにするな。** 不在の主張は最も検証が必要な主張だ。使者の探し方が悪かっただけかもしれない。重要な判断が「なし」の上に乗るなら、別の切り口(別の命名・別のディレクトリ・grep パターン変更)で1回だけ自分で裏を取るか、観点を変えた2人目を出す。
2. **「修正した/動いた」も現物を見る。** エージェントが変更したと言うファイルは、要点だけでも diff を見る。検証したと言うなら、何をどう実行したかが報告に含まれているか確認する。含まれていなければ検証されていないとみなす。
3. **報告はユーザーに届いていない。** エージェントの最終メッセージを受け取るのは君だけだ。重要な発見は、君の最終報告に**君の言葉で**書き直して伝える。エージェントの出力を生のまま貼り付けるな — 取捨選択と統合が君の仕事。
4. **続きは同じ使者に。** 一度出したエージェントに追加の質問や続きの作業があるなら、新しいエージェントを起動せず SendMessage で**同じエージェント**に送る。彼はすでに文脈を積んでいる。新規起動は毎回ゼロからの立ち上がりだ。

## 5. コンテキスト経済 — そもそも何のために委任するのか

サブエージェントの最大の価値は、**君自身のコンテキストを守る**ことだ。君のコンテキストは有限で、ファイルダンプで埋まった分だけ、後半の判断力が落ちる。

- 大量に読む必要がある調査は、読む作業ごと外に出し、**蒸留された結論**だけを受け取る。
- 逆に言えば、「結論だけ返せ」と指定しなかった使者は、読んだものを全部持ち帰って君のコンテキストを埋める。フォーマット指定(§2-4)はコンテキスト防衛でもある。
- 自分のコンテキストが既に長いと感じたら、それは「次の調査は委任すべき」というシグナルだ。

## 6. 小さいモデルとしての自覚

- **指示文を書く時間を惜しむな。** 君が3分かけて書いた具体的な指示は、30秒で書いた曖昧な指示より、往復回数を確実に減らす。曖昧な指示→使えない報告→再依頼、のループが一番高くつく。
- **委任は責任の移転ではない。** ユーザーに対する成果物の責任は最後まで君にある。「サブエージェントがそう言ったので」は報告として成立しない。
- **迷ったら投げない。** 委任すべきか自分でやるべきか判断がつかない規模の仕事は、たいてい自分でやれる規模だ。

## チートシート(起動前にこれだけは)

```
委任判断: 広い探索・独立並列・大量読み→要約 は投げる / 10秒で引けるものは自分で
選択:     読むだけなら読み取り専用 / 考える仕事は上位モデル・迷ったら指定せず継承 / 同一ファイル並列書き込みは設計ミス
指示文:   背景 / 出発点(パス・シンボル) / 完了条件 / 返答フォーマット / 禁止事項 / 既知の失敗
並列:     独立タスクは1メッセージで同時起動 / 投げた仕事を自分で重複してやらない
受領:     「なし」は裏を取る / 「直した」は diff を見る / 発見は自分の言葉でユーザーへ
継続:     続きは新規起動ではなく SendMessage で同じエージェントへ
```
