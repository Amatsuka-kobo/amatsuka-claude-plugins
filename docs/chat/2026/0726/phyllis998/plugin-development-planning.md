## セッション 3: guidepost 設計案の詳細提示と承認

# AI

guidepost プラグインの詳細設計を6セクションで提示した。主要な決定事項は pitcrew の実装資産(hook 注入・ローカルサーバ)を下敷きにし、API 不使用の制約を満たしながら実装することである。

各セクション：
1. **全体アーキテクチャ** ファイルキュー方式で Claude Code セッション ↔ ビューア間の双方向通信を実現。LLM 処理はセッション内、サーバは静的配信と質問書き込みに限定し API キー不要。
2. **ツアー生成(スキル)** diff を依存関係順に並べ替えたストップ列を生成。単なる diff 表示と異なり「理解しやすい読む順序」を実現。
3. **ビューア** 左にストップ一覧、右に差分表示。pitcrew serve と同型。
4. **質問→回答ループ(hook)** ビューア質問ボックス → キュー → セッション hook 検知 → 回答を answers/ に記録。セッション閉鎖時の遅延配送にも対応。
5. **エラー処理・エッジケース** 巨大 diff 畳み込み、ツアーベース SHA 不一致警告、gh コマンド未インストール時の代替案。
6. **テスト** ユニットテスト(キュー・スキーマ・hook 判定)、ビューア UI は手動確認。

ユーザーに「気になる点・変えたい点はありますか」を確認。プラグイン名は仮の「guidepost」だが他の名前の希望があれば対応可能と案内した。

# AI

既存プラグインの設計書の置き場所・体裁を確認し、`plugins/guidepost/DESIGN.md` として設計書を執筆。

### Haiku レビューの結果と反映

Haiku がプラグインの動作(生成→巡回→質問ループ)を誤読なく要約できたため、設計の骨格は明確に伝わると判断。指摘に基づき設計書に以下を追記：

1. **質問キューのスコープ** — 全ツアー共有の 1 箇所とし、各質問ファイルの YAML frontmatter(`tourId` / `stopId`)でスコープする方式を明記
2. **並行アクセス** — すべての書き込みをアトミック(tmp + rename)にし、`processed/` への移動主体は hook と確定
3. **回答ファイルの戦略** — 1 質問 = 1 ファイル、append はしない。タイムスタンプは質問ファイルから引き継ぐ
4. **PR の base 取得** — `gh pr view --json baseRefOid,headRefOid` で動的取得(`main` を暗黙仮定しない)
5. **ポート衝突** — 4870 から +1 ずつ最大 10 回自動リトライ
6. **概要ストップの内容** — `diffText` なし、ファイルパス一覧+各 1 行概要のみ
7. **ストップ ID・SHA 長** — 連番 `stop-01`〜、短縮 SHA は 7 文字
8. **ハイライト実装** — CDN 依存なし、オフライン動作必須
9. **serve のテスト方法** — リクエスト処理を純関数に分離し、実ポートを開かず検証
10. **pitcrew との関係** — 「パターン参照・コードはコピーして自己完結、追従しない」と明文化

レビュアの誤読そのものが設計書の曖昧さの検出器になる仕組みであり、誤読ゼロだったため指摘は暗黙知の穴埋めに集中。「pitcrew と同型」のような既存資産への参照は、流用の範囲(パターンか、コードか、依存か)を明文化しないと実装者が判断に詰まる点が最も価値が高かった。
