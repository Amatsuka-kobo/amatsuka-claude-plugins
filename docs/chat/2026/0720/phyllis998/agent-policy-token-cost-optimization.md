## 実施内容：CLIProxyAPI request-log による実リクエスト捕捉

## 裏取り結果（実測）

| 実行形態 | tools スキーマ | system | メッセージ(ブリーフ+履歴) | 合計/ターン |

## 主要発見3点

1. **サブエージェントは `tools:` frontmatter どおり7ツールしか積んでいない** — 「全56スキルカタログ・全エージェントカタログを毎ターン再送」という恐れは起きていない。スキル一覧は名前+短い説明(~1.5k)のみで、Serena 等 MCP ツールスキーマはサブエージェントに載っていない。ツールトリムで削れるのは 1ターン ~1.2k で効果は小さい。

2. **1ターン ~13k では、事件の 11M input (~97ターン想定)に到底届かない** — 13k × 97 ≈ 1.3M なので、「1ターン ~113k」という逆算が成立していない。メモ§3 の仮説は部分的に否定された。

3. **差を説明する有力候補はキャッシュの計上方法** — Codex 上流の usage を見ると `input_tokens: 37526` のうち `cached_tokens: 26112` のような応答が普通に返っており、プロキシの統計が「input=キャッシュ込み全量」を合算しているなら、11M の大半はキャッシュ読取(サブスク運用では実質コストほぼゼロ)の可能性が高い。「Luna 11M」は見かけほど痛くない疑い。

## 発見による方針への含意

メモの結論のうち **§5(委譲の損益分岐)と §6-1(Fable のターン数・文脈削減が最大レバー)は実測と整合し、むしろ強化**される。一方 §6-3 の「サブをトリム」は効果が小さいことが判明。フル設計のレバー優先順：

1. **Fable のターン数削減** — 転記の直接 Write、dispatch のバッチ化、並列ツールコール
2. **Fable の文脈軽量化** — メインセッションに常時載る MCP ツール(~15k)・カスタムエージェント(~20k)・スキルカタログの間引き、プロジェクト単位での不要プラグイン無効化
3. **計測の正常化** — プロキシ統計のキャッシュ込み/抜きを区別して読む運用
4. (効果小・ついで) サブエージェント報告フォーマット簡潔化・検証ターンのオーケストレーター寄せ

## 提案する3案

**A. 方針文書のみ更新(小)** — with-codex/claude-only の SKILL.md に「委譲の損益分岐」と「dispatch バッチ化・並列化」の規律を追記。プラグインのバージョンを 0.2.x に上げて完了。環境設定には触れない。

**B. A + コスト規律リファレンス新設(中・推奨)** — A に加えて `references/cost-discipline.md` を新設し、(1) 損益分岐表、(2) Fable 文脈軽量化のチェックリスト、(3) プロキシ統計の読み方(cached_tokens の扱い)を収録。方針本文からは1行で参照。今回の実測データが根拠として残る。

**C. B + テンプレート・環境改修(大)** — B に加えて gpt-* テンプレートへ報告簡潔化・検証省略の規律を組み込み、さらにこのリポジトリの `.mcp.json`/プラグイン構成の見直しまで踏み込む。効果の小さい箇所に工数がかかり、環境改修はプラグイン外の話。

推奨は **B** — 実測で効くと確認できたレバー(Fable 側)を文書として固定でき、効果が小さいと判明したツールトリムに実装コストを払わずに済む。C のテンプレート改修は、運用してみて報告の冗長さが実際に問題になってからで遅くない。

**確認待ち** — どの案で進めるか、また 11M の謎について「プロキシ統計がキャッシュ込み合算かどうか」をもう一段裏取りする価値があるかどうかをユーザーに確認。

## セッション2: 実測値の反証・深掘り調査・決定的発見

# phyllis998

> 入力トークン11Mが実際にはあまり重くない可能性を指摘されましたが、実測値(/costで確認した値)だと、claude-gpt5-6-luna (input ＄1 / output ＄6 / 1M) が input 11M, output 24.7K で、実際のコストが＄56.15と、SDDで複数のエージェントを駆使して開発した合計金額＄216.64のなかで、2番目に高い金額でした。(1番目はFableの＄75.08)

ユーザーは `/cost` の実測値を提示し、セッション1の「11M はキャッシュで軽い」仮説への反証を示す。Luna $56.15 は SDD 開発全体 $216.64 の24%を占め、無視できないコストであることを指摘。

# AI

$56.15 という実測値は重要な反証だが、単価と合わない点を指摘。input $1/1M なら 11M は $11 のはずが、5倍の $56.15 になっている矛盾がある。この矛盾を解くため、**事件セッションのトランスクリプト全件から usage を集計して実データで検証する決定**を下す。

## 実施内容：事件セッション 607f01ed の全トランスクリプト分析

- 全サブエージェント(Luna/Terra/Sol 他)の usage を集計
- リクエスト単位での input 内訳を分析
- スキルロード量の定量化
- キャッシュ効率の比較
- 単価テーブルの検証

## 判明した決定的事実

**1. 11.8M input は実測どおり実在する(キャッシュではない)**

| モデル | リクエスト数 | input(非キャッシュ) | cache_read | output |
|---|---|---|---|---|
| Luna | 193 | **11.80M** | 0.73M | 26k |
| Terra | 126 | 5.17M | 1.56M | 22k |
| Sol | 105 | 3.33M | 0.17M | 50k |
| (参考)Haiku | 564 | **0.03M** | 25.3M | 483k |

セッション1の「キャッシュ込み合算では」という仮説は誤りで、ユーザーの実測が正しかった。11M は本物の重さ。

**2. 真犯人: `claude-api` スキル(~139k トークン)の自動ロード**

事件セッションで **GPT エージェント13体が `Skill(claude-api)` を呼んでおり、1回あたり ~139k トークンのスキル本文を自分の文脈に取り込んでいた**。以後そのエージェントの全ターンで 139k が毎回再送される複利効果が発生。最大リクエストは 1ターン ~153k。

スキルロードが無ければ Luna の1ターンは ~13k(セッション1の裏取りと一致)なので、193リクエスト × 13k ≈ 2.5M で済んだはずが 11.8M に膨れた——**約5倍の増幅は、ほぼこの1つのスキルが説明する**。

なぜ呼んだか：`claude-api` スキルのトリガー定義が「**プロンプトに Claude/Anthropic の名が出たら必ず読め**」という強い書き方で、このリポジトリは Claude Code プラグイン開発なので**全タスクのブリーフが Claude に言及**する。真面目な GPT ワーカーほど毎回ロードする構造になっていた。

**3. GPT 経路はキャッシュがほぼ効いていない**

Haiku は input 0.03M / cache_read 25.3M(ほぼ全てキャッシュ)なのに対し、Luna は 11.8M / 0.73M(**94%が全額課金扱い**)。Claude 系では「文脈再送はキャッシュで1/10価格」になる前提が、Codex 上流では成立していない。プロキシ経由の Codex 変換でプロンプトキャッシュが効かない根本的な問題が存在。

メモ§3の「文脈再送×ターン数」モデルは GPT 側でこそ正しく効いている（逆に効きすぎている）。

**4. $56.15 という金額は /cost の単価テーブル側の問題**

11.8M input を実単価($1/1M)で計算すると **~$12**。$56.15 になるのは input を **~$4.7-5/1M** で計算した場合で、これは `/cost` がカスタムエイリアス `claude-gpt-5-6-luna` の単価を知らず、フォールバック単価で計算しているためとみられる(Opus 級 $5/$25 で計算すると $60.03 でほぼ一致)。

**トークン数は実在、ドル換算は約5倍過大**。

## 最適化レバーの改訂(フル設計のスコープ)

この発見でレバーの優先順位が大きく変わる。

1. **GPT エージェントのスキルロード規律(新・最大レバー)** — 巨大スキル(claude-api ~139k)の無自覚ロードを止める。gpt-luna/terra から `Skill` ツールを外す、またはエージェント定義に「指示されたスキル以外を読まない」規律を明記する。セッション1では「ツールトリムは効果小(~1.2k/ターン)」と評価したが、**Skill 外しの真価はスキーマ削減ではなくロード事故の構造的防止**で評価が逆転。支配的な最適化手段となった。

2. **Fable のターン数・文脈削減(継続・支配項)** — メモ§6-1 のまま有効。Fable $75.08 が1位である事実は不変で、削減効果は Luna より大きい。

3. **GPT 経路のキャッシュ改善(調査項目)** — CLIProxyAPI の Codex 変換でプロンプトキャッシュが効かない原因を調査。効けば再送コストが1/10になる可能性がある。

4. **計測の読み方の規律** — `/cost` のドル換算はカスタムエイリアスに対して不正確。トークン数を一次情報として判断する旨を方針に明記する。

### セクション2: レバー1 — スキルロード規律(最大レバー・事件の直接対策)

**原則: サブエージェントは、ブリーフで明示的に指定されたスキル以外を Skill ツールでロードしない。** スキル側のトリガー定義(「〜に言及したら必ず読め」)は、サブエージェントにおいてはブリーフの明示指定に劣後する——事件では `claude-api`(~139k トークン)のトリガーに GPT 13体が従い、~5倍の入力増幅が起きた。

実装方針：

- **gpt-luna テンプレート**: `tools:` から **`Skill` を削除**(推奨)。Luna 級の軽量タスクでスキルが必要なら、それは Terra 以上の仕事か、ブリーフへの断片転記で足りる。本質は事故経路の構造的封鎖(スキーマ削減 ~0.4k/ターンはおまけ)。

- **gpt-terra / gpt-sol テンプレート**: 「制約」節に「ブリーフで明示指定されたスキル以外は Skill ツールでロードしない」原則を追記。ロード前にスキルサイズが不明な場合は概要のみで判断し、巨大スキルの必要性はアドバイザー相談ではなく**差し戻し**(ブリーフに必要断片を転記してもらう)で解決。

- **オーケストレーター側(両 SKILL.md)**: ブリーフに「使用してよいスキル」を明示する(なければ「スキルロード禁止」)。巨大スキルの知識が必要なタスクは、スキル全文をロードさせるのではなく、必要な断片をブリーフに転記して渡す。

### セクション3: レバー2 — 委譲の損益分岐と Fable ターン数削減(支配項)

cost-discipline.md に損益分岐の原則と判断表を収録。セッション2で実測値でも確認されたルール：

- **転記**(完成形が全指定済み・サブ側の判断ターンほぼゼロ)→ **オーケストレーターが直接 Write**。複数ファイルは並列ツールコールで1ターンにまとめる。dispatch+受取で最低2ターン(~$4)を払う委譲は、1ターン(~$2)の直接書きに勝てない。
- **探索・反復**(サブが自前で多数ターンを消化)→ **バッチ委譲**。N 件を1 dispatch に束ね、オーケストレーターの関与を dispatch と受取の ~2ターンに固定する。タスク毎の個別 dispatch を禁止パターンとして明記。
- **並列 dispatch は同一ターンに束ねる**(既存の並列実行原則の強化)。
- **検証・コミットの寄せ**: サブに毎回 git commit や広域 grep 検証をさせず、バッチの最後にオーケストレーター側(または1回の検証 dispatch)へ寄せてサブのターン数を減らす。

### セクション4: レバー4 — 計測の読み方の規律

cost-discipline.md に「コスト計測の注意」節を収録：

- **/cost のドル換算はカスタムエイリアスに対して不正確**(単価テーブル外のモデルはフォールバック単価で換算。実測: Luna 実単価なら ~$12 のところ $56.15 と ~5倍過大)。プロキシ経由モデルは**トークン数を一次情報**として読む。

- usage 形式の差の注意: Anthropic 形式は `input_tokens` と `cache_read_input_tokens` が別建て、OpenAI 形式は `cached_tokens` が内数。集計時に混同しない。

- **GPT 経路は現状プロンプトキャッシュがほぼ不成立**(実測: Luna input 11.8M に対し cache_read 0.73M)。同じ「文脈再送」でも Claude 系より約10倍重い前提で損益分岐を判断する。

### セクション5: オーケストレーター文脈軽量化(チェックリスト)

cost-discipline.md に、セッション開始時・定期の点検項目として以下を記載：

- `/context` で常駐カタログ(MCP tools・custom agents・skills)のサイズを把握する
- 使わない MCP サーバー・プラグインはプロジェクト設定で無効化する(Fable の1ターン単価は文脈サイズに比例)
- CLAUDE.md・メモリの肥大を防ぐ(常時ロードされるため)

これは環境依存の運用項目なので、プラグインは手順を示すだけで自動変更しない。

### セクション6: レバー3 — 未解決事項(調査タスクとして収録)

- CLIProxyAPI の Codex 変換でプロンプトキャッシュが効かない原因(プロキシの変換仕様か Codex 上流仕様か)。効けば GPT 側の再送コストが ~1/10 になる可能性があり、損益分岐の数値の見直し条件になる。
- 既存プロジェクトの `.claude/agents/gpt-*.md` はテンプレート改修後に `agent-policy:setup` 再実行で再生成する(移行手順として README/setup に一行案内)。

## セッション4: Luna から Agent ツール削除の追加指摘・設計改訂

> 元々の検討時、LunaからはAgentツールも外すよう検討していました。理由はSkillツールと同等で、LunaレベルのタスクでFableアドバイザーに助言を求めることはないというものです。

ユーザーは、セッション3の設計案に対して、Luna から `Skill` ツールを外すだけでなく、**`Agent` ツールも外すべき**という追加指摘を提供。Luna のような軽量ワーカーではアドバイザーに相談する必要がなく、判断に迷った場合は差し戻すのが正しい設計という根拠を示す。

# AI

ユーザーの指摘を設計に反映。セッション3 の「Skill のみ削除」から「Skill と Agent の両方を削除」へ改訂し、整合性調整を追加。

## 改訂内容：gpt-luna テンプレートの Tool 削減強化

**セクション2(レバー1)の gpt-luna 改訂版:**

- `tools:` frontmatter から **`Skill` と `Agent` の両方を削除** → 残す tools は `Read, Grep, Glob, Write, Edit, Bash, LSP` の基本7つ
- 「アドバイザーへの相談」節を本文から削除し、「制約」節を「**判断・設計・複雑な読解を要する作業は引き受けず、判断に迷ったら差し戻す。アドバイザーに相談しない**」に一本化
  - Luna の役割(一括適用・反復変換・軽微コーディング)は「迷ったら引き返す」が正しい動作。Fable アドバイザー相談(それ自体が Fable のターン ~$2 を消費)を Luna 級のタスクで発動させる理由がない
- **副次効果**: Agent スキーマ ~0.75k + Skill スキーマ ~0.4k + スキル一覧リスト ~1.5k が毎ターンから消え、Luna の1ターンは ~13k → ~10k に軽量化

**整合のための追加変更(1ファイル追記):**

- `references/advisor-rules.md` — 既存の「オーケストレーターはサブエージェントがアドバイザーに相談できるよう Agent Tool を許可し」という全サブエージェント一律の書き方を修正
  - 追記内容：「**アドバイザー相談の要否は役割による。軽量ワーカー(GPT Luna 等)には Agent Tool を許可せず、判断の迷いは差し戻しで解決する**」
  - with-codex SKILL.md のアドバイザー節の要約も同旨に揃える

**Sol / Terra の保持:**

- GPT Sol・Terra は従来どおり `Agent` ツールを保持する。複雑な実装・通常実装では、アドバイザー相談(dispatch+受取 ~$4)が差し戻し+再 dispatch(~$6+)より安いケースが実際に存在するため。
