参照ファイルを読んで設計検討の準備をした。3つのメモを確認：
- 共有先メモ（context-map-sharing.md）: 論点A〜D が整理され、選択肢(1)〜(3)が示されている
- トークンコスト分析メモ（token-cost-analysis.md）: 実測データから、Fable の1ターンコストが約$2で支配項であることが判明

**主な発見：核になる再定義案**

共有モデル全体を見直す際の「効きどころ」として、以下の3点を指摘：

1. **「共有」という語のモデルを疑う** — Claude Code のエージェント間にはメッセージパッシングが無く、context-map は `.claude/context-maps/*.md` というディスク上のファイル。つまり「共有先」とは実際には「dispatch 時のブリーフにパスを含めて読ませるエージェントは誰か」という問い。この視点だと論点A（Opus 自己共有の冗長性）は自明に解ける — 作成者は自分で書いたので読み直す必要がない。

2. **現状の「Fable に必ず共有」はトークンコスト分析と正面衝突** — token-cost-analysis.md の結論は「最優先レバー = Fable の文脈を軽く保つ（$2/ターンの支配項）」。一方 context-map の現行記述は「map 全体を Fable に必ず読ませる」。最も高価なターンを最も太らせる指示になっている。ここが今回いちばん効く修正点。

3. **共有先が4箇所に散在**（SKILL 2件・guide・テンプレ）—変更同期のコストがかかるので、定義の一元化も設計に含める価値がある。

**提案：再定義の方向性**

現在の「共有 = 全文ロード」モデルを「共有 = 所在通知＋必要時のみロード」に再定義すべき。これにより：
- 上流への報告（Fable への確認用）には「map が存在すること」を通知すれば足り、全文ロードは不要
- 下流の実装者（Terra/Luna/Sonnet）には関連断片のみ渡し、map 全体は渡さない
- ターン数削減と文脈軽量化が同時に実現

これは論点A〜D を一貫して解く。

**確認事項：成果物の範囲**

このセッションのゴールを確認したい。3つの可能性が考えられる：
- (a) 共有モデルの「決定」まで — メモに結論を書き込み、実装反映は別途
- (b) 決定 + 実装（4箇所の同期修正）まで — 今回で反映完了
- (c) まず決定に集中し、まとまったら実装するか判断 — 走りながら決める

推奨は **(c)** — 設計判断が固まればトークン節約のため一気に反映した方がよいが、まず「所在通知モデルへ寄せる」という核の合意を取るのが先だと考える。

# AI

成果物の範囲を **(b) 決定 + 実装まで** で承知した。

提案する共有モデルの骨子を提示。「共有 = 全文ロード」を一律に適用するのをやめ、**そのエージェントが map をどう使うか**で読む深さを3段階に分ける3層モデルを提案：

| 読む深さ | 対象 | 根拠 |
|---|---|---|
| **① 全文参照** | map に基づき**設計に手を入れる者**(with-codex=Sol / claude-only=Opus、Opus の補足修正時も) | 全体構造が設計判断に直接効く。多くの場合**作成者と同一**なので追加ロードは不要 |
| **② 所在通知＋必要時ロード** | **承認だけ行う** Fable | 最終承認は設計書+WBS に対して行う。map は根拠資料 → **パス＋3〜5行要約**を渡し、疑問時のみ全文を読む |
| **③ 断片のみ** | **実装担当**(Terra / Luna / Sonnet) | 自己完結ブリーフで足りる。必要セクションだけブリーフに転記、map 全体は渡さない |

各論点の解き方：
- **論点A(自己共有の冗長)** → ファイルモデルで自明に解消。「作成者は自分で書いたので読み直し不要」。① の但し書きで表現。
- **論点B(Sol に共有?)** → Sol は作成者=消費者で同一なので通常不要。**作成者≠設計担当**になった場合(GPT不在フォールバック等)だけ、次の dispatch にパスを渡す。
- **論点C(上流/下流)** → 「設計に手を入れる=全文／承認する=要約/実装する=断片」という**役割ベースの3層**に置き換え。
- **論点D(コスト)** → 「Fable に必ず全文」を撤回。最も高価な Fable のターンを要約で守る。「必ず共有(must)」→「**所在通知は必須、全文ロードは役割に応じて**」。

さらに **§1 の散在解消** として、この3層定義は `context-map-guide.md` に一元記述し、SKILL 2件・テンプレは「詳細は guide 参照」+1行要約に落とす(変更同期コストの削減)。

確認したい点は2つ：
- **(i)** Fable を「要約+オンデマンド」に格下げする点 — 元の guide の趣旨「オーケストレーターへ全体整合の判断材料を共有」を、**Fable=要約 / Opus=全文**に分解する解釈でよいか
- **(ii)** 「必ず共有(must)」という強制語を弱める点に懸念はないか(共有漏れのリスク vs コスト)

> もう少し深堀させてください。Fable/Opusオーケストレータ―は、全ての実装が終わった後の最終レビュー担当でもあります。この場合、context-mapの扱いはどうしますか？

# AI

重要な指摘で、提案モデルの弱点を突かれた。「オーケストレーター=承認だけ」と狭く定義したが、実際には運用方針上、オーケストレーター(特に Opus / 場合により Fable)は「重い最終レビュー」担当でもある。つまり**同じオーケストレーターでも触れる「瞬間」が2つある**。この分解が必要。

**核のインサイト：設計承認時と最終レビュー時では map の性格が反転する**

- 設計承認時の map は「これから作るものの根拠資料(=背景)」
- 最終レビュー時の map は「実装が**カバーすべき範囲の照合リスト**(=能動的な検査器具)」

同じファイルでも用途が違うので、読む深さも変わる。最終レビューこそ map の §影響範囲・§既存契約・§未解決事項・§テスト方法 が一番効く — WBS/設計書は map から派生した二次資料なので、「WBS 自体が map の指摘を取りこぼした」欠落は WBS だけ見ても気づけない。map と実装を突き合わせて初めて出る（防御の多重化）。

## モデル補正：「深さ＝役割」ではなく「深さ＝その瞬間の使い方」

オーケストレーターの map への接触点を2つに分ける：

| 瞬間 | map の役割 | 読む深さ |
|---|---|---|
| **設計承認時**(実装前・フロー step 6) | 背景の根拠資料 | **要約＋オンデマンド**(tier ② のまま) |
| **最終レビュー時**(全実装後) | **カバレッジ/契約の照合リスト** | **主要セクションを能動参照**(§影響範囲・§既存契約・§未解決事項・§テスト方法を軸に、実装との差分を検査) |

map は意図的に「実装前(before)」のスナップショットなので、最終レビューでは「before の想定範囲 vs after の実装」を突き合わせる基準として機能。§現在の構造は陳腐化するが、それは想定内(差分の起点)。

方針の担当割り当て(重い最終レビュー → **Opus** 優先、Fable は直接時のみ)が、そのままコスト最適でもある — Fable($10/1M)より Opus の方が安いターンで map を読める。

**トークンコスト面の整合**

「最終レビューで map を読むのは『Fable の文脈を軽く保て』に反しないか?」— 反しない。コスト分析の病理は「**毎ターン**のカタログ×ターン数×dispatch 回数」の常駐増幅。最終レビューの map 読みは **1回きり(one-shot)の有界な読み込み**。テンプレ1枚分(数k トークン)を1パス読むだけなら、Fable 単価でも ≈$0.05。$2/ターンを支配する 200k 常駐文脈に対して誤差。**コスト漏れは「常駐と往復ターン数」であって「map の一度きりの参照」ではない**。

確認したい点は2つ：
- **(i)** 最終レビュー時は map を「照合リスト」として能動参照する — この位置づけを guide に明記する方向でよいか
- **(ii)** 最終レビューの主担当を **Opus 優先**(map 参照込み)とし、Fable は直接レビュー時のみ map に触れる、という routing でよいか

> あと、言い忘れていましたが、revelationプラグインの3スキルを読み込んでください。プラグインとしてインストールされていないのでReadツールでお願いします。

# AI

revelation プラグインの3スキル（fable-method / fable-subagents / fable-restraint）を読み込んだ。Fable 5 の規律を小型モデルに移植する手順書。特に fable-method §0「質問か変更依頼か / ユーザー領分なら聞く」という意思決定の仕分けが、本設計に直結する接続を発見。

ユーザーの指摘：要件定義がもう一つのチェックポイント。私のモデルは**フロー step 1(探索の前)**に要件定義を固定していたが、現実には**探索が要件を書き換える**。これで map への接触点が2つ→**3つ**に拡張される。

**核のインサイト：探索は要件にフィードバックする(上り方向)**

- map の §未解決事項・§既存契約・§影響範囲 は、しばしば「そもそもの要件」を変える。例：map に「未解決: この API を変えると外部利用者に影響、確認要」とあれば、それは実装以前に**要件級の判断**。現行フローは 要件(step1)→探索(step2) と一方向だが、実際は探索→要件の逆流がある。
- **map が上流へ運ぶべき本体は §未解決事項**。全文ではない。要件定義はこの「未解決事項への判断」で前に進む。これは revelation の fable-method §0「質問か変更依頼か / 選択がユーザーの領分なら聞く」と直結 — 未解決事項をオーケストレーターが仕分け(ユーザー領分=聞く / 妥当な方=決めて記録)する。

## モデルの再統合：map は「上へ共有する成果物」ではなく「オーケストレーターが複数チェックポイントで参照する共有リファレンス」

「深さ=その瞬間の使い方」の原則はそのままに、オーケストレーターの接触点を3つに整理する。**各点で読むのは"その点に必要なセクションだけ"**(全文常駐は一貫して避ける)。

| チェックポイント | 主に読むセクション | 深さ |
|---|---|---|
| **① 要件精緻化**(map 作成直後) | **§未解決事項(最重要)**・§既存契約・§影響範囲 | 該当セクションを参照。未解決事項は**要約で必ず上げる** |
| **② 設計承認**(実装前・step 6) | 要約 | 所在通知＋オンデマンド |
| **③ 最終レビュー**(全実装後) | §影響範囲・§既存契約・§未解決事項・§テスト方法 | 照合リストとして能動参照(one-shot) |

この再統合で、論点B の「上流再共有すべきか?」も自然に解ける — **上流へ伝わる本体は §未解決事項であり、Sol が map を更新して未解決事項が動いたら、その差分だけを要約で上げればよい**(map 全文の再共有ではない)。tier ②(所在通知+要約)の「要約」も、汎用サマリではなく **§未解決事項を前面に出したもの**、と定義を締める。

これは token 規律とも矛盾しません — どの点でも全文常駐はせず、セクション単位のスコープ読み。上りの信号は「未解決事項」という小さな payload に絞られる。

確認したい点は3つ：
- **(i)** 現行フローの「要件(step1)→探索(step2)」に、**探索→要件の逆流(①要件精緻化)を明示**する方向でよいか(guide のフロー節に1ステップ相当を足す)
- **(ii)** revelation を読ませたのは、この設計を Fable の規律と整合させる意図でしたか? それとも後続の実装で参照する予定がありますか?(意図を確認しておきたい)

## セッション4: 設計由来の明確化と統合モデル v3 の形成

# phyllis998

> ii の質問について、読んでいただいたのは、Fableの規律と整合させるためです。
> もうひとつ、context-mapについての設計由来をお話しておきます。
> そもそもなぜこの方式をとっているのかというと、Fableが全体のオーケストレーションをする際、要件定義を行う前に現状のフォルダ構成などを確認するフェーズが発生します。その作業をFable自身にやらせるのは無駄にトークンを消費する行為であり、コストパフォーマンスがよくないであろうということで、より軽量なモデルにファイル探索を行ってもらい、context-mapとして圧縮することでコストを抑えようとしたものです。この観点があることを前提に考えます。

# AI

設計由来がはっきりしました。これは私のモデルを**正しい向きに引き戻します**。fable-restraint §4 の規律を自分にも適用して、正直に修正 — 私の tier ②「Fable を要約に格下げ」は**行き過ぎでした**。

**核のインサイト：context-map の存在理由は「圧縮によるコスト最適化」そのもの**

- Fable が生のフォルダ探索を自分でやると高価なターンを浪費する。だから軽量モデル(Luna/Terra)に探索させ、**蒸留して map 化**し、Fable はそれを読む。つまり **map を Fable が読むことこそが設計目標**であって、避けるべきは「Fable が生ファイルを読む/保持する」方。私は後者を守ろうとして前者(=本来の目的)まで制限しかけていた。
- これは fable-subagents §5「大量に読む調査は外に出し、蒸留された結論だけ受け取る」の**"永続化"**: 探索サブエージェント(Luna/Terra)が使者、map が蒸留された報告書、Sol/Opus が蒸留者。ご質問(ii)の「Fable の規律と整合」は、まさにここで噛み合う — context-map は fable-subagents のコンテキスト経済を、その場の受け答えではなく**ファイルとして固定したもの**。
- したがって**"共有先"より"圧縮度"が本質**。圧縮が効いている限り、オーケストレーターが map を読むのは安くて正解。肥大した map(ダンプ)は、map が消すはずのコストを再導入する — これが**最大の失敗モード**。

## 統合モデル v3 —「まず圧縮(生産側)、次に読む深さ(消費側)」

設計判断の順序を入れ替える。**①どれだけ圧縮するか → ②誰がどの深さで読むか**。

**生産側(圧縮の規律 = 本質・最優先)**

生ファイル読みは軽量モデル(Luna/Terra)へ外注、**Sol/Opus が蒸留**して map 化。map は**ダンプではなく蒸留**。オーケストレーターが1回読んで安い程度に小さく保つ。「肥大した map」を最大の失敗モードとして明記。

**消費側(読む深さ)**

- **オーケストレーター(Fable/Opus)**: 圧縮された map を**読む**(=生探索の代替、これが設計目標)。3チェックポイント(①要件精緻化=§未解決事項中心 / ②設計承認 / ③最終レビュー=照合)で必要セクションを参照。§未解決事項は要約で先出しする速路を用意。
- **実装者(Terra/Luna/Sonnet)**: map 全体は渡さず**断片のみ**ブリーフに転記。
- **作成者**: 既に文脈内 → 自己共有不要(作成者≠下流設計者の時だけパスを渡す)。

**強制語の修正**: 「必ず共有(must)」→「map の**所在通知は必須**／読む深さは役割・チェックポイントに応じる／ただし **map を小さく保つことが最優先規律**」。

この v3 は、皮肉にも guide の原文「オーケストレーターへ共有する材料」の**意図を復元**する(オーケストレーターが主要消費者)。ただし「全文を積む」ではなく「**蒸留物を読む**」と正しく定義し直し、実装者=断片・作成者=除外・チェックポイント構造を足したもの。論点メモの3択(①現状維持/②最小化/③上下分離)は、この「圧縮×チェックポイント」軸に吸収されて役目を終える。

確認したい点：
- **(i)** 論点は出尽くし、v3 を設計の確定案として design doc に書き起こしてよいか
- **(ii)** 追加で詰めたい観点(例: 肥大 map を防ぐ具体基準、断片転記の運用、フォールバック時のパス受け渡し)があるか

**Haiku レビューからの主要指摘と反映:**

1. **用語の曖昧性** — 「全文参照」が「蒸留済み map の全文」か「生コード全文」か不明瞭。設計の骨格に関わるため**必須修正**。§3.0 に用語定義(所在通知・全文参照・蒸留)を明記。
