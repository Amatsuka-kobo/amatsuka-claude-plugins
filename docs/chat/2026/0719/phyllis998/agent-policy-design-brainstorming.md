## セッション23: 重大問題提起・GPT Agents のトークンコスト分析

# phyllis998

> 実は、今回のセッションで起動したGPT Agents合計のInputトークン量が膨大な量になっています。
> Solは1m input 21.7k output、Terraは5m input 21.8k output、Lunaは11m input 24.7k output
> コスト最適化を図るためのagent-policyプラグインですが、今回Solは設計・実装計画のフェーズで作業拒否を行っているため、Codex側の消費トークンはもっと増えることがよそうされ、このままでは今度はCodex側がかなり先にトークンリミットに達してしまうことが予想されます。
> なぜこうなってしまったのか調査・分析をお願いしたいです。私の予想では、GPT Agentsが正確な実装を行うために、毎回関連ファイルを全て読み込みに行った結果なのではないかと疑っており、これの解決策としてcontext-mapが有効になってくるのではないかと考えているところです。ここに関しても考えを聞かせてください。

# AI

重要な問題提起として、fable-method の規律どおり分析を実施(成果物は分析であり、勝手な修正は行わない)。数字の性質に注目することで原因を究明します。

**数字の逆説:** 最も軽量な Luna が最大 11M、最も複雑な Sol が最小 1M。タスク複雑さと逆相関。これが原因究明の鍵です。

**否定できる原因:**
- **エージェント定義やブリーフのサイズではない**: 両方とも数千トークン程度で、11M には桁が全く足りない。つまり巨大な input は定義やタスク入力ではありません。

**実際のメカニズム:**

Input トークンは「(1ターンあたりの基礎文脈) × (総ターン数)」で決定されます。LLM はツール1回呼ぶたびに全文脈(システムプロンプト + 全ツールのスキーマ + スキル/エージェントのカタログ + これまでの会話)を丸ごと再送します。転記タスクでも「ブリーフを読む→ディレクトリ確認→ファイル書き込み→検証 grep 数回→git add→git commit」で 9〜16 ターン。これが dispatch ごとに繰り返されます。

**概算(強い状況証拠):**
- Luna: 8 dispatch × 平均 ~12 tool_uses ≈ 97 ターン。11M ÷ 97 ≈ **1ターン ~113k トークン**
- Terra: 5 dispatch × ~10 ≈ 52 ターン。5M ÷ 52 ≈ **~96k トークン**

両者とも **1ターン約100k** で一致します。この 100k は、ブリーフでもエージェント定義でもなく、**毎ターン再送される固定の基礎文脈**です。その正体は、GPT エージェントの `tools: Read, Grep, Glob, Write, Edit, Bash, Skill, LSP, Agent` に含まれる:
- **`Skill`** — 全56スキルのカタログが毎ターン読み込まれる
- **`Agent`** — 全カスタムエージェント(9種)のカタログ(メインセッションで ~20k)が毎ターン読み込まれる
- システムプロンプト + 許可ツールのスキーマ

転記タスクは Skill も Agent もほぼ使わないのに、そのカタログを毎ターン100k 近く運んでいた、というのが実態です。

**ユーザー仮説(「毎回関連ファイルを全読み」)の評価:**

実装フェーズについては、主因ではありません。ブリーフは完成形全文を埋め込んだ自己完結型で、実装者はブリーフ1つを読んで1ファイルを書いただけ。プロジェクトファイルの全読みはしていません。コストは「読んだ量」ではなく「同じ基礎文脈を何度も再送した回数」です。

ただし、設計・実装計画フェーズについては、あなたの直感は正しい。そこは本質的に探索(リポジトリ理解)を伴い、毎回ファイルを読み直せば、読んだ内容が会話文脈に積み上がり、以降のターンの再送コストを押し上げます。ここで **context-map は効きます** — 「20ファイル読んで構造を把握」を「context-map 1枚を読む」に圧縮でき、探索ターン数と累積文脈の両方を削れます。あなたが懸念する「Sol が本来やるはずだった設計・計画を実行したら Codex 側が先にリミット」というシナリオに対しては、context-map は正しい対策です。

**context-map だけでは足りない — より大きなレバー3点:**

1. **エージェントの積載文脈を削る(最大のレバー):** 転記・軽微作業しかしない Luna から `Agent`・`Skill` ツールを外せば、毎ターンのカタログ(数十k)が丸ごと消えます。1ターン100k → 例えば40k になれば input は6割減。トレードオフはアドバイザー相談ができなくなる点ですが、Luna はほぼ相談しません。

2. **転記タスクはそもそもサブエージェントに投げない(構造的な最大の気づき):** 計画にファイルの完成形全文が埋め込まれているなら、**オーケストレーターが Write で直接書けば、100k×12ターンの再送はゼロ**です。サブエージェント駆動が逆にコストを膨らませた構造です。サブエージェントが真価を発揮するのは「探索・判断・文脈隔離が要る仕事」であって、「すでに書かれた内容の機械的転記」ではありません。

3. **1タスクあたりのターン数を減らす:** 実装者に全検証 grep + git 操作までやらせるとターンが伸びます。検証・コミットをオーケストレーター側に寄せれば、実装者のターンは「読む・書く」だけに縮みます。

**agent-policy への含意(次の改善ネタ):**

今回の実地テストは、方針そのものに2つの改善点を示しました:
- 「機械的転記はサブエージェントに委譲せず、オーケストレーターが直接行う」を方針に明記
- エージェントごとにツール権限を最小化する設計

**確認方法(私の側では実トークンが見えないため):**

推論の裏取りとして、プロキシ(CLIProxyAPI)の**リクエストログで1リクエストあたりの input トークン**を見てください。転記タスクのどのリクエストも ~100k 前後で、かつ**中身の大半がツール/スキル/エージェントのカタログ**なら、上記の診断が確定します。もし逆に、プロジェクトファイルの中身が大量に含まれていれば、あなたの「全読み」仮説が主因ということになり、その場合は context-map と「実装者に読ませるファイルを絞る指示」が第一対策になります。

## セッション24: 転記の委譲判断・コスト分析の深掘り

# phyllis998

> 例えば、Fableオーケストレータ―(＄50/1m output)が転記を行う場合と、Skill,Agentを外したLunaエージェント(＄6/1m output)に転記を委譲した場合、どちらが安くすみますか？

# AI

良い深掘りです。これは分析の依頼なので、数字で答えます。

## 結論: 転記なら Fable が直接書く方が安い(数倍〜桁で)

出力単価は Fable が $50、Luna が $6 で 8倍差ですが、**転記のコストを支配するのは出力ではなく入力(文脈の再送)**です。そして委譲は必ずその入力を上乗せし、直接書き込みはそれを丸ごと回避します。出力単価の裁定取引($50→$6)は、出力が小さい転記では効きません。

## なぜそうなるか(限界コストで考える)

決定の瞬間、Fable はどちらにせよ1ターンを使います(Write するか Dispatch するか)。そのターンの入力(Fable の全文脈)は両案共通なので相殺。差が出るのは**その先**です。

**案A(Fable が直接 Write):**
- 追加コスト = ファイル内容 F を出力するだけ ≈ **F × $50/1M**
- 内容は既に Fable の文脈(計画書)にあるので追加入力ゼロ

**案B(トリム済み Luna に委譲):**
- Fable の dispatch 出力(指示文 P)× $50/1M
- **Luna の入力 =(ターン数 T)×(1ターン文脈 C)× Luna入力単価** ← これが巨大項
- Luna の出力(F + 報告)× $6/1M
- **さらに Fable が結果を受け取るための追加1ターン**(全文脈の再送)

決め手は、**案A の「F × $50」 vs 案B の「T×C × Luna入力単価」**の対決です。

## 具体例(SKILL 1枚 ≈ 60行 ≈ F=1,500 トークン)

| | 案A: Fable 直接 | 案B: トリム Luna 委譲 |
|---|---|---|
| 支配項 | F 出力 1.5k × $50/1M = **$0.075** | Luna 入力 ≈ 4ターン × 45k = 180k |
| | | 180k × 入力単価 |
| 〃(入力$0.5/1M と仮定) | — | **$0.09** |
| 〃(入力$1.5/1M と仮定) | — | **$0.27** |
| その他 | (将来の文脈肥大 少々) | + dispatch指示 $0.05 + Fable受取1ターン + Luna出力 |

Luna の**入力項だけ**でも、どんな現実的単価でも案A の総額に並ぶか上回ります。転記の出力(F)は両案で同一・小さいので、$6 の安さが効く余地がありません。

## 今セッションの実数での裏付け

Luna 8タスクを**もし Fable が直接 Write していたら**:
- Fable の出力増分 ≈ 8ファイル × ~1.5k = ~12k トークン × $50/1M ≈ **$0.6**(+文脈肥大 少々)

実際の Luna 委譲:
- **入力 11M トークン**。入力単価を仮に $1.5/1M としても **≒ $16.5**(Skill/Agent 積載ありの実測。トリムしても入力支配で $0.6 には遠く及ばない)

**$0.6 対 $16 超** — 転記を委譲したことが、まさにこのセッションのトークン膨張の正体です。

## 唯一の反対向きの力(委譲が勝つ条件)

直接 Write には副作用があります: **書いた内容が Fable の文脈に残り続け、以降の全ターンの入力を押し上げる(文脈肥大)**。ただしこの肥大コストは、典型的なファイル数・サイズでは委譲オーバーヘッドよりずっと小さい。委譲が本当に得になるのは:
- **出力が大きい仕事**(ゼロから生成する実装・長文。転記ではない)
- **入力・探索が重く、その汚れをオーケストレーターの高価な文脈から隔離したい**仕事(まさに context-map を作る探索フェーズ)

転記はこのどちらにも当たらないので、直接書き込みが正解です。
