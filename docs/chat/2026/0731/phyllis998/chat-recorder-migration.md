## セッション 4: Sonnet 選定の詳細説明と Haiku の限界確認

# AI

**Sonnet 選定の 3 軸根拠**

1. **下限(何が不足したか)**  
   haiku は実測で会話記録の読解+抽出で失敗。入力不足ではなく推論余力の問題と確認済み。トランスクリプト片(4,700〜7,100 字)を「〜を調査した」「〜を修正した」のように 1 行に潰してしまい、何を調べてどう分かったかの過程が失われている。設計書 §3 で「失敗・やり直しの経緯はこのリポジトリで最も価値の高い記録」と定義したスロットが全滅する。

2. **適合性(難度帯の判定)**  
   agent-policy 担当表でいう Sonnet の役割は「コードレビュー」 = 成果物を読解して評価・言語化する作業。会話記録の構造化要約は読解系タスク(不足していたのは要約度、つまり抽象化の推論)であって、アーキテクチャ判断や設計トレードオフ(Opus/Fable 帯)ではない。

3. **上限(実行頻度がコストを決める)**  
   chat-recorder は「1 ターン = 最大 1 回」毎ターン裏で走る。API 不使用の制約上、消費は全部ユーザーサブスク。Opus を常駐させると日常的にレート圧迫。Sonnet で品質とコスト両立が狙い。

**ただし、「haiku で OK」となる場合もある**  
設計書 §8-7 で「sonnet + 粒度指示強化」を 1 本検証し、不足時だけモデル引き上げと設計。つまり、粒度指示強化後の検証が先。今の propose は「直近記録の失敗パターン(過程を 1 行に潰す)から逆算した指示改訂」ですが、その指示改訂だけで haiku が復活する可能性も残っています。

## セッション 5: 満足していた時代のモデル検証と方針修正

# AI

良い指摘です。「品質に満足していた時代(claude -p 以前)の記録主体が実際に何のモデルだったか」が判断の要なので、推測でなく git 履歴で確認しました。

**履歴が示す事実: 満足していた時代も haiku だった**

| 時期 | 方式 | モデル |
|---|---|---|
| 7/08〜(初版・品質に満足) | サブエージェント、毎回会話全体を記録 | **haiku** |
| 7/24 昼(差分追記化) | サブエージェント、未記録分のみ追記 | **haiku** |
| 7/24 夕方〜(品質不満) | headless `claude -p` | **haiku** |

`chat-recorder.md` の frontmatter は初版(`3a803a4`)から一貫して `model: haiku` で、headless の起動引数も `--model haiku` でした。モデルは全時代で共通なので、品質低下の原因をモデルに帰す根拠は履歴にありません。前ターンの「haiku では不足が実証済み」は言い過ぎで、正しくは「**headless 環境の haiku では不足**」です。訂正します。

headless で何が変わったか。モデル以外に同時に変わったのは次の 2 点です:

1. **プロンプトの機械化**: headless はコード生成の固定プロンプト(`buildRecorderPrompt`)で「各コマンド 1 回で実行」など手順遵守に強く寄せた指示になった。
2. **`--append-system-prompt` による責務の強い抑制**: 「prepare、記録本文生成、commit 以外を実行しない」という system prompt が付き、要約に推論を割く余地をさらに狭めた。

「簡潔すぎる要約」はこの環境要因で説明でき、モデルを上げなくても解消しうる、というのが履歴の示すところです。

**ただし 1 点だけ留保**

「差分追記 + サブエージェント + haiku」の組み合わせ自体は、実は**ほぼ実績がありません**。差分追記化から headless 化まで同日 4 時間しかなく、しかもその間は抽出バグ(AI 本文を捨てる `a6e0015` 修正前)が生きていました。満足されていた品質の大半は「会話全体を毎回書き直す」時代のものです。とはいえ、抽出修正後は入力に 4,700〜7,100 字が入ることを確認済みなので、懸念は入力量ではなく「書く側への指示」に絞られます。これはモデルと独立に、設計済みの粒度指示強化(§3.2)が受け持ちます。

**修正提案**

- **`model: haiku` に据え置き**、品質対策は粒度指示の強化に一本化する(毎ターン裏で走るエージェントなのでサブスク枠の消費も最小で済む)
- 実機検証 §8-7(実記録 1 本の品質確認)で不足が出た場合にのみ sonnet へ引き上げる。frontmatter 1 行の変更で済み、設計の他の部分には影響しません
- 設計書 §1.2 の「haiku 固定が原因の一つ」という記述も、上記の履歴事実(モデルは全時代共通、原因は headless の環境要因)に訂正する
