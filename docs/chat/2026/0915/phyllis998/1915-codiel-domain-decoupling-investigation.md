# §6-4 解説: 「任意ドメイン名の行き先が無い」穴

## 1. 穴の正体 — 契約と消費側の非対称

契約側(`file-contract-freeze.md:53`)は **ドメイン名を任意の文字列**と定めている。対して消費側は 3 値固定。ずれが出るのは次の 3 箇所だけ。

| # | 場所 | 任意キー `impl` が来たときの挙動 |
|---|---|---|
| 1 | `orchestrating-runs/SKILL.md:197-205` の対応表 | `frontend`/`backend`/`data`/`generic` の 4 値しか書いていない。`codiel-implementer-impl` へ送ろうとして**存在しない**、または対応表に無く判断不能 |
| 2 | `agents/codiel-implementer-*.md:15-17` の規律 | 「`[domain: backend]` タグのみ」「縮退モードでは `[domain: generic]` タグのみ」。`[domain: impl]` は**どの担当も引き受けない** |
| 3 | `agents/codiel-reviewer-*.md` の観点 | 観点が backend/frontend/data に固定。任意ドメインに当てる観点が定義されていない |

**重要なのは、穴が指示層のディスパッチにしか無いこと。** `guard-write.ts:153-174` は `domains[domain]` を引いて glob 照合するだけで、キー名を検査しない。`RunState.domain` のコメントも「値がドメインマップに存在するかは検証しない — 判断は読む側の責務」と明記している。つまり **hook 層は任意キーで既に正しく動く**。

## 2. 現状の縮退運用は「backend 兼任」で作られている

agent 定義を実物で確認したところ、`generic` 縮退は次の形で焼き込まれていた。

- `codiel-implementer-backend.md:16` — 「縮退モードでは汎用実装担当を**兼ね**、`[domain: generic]` タグのステップを実施する」
- `codiel-implementer-frontend.md` / `-data.md` — 「generic 縮退時の汎用実装は codiel-implementer-backend の担当である」「**generic 縮退時は呼ばれない**」
- `codiel-reviewer-backend.md:3` — 「ドメイン縮退時は汎用レビュー担当を**兼ねる**」。観点節に「`generic` 1 つに縮退しているプロジェクトでは、diff 全体を確認する」

`★ Insight ─────────────────────────────────────`
ここに見落としやすい事実がある。**汎用レビューは「backend 観点で diff 全体を見る」という形になっている。** `codiel-reviewer-backend` の観点は「API 設計・エラーハンドリング・パフォーマンス・互換性」で固定されており、縮退時に足されるのは「diff 全体を見よ」という**範囲**の指示だけで、**観点は差し替わらない**。

`generic` 1 つのプロジェクトなら「まあ妥当」で済む割り切りだったが、任意キーへ一般化すると破綻が見える。このリポジトリの `docs` ドメイン(`harness-docs/**`, `README.md`, `.serena/**`)の変更を **backend 観点(API 設計・N+1・エンドポイント互換性)でレビューする**ことになる。穴を塞ぐ方法の選択は、この歪みを引き継ぐか断つかの選択でもある。
`─────────────────────────────────────────────────`

## 3. 塞ぎ方 3 案 — 推奨は案2

**推奨は案2(汎用担当エージェントの新設)。** 理由を先に述べる。

案1 は変更が最小に見えるが、`codiel-implementer-backend` の `description`(「backend ドメインの dev-plan.md ステップを TDD で実装する」)を嘘にする。description は Claude Code が委譲判断に使う一次情報であり、ここに嘘を置くと将来設計(Agents → Skills)でその嘘がそのまま移る。加えて §2 の観点の歪み — `docs` ドメインを backend 観点でレビューする — を一般化して固定してしまう。案2 は定義を 2 つ増やす代わりに、名前・description・観点のすべてを実態に一致させられる。`codiel-reviewer-doc` / `-security` という「ドメイン非依存の reviewer」の先例が既にあるので、形も収まる。

### 各案の具体的な変更内容

**案1: backend 兼任の一般化(新規定義なし)**

- 対応表を「`codiel-implementer-<D>` が実在すればそれ、無ければ `codiel-implementer-backend` を汎用担当として使う」に一般化
- `set-domain` に渡す値は `D` のまま(`generic` に書き換えない)→ glob 境界は維持される
- `implementer-backend.md:16` の「`[domain: generic]` タグのみ」→「専門担当が存在しないドメインのタグ」へ拡張
- `implementer-frontend/data.md` の「generic 縮退時は呼ばれない」→「専門担当が存在するドメインのときだけ呼ばれる」へ書き換え
- `reviewer-backend.md` の縮退観点を同様に拡張

**案2: 汎用担当の新設(推奨)**

- `codiel-implementer-generic` と `codiel-reviewer-generic` を新設(`prompt-smith:agent-creator` で作る)
- `reviewer-generic` の観点は**ドメイン非依存の一般観点**として定義する(design.md との整合、エラーハンドリング、明らかな性能問題など)。backend 観点を流用しない
- 対応表を「専門担当が実在すればそれ、無ければ `-generic`」に
- `implementer-backend.md` / `reviewer-backend.md` から**兼任記述を外す** → backend が backend 観点に専念できる
- `implementer-frontend/data.md` の「汎用実装は backend の担当」も `-generic` へ書き換え
- 既存の `{"generic":["**"]}` 縮退も自然に `-generic` へ流れ、特殊ケースが消える

**案3: reviewer の観点をドメインから切り離す**

- ドメインで reviewer を選ばず、常時参加 + 汎用 1 体に固定し、ドメイン観点はディスパッチプロンプトで渡す
- 将来設計(§8 の「フェーズ／役割 × ドメイン → スキル集合＋既定担当」)の先取りになる
- **本件のスコープを超える。**引き継ぎ書 §10 が将来設計の実装をスコープ外としているため、非推奨

## 3. §6-5 の判定 — 契約変更は 1 行に限定できる
