- 設定: `decision-kernel.config.yaml` を内蔵デフォルトに深マージ、configHash で再現性担保

# AI

- `--output-format json` + zod 検証、失敗はフェイルクローズドで ASK へ

設計書 §7 をこの方式に書き換え、`@anthropic-ai/sdk` 依存を削除。

## セッション3: パネル型判定のディスカッション

# hiro0209

各ツールの内部で使われる決定論チェックプログラムに、次の観点を追加したいです。

- adversarial reviewer
- cross check
- steelman

また、最後にAIによる自己評価フェーズも入れたいです。決定論チェックは、何らかの方法で現在のタスクの重さを判定し、それらの決定論チェックを行うかを判定させたいです。そして、内部で行われるチェックのエビデンスとして各フェーズ毎にファイルとして保存しておきたいです。これには、なぜこの判断だったのかを明確にし、AIに対するコンテキストとする意図があります。これらの判断は決定ではありません。もっとこうすればよいのではないかというアイディアや、これは無理があるなどのディスカッションがしたいです。

# AI

ディスカッションとして以下を提示:

1. **カテゴリエラーの指摘**: adversarial / cross check / steelman は推論・批評という LLM の営みであり「決定論チェック」ではない。「決定論的なのは、どの観点をいつ走らせ結果をどう合成するかであって、観点そのものは LLM 判定のバリエーション」と再解釈し、**法廷モデル**を提案(ルールパス=物証、adversarial=検察、steelman=弁護、cross check=鑑識、自己評価=裁判官)
2. **steelman 賛成の理由**: アラーム疲れがガードレールの真の死因。ASK 乱発 → 人間のラバースタンプ化を防ぐ false positive 削減装置として必須
3. **無理がある点**: 「自己評価」が産出 AI 自身の自己採点なら反対(自己過信・利益相反)。別コンテキストの独立 meta 評価者なら強く賛成 → 主語の確認を要求
4. **重さゲーティング**: 賛成。ただし**昇格のみ**(「軽く見える危険な変更」でパネル回避を封じる)。パネルは並列起動、パネル間の分散自体がシグナル
5. **証拠ファイル**: 最良のアイディア。evaluationId 単位より **run 単位のケースファイル**に拡張し、フェーズ間 crosscheck(「この diff は承認された計画をやっているか」)を可能に。懸念: インジェクションのロンダリング、ツール応答にはパスのみ返す
6. 残論点: ①自己評価の主語、②「弁護士だけ呼ぶ」骨抜き設定を防ぐ不変条件の要否

## セッション4: 追加観点と不変条件

# hiro0209

1. 独立meta
2. 弁護士だけ呼ぶのは非常にまずいので、なんらかの不変条件を仕様に入れるべきかと思います。

ほかに追加した方がよいと考えられる観点などありますか？

# AI

**追加推奨**:

- **前提監査(assumption auditor)**: 「間違った前提を幻覚し、その上に正しい推論を積む」暴走パターンへの対策。critical ティアのみ
- **再提出ループ検知**: パネルではなく決定論ルール層。ASK/STOP 後の近似成果物再提出を検知し N 回で STOP へ昇格。「判定に落ちたらちょっと変えて再挑戦」は暴走の署名そのもの。費用対効果最高と評価
- **cross check の両方向明文化**: 未達(計画にあるのにやっていない)と逸脱(計画にないのにやっている)の両方向必須

**条件付き**: blast radius は独立パネリストにせず、重さ判定への入力 + meta のルーブリック軸へ

**見送り**: セキュリティ専門レンズ(adversarial の職務指示に吸収)、YAGNI レンズ(品質論であり暴走防止でない)、判例チェッカー(コールドスタート問題で v2 送り → 次セッションで撤回)

**不変条件案(7項目)**: 弁護は検察なしに存在できない / 昇格のみ原則 / sealed ルール / meta の独立性 / 分散は ASK に倒す / 証拠のハッシュチェーンによる改竄検知(判定対象 AI が自分のケースファイルを書き換えて「無罪の証拠」を捏造する攻撃への対処) / 自由記述は判定を動かせない

## セッション5: 判例チェッカーの再評価

# hiro0209

このDecisionKernelを使用するプラグインCodielは、AIによる失敗例を蓄積し、プロジェクト毎に成長させるという特性を持たせる予定です。判例チェッカーはこの思想に合致するのではないでしょうか。

# AI

前言撤回。Codiel の思想なら判例チェッカーは周辺機能ではなく**蓄積した失敗例を判定に還流させる出口**そのもの。設計の急所3つ:

1. **判例の価値は verdict ではなく「結末」にある**: `record_outcome(evaluationId, outcome: approved/rejected/incident)` ツールを新設し、人間の裁定・事後の障害を記録して閉ループを完成させる。`incident`(PROCEED したのに実害)は kernel の見逃し記録で最も価値が高い
2. **検索は決定論・当てはめは LLM**: API なし制約下で埋め込みは使えないが、kind・発火ルール指紋・パス重なり・BM25 程度の語彙類似で決定論的に検索可能。コールドスタートは**内蔵シード判例集**(幻覚 API、テスト削除による偽装グリーン、スコープ肥大等)で解消
3. **不変条件の拡張**: 判例による降格の禁止(approved 判例は参考情報のみ、合成に入るのは失敗判例の昇格シグナルだけ)/ 判例の書込は kernel の専権(捏造防止)。将来の宿題として判例の賞味期限

- **Metatron** — 天界の書記。ケースファイル・判例ストア推しなら

総合推薦は Verdiel、意味重視なら Raguel。
