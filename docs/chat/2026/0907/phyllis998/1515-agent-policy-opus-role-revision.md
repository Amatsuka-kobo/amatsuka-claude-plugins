## セッション 3: Opusサブエージェント化を推奨へ転換、担当表の意味から根拠づけ

# AI

了解。実装抜き、役割の本質で再評価。

**推奨: 案 2(Opus サブエージェント)。判断・承認だけオーケストレーターに残す。**

理由:
- 担当表は「役割→モデル」の表。オーケストレーターのモデルはセッション依存(Fable/Opus/Sonnet)で表に書けない。表に `Opus` と書ける役割 = サブエージェントの役割。オーケストレーター=Opus 前提を捨てると、表の `Opus` 行はサブエージェント以外の読み方なし。
- context-map の設計自体が「作成者(統括)≠オーケストレーター」。`context-map-guide` はオーケストレーターを「圧縮された map を読む側」と定義、探索実働は「作成者へ要約を上げる」と書く。統括をオーケストレーターに寄せると、map の目的(オーケストレーターの生探索回避)が消える。
- 設計書のパイプライン(Haiku レビュー → Sonnet 独立レビュー → オーケストレーター採否 → ユーザー承認)は「作者 ≠ 採否判断者」で最も機能する。オーケストレーターが自分で書いた設計書の反証を自分で採否するより独立性高い。
- 設計書の入力は context-map + 要件。discipline 既定で context-map 作成後に設計着手 → 委譲に必要な文脈は既に文書化済み。会話文脈の欠落は依頼文への要件転記で埋まる。

判断軸と各案:
- **オーケストレーターのモデル非固定との整合**: 案 1(表内「オーケストレーター」)= 整合するがモデル表に非モデルが混入。案 2 = 整合。案 3(削除)= 整合するが役割の所在が暗黙化。
- **オーケストレーター文脈の保護**: 案 1・3 = 探索・設計執筆の全文脈がオーケストレーターに積まれる。案 2 = map と設計書だけ受け取る。
- **要件判断の所在**: 案 1・3 = 自然に一致。案 2 = 「§未解決事項の判断・要件確定」はオーケストレーターへ明示分離が必須。
- **品質の安定**: 案 1・3 = オーケストレーターが Sonnet なら設計品質低下。案 2 = 常に Opus。
- **custom 構成での差し替え**: 案 2 のみ帯として GPT 等へ差し替え可能。案 1・3 は不可。

案 2 の文書変更(方針レベル):
- 両 SKILL.md: 2 行を `Opus` のまま維持。「サブエージェントへ委譲する帯」と明記、Agent Tool 許可(統括は探索実働を dispatch)。
- custom-policy: 「オーケストレーター自身が担う。委譲しない」の箇条を削除。
- orchestration-discipline: 「担当表に帯を持たない作業」の括弧書きと合成除外を撤回、L85-86 は帯扱いのまま。「§未解決事項の判断・要件確定への接続」を統括からオーケストレーターへ移す。
- context-map-template: 「作成者: Opus(探索統括)」維持。

帰結(理由ではなく結果): RoleId に 2 帯追加、マーカー対応表・setup-agents・合成対象 15 帯化が追随。
