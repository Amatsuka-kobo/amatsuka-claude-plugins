# native-japanese の強化案:書いた後の検査を足し、他の指示に譲る条項を狭める

3 者の結果をまとめると、推奨は次の 3 手をこの順で進めることです。hook の仕様は公式ドキュメントで確認済みです。2 名の助言者(technical-adviser、independent-tech-adviser)は、互いの見解を見ずに独立して検討しました。

1. **弱さを数える lint を作る。** 過去の transcript から、避ける語と翻訳調の出現を規則ごとに数えます。どの対策を採るかを決める物差しになり、これが無いと「弱い」が印象のままになります。2 名とも最初にやるべきだと答えました。
2. **他の指示に譲る条項を狭める。** 文書の数行を直すだけで済みます。
3. **1 の lint を Stop / SubagentStop hook に載せる。** 違反があれば、応答を 1 回だけ書き直させます。

## 弱い原因は「他の指示への譲り方」と「書いた後の検査が無いこと」と推定する

観測されている事象は、全文を注入しているのに避ける語や翻訳調が残ることです。原因の候補を上から順にたどると、次のようになります。

- **競合による格下げ(2 名が共通して指摘)。**
  - このセッションだけでも、文体を指示する注入が 4 系統あります。output style の EnhancedClaude5、毎ターン注入される genshijin(極限)、ponytail、explanatory です。
  - `discipline.md` の適用範囲には「口調や文体を別の指示が定める場合はそちらに従う」とあります。「文体」は語彙や接続の仕方まで含めて読めるので、モデルは規律全体が格下げされたと受け取っていると推定します。
  - EnhancedClaude5 は「衝突するいかなる指示よりも優先」と宣言しています。
- **書いた後の検査が無い。** 設計書の §2-2 で lint を対象外にしたため、今の仕組みは書く前の制約だけです。「〜することができる」のような癖は、書く瞬間に避けるより、書いた後に見つけて直すほうが確実だと推定します。
- **注入位置が遠くなる。** SessionStart の注入はターンが進むほど遠くなります。一方で genshijin は毎ターン注入していて、実際によく効いています。直近の注入が勝つことの傍証です。
- **規則が多すぎる。** 規則はおよそ 100 項目あり、うち避ける語が約 60 語です。書きながら同時に意識できる数を超えています。

どれが主因かは、1 の lint で切り分けられます。セッションの冒頭と後半、genshijin を有効にしたときと無効にしたときで違反率を比べれば分かります。

- **C は段階的に入れる。** technical-adviser の提案で、はじめは block せず `systemMessage` で警告だけ出します。誤検知率を見てから block に切り替えます。

- **independent-tech-adviser の別案が 2 つあります。**
  - サブエージェントから完成した文章ではなく、事実・根拠・未確認事項を材料として受け取り、main が材料から文章を書く。

- **採れない案があります。** output style をプラグインに同梱する案は、同時に有効にできる style が 1 つだけなので EnhancedClaude5 と共存できません。

# AI

# 対象がコメントと文書なら、推奨は F(書き込み後の lint)に替わる

弱いのがプログラムファイルのコメントと文書だと分かったので、前回の推奨を組み替えます。前回の案の記号 A〜F はそのまま使います。

**新しい推奨は、A の lint を F として PostToolUse に載せ、ファイルへの書き込みを検査して直させることです。**

- 会話を対象にした C(Stop / SubagentStop)は、弱さを確かめる手段が無いので保留にします。
- B(譲る範囲の限定)は優先度を下げます。genshijin は「チャット外に残る文章は通常記述」と定めているので、ファイルの中身とは競合していないと推定します。

## 原因の見立ても変わる

競合が主因という仮説は、ファイルについては成り立ちにくくなりました。代わりに有力なのは次の 2 つです。

- **書き込みの時点で規律が遠い。** コードや文書を書いている間、注意は内容の正しさに向いています。規律はセッションの冒頭、あるいはサブエージェント起動時の注入にしかありません。適用範囲には「コード内のコメント」と明記してありますが、書く瞬間に参照されていないと推定します。
- **書いているのがサブエージェント、とくに GPT 系である可能性。** このリポジトリでは実装を general-implementer や gpt-terra などへ委譲しています。GPT 系も SubagentStart で規律を受け取りますが、日本語の規律にどこまで従うかは確かめていません。【要確認】A の測定で、どのエージェントが書いたかも記録すれば切り分けられます。

## F を実装するときに決めること

| 論点 | 案 |
| --- | --- |
| 検査する範囲 | ファイル全体ではなく、今回書き込んだ部分だけにする。Edit なら `new_string`、Write なら `content` を検査する。全体を検査すると、既存の違反が編集のたびに蒸し返される |
| コードファイル | 拡張子ごとにコメントと docstring だけを抜き出し、日本語の文だけを検査する |
| Markdown | コードフェンスとインライン code は除外する |
| matcher | Write / Edit / MultiEdit / NotebookEdit に加えて、Serena の編集系ツール(`replace_content`、`replace_symbol_body`、`insert_*`、`replace_in_files`)も対象にする。規約で TS・MD・Python の編集は Serena を使うと決めているので、Write / Edit だけでは主な経路を取りこぼす |
| 差し戻し方 | 書き込みはすでに済んでいるので止められない。違反の行と、書き換える方針を返して直させる |
| 除外 | `discipline.md` のように、避ける語を意図して列挙する文書がある。パスの除外指定か、行単位の無視マーカーが要る |
| 導入の順序 | 最初は警告だけにする。誤検知率を見てから、強く差し戻す形に切り替える |

仕様面で確かめていない点が 3 つあります。PostToolUse の `decision:"block"` が reason をモデルへ渡すか、サブエージェント内のツール呼び出しでもプラグインの PostToolUse が発火するか、MCP ツールの `tool_input` にどのフィールド名で本文が入るか、です。【要確認】設計に入る前に公式ドキュメントと実機で確認します。

## 実現方法

HTML は、タグで囲まれた地の文を取り出し、ブロック要素ごとに 1 つの段落として扱えば検査できます。標準ライブラリの正規表現だけで作れるので、パーサー(parse5 など)の依存は不要と判断しています。

| 処理 | 内容 |
| --- | --- |
| 対象の拡張子 | `.html` と `.htm` |
| 丸ごと除外する要素 | `<script>` `<style>` `<pre>` `<code>` `<template>` `<svg>` |
| 除外するもの | HTML コメント。ただし ignore-file の目印は目印として扱う |
| 段落の区切りにする要素 | `p` `li` `h1`〜`h6` `td` `th` `dt` `dd` `blockquote` `figcaption` `div` `section` `br` など |
| 取り除くタグ | インラインのタグ(`<strong>` `<a>` `<span>` など)。タグだけを消し、中の文字は残す |
| 実体参照 | `&amp;` `&nbsp;` と数値文字参照を戻してから検査する |
| 行番号 | 取り出した文字の位置から、元のファイルの行番号へ戻して報告する |

## Markdown と違う点:正規表現の層も段落単位で当てる

HTML では、1 つの文がタグや改行をまたぐことがよくあります。たとえば「短縮することが<em>できる</em>」は、行単位で見ると正規表現に当たりません。

そのため、HTML では正規表現の層も、行ではなくブロック単位の本文に当てる必要があります。

- Edit の `new_string` のような断片ではタグが閉じていないことがあるので、書き込み後のファイル全体から本文を取り出す。
- そのうえで、今回の編集範囲と重なる違反だけを差し戻す。これは形態素解析の層ですでに設計した仕組みと同じです。

## 限界

- `<script>` の中の JS コメントと文字列は検査しません。検査するなら、JS の抜き出し規則を入れ子で当てることになります。
- `alt` や `title` などの属性値は検査しません。
- Vue や JSX のようなテンプレートは対象外です。
- 閉じ忘れのある壊れた HTML では、段落の区切りがずれることがあります。

いずれも正規表現で処理することに伴う限界で、コードには `ponytail:` コメントでこの上限を明記します。誤検知や取りこぼしが問題になったら、パーサーに置き換えます。
