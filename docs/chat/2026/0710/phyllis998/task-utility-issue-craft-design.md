# phyllis998

> task-utilityプラグインに、GitHub Issueを起票するスキルを追加したいです。
> プラグインがインストールされたプロジェクトのリモートリポジトリが対象です。
> インストールされたプロジェクトがgitリポジトリではない場合は、gitリポジトリにするよう推奨しつつSTOPします。
> MCPサーバーなどから提供されるToolでGitHubが操作できる環境であった場合はそのToolを、そうでなかった場合はghコマンドを使用します。
> ユーザーから与えられた情報をもとに、ユーザーとのブレインストーミングをもってIssueの内容を決めていきます。
> ユーザーとのディスカッションには、ユーザーが使用する言語の使用を厳密に守る必要があります。(有意義な対話にするため)
> 対象のリポジトリにIssue Templateが設定されている場合、ユーザーとのディスカッションの中でどのテンプレートを使用するか、あるいはテンプレートは使用しないか、最初に確認をとる必要があります。
> このスキルの名前は何がよいかを含め、一緒に設計を考えてください。

ユーザーから GitHub Issue 起票スキル追加の要件を受け取った。対象の範囲、環境チェック、操作手段の選択、ユーザーとのディスカッションプロセス、テンプレート対応、スキル名検討まで含めた総合設計を求めている。

## セッション2: 複数起票モード設計と別スキル検討

# phyllis998

> a: リモート未設定時もSTOPでよいです
> b: 最初の確認でまとめてよいです
> もう一つ案があります。ユーザーが複数のIssueを一括で起票したい場合もあると思います。その場合のアプローチはどうしましょうか。また、ブレインストーミングの結果、これを1つのIssueにまとめるのは重いと判断できる場合、ユーザーに確認をとりつつ承認が得られれば複数起票モードに切り替えるようにしたいです。

セッション1の確認事項2点(a: リモート未設定時の STOP、b: テンプレート選択と言語確認の1回質問への統合)に対し承認。加えて複数 Issue の一括起票と、ブレスト途中での単一→複数モード切替の要望を提示。

# AI

セッション1の設計確認2点(a, b)の承認を受けた。複数起票モードは拡張として有効と判断し、設計案を提示。

**複数起票モードの入り方**: 2 経路を定義
- 最初から: ユーザーの依頼自体が複数件の起票を含む場合
- 途中から: ブレスト中に「1 Issueには重い」と判断したとき、分割案(各タイトル+スコープ1行)を提示し、ユーザー承認で切替。拒否なら単一のまま続行

切替判断基準を SKILL.md に明記: 独立してクローズできる関心事が複数 / 担当や時期が分かれうる / テンプレート種別が混在する。

**モード内フロー**: 環境チェック・操作手段・言語は全体で1回 → 分割設計確定(タイトル・スコープ・依存関係) → テンプレートは Issue ごと確認 → 各ドラフト順に練る → 全ドラフト一覧で一括承認 → 一括起票。

このときユーザーに Issue 間の関連付け方針を質問: 親トラッキング Issue を作成するか、相互参照(`Related: #n`)のみにするか。

**Issue 間の関連付けについて AskUserQuestion で確認を取った**。ユーザーは「親は作らず各 Issue から追える形(相互参照)」を選択。

ユーザーから追加要望: 「既存 Issue を子 Issue にタスク分解する AI ツールも欲しい」と提示。このツールの提供方法(issue-craft の別モード、別スキル、別の案)を検討する旨を述べた。

**既存 Issue 分解ツールについて**: 別スキルとして後日設計することを推奨。理由は3つ：
1. Description 照合による発動の明確さ(既存 Issue 読解が新規 Issue 起票と異なる関心事)
2. 親子リンク・gh api 必須など、issue-craft の責務外
3. issue-craft SKILL.md の肥大化を回避

実装上の共用: `check-issue-env.mjs` をプラグイン直下の `scripts/` 配置(tools-utility 共通)にすることで、両スキルが環境チェック・テンプレート検出を共用できる設計とする。

**設計書の作成**: 上記2点の承認を経て、設計書を `docs/superpowers/specs/2026-07-10-task-utility-issue-craft-design.md` に作成。セルフレビューを行った上でコミット(`3eab5cf`)。設計書にはセッション1・2の全決定事項、フロー詳細、check-issue-env.mjs 仕様、エラー処理、テスト方針を記載。

ユーザーのスペックレビュー待ちで終了。実装スクリプト・SKILL.md 作成は承認後。
