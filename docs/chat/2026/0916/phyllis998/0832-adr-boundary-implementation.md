## 核心: なぜ挿入だけでは済まないか

ADR は独立ファイルではなく `harness-docs/ARCHITECTURE.md` の `## ADR 一覧` 節に直書き。パーサの刻み目は `### ADR-NNN:` 見出しのみ。エントリ間の接着剤は `plugins/metatron/src/lib/adr.ts:664` の `\n\n` リテラル 1 行だけ。

`---` を素朴に挟むと 3 つ壊れる。実測確認済み。

1. **状態変更の履歴行が次の ADR 側へ入る（静かに壊れる）**。`contentEndIndex` の遡り（`adr.ts:215-220`）は空行しか遡らない。`---` は非空行 → 走査が停止 → 履歴行の挿入位置が区切り線の**後ろ**になる。パーサは見出しでしか切らないので**エラーにならずに**前の ADR に属したまま表示され、契約 §6-2「エントリ末尾に 1 行を追記する」に違反する。
2. **`entry.raw` に後続の `---` が混入**。`raw` は次の見出しまでを取る → 区切りが前のエントリ末尾に付き、最後の 1 件だけ付かない非対称。`get adr` の消費者に漏れる。
3. **追加分だけ不揃い**。`buildAdrAddition` は `\n\n` 固定 → 新エントリの前に区切りが入らない。

加えて Markdown の罠: 非空行直後の `---` は水平線ではなく **setext H2**。区切りは必ず `\n\n---\n\n` の形にする必要がある。

`★ Insight ─────────────────────────────────────`
- `contentEndIndex`（本文の終端）と `endIndex`（エントリの終端）を分けている設計が効いている。前者は履歴行の挿入点、後者は `raw` の範囲。`---` は両方の境界条件に同時に触れるため、片方だけ直すと非対称が残る
- `## ADR 一覧` に書き込める口は `stage-adr` **だけ**。`stage-architecture` は `heading: "ADR 一覧"` を `adr_heading` で明示的に拒否し（理由: 採番・値域・履歴追記の迂回防止）、Edit/Write は `guard-docs.ts` の hook が deny する。つまり**既存 3 件の間に区切りを入れる手段が現状の CLI に存在しない** — これが本件最大の設計論点
- 契約凍結文書自身が節の区切りに `---` を多用している（§6 の前後）。リポジトリの文書スタイルとしては整合する要望
`─────────────────────────────────────────────────`

## 私が確定させた設計判断（4 件）

- **置き方は「エントリ間にだけ挟む」**。「各エントリの後」は節末に孤立した水平線が残る（`normalizeBody` は空白しか trim しない）。「各エントリの前」は `## ADR 一覧` 見出し直後に線が来て冗長。「間」は `adr.ts:664` の連結式を `${existing}\n\n---\n\n${rendered}` に変えるだけで自然に実現し、`renderAdrEntryLines`（区切りを含まない「1 件の中身」を返す）の責務とも食い違わない。
- **`---` は装飾に留め、パーサの境界トークンにしない**。刻み目を見出しのまま据えれば既存の分割ロジックと 4 本のテストが無傷で通る。境界トークン化すると ADR 本文中の水平線と衝突する。
- **`contentEndIndex` の遡り条件を「空行 **または** 区切り線」へ拡張**。これ 1 箇所で上記の破損 1 と 2 が同時に解ける。
- **`entry.raw` からは区切りを除く**。区切りは隣との関係であってエントリの内容ではない。除けば `get adr` の出力が対称になる。
