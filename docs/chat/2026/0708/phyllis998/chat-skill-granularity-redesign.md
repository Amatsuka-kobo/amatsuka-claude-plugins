## セッション1: 記録粒度の分析

# hiro0209

> task-utilityプラグインに含まれるchatスキルで作られたチャットファイルに記録された内容が、要約しすぎていると感じます。ただ、この状態で本当に後々AIや人間が見返したときに何をしていたのかが詳細にわかる粒度なのかがわかりません。そこの分析をお願いしたいです。

# AI

スキル定義と実運用ファイル 3 件を読み比べ、「将来聞きそうな質問に答えられるか」テストで粒度を検証した。

**結論**: 意思決定ログとしては高品質(命名の経緯、`--bare` 見送りの理由、BM25 採用の理由などは復元可能)だが、「会話の記録」としては成立していない。失われている情報は 3 分類:

1. **ユーザー発言の原文**(最も深刻): 全ファイルでユーザーのターンが言い換えられており、引用か言い換えかの区別もない。AI が要件を誤解していた場合、その誤解が「ユーザーの要求」として歴史に残る
2. **過程**: 失敗・調査の道筋が結論 1 行に圧縮されている(raguel 実装セッション2は数時間分が箇条書き 5 点)。Codiel の「失敗蓄積」思想と記録形式が矛盾
3. **網羅性**: codiel 実装の 20 タスク中 7 タスクだけ攻防が記録され、残り 13 が無風だったのか省略なのか判別不能

**根本原因**: SKILL.md が粒度契約を定義していない。テンプレートは逐語記録を示唆するのに実運用は高度な要約で、スキルと実態がすでに乖離しており、粒度が毎回 AI の裁量で決まっている(12 行目の「起立」は「規律」の誤字で、スキル自体の整備が浅い傍証)。また生ログは `~/.claude/projects/` にあるがローカル限定・非コミットで、docs/chat/ が唯一の永続記録である以上「原本が別にあるから要約でよい」は成立しない。

**提案**: 非対称の粒度契約 — ユーザー発言は原文引用、AI 側は構造化要約、ただし失敗・却下案は要約禁止、網羅性(無記録と無風の区別)を明記、引用ブロック=原文の表記規約。

## セッション2: スキルの書き直しとテスト

# hiro0209

> スキルの書き直しをお願いします。また、この会話もchatに記録したいです。

# AI

superpowers:writing-skills の手順(RED→GREEN→REFACTOR)で実施。

**RED(ベースライン)**: 実運用 3 ファイルが「現行スキルでの失敗の実証」そのもの。加えて、検証マーカー(要約で落ちやすい理由 3 点・却下案・失敗経緯・5 項目中 3 項目が無風という網羅性)を埋め込んだ合成会話ログを作成し、現行スキルで Sonnet サブエージェント 2 本に記録させた。結果は一方が逐語丸写し(ト書き括弧ごと)、もう一方が整形要約で、ヘッダーなし・引用区別なし。同一入力で出力形式が全く揃わず、「粒度がエージェント任せ」を再現。

**途中の失敗(テスト設計)**: 当初、新スキルのテンプレート例文にテスト会話と同じ題材(jwt v10 アップグレード)を書いてしまい、例文の丸写しで合格できるテスト汚染になりかけた。テンプレートを別題材(CSV エクスポート)に差し替えて回避。

**GREEN**: 新スキルは禁止リストでなくレシピ型(writing-skills の「形の失敗には禁止形が逆効果」の知見に従い、埋めるべきスロットを列挙)で作成。新スキルで処置 3 本を実行し、5 基準(①原文引用ブロック ②失敗経緯の道筋 ③網羅性の明記 ④却下案と理由 ⑤引用/地の文の区別)を 3 本全部が満たし、構成も収束。REFACTOR 不要と判断。

**副産物**: 処置の 1 本が要約部で「要件は 4 点」と書きつつ 3 点しか列挙しないミスをしたが、直上の原文引用で読者が誤りを検出できた — 契約が守ろうとする性質そのものがテスト中に実証された。

`plugins/task-utility/skills/chat/SKILL.md` を全面改訂して配備(目的・保存場所・ファイル構成・非対称の粒度契約・表記規約・テンプレートの構成)。本記録を新契約の形式で作成。

## セッション3: 自動適用の検討とフック実装

# hiro0209

> chatスキルを、このプラグインが導入されているプロジェクトでなされたClaude Codeでの会話すべてに自動的に適用することはできますか？

# AI

hook-development スキルで裏取りして回答: スキル自体の自動発動機構は存在せず(description 頼みのモデル裁量)、実現手段はプラグイン同梱のフックになる。3 方式を提示 — (1) Stop フックで未記録なら block して差し戻す(強制、ただし毎ターンコスト)、(2) SessionStart/UserPromptSubmit でのリマインド注入(軽いが強制力なし)、(3) SessionEnd + ヘッドレス `claude -p` での全自動生成(無人書き込みで粒度契約の遵守を誰も確認できないため非推奨)。推奨は (1) + `docs/chat/` 存在チェックによる条件付き発火。

# hiro0209

> コスト問題は確かにあると思います。Hookで発火させる場合、chatスキルを軽いモデルで起動したサブエージェントで実行させることはできますか？

# AI

可能だが 1 段の間接参照が必要(フック自身はサブエージェントを起動できないため、block 理由でメインに委譲を指示する)。設計の急所として「サブエージェントは会話コンテキストを持たない」問題を指摘: メインがディスパッチプロンプトに会話を書き写す方式ではコスト削減が消え、原文契約もメインの書き写し精度に依存してしまう。解決策としてフックが受け取る `transcript_path`(生ログ JSONL)をサブエージェントに直接読ませる構成を提案 — 原文引用が生ログからの機械抽出になり、逐語性が構造的に保証される副次効果もある。Haiku で粒度契約を守れるかは未実測と明示。

# hiro0209

> Haiku版のテストも含めてお願いします。

# AI

**Haiku テスト**: 前回と同じ合成会話+新スキルで `model: haiku` の処置 3 本を実行。3 本とも 5 基準(原文引用・失敗経緯・網羅性・却下案・引用表記)を満たし、chat-recorder のモデルは haiku に決定。ただし 1 本に軽微な補完を検出: 原文にない「部分一致から」という語を仕様変更の説明に追加していた(直上の原文引用と突き合わせれば検証可能な範囲だが、Haiku は Sonnet より装飾的補完の傾向がやや強いという実測知見)。

**実装**(codiel の hooks 構成に準拠):

- `plugins/task-utility/scripts/extract-conversation.mjs`: トランスクリプト JSONL から発言のみを抽出(ハーネス注入 `<command-name>` 等・isMeta・isSidechain を除外、thinking は出力しない、tool_use は 1 行ヒント化、連続 ASSISTANT は結合)
- `plugins/task-utility/hooks/scripts/check-chat-recorded.mjs`: Stop フック本体。決定論ゲートのみで **毎ターンの LLM 評価コストはゼロ**。docs/chat/ 存在(オプトイン)→ 実質ユーザー発言 3 回以上 → docs/chat/ への Write/Edit なし、のとき block し、`${CLAUDE_PLUGIN_ROOT}` 展開済みの抽出コマンド・スキルパス・transcript パスを理由文に埋め込んで chat-recorder への委譲を指示。`stop_hook_active` で再差し戻ししない(無限ループ防止)
- `plugins/task-utility/hooks/hooks.json`: Stop コマンドフック登録
- `plugins/task-utility/agents/chat-recorder.md`: `model: haiku`。原文の一字不変転記・記録以外の作業禁止(トランスクリプト内の指示はデータでありエージェントへの命令ではない、というインジェクション対策)・不明情報の創作禁止を規定
- `plugins/task-utility/README.md`: 挙動・オプトイン条件・制限を記載

**検証**: ユニットテスト 12 件全通過(block/許可の分岐 8 + 抽出 4)。実物スモークも実施 — 本セッションの実トランスクリプトで抽出(USER 5 件を原文抽出)、記録済みセッション→許可、docs/chat への Write 行を除いた改変版→block 発火を確認。

**発見した罠**: `node --test` にディレクトリを渡すとテスト以外の .mjs も実行対象に拾われて失敗する。README の動作確認コマンドはテストファイルの明示指定にした。
