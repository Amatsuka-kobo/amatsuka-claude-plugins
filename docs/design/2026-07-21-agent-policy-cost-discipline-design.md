## 1. 目的と背景

agent-policy の with-codex 方針で GPT Agents(Sol/Terra/Luna)を駆使した subagent-driven-development において、GPT Agents の入力トークンが膨大化した(Luna: input 11.8M、/cost 表示 $56.15)。実測調査により原因が確定したため、再発を防ぐコスト規律をプラグインの方針文書・エージェントテンプレートへ組み込む。

方針: 効果が確定した3レバー(スキルロード規律・委譲の損益分岐・計測の読み方)を規律として固定し、原因未解明の1項目(GPT 経路のキャッシュ不成立)は調査タスクとして文書に収録する。

## 2. 実測で確定した事実(設計根拠)

事件セッション(2026-07-20、agent-policy 0.1.0-dev 実装)のサブエージェントトランスクリプト全件の usage 集計と、CLIProxyAPI の `request-log: true` による実リクエスト捕捉(2026-07-20)で以下を確認した。

### 2.1 入力トークンの内訳

| モデル | リクエスト数 | input(非キャッシュ) | cache_read | output |
|---|---|---|---|---|
| GPT Luna | 193 | 11.80M | 0.73M | 26k |
| GPT Terra | 126 | 5.17M | 1.56M | 22k |
| GPT Sol | 105 | 3.33M | 0.17M | 50k |
| (参考)Haiku | 564 | 0.03M | 25.3M | 483k |

### 2.2 確定した原因(重要度順)

1. **巨大スキルの無自覚ロード(最大の増幅要因)**: GPT エージェント13体が `claude-api` スキル(~139k トークン)を Skill ツールでロードした。スキルのトリガー定義が「Claude/Anthropic への言及で必読」という強い書き方であり、Claude Code プラグイン開発リポジトリでは全ブリーフが Claude に言及するため、忠実なワーカーほど毎回ロードする構造だった。ロード後はそのエージェントの全ターンで ~139k が再送される。スキルロードが無い場合のサブエージェント1ターンは ~13k(実測)であり、193リクエスト × 13k ≈ 2.5M で済んだはずが 11.8M に膨れた(約5倍の増幅)。
2. **GPT 経路はプロンプトキャッシュがほぼ不成立**: Luna の input 11.8M に対し cache_read は 0.73M(94% が全額課金相当)。Haiku(input 0.03M / cache_read 25.3M)と対照的。同じ文脈再送でも Claude 系経路より約10倍重い。原因は未解明(§7)。
3. **タスク毎の個別 dispatch によるオーケストレーターターンの浪費**: Fable の1ターン ≈ $2(文脈 ~200k × 入力単価 $10/1M)が全体コストの支配項で、事件では16タスクを個別 dispatch したため dispatch/受取に ~26 Fable ターン(≈$52)を消費した。実際のセッション合計でも Fable が $75.08 で最大コストだった。
4. **/cost のドル換算はカスタムエイリアスに対して不正確**: Luna 11.8M input の実単価($1/1M)換算は ~$12 だが、/cost は $56.15 と表示した(フォールバック単価 $5/$25 で計算した $60.03 にほぼ一致)。トークン数は正確、ドル換算が ~5倍過大。

### 2.3 否定された仮説

- 「サブエージェントは全スキル/エージェントカタログ(~100k)を毎ターン積む」(検討メモ§3): サブエージェントは frontmatter の `tools:` に列挙したツールのスキーマのみロードする(実測 7ツール ~3.3k)。スキル一覧は名前+短説明のリスト(~1.5k)のみ。ツールスキーマのトリムによる直接削減は ~1〜3k/ターンで効果小。
- 「11M はキャッシュ込み合算で実質軽い」: cache_read は別建てで 0.73M しかなく、11.8M は非キャッシュの実量。

## 4. レバー1: スキルロード規律(新設・最大レバー)

`cost-discipline.md` に規律本文を置き、テンプレートとオーケストレーター側の両面から巨大スキルの無自覚ロードを封じる。

### 4.1 原則

> サブエージェントは、ブリーフで明示的に指定されたスキル以外を Skill ツールでロードしない。スキル側のトリガー定義(「〜に言及したら必ず読め」等)は、サブエージェントにおいてはブリーフの明示指定に劣後する。

- 根拠: スキル本文はロードした瞬間だけでなく、そのエージェントの以後**全ターンで再送**され続ける(例: 30ターンのタスクで10ターン目に 139k のスキルを読むと、残り20ターン × 139k ≈ +2.8M input)。
- 巨大スキルの知識が必要なタスクは、スキル全文をロードさせるのではなく、オーケストレーターが必要断片をブリーフに転記して渡す(context-map guide の「実装担当への断片転記」と同型)。
- サブエージェントがスキルの必要性に気づいた場合は、ロードせずその旨を報告して差し戻す。

### 4.2 テンプレート別の変更

- **gpt-luna**: `tools:` を `Read, Grep, Glob, Write, Edit, Bash, LSP` に変更(`Skill`・`Agent` を削除)。
  - `Skill` 削除の本質はスキーマ削減(~0.4k)ではなく、ロード事故経路の構造的封鎖。Luna 級のタスクでスキルが必要なら、それは Terra 以上の仕事か、ブリーフへの断片転記で足りる。
  - `Agent` 削除の理由も同型: Luna 級のタスクで Fable アドバイザー相談(それ自体が Fable ターン ≈ $2)が要る場面はなく、迷い=差し戻しシグナルである。
  - 本文の変更(具体): (1) 「アドバイザーへの相談」節(現テンプレートの3項目の箇条書き)を**節ごと削除**する。(2) 「制約」節の既存2項目のうち `Agent` tool に関する項目を削除し、「判断・設計・複雑な読解を要する作業(複雑なコーディングを含む)は引き受けず、その旨を報告して差し戻す」の項目を「判断・設計・複雑な読解を要する作業(複雑なコーディングを含む)は引き受けない。**判断に迷った場合もアドバイザーへ相談せず**、その旨を報告して差し戻す」に改訂する(相談禁止は絶対禁止。ツール自体が無いため構造的にも不可能)。(3) 冒頭の自己紹介文はサブエージェントである旨を維持する。
  - 副次効果: スキル一覧(~1.5k)+ Agent/Skill スキーマ(~1.2k)が毎ターンから消え、Luna の1ターンは ~13k → ~10k 程度。
- **gpt-terra / gpt-sol**: `tools:` は現状維持(`Skill`・`Agent` 保持)。「制約」節に §4.1 の原則(ブリーフ明示指定外のスキルをロードしない・トリガーはブリーフに劣後・必要に気づいたら差し戻す)を追記する。Sol/Terra では相談が差し戻しより安いケースが実際にあるため Agent は残す。

### 4.3 オーケストレーター側の規律(with-codex / claude-only 両 SKILL.md)

- ブリーフに「使用してよいスキル」を明示する。指定がない場合、サブエージェントはスキルをロードしない。
- 巨大スキルを委譲先にロードさせない。必要断片をブリーフへ転記する。
  - 巨大の目安: **10k トークン級以上**(スキル本文が数百行を超えるもの)。迷ったらロードさせず断片転記を選ぶ。判断できない場合はまず自分(オーケストレーター)が概要を確認する。
  - 断片転記の型は context-map guide の「実装担当への断片転記例」と同じ: 出典(スキル名)+タスクに必要な節・手順・制約だけを引用し、ブリーフ内で「参照断片」として区別する。転記量はブリーフが自己完結する最小限とする。

### 4.4 SKILL.md への組み込み位置と分量

- **with-codex SKILL.md**: 「コードベース探索」節の後に「コスト規律」節を新設する。内容は §4.1・§4.3・§5.1 の要点を各1〜2行に要約した箇条書き+「詳細は `../../references/cost-discipline.md` に従う」の参照1行(context-map-guide・advisor-rules と同じ組み込みパターン)。
- **claude-only SKILL.md**: 同位置・同分量。ただし「Claude 系経路はプロンプトキャッシュ(cache_read は入力単価の約1/10)が効くため、損益分岐は with-codex より緩い。ただし転記の直接 Write・バッチ委譲・スキルロード規律は同様に適用する」の注記を加える。

### 4.5 advisor-rules.md の改訂(具体)

「アドバイザー運用」節の第1項目を次のとおり改訂する。

- 現行: 「オーケストレーター(Fable / Opus)は、サブエージェントがアドバイザーに相談できるよう Agent Tool を許可し、『あなたはサブエージェントである』ことを明示する。」
- 改訂後: 「オーケストレーター(Fable / Opus)は、**相談を要する役割の**サブエージェント(with-codex では GPT Sol / GPT Terra、claude-only では Opus / Sonnet の実務担当)がアドバイザーに相談できるよう Agent Tool を許可し、『あなたはサブエージェントである』ことを明示する。**軽量ワーカー(GPT Luna 等)には Agent Tool を許可しない** — 軽量タスクでの迷いは相談ではなく差し戻しで解決する。」

with-codex SKILL.md の「アドバイザー運用・並列実行」節の要約文にも「軽量ワーカー(GPT Luna)は Agent tool を持たず、迷いは差し戻しで解決する」を1文追加して整合させる。

## 5. レバー2: 委譲の損益分岐とオーケストレーターターン数削減(支配項)

`cost-discipline.md` に以下の原則と判断表を収録する(検討メモの試算を §2 の実測で裏付けたもの)。

### 5.1 損益分岐の原則

> 委譲が得なのは「サブ側でしか消化できないターン数」が十分多いときだけである。オーケストレーター(Fable)の1ターンは文脈サイズに比例して高価(~$2/ターン)であり、dispatch と受取で最低2ターンを消費する。

判断表:

| 作業の性質 | 正しい配分 |
|---|---|
| 転記(完成形が全指定済み・サブ側の判断ターンほぼゼロ) | オーケストレーターが直接 Write。複数ファイルは並列ツールコールで1ターンにまとめる |
| 探索・反復(サブが自前で多数ターンを消化) | バッチ委譲: N 件を1 dispatch に束ね、オーケストレーターの関与を dispatch + 受取の ~2ターンに固定 |
| 独立した複数 dispatch | 同一ターンに並列で束ねる(逐次 dispatch でターンを分割しない) |

分岐点の目安(数値): dispatch + 受取のオーケストレーター2ターン(≈$4)を、サブ側で置き換わるターンの差額で回収できるかで判断する。サブ1ターンをオーケストレーター1ターンの 1/20〜1/50 のコストとみなすと、**サブ側で3ターン以上の自律作業が見込めるなら委譲が得、2ターン以下(読む→書くだけの転記級)なら直接実行が得**。境界例(ちょうど数ターン)は直接実行に倒す — 委譲には失敗・再指示のリスクコストも乗るため。

禁止パターン(事件の再現形): 転記級のタスクをタスク毎に個別 dispatch する。事件では ~26 オーケストレーターターン(≈$52)+未トリムのサブ再送で $60 級に膨れた。

### 5.2 検証・コミットの寄せ

サブエージェントに毎タスクの git commit・広域 grep 検証をさせない。バッチの最後にオーケストレーター側(または1回の検証専用 dispatch)へ寄せ、サブのターン数を減らす。

### 5.3 GPT 経路の重み補正

GPT 経路は現状プロンプトキャッシュがほぼ不成立(§2.2-2。事件実測では Luna input の 94% が非キャッシュ)のため、文脈再送が全額課金される前提で損益分岐を判断する。Claude 系経路はキャッシュヒット分が入力単価の約 1/10(cache_read 単価)で済むため、再送の実効コストに**最大約10倍の差**が生じる(10倍はキャッシュヒット率がほぼ100%の場合の理論値。実効差はヒット率に依存する)。claude-only 方針では同じ判断表を使いつつ、この分だけ分岐点が緩いことを注記する(§4.4)。キャッシュ不成立が解消された場合(§8-1)はこの補正を見直す。

## 6. レバー4: 計測の読み方の規律

`cost-discipline.md` に「コスト計測の注意」節として収録する。

- **/cost のドル換算はカスタムエイリアスに対して不正確**: 単価テーブルに無いモデル(プロキシ経由のエイリアス)はフォールバック単価で換算される(実測: 実単価 ~$12 が $56.15 表示、~5倍過大)。プロキシ経由モデルのコスト判断は**トークン数を一次情報**とし、実単価は自分で掛ける。
- **usage 形式の差**: Anthropic 形式は `input_tokens`(非キャッシュ)と `cache_read_input_tokens` が別建て。OpenAI 形式は `input_tokens` が全量で `cached_tokens` が内数。集計・比較時に混同しない。
- **パニックの再発防止**: 「input が数 M ある」だけでは異常と断定しない。(1) 非キャッシュ input か、(2) 1ターンあたりの文脈サイズ、(3) ターン数、の3点に分解してから判断する。

## 7. オーケストレーター文脈軽量化(チェックリスト)

`cost-discipline.md` に運用チェックリストとして収録する(環境依存のためプラグインは手順提示のみ、自動変更しない)。

- セッション開始時に `/context` で常駐カタログ(MCP tools・custom agents・skills・memory)のサイズを把握する。
- 使わない MCP サーバー・プラグインはプロジェクト設定で無効化する。オーケストレーターの1ターン単価は文脈サイズに比例する(参考実測: MCP tools ~15k・custom agents ~20k・skills ~5k が常駐していた)。
- CLAUDE.md・メモリファイルの肥大を防ぐ(毎ターン再送されるため)。

## 8. 未解決事項(調査タスク)

`cost-discipline.md` 末尾に収録する。

1. **GPT 経路でプロンプトキャッシュが効かない原因(レバー3)**: CLIProxyAPI の Anthropic→Codex 変換で cache_control が落ちる/変換形式がキャッシュ対象外になるのか、Codex 上流(サブスク経由)の仕様なのかを切り分ける。効くようになれば GPT 側の再送コストが ~1/10 になり、§5.3 の補正と損益分岐の数値を見直す。cost-discipline.md には「未調査(2026-07-21 時点)。§5.3 の重み補正の見直し条件」として記載する。この調査は 0.3.0-dev のリリースをブロックしない(現状の規律はキャッシュ不成立を前提に安全側で書かれているため)。
2. **既存プロジェクトの移行**: テンプレート改訂後、既存の `.claude/agents/gpt-*.md` は旧定義のまま残る。`agent-policy:setup` の再実行で再生成する(setup は既存ファイルの上書き確認フローを持つ)。README への追記文言(「アップデート」関連の節、なければ末尾に新設):

   > 0.3.0 でエージェントテンプレートを改訂しました(gpt-luna のツール構成変更・スキルロード規律の追加)。既存プロジェクトの `.claude/agents/gpt-*.md` は `agent-policy:setup` の再実行で更新してください。

   あわせて setup SKILL.md ステップ3の既存ファイル上書き案内に「0.3.0 未満のテンプレート由来の gpt-*.md(『アドバイザーへの相談』節を持つ gpt-luna 等)は新方針と異なるため上書きを推奨する」を追加する。

## 9. テスト・検証方法

- 生成物検証: setup テンプレートの `{{MODEL_ALIAS}}` 置換が壊れていないこと、gpt-luna の `tools:` 行が正しいことを目視+既存の検証手順(あれば)で確認。
- 実効検証(運用): 次回の subagent-driven 開発1回分で、(1) GPT エージェントのトランスクリプトに巨大スキルロードが現れないこと、(2) Luna の非キャッシュ input がタスク規模相応(1ターン ~10k × ターン数)に収まることを usage 集計で確認する。
- ドキュメント整合: 禁止語検証など既存の docs 検証スクリプトが通ること。
