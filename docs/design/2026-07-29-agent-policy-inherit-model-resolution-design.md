## 1. 目的と背景

両方針スキルの最終節「役割 Agents を持つプラグインとの併用」は、対象を「役割プロンプトを持つワークフロープラグイン(例: Codiel)」に限定している。本設計はこの限定を外し、**`model` 未指定または `model: inherit` の Agents 定義全般**を対象とする規律へ拡張する。

### 1-1. 現行規律が防いでいる事故の真因

現行節が防ぐのは表層的には「Codiel の役割 Agents を素のまま起動すると実装フェーズが担当表どおりの帯で走らない」ことである。しかし真因は 1 層下にある。

対象の Agents が `inherit` であること。`inherit` の Agents は委譲元のモデルで走る。委譲元であるオーケストレーターは担当表上つねに Fable / Opus すなわち最上位帯にいる。したがって `inherit` の Agents へ委譲するたび、担当表で下位帯に割り当てたはずの作業が黙って最上位帯で実行される。**担当表とコスト規律が同時に空文化する。**

真因が「`inherit` であること」なら、プラグイン由来かどうか・役割プロンプトを持つかどうかは無関係である。現行の限定は真因の粒度と一致していない。

### 1-2. 拡張で新たに対象へ入るもの

| 対象 | 現行 | 拡張後 |
| --- | --- | --- |
| プラグインの役割 Agents(`inherit`) | 対象 | 対象 |
| プラグインの Agents(`model` 行なし) | 文言上は対象外 | 対象 |
| プロジェクト `.claude/agents/` の自作 Agents | 対象外 | 対象 |
| ユーザーレベル `~/.claude/agents/` の Agents | 対象外 | 対象 |
| ビルトイン Agents(`Explore` / `Plan` / `general-purpose`) | 対象外 | 対象 |
| `model` が pin 済みの Agents | 無言 | 対象外(明記する) |

実環境(2026-07-29 時点のローカル調査)では、インストール済みプラグインの Agents に `inherit` が多数存在し(`claude-security` の `scan-researcher` / `patch-generator` / `patch-verifier`、`plugin-dev` の `skill-reviewer` / `plugin-validator`、`hookify` の `conversation-analyzer`)、`skill-creator` 配下の 3 体は `model` 行そのものを持たない。「未指定」は仮想の事例ではない。

実務上の影響量では、ビルトイン `Explore` がオーケストレーターのモデルで走る事象が最も高頻度である。

## 2. 前提となる確定事実(制約)

### 2-1. `model` 未指定と `model: inherit` は同義

公式仕様上、frontmatter `model` を省略した場合の既定値は `inherit` である。したがって「未指定 or inherit」は 2 つの条件ではなく、実体は 1 つの状態「実行モデルが委譲元に従う」である。

**帰結:** 規律本文で両者を別扱いしない。判定は「具体的なモデルが書かれているか否か」の二値で足りる。

### 2-2. モデル解決の優先順序

`CLAUDE_CODE_SUBAGENT_MODEL` 環境変数 > dispatch 時 `model` パラメータ > 定義 frontmatter `model` > メイン会話のモデル。

**帰結:** 現行規律の「dispatch 時上書き」は第 2 順位を使っており、frontmatter の `inherit` を上書きできる。この手段は拡張後も有効である。

### 2-3. dispatch の `model` は enum に制限される

README §設計上の確定事実(2026-07-20 実測)のとおり、dispatch 時 `model` 上書きは `sonnet` / `opus` / `haiku` / `fable` の enum に制限され、カスタムエイリアス(`claude-gpt-5-6-*`)は実行前に拒否される。

**帰結:** GPT 帯へ寄せる手段は dispatch 上書きではなく「定義本文を依頼文へ同梱して GPT エージェントを起動する」方式に限られる。現行規律の方式を拡張後も維持する。

### 2-4. ビルトイン Agents は定義ファイルを持たない

`Explore` / `Plan` / `general-purpose` はファイルとして存在せず、frontmatter を読む手段がない。`Explore` の実装は inherit 相当(Claude API では Opus 上限)である。

**帰結:** ビルトインは判定の例外ではなく、**`inherit` として扱う**と規定することで判定が決定的になる。あわせて、これらには依頼文へ同梱できる本文が存在しないため、GPT 帯に相当する場合の扱いを別に定める必要がある(§3-4)。

## 3. 設計判断

### 3-1. 判定タイミング: 初回委譲時に定義を読む

採用案: **セッションでその Agents へ初めて委譲するとき、定義ファイルの frontmatter `model` を確認する。**

不採用案と理由:

| 案 | 不採用の理由 |
| --- | --- |
| 常に dispatch で上書きし、例外だけ確認 | ファイルを読まずに成立しコストも低いが、pin 済み Agents に対して上書きが定義者の意図を破る。§3-2 の決定と衝突する |
| with-codex だけ定義を読む | with-codex は本文同梱のためどのみち定義を読む。claude-only だけ規律の粒度を変えると、2 スキル間で判定手順が非対称になり保守が割れる |

「セッションで初めて」という限定がコスト規律との衝突を抑える。同一 Agents への 2 回目以降の委譲で再読は不要である。判定結果のキャッシュ手順は規律に書かない — この限定が既に再読を抑止しており、手順を増やすと本文が肥大する。

### 3-2. pin 済み Agents は対象外

採用案: **`model` が具体的なモデルに指定されている Agents は、そのまま起動する。担当表による上書きをしない。**

`pin` は定義者による「このプロンプトはこのモデルで動くよう作った」という意図表明である。担当表で上書きすると、他プラグインが前提としたモデル特性(例: haiku 向けに書かれた短いプロンプト)を壊しうる。実環境には担当表と食い違う pin が実在するが(`claude-security:explore` = `sonnet`、`codex:codex-rescue` = `sonnet`)、食い違いの是正より他プラグインの動作保証を優先する。

この決定は §3-1 と組み合わせることで判定を完全に決定的にする: **定義ファイルがある → frontmatter を見る / ない → `inherit` として扱う。** 判定に迷う余地が残らない。

### 3-3. ビルトインを対象に含める

採用案: **ビルトイン Agents を `inherit` として扱い、規律の対象に含める。**

真因(§1-1)がビルトインにもそのまま当てはまるため、除外する根拠がない。実務頻度は最大である。

**帰結として節の性格が変わる。** 対象が「特定プラグインを使うとき」から「すべての dispatch」へ広がるため、この節はもはや併用ルールではなく**全 dispatch の前提チェック**である。これが §4-1 の構成変更(節タイトルと配置)の根拠になる。

### 3-4. GPT 帯 × ビルトイン: ビルトインを使わず直接委譲

採用案: **担当帯が GPT に相当する作業をビルトイン Agents へ投げない。担当 GPT エージェントへ直接委譲する。**

不採用案と理由:

| 案 | 不採用の理由 |
| --- | --- |
| ビルトインを使い `model` を落とす | ビルトインの探索最適化プロンプトを保てるが、担当表と部分的に不一致になる。with-codex の探索実働は GPT 帯という担当表の記述が空文化する |
| 作業種別で使い分ける | 最も精密だが規律が 1 段複雑になる。判断コストに見合う差が示せない |

`Explore` の探索最適化プロンプトを失うが、`context-map-guide.md` による探索手順の規定が既にその役割を担っている。

この決定により、with-codex の GPT 帯セクションの分岐が「本文がある/ない」ではなく「委譲先を替える/替えない」で閉じる。本文なしの例外処理が不要になる。

### 4-2. 記述方針

SKILL.md は AI 向けであり、人間が読むことを想定しない。**規律の実行に不要な根拠・引用・補足を本文に置かない。**

本文から除外し、他所へ回す/削除するもの:

| 内容 | 行き先 |
| --- | --- |
| `inherit` が担当表を空文化する真因の説明 | 本設計書 §1-1 |
| Codiel `codiel-implementer-*` の具体例 | README(併用例として記載済み) |
| 定義ファイルの探索パス 3 種の列挙 | 削除(標準知識) |
| GPT 利用不可の条件の列挙 | 削除(既存節「GPT が使えない場合のフォールバック」が定義済み) |
| dispatch enum 制限が本文同梱方式の根拠であること | README §設計上の確定事実(記載済み) |

一方、**削ってはならない短句**がある: 「委譲元と同じ帯でも明示する」。短いが、これが無いと「同じ帯だから省略してよい」という抜け道が残る。

### 4-3. `with-codex/SKILL.md` 新節本文(確定)

以下のコードフェンスは表記上の引用であり、フェンス自体は SKILL.md に含めない。中身をそのまま本文として使う。既存節と同じ書式(`##` / `###` 見出し、`-` 箇条書き)で揃っており、追加の整形は不要。

現行 64〜77 行目の節全体(見出し・導入 3 行・`###` サブ節 2 つ)を削除し、この新節を 35 行目(「モデル別役割」の箇条書き末尾)と 37 行目(`## コードベース探索`)の間へ挿入する。

````markdown
## 委譲先の実行モデルの確定

すべての dispatch の前に、委譲先の実行モデルを確定させること。

- セッションで初めて委譲する Agents は、定義ファイルの frontmatter `model` を確認する。原本を読み、複製・改変版を作らない。
- ビルトイン Agents(`Explore` / `Plan` / `general-purpose` 等)は `inherit` として扱う。
- `model` が具体的なモデルに指定されている Agents は、そのまま起動する。担当表で上書きしない。
- `model` 未指定・`inherit` の Agents は、作業種別を担当表に照らして実行帯を決め、以下に従う。

### 実行帯が Claude モデルの場合

dispatch 時の `model` 上書きで実行帯を明示する。委譲元と同じ帯でも明示する。

### 実行帯が GPT モデルの場合

- 定義ファイルを持つ Agents: 定義本文(frontmatter を除く)を担当 GPT エージェントへの依頼文に役割定義として同梱して dispatch する。`model` 上書きは使わない。依頼文に「この tools のみ使用」と明記する。
- ビルトイン Agents: 使わず、担当 GPT エージェントへ直接委譲する。
- GPT が利用不可なら、対象 Agents をそのまま起動する。
````
