# forerunner 設計書

- 作成日: 2026-07-21
- ステータス: 設計(Haiku レビュー前)
- 対象プラグイン: `plugins/forerunner/`(新規、0.1.0-dev)

---

## 1. 目的と背景

Claude Code のオーケストレーション作業では、設計提示・計画承認・AskUserQuestion・スペックレビューなどで**ユーザー入力を待つブロッキング区間**が頻繁に発生する。この間 AI 側の作業は完全に停止しており、承認後にほぼ確実に行う探索・調査(読み取り主体の作業)は承認が下りてから直列に走る。結果として、人間から見た「承認してから動き出すまでの待ち時間」が長くなる。

forerunner は、ユーザー入力待ちに入る**直前**に「承認後に高確率で必要になる読み取り主体の作業」を予測し、バックグラウンドサブエージェントで**投機的に先行実行**する。ユーザーの回答が届いた時点で成果を回収して即利用することで、承認後の立ち上がりを短縮する。CPU の投機実行(speculative execution)のワークフロー版である。

### 制約(リポジトリ要件)

- Anthropic API を使用しない。Claude Code の機構(Agent tool のバックグラウンド実行)に閉じる
- 先行実行は**読み取り主体のみ**。リポジトリのコード・設定への書き込みは行わず、書き込みは成果物置き場 `.forerunner/` 配下に限定する
- 単体で導入して動作する(agent-policy 等の他プラグインへの依存なし)。ただし併用時はそれらのコスト規律と整合する

## 2. 動作モデル(予測 → 先行 → 回収)

### 2.1 予測(predict)

メインエージェントは、ユーザー入力待ちに入るツール呼び出し(AskUserQuestion / ExitPlanMode)またはレビュー依頼メッセージを発する**同一ターン内の直前**に以下を行う:

1. 待ちの種別を判定する(設計承認待ち / 質問回答待ち / 計画・スペックレビュー待ち)
2. 現在の文脈から「承認後に必要になる作業」を 0〜N 件予測する
3. 各予測に**有効条件**(どの回答・どの分岐が来たらこの成果が有効か)を付与する。有効条件は自然言語 1 文で記述し、回収時の合致判定はメインエージェントが文脈で行う(機械判定はしない)

予測の優先基準:

- **no-regret 優先**: どの回答が来ても必要になる作業(影響範囲調査、対象ファイルの現状把握、テストケースの洗い出し等)を最優先する
- 回答分岐に依存する作業は、確度が高い分岐(推奨案を提示している場合はその案)のみ投機する
- 予測できる作業がなければ何もしない(0 件は正常。無理に投機しない)

### 2.2 先行(run ahead)

予測した作業ごとにバックグラウンドサブエージェント(`run_in_background: true`)を起動してから、ユーザーへの質問・レビュー依頼を行う。サブエージェントはユーザーが考えている間も走り続け、完了通知は次ターン以降に届く。サブエージェントはメインセッションのライフサイクルに従属する(セッション終了で停止する)ため、成果は常に `result.md` へ書き終えた分だけが有効となる。

dispatch ブリーフの必須事項:

- 読み取り主体であること(コード・設定への書き込み禁止)を明記
- 成果の出力先(`.forerunner/<task-id>/result.md`)を指定
- スキルをロードしないことを明記(コスト規律)

### 2.3 回収(harvest)

ユーザーの回答が届いたターンの冒頭で:

1. `.forerunner/manifest.md` を確認する
2. 有効条件が実際の回答に**合致した**成果を読み込み、以降の作業に即利用する
3. 合致しなかった成果(予測ミス)は読み込まずに破棄扱いとし、manifest 上で `discarded` にマークする
4. まだ実行中のタスクは、有効条件に合致するなら完了を待って利用してよいし、待たずに本作業を進めて後から合流させてもよい(オーケストレーターの判断)

## 3. コンポーネント構成

| コンポーネント | 種別 | 役割 |
|---|---|---|
| `skills/forerunner/SKILL.md` | スキル | 予測基準・ガードレール・ブリーフ雛形・回収手順の定義。メインエージェントがユーザー待ちに入る前に参照する本体 |
| `hooks/hooks.json` + 回収リマインダー | UserPromptSubmit フック | `.forerunner/manifest.md` に未回収(`running`/`done`)エントリがある場合のみ、フックの stdout(additionalContext としてコンテキストに注入される)へ「回収プロトコルを実行せよ」というリマインダーを出力する。manifest が無い・全件回収済みの場合は何も出力しない(ノイズゼロ)。判定はシェルスクリプトの grep で行い、LLM は使わない |
| 回収プロトコル(manifest 仕様) | 規約 | `.forerunner/manifest.md` のエントリ形式と状態遷移の定義(スキル内に記載) |

### 3.1 manifest 仕様

`.forerunner/manifest.md`(プロジェクトルート直下の `.forerunner/` 内。初回 dispatch 時にメインエージェントが作成する)に 1 タスク 1 エントリのテーブルで記録する:

| フィールド | 内容 |
|---|---|
| task-id | `fr-<連番>` |
| 予測内容 | 何を先行実行しているかの 1 行要約 |
| 有効条件 | どの回答・分岐が来たら有効か(自然言語 1 文) |
| 状態 | 下記の状態遷移に従う |
| 成果パス | `.forerunner/<task-id>/result.md` |

状態遷移(書き込みは常にメインエージェントのみが行い、競合は発生させない):

- `running`(dispatch 時に記録)→ `done`(完了通知の受領時)→ `harvested`(成果を利用)/ `discarded`(有効条件に不合致で破棄)
- `running` → `failed`(サブエージェントの失敗)
- 先行サブエージェントは manifest に触れず、成果を `result.md` に書くのみ。状態更新はメインエージェントが完了通知・回収の各時点で行う

### 3.2 成果物と git

- `.forerunner/` はセッションローカルな作業領域であり、git 管理しない(プラグインの README で `.gitignore` への追加を案内する)

## 4. ガードレール

- **読み取り主体のみ**: 先行サブエージェントの書き込みは `.forerunner/` 配下のみ。実装・修正の先行は行わない
- **件数上限**: 1 待ち区間(=1 回のユーザー入力待ち)あたり最大 3 dispatch。待ち区間ごとにカウントはリセットされるが、前区間の `running` が残っている場合は合計 3 を超えて起動しない
- **軽量実行**: 先行サブエージェントにはスキルをロードさせない。モデルはデフォルトで `haiku` とし、コード理解の深さが必要な探索のみ `sonnet` に上げる(ブリーフ雛形に明記)
- **ベストエフォート**: forerunner はあくまで加速装置であり、失敗・未完了でも本作業のフローを変えない

## 5. エラー処理

| ケース | 扱い |
|---|---|
| 予測ミス(有効条件に合致しない回答) | 成果を読み込まず破棄。読み取り主体なので副作用ゼロで無害 |
| 先行サブエージェントの失敗 | manifest を `failed` にして無視。本作業は通常フロー(その場で探索)で続行 |
| 二重利用 | 回収済みエントリは `harvested` / `discarded` にマークし、再回収しない |
| ユーザーが想定外の回答(全予測ミス) | 全件 discard して通常フローへ。損失は先行分のトークンのみ |

## 6. テスト方針

自動テストは持たず、手動シナリオ検証で確認する:

1. **正常系**: 設計承認待ち区間で予測 → 先行 → 承認 → 回収が機能し、成果が即利用される
2. **予測ミス系**: 想定外の回答時に成果が破棄され、通常フローに影響しない
3. **フック系**: manifest に未回収エントリがある場合のみリマインダーが注入される。否定系はフックスクリプトを直接実行し、`running`/`done` を含まない manifest・manifest 不在の両ケースで stdout が空であることを確認する
