# chat-recorder パフォーマンス改善 設計書

- 日付: 2026-07-24
- 対象: task-utility プラグイン(chat-recorder エージェント / Stop フック / 抽出スクリプト)
- ステータス: Haiku レビュー済み・補足修正反映済み(ユーザーレビュー待ち)

## 1. 背景と問題

chat スキルの毎ターン記録が遅く、ターン終端で数分単位の待ち時間が発生している。

実測(このリポジトリ):

- トランスクリプト 6.9MB → 抽出結果 35KB(≈1.2 万トークン)。毎ターンこの全量を chat-recorder が読む
- 記録ファイルは最大 55KB(≈1.5〜2 万トークン)。追記のたびに Write(全文上書き)で全体を再出力する
- セッション序盤の小規模記録でも 65 秒・7 ツール呼び出し・約 2.5 万トークンを要した

ボトルネックは chat-recorder(Haiku)の入出力トークン量であり、いずれも**セッション長に比例して毎ターン悪化する**:

- (a) 入力: 毎回会話全量を抽出し、未記録範囲の判定を LLM が高コストに再計算している。Stop フック(`check-chat-recorded.ts`)は走査時に「最後の記録イベントの行番号」(`lastRecord`)を既に持っているのに、抽出コマンドへ渡していない
- (b) 出力: 追記を Write(全文上書き)で行うため、追記量が一定でも出力コストがファイルサイズに比例する

## 2. 採用した方針

- **案 A: 差分抽出 + 追記専用化**(効果最大・フォーマット契約は不変)
- **案 B: ユーザー発言引用ブロックの機械生成**(「一字も変えない」契約をスクリプトで機械的に保証)

却下した選択肢:

- **案 C: バックグラウンド実行** — Claude Code のバージョン・実行環境によりサポート差があり、「全ユーザーが使える」必須要件との互換検証が別途必要。案 A/B の効果を見てから再検討
- **案 D: 記録頻度の間引き** — 「毎ターン追記して常に最新」という chat スキルの契約変更を伴うため見送り

## 3. 変更内容

### 3.1 `src/extract-conversation.ts` — 差分抽出と引用整形

1. **`--since-line <N>` オプションを追加する**
   - 使い方: `node extract-conversation.mjs <transcript.jsonl> --since-line <N>`
   - 判定は 2 段階: まず `lineNo <= N` の行をすべて読み飛ばす。次に、残りの先頭から**最初の USER 実発言**(check-chat-recorded と同じ実発言判定: `type === "user"` かつ文字列 content、`<` 始まり・`isMeta` を除外)が現れるまでの ASSISTANT 断片を捨て、そこから抽出を開始する
   - 例: N+1 行目が ASSISTANT、N+2 行目が USER のとき、N+1 は切り捨てて N+2 から始める
   - 省略時・`N <= 0` のとき: 従来どおり全量抽出
2. **行カウントを `check-chat-recorded.ts` と同一ロジックに揃える(現行実装の変更を伴う)**
   - 現行の extract-conversation は行番号を数えておらず、空行・パース不能行を `continue` している。改修では **`split("\n")` 直後・スキップ判定より前に行番号を加算**し、check-chat-recorded の数え方(空行・JSON パース不能行も 1 行と数える)と厳密に一致させる
   - この一致は両ファイルのテストで固定する(不変条件)
3. **USER 発言を引用ブロック形式で出力する**
   - 変換規則: USER 発言の各行の先頭に `> ` を付ける。空行は `>` のみにする。改行構造・本文はそのまま(例: `"line1\n\nline2"` → `"> line1\n>\n> line2"`)
   - 引用記号の付加はフォーマットであり本文の改変ではない。「一字も変えない」契約の対象は本文であり、これをスクリプトで機械的に保証するのが本改修の趣旨
   - chat-recorder は整形済みブロックをそのまま転記するだけになる(再整形・記号の付け直しをしない)

孤立 ASSISTANT 断片の扱い(トレードオフ): 差し戻し→ディスパッチ→最終報告という順序のため、前回記録時点より後にターン末尾の ASSISTANT テキストが残ることがある。これは「最初の USER 発言から開始」の規則で切り捨てる。切り捨てられるのは前ターンの締めの報告文が主で、実質的な内容は前回記録の要約に含まれている。現行実装でも次回記録時に確実に拾われる保証はなく、リスクは同等である。

### 3.2 `src/hooks/check-chat-recorded.ts` — 行番号の受け渡しと指示の更新

1. `lastRecord > -1` のとき、差し戻し reason 内の抽出コマンド文字列(現行実装の「抽出コマンド:」行)に `--since-line ${lastRecord}` を付与する
2. reason 末尾の指示箇条書きに、次の 2 項目を追加する(既存項目は変更しない):
   - 既存記録ファイルの確認は全文 Read でなく末尾確認(`tail`)で行うこと
   - 追記は全文上書きでなく末尾追記で行うこと

### 3.3 `agents/chat-recorder.md` — 追記専用の手順に改訂

frontmatter:

- `tools: Read, Write, Edit, Bash, Glob`(`Edit` を追加)

手順(改訂後の骨子):

1. 抽出コマンド(`--since-line` 付き)を Bash で実行し、未記録分の発言列を得る
2. SKILL.md を Read し、ファイル構成と粒度契約に従う(従来どおり)
3. Glob で既存ファイルを特定し、**`tail -n 60` で末尾のみ確認**して最終セッション番号と文脈を得る(全文 Read をしない)
4. 追記時: 新セッション部分を Write で**一時ファイル**(`/tmp` 等の作業領域)に書き、`cat <一時ファイル> >> <記録ファイル>` で末尾追記する
   - ヒアドキュメント(`<<EOF`)は本文中の区切り文字衝突リスクがあるため使わない
5. 新規作成時: 従来どおり Write で作成する(初回はファイルが小さい)
6. INDEX.md の更新: Read(小ファイルなので許容)+ **Edit で対象 1 行のみ**追加・置換する
7. ヘッダーの成果物追記が必要な場合も Edit の部分置換で行う

厳守事項に追加:

- 既存記録ファイルの全文を Write で再出力することを禁止する(追記は必ず末尾追記、修正は Edit の部分置換)
- 抽出結果の USER 引用ブロックは整形済みなので、そのまま転記する(再整形しない)

### 3.4 波及作業

- `pnpm build` でバンドル済み `scripts/*.mjs` を再生成しコミットする(利用者はビルド不要の原則)
- `plugins/task-utility/.claude-plugin/plugin.json` のバージョンを `0.4.0-dev` → `0.5.0-dev` に上げる
- `skills/chat/SKILL.md` は**変更しない**。SKILL.md が定めるのは記録ファイルの完成形(引用ブロックで原文を載せる)であり、本改修は完成形に変更を加えず「誰が引用記号を付けるか」だけをエージェントからスクリプトに移す。転記手順の変更はすべて `agents/chat-recorder.md` 側に閉じる

## 4. テスト

既存のテストファイル(`src/__test__/extract-conversation.test.ts`、`src/hooks/__test__/check-chat-recorded.test.ts`)に**追加**する(新規ファイルは作らない)。

- `extract-conversation.test.ts` に追加:
  - `--since-line N` で N 行目以前が除外され、N より後の最初の USER 実発言から始まること(境界値: `N = 0`(全量と同等)、途中の行、最終行以降(空出力))
  - N 直後の孤立 ASSISTANT 断片が切り捨てられること(N+1 が ASSISTANT・N+2 が USER のケース)
  - 行カウントが空行・パース不能行を含めて加算されること(単体: 手計算の行番号で検証)
  - USER 発言が `> ` 前置の引用ブロックで出力されること(複数行・途中の空行を含むケース)
  - `--since-line` 省略時は従来出力と同等であること(引用整形を除く)
- `check-chat-recorded.test.ts` に追加:
  - `lastRecord` 検出時に reason の抽出コマンドへ `--since-line <lastRecord>` が埋め込まれること
  - `lastRecord === -1` のときは付与されないこと
  - 統合検証: フックが報告する行番号を `--since-line` に渡し、空行・パース不能行を挟んでも差分が欠落・重複しないこと(フック実行の足場があるこちら側に置く)

## 5. 期待効果

毎ターンの chat-recorder の入出力が「会話全量 + 記録全文」(合計 3〜4 万トークン)から「新規ターン分のみ」(数百〜数千トークン)に減る。待ち時間はセッション長に依存しない、ターン内容量に比例する一定時間になる。

## 6. リスクと限界

- **行番号契約のずれ**: 抽出側とフック側で行の数え方が食い違うと差分が静かに欠落する。同一ロジックをテストで固定して防ぐ
- **記録失敗時の欠落**: ディスパッチ自体を記録の証跡と見なす現行設計のため、chat-recorder が書き込みに失敗するとそのターンは以後拾われない。ディスパッチを証跡と見なすモデル自体は現行と同じだが、旧方式が持っていた「次回の全量抽出で取りこぼしを拾い直せる」暗黙の回復性は差分方式では失われる(既知のトレードオフとして受容)
- **コンパクション等でトランスクリプトが書き換わる場合**: フックは毎回現在のファイルを走査して `lastRecord` を再計算するため、reason 内の行番号と抽出対象は常に同一ファイル・同一走査に基づき整合する
