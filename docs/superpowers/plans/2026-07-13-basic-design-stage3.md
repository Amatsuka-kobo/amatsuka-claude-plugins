# API List — API/IF 一覧の作成

## 目的

ユーザーから与えられた情報を出発点に、ブレインストーミングでシステムのエンドポイントを洗い出し、API/IF 一覧として Markdown で保存する。

## 大原則

- **ディスカッションはユーザーが使用する言語を厳守する**
- **ユーザーの明示的な承認を得るまで生成・保存しない**
- STOP するときは必ず「理由+次にユーザーがすべきこと」を伝えて終了する

## 手順

### 1. 最初の確認

AskUserQuestion で次を確認する:

- **保存先**: `docs/design/api/` を既定として提案し、変更希望を確認する
- **対象範囲**: システム全体か、特定の機能・サブシステムか

すでに入口スキル(basic-design)から引き継いでいる場合、**保存先の確認は省略**する(手順 2 の値を使う)。**対象範囲**は、会話ですでに明らかなら聞き直さず、不明なときだけ確認する(単独呼び出し時も同じ判断でよい)。

### 2. ブレインストーミング

自由対話で進めつつ、次の観点がすべて埋まるまで、**不足している観点だけを 1 問ずつ**質問する。選択式で聞ける場面では AskUserQuestion を使う。

| 観点 | 埋まる状態 |
| --- | --- |
| エンドポイント一覧 | 対象範囲の API が列挙され、それぞれの役割を一言で説明できる |
| メソッドとパス | 各 API の HTTP メソッドと URL パス(パスパラメータ含む) |
| 認証 | 各 API の認証要否と方式(例: Bearer トークン / セッション / 不要) |
| リクエスト概要 | 主要な入力(パスパラメータ・クエリ・ボディの主要フィールド)。**フル JSON 定義は書かない** |
| レスポンス概要 | 正常時の主要な出力フィールドとステータスコード。**フル JSON 定義は書かない** |

先行する成果物・用語集(入口スキルの概要ブレストなど)がある場合、リソース名・エンティティ名はそれに従う(例: ER図の `orders` エンティティに対応する API は `/orders`)。

画面遷移図や ER図が先に存在する場合は、画面・エンティティごとに必要な API を洗い出す問いかけをすると漏れが減る(例: 「注文一覧画面はどの API からデータを取得しますか?」)。

### 3. ドラフト提示 → 明示承認

`references/template.md` の形式で一覧表の**全文**を提示し、ユーザーの承認を得る。

### 4. 保存

承認された内容を `docs/design/api/<名前>.md` に保存する。ファイル名はケバブケース(例: `order-api.md`)。git コミットはユーザーの指示があったときのみ行う。

## 既存一覧の更新

同名のファイルが既にある場合は、それを読み込んで現状を把握し、差分(追加・変更・廃止エンドポイント)をブレストしてから全文を更新する。

# NFR Checklist — 非機能要件チェックリストの作成

## 目的

観点カタログ(`references/catalog.md`)を網羅的にたどりながら、対象システムの非機能要件の「要否と目標値」をブレインストーミングで埋め、チェックリストとして Markdown で保存する。

## 大原則

- **ディスカッションはユーザーが使用する言語を厳守する**
- **ユーザーの明示的な承認を得るまで生成・保存しない**
- STOP するときは必ず「理由+次にユーザーがすべきこと」を伝えて終了する
- **観点を勝手にスキップしない**。対象外とする場合も「対象外」という判断を明示的にユーザーと確認して記録する

## 手順

### 1. 最初の確認

AskUserQuestion で次を確認する:

- **保存先**: `docs/design/nfr/` を既定として提案し、変更希望を確認する
- **システムの性質**: 社内システム / 一般公開サービス / 組み込み等(カタログのどの観点を重点的に扱うかの判断材料)

すでに入口スキル(basic-design)から引き継いでいる場合、**保存先の確認は省略**する(手順 2 の値を使う)。**システムの性質**は、会話ですでに明らかなら聞き直さず、不明なときだけ確認する(単独呼び出し時も同じ判断でよい)。

### 2. ブレインストーミング(カタログ巡回)

`references/catalog.md` の 8 分類を**分類ごとに**たどる。分類単位で現状の想定を要約提示し、不足している下位観点だけを 1 問ずつ質問する。選択式で聞ける場面では AskUserQuestion を使う。

各観点で埋めるのは次の 3 点:

1. **要否**: 必要 / 対象外(理由付き)
2. **目標値・方針**: 数値目標(例: 応答 1 秒以内、稼働率 99.9%)または方針(例: 日次バックアップ)
3. **備考**: 前提や補足があれば

すべての分類を巡回し終えるまで保存に進まない。ユーザーが「残りはまとめて対象外でよい」と明示した場合はその旨を記録して先へ進む。

### 3. ドラフト提示 → 明示承認

チェックリストの**全文**を提示し、ユーザーの承認を得る。形式:

​```markdown
# <システム名> 非機能要件チェックリスト

- 作成日: YYYY-MM-DD
- 対象: <一言説明>

## 1. 性能・拡張性

| 観点 | 要否 | 目標値・方針 | 備考 |
| --- | --- | --- | --- |
| 応答時間 | 必要 | 主要画面 1 秒以内 | ピーク時 3 秒まで許容 |
| スループット | 必要 | 100 req/s | |
| スケーラビリティ | 対象外 | — | 利用者数が固定のため |

(以下、8 分類すべて)
​```

### 4. 保存

承認された内容を `docs/design/nfr/<名前>.md` に保存する。ファイル名はケバブケース(例: `order-system-nfr.md`)。git コミットはユーザーの指示があったときのみ行う。

## 既存チェックリストの更新

同名のファイルが既にある場合は、それを読み込んで現状を把握し、変更のある分類だけを再ブレストして全文を更新する。
```

# Basic Design — 基本設計オーケストレーション

## 目的

対象システムの概要を短いブレインストーミングで固め、必要な成果物を選択し、各専用スキルを順に実行して基本設計ドキュメント一式を作る。

## 大原則

- **ディスカッションはユーザーが使用する言語を厳守する**
- **ユーザーの明示的な承認を得るまで生成・保存しない**(各成果物のドラフト承認は各スキルの規律に従う)
- STOP するときは必ず「理由+次にユーザーがすべきこと」を伝えて終了する
- **成果物は 1 つずつ逐次で作る**。並列にしない(ブレストは 1 本の対話であり、用語の整合は逐次実行に依存する)

## 手順

### 1. 概要ブレスト

対象システムについて、次の 3 点を軽い対話で確認する(まとめて聞いてよい。既に会話に出ていれば聞き直さない):

- **システム名と一言サマリ**(何をするシステムか)
- **主要ユースケース 2〜3 個**(誰が・何をする)
- **登場する主な概念**(画面になりそうなもの・データになりそうなもの・連携する外部システム)

### 2. 全体設定の確認(1 回だけ)

AskUserQuestion で次を確認し、**以降の全成果物に引き継ぐ**(各スキルでの再確認はしない):

- **出力形式**(図系スキル用): Draw.io / インタラクティブ HTML / 両方。Markdown 系スキル(api-list / nfr-checklist)には適用しない(常に Markdown)
- **保存先ルート**: `docs/design/` を既定として提案(各成果物は `docs/design/<種別>/` に入る)

ここで引き継ぐのは**出力形式と保存先だけ**。各スキルが必要とするそれ以外の情報(対象範囲、システムの性質など)は、概要ブレストと会話の文脈から判断し、不明なときだけ各スキルの手順で確認する。

### 3. 成果物の選択

AskUserQuestion(multiSelect)で作る成果物を選んでもらう:

- ER図(er-diagram)
- 画面遷移図(screen-flow)
- システム構成図(system-architecture)
- シーケンス図(sequence-diagram)
- API/IF 一覧(api-list)
- 非機能要件チェックリスト(nfr-checklist)
