## 1. 背景: 全部を委譲する agent-policy では、往復のたびに文脈を作り直す

agent-policy のオーケストレーターは、担当表のどの役割も自ら実行しない(`:81`)。探索・実装・レビュー・修正のすべてが、サブエージェントへの委譲になる。better-agentics のオーケストレーターは調査・設計・実装を自分で行い、委譲は review・split・stuck の 3 場面に限る。この違いを、食い違いの文書では G8 と呼んでいる。

better-agentics の設計書は、サブエージェントが遅くなり質が落ちる主な原因を、文脈の作り直しとした。fork でないサブエージェントは毎回まっさらな状態から始まり、親と別のプロンプトキャッシュを 5 分の寿命で温め直す。agent-policy ではレビューの指摘の修正も委譲するので、委譲の回数が多く、そのたびに文脈を作り直す。

一方で、better-agentics の策には、オーケストレーターが自分で作業することを前提にしたものがある。この設計書は、better-agentics の策を agent-policy に当てはまるものと当てはまらないものに分け(4 章)、あわせて食い違いの文書の agent-policy 側の項目を直す(5〜7 章)。

## 2. 目標と非目標

### 2.1 目標は、委譲の往復で文脈を作り直す回数を減らし、codiel の手順とぶつからないこと

- 指摘を直したら再レビューし、その再レビューと修正の依頼で、前の委譲先の文脈を引き継ぐ(D1・D11)。
- 仕様を書き切れない complex-impl の作業に、オーケストレーターの文脈を渡す(D2)。
- 定義の起動時の負荷と、レビュアーのキャッシュの作り直しを減らす(D3・D4)。
- 役割の model・effort・キャッシュの寿命が環境変数で上書きされているとき、利用者が気づける(D5)。
- 委譲先が、結果の無いときにも決まった形で報告する(D6)。
- codiel 1.1〜2.0 の手順の中で、agent-policy の規律が codiel の手順とぶつからない(D7・D8・D12)。delegation gate を有効にしたプロジェクトは除く(D10、M6)。

### 2.2 非目標

- better-agentics の改修。食い違いの文書の better-agentics 側の項目は扱わない。
- codiel の改修。codiel への申し送りは 9 章に書くだけである。
- 委譲先の選定に Jev を使うこと。agent-policy は Jev を使わない(`grep -rni "jev\|typesafe" plugins/agent-policy` で 0 件)。
- 定義の無い readonly の役割の委譲先を、`Explore` から別のビルトインへ変えること(12 章)。

## 4. better-agentics の性能策を agent-policy に当てはめる

### 4.1 再レビューの条項を足し、再レビューと修正で前の委譲先を再開する(D1・D11)

agent-policy には再レビューの条項が無い(3.2)ので、条項を足す(D11)。better-agentics の D24 と同じ形である。そのうえで、better-agentics の D5 の範囲(再レビュー)に、修正の依頼を加える(D1)。

- 再レビュー(D11)
  - レビューの指摘には、medium 以下を含めてすべて対応する。指摘の採否はオーケストレーターが決める(現行の `:87`・`:223` と同じ)。対応は、採る指摘を直すか、採らない指摘の理由を記録するかのどちらかである。
  - 指摘に critical・high があった巡の後は、その巡の採る指摘を直し、採らない指摘の理由を記録したうえで、同じ観点の再レビューを依頼する。critical・high が残らなくなるまで、上限なくレビューと修正を回す。修正する担い手の替え方は、下の「修正のループの回し方」(D20)による。外側の手順が修正の回し方(回数の上限や担い手の替え方)を定めていて、この規律と両立しなければ、原則(5.1)で外側の手順が効く。
  - critical・high の無い巡では、その巡の medium 以下を直さずに判断を仰ぐ(better-agentics の J31 と同じ読み方)。判断を仰ぐのは、この最後の巡に残った指摘だけである。
  - 判断を仰いだら、答えを待つ。答えを得るまで、ユーザーへの提示・完了の報告・push に進まない。仰ぐ先と聞き方は、外側の手順が定めていればそれに従い(5.1)、定めていなければオーケストレーターに任せる(better-agentics の J34 と同じ)。答えを受けて直した変更も、コミットしてから再レビューに回す。
  - この条項は、§設計・実装計画の規律 の 2 つのレビューにも当てる。`:223` の「補足修正を加えてからユーザーへ提示して承認を得る」は、この回し方を終えた後に行う。
  - 実装のレビューは、変更をコミットした後に依頼する。指摘を直した変更も、コミットしてから再レビューに回す。コミットの担い手と方法は J20 に書く。
  - 文書のレビュー中は、依頼したレビューがすべて戻るまで、その文書を編集しない(better-agentics の J22 と同じ)。2 つのレビューを並列に起動する(D15)ので、先に戻った指摘を直し始めると、もう 1 つのレビューの対象が動く。
  - 重大度は、レビューの 5 役割の Output Format で付けさせる(4.5、J18)。委譲先が重大度を返さないとき(再生成していない定義、合成で起動した外部定義など)は、オーケストレーターが指摘ごとに判定する。要件を満たさない・動かない・安全を損なう指摘は critical か high、誤解や後の不具合を招く指摘は medium、表記や体裁だけの指摘は low とする。
- 再開(D1)
  - 再レビューは、前の巡のレビュアーへ SendMessage で続きを頼む。送るのは、直した後の差分の取り方か文書のパスと、満たすべき要件だけとする。指摘の採否や自分の結論は送らない。`:222` の「他のレビューの指摘は渡さない」と同じ考え方である。
  - レビューの対象のコードは、コミットの範囲(`git diff <base>..<head>`)で渡す(better-agentics の D14 と同じ)。レビューする変更の作業の間に、別の委譲先が同じブランチへコミットしたときは、範囲に別のコミットが挟まるので、レビューする変更のコミットの ID を列挙して渡す(J20)。
  - レビューの指摘の修正を誰に頼むかは、下の「修正のループの回し方」(D20)で決める。5 軸で役割を決め直さない(J28)。
  - 修正の依頼では、直す指摘(採った指摘の本文)と、満たすべき要件を送る。直さないと決めた指摘は送らない。
  - 再開する相手は、委譲先が完了したときに返る `agentId` で指す。オーケストレーターは、委譲した作業と `agentId` の対応を会話に残しておく。会話の圧縮で `agentId` を失ったときは、再開できないときと同じく新しく起動する。
  - 修正のループの回し方で escalation に移るとき・escalation を起動し直すとき、差し戻しで役割を上げるとき(`:130-131`)は、新しく起動する。
  - 再開するときは、`:47` の「候補から 1 件を選ぶことと起動形態を決めることを委譲のたびに行う」を当てない。前の委譲で選んだ定義と起動形態を引き継ぐ。
  - 再開できないときは、前と同じ委譲先と起動形態で新しく起動する。依頼文は最初の巡と同じ形にし、`:136-146` の項目と、直した後のレビューの対象を入れる。`Explore`・`Plan` へ委譲していたときは再開できない(3.1)。合成で起動した定義、custom 構成の外部ベンダーのモデルの定義、fork で再開できるかは、S2 で確かめる。再開がエラーになったときも、新しく起動する。
- 修正のループの回し方(D20)
  - ラウンドは、critical・high のある巡の指摘を直して再レビューに回すまでを 1 と数える(better-agentics の D29 と同じ数え方)。変更ごとに数え、観点が複数あっても、どれかの観点に critical・high があった巡を 1 ラウンドと数える。オーケストレーターは、変更ごとのラウンドの数を会話に残す。
  - 1〜3 ラウンドは、指摘が当たる箇所を書いた委譲先を SendMessage で再開して直させる(D1)。指摘が複数の書き手の箇所にまたがるときは、書き手ごとに分けて頼む。オーケストレーターが自分で書いた箇所(J23 で自分で行った実装を含む)は、自分で直す。
  - 4 ラウンド以上は、行き詰まりの打開として escalation に委譲する。escalation の 1 体が受け持つのは、連続する 2 ラウンドまでとする。4 ラウンド目で 1 体目を起動し、5 ラウンド目はその再開とする。6 ラウンド目で 2 体目を起動し、7 ラウンド目はその再開とする。以降も同じ。
  - escalation を起動し直すときは、前の escalation と同じ定義と起動形態で新しく起動し、候補を選び直さない(`:47` を当てない。better-agentics の J36 と同じ)。
  - escalation への依頼文には、`:134` の 3 項目を入れる。試行履歴は、それまでのラウンドの担い手・直し方・レビューの指摘である。失敗出力の原文は、最後の巡で採った指摘の原文である。未解決の制約は、直さないと決めた指摘とその理由、満たすべき要件である。新しく起動し直すときは、前の escalation のラウンドも試行履歴に入れる。
  - 4 ラウンド目以降の修正は、同じ変更の修正の続きなので、`:135` の「初回の作業は escalation へ委譲しない」に当たらない(J29)。
  - ループの中では、この規則で担い手を決める。1〜3 ラウンドは、5 軸の escalation の条件(`:116`)や `:133` に当たって見えても、escalation に回さない。ループの外では、現行どおり 5 軸で決める(J28)。
  - 1〜3 ラウンドで修正する担い手が差し戻したときは、現行の差し戻しの経路(`:130-131`)で役割を上げる。これは「同じ委譲先で続ける」の例外である。上げた先の委譲先が、そのラウンドから続ける。差し戻しで escalation に届いたときは、その escalation が連続する 2 ラウンドまで受け持ち、使い切ったら新しく起動し直す。ラウンドの数え方は変えない。
  - escalation が断ったときは、選び直しの候補が尽きたとみなす(J11)。外側の手順の外では、オーケストレーターがそのラウンドを自分で直す(J23)。次に escalation を起動する時点(起動し直しの時点)で、改めて escalation に委譲する。
  - この規則は、修正する担い手にだけ当てる。レビュアーは、前の巡のレビュアーを再開し続ける(D1)。
  - オーケストレーターが自分で書いた文書(`:81`・`:220`)の修正には当てない。上限なく、オーケストレーターが自分で直す(D11、J27)。
  - 外側の手順に従って作業している間は、修正の回し方(ラウンドの数え方・担い手の替え方・上限)も外側の手順に従い、この規則で別に数えない(原則 5.1。better-agentics の設計書 6.3 と同じ)。外側の手順が、行き詰まりの打開と書いた作業の単位を出したときは、escalation に委譲する。その依頼文にも `:134` の 3 項目を入れる。
- 規律への置き場所は、§モデル別役割の運用 の差し戻しの経路(`:130-131`)の直後とする。

修正の依頼で実装の委譲先を再開すると、委譲先は自分の書いたコードと読んだファイルを覚えている。一方、レビューと採否の判断を挟むので、再開までの間は 5 分を超えやすい。そのときはキャッシュが切れていて、履歴の全体を書き込み直す。修正の依頼の再開で見込めるのは文脈を保つ利点で、費用は新しく起動するより高くなりうると推定する(14 章)。

### 4.2 fork は complex-impl に限り、オーケストレーターの規律を依頼文の冒頭で外す(D2)

agent-policy では、fork の会話の履歴に方針スキルの規律(担当表の役割を自ら実行しない・委譲先の解決)が入っている。fork がそれに従って、さらに委譲しかねない。fork は親のツールを持つので Agent ツールも持つ。ただし Agent ツールを持つのは、ビルトインの `general-purpose` への委譲でも同じである(3.2)。この穴は、§サブエージェントの規律 に足す条項(6.1、J16)で両方の経路について塞ぐ。

それでも complex-impl に使うのは、オーケストレーターの文脈が役立つ場面があるためである。オーケストレーターはコードを読まないが、要件の確定・探索の報告・設計の判断の経緯は会話に残っている。仕様を文書に固定できない complex-impl の作業(`:124`)では、それが依頼文に書き切れない材料になる。normal-impl は「仕様と設計が済んだ実装」(`:118`)なので、文脈が要る場面が無い。

fork するのは、次をすべて満たすときだけとする。

- 5 軸で complex-impl に当たり、判断部分の成果を文書に固定できず、作業の全体を complex-impl に任せる(`:124`)。
- complex-impl の委譲先の実行モデルが、オーケストレーター自身のモデルと同じである(J1)。実行モデルは、§委譲先の実行モデルの確定 でその委譲に決まるモデルである。
- 外側の手順に従って作業している間ではない(J3、M2)。外側の手順のスクリプトへ渡す作業に限らず、外側の手順の下では fork を使わない。

fork の起動が拒否されたとき(fork を止める設定があるとき)は、complex-impl の通常の起動に戻す(J2)。

fork の依頼文の冒頭には、次を置く(J4)。

- fork された complex-impl の担い手であること。会話の履歴にあるオーケストレーターの規律(委譲・担当表の役割を自ら実行しない・委譲先の解決)を当てず、依頼文の作業だけを行うこと。
- 使ってよいツールは、選んだ complex-impl の定義の `tools` に限ること。定義が無いときは、complex-impl の役割断片の `tools` に限る。custom-policy の「この tools のみ使用」の明記(`skills/custom-policy/SKILL.md:18`)に当たる。
- 選んだ complex-impl の定義の本文(frontmatter より後の全文)。定義が無いときは、complex-impl の役割断片の本文とし、置き場所の選び方はビルトインへ委譲するときと同じ(`:75-76`)とする。プロジェクトに最適化された定義を、同梱の断片より優先する(2026-09-29 の設計書 4.7 と同じ考え方)。
- 規律の「サブエージェントは〜」で始まる条項(`:145` の転記)。J16 の Agent ツールの条項も、ここに入る。

fork は親の effort で動き、complex-impl の effort(medium)は使われない。README で利用者に知らせる。complex-impl の定義が無いときや、定義が `inherit`・未宣言でモデル注入起動になるときは、実行モデルは担当表の Opus である。このときは Opus のオーケストレーターだけが fork の条件を満たす。プロジェクトの complex-impl の定義が `model: sonnet` などを宣言していれば、その値と比べる。

### 4.3 setup-agents で `omitClaudeMd` を聞き、レビューの定義に 1 時間のキャッシュを書く(D3・D4)

2 つのキーは、テンプレート(`compose`)に出さない。専用の処理が、生成の前に既存のファイルから 2 つのキーの値を読み、生成と保持マージの後に、決めた値を行単位で書き込む(J17)。保持マージの自動保持は変えない。ステップ 5b の「完全上書き」でも、質問で答えていない `omitClaudeMd` と、`experimental` の他の下位キーは、生成の前に読んだ値で書き戻す。

- `omitClaudeMd`(D3)
  - 新規生成(ステップ 5n)では、役割ごとに付けるかを聞く。
  - 再生成で個別に調整する定義(ステップ 5b)では、既存の値を示して聞く。
  - 聞き方: `AskUserQuestion` で「付けない」「付ける」を出す。推奨の側に「(推奨)」を付ける。先頭に置くのは、既存の値があればその側、無ければ推奨の側とする(better-agentics の設計書 7.2 と同じ)。
  - 推奨は、knowledge-elicitation では「付ける」、それ以外では「付けない」とする。複数の役割を持つ定義の扱いは J5 に書く。
  - 選択肢の説明には、プロジェクトの CLAUDE.md・`.claude/rules/`(規約・保護パスの指定を含む)・ユーザーの rules が届かなくなることを書く。
  - 「付ける」なら `omitClaudeMd: true` を書き、「付けない」なら既存の行を消す。
  - 質問しない経路(個別に調整しない再生成、`--yes`、`--recommended`)の扱いは J7 に書く。
- `experimental.cacheTtl: 1h`(D4)
  - レビューの 5 役割の定義で、Claude のモデルで動くものには、聞かずに書く。Claude のモデルで動くかの判定は、規律 §委譲先の候補 と同じとする(`:31`。`sonnet`・`opus`・`haiku`・`fable`・`inherit`・未宣言のどれかで、`agent-policy-vendor` が未宣言・`claude`・`none` のどれか)。
  - 外部ベンダーのモデルの定義には書かない。再生成で外部ベンダーのモデルに変えた定義からは、`cacheTtl` だけを消す(J6)。
  - 既存の `experimental` の他の下位キーは残す。
  - レビューの役割を持たない定義では、`experimental` に触れない。
- ステップ 7 の報告に、2 つのキーを書き込んだ・書き換えた・消した定義を載せる。
- 規律の起動形態の判定表の 3 行目(`:173`)の許可一覧に、`omitClaudeMd` と `experimental` を足す(J8)。

1 時間のキャッシュが得になるのは、再レビューが 5 分を超えてから起きるときだけである(better-agentics の設計書 14 章)。D11 で、critical・high があった巡の後は再レビューが起きる。agent-policy では修正も委譲するので、その間は 5 分を超えやすいと推定する。再レビューが起きない巡では、レビュアーの接頭辞の書き込みが 5 分のときの 1.6 倍(2.0 / 1.25)になる。

### 4.4 SessionStart で、役割の設定を上書きする環境変数を警告する(D5)

方針を注入するとき(`AMATSUKA_AGENT_AUTO_INJECTION` が `claude`、`custom`、または custom の旧値。`src/agents/policies.ts:257-268` の `isCustomInjection`)に、次のどれかに当たれば、警告の文を足す。注入は止めない。`none` と未設定のときは agent-policy の方針が委譲を決めないので、警告しない。

| 条件 | 起きること |
| --- | --- |
| `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` が空でも `0` でも `false` でもない | 役割のモデルが一律になる。custom 構成の外部ベンダーの定義も同じモデルで動く |
| `CLAUDE_CODE_EFFORT_LEVEL` が空でない値に設定されている | 役割の effort が使われない |
| `FORCE_PROMPT_CACHING_5M` が設定されていて、`cacheTtl` を書いた定義がある | レビュアーの 1 時間のキャッシュが効かない |
| `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` が `5m` で、`cacheTtl` を書いた定義がある | 同上 |

- `CLAUDE_CODE_SUBAGENT_MODEL` だけの設定は警告しない。定義と呼び出しの `model` が勝つためである。
- 2026-09-29 の設計書は、`CLAUDE_CODE_EFFORT_LEVEL` と `maxEffortLevel` による effort の上書きを、README で知らせる扱いにした(8 章のリスクの表)。D5 は、このうち環境変数を SessionStart の警告へ広げる。
- 設定ファイルの `maxEffortLevel`・`subagentPromptCacheTtl`・`availableModels` と、組織の effort の上限は検出しない。README に書く(14 章)。
- `cacheTtl` を書いた定義は、SessionStart の走査(`src/hooks/marker-scan.ts` の `scanAgents`)で見分ける(J9)。現行の `MarkedAgent` は 6 項目しか持たず、`frontmatter()` は字下げ行を親のキーと無関係に読む(`marker-scan.ts:6-14`、`:26-53`)。そのため、`experimental` の下に `cacheTtl: 1h` があるかを判定する項目を足す。

### 4.5 役割断片の Output Format に、結果が無いときの書き方と重大度を足す(D6・D11)

- 13 役割の断片(ja・en)の Output Format に、結果が無いときの書き方を足す。例は code-review の「指摘が無いときは『指摘なし』と書き、確かめた範囲を添える」である。文言は役割ごとに決める。
- レビューの 5 役割の Output Format には、指摘ごとの重大度(critical・high・medium・low)を足す(J18)。knowledge-elicitation では、矛盾・不整合と記述の過不足の各項目に付ける。
- `realtime-research.grok.md` は、`realtime-research.md` のセクションへ追記される重ね書き(`src/agents/fragments.ts:100-108`)で、Output Format を持たないので、足さない。
- ビルトインへの委譲では、断片を依頼文へ転記するので、プラグインの更新ですぐ届く。プロジェクトの `.claude/agent-policy/roles/<RoleId>.md` があれば、それが優先される(`:75`)ので届かない。
- 生成済みの定義には、setup-agents の再実行で届く(9 章)。
- 規律 `:140`「その役割の Output Format を依頼文で指定する」は、「定義の本文か転記した断片に Output Format が無いときだけ、依頼文で指定する」に改める(J19)。現行のままでは、オーケストレーターが毎回書く Output Format が 6.1 の出力の形の条項で優先され、この変更が委譲先に届かない。
- 外側の手順が出力の形を定めているときは、役割の Output Format より依頼文が優先される(6.1)。そのときは、結果が無いときの書き方と重大度も依頼文の形に従う。外側の手順のレビューと 4.1 の再レビューの条項が両立しないか、同じ目的で重なるときは、外側の手順を優先する(5.1)。

## 5. 外側の手順と規律の両方に従い、両立しないときだけ外側の手順を優先する(D7・D12)

### 5.1 原則と、今わかっている両立しない例

- 「外側の手順」は、このプラグインの外のスキルやコマンドが定める手順である。
- 原則(D7): オーケストレーターは、外側の手順に沿って作業している間も、外側の手順と方針の規律の両方に従う。両方に従えないとき、または両方に従うと同じ目的の手順が重なるとき(レビューの二重化など)だけ、名前で起動した外側の手順を優先し、その規律の条項を当てない(J22)。以下、この 2 つを「両立しない」と書く。当てないのは両立しない条項だけで、同じ規律の他の条項は当てる。
- 優先するのは、ユーザーか、セッションを起動した指示(プロンプト)が名前で起動した外側の手順に限る(D12)。Claude が description を見て自分から読み込んだスキルの手順も「両方に従う」の対象だが、規律と両立しないときは規律に従う。
- `:81` の最後の文「コマンドで起動したスキルの手順(スキル駆動のワークフロー)がこの規律のオーケストレーター条項と衝突するときは、ワークフローの手順を優先する」を、この原則に置き換える。
- 原則が比べるのは、外側の手順と、オーケストレーターの規律である。役割断片と `_common.md` の制約(6.2 の安全弁を含む)は、委譲先が自分の条件どおりに当てる。
- 「名前で起動した」には、次の 3 つを含める(J24。D12 の決定文の「ユーザーか起動の指示」を、ユーザーが置いた指示まで読み広げた解釈である)。
  - ユーザーがスラッシュコマンドで起動したもの
  - ユーザーが会話でスキルの名前を挙げて使うよう求め、Claude が起動したもの
  - CLAUDE.md・rules・hook の注入文が名前を挙げて起動を求め、Claude が起動したもの(ユーザーが置いた指示であるため)
- 名前で起動した手順が、その中で名指しして起動させるスキルの手順も、外側の手順に含める(J24)。コマンドがスキルを名指しし、そのスキルがさらに別のスキルを名指しする連鎖を、1 つの外側の手順として扱う。
- 当てるのは、オーケストレーターがその手順に沿って作業している間である。手順の最後のステップを終えたとき、またはユーザーが手順を止めたときに終わる。オーケストレーターは自分がスキルを起動したことを会話から知れるので、別の信号は設けない。会話が圧縮された後は、要約に手順の作業が続いていると残っていれば、続いているとみなす。
- 外側の手順が担い手を「定めた」とみなすのは、作業ごとに誰が行うか(オーケストレーター自身が行う、委譲せずに行う、など)を明記しているときだけとする(J14)。「自分で作業するときは〜」「委譲する場合は〜」のように、担い手を条件として書いた手順は、委譲しても両立する。そのときは、原則どおり両方に従い、`:81` のとおり委譲する。
- agent-policy の規律(skills・references・assets)には、codiel の名前も codiel 固有の語も書かない(ARCHITECTURE の指示層・参照層の規則)。この設計書の codiel への言及は、規律を決めた根拠であり、規律の文面には写さない。Jev と Auto Ask の名前も写さず、「人の判断の代わりに別の仕組みで判断する」と書く。agent-policy は Jev を使わない(2.2)。
- 次の表は、今わかっている両立しない例である。閉じた列挙ではない。表に無い対立にも、同じ原則を当てる。
- 規律の文面には原則だけを書き、表は写さない(better-agentics と同じ)。例を写すと閉じた列挙として読まれ、例に無い対立で原則が選ばれにくくなる(2026-09-24 の設計書 9 章の不採用案と同じ理由)。表は、実装計画と S6 の確認に使う。

### 5.3 外側の手順のスクリプトへ起動の指定を渡すとき

codiel 1.2・2.0 の Workflow のスクリプトは、委譲の指定(`agentType`・`model`・`effort`・依頼文の前置き)を `args` で受け取る(codiel 1.2 の 3.4)。「委譲の指定」は codiel の語なので、規律の文面では「スクリプトに渡す起動の指定(定義名・モデル・effort・依頼文の前置き)」と書く(J10)。

- 起動の指定は、Agent ツールで起動するときと同じく、§委譲先の解決 と §委譲先の実行モデルの確定 で決める。
- 依頼文に書く項目は、前置きに入れる(J10、M1)。前置きを渡す項目の名前は、外側の手順が定める名前に従う(codiel 1.2 では `preamble`。codiel 1.2 の 11 章)。前置きに入れるのは次のとおりである。
  - 5.2 の依頼文に書く項目(`:136`・`:139`・`:145`・`:146`)
  - ビルトインへ委譲するときは、元の役割の役割断片の本文(`:73`)
  - 合成で起動するときは、外部定義の本文と、その禁止条項・制約条項がホストの本文より優先する旨(`:165`・`:196-197`)
  - readonly の役割を Write・Edit を持つ定義へ回すときの明記(`:141-144`。ステップ 3 で general へ回すときの `:68` を含む)
  - 実装の役割では、変更した各箇所を判定した検査とその結果を報告に添える指示(`:128`)
  - custom 構成では、「この tools のみ使用」の明記(`skills/custom-policy/SKILL.md:18`)
- fork の指定は渡さない。外側の手順の下では fork を使わない(4.2、J3、M2)。
- 外側の手順が、断られた作業の起動の指定を選び直すよう求めたら、断った定義を外して次のように選び直す(J11)。どの定義が断ったかは、オーケストレーターが渡した起動の指定の控え(外側の手順の記録か自分の会話)で知る。複数の役割を持つ定義では、委譲先が報告に添える役割 ID(6.1、M3)で、どの役割で断ったかを知る。報告が無いか ID が無いときは、渡した起動の指定の役割を断った役割とみなす。
  - 実装の役割(`:106` の 4 役割)は、差し戻しの経路で上げる。light-impl と normal-impl が断ったときは complex-impl へ(`:130`)、complex-impl が断ったときは escalation へ上げる(`:131`)。escalation へは、前置きに `:134` の試行履歴(どの役割が何を断ったか)・断った理由の原文・未解決の制約を入れる。escalation の断片は、これらが欠けると着手しない(`assets/roles/ja/escalation.md:23`)。
  - それ以外の役割(general・e2e-verify・readonly の役割)は、§同じ役割の候補から選ぶ の順(特化定義 → 汎用定義 → general → ビルトイン)で、断った定義の次に当たる候補を選ぶ。役割の定義が 1 件だけのときも、この順で次に当たるもの(general、ビルトイン)を選ぶ。
  - 実装の役割で同じ役割の他の候補を見ずに上げるのは、断る理由が役割断片の制約(6.2)にあるためである。同じ役割の別の定義も同じ制約を持つので、同じ理由で断る。
  - escalation が断ったとき、またはビルトインまで選んでも断られたときは、選び直しの候補が尽きたとみなす(D17)。Jev にも人にも判断を求めず、委譲しない。
  - 候補が尽きた作業は、外側の手順の既定の担い手に任せる。外側の手順が既定に戻す方法(断った役割の指定を空の指定で置き換えるなど)を定めていれば、それに従う。
  - 人が起動の指定を示したときは、それを使う。
- 外側の手順の外で委譲先が断ったときも、同じ順で選び直す。実装の役割は現行の差し戻しの経路(`:130-131`)に当たる。候補が尽きたら、オーケストレーターが自分で行う(D17、J23)。
  - レビューの役割の候補が尽きて自分で見直したときは、4.1 の再レビューの巡に数えない。レビューが済んでいないことを、ユーザーへの報告に書く(better-agentics の J33 と同じ)。

## 7. delegation gate は、外側の手順と両立しないことを README に書く(G11、D10)

- gate は PreToolUse の hook なので、規律の「外側の手順に従う」条項(D7)では止まらない。
- 2026-09-30 の hook の棚卸しで、一時解除(`--direct`・TTL)は廃止された(コミット bbd7ffcc)。理由は 2 つある。
  - 利用者はプラグイン同梱のスクリプトの絶対パスを知らず、実行できない(ユーザーの指摘)。
  - 拒否理由に実行できるコマンドを載せると、AI が自分で解除できてしまう。
  - 解除の手段は、`AMATSUKA_AGENT_DELEGATION_GATE` を外してセッションを再起動する方法だけになった。
- この改修では gate のコードを変えない。README の gate の説明に、次を書く。
  - 外側の手順のスクリプトは、エージェントを起動して書き込ませることがある。外側の手順がメインセッションに書き込ませることもある。どちらの運用でも、書き込む先が `denyGlobs` に当たると、gate は拒否する。gate は、プロジェクトのルートに設定ファイルがあり、書き込む先が `denyGlobs` に当たるときだけ拒否する(`src/hooks/delegation-gate.ts:249-270`)。
  - そうした運用のセッションでは、`AMATSUKA_AGENT_DELEGATION_GATE` を外して gate を無効にする。
  - Workflow のエージェントの tool 呼び出しに `agent_id` が入るかは確かめていない。入らなければ、その書き込みも拒否される。
- gate は既定で無効(3.2)なので、有効にした利用者にだけ影響する。

## 14. 既知の限界

- 定義の無い readonly の役割は `Explore` へ委譲するので、再開できない。再開が要る役割は、setup-agents で定義を作る。
- `omitClaudeMd` と 1 時間のキャッシュは、定義の frontmatter でしか効かない。ビルトインへの委譲には当たらない。
- 1 時間のキャッシュは、`FORCE_PROMPT_CACHING_5M`・`CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`・設定の `subagentPromptCacheTtl` に負ける。サブスクリプションの使用クレジットを消費している間も効かない。
- 再レビューが起きない巡では、1 時間のキャッシュの書き込みが 5 分のときの 1.6 倍になる(4.3)。
- 実装の委譲先を 5 分を超えてから再開すると、キャッシュが切れていて、履歴の全体を書き込み直す(1.25 倍)。実装の役割には 1 時間のキャッシュを付けない(D4)ので、この費用は残る。修正の依頼の再開は、新しい起動より高くなりうる(4.1)。
- 再開した再レビューのレビュアーは、前の巡の自分の指摘を覚えている。修正の確認には向くが、新しい目で読み直すことにはならない。
- fork は親の effort で動き、定義の `tools` と本文を通らない。fork の担い手の制約は、依頼文の冒頭の指示と転記だけで担保する。
- complex-impl の実行モデルが担当表の Opus のとき(定義が無いか、`inherit`・未宣言の定義)は、fork が起きるのは Opus のオーケストレーターだけである。
- レビューの対象をコミットで渡す(J20)ので、まだコミットされていない変更はレビューの対象に入らない。コミットを禁じるプロジェクトでは作業ツリーの差分で渡すので、並行する委譲先の変更が混ざりうる。
- 「同じ目的の手順が重なる」(J22)かどうかは、オーケストレーターが判断する。rules が名前を挙げて起動を求めるスキル(J24)が独自の確認の手順を持つと、重なりとみなしてレビューを外す判断が分かれうる(S6)。
- 規律の変更(4.1・4.2・5 章・6.1 の転記の条項)はプラグインの更新で届くが、生成済みの定義の `_common.md` と Output Format は、setup-agents を再実行するまで古いままになる。前置きに入る `:9` の条項は、置き換えの質問で置き換えを選ばない限り入らない。プロジェクトの `_common.md` でセクションを差し替えた利用者と、訳し直していない ja・en 以外の利用者には、再実行しても入らない(9 章)。
- 6.1 の `:14` の改め方は、外側の手順の外でも、依頼文が作業と書いてよい範囲を列挙すれば効く。オーケストレーターが役割を取り違えて委譲しても、委譲先は役割の範囲を理由に断らない。役割断片の安全弁(6.2)は残るので、安いモデルが担えない作業は断られる。
- 外側の手順のレビューと承認が規律と両立しなければ、§設計・実装計画の規律 の 2 つのレビューは外れる。codiel 以外の手順でも、名前で起動した手順なら同じである(D12)。
- 「両立しない」かどうかは、オーケストレーターが判断する。判断が分かれうる対立は、5.1 の表に例として足していく。
- D11 のレビューと修正には上限が無く、人のいないセッションで止める仕組みも足さない(D20)。critical・high の指摘が出続けると、レビューと修正が止まらない。外側の手順が上限を定めていれば、外側の手順に従う間はその上限が効く。codiel は上限を外して同じ向きの回し方にした(codiel 1.1・1.2・2.0 の設計書、作業ツリーで改め済み)ので、codiel の中でも止まらない。
- ラウンドの数は、オーケストレーターが会話に残す数に頼る。会話の圧縮で数を失うと、4 ラウンド目・6 ラウンド目の判定がずれうる。
- 判断を仰いだら答えを待つ(4.1)ので、人のいないセッションで外側の手順が仰ぎ方を定めていなければ、そこで止まる。
- 4 ラウンド以上は、2 ラウンドごとに escalation(担当表では Fable・high)を新しい文脈で起動し直す(D20)。ループが長引くほど、起動のたびに試行履歴を読み直す費用が積み上がる。
- 選び直しの候補が尽きた作業(D17)は、委譲されない。外側の手順の中では外側の手順の既定の担い手が、外側の手順の外ではオーケストレーターが行う。役割のモデルで作業させたい利用者は、起動の指定を自分で示す。
- 「サブエージェントは Agent ツールでさらに委譲しない」(J16)は、規律の文でしか担保しない。機械的に止めたい利用者は、`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` で入れ子の起動を止められる(docs-reviewer が Context7 で確認)。README に書く。
- 設定ファイルの `maxEffortLevel`・`subagentPromptCacheTtl`・`availableModels` と、組織の effort の上限は、SessionStart が検出しない。
- delegation gate は、外側の手順がメインセッションか Workflow のエージェントに `denyGlobs` に当たるパスを書き込ませる運用と両立しない(7 章)。
