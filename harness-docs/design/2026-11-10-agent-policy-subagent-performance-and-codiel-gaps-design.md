## 1. 背景: 全部を委譲する agent-policy では、往復のたびに文脈を作り直す

agent-policy のオーケストレーターは、担当表のどの役割も自ら実行しない(`:81`)。探索・実装・レビュー・修正のすべてが、サブエージェントへの委譲になる。better-agentics のオーケストレーターは調査・設計・実装を自分で行い、委譲は review・split・stuck の 3 場面に限る。この違いを、食い違いの文書では G8 と呼んでいる。

better-agentics の設計書は、サブエージェントが遅くなり質が落ちる主な原因を、文脈の作り直しとした。fork でないサブエージェントは毎回まっさらな状態から始まり、親と別のプロンプトキャッシュを 5 分の寿命で温め直す。agent-policy ではレビューの指摘の修正も委譲するので、委譲の回数が多く、そのたびに文脈を作り直す。

一方で、better-agentics の策には、オーケストレーターが自分で作業することを前提にしたものがある。この設計書は、better-agentics の策を agent-policy に当てはまるものと当てはまらないものに分け(4 章)、あわせて食い違いの文書の agent-policy 側の項目を直す(5〜7 章)。

## 2. 目標と非目標

### 2.1 目標は、委譲の往復で文脈を作り直す回数を減らし、codiel の手順とぶつからないこと

- 指摘を直したら再レビューし、その再レビューと修正の依頼で、前の委譲先の文脈を引き継ぐ(D1・D11)。
- 仕様を書き切れない complex-impl の作業に、オーケストレーターの文脈を渡す(D2)。
- 定義の起動時の負荷と、レビュアーのキャッシュの作り直しを減らす(D3・D4)。
- 役割の model・effort・キャッシュの寿命が環境変数で上書きされているとき、利用者が気づける(D5)。
- 委譲先が、結果の無いときにも決まった形で報告する(D6)。
- codiel 1.1〜2.0 の手順の中で、agent-policy の規律が codiel の手順とぶつからない(D7・D8・D10・D12)。

### 2.2 非目標

- better-agentics の改修。食い違いの文書の better-agentics 側の項目は扱わない。
- codiel の改修。codiel への申し送りは 9 章に書くだけである。
- 委譲先の選定に Jev を使うこと。agent-policy は Jev を使わない(`grep -rni "jev\|typesafe" plugins/agent-policy` で 0 件)。
- 定義の無い readonly の役割の委譲先を、`Explore` から別のビルトインへ変えること(12 章)。

## 4. better-agentics の性能策を agent-policy に当てはめる

### 4.1 再レビューの条項を足し、再レビューと修正で前の委譲先を再開する(D1・D11)

agent-policy には再レビューの条項が無い(3.2)ので、better-agentics と同じ条項を足す(D11)。そのうえで、better-agentics の D5 の範囲(再レビュー)に、修正の依頼を加える(D1)。

- 再レビュー(D11)
  - レビューの指摘を直したら、直した指摘に critical・high・medium のどれかがあれば、同じ観点で再レビューを依頼する。low だけを直したときは、再レビューしない。
  - 最初のレビューの後の再レビューを 2 巡しても critical・high・medium の指摘が残るなら、ユーザーに判断を仰ぐ。外側の手順が人への聞き方を定めていれば、それに従う(5.1)。
  - 巡の数は、同じ観点を同じ委譲先が見る組ごとに数える。
  - 重大度は、レビューの 5 役割の Output Format で付けさせる(4.5、J18)。委譲先が重大度を返さないとき(再生成していない定義、合成で起動した外部定義など)は、オーケストレーターが指摘ごとに判定する。要件を満たさない・動かない・安全を損なう指摘は critical か high、誤解や後の不具合を招く指摘は medium、表記や体裁だけの指摘は low とする。
- 再開(D1)
  - 再レビューは、前の巡のレビュアーへ SendMessage で続きを頼む。送るのは、直した後の差分の取り方か文書のパスと、満たすべき要件だけとする。指摘の採否や自分の結論は送らない。`:222` の「他のレビューの指摘は渡さない」と同じ考え方である。
  - レビューの対象のコードの差分は、コミットの範囲(`git diff <base>..<head>`)で渡す。作業ツリーの差分を渡すと、並行して動く別の委譲先の変更まで対象に入る(J20)。
  - レビューの指摘の修正を委譲するときは、5 軸で役割を決め直す。決めた役割の ID が、その変更を書いた実装の委譲先の役割の ID と同じなら、その委譲先を再開する。
  - 役割が変わるときは、新しく起動する。差し戻しで役割を上げるとき(`:130-131`)もこれに当たる。
  - 再開するときは、`:47` の「候補から 1 件を選ぶことと起動形態を決めることを委譲のたびに行う」を当てない。前の委譲で選んだ定義と起動形態を引き継ぐ。
  - 再開できないときは、前と同じ委譲先と起動形態で新しく起動する。依頼文は最初の巡と同じ形にし、`:136-146` の項目と、直した後のレビューの対象を入れる。`Explore`・`Plan` へ委譲していたときは再開できない(3.1)。合成で起動した定義、custom 構成の外部ベンダーのモデルの定義、fork で再開できるかは、S2 で確かめる。再開がエラーになったときも、新しく起動する。
- 規律への置き場所は、§モデル別役割の運用 の差し戻しの経路(`:130-131`)の直後とする。

修正の依頼で実装の委譲先を再開すると、委譲先は自分の書いたコードと読んだファイルを覚えている。一方、レビューと採否の判断を挟むので、再開までの間は 5 分を超えやすい。そのときはキャッシュが切れていて、履歴の全体を書き込み直す。修正の依頼の再開で見込めるのは文脈を保つ利点で、費用は新しく起動するより高くなりうると推定する(14 章)。

### 4.2 fork は complex-impl に限り、オーケストレーターの規律を依頼文の冒頭で外す(D2)

agent-policy では、fork の会話の履歴に方針スキルの規律(担当表の役割を自ら実行しない・委譲先の解決)が入っている。fork がそれに従って、さらに委譲しかねない。fork は親のツールを持つので Agent ツールも持つ。ただし Agent ツールを持つのは、ビルトインの `general-purpose` への委譲でも同じである(3.2)。この穴は、§サブエージェントの規律 に足す条項(6.1、J16)で両方の経路について塞ぐ。

それでも complex-impl に使うのは、オーケストレーターの文脈が役立つ場面があるためである。オーケストレーターはコードを読まないが、要件の確定・探索の報告・設計の判断の経緯は会話に残っている。仕様を文書に固定できない complex-impl の作業(`:124`)では、それが依頼文に書き切れない材料になる。normal-impl は「仕様と設計が済んだ実装」(`:118`)なので、文脈が要る場面が無い。

fork するのは、次をすべて満たすときだけとする。

- 5 軸で complex-impl に当たり、判断部分の成果を文書に固定できず、作業の全体を complex-impl に任せる(`:124`)。
- complex-impl の委譲先の実行モデルが、オーケストレーター自身のモデルと同じである(J1)。実行モデルは、§委譲先の実行モデルの確定 でその委譲に決まるモデルである。
- 外側の手順のスクリプトへ渡す作業ではない(J3)。

fork の起動が拒否されたとき(fork を止める設定があるとき)は、complex-impl の通常の起動に戻す(J2)。

fork の依頼文の冒頭には、次を置く(J4)。

- fork された complex-impl の担い手であること。会話の履歴にあるオーケストレーターの規律(委譲・担当表の役割を自ら実行しない・委譲先の解決)を当てず、依頼文の作業だけを行うこと。
- 使ってよいツールは、選んだ complex-impl の定義の `tools` に限ること。定義が無いときは、complex-impl の役割断片の `tools` に限る。custom-policy の「この tools のみ使用」の明記(`skills/custom-policy/SKILL.md:18`)に当たる。
- 選んだ complex-impl の定義の本文(frontmatter より後の全文)。定義が無いときは、complex-impl の役割断片の本文とし、置き場所の選び方はビルトインへ委譲するときと同じ(`:75-76`)とする。プロジェクトに最適化された定義を、同梱の断片より優先する(2026-09-29 の設計書 4.7 と同じ考え方)。
- 規律の「サブエージェントは〜」で始まる条項(`:145` の転記)。J16 の Agent ツールの条項も、ここに入る。

fork は親の effort で動き、complex-impl の effort(medium)は使われない。README で利用者に知らせる。complex-impl の定義が無いときや、定義が `inherit`・未宣言でモデル注入起動になるときは、実行モデルは担当表の Opus である。このときは Opus のオーケストレーターだけが fork の条件を満たす。プロジェクトの complex-impl の定義が `model: sonnet` などを宣言していれば、その値と比べる。

### 4.3 setup-agents で `omitClaudeMd` を聞き、レビューの定義に 1 時間のキャッシュを書く(D3・D4)

2 つのキーは、テンプレート(`compose`)に出さない。専用の処理が、生成の前に既存のファイルから 2 つのキーの値を読み、生成と保持マージの後に、決めた値を行単位で書き込む(J17)。保持マージの自動保持は変えない。ステップ 5b の「完全上書き」でも、質問で答えていない `omitClaudeMd` と、`experimental` の他の下位キーは、生成の前に読んだ値で書き戻す。

- `omitClaudeMd`(D3)
  - 新規生成(ステップ 5n)では、役割ごとに付けるかを聞く。
  - 再生成で個別に調整する定義(ステップ 5b)では、既存の値を示して聞く。
  - 聞き方: `AskUserQuestion` で「付けない」「付ける」を出す。推奨の側を先頭に置いて「(推奨)」を付ける。既存の値があるときは、その側の説明に「現在の値」と書く。
  - 推奨は、knowledge-elicitation では「付ける」、それ以外では「付けない」とする。複数の役割を持つ定義の扱いは J5 に書く。
  - 選択肢の説明には、プロジェクトの CLAUDE.md・`.claude/rules/`(規約・保護パスの指定を含む)・ユーザーの rules が届かなくなることを書く。
  - 「付ける」なら `omitClaudeMd: true` を書き、「付けない」なら既存の行を消す。
  - 質問しない経路(個別に調整しない再生成、`--yes`、`--recommended`)の扱いは J7 に書く。
- `experimental.cacheTtl: 1h`(D4)
  - レビューの 5 役割の定義で、Claude のモデルで動くものには、聞かずに書く。Claude のモデルで動くかの判定は、規律 §委譲先の候補 と同じとする(`:31`。`sonnet`・`opus`・`haiku`・`fable`・`inherit`・未宣言のどれかで、`agent-policy-vendor` が未宣言・`claude`・`none` のどれか)。

  - 既存の `experimental` の他の下位キーは残す。
  - レビューの役割を持たない定義では、`experimental` に触れない。
- ステップ 7 の報告に、2 つのキーを書き込んだ・書き換えた・消した定義を載せる。
- 規律の起動形態の判定表の 3 行目(`:173`)の許可一覧に、`omitClaudeMd` と `experimental` を足す(J8)。

1 時間のキャッシュが得になるのは、再レビューが 5 分を超えてから起きるときだけである(better-agentics の設計書 14 章)。D11 で、critical・high・medium を直したら再レビューが起きる。agent-policy では修正も委譲するので、その間は 5 分を超えやすいと推定する。再レビューが起きない巡では、レビュアーの接頭辞の書き込みが 5 分のときの 1.6 倍(2.0 / 1.25)になる。

## 5. 外側の手順に従う条項を、規律の全体へ広げる(D7・D12)

### 5.1 「外側の手順」と、置き換わる規律

- 「外側の手順」は、このプラグインの外のスキルやコマンドが定める手順である。ユーザーか、セッションを起動した指示(プロンプト)が、名前で起動したものに限る(D12)。Claude が description を見て自分から読み込んだスキルは含めない。
- 「名前で起動した」には、次の 3 つを含める。
  - ユーザーがスラッシュコマンドで起動したもの
  - ユーザーが会話でスキルの名前を挙げて使うよう求め、Claude が起動したもの
  - CLAUDE.md・rules・hook の注入文が名前を挙げて起動を求め、Claude が起動したもの(ユーザーが置いた指示であるため)
- 名前で起動した手順が、その中で名指しして起動させるスキルの手順も、外側の手順に含める。コマンドがスキルを名指しし、そのスキルがさらに別のスキルを名指しする連鎖を、1 つの外側の手順として扱う。
- 当てるのは、オーケストレーターがその手順に沿って作業している間である。手順の最後のステップを終えたとき、またはユーザーが手順を止めたときに終わる。オーケストレーターは自分がスキルを起動したことを会話から知れるので、別の信号は設けない。会話が圧縮された後は、要約に手順の作業が続いていると残っていれば、続いているとみなす。
- `:81` の「コマンドで起動したスキルの手順(スキル駆動のワークフロー)」を、この語に置き換える。
- 外側の手順が担い手を「定めた」とみなすのは、作業ごとに誰が行うか(オーケストレーター自身が行う、委譲せずに行う、など)を明記しているときだけとする(J14)。「自分で作業するときは〜」「委譲する場合は〜」のように、担い手を条件として書いた手順は、担い手を定めていない。そのときは、`:81` のとおり委譲する。
- agent-policy の規律(skills・references・assets)には、codiel の名前も codiel 固有の語も書かない(ARCHITECTURE の指示層・参照層の規則)。この設計書の codiel への言及は、規律を決めた根拠であり、規律の文面には写さない。
- 外側の手順が次の表の事項を定めているときは、外側の手順に従い、表の右の規律を当てない。外側の手順が定めていない事項には、現行の規律を当てる。
- 規律の文面に写すのは、表の左の 2 列(定める事項と、当てなくなる規律)だけとする。「食い違い」の列は、この設計書の照合のための列である。

| 外側の手順が定める事項 | 当てなくなる規律 | 食い違い |
| --- | --- | --- |
| 作業の担い手(オーケストレーター自身が行う作業を含む) | `:81` の「担当表の全役割はサブエージェントが担い、オーケストレーターはそのどれも自ら実行しない」。`:215` の探索の委譲 | G8 |
| 委譲する作業の単位と、委譲先に任せる判断 | `:105` の「その役割タスクのみを担当する」。`:121-124` の分解の規定 | G3(オーケストレーター側) |
| 文書の書き手、レビューの時点・方法・順序、承認 | §設計・実装計画の規律(`:220-224`)。4.1 の再レビューの条項 | G6 |
| 並列に進める範囲と条件 | `:137` の「独立したタスクを並列に起動する」 | G10 |
| 人への聞き方と報告の仕方(人の判断の代わりに別の仕組みで判断する定めを含む) | `:91` の `AskUserQuestion`、`:209` の MCP サーバーの付与の提案、`:223` のユーザーの承認、4.1 の「2 巡しても残ればユーザーに判断を仰ぐ」 | G4 |

## 7. delegation gate は、外側の手順と両立しないことを README に書く(G11、D10)

- gate は PreToolUse の hook なので、規律の「外側の手順に従う」条項(D7)では止まらない。
- 2026-09-30 の hook の棚卸しで、一時解除(`--direct`・TTL)は廃止された(コミット bbd7ffcc)。理由は 2 つある。
  - 利用者はプラグイン同梱のスクリプトの絶対パスを知らず、実行できない(ユーザーの指摘)。
  - 拒否理由に実行できるコマンドを載せると、AI が自分で解除できてしまう。
  - 解除の手段は、`AMATSUKA_AGENT_DELEGATION_GATE` を外してセッションを再起動する方法だけになった。
- この改修では gate のコードを変えない。README の gate の説明に、次を書く。
  - 外側の手順のスクリプトは、エージェントを起動して書き込ませることがある。外側の手順がメインセッションに書き込ませることもある。どちらの運用でも、書き込む先が `denyGlobs` に当たると、gate は拒否する。gate は、プロジェクトのルートに設定ファイルがあり、書き込む先が `denyGlobs` に当たるときだけ拒否する(`src/hooks/delegation-gate.ts:249-270`)。
  - そうした運用のセッションでは、`AMATSUKA_AGENT_DELEGATION_GATE` を外して gate を無効にする。
  - Workflow のエージェントの tool 呼び出しに `agent_id` が入るかは確かめていない。入らなければ、その書き込みも拒否される。
- gate は既定で無効(3.2)なので、有効にした利用者にだけ影響する。

## 14. 既知の限界

- 定義の無い readonly の役割は `Explore` へ委譲するので、再開できない。再開が要る役割は、setup-agents で定義を作る。
- `omitClaudeMd` と 1 時間のキャッシュは、定義の frontmatter でしか効かない。ビルトインへの委譲には当たらない。
- 1 時間のキャッシュは、`FORCE_PROMPT_CACHING_5M`・`CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`・設定の `subagentPromptCacheTtl` に負ける。サブスクリプションの使用クレジットを消費している間も効かない。
- 再レビューが起きない巡では、1 時間のキャッシュの書き込みが 5 分のときの 1.6 倍になる(4.3)。
- 実装の委譲先を 5 分を超えてから再開すると、キャッシュが切れていて、履歴の全体を書き込み直す(1.25 倍)。実装の役割には 1 時間のキャッシュを付けない(D4)ので、この費用は残る。修正の依頼の再開は、新しい起動より高くなりうる(4.1)。
- 再開した再レビューのレビュアーは、前の巡の自分の指摘を覚えている。修正の確認には向くが、新しい目で読み直すことにはならない。
- fork は親の effort で動き、定義の `tools` と本文を通らない。fork の担い手の制約は、依頼文の冒頭の指示と転記だけで担保する。
- complex-impl の実行モデルが担当表の Opus のとき(定義が無いか、`inherit`・未宣言の定義)は、fork が起きるのは Opus のオーケストレーターだけである。
- レビューの対象をコミットの範囲で渡す(J20)ので、まだコミットされていない変更はレビューの対象に入らない。
- 規律の変更(4.1・4.2・5 章・6.1 の転記の条項)はプラグインの更新で届くが、生成済みの定義の `_common.md` と Output Format は、setup-agents を再実行するまで古いままになる。前置きに入る `:9` の条項は、置き換えの質問で置き換えを選ばない限り入らない。プロジェクトの `_common.md` でセクションを差し替えた利用者と、訳し直していない ja・en 以外の利用者には、再実行しても入らない(9 章)。
- 6.1 の `:14` の改め方は、外側の手順の外でも、依頼文が作業と書いてよい範囲を列挙すれば効く。オーケストレーターが役割を取り違えて委譲しても、委譲先は役割の範囲を理由に断らない。役割断片の安全弁(6.2)は残るので、安いモデルが担えない作業は断られる。
- 外側の手順がレビューと承認を定めていれば、§設計・実装計画の規律 の 2 つのレビューは外れる。codiel 以外の手順でも、名前で起動した手順なら同じである(D12)。
- 設定ファイルの `maxEffortLevel`・`subagentPromptCacheTtl`・`availableModels` と、組織の effort の上限は、SessionStart が検出しない。
- delegation gate は、外側の手順がメインセッションか Workflow のエージェントに `denyGlobs` に当たるパスを書き込ませる運用と両立しない(7 章)。
