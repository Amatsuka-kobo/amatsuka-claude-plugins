## 0. v3 からの変更点(v4 changelog)

v3 の精査(Haiku レビュー+オーケストレーター照合)と、その後の深堀り(「逆流」の由来 → 順番付きフロー自体の見直し)を受けて改訂した。

1. **順番付きフロー(step 1〜6)の廃止を決定**(新設の論点E・§3.1)。SKILL 2件の「設計・実装計画のフロー」節は宣言的規則群へ書き換える。役割分担(誰が設計し・実装し・レビューするか)は変えない。
2. **「逆流」概念の解消**: フロー廃止により、探索 → 要件への還元は例外(逆流)ではなく context-map の主目的として、事前条件の形で表現する(§3.1 の要件確定規則)。v3 §5 脚注で予定していた「チェックポイント → フロー step の橋渡し表」は不要となり削除。
3. **チェックポイントごとの主担当を明記**(§3.4 の表に主担当列を追加)。v3 精査の要修正指摘(v3 §3.2 と §3.3 でオーケストレーターの読む深さの定義にゆれ)の解消。
4. **guide 冒頭(:7)の定義文を変更対象に明記**(§5)。v3 精査の推奨指摘の反映。
5. **モデル名から役割名への正規化**(ユーザー指摘): 規範文の主語を「Fable」等の固定モデル名から「オーケストレーター」等の役割名に統一。オーケストレーターになりうるのは構造的に全モデルであり、役割 → モデルの割り当ては各方針(SKILL)の担当表が与える。コスト分析の数値は「単価が最も高い具体例」として Fable を基準に残す。

## 1. 背景と問題

context-map の「共有先」の記述は現在4箇所+テンプレに散在しており(論点メモ §1)、次の未解決課題があった。

- **論点A**: 作成者を共有先に含める冗長性(claude-only の「Fable / Opus に共有」は Opus→Opus の自己共有を含む)。
- **論点B**: 「Sol に共有するか」— 作成者としての自己共有(不要)と、下流設計者への共有(フォールバック時に要る)の混同。
- **論点C**: 上流共有(オーケストレーター向け)と下流共有(設計・実装向け)の未分離。
- **論点D**: 「必ず共有(must)」という強制語が、コスト上不要な広域共有を促していないか。
- **論点E(v4 追加)**: 順番付きフロー(step 1〜6)自体の過剰定義。従来方針 `agents-with-codex.md`(全21行)は「役割の割り当て+成果物ごとの事前条件+横断規則」だけで順番定義を持たず、そのレベルで意図どおり機能していた。v3 精査で検出された問題 —「逆流」・橋渡し表・読む深さの記述ゆれ — はいずれも順番付きフローの導入が原因で、フローが無ければ発生しない。

加えて、現行記述「作成した context-map を **Fable / Opus に必ず共有**する」は、トークンコスト分析の結論「最優先レバー=**Fable の文脈を軽く保つ**($2/ターンの支配項)」と一見衝突していた。

## 2. 設計由来(評価軸の起点)

再設計の判断軸は、context-map の**存在理由**から導く。

> Fable が全体オーケストレーションを行う際、要件定義の前に現状のフォルダ構成などを確認するフェーズが発生する。これを Fable 自身にやらせるのはトークンの浪費でコストパフォーマンスが悪い。そこで**より軽量なモデルにファイル探索を行わせ、context-map として圧縮**することでコストを抑える。

つまり context-map は **「オーケストレーターが生探索を避けるための圧縮成果物(コスト最適化装置)」** である。この由来から2つの帰結が出る。

1. **オーケストレーターが map を読むことこそが設計目標**であり、避けるべきは「オーケストレーターが生ファイルを読む/保持する」方。map の全文をオーケストレーターに積むこと自体は敵ではない(map が十分小さい限り)。※引用中の「Fable」は、この役割を担うモデルのうち単価が最も高い具体例である(オーケストレーターの一般化は §3.0)。
2. したがって設計判断の本質は **「誰に共有するか」より前に「どれだけ圧縮されているか」**。圧縮が効いている限り、オーケストレーターが map を読むのは安く正しい。**肥大した map(ダンプ)は、map が消すはずのコストを再導入する最大の失敗モード**。

さらに v4 で明確化した帰結がある。上の由来のとおり、**探索は要件定義フェーズの内部で発生する**(オーケストレーターが要件を固める前に現状把握が要る)。v3 は SKILL のフロー番号(step 1=要件 → step 2=探索)を正として、この還元を「step 2 → step 1 への逆流」と表現したが、実態の順序は「暫定要件 → 探索 → 要件確定」であり、**還元は例外ではなく context-map の主目的そのもの**である。番号付きの台本を廃止すれば、この現象を「逆流」と呼ぶ必要自体が消える。

### Fable 規律との整合

context-map は `fable-subagents` §5「大量に読む調査は読む作業ごと外に出し、**蒸留された結論だけ**を受け取る」の**永続化**にあたる。探索サブエージェント(軽量モデル)が使者、map が蒸留された報告書、map 作成者(設計担当)が蒸留者。本設計はこの規律をその場の受け答えではなくファイルとして固定したものとして扱う。

## 3. 決定: 統合モデル v4

### 原則

- **① まず圧縮(生産側)→ ② 次に読む深さ(消費側)**、の順で定義する。「読む深さ = そのエージェントが map をその瞬間どう使うか」で決まる(役割の固定ラベルではなく用途で決まる)。
- **規則は宣言的に書く**。順番の台本(step 番号)ではなく、役割の割り当てと成果物ごとの事前条件で表現する(従来方針 `agents-with-codex.md` が機能していた形式)。

### 3.0 用語

- **オーケストレーター**: セッションを主導し、dispatch・要件確定・承認を行う**役割**。モデル名ではない。構造的にはどのモデルもこの役割に就きうる。本設計では2層を区別する — **最上位オーケストレーター**(要件確定・承認ゲート担当)と**戦術オーケストレーター**(中間統括・重い最終レビュー担当)。役割 → モデルの割り当ては各 SKILL の担当表が与える(with-codex / claude-only 方針の典型は 最上位=Fable、戦術=Opus)。本設計の規範文はすべて役割名で書く。
- **所在通知**: dispatch の依頼文や報告に map の**ファイルパスを含める**こと。map 本文の貼り付けではない。
- **(全文)参照**: **蒸留済み map の全セクションを読む**こと。**生コードの全文ではない**(生探索は生産時に軽量モデルへ外注済み)。
- **蒸留**: 生探索の結果を、判断に要る最小限へ要約・構造化して map に落とすこと。ダンプ(全部貼り)の反対。**生産時**(map 作成時)の圧縮を指す。
- **要約(上流報告)**: 蒸留済み map のうち **§未解決事項を上流(オーケストレーター)への報告に載せる**行為。蒸留とは別の瞬間(消費時)に起きる二次圧縮であり、対象は §未解決事項(とその差分)に限る。テンプレートの Open Questions 表がその原文にあたる。

### 3.1 前提: 順番付きフローの廃止(宣言的規則への置換)

SKILL 2件の「設計・実装計画のフロー」(with-codex :37-46 / claude-only :27-34 の step 1〜6)を廃止し、次の宣言的規則群に置き換える。**役割分担(担当表・実装フェーズ・レビュー運用の各節)は変えない** — 変えるのはフロー節の表現形式のみ。

順序は「台本」ではなく「**成果物ごとの事前条件**」としてのみ残す。各規則は独立の条件であり、**列挙順に実行順の意味は無い**(SKILL へ書き換える際も番号ではなく箇条書きとし、順序の含意を持たせない):

- **規則: 要件確定の事前条件** — Blueprint(高レベル要件)は暫定として出発してよい。コードベース探索を伴うタスクでは、context-map の §未解決事項の要約(上流報告)を受けて要件を確定する(= v3 の「逆流」の宣言的表現。§3.4 ①)。
- **規則: 設計・実装着手の事前条件** — コードベース探索を伴う設計・実装は、context-map の作成後に着手する(作成契機の判定は guide 既定のまま)。
- **規則: ユーザーレビューの事前条件** — 設計書・実装計画書は、ユーザーレビューの前に Haiku レビュー(理解+暗黙知・矛盾抽出)→ 補足修正(戦術オーケストレーター)を通す(従来方針から継続の必須手順。Haiku レビューはレビュー手法の固有名であり、with-codex 構成でも GPT Luna に置き換えない)。
- **規則: 計画確定の事前条件** — 実装への移行は、最上位オーケストレーターの承認(Approve: 計画が全体要件を満たすことの確認)を経る。

これら以外の順序(たとえば探索と要件定義の厳密な前後関係)は規定しない。

なお「承認(計画の確定ゲート)」と「最終レビュー(実装完了後の品質確認。§3.4 ③)」は**別の行為**である。前者は計画フェーズの出口で最上位オーケストレーターが担い、後者はレビュー運用の既定どおり戦術オーケストレーター優先で行う。

### 3.2 生産側の規律(本質・最優先)

- 生ファイル読みは探索担当の軽量モデル(with-codex=Luna/Terra / claude-only=Sonnet/Haiku)へ外注し、**map 作成者(with-codex=Sol / claude-only=Opus)が蒸留**して map 化する。
- map は**ダンプではなく蒸留**。オーケストレーターが一度読んで安い程度に小さく保つ。
- **「肥大した map」を最大の失敗モードとして明記**する。map が大きくなったら、それは圧縮(蒸留)の失敗であり、共有可否の問題ではない。

### 3.3 消費側の読む深さ

| 対象 | 読む深さ | 根拠 |
|---|---|---|
| **オーケストレーター**(最上位・戦術) | 圧縮された map を**読む**(= 生探索の代替、設計目標)。チェックポイントごとの主担当・参照セクションは §3.4 の表に従う | map の主要消費者。読むこと自体がコスト削減 |
| **設計担当**(with-codex=Sol / claude-only=Opus) | **蒸留済み map の全文**を参照(生コード全文ではない)。多くは**作成者と同一**なので追加ロード不要 | 全体構造が設計判断に直接効く。生ファイル探索は生産時に軽量モデルへ外注済み |
| **実装担当**(Terra / Luna / Sonnet) | map 全体は渡さず**断片(必要セクション)のみ**ブリーフに転記 | 自己完結ブリーフで足り、広域共有はコスト増 |
| **作成者** | 自己共有は不要(既に文脈内)。**作成者 ≠ 下流設計者**になった場合(GPT不在フォールバック等)だけ、次の dispatch にパスを渡す | 論点A・Bの解 |

### 3.4 オーケストレーターの3チェックポイント

同じオーケストレーターでも、map に触れる「瞬間」で用途と読む深さが変わる。チェックポイントは**作業フェーズ(要件 → 設計 → 実装 → レビュー)の進行に沿って自然に現れる**(オーケストレーターが明示宣言するのではない)。フロー step への対応付けは不要 — フロー自体を廃止したため。

| チェックポイント | 作業フェーズ | 主担当 | map の役割 | 主に読むセクション | 深さ |
|---|---|---|---|---|---|
| **① 要件精緻化**(map 作成直後) | 要件定義 | **最上位オーケストレーター** | 探索 → 要件確定の入力(§3.1 要件確定規則) | **§未解決事項(最重要)**・§既存契約・§影響範囲 | 作成者が §未解決事項を**要約で必ず上げる**。最上位オーケストレーターは要約で受け、判断に必要なときだけ該当セクションを参照 |
| **② 計画承認**(設計書/WBS 完成時。§3.1 計画確定規則の Approve と同一の瞬間) | 設計 | **最上位オーケストレーター**(承認ゲート) | 設計書/WBS の背景資料 | 要約(§未解決事項を前面に) | 所在通知＋オンデマンド全文(承認判断に必要なときだけ map 全文を読む) |
| **③ 最終レビュー**(全実装後) | レビュー | **戦術オーケストレーター優先**(最上位は直接レビュー時のみ) | カバレッジ/契約の**照合リスト** | §影響範囲・§既存契約・§未解決事項・§テスト方法 | 能動参照(one-shot・有界) |

- **上流へ伝わる本体は §未解決事項**。設計担当が map を更新して未解決事項が動いたら、その**差分だけ**を要約で上げればよい(map 全文の再共有ではない)。これが論点B「上流再共有」の解。
- ③最終レビューは通常**作業フェーズ最終段の1回**であり、dispatch ごとに繰り返すものではない。だから map 読みは one-shot の有界読み込みで、コスト病理(毎ターンのカタログ × ターン数 × dispatch 回数)には当たらない。

### 3.5 強制語の置換

「必ず共有する(must)」を撤回し、次に置き換える。

> map の**所在(パス)の通知は必須**。**読む深さは役割・チェックポイントに応じる**。ただし **map を小さく(蒸留された状態に)保つことが最優先の規律**である。

## 4. 各論点の解決(対応表)

| 論点 | v4 での解決 |
|---|---|
| A(自己共有の冗長) | ファイルモデルで自明に解消。「作成者は自分で書いたので読み直し不要」。§3.3 作成者行で表現 |
| B(Sol に共有?) | 作成者=消費者で同一なら不要。作成者≠下流設計者の時だけパスを渡す、と一般化。上流再共有は §未解決事項の差分のみ |
| C(上流/下流) | 「オーケストレーター=蒸留 map を読む/設計担当=全文/実装担当=断片」+ オーケストレーターの3チェックポイント(主担当付き)に再構成 |
| D(コスト) | 敵は「オーケストレーターが map を読むこと」ではなく「肥大 map」と「毎ターン常駐・広域共有」。生産側=蒸留規律、消費側=実装者は断片、で対処。強制語を緩和 |
| E(フローの過剰定義) | step 1〜6 を廃止し §3.1 の宣言的規則4つ(成果物ごとの事前条件)へ置換。「逆流」「橋渡し表」「読む深さのゆれ」は発生源ごと解消 |

論点メモ §3 の3択(①現状維持/②最小化/③上下分離)は、この「圧縮 × チェックポイント」軸に吸収されて役目を終える。

## 6. 非目標・残課題

- **肥大 map を防ぐ具体的な数値基準**(行数/トークン上限など)は本設計では定めない。運用で蒸留品質を見ながら別途詰める。まずは「ダンプではなく蒸留」という規律の明文化に留める。
- 断片転記の具体運用(どのセクションを実装者ブリーフに写すかの標準)は、実装フェーズで guide に例示する。
- **上流再共有の「差分」記述の形式**も実装フェーズで定める。差分記述それ自体が新たな文脈コストになりうるため、§未解決事項の更新は簡潔に保つ(長い changelog 化を避ける)方針だけ先に置く。
- SKILL のフロー節**以外**の節(基本原則・担当表・実装フェーズ・レビュー運用・アドバイザー運用・役割 Agents 併用)は本設計の対象外であり変更しない。
- オーケストレーター文脈の総合軽量化(MCP 遅延ロード等)はトークン分析メモの管轄で、本設計の範囲外。
