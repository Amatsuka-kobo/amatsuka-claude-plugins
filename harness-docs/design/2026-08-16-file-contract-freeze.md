- 作成日: 2026-08-16
- ステータス: 凍結(実装中は変更しない)
- 出典: `harness-docs/design/2026-08-16-metatron-design.md` §5・§6・§7・§8、

- 適用範囲: `plugins/metatron/`、`plugins/codiel/`、`plugins/sandalphon/`、`plugins/gh-utility/`

## この文書の位置づけ

metatron / codiel / sandalphon の 3 プラグインは、互いのインストールパスを解決できない。
したがってソースを共有せず、**同じ規則を独立に 3 回実装する**。
本書はその規則の唯一の写しであり、実装中に参照する基準である。

実装者はこのファイルを直接読む。設計書からの要約を受け取って作業しない。
要約が実装ごとに違えば、契約が割れる。

本書の内容を変更する必要が生じたときは、実装を止めてユーザーに確認する。

## 1. マーカー名

ドメインマップの機械可読ブロックの開始行を次に固定する。

````
```json metatron:domains
````

- 旧マーカー `codiel:domains` は**読まない**。互換読み・移行スクリプト・二重マーカー対応を一切設けない。
- 抽出は開始行と終了フェンスの間の文字列を JSON として解釈する。
- **終了フェンスの判定は §4-2 の規則 2 と同一**とする(開始と同じ文字を開始と同数以上連続させ、
  その後に info string を持たない行)。開始行・終了行の認識も §4-2 の正規化(インデント許容・
  改行コード・末尾空白の扱い)に従う。独自のフェンス判定を書かない。
- データ形式は `{ "<ドメイン名>": ["<glob>", ...] }`。

- **同一ファイル内にブロックが 2 個以上あるときは、最初のものを採る。**
  警告は経路を問わず返す(書き込み経路も読み取り経路も拒否しない)。
  重複は異常な状態であり、気づける形にしておく価値が、警告 1 行のコストを上回る。
  注入経路では他の警告と合わせて上限行数に収まるため、予算を圧迫しない。
  §4-2 の同名見出しの扱いと同型にする。ブロックだけを別扱いにすると、
  同じ「重複」という事象に 2 通りの規則が並ぶ。
  読み取りをエラーにしないのは、注入がフェイルオープンでなければならないためである(§12)。

```json metatron:domains
{
  "frontend": ["src/app/**", "src/components/**"],
  "backend": ["src/server/**", "src/api/**"],
  "data": ["prisma/**", "db/**"]
}
```

- ドメイン名は任意の文字列。`frontend` / `backend` / `data` は例であり固定語彙ではない。
- 分割が馴染まないプロジェクトは `{ "generic": ["**"] }` に縮退させる。

- **開始マーカーが他のフェンスに取り込まれ、ブロックとして認識されないときは警告を返す。**
  例: マーカーより前に閉じられていないフェンスがあり、マーカー行がその内側に入る場合。
  この状態は「ブロックが無い」のと結果は同じ(`null` を返す)が、**原因がまったく違う**。
  前者は書き手が意図してブロックを置いたのに読めていない状態であり、
  後者は最小 ARCHITECTURE のような正当な状態である。区別せずに黙って `null` を返すと、
  書き手は自分のブロックが読まれていないことに気づけない。
  警告は経路を問わず返す(読み取り・注入経路も含む。拒否はしない)。

- **例外(PreToolUse hook の限界)。** codiel の `guard-write` が出せるのは
  `deny` / `ask` / 無出力の 3 つだけで、「素通しするが警告はある」を表現する口が無い。
  そのため**素通しする書き込みでは警告が届かない**。この 1 点だけを限界として認め、
  素通しを ask へ格上げして届けることはしない(警告は拒否の理由ではない)。
  警告が届く経路は次の 3 つである。
  - CLI(`readDomainsResult` を直接呼ぶ経路)
  - skills の検証コマンド(codiel `initializing-harness` の手順 5、`orchestrating-runs` の §0)
  - `ask` の理由(境界判定が誤っているかもしれない文脈に添える)

  読み取り実装(`readDomainsResult`)は経路に関わらず警告を返す。捨ててよいのは、
  出力する口を持たない呼び出し元だけである。警告を出せる呼び出し元が
  `readDomains`(警告を落とす薄いラッパ)を使うことは、この規則への違反とみなす。

### 検証(4 項目)

書き込み時に次をすべて満たすことを確認する。1 つでも反すれば書き込まない。

1. ブロック内が有効な JSON である。
2. トップレベルがオブジェクトで、配列でない。
3. 各値が 1 要素以上の文字列配列である。
4. キーが 1 個以上ある。

読み取り時にこれらを満たさない場合は「読めない」として扱い、例外を投げない。

## 2. 共有設定ファイル `metatron.config.json`

| 項目 | 決定 |
| --- | --- |
| ファイル名 | `metatron.config.json` |
| 置き場 | ルート直下(ルートの定義は §3) |
| 形式 | JSON |
| 存在の要否 | **任意**。無い場合は全項目が既定値。「設定ファイルが無い」はエラーではなく、報告もしない |

### スキーマ

```json
{
  "version": 1,
  "paths": {
    "architecture": "docs/ARCHITECTURE.md",
    "gotchas": "docs/GOTCHAS.md"
  },
  "injection": {
    "enabled": true,
    "gotchasRecentCount": 5,
    "maxChars": 9000
  }
}
```

| キー | 型 | 既定値 | 意味 |
| --- | --- | --- | --- |
| `version` | number | `1` | スキーマバージョン。未知の値なら**全項目を既定値として扱い**、警告を 1 行添える(読み手を止めない) |
| `paths.architecture` | string | `docs/ARCHITECTURE.md` | ARCHITECTURE のパス |
| `paths.gotchas` | string | `docs/GOTCHAS.md` | GOTCHAS のパス |
| `injection.enabled` | boolean | `true` | SessionStart 注入の有効/無効 |
| `injection.gotchasRecentCount` | number | `5` | 全文で注入する直近エントリ数 |
| `injection.maxChars` | number | `9000` | 注入全体の文字数上限 |

- `$schema` キーは定義しない。利用者が独自に書いた場合は**未知キーとして無視する**(エラーにしない)。
- 未知キー全般をエラーにしない。
- 壊れた JSON のときは全項目を既定値として扱い、理由を呼び出し元へ返す。例外を投げない。
- **「壊れた JSON」には構文エラーだけでなく、トップレベルがオブジェクトでない場合
  (配列・`null`・数値・文字列)も含める。** 判定を実装ごとに分けない。
  個々のキーの型不整合(例: `injection.maxChars` が文字列)は「壊れた JSON」ではなく
  **その項目だけを既定値に落とす**(未知キーと同じく全体を止めない)。

## 3. ルート解決とパス解決の規則

**この規則が契約の中核である。** パスの相対解決だけを揃えても、基準ディレクトリが実装ごとに違えば、
同じカレントディレクトリから別のファイルに辿り着く。

### 規則 1: ルート解決

カレントディレクトリ(または引数で与えられた開始ディレクトリ)から上方向に探索し、
最初に見つかったものを採る。

1. `metatron.config.json` を持つ最も近い祖先ディレクトリ
2. 無ければ `git rev-parse --show-toplevel`(リポジトリルート)
3. それも無ければ開始ディレクトリ

この結果を **`docRoot`** と呼ぶ。

#### 規則 1 の細目(3 実装で必ず一致させる)

- **開始ディレクトリ**は、引数が与えられていればその値、無ければプロセスのカレントディレクトリ
  (`process.cwd()`)である。
- **探索は開始ディレクトリ自身を候補に含める(inclusive)。** 開始ディレクトリ直下に
  `metatron.config.json` があれば、そこが `docRoot` になる。真の親からは始めない。
  (codiel の既存 `findProjectRoot` と同じ包含規則。)
- **探索を始める前に開始ディレクトリを `fs.realpathSync` で実体パスへ解決する。**
  段 2 の `git rev-parse --show-toplevel` が実体パスを返すため、段 1 を文字列の
  `path.dirname` だけで辿ると、シンボリックリンク越しに起動したとき段 1 と段 2 が
  別のディレクトリ木を辿り、実装間で `docRoot` が食い違う。
  開始ディレクトリが解決できない場合は解決前のパスをそのまま使う。
- **段 2 は必ず `git rev-parse --show-toplevel` を実行して得る。**
  `.git` を手作業で祖先探索する代替実装にしない(worktree の `.git` ファイル形式や
  `GIT_CEILING_DIRECTORIES` 等の挙動を再現できず、実装間で結果が割れるため)。
- **git の実行が失敗したときは、原因を区別せず段 3 へ進む。**
  git 未インストール(`ENOENT`)・git 管理外(exit 128)・その他の非 0 終了・タイムアウトの
  いずれも「無かった」として扱い、例外を外へ投げない。
- 段 1 の探索は、ファイルシステムのルート(それ以上親が無いディレクトリ)に達したら打ち切る。

### 規則 2: パスの解決

`paths.architecture` / `paths.gotchas` を `docRoot` からの**相対パス**として解決する。

### 規則 3: 拒否

**絶対パスと、ルートの外へ出るパス(`..` による脱出)は拒否する。**
拒否した場合はその項目だけ既定値に落とし、理由を呼び出し元へ返す。

### 規則 4: キャッシュしない

解決結果はキャッシュしない。

### 各実装の担当

| 実装 | 場所 | 備考 |
| --- | --- | --- |
| metatron | `plugins/metatron/src/lib/config.ts` | **正本の実装** |
| codiel | `plugins/codiel/src/hooks/lib.ts` の `findDocRoot` / `resolveDocPaths` | 独立実装 |
| sandalphon | `plugins/sandalphon/src/check-intent-env.ts` | 独立実装 |

### codiel における 2 つのルート概念

codiel は用途の異なる 2 つのルートを持つ。**関数名で区別し、混同しない。**

| 関数 | 基準 | 用途 |
| --- | --- | --- |
| `findDocRoot(startDir)` | 本書 §3 の規則 1(config 祖先 → git ルート → 開始ディレクトリ) | **文書**(ARCHITECTURE / GOTCHAS)の解決 |
| `findProjectRoot(startDir)` | `.codiel` を持つ祖先(現行のまま) | **codiel 固有資産**(`.codiel/runs` 等)の解決 |

どちらを使うかは「探しているものが文書か codiel 資産か」で決まる。
`guard-write` の `.codiel/runs/**/state.json` 判定など既存の用途は `findProjectRoot` のままでよい。

sandalphon は 3 つの基準を使い分ける。**どれか 1 つに寄せない。**

| 対象 | 基準 |
| --- | --- |
| intent 文書(`docs/intents/`) | `repoRoot`(git ルート) |
| ARCHITECTURE / GOTCHAS | `docRoot`(本書 §3 の規則 1) |
| `.codiel/` の有無と `runDirs` | **開始ディレクトリからの上方向探索**(codiel の `findProjectRoot` と同じ基準) |

3 者が別ディレクトリを指すのは正常な状態である。

**`.codiel` の探索を `docRoot` 直下に限定しない。** sandalphon がこの判定で答えるのは
「codiel へ委譲できるか」であり、答えるべき相手は codiel 自身の探索規則である。
`docRoot` 直下だけを見ると、`repo/.codiel/` があり `repo/sub/metatron.config.json` がある構成で
`repo/sub` から実行したとき、codiel は `repo/.codiel` を見つけて動くのに
sandalphon は「無い」と判定し、正当な委譲経路を塞ぐ。

### 一致の機械的担保

3 実装が写しを持つため、一致はテストで検証する(§12)。
これが唯一の機械的担保である。

## 4. ARCHITECTURE の書式

### 4-1. セクション構成(10 節)

見出し名と順序を固定する。CLI はこのキー列以外の見出しを受け付けない。

| # | 見出し | CLI の `heading` キー | 機械可読 |
| --- | --- | --- | --- |
| 1 | `## システム概要` | `システム概要` | — |
| 2 | `## 技術スタック` | `技術スタック` | — |
| 3 | `## レイヤー構造` | `レイヤー構造` | — |
| 4 | `## ディレクトリ構成と責務` | `ディレクトリ構成と責務` | — |
| 5 | `## ドメインマップ` | `ドメインマップ` | **○**(§1) |
| 6 | `## コマンド定義` | `コマンド定義` | △ |
| 7 | `## テスト方針` | `テスト方針` | — |
| 8 | `## 保護パス` | `保護パス` | △ |
| 9 | `## 規約` | `規約` | — |
| 10 | `## ADR 一覧` | `ADR 一覧` | △(採番) |

- **すべてのセクションは任意である。** 存在しないセクションがあってもエラーにしない。
  `## ドメインマップ` だけを持つ最小ファイルも正当な ARCHITECTURE として扱う。
- `overview` 疑似キーは**廃止**した。冒頭の概要は `システム概要` に統合する。
- `# ARCHITECTURE` と最初の `##` の間に本文を置かない。既存ファイルにそこへ本文がある場合、
  書き込み経路は**警告を返す**(拒否しない)。
- `heading` に `ADR 一覧` を指定した場合は**エラー**にし、`stage-adr` を使うようメッセージで誘導する。

### 4-2. セクション分割の規範アルゴリズム

行を先頭から 1 行ずつ走査し、**フェンス状態を持つ状態機械**として処理する。
Mermaid 図やコードブロックの中の `##` を見出しと誤認しないために必須である。

**行の正規化(判定の前に必ず行う)**

- 行を分割したのち、各行の**末尾の `\r` を除去**してから判定する。CRLF 改行のファイルで
  終了フェンス判定や見出し判定が実装ごとに割れるのを防ぐ。書き戻すときは元の改行コードを保つ。
- 以下の「行頭」は、**0〜3 個の半角スペースのインデントを許容**した位置を指す(CommonMark に準拠)。
  半角スペース 4 個以上のインデントは行頭とみなさない。タブは行頭のインデントとして扱わない。

**状態機械**

1. **フェンスの開始**: フェンス外で、行頭が `` ` `` または `~` を **3 個以上連続**した同一文字で始まる行。
   その文字と個数を記憶する(CommonMark に準拠)。
2. **フェンスの終了**: フェンス内で、行頭が**開始と同じ文字**を**開始と同数以上**連続させ、
   かつ**その後に info string を持たない**行。
   連続の後に**半角スペース・タブのみが続く場合は info string を持たないものとして扱い、
   終了フェンスと判定する**(末尾空白で閉じ損ねない)。
3. **フェンス内の行は本文として扱う。** 行頭が `## ` でもセクション見出しにしない。
4. **見出しの判定**: フェンス外で、行頭が `## `(`#` 2 個の直後に半角スペース)で始まる行。
   `#` 1 個(ファイルタイトル)と `###` 以下(節内の小見出し)は見出しにしない。
5. **未閉フェンス**: ファイル終端に達してもフェンスが閉じていない場合、`unclosed_fence` エラーを返す。

インデント許容を明記するのは、リスト項目の中に置かれたフェンス
(`- 使い方:` の下に 2 スペース下げて書かれたコードブロックなど)を行頭固定の判定が取りこぼし、
その中身の `## ` を見出しと誤認するためである。これは 4-2 冒頭の目的と正面から反する失敗方向である。

同名の見出しが複数あるときは**最初のものを採り**、書き込み経路は重複を警告する(拒否しない)。

### 4-3. `unclosed_fence` の扱い(2 層に分かれる)

| 経路 | 挙動 |
| --- | --- |
| **書き込み経路**(`stage-architecture` / `stage-adr`) | **拒否**し `stagingId` を発行しない |
| **読み取り・注入経路** | 処理を続け、未閉フェンス以降を 1 セクション扱いにしたうえで警告を 1 行添える |

**「書き込み経路」「読み取り・注入経路」の定義**(§11 のサブコマンド一覧と 1 対 1 に対応する。
以後この文書ではこの定義で用いる)

| 経路 | 該当するもの |
| --- | --- |
| 書き込み経路(第 1 層・フェイルクローズド) | `stage-architecture` / `stage-adr` / `commit-architecture` / `append-gotcha` / `tag-gotcha` |
| 読み取り・注入経路(第 2 層・フェイルオープン) | `get config` / `get architecture` / `get domains` / `get gotchas` / `get adr` / `scan` / `diff-architecture` / SessionStart 注入 hook / PreToolUse deny hook |

### 4-4. `## システム概要` と `## レイヤー構造` の要件

**`## システム概要`**

- 散文でプロジェクトの目的・利用者・主要な技術的制約を 1 段落。
- **全体アーキテクチャ図を Mermaid で置く。** 主要コンポーネントとその間のデータ・制御の流れを表す。
- **Mermaid の構文は検証しない。**

**`## レイヤー構造`**

- レイヤーを上から下へ列挙し、各レイヤーの責務を 1 行で書く。
- **依存の許される方向を明記する。**
- **禁止される依存方向を明記する。**
- 禁止は「〜しない」で終えず、**代わりに取る手段を併記する**。

## 5. ADR の書式

### 5-1. エントリ書式

````markdown
### ADR-001: [判断のタイトル]

- 状態: 採用/提案/廃止
- 決定日: YYYY-MM-DD
- 決定者: [氏名またはチーム名]

#### 背景
#### 検討した選択肢
1. [選択肢A]: メリット/デメリット
#### 採用した結論
#### 理由
#### 影響範囲
````

- 見出しは `###`、内部の小見出しは `####` で固定する。
- `状態` の値域は `採用` / `提案` / `廃止` の 3 つ。他は拒否する。
- 採番 `ADR-NNN` は `## ADR 一覧` 配下の `### ADR-NNN:` を**全件走査して最大値 + 1**。
- 追加位置は `## ADR 一覧` 節の**末尾**(GOTCHAS と逆向き)。
- **エントリは削除しない。** 覆した判断は `廃止` の状態で残す。

### 5-2. 状態変更の履歴

`状態` 行を書き換えるだけでなく、**エントリ末尾に 1 行を追記する**。

```
- 状態変更(YYYY-MM-DD): 採用 → 廃止。<理由>
```

- 理由は必須。省略された状態変更は拒否する。
- 変更のたびに追記し、**過去の行は消さない**。
- `状態` 行そのものは最新の値に書き換える。

### 5-3. 何を ADR にするか

**3 つすべてを満たすものだけ**を ADR にする。

1. **覆すコストが大きい。** 後から変えると複数コンポーネントに波及する、またはデータ移行を伴う。
2. **選択肢が実在した。** 比較した代替を具体的に挙げられる。
3. **理由が自明でない。** コードや設定を読んだだけでは「なぜそうしたか」が分からない。

満たさない例(ライブラリのバージョン選定、命名規約、ディレクトリの分け方)は他セクションに属する。

## 6. GOTCHAS の書式

**旧書式(発生フェーズ / 症状 / 根本原因 / 予防策 / 関連ファイル)は廃止し、新書式へ全面置換する。**
互換読みは設けない。

### 6-1. ファイル構成

````markdown
# GOTCHAS

このプロジェクトで AI が実際にやってしまった失敗のパターンを蓄積する。
発見された失敗を、下記のフォーマットで追記していく。

## 運用ルール

- 新しいものを上に追加する。
- 同じパターンが 5 件以上蓄積されたら、スキルまたは Hook への昇格を検討する。
- 解決済みの項目は `[解決済み]` タグを付けて残す。削除しない。
- 陳腐化した項目は `[対象外]` タグを付けて残す。削除しない。

## 記入テンプレート

### [YYYY-MM-DD] GOTCHA-NNN: 失敗のタイトル

**タスク**: (何をしようとしていたか)
**失敗内容**: (具体的に何を間違えたか)
**原因 (推測)**: (なぜそうなったか)
**対策**: (今後 AI はどう振る舞うべきか)
**昇格候補**: Yes / No (スキルや Hook にするべきか)

## 失敗パターン一覧

### [2026-08-16] GOTCHA-002: 最新のエントリ

...

### [2026-08-10] GOTCHA-001: 古いエントリ

...
````

### 6-2. 解析の規約

- **エントリとして解析するのは `## 失敗パターン一覧` 配下の `###` ブロックだけ**とする。
  `## 記入テンプレート` 配下の同形の見出しをエントリとして数えない。
- エントリ見出しの形は `### [YYYY-MM-DD] GOTCHA-NNN: [タグ] タイトル`。タグは省略可。
- フィールドは `**名前**: 値` の 5 行。`タスク` / `失敗内容` / `原因 (推測)` / `対策` / `昇格候補`。
- `昇格候補` は `Yes` または `No` のみを受け付ける。他の値は拒否する。

### 6-3. 挿入位置と採番

- 新エントリは **`## 失敗パターン一覧` の直下(先頭)** に挿入する。ファイル末尾に追記しない。
- **採番は `## 失敗パターン一覧` 配下の全エントリを走査して最大値 + 1** とする。
  手編集で並びが崩れていても番号が衝突しないようにする。
- 台帳または `## 失敗パターン一覧` 節が無ければ、雛形ごと作成する
  (冒頭説明・運用ルール・記入テンプレート・空の一覧節を含む)。

### 6-4. タグの検出規則(規範)

タグを置ける位置を**1 箇所に固定する**。検出は次の規則だけで行い、他の位置は認識しない。

- 位置は **`GOTCHA-NNN:` の直後**、タイトル文字列の直前。区切りは半角スペース 1 個。
- 認識するのは **`[解決済み]` と `[対象外]` のリテラル 2 種のみ**。
- **タイトル内に現れる他の角括弧は無視する。**
  `[Prisma] マイグレーションを二重適用した` のようなタイトルはタグを持たないものとして扱う。
- 先頭の `[YYYY-MM-DD]` は日付であり、タグの検出対象位置ではない。

正規化した見出しの形:

```
### [YYYY-MM-DD] GOTCHA-NNN: [解決済み] タイトル
```

**検出は生成と同じ厳密さで行う。** 「区切りは半角スペース 1 個」は生成時のテンプレートであると
同時に**検出時の必須条件**である。`GOTCHA-NNN:` の直後が半角スペース 2 個以上・全角スペース・
タブである場合、リテラルが `[ 解決済み ]` のように変形している場合は、いずれも**タグ無し**として
扱う。タグは高々 1 個であり、2 個以上並んでいる場合も先頭の 1 個だけをタグとして認識し、
残りはタイトルの一部として扱う。

**既知の限界**: 人間が手編集でタグを別位置に書いたり、リテラルを変えたり、区切りの空白を崩したり
した場合、CLI と注入はそれをタグとして認識しない(タグ無しのエントリとして扱う)。
`tag-gotcha` を通せば必ず正しい位置・正しい形で入るため、手編集の崩れは
**「CLI を使わなかった場合の自己責任」として受け入れる**。検出側を緩めない。
緩めると「タイトルの一部なのかタグなのか」の判定が文字列の意味に依存し、決定的でなくなる。

### 6-5. タグ付与の方法

次の 2 箇所への追記とする。**エントリ本文は書き換えない。**

1. 見出し行のタイトル直前にタグを挿入する。
2. エントリ末尾に理由を 1 行追記する(`**[解決済み] (2026-08-20)**: <理由>`)。

既にタグが付いているエントリへの再付与は、見出しのタグを差し替え、理由行を**追記**する
(前の理由行も残す)。

### 6-6. 記録の判断

- **記録判断フローは 1 問。**「次にこのプロジェクトを触るエージェントがこれを知らないと
  同じ失敗をするか?」が Yes のときだけ記録する。
- 別のリポジトリでも同じ対策が要るなら、それは GOTCHAS ではない。
- `対策` に精神論を書かない。「気をつける」ではなく「〜する前に〜を Read して確認する」の形。
- `昇格候補: Yes` の基準: その対策が「特定の操作をするとき常に」効くものであるとき。

## 8. intent 文書の書式

### 8-1. 保存先と命名

- `docs/intents/YYYY-MM-DD-<slug>.md`。
- `<slug>` は英小文字ケバブケース。日本語プロジェクトでも slug は英字。
- 同日に同一 slug が存在する場合は `-2` を付す。上書きしない。
- git リポジトリでない場合はカレントディレクトリ基準を提案し、**保存前に絶対パスを提示して確認を取る**。

### 8-2. セクション構成

```markdown
---
intent: v1
slug: add-oauth-login
created: 2026-08-16
status: approved
issue:
---

# intent: <一行で表した TOBE>

## ASIS

## TOBE

## 受け入れ基準

## 実装方針

## 合意済み事項

## 非スコープ

## 未確定事項
```

- frontmatter は **5 キー平坦**(`intent` / `slug` / `created` / `status` / `issue`)。
  ネスト・複数行文字列・リストは解釈しない。
- `status` の値域は `approved` / `issued` / `done`。`draft` はファイルに現れない概念上の状態。
- frontmatter は**issue 本文へ転記しない**。
- 見出しは `##` レベル。名称と順序は §9 の intent-issue と**完全に一致させる**。

**frontmatter の 5 キー**

| キー | 型 | 必須 | 内容 |
| --- | --- | --- | --- |
| `intent` | string | 必須 | intent 文書のフォーマットバージョン。v1 では `v1` 固定 |
| `slug` | string | 必須 | ファイル名の `<slug>` と同じ英小文字ケバブケース |
| `created` | string | 必須 | 作成日 `YYYY-MM-DD` |
| `status` | string | 必須 | `approved` / `issued` / `done` のいずれか |
| `issue` | string | 必須(値は空でよい) | issue の番号または URL。`issued` になるまでは空 |

**frontmatter の解析方式(読み手が 3 者いるため規範として固定する)**

- **YAML パーサを導入しない。** `---` で挟まれた先頭ブロックを対象に、
  **トップレベルのキーだけを行単位で `キー: 値` として抽出する簡易方式**とする
  (gh-utility `check-issue-env.ts` の Issue テンプレート解析と同一のパターン)。
- 値は前後の空白を除いた文字列として扱う。空値は空文字列。引用符は剥がさない。
- 未知キーがあっても無視する(エラーにしない)。5 キーのいずれかが欠けている場合は
  そのキーを未設定として扱い、例外を投げない。

**ライフサイクル**

| status | 意味 | 遷移させる主体 |
| --- | --- | --- |
| `draft` | ドラフト提示中。ファイルとしては未保存 | (ファイルに現れない概念上の状態) |
| `approved` | ゲート 1 を通過し保存された | sandalphon `capturing-intent` |
| `issued` | issue 化された(`issue:` に番号または URL が入る) | sandalphon `bridging-execution` |
| `done` | 自前実行が完了した | sandalphon `executing-intent` |

- Codiel へ委譲した場合、intent 文書は `issued` のまま残る。以降の状態は issue と PR が持つ。
- **frontmatter の書き込みはスキルの責務である。** `status` と `issue` の更新は各フェーズのスキルが
  Edit ツールで行う。`check-intent-env.mjs` は intent 文書を**読み取るだけで、一切書き込まない**。

- **status の遷移をスクリプトで検証しない。契約が定めるのは値域だけである。**
  `check-intent-env` は遷移の妥当性を判定せず、読み取った値をそのまま返す。
  後戻り(`issued` → `approved` 等)を禁止しないのは、既存 intent 文書を
  `/sandalphon:run` に渡してやり直す経路(sandalphon 設計書 §5-3)が正当な運用であり、
  そこで status が巻き戻ることがあるためである。
  遷移が妥当かどうかは意味の判断であり、スキルが文脈と併せて行う
  (スクリプトに判断を持たせないという sandalphon 設計書 §7-1 の方針に従う)。

## 9. intent-issue の書式(v1)

### 9-1. 本文の構造

```markdown
<!-- intent:v1 -->

## ASIS
## TOBE
## 受け入れ基準
## 実装方針
## 合意済み事項
## 非スコープ
## 未確定事項

<!-- intent-source: docs/intents/2026-08-16-add-oauth-login.md -->
```

- **マーカーは `<!-- intent:v1 -->`。書き出す位置は 1 行目を推奨する。**
- **検知側は本文全体を対象にマーカーを探し、位置の制約を課さない。**
  テンプレートのヘッダが前置されてマーカーが本文の中ほどに来ることがある。
- **§4-2 のフェンス除外をここには適用しない。** 引用フェンスの中に例示としてマーカー文字列が
  現れた場合も intent issue として検知する。取りこぼしの損失(写像が効かず精度が落ちる)は
  誤検知の損失より確実に大きく、HTML コメント形式のマーカーは十分に特徴的で偶然の一致が
  実質的に起きないため。**同一文書内で §4-2 と規律が異なるのは意図した非対称である。**
- 検知は**マーカー文字列の完全一致**で行う。`<!--intent:v1-->` のように空白が異なる形は
  検知対象としない(書き出し側は必ず `<!-- intent:v1 -->` の形で出す)。
- 見出しは `##` レベル、名称と順序は intent 文書と完全一致。
- 末尾に `<!-- intent-source: <リポジトリルートからの相対パス> -->`。
- タイトルは intent 文書の `# intent: <...>` の内容(`intent:` の接頭辞を外したもの)。

### 9-2. バージョニング

`v1` はフォーマットのバージョンである。見出しの追加・削除・改名を行う場合は `v2` に上げる。
検知側は**自分が知らないバージョンを見たら機械的写像をせず**、本文全文を原文として扱う既定動作に落とす。

### 9-3. issue.md への写像表(codiel `analyzing-issues` 用)

| issue 本文のセクション | issue.md の写像先 | 扱い |
| --- | --- | --- |
| `## TOBE` | `## 要件` | 1 行 1 要求のまま**そのまま転記** |
| `## 受け入れ基準` | `## 受け入れ基準` | そのまま転記。機械的に YES/NO を判定できない行だけ `## 不明点` へ格下げ |
| `## 非スコープ` | `## 非スコープ` | そのまま転記 |
| `## 未確定事項` | `## 不明点` | そのまま転記。「なし」だけなら何も写さない |
| `## ASIS` | (写像先なし) | `## 原文` に含まれるため十分 |
| `## 実装方針` | (写像先なし) | **`## スコープ` へ要約して落とさない**。`## 原文` に残す |
| `## 合意済み事項` | 条件付き | スコープの合意が含まれる場合のみ、その行を `## スコープ` / `## 非スコープ` へ**そのまま転記** |

**要約を伴う抽出をしない**のがこの写像の要点である。

## 11. CLI の入出力規約(metatron)

```
node <metatron-plugin-root>/scripts/metatron.mjs <subcommand> [options]
```

| サブコマンド | 種別 |
| --- | --- |
| `get config` | 読 |
| `get architecture [--section <見出し>]` | 読 |
| `get domains` | 読 |
| `get gotchas [--recent N \| --id <ID> \| --query <語>] [--exclude-tagged] [--promotion-candidates]` | 読 |
| `get adr [--id <ID> \| --status <状態>]` | 読 |
| `scan` | 読 |
| `diff-architecture` | 読 |
| `stage-architecture --input <path>` | 段階 |
| `stage-adr --input <path>` | 段階 |
| `commit-architecture --staging-id <id>` | 書 |
| `append-gotcha --input <path>` | 書 |
| `tag-gotcha --id <ID> --tag <解決済み\|対象外> --reason <理由> [--date <YYYY-MM-DD>]` | 書 |

### 規約

- 出力は**常に JSON を stdout へ**。人間向けの補足は stderr へ。
- 読み取り系は**常に exit 0**(「読めなかった」も事実として JSON で返す)。
- 書き込み系は成功で exit 0、拒否・失敗で**非 0**。理由は JSON の `error` に入れる。
- **長い入力は一時ファイルに書き、`--input <path>` で渡す。** これを正式な呼び出し規約とする。
  スキル・拒否メッセージ・注入の案内はすべてこの形式で書く。
- 一時ファイルの置き場は OS の一時ディレクトリ。CLI は読み取り後に削除しない。

### staging の保証

1. **diff を計算せずに書き込むことはできない。** `commit-architecture` は `stagingId` 無しでは失敗する。
2. **staging は単回使用かつ有効期限つき**(既定 30 分)。
3. **stage 後に対象ファイルが変化していたら commit は失敗する**(ハッシュ照合、`file_changed`)。

保存先は `<tmpdir>/metatron-staging/<プロジェクトパスのハッシュ>/<id>.json`。
プロジェクト内には置かない。

### 採番と挿入の原子性

1. `<対象文書パス>.lock` を **`fs.open` の `wx` フラグ**で作成してロックを取る。
2. 取得できたら「最大値の読み取り → 挿入 → ロック削除」を行う。
3. 取得できなければ **50ms 間隔で最大 20 回リトライ**(合計約 1 秒)。
   それでも取れなければ非 0 終了し `{ error: "lock_timeout" }` を返す。
4. ロックファイルの**更新時刻が 60 秒より古ければ死んだロックとみなして奪う**。
   奪取の手順は次に固定する。
   1. `unlink` の**直前に更新時刻を再取得し**、なお 60 秒より古いことを確認する。
      新しくなっていた場合は奪わず、3 のリトライへ戻る。
   2. `unlink` する。ファイルが既に無い(`ENOENT`)場合もそのまま次へ進む。
   3. 改めて `wx` で作成を試みる。**奪取後の作成成功を仮定しない。**
      作成に失敗したら他プロセスが先に取ったものとして 3 のリトライへ戻る。

**既知の限界(受け入れる)**: 上記の再確認を経てもなお、奪取側が `unlink` する直前に
正当な保持者がロックを取り直した場合、両者が同時に保持者だと信じる窓が残る。
ロックファイルの内容にトークン(PID・取得時刻・nonce)を持たせるフェンシングを導入すれば塞げるが、
**導入しない**。理由は 2 つある。

1. 設計書 §7-4 が `wx` による排他・50ms × 20 回・mtime 60 秒を明示的に決定しており、
   機構の追加は契約ではなく設計の変更にあたる。
2. この窓に入るには「正当な保持者が 60 秒を超えてロックを保持し、かつ奪取側の
   再確認と `unlink` の間の数ミリ秒で取り直す」ことが要る。GOTCHAS / ARCHITECTURE への
   書き込みは初回生成と時々の記録・更新だけであり、この同時性は実運用で起こらない。

フェンシングが要ると判断する材料が出たら、そのときに設計書へ差し戻して決める。

| ロック | 取得するサブコマンド |
| --- | --- |
| `<gotchas パス>.lock` | `append-gotcha` / `tag-gotcha` |
| `<architecture パス>.lock` | `stage-adr`(採番の読み取り) / `commit-architecture`(書き込み) |

2 文書のロックは独立しており、互いをブロックしない。

## 12. hook 出力の形式

リポジトリ内の既存実装(codiel / revelation / agent-policy)と完全に同一の形に揃える。

### SessionStart

```ts
process.stdout.write(
  `${JSON.stringify({
    hookSpecificOutput: {
      hookEventName: "SessionStart",
      additionalContext: content
    }
  })}\n`
)
```

### PreToolUse

```ts
process.stdout.write(
  `${JSON.stringify({
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: decision,      // "deny" | "ask"
      permissionDecisionReason: reason
    }
  })}\n`
)
process.exit(0)
```

- **素通しは何も出力せず `process.exit(0)`。** `permissionDecision: "allow"` は出さない
  (許可システムをバイパスして自動実行になるため)。
- `hooks.json` の `command` は `node "${CLAUDE_PLUGIN_ROOT}/scripts/<name>.mjs"` の形式。

### deny hook から CLI の絶対パスを組み立てる

- **deny hook は CLI を実行しない。** hook が行うのは、CLI の絶対パスを**文字列として組み立て、
  `permissionDecisionReason` に載せる**ことだけである。実際に CLI を実行するのはモデル(Bash 経由)。
- 組み立て方は、**hook 自身の位置(`import.meta.url`)からプラグインルートを求め、
  その配下の `scripts/metatron.mjs` を連結する**。これにより、AI は metatron が
  どこにインストールされているかを知らなくても CLI を呼べる。
- 拒否メッセージには必ずこの絶対パスを含める。対象が ARCHITECTURE か GOTCHAS かで
  案内するサブコマンドを出し分け、ARCHITECTURE の場合は
  「ADR の追加・状態変更は `stage-adr` を使う(`stage-architecture` では拒否される)」を 1 行添える。

### 失敗時の方針(プラグインごとに異なる。混同しない)

| 対象 | 方針 |
| --- | --- |
| metatron の SessionStart 注入 hook | **フェイルオープン**。**文書の内容**を出力せず exit 0(CLI 案内は出す。下の限定を見よ) |
| metatron の PreToolUse deny hook | **フェイルオープン**。素通しする |
| codiel の PreToolUse hook(既存) | **フェイルクローズド**。catch で `emit("ask", ...)` |

**SessionStart 注入の「何も出力しない」の限定(metatron 設計書 §8-7)。**
「何も出力しない」は「**文書の内容を**出力しない」の意味に限定する。
**ARCHITECTURE も GOTCHAS も無い(読めない場合を含む)ときも、CLI 案内だけは注入する。**
`/metatron:init` はまさにその状態で使うコマンドであり、案内を落とすと AI は CLI の
絶対パスを知る手段を持たず、init を開始できない。これは「CLI の発見性はモデル
コンテキストで担保する」という本契約の前提と両立しない。文書が無いときの案内は、
「まだ文書が無く `/metatron:init` で作れる」ことが分かる別文面にする。

案内まで落とすのは次の 2 つだけ。

- **設定の読み取り自体が例外で失敗したとき。** 壊れた機構が誤った CLI パスを広告しかねない。
- **`injection.enabled: false` のとき。** 利用者が明示的に切っている。

metatron がフェイルオープンなのは、metatron の不具合でセッション開始やユーザーのあらゆる編集が
止まる損害のほうが、直接編集 1 回の見逃しより大きいためである。

## 13. 実装間の一致検証

3 実装が写しを持つ設計における唯一の機械的担保。

**テスト R4 / sandalphon ケース 16f**: 同一の一時ディレクトリ構成に対して次の 3 つを走らせ、
`docRoot` と解決されたパスが**すべて一致する**ことを検証する。

1. metatron の `src/lib/config.ts`
2. codiel の `src/hooks/lib.ts` の `findDocRoot` + `resolveDocPaths`
3. sandalphon の `src/check-intent-env.ts`

**パス文字列だけでなくルート解決の結果も比較対象に含める。**

検証する構成は最低限次を含む。

- 設定ファイル無し + git リポジトリ
- 設定ファイル無し + git 管理外
- サブディレクトリから実行し、祖先に `metatron.config.json` がある
- `repo/metatron.config.json` と `repo/sub/.codiel/` が併存し `repo/sub` から実行
- `paths` が絶対パス / ルート脱出
- **開始ディレクトリ自身に `metatron.config.json` がある**(inclusive 探索の確認。§3 規則 1 の細目)
- **シンボリックリンク経由で開始ディレクトリを与える**(実体パスに `metatron.config.json` があり、
  リンクパス側には無い構成。realpath 解決の有無で `docRoot` が割れないことの確認)
- **git バイナリが無い環境**(`PATH` から git を外して実行。3 実装とも段 3 へフォールバックし、
  例外を投げないこと)
- **ネストした git リポジトリ**(`repo/inner/.git` があり `repo/inner/sub` から実行)
- **Windows 形式のパス区切り**(`\` を含む構成で `docRoot` と解決パスが一致すること)
