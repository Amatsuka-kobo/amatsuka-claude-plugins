## 1. 規律が弱いのはファイルに書くコメントと文書であり、書いた後に検査して直させる

0.1.0-dev は `references/discipline.md` を SessionStart と SubagentStart で注入するだけの構成である。ユーザーは、プログラムファイル内のコメントと文書に翻訳調や避ける語が残ると判断した。会話は別の圧縮口調プラグインが口調だけを上書きしているため、規律が弱いかどうかを判断できない。

原因は次の 2 つと推定する。

- ファイルを書く時点で規律が遠い。注入はセッション冒頭とサブエージェント起動時だけで、コードや文書を書く間は内容の正しさに注意が向く。
- 書いた後に検査する工程が無い。前回の設計書は lint を非スコープにしていた(前回の設計書のセクション 2-2)。

本改修では次の 5 つの施策を行う。記号は検討時の案の記号を引き継ぐ。

| 記号 | 施策 | 本書のセクション |
| --- | --- | --- |
| A | 違反を数える測定 CLI。F と同じ lint を使う | 4, 5, 6 |
| F | PostToolUse でファイルへの書き込みを検査し、違反を差し戻す | 4, 5, 7 |
| B | `discipline.md` の適用範囲に、翻訳調・避ける語・結論を先に書く規律はどの口調でも適用すると明記する | 8 |
| E | UserPromptSubmit で短い要約を毎ターン注入する | 9 |
| D | A の測定結果から `discipline.md` を組み直す | 10 |

A と F が使う lint は 2 層で動く。正規表現の層は避ける語と翻訳調の定型を拾い、常に動く。形態素解析の層は文の長さや文末の連続のような文の規律の一部を拾い、辞書を取得できた環境でだけ動く(セクション 5)。

会話の最終応答を Stop / SubagentStop で検査する案(C)は今回扱わない。

設計書と実装計画書も検査の対象とし、本書もその例外にしない。ignore-file の目印を置くのは、避ける語を意図して列挙する `discipline.md` だけとする。本書で避ける語や翻訳調の型を例として引くときは、インラインコードで囲む。インラインコードの中は検査しないので、引用だけが検査から外れる。

### 2-2. 形態素解析は lindera の N-API バインディングが最も速い

計測は 2026-09-28、AMD Ryzen 7 5700X と node 26.3.1 の環境で行った。各構成を新しい node プロセスで 5 回実行し、中央値を取った。計測に使ったスクリプトは `/tmp/nj-morph/measure-lindera-napi.mjs` などで、入力は 20 行のコメントと 300 行の文書である。

| 構成 | プロセス全体 | 辞書ロード | 20 行の解析 | 300 行の解析 | 最大 RSS |
| --- | --- | --- | --- | --- | --- |
| node の起動のみ | 20ms | — | — | — | 41MB |
| lindera(N-API) | 60ms | 0.64ms | 5.8ms | 22.1ms | 80MB |
| lindera-wasm | 300ms | 183ms | 11.9ms | 46.7ms | 269MB |
| kuromoji 0.1.2 | 820ms | 677ms | 15.3ms | 46.3ms | 432MB |

lindera(N-API)は辞書を mmap で読み込む。`/proc/<pid>/smaps` で、辞書の全ファイルが `r--s` としてマップされ、Rss がファイルサイズの一部にとどまることを確かめた。hook は書き込みのたびに新しいプロセスで動くので、辞書ロードが 1ms を切る点が採用の決め手になった。

採用する構成と入手元は次のとおり。

| 項目 | 内容 |
| --- | --- |
| 解析器 | lindera 6.2.0 の N-API バインディング。ライセンスは MIT |
| 辞書 | `lindera-ipadic-6.2.0.zip`(https://github.com/lindera/lindera/releases/tag/v6.2.0)。zip は 10.5MB、展開後は 46MB。IPADIC は NAIST と ICOT の条件で配布され、NOTICE を添える必要がある |
| `.node` | npm registry にある OS ごとのパッケージ(例: `lindera-linux-x64-gnu`)の tarball。tarball の中の `.node` 1 ファイルだけを使う。パスは target ごとにセクション 2-5 の表に示す。linux-x64 の `.node` は 7.4MB |

辞書の zip の中身は `lindera-ipadic/` の下の 10 ファイル(`NOTICE.txt` `metadata.json` `dict.*` `matrix.mtx` `char_def.bin` `unk.bin`)で、すべて deflate で圧縮されている(Python の `zipfile` で確かめた)。

### 2-3. lindera の読み込みには 2 つの落とし穴がある

1 つ目はフィールド名である。lindera の `metadata.json` は `details` の並びを `conjugation_form`、`conjugation_type` の順に定める。ところが `conjugation_form` には活用型(例: `サ変・スル`)、`conjugation_type` には活用形(例: `基本形`)が入る。名前と中身が逆になっている。`短縮することができる` を解析すると、`する` の `details[4]` は `サ変・スル`、`details[5]` は `基本形` だった(`/tmp/nj-morph/show-analysis-lindera.mjs` で確かめた)。本プラグインは `details` を名前で読まず、添字で読んで自前の名前に付け替える(セクション 5-4)。

2 つ目はバンドルである。npm の `lindera` パッケージをそのまま ESM へバンドルすると、`Error: Dynamic require of "fs" is not supported` で失敗した。原因は、パッケージの `index.js` が CommonJS の `require` で `fs` や OS ごとのパッケージを読むことにある。

これに対し、`.node` を直接読み込む方法は ESM のバンドルでも動いた。`createRequire(import.meta.url)` で作った `require` に `.node` の絶対パスを渡す短いスクリプトを、esbuild で `format: "esm"`、`platform: "node"`、`target: "node22"` にバンドルし、`.mjs` として実行した(2026-09-28、`/tmp/nj-direct-bundle.mjs`)。返る値は `loadDictionary` と `Tokenizer` を持ち、`lindera` パッケージの公開 API と同じ形だった。ARCHITECTURE の「出力は ESM とし、拡張子は `.mjs` とする」はこの方法で守れる。

### 2-4. 取得物の置き場所は `CLAUDE_PLUGIN_DATA` が使える

公式ドキュメントで次を確かめた。出典は `https://code.claude.com/docs/en/plugins-reference` の Environment variables と Persistent data directory である。実機での値は実装の Step 2 で確かめる。

- `${CLAUDE_PLUGIN_DATA}` はプラグインの更新をまたいで残るディレクトリで、初めて参照したときに作られる。
- 実体は `~/.claude/plugins/data/{id}/` で、`{id}` はプラグインの識別子の英数字・`_`・`-` 以外を `-` に置き換えたものになる。
- hook のプロセスには環境変数として渡る。Bash ツールで実行するコマンドには渡らない。
- プラグインを最後のスコープからアンインストールすると、ディレクトリは消える。

このリポジトリの利用者の環境には、`native-japanese-amatsuka-claude-plugins` と `native-japanese-inline` の 2 つがすでにある(`~/.claude/plugins/data/` の一覧で確かめた)。`--plugin-dir` で読み込んだときは `inline` の側になると推定する。

## 3. スコープと前提とする制約

### 3-1. スコープ

- `plugins/native-japanese/` の lint 本体(正規表現の層と形態素解析の層)、測定 CLI、PostToolUse hook、UserPromptSubmit の注入
- 形態素解析の `.node` と辞書を初回に取得する仕組み
- `references/discipline.md` の適用範囲(B)と組み直し(D)
- `references/reminder.md` の新設(E)
- ADR の追加(セクション 11)
- README、ルート README、バージョン(0.2.0-dev)

### 3-2. 非スコープ

- 会話の最終応答の検査(C)
- 構成の規律(結論を先に書く、見出しに結論を含める、箇条書きの使い方など)の機械検査。規律として注入は続ける
- 文の規律のうち、品詞・原形・活用だけでは判定できない項目。読点の位置、語順、接続詞の射程、主語と述語の距離、cleft 構文がこれに当たる
- 違反の自動修正。直すのはモデルである
- Bash(リダイレクトや `sed` など)と Claude Code の外のプロセスによる書き込み。PostToolUse の matcher に当たらないため検査されない
- 書き込みの取り消し。PostToolUse の差し戻しは、書き込みが成功した後に直すよう促すだけである
- musl の Linux と、セクション 2-5 の 6 種以外の OS での形態素解析

### 3-3. 制約

- hook 1 件の `additionalContext` は 10,000 文字以内に保つ(前回の設計書のセクション 2-3)。`discipline.md` の 9,000 文字の上限は維持する。
- lint 本体はプラグイン内で 1 つだけ持ち、hook と測定 CLI が共有する。CLAUDE.md の「セッション内ツールは Python で `tools/`」には当たらない。測定 CLI は配布物の一部として利用者も使うためである。
- npm の依存を増やさない。コードは Node.js の標準ライブラリだけで書く。lindera は npm の依存に加えず、`.node` と辞書を実行時に取得する(セクション 5-2)。tarball と zip の展開も標準ライブラリの `zlib` で行う。
- `.node` と辞書は git に入れない。
- `discipline.md` の避ける語は、表から実行時に読み取る。語の一覧を lint 側に二重に持たない。
- 取得は hook を止めない。取得が終わるまでと、取得できない環境では、正規表現の層だけで検査する。

## 4. lint 本体は 2 層に分け、ファイルを読むのはエントリポイントだけにする

### 4-1. モジュール構成

| ファイル | 責務 |
| --- | --- |
| `src/lib/rules.ts` | 正規表現の規則を組み立てる。避ける語は、渡された `discipline.md` の本文の「## 避ける語」の表から、翻訳調はコード内の定義から作る。ファイルは読まない |
| `src/lib/extract.ts` | パスと本文から、検査する日本語の行と、文の規則にかける段落を抜き出す |
| `src/lib/morph.ts` | 形態素の列を受け取り、文に分けて文の規則を当てる。解析器の型だけを持ち、`.node` は読まない(セクション 5-4) |
| `src/lib/lint.ts` | 抜き出した行に正規表現の規則を、段落に形態素解析の規則を当て、違反の一覧を返す。解析器は引数で受け取り、無ければ正規表現の層だけを動かす |
| `src/lib/archive.ts` | tarball と zip の Buffer から、指定した名前のファイルだけを取り出す。ファイルは読まない |
| `src/morph-runtime.ts` | 取得物の置き場所の解決、取得の起動、`.node` と辞書の読み込み、取得と展開の本体(セクション 5) |

`discipline.md` を読むのはエントリポイント(`src/check.ts` `src/measure.ts` `src/inject.ts`)だけとし、`new URL("../references/discipline.md", import.meta.url)` で解決する。エントリポイントは、ソースでもバンドル後の `scripts/*.mjs` でも、プラグインルートの 1 階層下にある。そのため同じ相対パスが両方で同じファイルを指す(前回の設計書のセクション 4-4)。`src/lib/` から読むと、バンドル後に指す場所がずれる。

`src/morph-runtime.ts` もエントリポイントと同じ `src/` の直下に置く。取得を起動するときに `new URL("../scripts/fetch-morph.mjs", import.meta.url)` を解決するので、`src/lib/` に置くと同じずれが起きる。

### 4-2. 正規表現の規則

各規則は `id`・`category`・`pattern`(RegExp)・`advice`(書き換えの方針、1 文)を持つ。

避ける語の規則は、表の各行の「」で囲まれた語から作る。

- 分類の列を `category` にする。
- 語の中の「〜」は `.{0,30}?` に置き換える。
- 語に含まれる正規表現の特殊文字はエスケープする。
- 語がカタカナか漢字で始まるときは、直前の文字がカタカナでも漢字でもないことを条件にする。`承認ポイントはなく` の `ポイントは` のように、複合語の一部に当たるのを防ぐ。
- `advice` は、表の直前の文の「語を消して具体的な事実・数値・条件を書く」とする。

翻訳調の規則は `rules.ts` に正規表現で定義する。表の Before は例文であり、そこから型を作れないためである。最初に入れる型は次の 7 つとする。

| id | 型 | 正規表現(概略) | advice |
| --- | --- | --- | --- |
| `koto-dekiru` | `〜することができる` | `することが(でき\|可能)` | `することができ` を「でき」に縮める。否定や過去の活用(できない・できた)は保つ |
| `kanten` | `〜という観点から` | `という観点(から\|で)` | 「〜で見れば」「〜では」に言い換える |
| `ni-totte-juyo` | `〜にとって重要` | `にとって(重要\|大切)` | 何が何を決めるのかを、元の文の強さを変えずに書く |
| `wo-motsu` | `〜を持つ`(抽象名詞) | `(意味\|価値\|影響)を持つ(?=。\|$)` | 「〜がある」に言い換える |
| `koto-ni-yotte` | `〜することによって` | `ことによって` | 「〜すると」「〜して」に言い換える |
| `hoka-naranai` | `〜に他ならない` | `に(他\|ほか)ならない` | 言い切りに直す。元の文に無い因果を足さない |
| `dash-insert` | ダッシュで挟む挿入句 | `——` または `―` の 2 連 | 括弧に入れるか、文を分ける |

`wo-motsu` は「意味・価値・影響」の 3 語に限り、句点か行末の直前にある `持つ` だけを拾う。`鍵を持つ` のような具体物や、`役割を持つ定義` `意味を持つ定義` `責任を持って` のような連体修飾と技術文の定型を拾わないためである。`hoka-naranai` は、漢字の `他` とひらがなの `ほか` の両方に当たるようにする。

訳語の表(`版` `緑・赤` など)は文脈なしに判定できないため、lint の対象にしない。

### 4-3. 行と段落の抜き出し

日本語の行とは、ひらがなかカタカナを 1 字以上含む行を指す。漢字だけの行は中国語と区別できないため対象にしない。

| 拡張子 | 抜き出す範囲 |
| --- | --- |
| `.md` `.mdx` `.markdown` `.txt` | 全行。コードフェンス内の行を除き、インラインコード(バッククォートの内側)を空白に置き換える |
| `//` 系(`.ts` `.tsx` `.js` `.mjs` `.cjs` `.jsx` `.java` `.kt` `.go` `.rs` `.c` `.h` `.cpp` `.cs` `.swift` `.dart` `.scala`) | `//` 以降、`/* */` の内側、`*` で始まる行 |
| `#` 系(`.py` `.sh` `.bash` `.zsh` `.rb` `.yaml` `.yml` `.toml` `.r` `.pl`) | `#` 以降。`.py` は三重引用符の内側も含める |
| `--` 系(`.sql` `.lua` `.hs`) | `--` 以降 |
| `.html` `.htm` | 行単位では抜き出さない。後述の「HTML は、書き込み後のファイル全体からブロック単位で抜き出す」に従う |
| NotebookEdit のセル | 拡張子の代わりに `cell_type` で決める。`markdown` は Markdown として扱う。`code` はノートの言語を見ずに、`//` 以降と `#` 以降の両方をコメントとして抜き出す |
| 上記以外 | 抜き出さない |

HTML 以外では、正規表現の層を Edit の `new_string` のようなファイルの一部分にも当てるので、抜き出しは行単位の簡易判定で行う。文字列リテラル内の `//` や `#` を誤ってコメントとみなすことがある。誤検知が問題になったら、拡張子ごとの字句解析へ置き換える。

形態素解析の層は、書き込み後のファイル全体から段落を組む。`new_string` のような断片だけを見ると、段落の途中から始まり、文末の連続や文の区切りを正しく判定できないためである。書き込み後のファイルは、ignore-file の判定のためにも読む(セクション 7-2)。段落は、抜き出した行から次のように組む。

| 種類 | 段落の単位 | 文末の連続の規則 |
| --- | --- | --- |
| Markdown の地の文 | 空行・見出し・リスト・表・コードフェンスで区切られた連続行 | 当てる |
| Markdown のリストの 1 項目 | 項目ごと(折り返した継続行を含む) | 当てない |
| コメント | 連続するコメント行 | 当てる |
| 見出し・表の行 | 形態素解析の規則にかけない | — |

段落に渡すときは、インラインコードと URL を名詞として解析される 1 字に置き換える。空白に置き換えると、文の長さの数え方と品詞の並びが変わるためである。どの字を使うかは実装で決め、名詞として解析されることをテストで確かめる。

ignore-file の目印は、行全体が目印である行に限る。Markdown では `<!-- native-japanese: ignore-file -->` の 1 行、コードではコメントの内容が `native-japanese: ignore-file` だけの行を指す。コードフェンスの中とインラインコードの中の記述は目印として数えない。目印を含むファイルは、どの層でも検査しない。

目印を置くのは `discipline.md` だけとする。本書と実装計画書を含む設計の文書には置かない。モデルが目印を足せば検査を逃れられるが、足した行は差分に残るので、レビューで見つける。

#### HTML は、書き込み後のファイル全体からブロック単位で抜き出す

`.html` と `.htm` は、他の拡張子と違って行単位では抜き出さない。1 つの文がタグや改行をまたぐので、行単位で見ると `することが<em>できる</em>` のような違反を拾えないためである。正規表現の層も形態素解析の層も、書き込み後のファイル全体から取り出したブロック単位の本文に当てる。差し戻しと集計に使うのは、今回の編集範囲と重なる違反だけとする(セクション 4-4)。形態素解析の層で決めた扱いを、HTML では正規表現の層にも広げる形である。

抜き出しは `src/lib/extract.ts` の中で、次の順に正規表現で行う。

1. 除外する範囲を消す。`<script>` `<style>` `<pre>` `<code>` `<template>` `<svg>` の要素は、開始タグから終了タグまでを中身ごと消す。HTML コメントも消す。消した範囲の改行は残し、行番号がずれないようにする。
2. ブロックの区切りを決める。`p` `li` `h1`〜`h6` `td` `th` `dt` `dd` `blockquote` `figcaption` `div` `section` `article` `header` `footer` の開始タグと終了タグ、および `br` の位置で本文を区切る。区切りと区切りの間が 1 ブロックになる。
3. 残りのタグは、タグだけを取り除き、中の文字は残す。
4. `&amp;` `&lt;` `&gt;` `&quot;` `&nbsp;` と数値文字参照(`&#12354;` `&#x3042;`)を文字に戻す。これ以外の名前付きの実体参照は、戻さずにそのまま残す。
5. ブロックの中の改行は、前後がどちらも ASCII 以外の文字なら取り除き、それ以外なら空白 1 つにする。日本語の文を途中で折り返した行を、1 つの文としてつなぐためである。
6. 抜き出した 1 字ごとに元のファイルでの位置を持たせ、違反を報告するときに元の行番号へ戻す。違反が複数行にまたがるときは、始まる行を `line`、終わる行を `endLine` に入れる。

1 で消す `<code>` がブロックの途中にあるとき(`<p>設定は <code>foo</code> で変える。</p>`)は、形態素解析の層に渡す前に、Markdown のインラインコードと同じ 1 字に置き換える。空文字にすると、前後の語がつながって品詞の並びが変わるためである。

ブロックの種類ごとの扱いは、Markdown に揃える。`p` `div` `section` `article` `header` `footer` `blockquote` `figcaption` と、`br` で区切った本文は地の文として扱い、文末の連続の規則も当てる。`li` `dt` `dd` はリストの項目として扱い、文末の連続の規則は当てない。`h1`〜`h6` `td` `th` は見出しと表の行として扱い、正規表現の層だけを当てる。

ignore-file の目印は、行全体が `<!-- native-japanese: ignore-file -->` である行として、Markdown と同じ条件で判定する。1 で HTML コメントを消す前に判定するので、目印は目印として働く。

次のものは抜き出さない。

- `<script>` の中の JavaScript のコメント
- 属性値(`alt` `title` など)
- Vue や JSX のテンプレート。拡張子が `.vue` `.jsx` `.tsx` のファイルは、この HTML の抜き出しを使わない

抜き出しを正規表現で行うので、閉じタグの抜けた壊れた HTML では、ブロックの区切りがずれる。この上限は、実装のコメントに `ponytail:` を付けて書く。コメントには、パーサーを使わない理由と、誤検知や取りこぼしが問題になったらパーサーに置き換えることを書く。パーサーの npm の依存は増やさない(セクション 3-3)。

### 4-4. 出力

`lint(path, text, analyzer?)` は `{ line, endLine, text, ruleId, category, match, advice }[]` を返す。`line` は渡された本文の中での行番号である。形態素解析の規則では、違反した文が始まる行を `line` に、終わる行を `endLine` に入れる。`match` は、正規表現の規則では該当部分、形態素解析の規則では違反した文の先頭 20 字とする。

呼び出し側は、違反を編集範囲で絞る。編集範囲とは、今回の書き込みで変わった行の範囲を指す。形態素解析の規則の違反は、`line` から `endLine` までが編集範囲と 1 行でも重なるものだけを差し戻しや集計に使う。編集範囲の求め方は、hook ではセクション 7-2、測定 CLI ではセクション 6-1 に書く。

## 5. 形態素解析は初回に取得し、取得済みのときだけ文の規則を足す

### 5-1. `.node` は `createRequire` で直接読み込み、lindera のパッケージは使わない

`src/morph-runtime.ts` の `loadAnalyzer(dataDir)` が次の順で読み込む。

1. `<dataDir>/morph/lindera-6.2.0/ready.json` が無ければ `null` を返す。
2. `ready.json` に記録したファイルごとのサイズと mtime を、`.node` と辞書の 10 ファイル(計 11 ファイル)の実物と比べる。1 つでも合わなければ `ready.json` を消して `null` を返す。次の SessionStart で取得に戻る。
3. `createRequire(import.meta.url)` で作った `require` に、`ready.json` が指す `.node` の絶対パスを渡す。
4. 返った `loadDictionary(<辞書のディレクトリ>)` と `new Tokenizer(dict, "normal")` で解析器を作る。
5. 1〜4 のどこで例外が起きても `null` を返す。

sha256 の照合は取得の直後に 1 回だけ行い(セクション 5-2)、hook ではサイズと mtime だけを比べる。理由は次の 3 つである。

- sha256 を毎回照合すると、hook が遅くなる。実測では 76〜371ms かかり、形態素解析そのものにかかる 60ms を上回る。計測は 2026-09-28、セクション 2-2 と同じ環境で、11 ファイル(54MB)を対象に行った。76ms はページキャッシュに載った状態、371ms は初回の値である。
- データディレクトリに書き込める者は、hook のスクリプトそのものも書き換えられる。毎回照合しても、防げる脅威は増えない。
- 毎回の照合で防ぎたいのは、途中で止まった展開と、偶発的な破損である。この 2 つは、サイズと mtime の比較で検出できる。

hook は `loadAnalyzer` を呼ぶ前に `AMATSUKA_NATIVE_JAPANESE_MORPH` を見て、`off` なら呼ばない。測定 CLI の扱いはセクション 6-1 に書く。

npm の `lindera` パッケージを使わないのは、セクション 2-3 のとおり ESM へバンドルできないためである。型は `src/lib/morph.ts` に、使う分(`Tokenizer.tokenize` が返す `surface` と `details`)だけを自前で宣言する。esbuild は `createRequire` で作った `require` を追わないので、`.node` はバンドルに入らない。`build.ts` の設定は変えない。

### 5-2. 取得は SessionStart で切り離したプロセスに任せる

取得の流れは次のとおり。hook のプロセスは子プロセスを起動するだけで、終わりを待たない。

1. `src/inject.ts` は SessionStart のときだけ `maybeStartFetch()` を呼ぶ。SubagentStart と UserPromptSubmit では呼ばない。呼び出し全体を `try` で囲み、どんな失敗でも注入の JSON を書いて exit 0 で終える。取得の失敗で注入を止めない。
2. `maybeStartFetch()` は、次のどれかに当たれば何もしない。
   - `CLAUDE_PLUGIN_DATA` が無い。
   - `AMATSUKA_NATIVE_JAPANESE_MORPH=off` か `AMATSUKA_NATIVE_JAPANESE_CHECK=off` が設定されている。
   - 実行中の OS と CPU が、セクション 2-5 の 6 種に当たらないか、判定できない(セクション 5-3)。
   - `ready.json` がある。
   - 10 分以内に作られた `fetch.lock` がある。
   - 24 時間以内に書かれた `fetch-failed.json` がある。
3. 当たらなければ `node <プラグインルート>/scripts/fetch-morph.mjs` を `detached: true`、`stdio: "ignore"`、`windowsHide: true` で起動し、`unref()` する。起動の失敗は無視する。`detached` と `unref()` の書き方は、`plugins/guidepost/src/serve.ts` の 84-90 行に倣う。hook のプロセスが終わった後も子プロセスが残って取得を続けることは、Step 2 で確かめる。
4. `fetch-morph.mjs` は、mtime が 10 分より古い `fetch.lock` があれば消す。その後 `fetch.lock` を `wx` で作る。作れなければ別のプロセスが取得中なので終わる。
5. `.node` の tarball と辞書の zip を `fetch` で取得する。1 件あたり `AbortSignal.timeout(120_000)` で打ち切る。
6. 取得した Buffer の sha256 を、コードに固定した値(セクション 2-5)と比べる。一致しなければ捨てて失敗とする。
7. `src/lib/archive.ts` で展開する。tarball からは、セクション 2-5 の表で target に対応する `.node` のパス(例: `package/lindera.linux-x64-gnu.node`)だけを取り出す。zip からは `lindera-ipadic/` の直下にある既知の 10 ファイルだけを取り出す。名前に `..` や絶対パスを含む項目は取り出さない。
8. 一時ディレクトリ `morph/lindera-6.2.0.tmp-<pid>` へ書く。書いた 11 ファイルそれぞれの sha256 を、手順 6 で検証済みのアーカイブから取り出した内容の sha256 と照合する。sha256 の照合を行うのはこの 1 回だけである。通らなければ手順 11 の失敗として扱う。`morph/lindera-6.2.0` がすでにあり、中に `ready.json` が無ければ、途中で止まった展開の残りとみなして消す。その後、一時ディレクトリを `morph/lindera-6.2.0` へ rename する。
9. `ready.json`(バージョン、target、`.node` と辞書の相対パス、11 ファイルそれぞれのサイズと mtime)を一時ファイルから rename で置く。サイズと mtime は rename の後のファイルから読む。`ready.json` は常に最後に置くので、ある時点で取得物はそろっている。
10. `morph/` の下にある、現在と違うバージョンのディレクトリを消す。
11. 失敗したときは `fetch-failed.json` に時刻と理由を書き、一時ディレクトリを消す。どの場合も `fetch.lock` を消して終わる。

置き場所は次のとおり。

```text
${CLAUDE_PLUGIN_DATA}/morph/
├── lindera-6.2.0/
│   ├── lindera.linux-x64-gnu.node  target ごとの名前(セクション 2-5 の表)
│   ├── ipadic/                   zip の lindera-ipadic/ の中身(NOTICE.txt を含む)
│   └── ready.json
├── fetch.lock                    取得中だけある
└── fetch-failed.json             最後の失敗の時刻と理由
```

取得には、1 回目のセッションで 13MB ほどの通信がかかる(tarball が 2.1〜2.7MB、zip が 10.5MB)。取得が終わるまでの書き込みは正規表現の層だけで検査し、終わった後の書き込みから形態素解析の層も加わる。`check.ts` は呼ばれるたびに `ready.json` を見るので、同じセッションの途中からでも切り替わる。

取得と展開の本体は `morph-runtime.ts` の `installMorph({ dataDir, target, sources })` に置き、`sources` に URL と sha256 を渡せる形にする。`src/fetch-morph.ts` は固定の `sources` を渡して呼ぶだけのエントリポイントとする。テストでは、ローカルの HTTP サーバーと小さな固定データの sha256 を渡す(セクション 13)。

### 5-3. target は `process.platform` と `process.arch` で決め、Linux では glibc かを確かめる

`process.platform` と `process.arch` の組を、セクション 2-5 の 6 種に対応づける。Linux では `process.report.getReport().header.glibcVersionRuntime` があるときだけ glibc とみなす。`getReport()` を呼ぶ前に `process.report.excludeNetwork = true` を置き、報告の作成でネットワークの情報を集めないようにする。

`glibcVersionRuntime` が無ければ、musl か判定できない環境として扱う。6 種に当たらない組と同じく、取得を試みず、`fetch-failed.json` も書かない。検査は正規表現の層だけで行う。

判定を誤って読み込めない `.node` を取得しても、セクション 5-1 の 5 で `null` になり、正規表現の層だけで動く。

lindera 6.2.0 の `engines` は `^20.17.0 || ^22.13.0 || >= 23.5.0` である。README が求める node 22 以上のうち 22.0〜22.12 はこの範囲の外になる。N-API は node のバージョンをまたいで互換なので読み込めると推定するが、確かめていない。読み込めなければ同じく正規表現の層に戻る。

### 5-4. 文の規則は品詞・原形・活用で判定できる 4 つに限る

`src/lib/morph.ts` は、lindera の 1 トークンを次の形に付け替える。`details` の添字は `metadata.json` の `dictionary_schema.fields` から `surface` と 3 つの ID・コストを除いた並びに対応する。

| 自前の名前 | 添字 | 中身 | 例 |
| --- | --- | --- | --- |
| `pos` | `details[0]` | 品詞 | `動詞` |
| `pos1` | `details[1]` | 品詞の細分類 1 | `自立` `非自立` `接続助詞` |
| `pos2` | `details[2]` | 品詞の細分類 2 | `人名` |
| `conjType` | `details[4]` | 活用型。lindera の名前は `conjugation_form` | `サ変・スル` |
| `conjForm` | `details[5]` | 活用形。lindera の名前は `conjugation_type` | `基本形` `連用形` |
| `base` | `details[6]` | 原形 | `示す` |

名前と中身が逆になる落とし穴(セクション 2-3)を避けるため、`conjugation_form` と `conjugation_type` の語はこのファイルの外に出さない。付け替えはテストで固定する。

文は、段落の中を `。` `！` `？` で区切り、区切りが無ければ段落の終わりまでを 1 文とする。サ変接続の名詞の直後に `する` が続くときは、2 つを合わせた原形(例: `意味する`)を 1 語の述語とみなす。

4 つの規則は、どれも保守的に判定する。閾値はすべて `morph.ts` の先頭の定数に集め、セクション 6-3 の基準値を見てから調整する。

| id | category | 対象の規律(`discipline.md`) |
| --- | --- | --- |
| `muse-shugo` | 翻訳調 | 翻訳調の表の先頭の型(無生物主語 + 他動詞) |
| `bunmatsu-renzoku` | 文 | 同じ文末表現が 3 文続いたら、次の文で形を変える |
| `bun-nagasa` | 文 | 長さは 40〜60 字を目安にする。一文一義なら超えてよい |
| `rentai-kasanari` | 文 | 1 つの名詞に連体修飾を重ねない。修飾の節が 2 つ以上重なったら文を分ける |

#### `muse-shugo`: 命題を目的語にとる「示す」系の述語だけを拾う

判定は、1 文が次の 3 つをすべて満たすときに違反とする。

- 係助詞か格助詞の `は` `が` で受けた名詞がある。
- 文の述部の中心の原形が、`示す` `意味する` `物語る` `裏付ける` `示唆する` のどれかである。述部の中心とは、文末から助動詞・助詞・非自立の動詞・接尾の動詞(`れる` `られる` `せる` など)を除いた後の、最後の自立の動詞を指す。除く品詞は `bunmatsu-renzoku` の文末表現と揃える。
- その述語の直前が、非自立の名詞 `こと` か `の` に格助詞 `を` が続く形である。

述語の一覧は、Step 4 の基準値で見直すための最初の値である。誤検知と見逃しの例を読んでから、語を足すか削る。

例外は、述語に最も近い `は` の直前の名詞だけで判定する。その名詞が次のどちらかなら当てない。

- 代名詞。`pos1` が `代名詞` か、表層が `私` `僕` `我々` `彼` `彼女` `あなた` のどれかである。
- 固有名詞の人名。`pos1` が `固有名詞` で、`pos2` が `人名` である。

`この事実は、前提が誤っていたことを示している。` は当たる。目的語を `こと` の節に限ったので、`図 1 は構成を示す。` や `exit code 2 はエラーを示す。` のような技術文の定型には当たらない。`手順を理解したことを示す必要がある` は、述部の中心が `ある` なので当たらない。

誤検知として残るのは、人を指す普通名詞が主語の文である。`ユーザーは、手順が分かりにくいことを示した。` がこれに当たる。IPADIC の品詞では人か物かを区別できないので、差し戻し文の「検査の誤りは残してよい」(セクション 7-3)で受ける。

advice は「`〜から、〜と分かる` のように、読み手が読み取る形に言い換える。元の文の確信度は変えない」とする。

#### `bunmatsu-renzoku`: 2 字以上の同じ文末表現が 4 文続いたとき、4 文目を拾う

文末表現は、句点の直前から文頭へ向かって、助動詞・助詞・非自立の動詞・接尾の動詞・非自立の名詞が続く範囲の表層形とする。`検査である。` の文末表現は `である`、`直している。` は `ている`、`書く。` は空になる。

規律は「同じ文末表現が 3 文続いたら、次の文で形を変える」と定める。3 文までは規律の範囲内なので、同じ段落で 2 字以上の同じ文末表現が 4 文続いたときに、4 文目で 1 件を出す。5 文目以降も同じ表現が続いても、同じ連続からは 1 件だけにする。

文末表現が空の文と 1 字の文(`た` `だ` など)は、そこで連続を切る。手順を平叙文で並べた段落(`〜を読む。〜を書く。〜を消す。`)と、経緯を過去形で書いた段落を拾わないためである。リストの項目は並列に書くのが正しい形なので、リストには当てない(セクション 4-3)。

advice は「4 文目の文末の形を変えるか、隣の文とつなぐ」とする。

#### `bun-nagasa`: 100 字以上で、読点の付いた節の切れ目が 2 つ以上ある文だけを拾う

長さは文の文字数で、空白を数えない。インラインコードと URL は、置き換えた 1 字として数える(セクション 4-3)。

節の切れ目は、読点の直前が次のどちらかである箇所とする。

- 接続助詞(`pos1` が `接続助詞`。`て` `が` `ので` `から` `けど` `ば` `し` `ながら` など)
- 動詞・形容詞・助動詞の連用形(`conjForm` が `連用形` か `連用テ接続`)

係助詞 `は` の直後の読点(`この結果は、`)は、主題を示す読点なので切れ目に数えない。

違反は、長さが 100 字以上で、かつ節の切れ目が 2 つ以上ある文とする。

規律は 40〜60 字を目安とし、一文一義なら超えてよいと定める。長さだけでは一文一義かを判定できないので、読点の付いた節の切れ目を「内容が 2 つ以上ある」ことの代わりに使う。長い識別子やパスを含む一義の文は、切れ目が無いので当たらない。名詞を読点で並べた列挙(`A、B、C を読む`)も、読点の直前が名詞なので切れ目に数えない。

当たる例として、句点を除いて 110 字の次の文を固定データに入れる。`ので、` と `が、` の 2 か所が切れ目になる(lindera で解析して確かめた)。

`取得が終わるまでの書き込みは正規表現の層だけで検査するので、形態素解析の規則による差し戻しは届かないが、取得が終わった後に書き込めば同じセッションの途中からでも形態素解析の層が加わり文の長さや文末の連続も検査の対象になる。`

advice は「節の切れ目で文を分ける。分けた後も主語と必要な事実を残す」とする。

#### `rentai-kasanari`: 読点の無い 30 字以上の区間に、修飾の節が 2 つある文だけを拾う

修飾の節は、動詞・形容詞・助動詞の `基本形` か `体言接続` の直後に名詞が来る箇所とする。接頭詞は名詞の一部とみなす。次のどれかに当たるものは数えない。

- 直後の名詞の表層が、`こと` `もの` `の` `とき` `時` `際` `ため` `よう` `ところ` `場合` `後` `前` `間` `うち` `まま` のどれかである。
- 直後の名詞の品詞が、接尾・代名詞・数である。
- 形容動詞の語幹に `な` が続く形(`静かな部屋`)である。形容動詞は 1 語の形容で、節ではないからである。

除く名詞を品詞(副詞可能)ではなく表層の一覧で指定するのは、`事実` や `結果` も IPADIC では副詞可能に分類されるためである。この 2 語は連体修飾を受ける普通の名詞として数える。一覧の語は、節を名詞にしたり、時や条件を表す副詞にしたりする働きを持つ。連体修飾の重なりとは別物なので除く。

違反は、読点・句点・係助詞 `は` で区切った 1 区間に修飾の節が 2 つ以上あり、区間が 30 字以上のときとする。

`利用者が昨日書いた設計に含まれる未解決の事項を確かめる。` では、`書いた→設計` と `含まれる→未解決` の 2 つが修飾の節になる。区間は句点を除いて 27 字なので、違反にはならない。これに 3 字以上の語句が加わって 30 字に達すれば当たる。`〜したときは、` の `とき` と `〜する場合は` の `場合` は数えない。

`の` による連体修飾の連鎖(`AのBのC`)は、今回は数えない。技術文では `plugin の hooks の matcher` のような所属の表現が多く、誤検知を抑えられないと判断した。

advice は「修飾の節を 1 つ残し、残りは前の文に出す。時系列か因果の順に並べる」とする。

### 5-5. 形態素解析が使えないときは、黙って正規表現の層だけで検査する

次のどの場合も、差し戻し文と測定の出力は正規表現の層の結果だけになる。hook は失敗を表に出さない。

- `CLAUDE_PLUGIN_DATA` が無い、取得が終わっていない、取得に失敗した。
- hook の環境に `AMATSUKA_NATIVE_JAPANESE_MORPH=off` が設定されている。
- 対応しない OS か、判定できない環境である。
- ファイルのサイズか mtime が `ready.json` と合わないか、`.node` や辞書の読み込みで例外が起きた。

`AMATSUKA_NATIVE_JAPANESE_MORPH=off` は、hook での形態素解析の取得と使用だけを止める。SessionStart の取得も、PostToolUse の読み込みも行わない。測定 CLI は利用者が明示的に実行するものなので、`--data-dir` を渡されたときは、この変数の値にかかわらず形態素解析を使う。`AMATSUKA_NATIVE_JAPANESE_CHECK=off` は書き込み後の検査をすべて止め、取得もしない。

## 6. 測定 CLI(A)は両方の層の違反を数え、形態素解析を使ったかを出力に書く

`scripts/measure.mjs`(元は `src/measure.ts`)として出力する。

### 6-1. 入力

| オプション | 対象 |
| --- | --- |
| `--git <range>` | `git diff -U0 <range>` で加わった行。正規表現の層は、加わった行をファイルの拡張子ごとにセクション 4-3 で抜き出して検査する。形態素解析の層は、変更後のファイル全体(`git show <range の終点>:<パス>`)から段落を組み、加わった行と重なる違反だけを数える(セクション 4-4)。HTML は、両方の層とも変更後のファイル全体からブロックを取り出し、加わった行と重なる違反だけを数える |
| `--transcripts <dir>` | `<dir>` 以下の `*.jsonl`。assistant の `tool_use` のうち、セクション 7-2 のツールの入力を検査する。subagent の jsonl は、隣の meta.json の `agentType` を書き手とする。書き込み後のファイルが無いので、HTML は入力の本文そのものからブロックを取り出し、全体を編集範囲とする |
| `--since <YYYY-MM-DD>` | `--transcripts` で、その日以降の記録だけを対象にする |
| `--data-dir <dir>` | 形態素解析の取得物がある `CLAUDE_PLUGIN_DATA` のディレクトリ。省略時は環境変数 `CLAUDE_PLUGIN_DATA` を使う。渡されたときは `AMATSUKA_NATIVE_JAPANESE_MORPH` の値を見ない(セクション 5-5) |

### 6-2. 出力

次の値を出す。

- 形態素解析を使ったか。使えなかったときはその理由(取得物が無い、読み込みに失敗した、など)
- 検査した行数と文の数、違反数、100 行あたりの違反数
- 規則ごとの違反数(多い順)。正規表現の層と形態素解析の層を分けて並べる
- 書き手ごと(main または agentType)の検査行数と違反数。`--transcripts` のときだけ出す
- 違反の例。規則ごとに 3 件まで

### 6-3. 基準値の取り方

基準値は、形態素解析の 4 規則まで実装し終えた後の Step 4(セクション 14)で取る。形態素解析を使える状態で、次の 2 つを記録する。

1. `--git 4049e9e..HEAD`(0.1.0-dev の導入以降にこのリポジトリへ加わった行)
2. `--transcripts ~/.claude/projects/<このリポジトリ>/ --since 2026-09-26`

結果は、測定に使ったコミットのハッシュと一緒に実装計画書の実施記録に残し、セクション 10(D)の入力にする。改修後に測り直すときは、同じハッシュの測定 CLI も使う。こうすると、規則の変更による差と出力の変化による差を分けられる。

形態素解析の 4 規則は、基準値の違反の例を人が読み、誤検知の割合を出す。誤検知が違反の半分を超えた規則は、セクション 5-4 の閾値か判定を絞ってから D に進む。

測定値の読み方には 2 つの限界がある。

- `--git` は起点と HEAD の差分なので、途中で書いて消した行は入らない。途中の書き込みは `--transcripts` で補う。
- 数えられるのは、避ける語、セクション 4-2 の 7 型、セクション 5-4 の 4 規則だけである。構成の規律と、セクション 3-2 に挙げた文の規律は測れない。効果を確かめるときは度数とは別に、改修後に書かれたコメントと文書を 30 件ほど人が読んで評価する。

## 7. 書き込み後の検査(F)は違反を差し戻し、同じ違反はセッションで 1 回だけにする

### 7-1. hook

`hooks/hooks.json` の PostToolUse に `scripts/check.mjs`(元は `src/check.ts`)を登録する。

matcher は次のとおりとする。MCP のサーバー名は書かず、ツール名で絞る。部分一致で `Edit` が他のツール名に当たらないよう、`^...$` で囲む。

```text
^(Write|Edit|MultiEdit|NotebookEdit|mcp__.+__(replace_content|replace_symbol_body|insert_after_symbol|insert_before_symbol|replace_in_files|create_text_file|replace_lines|insert_at_line))$
```

`replace_lines` と `insert_at_line` は Serena の任意ツールで、既定では無効である。有効にしたときに検査を逃れないよう、matcher に含める。存在しないツールの名前は、どの呼び出しにも一致しないだけなので、含めても害は無い。

### 7-2. 入力から検査対象を取り出す

- パスは `tool_input` の `file_path` `notebook_path` `relative_path` の順に探す。相対パスは入力の `cwd` から解決する。
- 本文は `content` `new_string` `edits[].new_string` `new_source` `body` `repl` を集める。`edits[]` の各要素は連結せず、1 件ずつ別の本文として扱う。
- NotebookEdit の入力は `notebook_path` `new_source` `cell_type` `edit_mode` `cell_id` である(このセッションのツール定義で確認)。抜き出し方はセクション 4-3 の表に従う。
- パスが無いか、本文が無いときは何も出力せずに終える。
- `replace_in_files` でパスがディレクトリのときは検査しない。対象のファイルを列挙できず、ignore-file の判定もできないためである。
- 書き込み後のファイルを 1 回読み、ignore-file の判定と、形態素解析の層の入力の両方に使う(セクション 4-3)。
- 正規表現の層は、HTML 以外では集めた本文に当てる。HTML では、書き込み後のファイル全体から取り出したブロックに当て、編集範囲と重なる違反だけを差し戻す(セクション 4-3)。
- 形態素解析の層と、HTML の正規表現の層の編集範囲は、書き込み後のファイルの中から各本文を探して決める。見つかった位置の最初の行から最後の行までを、その本文の編集範囲とする。Write と `create_text_file` はファイル全体を編集範囲とする。本文がファイルの中に見つからないとき(書き込み後に別の変更が入った場合など)は、その本文について形態素解析の層を当てない。HTML では正規表現の層も当てない。
- 形態素解析の解析器は、`AMATSUKA_NATIVE_JAPANESE_MORPH=off` でなければ、セクション 5-1 の `loadAnalyzer(process.env.CLAUDE_PLUGIN_DATA)` で得る。`null` なら正規表現の層だけで検査する。

### 7-3. 出力

違反が無ければ何も出力しない。違反があれば次を返す。

```json
{"decision": "block", "reason": "<差し戻し文>"}
```

差し戻し文は次の形にする。違反は 10 件までを載せ、残りは件数だけを書く。形態素解析の規則の違反では、該当部分の代わりに文の先頭 20 字を載せる。

```text
[native-japanese] <パス> に書いた日本語に、書き方の規律の違反が <n> 件ある。該当箇所を書き直す。
- L<行>: 「<該当部分>」(<分類>)→ <advice>
...
引用・固有名詞・識別子・コード例として意図して書いた箇所と、検査の誤りと判断した箇所は、直さずに残してよい。直すときは、否定・条件・確信度を元の文のまま保つ。
```

### 7-4. 無効化と異常時

- 環境変数 `AMATSUKA_NATIVE_JAPANESE_CHECK=off` で検査を止める。既定は有効とする。
- 入力の JSON が壊れている、`discipline.md` が読めない、などのどの失敗でも、何も出力せず exit 0 で終える。検査の失敗で作業を止めない。
- 形態素解析の読み込みの失敗は、検査の失敗として扱わない。正規表現の層の結果だけで続ける(セクション 5-5)。

### 7-5. 同じ違反は 1 セッションで 1 回だけ差し戻す

直した結果の書き込みも再び検査される。意図して残した引用などを毎回差し戻すと、モデルが同じ箇所を書き換え続けるおそれがある。これを防ぐため、差し戻した違反を記録し、同じ違反は 2 回目以降は差し戻さない。

- 記録先は `os.tmpdir()/native-japanese/<session_id>.json` とする。
- 違反の同一性は、パスと規則 id と `match`(セクション 4-4)の組で判定する。行番号は編集でずれるため使わない。
- 記録済みの違反だけのときは何も出力しない。未記録の違反が 1 件でもあれば、未記録の分だけを差し戻して記録に加える。
- 記録は一時ファイルへ書いてから rename で置き換え、並行する書き込みで壊れないようにする。
- 記録の読み書きに失敗したときは、記録なしとして差し戻す。セクション 7-4 の「失敗で作業を止めない」には反しない。
- 記録は削除しない。一時ディレクトリの掃除に任せる。

この記録で止まるのは 2 回目以降の差し戻しだけで、最初の差し戻しで誤検知の箇所をモデルが書き換えることは防げない。誤検知による書き換えは、セクション 4-2 と 5-4 の規則の絞り込みと、差し戻し文の 2 つの指示で抑える。2 つの指示とは「検査の誤りは残してよい」と「否定・条件・確信度を保つ」である。同じ `match` を持つ別の行の違反も、同じセッションでは差し戻されなくなるが、これは許容する。

## 8. 翻訳調・避ける語・結論を先に書く規律は、どの口調でも適用すると明記する(B)

現行の適用範囲は「口調や文体を別の指示が定める場合、その項目は別の指示に従う」と書く。「文体」は広く読めるので、翻訳調や避ける語まで譲ると読める余地がある。譲る範囲そのものは変えず、譲らない項目を明記する。

譲る範囲を「敬体・常体・圧縮・体言止め」に狭める案と、「会話の口調はファイルに及ばない」と書く案は採らない。前者を採ると、今回対象外の会話で、構成と文の規律が圧縮口調の指示とぶつかる。後者は、ファイルにも圧縮口調を使うと利用者が選べる他の指示と逆になる。

0.1.0-dev の README の「他の口調指示との関係」は、口調の項目を譲った後も「翻訳調の言い換えや結論を先に書く規律は残ります」と書いている。この「結論を先に書く」も譲らない項目に含める。

`discipline.md` の「## 適用範囲」の 3 項目めと 4 項目めの間に、次の 1 項目を加える。

```markdown
- 翻訳調の言い換え、避ける語、最初の一文に結論を書く規律は、口調や文体を別の指示が定めていても適用する。会話にも、コード内のコメントと文書にも適用する。
```

README の「他の口調指示との関係」も、同じ段落の中に同じ 3 つを並べて書く。README の「無効にする方法」には、`AMATSUKA_NATIVE_JAPANESE_CHECK=off` で書き込み後の検査だけを止められることを足す。`AMATSUKA_NATIVE_JAPANESE_MORPH=off` で形態素解析の取得と使用を止められることも足す。`discipline.md` の編集は、セクション 10 と同じく `prompt-smith:prompt-smith` の規律で行う。

## 9. 毎ターンの要約注入(E)は、ファイルに書く日本語だけを 300 文字以内で促す

毎ターン届く注入は、会話の口調を毎ターン補強する他の指示と並ぶ。会話の口調を揺らさないよう、要約はファイルに書く日本語だけを対象にし、短く保つ。

- `references/reminder.md` を新設する。本文は 300 文字以内とし、テストで守る。
- `reminder.md` は固定のファイルで、UserPromptSubmit のたびに同じ内容を読んで注入する。ターンごとに内容を変えない。
- `reminder.md` には次の 2 つだけを置く。
  - 会話の口調は変えず、コード内のコメントと文書では翻訳調と避ける語を直してから書く、という趣旨の 1 文。
  - A の測定で違反の多かった上位の規則を、1 行ずつ最大 5 行。形態素解析の規則も候補に含める。
- 内容は D と同時に決め、`prompt-smith:prompt-smith` の規律で書く。

## 10. 測定結果から規律を組み直す(D)

セクション 6-3 の基準値を得てから行う。手順は次のとおりとする。

1. 基準値の違反の例を人が読み、誤検知を除いた度数を出す。以降の手順はこの度数を使う。誤検知が多かった規則は、セクション 4-2 か 5-4 の規則のほうを直す。
2. 避ける語の表と翻訳調の表の中で、度数の多い語と型を表の先頭に移す。構成と文のセクションは、項目が論理の順に並んでいるので並べ替えない。形態素解析で数えた 4 規則の度数は、E の要約に載せる規則を選ぶときに使う。
3. 避ける語のうち、誤検知を除いた度数の上位 10 語には、書き換えた例を添える。
4. 基準値の違反の例を読んで、セクション 4-2 の 7 型に当たらない翻訳調が繰り返し見つかったら、翻訳調の表に型を加えてよい。加えた型を正規表現で拾えるなら、`rules.ts` にも規則を足す。
5. 翻訳調の表で意味を変えている例を直す。
   - `〜にとって重要` の After の `この計画は、初期に合意を作れるかで決まる。` は、元の文に無い断定を加えている。
   - `〜に他ならない` の After の `時代が変わったから、こうなった。` は、元の文に無い因果を加えている。
6. 違反が 0 件だった規則は削らない。測定で数えられない規律(セクション 6-3 の限界)は、違反数を削る根拠にしない。
7. 9,000 文字以内に収める。

測れる範囲は形態素解析で広がった。文のセクションのうち、文の長さ、文末の連続、連体修飾の重なりの 3 項目と、翻訳調の表の先頭の型(命題を目的語にとる述語に限る)は度数で比べられる。構成のセクションと、読点の位置・語順・接続詞の射程・主語と述語の距離・cleft 構文は、引き続き度数では測れない。

`discipline.md` は `references/` にあるため、編集は `prompt-smith:prompt-smith` の規律で行う。避ける語の表の形式(分類の列と「」で囲む語)を変えるときは、`rules.ts` の読み取りを追随させる。

## 11. 実行時の取得は既存の方針に無い依存なので、ADR を追加する

ARCHITECTURE のシステム概要は、ソースを esbuild でバンドルして `scripts/` へ出力し、git 管理下に置くと定める。技術スタックは、プラグイン固有のランタイム依存をそのプラグインの `package.json` に置くと定める。ADR-005 が認めたのは、API キーを前提にした外部 API への依存である。

本改修は、ネイティブコードと辞書を git にも `package.json` にも置かず、実行時に外部から取得して hook の中で実行する。どの既存の規定にも当たらないので、ADR を 1 件追加する。追加は `metatron:updating-architecture` を起動して行い、`diff-architecture`、`get rules`、草案の第三者検査の手順を経る。本書の作成では実行しない。

草案の要点は次のとおり。

- タイトル: `[native-japanese] 形態素解析の実行物と辞書は初回に取得し、git に同梱しない`
- 背景: 文の規律を検査するには形態素解析が要る。lindera の `.node` は OS ごとに 5〜7.4MB あり、IPADIC の辞書は展開後 46MB になる。バンドル出力を git に置く方針のままでは、リポジトリに 6 種の `.node` と辞書が入る。
- 検討した選択肢:
  1. `.node` と辞書を git に同梱する
  2. `package.json` に lindera を置き、Claude Code のプラグイン導入時の自動インストールに任せる
  3. 初回に npm registry と GitHub のリリースから取得し、固定した sha256 で検証する(採用)
  4. 辞書を同梱できる純 JavaScript の kuromoji か lindera-wasm を使う
- 採用した結論: 取得元の URL と sha256 をコードに固定し、`${CLAUDE_PLUGIN_DATA}` へ保存する。取得は hook を待たせない。取得できない環境では形態素解析を使わずに動く。利用者は `AMATSUKA_NATIVE_JAPANESE_MORPH=off` で取得を止められる。
- 理由: 1 はリポジトリが 50MB 以上増え、使わない OS の `.node` も全員に配る。2 は成り立たない。利用者の導入はファイルの配置であり、`package.json` の依存は入らない。辞書も npm に無い。4 はセクション 2-2 の計測で、プロセス全体が 300ms と 820ms かかる。書き込みのたびに起動する hook には重い。
- 影響範囲: native-japanese は外部資産を実行時に取得する。システム概要に、このことを追記する。技術スタックの「プラグイン固有のランタイム依存は、そのプラグインの `package.json` に置く」に、この ADR を例外として添える。

## 13. テスト

vitest で書き、`.claude/rules/metatron/testing-policy.md` に従って配置する。`src/lib/` のモジュールのテストは `src/lib/__test__/` に、`src/` の直下のモジュールのテストは `src/__test__/` に置く。固定の transcript、`discipline.md` の抜粋、形態素の列、小さな tarball と zip は `src/fixtures/` に置く。

### 13-1. 辞書が無い環境でも、形態素解析の規則のテストは固定した形態素の列で動かす

形態素解析の規則は、解析器ではなく形態素の列を入力にとる純粋な関数にする。実物の lindera の解析結果は、JSON の固定データ(`src/fixtures/morph/*.json`)にしておく。テストはこの固定データを読む。辞書と `.node` が無い環境でも、4 規則の判定はすべて確かめられる。

固定データは `src/testing/dump-tokens.mjs` で作る。このスクリプトは取得済みのディレクトリを引数にとり、例文ごとに `surface` と `details` を JSON に書き出す。拡張子を `.mjs` にして、lint と型検査の対象から外す。

実物の lindera を使うテストは、環境変数 `NATIVE_JAPANESE_MORPH_DIR` に取得済みのディレクトリがあるときだけ動かす。書き方は `describe.skipIf(!process.env.NATIVE_JAPANESE_MORPH_DIR)` とする。環境変数で `describe` ごと飛ばす形は、`plugins/metatron/src/__test__/rules-subagent-probe.test.ts` の 110 行の `describe.skipIf(!ENABLED)` に倣う。ただし、そちらの `ENABLED` は環境変数が `"1"` と等しいかで決まり、本書の変数はディレクトリのパスを値にとる点が違う。このテストは次の 2 つを確かめる。

- 固定データの例文を今の lindera で解析し直すと、固定データと一致する。lindera のバージョンを上げたときに固定データの作り直しを促す。
- 4 規則を実物の解析器で動かし、固定データのときと同じ違反が出る。

このリポジトリには CI の設定(`.github/`)が無い。形態素解析のテストは、取得済みの開発機で環境変数を設定して実行し、実施記録に残す。

## 15. リスク

| リスク | 起きたときの影響 | 対策 |
| --- | --- | --- |
| 形態素解析の規則の誤検知 | モデルが正しい文を書き換え、作業が遅れる | 判定と閾値を保守的にし(セクション 5-4)、基準値で誤検知の割合を確かめてから有効にする(Step 4)。同じ違反は 1 セッションで 1 回だけ差し戻す |
| `.node` がプロセスごと落ちる | 例外ではないので `try` で受けられず、hook が異常終了する。書き込みは成功しており、差し戻しが出ないだけで作業は続く | 利用者は `AMATSUKA_NATIVE_JAPANESE_MORPH=off` で止められる。README に書く |
| 取得物のすり替え | hook の中で任意のネイティブコードが動く | HTTPS で取得し、コードに固定した sha256 と一致しないものは捨てる。展開は既知の名前だけに限る |
| 取得の失敗の繰り返し | ネットワークの無い環境で、セッションのたびに取得を試みる | 失敗から 24 時間は取得しない |
| 取得の途中で止まる | `fetch.lock` や展開途中のディレクトリが残り、以後の取得が進まない | mtime が 10 分より古い `fetch.lock` は子プロセスが消す。`ready.json` の無いディレクトリは rename の前に消す。ファイルのサイズか mtime が `ready.json` と合わなければ、読み込み時に `ready.json` を消して取得に戻る |
| 取得の後の改変や破損を sha256 で見逃す | 取得の後にファイルが書き換えられても、サイズと mtime が同じなら読み込む | sha256 の照合は取得の直後に限る。データディレクトリに書き込める者は hook のスクリプトも書き換えられるので、毎回照合しても防げる脅威は増えない。途中で止まった展開と偶発的な破損は、サイズと mtime の比較で検出する(セクション 5-1) |
| HTML の抜き出しのずれ | 閉じタグの抜けた HTML でブロックの区切りがずれ、誤検知か取りこぼしが出る | 正規表現での抜き出しの上限を、実装のコメントに `ponytail:` として書く。問題になったら HTML のパーサーに置き換える。それまでパーサーの依存は増やさない |
| 確かめていない OS | macOS・Windows・arm64 で読み込めない | 読み込めなければ正規表現の層に戻る。linux-x64(WSL2)以外は未検証と README に書く |
| ディスクの使用 | `${CLAUDE_PLUGIN_DATA}` に 54MB ほどを置く | 古いバージョンのディレクトリは取得の後に消す。アンインストールで消える |
| lindera の更新 | 固定データと実物の解析結果がずれる | バージョンと sha256 をコードに固定し、上げるときは固定データを作り直す。セクション 13-1 のテストがずれを検出する |

## 17. 不採用案

| 案 | 採らなかった理由 |
| --- | --- |
| Stop / SubagentStop で会話を検査する(C) | 会話は圧縮口調で上書きされ、弱さを判断できない。今回はユーザーの判断で扱わない |
| output style を同梱する | 同時に有効にできる output style は 1 つだけで、利用者の output style と共存できない |
| 測定を Python で `tools/` に置く | hook は Node で動くため lint 本体が二重になる。測定は利用者にも配る |
| 避ける語を lint 側に列挙する | `discipline.md` と二重管理になる |
| 適用範囲で譲る項目を敬体・常体・圧縮・体言止めに狭める、またはファイルには会話の口調が及ばないと書く | 前者を採ると、今回対象外の会話で、構成と文の規律が圧縮口調とぶつかる。後者は、ファイルにも圧縮口調を使うという利用者の選択と逆になる(セクション 8) |
| Bash によるファイル書き込みも検査する | Bash の呼び出しのたびに Node が起動し、コマンドから書き込み先と本文を取り出す処理も要る。Bash での文書作成は例外的な経路とみなす |
| 違反を最初は警告だけにする | PostToolUse の block は書き込みを取り消さず、差し戻しの文を届けるだけである。警告との差が小さい |
| MCP ツールをすべて matcher に入れる | 書き込みと無関係な MCP 呼び出しのたびに Node が起動する |
| 検査を正規表現に限り、形態素解析を使わない | 文の長さ、文末の連続、連体修飾の重なりは語の並びだけでは判定できない。lindera(N-API)なら hook 1 回あたり 40ms ほどの増加で済む(セクション 2-2) |
| kuromoji か lindera-wasm を使う | 辞書ロードが 677ms と 183ms かかり、書き込みのたびに起動する hook には重い(セクション 2-2) |
| npm の `lindera` パッケージをバンドルに含める、または `package.json` の依存にする | ESM へのバンドルが失敗する(セクション 2-3)。依存にしても、利用者の導入はファイルの配置なので `package.json` の依存は入らない。辞書も npm に無い(セクション 11) |
| `.node` と辞書を git に同梱する | リポジトリが 50MB 以上増え、使わない OS の `.node` も全員に配る(セクション 11) |
| 取得を hook の中で同期して行う | 初回の書き込みか起動が、13MB の取得を待って止まる |
| zip と tarball の展開に npm のライブラリか OS の `unzip` `tar` を使う | ライブラリは依存を増やす。`unzip` は Linux に無いことがあり、GNU tar は zip を展開できない。zip は deflate だけなので `zlib.inflateRawSync` で足りる |
| `の` の連鎖も連体修飾の重なりとして数える | 技術文の所属の表現(`A の B の C`)に多く当たり、誤検知を抑えられない |
| HTML をパーサーの npm パッケージで解析する | 依存を増やす(セクション 3-3)。正規表現での抜き出しの上限は `ponytail:` のコメントに残し、問題になってから置き換える |
| ignore-file の目印をファイルのどこにあっても認める | 目印を説明する文書(本書など)が検査から外れる |
