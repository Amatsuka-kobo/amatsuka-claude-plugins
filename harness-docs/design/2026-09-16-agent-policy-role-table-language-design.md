## 1. 背景と目的

SubagentStart と SessionStart のフックは、プロジェクトの `.claude/agents/` を走査して「役割 → Agent 名」の対応表をセッションへ注入する。対応表の各行は次の形である(`src/hooks/marker-scan.ts:241`)。

```ts
lines.push(`- ${labelOf(role)}: ${names.join(" / ")}`)
```

`labelOf` が返すのは `ROLES[].label`、すなわち**日本語ラベル**である(`src/agents/roles.ts:30-133`。17 役割すべて日本語)。したがって実際に注入される行はこうなる。

```
- 文書作成: document-writer (gpt)
- 設計・計画・実装のアドバイザー: independent-tech-adviser (gpt) / technical-adviser (claude)
```

(本リポジトリで 2026-09-16 に実測した行である。定義を再生成すると vendor 表記は変わる。§3.4 を参照)

一方、`--lang en` で生成した Agent 定義に埋め込まれる共通規律断片 `assets/roles/en/_common.md` は、役割を**英語名**で参照する。役割名で対応表を引くことに関わる条項はこの断片の 2 箇所である。

**`en/_common.md:21`(文書作成への再委譲)**

> - When you need to write a **document that is saved as a file**, re-delegate to the definition for the role labelled Document Authoring **in the role marker table**, if the table has one.

**`en/_common.md:14`(アドバイザー照合)**

> - Use the definition for the "design, planning, and implementation advisor" band. If the project has one, call it by name; otherwise start a subagent with a `model` override of `Fable`.

**2 条項は同じ欠陥ではない。** 症状を分けて述べる。

| 条項 | 対応表の指名 | 症状 |
| --- | --- | --- |
| `:21` | **する**(`in the role marker table`) | 対応表を明示的に指名し、`Document Authoring` で行を探す。**表に該当する行が無い**(不一致) |
| `:14` | **しない**(`role marker table` の語が無い) | 表を指名しないまま「`"design, planning, and implementation advisor"` の定義を使え」と命じる。**表を見る根拠も、見たときに一致する行も無い。指示として宙に浮いている** |

なお `:14` の `band` は 0.18 以前の用語であり、現行の語彙(`role` / 担当表)と食い違ったまま残っている。

ja の対応表には `文書作成` も `設計・計画・実装のアドバイザー` も実在するため ja 定義は成立するが、en 定義が探す `Document Authoring` / `design, planning, and implementation advisor` は対応表のどの行にも存在しない。**`--lang en` で生成した定義では、この 2 条項の照合先が無い。**

この欠陥は既存設計書 §10-9 で「既存の欠陥・スコープ外」として記録されていた。本設計書はその積み残しを解く。

### 1.1 欠陥の実際の重さ(設計判断の前提)

**対応表を読むのは文字列マッチャではなく LLM である。** `設計・計画・実装のアドバイザー` は `design, planning, and implementation advisor` のほぼ逐語訳であり、`文書作成` と `Document Authoring` も同様に対応づく。多言語モデルであれば、対応表が日本語でも条項が英語でも、意味で橋渡しできる場合がある。したがって症状は「必ず失敗する」ではなく、**「橋渡しの成否がモデルとその時の推論に委ねられ、失敗しても誰にも見えない」**である。

この性質は両方向に効く。一方では「実害が観測されていない」ことの説明になり(案 (c) を支える)、他方では「規律の成立が検証不能な推論に依存している」という問題そのものでもある(案 (a) を支える)。本設計書は、この事実を伏せずに各案の評価へ持ち込む。

### 1.2 依頼文転記の経路が、欠陥を部分的に塞いでいる

もう 1 つ、欠陥の形を正確にするために要る事実がある。**オーケストレーターは `references/orchestration-discipline.md:92`,`:93` を依頼文へ転記する**(§3.6)。この 2 条項は `_common.md:21`,`:14` と同じ内容を日本語ラベルで書いており、日本語ラベルは対応表の行に実在する。

したがって**転記が行われたセッションでは、en 生成定義のサブエージェントであっても、依頼文側の経路で日本語ラベル照合が成立する。**

欠陥の正確な形は「en 定義は照合できない」ではなく、次のとおりである。

> 定義本文(英語)と依頼文(日本語)が**別のキー**で対応表を引くよう命じており、そのうち定義本文側だけが表と文字一致しない。オーケストレーターが規律どおり転記すれば、依頼文側の経路が成立する。

**この事実は欠陥を軽くするが、解消はしない。** 依頼文転記は**オーケストレーターが規律を守った場合にのみ**効く経路であり、定義本文の欠陥そのものには触れない。転記が漏れたセッション、および定義を名指しで直接起動したセッションでは、en 定義は依然として照合先を持たない。§5.3 の軸 1 で (c) の評価を「無し」とするのはこのためである。

## 2. 解くべき問題(確定済み)

1. `--lang en` で生成した定義の `en/_common.md:21` が対応表を指名しながら、探す `Document Authoring` が表のどの行とも一致しない。
2. 同 `:14` は対応表を指名しないまま英語の役割名で定義を指せと命じており、表を見る根拠も一致する行も無い。
3. この 2 条項は「アドバイザーへの相談先の決定」と「文書作成役への再委譲」という、サブエージェントの委譲挙動そのものを決める条項である。
3. 緩和策として一度採られた「en 断片へ日本語ラベルを併記する」案は、英語出力の純度検査と衝突して撤回済みである(§13)。

### 3.5 英語出力の純度検査の所在

検査の名前は **`it("英語で合成した定義に日本語と日本語約物が混入しない")`**(`src/agents/__test__/compose.test.ts`)。

- **作業ツリー基準・HEAD 基準ともに `:587-597`**(2026-09-16 の本設計書執筆完了時点)。
- **行番号は不安定であり、参照に使ってはならない。** 経緯は次のとおりである。既存設計書 §5.11c と §9 は `:616` を参照しており、これは執筆当時の HEAD では正しかった。context-map §10-2 は作業ツリー基準を `:595` と記録した。本設計書の調査時点では作業ツリーで `:587`、HEAD で `:616` だった。その後 `99eb595`(死んだ `modelId` 配管の除去)がコミットされ、**HEAD 側も `:587` へ移動して両者が一致した。** 数時間のうちに同一の検査が 3 つの異なる行番号で参照されたことになる。

## 6. 案 (a) の詳細 —— 対応表の各行に RoleId を併記する

### 6.1 役割行の形式(未解決事項 #4 への答え)

**採る形式: `- ${label} [${id}]: ${names}`**

```
- 文書作成 [doc-writing]: document-writer (gemini)
- その他のタスク [general]: general-implementer (gpt) / general-worker (claude)
- 設計・計画・実装のアドバイザー [advisor]: independent-tech-adviser (gpt) / technical-adviser (claude)
```

**この形式にする理由。**

1. **角括弧を使い、丸括弧を避ける。** 定義名の側が既に `名前 (vendor)` の形で丸括弧を使っている(`marker-scan.ts:225-228`)。`- 通常の実装 (normal-impl): general-implementer (gpt)` と書くと、1 行の中で意味の違う丸括弧が 2 種類並び、`(gpt)` と `(normal-impl)` が同格に見える。角括弧なら衝突しない。
2. **ラベルを先頭に置く。** 現在の運用はすべて ja であり、読み手(オーケストレーターと ja サブエージェント)は日本語ラベルで行を引く。ラベルを先頭に残せば、`toContain(label)` を使う既存検査群もそのまま通る(§10.1)。
3. **ラベルを落とさない。** RoleId だけの `- doc-writing: names` は ja の可読性を大きく損ない、`session-start.test.ts` の日本語ラベル `toContain` 検査を多数壊す。採らない。

**代替の書き方(採らないが記録する)。**

| 形式 | 採らない理由 |
| --- | --- |
| `- doc-writing (文書作成): names` | RoleId が先頭に来て ja の一覧性が落ちる。丸括弧が vendor と衝突する |
| `- 文書作成 (doc-writing): names` | 丸括弧が vendor と衝突する。角括弧に対する利点が無い |
| `- doc-writing: names` | ja の可読性を失い、日本語ラベルを参照する既存の生成済み定義と規律(§3.6)がすべて空振りする |
| 2 行に分けて RoleId を別行に出す | 行数が倍になり、切り詰め(C6)の単位が壊れる |
