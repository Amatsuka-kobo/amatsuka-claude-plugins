## 0. 第 2 版で変わったこと

第 1 版は「claude プロファイルでは Claude モデル以外の定義を対応表から**除外する**」という減算モデルで書いた。ユーザーの判断により、これを**加算モデル**へ反転する。

- **claude 構成** = `model` が Claude のモデルで実行される定義を委譲先の候補とする構成。これが既定である。
- **custom 構成** = 上記に加えて、外部ベンダーのモデルを指定した定義も候補に含める構成。

反転は表現の問題に留まらない。判定の主語が「除外規則」から「プロファイルが決める候補集合」へ移り、候補集合が 1 箇所で決まる。これにより、第 1 版の最大の欠陥(対応表から外した定義が、対応表に無い役割の選定で拾い直される)が **claude 構成と custom 成功時については機械的に解消する**(§6.4)。

**ただし custom フォールバック時だけは、子(SubagentStart)の候補範囲が `with-external` のまま残る。** SubagentStart は環境変数の値しか見られず、親がフォールバックした事実を知る手段を持たないためである。この 1 経路は機械的には塞がらないので、規律の条項で埋める(§6.13)。「構造的に解消」と書けるのは残り 2 経路である。

あわせて `setup-agents` の「Claude のみ」を CLI フラグまで貫徹させ(§6.9)、第 1 版で見落としていた 10 件の不整合を直す。

## 2. 背景と目的

2 つのプロファイルは現在「対応表を持つか否か」で分かれている。この分け方が 3 つの問題を生んでいる。

- **claude 構成では、プロジェクトの Claude 定義が委譲先として使われない。** 両 SKILL は「担当表の『種別』が `readonly` の役割はビルトイン `Explore`、`impl` の役割は `general-purpose` へ委譲する」と書き、ビルトインを第一候補にしてしまう。プロジェクトが `code-reviewer`(`sonnet`)や `haiku-reviewer`(`haiku`)を持っていても使われない。**ユーザーはこの記述を誤りと判断した**(R4)。
- **同じ規律が 2 通りに書かれている。** 委譲先解決が claude SKILL L18 と custom SKILL L21 に別々の形で存在する。
- **`setup-agents` が custom 専用である。** Claude だけの構成を作りたい利用者に生成経路が無い。一方で Claude enum は照会なしで候補提示から生成まで通る(§4.2)。

本設計は、委譲先の候補集合という 1 つの概念で 2 つの構成を表し、対応表・規律・setup をその概念の上へ載せ替える。

## 6. 設計判断

### 6.1 委譲先の候補集合(A-1)

**決定: 「候補集合」を中心概念に据える。プロファイルが候補集合を決め、その集合を対応表の生成と委譲先の選定の両方へ当てる。**

- **claude 構成の候補** = `model` が Claude のモデルで実行される Agent 定義。これが基底である。
- **custom 構成の候補** = 上記に加えて、外部ベンダーのモデルを指定した定義。

「Claude のモデルで実行される」の条件は次の 2 つを満たすことである。

1. `model` が未宣言、または `inherit`、または Claude enum(`sonnet` / `opus` / `haiku` / `fable`)である。
2. `agent-policy-vendor` が未宣言、`claude`、`none` のいずれかである。

**条件 1 が主である理由。** 沈黙故障の直接原因は「プロキシにしか存在しないモデル名で dispatch すること」であり、それは `model` の値そのものである。同じ判定は `session-start.ts` L149-155 が custom 検証で既に行っており、意味と集合をそこと揃えられる。`inherit` と未宣言を含めるのは、これらが親のモデルを継ぎ Claude 側で常に安全に解決されるためである(`two-profile-design` §6.2 L206 の判断を踏襲する)。

**条件 2 を足す理由。** `model: inherit` かつ `vendor: gpt` の定義は、条件 1 だけでは候補に入る。この定義を claude セッションで起動すると、GPT 向けに最適化された本文が Claude モデルで動く。沈黙故障ではないが、役割の第一候補として推すべきではない。

**`none` と未宣言を含める理由。** `setup-agents` は `vendor` が `none` のとき frontmatter へ出力しない。手書きの定義も持たない。候補から外すのは「外部ベンダーである積極的な証拠」がある場合に限る。未知のベンダー値(`gpt` / `grok` / `claude` / `none` 以外)は候補に含めない。条件 1 が最終的な安全弁として働く。

**手書き定義で `model` に実 ID を書いた場合(B-8)。** `model: claude-sonnet-4-6` のように実際の API モデル ID を書いた定義は Claude enum に無いため候補に入らない。沈黙故障は起きないが、対応表にも順 2 の候補にも現れない。**これは受容する。** 実 ID を前方一致などで Claude と推定する案は、プロキシのエイリアス命名(`claude-gpt-5-6-luna` が `claude-` で始まる)と衝突して誤判定する。回避策は `model` を enum(`sonnet` 等)で書くか、`setup-agents` で生成し直すことであり、README の移行項目に書く(§7.17)。拡張の可否は §12-3 へ回す。

**実装のシンボル名は加算側の語彙にする。** 第 1 版の `claudeRunnable`(減算を含意)は使わない。

### 6.2 規律断片の廃止(R5)

**決定: `references/subagent-discipline.md` を削除し、SubagentStart は対応表の注入専用にする。フックそのものは残す。**

フックごと廃止しない理由は 3 つある。(a) 対応表は実行時に `.claude/agents/` を走査して組み立てる**動的データ**であり、文書に静的に書けない。(b) `delegation-gate.ts` は `agent_id` で return し matcher も `Agent` を含まない。`session-start.ts` はメインセッション専用である。**対応表がサブエージェントへ自動で届く経路は SubagentStart だけである。**(c) R2 と A-2 により、SubagentStart は候補集合の範囲をサブエージェントへ伝える唯一の経路にもなる(§6.6)。

### 6.3 対応表を出すプロファイル(R2)

**決定: `claude` 分岐と、custom の claude フォールバック 3 経路で、`claude-only` の候補集合による対応表を注入する。`custom` 成功時は `with-external` の候補集合による対応表を注入する(現状どおり全定義)。`none` / 未設定 / 未知では対応表を出さない。**

### 6.4 候補集合を順 1 と順 2 の両方へ当てる(A-2)

**決定: 共通規律 `## 委譲先の解決` の冒頭に候補集合の定義を置き、解決順の全行がその集合の中だけを見るようにする。**

第 1 版の欠陥は、候補集合を対応表(順 1)にだけ当て、順 2「プロジェクトの Agent 定義に担当範囲が合うものがある」を無制約にしたことである。対応表から外した定義はディスク上に残るため、順 2 が拾い直す(§4.7 の具体例)。塞ぎ方を変えたのではなく迂回路を開いていた。

**独立レビュー役割にだけ置いた例外では足りない。** 第 1 版は「「設計書・実装計画書の独立レビュー」の役割は順 2 と順 3 へ進めない」という 1 役割ぶんの例外を置いたが、それ以外の 15 役割は無防備だった。候補集合を全行へ当てれば構造的に解消する。独立レビューの例外は、候補集合とは別の理由(同一ベンダーのレビューは独立性を持たない)で引き続き必要なので残す。

**サブエージェントは方針スキルを読まない。** したがって「自分が claude 構成にいるのか custom 構成にいるのか」を知る手段が要る。これを対応表そのものに載せる(§6.6)。

### 6.5 切り詰めの扱い(R5)

**決定: `MAX_CONTEXT_CHARS = 9500` を維持し、`ContextSections` / `render()` / `truncateContext()` を廃して表専用の `truncateTable()` に置き換える。表の先頭 2 行(説明行と候補範囲の行)を残す。**

上限を撤廃しない理由は、対応表だけでも上限を超えうるという実測があることである(テスト L430-463 が 112 定義で 9,500 字超を固定)。`before` と `after` が常に空になるため、3 段の削り順は表の後方行を削る 1 段へ縮む。

**先頭 2 行の意味が変わる。** 現状は「説明行 + 最初の役割行」だが、候補範囲の行を 2 行目に置くため「説明行 + 候補範囲の行」になる。候補範囲は切り詰めで落ちてはならない情報なので、この位置が正しい。テスト L430-463 の `context.split("\n").slice(0, 2)` は完全な表の先頭 2 行との比較なのでそのまま成立するが、**同テストの `fullRoleLines = fullLines.slice(1)`(L446)は役割行の起点が 1 行ずれるため `slice(2)` へ直す必要がある**(§9.2 No. 37)。

**役割行が 0 本になることはない。** 112 定義のフィクスチャでは役割行 1 本が約 1,100 文字であり、9,500 字の枠に 7 本程度が残る。役割行が 0 本になるのは 1 本が 9,300 文字を超える場合だけで、役割ラベルと定義名の長さから現実には起こらない。したがって `retainedRoleLines.length >= 2` を要求する既存アサーション(L454)は成立し続ける。

### 6.6 候補範囲を対応表に載せる(A-2 の実装手段)

**決定: `markerTable(env, marked, scope)` へ引数を足し、表の 2 行目に候補範囲を示す 1 行を出す。冒頭行(L208)の文面は変えない。**

この位置を選ぶ理由は 3 つある。

- **切り詰めで落ちない。** 先頭 2 行は `truncateTable()` が必ず残す(§6.5)。
- **SessionStart と SubagentStart で同一になる。** 両者が同じ env から同じ `scope` を導くため、テスト L276-293 が固定する同一性が保たれる(custom フォールバック時の乖離は §10 リスク 4 のとおり既知の受容)。
- **サブエージェントへ自動で届く。** 方針スキルを読まないサブエージェントが候補範囲を知る唯一の経路である。

冒頭行を変えず 2 行目を足すのは、`subagent-start.test.ts` の `TABLE_INTRO` を `toContain` する 7 ケースを壊さないためでもある。候補範囲の行は `- ` で始めない(役割行を数えるテストの判定を壊さないため)。

**文面は §6.1 の候補条件と過不足なく一致させる(A-4)。** 子はこの 1 行だけを手がかりに順 2 を実行するため、条件が狭いと誤る。enum だけを挙げると、`model` 未宣言や `inherit` の定義(機械側は候補)を子が過剰に除外し、`model: sonnet` + `vendor: gpt` の定義(機械側は候補外)を子が候補と誤る。

出力する文面。

| scope | 2 行目 |
| --- | --- |
| `claude-only` | 表に無い役割の委譲先も、`model` が `sonnet` / `opus` / `haiku` / `fable` / `inherit` のいずれかまたは未宣言で、かつ `agent-policy-vendor` が `claude` / `none` のいずれかまたは未宣言である定義から選ぶ。それ以外の定義は委譲先にしない。 |
| `with-external` | 表に無い役割の委譲先は、外部ベンダーのモデルを指定した定義も含めて選んでよい。 |

`claude-only` の文面は 110 字ほどで、enum だけを挙げる案より約 40 字(**約 120 B**)長い。claude 構成の全セッションと全 spawn に乗る固定費だが、条件を落として子が誤るコストのほうが高い。

**代案「子には順 2 を行わせない」は採らない。** 「対応表に載っている名前だけを使う」と限定すると、対応表に無い役割を子が再委譲するときに順 3(ビルトイン)へ直行することになり、プロジェクト定義が使われない。これは R3 / R4 が直そうとした問題を子の階層で再現する。また親と子で解決順が変わるため、規律を 2 通り書くことになる。

### 6.7 非 custom / 非 claude 分岐の出力

**決定: `none` / 未設定 / 未知では、SubagentStart は従来どおり `NO_MARKERS`「対応表なし(このプロジェクトに役割マーカー付き定義は無い)」だけを返す。注入を取りやめない。**

### 6.8 委譲先解決の共通規律(R3 / R4 / A-2)

**決定: 共通規律へ `## 委譲先の解決` 節を新設し、両 SKILL の `## 実行役割の解決順` 節を削除する。節は「候補」と「解決順」の 2 つの小節で構成する。**

### 6.9 `setup-agents` の構成貫徹(R1 / A-3)

### 6.10 規律の主語整備と転記の射程(R6)

#### 6.10.1 転記の射程 —— 全条項を転記する

**決定: オーケストレーターとサブエージェントのいずれも、「サブエージェントは〜」で始まる条項を全て転記する。**

| 案 | 内容 | 転記量 | 判断の要否 |
| --- | --- | --- | --- |
| (A) 全条項 | 「サブエージェントは〜」で始まる条項をすべて転記する | 9 条項 / 約 1,928 B / 約 640 token | 不要 |
| (B) 関わる条項 | その委譲に関わるものだけを転記する | 可変 | **毎回必要** |
| (C) 条件つき部分集合 | Agent Tool を許可する委譲先には全条項、許可しない委譲先には再委譲・アドバイザー関連を除く | 約 60〜100% | 1 回 |

**(A) を採る。** 軸は「転記量」対「確実性」である。

- (B) は「関わる」の判断基準を書けない。既存 L54 の「必要な規律は」という曖昧さを別の曖昧さに置き換えるだけである。判断を挟む規律は落ちる。

サブエージェント側の条項は「**依頼文で受け取った**「サブエージェントは〜」で始まる条項をすべて」と書く。「自身が受け取った」では生成定義の本文由来か依頼文由来かが定まらない。依頼文に限定すれば、親が転記した集合がそのまま子へ渡り、孫へ渡る。この条項自身も「サブエージェントは〜」で始まるため、転記先で再び転記の対象になる。**追加の機構なしで全階層へ伝播する。**

#### 6.10.2 転記可能性の要件

転記される条項は文書から切り出されて依頼文へ運ばれる。したがって**隣の箇条書きを参照する書き方はできない**。「直前の 2 項目を明記する」と書くと転記先で指示対象が失われる。各条項は単独で読めるように書く。オーケストレーター向け条項との文言の重複は、この転記可能性の対価として受け入れる。「サブエージェントは〜」条項は文書内で連続したブロックに集める。

### 6.13 custom フォールバック時の子の候補範囲(A-2 の残り 1 経路)

SessionStart は custom がフォールバックしたとき `claude-only` へ絞るが、SubagentStart は環境変数の値しか見られないため `with-external` のままである。子の対応表に GPT / Grok の定義が載り、子がそこへ再委譲すると沈黙故障する。フォールバックの理由がまさに「外部モデルが実在しない」であるため、A-2 の趣旨と衝突する。

| 軸 | 案 1(フォールバックを記録して読む) | 案 2(受容する) | **案 3(規律の条項で埋める)** |
| --- | --- | --- | --- |
| 実装コスト | SessionStart に書き込み、SubagentStart に読み込み、後片付けの 3 箇所。**`session-start.ts` L3 の「ファイルは書かない」という明示の不変条件を破る** | 0 | 共通規律に 1 条項。コード変更 0 |

```ts
export const CLAUDE_ENUM_MODELS: readonly string[] = [
```

```ts
function truncateTable(table: string): {
  context: string
  truncated: boolean
} {
  if (table.length <= MAX_CONTEXT_CHARS) {
    return { context: table, truncated: false }
  }

  const lines = table.split("\n")
  let context = lines.join("\n")
  while (lines.length > 2 && context.length > MAX_CONTEXT_CHARS) {
    lines.pop()
    context = lines.join("\n")
  }
  if (context.length > MAX_CONTEXT_CHARS) {
    context = context.slice(0, MAX_CONTEXT_CHARS)
  }
  return { context, truncated: true }
}
```

`lines.length > 2` が残す先頭 2 行は、説明行と候補範囲の行である(§6.5)。`NO_MARKERS` は 1 行なので while に入らず、最終行の `slice` だけが働く。

## 11. 不採用案

### 11.1 SubagentStart フックごと廃止

**不採用の理由。** 対応表は実行時に走査して組み立てる動的データであり文書に静的に書けない。`delegation-gate` はサブエージェントに発火せず、`session-start` はメインセッション専用である。R2 と A-2 により、SubagentStart は候補集合の範囲をサブエージェントへ伝える唯一の経路でもある。二段フックの P0(role map の全階層伝播)を放棄することになる。

### 11.2 claude 構成では対応表を出さない(現状維持)

**不採用の理由。** ユーザーが R2 で覆した。沈黙故障を塞ぐ目的は候補集合で達成でき、その代わりにプロジェクトの Claude 定義が委譲先として使えるようになる。旧決定は「表を出すか否か」の 2 択で考えていたが、「候補集合を定義し、表と選定の両方へ当てる」という第 3 の選択肢があった。

### 11.3 候補集合を対応表にだけ当てる(第 1 版の案)

**不採用の理由。** 対応表から外した定義がディスク上に残るため、対応表に無い役割の選定で拾い直される(§4.7 の具体例)。塞ぎ方を変えたのではなく迂回路を開くことになる。独立レビュー役割にだけ例外を置く案は 1 役割ぶんの穴しか塞がない。

### 11.4 候補の判定に `agent-policy-vendor` だけを使う

**不採用の理由。** `agent-policy-vendor` は `setup-agents` が書くフィールドであり、手書きの定義には無い。`vendor` を持たない外部モデル定義(`model: claude-gpt-5-6-luna` だけの手書き定義)を取りこぼす。沈黙故障の直接原因は `model` の値である。

### 11.5 候補の判定に `model` だけを使う

**不採用の理由。** `model: inherit` かつ `vendor: gpt` の定義が候補に入る。沈黙故障は起きないが、GPT 向けに書かれた本文を Claude モデルで動かすことになる。ただしこの案でも安全性は確保されるため、実装の簡素さを優先するなら選びうる(§12-2)。

### 11.6 `vendor` 未宣言を候補から外す

**不採用の理由。** `setup-agents` は `vendor` が `none` のとき出力せず、手書き定義も持たない。`model: sonnet` の手書き定義がすべて候補から消える。候補から外すのは「外部ベンダーである積極的な証拠」がある場合に限る。

### 11.7 候補範囲を対応表の外(別ブロック)で伝える

**不採用の理由。** 切り詰めで落ちる。`truncateTable()` が保証するのは表の先頭 2 行だけであり、表の外に置いた行は真っ先に削られる。また SubagentStart の `additionalContext` は対応表だけと決めた(§6.2)ため、別ブロックを足すとその決定と矛盾する。

### 11.8 転記の射程を「関わる条項」または Agent Tool 可否で分岐させる

**不採用の理由。** §6.10.1 のとおり。前者は判断基準を書けず、後者は害の無い節約のために判断ステップを足す。

### 11.9 `PreToolUse: Agent` の転記 nudge を同時に足す

**不採用の理由。** 相乗り先として想定される `delegation-gate` は matcher が `Edit|Write|NotebookEdit|mcp__.*` で `Agent` を含まず、`agent_id` でも return するため成立しない。唯一の相乗り先 `parallel-nudge` は並列化という別の規律を運んでおり、1 つの注入文へ 2 つの規律を束ねると両方の効きが落ちる。`two-profile-design` §2.3 の実測は「Claude が取ろうとしている行動の抑止」についてのものであり、依頼文へ項目を足す加算的な指示に同じ結論が当たる実測は**明示なし**である。**「効かないから不採用」ではなく「効くか不明なので先送り」である**(§12-6)。

### 11.10 対応表そのものを依頼文へ転記させる

**不採用の理由。** SubagentStart が spawn ごとに注入するため二重配布になる。対応表は動的データであり、依頼文へ書き写すとスナップショットが固定され、注入される最新の表と食い違いうる。SubagentStart が発火しない環境(Claude Code 2.0.43 未満)で対応表が届かない件は、規律 L55 が縮退を定めている。

### 11.11 `setup-agents` に `--policy` を復活させる

**不採用の理由。** `two-profile-design` §7.1 で削除済みであり、同名を復活させると移行の混乱を招く。`parseArgs` は現在この名前を「削除済み」として拒否しており、その挙動を維持したまま新しい名前 `--scope` を足すほうが安全である。

### 11.12 `discipline-role-table.test.ts` ではなく担当表の整形を戻す

**不採用の理由。** 長いダッシュ列は Markdown の表として正しく、整形ツールを通せば再発する。テストが守るべきは「区切り行であること」であって「ダッシュが 3 個であること」ではない。

### 11.13 手書きの実モデル ID を前方一致で Claude と推定する

**不採用の理由。** プロキシのエイリアスが `claude-gpt-5-6-luna` のように `claude-` で始まるため、前方一致では誤判定する。実 ID の網羅列挙はモデルの追加ごとに追随が要る。

### 11.14 custom フォールバックの事実を状態ファイルへ記録し、SubagentStart が読む

SessionStart がフォールバックしたときに `.claude/agent-policy/` へ印を残し、SubagentStart がそれを読んで `claude-only` へ倒す案(§6.13 の案 1)。

**不採用の理由。** 3 つある。

- **並行セッションで誤った拘束を生む。** 印はプロジェクト単位になる。同じプロジェクトで custom 成功セッションとフォールバックセッションが並走すると、成功しているセッションの子まで `claude-only` へ倒れ、外部ベンダーへの委譲がすべて止まる。塞ごうとしている沈黙故障より被害が広い。セッション単位に鍵を切れば回避できるが、`SubagentStart` の入力にセッション識別子があるかは**明示なし**であり、確証の無い前提の上に状態管理を積むことになる。
- **`session-start.ts` L3 の「ファイルは書かない」という明示の不変条件を破る。** SessionStart に副作用の有無という、候補集合より大きな契約の変更が要る。
- **状態の寿命を決められない。** 次回の SessionStart が成功しても、書き換えの前に spawn した子は古い印を読む。後片付けの契機が無い。

代わりに規律の条項で埋める(§6.13 の案 3、§7.5 新設 7)。なお `two-profile-design` §13 が却下したのは SubagentStart からの HTTP 照会であり、記録の読み書きそのものではない。本設計は別の理由で不採用としている。

### 11.15 過去に却下済みで再提案しない配布案

`CLAUDE.md` への焼き込み、反転注入、サイドカー割当マップ、派生定義の生成、`UserPromptSubmit` の毎ターン注入、system prompt の原文引用と名指し上書き、SubagentStart の fail-closed、allow-list による選別、SubagentStart からの `/v1/models` 照会。
