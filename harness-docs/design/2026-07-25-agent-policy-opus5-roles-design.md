## 1. 目的と背景

agent-policy の 2 方針スキル(`with-codex` / `claude-only`)の担当表は、Opus 枠の実体として Opus 4.8 世代を想定して書かれていた。Opus 5 世代(長文脈・高 effort)が Opus 枠の実体になったことで、**同じ担当表のままでは Opus 枠の能力が使われない**箇所が生じている。

本設計は「Opus 5 という行を担当表に足す」ものではない。後述の制約(§2-1)により行を足すことは構造的に不可能であり、**Opus 枠の担当範囲の境界線を引き直す**ことが実質的な作業になる。

## 2. 前提となる確定事実(制約)

### 2-1. dispatch の `model` にバージョン粒度がない

Agent tool の `model` 上書きパラメータは enum(`sonnet` / `opus` / `haiku` / `fable`)であり、Opus 4.8 と Opus 5 を dispatch で呼び分ける手段がない(2026-07-25 時点のツールスキーマで確認)。バージョン固定が可能なのは Agents 定義 frontmatter の `model:` フィールドのみで、これは README §設計上の確定事実(2026-07-20 実測)が GPT エイリアスについて記録した制約と同一の構造である。

**帰結:** 担当表を Fable / Opus 5 / Opus 4.8 / Sonnet / Haiku の 5 層にすると、Opus 5 と Opus 4.8 の呼び分けのために frontmatter でモデルを固定した Agents 定義ファイルが別途必要になり、`setup` ウィザードの守備範囲が広がる。本設計では 5 層化を採らず、**Opus 枠を 1 つに保つ**(§6-1)。

### 2-2. per-subagent の effort 指定手段がない

reasoning effort をサブエージェント単位で指定できるのは Workflow tool の `effort` パラメータのみで、Agent tool のスキーマには存在しない。effort はセッション設定(`settings.json` の `effortLevel`)でしか制御できない。

**帰結:** 「重い判断では effort を上げる」を方針の規範として書いても実行手段がないため、**方針文書には書かない**。

### 2-3. GPT 経路のプロンプトキャッシュ不成立

`cost-discipline.md` に実測と原因が記録済み。GPT Luna の input の 94% が非キャッシュであり、CLIProxyAPI の Anthropic→Codex 変換が暗号化 reasoning アイテムを履歴先頭付近に注入することが原因と確定している。Claude 系経路はこの変換を通らず正常にキャッシュされる。

**帰結:** **文脈が単調増加する役**(探索を統括して結果を積み上げる役)を GPT 経路に置くのが構造的に最も不利である。一方、grep/read を数ターン回して報告して終わる**短命な探索実働**は、非キャッシュでも損失が小さい。この非対称性が §3-2 の判断根拠になる。

## 3. 設計判断

### 3-1. Opus 枠は 1 つに保ち、世代前提はスキル本文に書かない

担当表の見出しは `Opus` のまま据え置く。見出しを「Opus 5」に変えても §2-1 により呼び分けは実現せず、可搬性だけが落ちる。

「Opus 枠の実体が Opus 5 世代である」という前提そのものも、スキル本文には書かない(§3-7)。エージェントの振る舞いを変えるのは担当表の割り当てであり、世代の宣言は行動を変えないためである。Opus 5 世代の能力は、担当範囲の引き直し(§3-2 / §3-3)と長文脈を前提とした 1 行の規律(§4-1 / §4-3 の末尾)としてのみスキルに現れる。

### 3-2. コードベース探索は「統括=Opus / 実働=GPT」のハイブリッドにする(`with-codex`)

現行は探索のオーケストレーションごと GPT Sol に委ねている。これを、**context-map の執筆・§未解決事項の判断・要件確定への接続を Opus が自ら行い、grep/read の反復など短命な探索実働のみ GPT Luna / GPT Terra へバッチ委譲する**形に変更する。

根拠は §2-3 の非対称性である。探索の統括は定義上「読んだものが積み上がる」役であり、キャッシュが効かない経路に置くと文脈全量が毎ターン全額課金される。実働ワーカーは短命なので同じ問題を受けない。加えて Opus 枠が長文脈になったことで、探索結果を保持したまま context-map を書けるようになった。

`claude-only` の探索章は現行のまま(Opus が統括し Sonnet / Haiku の探索サブエージェントを使う)で正しく、変更しない。

### 3-3. Fable を「承認ゲート + アドバイザー」に絞る

現行の担当表末尾には次の行がある。

> 重い最終レビュー・重要な設計判断は **Opus**(または Fable が直接)が担う。

この「または」が、判断のたびに「Fable に上げるべきか」を考えるコストを生んでいる。実際に上げすぎた結果が `cost-discipline.md` に記録された **Fable 約 26 ターン(≈ $52)** である。Opus 枠が Opus 5 世代になったことで、この行を Opus 側に一本化できる。

- 削除: 上記の末尾 1 行(Opus 行に吸収する)
- Fable の担当: ① 不可逆な決定の承認ゲート(計画確定 Approve) ② サブエージェントからのアドバイザー相談 — の 2 つのみ。自ら実務・レビューを行わない。

### 3-4. Haiku レビューの置き換え禁止を、理由ごと明記する

`with-codex` には既に「Haiku レビューはレビュー手法の固有名であり、GPT Luna に置き換えない」がある。Opus 枠が強くなるほど「Haiku ではなく Opus に見せた方が良いのでは」という誘惑が増すため、**禁止対象に Opus を含め、理由を明記する**。

> Opus・GPT に置き換えない — 強いモデルは行間を推論で埋めるため、弱い読者テストとしての価値が失われる。

### 3-5. `claude-only` の Opus は「複雑/重要な実装」を持ち続ける

`with-codex` と対称にして実装を Sonnet 主力へ寄せる案も検討したが、GPT 帯を持たない `claude-only` で難しい実装を Sonnet に完全委譲するのはリスクが大きい。現行維持とし、2 方針間の非対称を許容する。

**非対称の範囲を明示しておく:** `claude-only` の Opus は詳細設計・実装計画・複雑な実装を持つが、`with-codex` の Opus はこれらを持たない(GPT Sol の担当)。つまり非対称は実装作業量だけでなく設計・計画の主導権にも及ぶ。これは本設計が持ち込む差ではなく、**GPT 帯の有無から必然的に生じる現行どおりの差**である。両方針は CLAUDE.md でどちらか一方のみを指定して使うため、同一セッション内で 2 つの担当表が混在することはなく、緩和策は不要と判断する。

### 3-6. 2層オーケストレーター定義への波及(派生的判断)

§3-3 で Fable の担当を絞った結果、`context-map-guide.md:17` の 2 層定義に不整合が生じる。

現行 L17:

> 本設計では2層を区別する — **最上位オーケストレーター**(要件確定・承認ゲート担当)と**戦術オーケストレーター**(中間統括・重い最終レビュー担当)。…典型は 最上位=Fable、戦術=Opus

Fable が「自ら実務・レビューを行わない」なら、実務である**要件確定は最上位の担当から外れて戦術へ降りる**。承認ゲートは最上位に残る。

**採る形(層の名称は変えない):**

- **最上位オーケストレーター = 承認ゲート担当**(典型: Fable)
- **戦術オーケストレーター = 要件確定・中間統括・重い最終レビュー担当**(典型: Opus)

この形なら「最上位=Fable / 戦術=Opus」という典型対応がそのまま維持され、guide の規範文(すべて役割名で書かれている)は書き換え不要になる。変更は **L17 の括弧内の担当列挙から「要件確定」を最上位→戦術へ移す 1 箇所のみ**で済む。

**それでも SKILL 側では「Fable の承認」と具体名で書く理由:** 規律文が「最上位オーケストレーターの承認」のままだと、メインセッションが Opus のとき「自分が最上位だ」と解釈して自己承認する余地が残る。この曖昧さこそ §3-3 が潰そうとしているものなので、SKILL の規律文だけはモデル名で固定する(§4-4)。guide が役割名を保つこととは矛盾しない — **guide は役割の定義、SKILL は役割→モデルの割り当ての宣言**であり、両者の分担は `context-map-guide.md:17` が元から定めている。

**既知のトレードオフ:** 計画確定ごとに Fable への dispatch が 1 回確定発生する。従来は「最上位オーケストレーター」の解釈次第で自セッション内に閉じる余地があった。Fable ターンは高価だが、承認ゲートは 1 計画につき 1 回であり、§3-3 が削減する「重い最終レビューを Fable に上げるかの都度判断」より発生頻度は低い。品質のバックストップとして残す価値が上回ると判断する。

### 3-7. スキル本文には規律だけを書く(記述スタイル)

2 つの方針スキルは毎セッション冒頭にエージェントへロードされるため、本文は必要最小限の規律に留める。根拠・背景・実測値・トレードオフは本設計書と `references/` に置き、スキル本文へ持ち込まない。

見本はリポジトリルートの `agents-with-codex.md` / `agents-claude-only.md`。命令形の箇条書きのみで構成され、理由の説明を含まない。

**残す / 削るの境界:** 読んだ後にエージェントの振る舞いが変わる文は残す。納得を与えるだけの文は削る。

本設計の改訂文はすべてこのスタイルに従う。検討段階で候補にしていた次の記述は、スキル本文から除外する(いずれも本設計書に記録済み):

- 世代前提の宣言文「本方針は Opus 5 世代(長文脈・高 effort)を Opus 枠の実体として前提とする」(§3-1)
- Haiku を置き換えない理由「強いモデルは行間を推論で埋めるため、弱い読者テストとしての価値が失われる」(§3-4)
- 探索統括を Opus に置く根拠「文脈が単調増加する役をキャッシュの効く経路に置く」および `cost-discipline.md` への参照(§3-2)

## 6. 採用しなかった案

### 6-1. 担当表を 5 層(Fable / Opus 5 / Opus 4.8 / Sonnet / Haiku)にする

§2-1 により dispatch で呼び分けられず、frontmatter でモデルを固定した Agents 定義ファイルが別途必要になる。さらに `with-codex` のフォールバック記述・`context-map-guide.md` の役割→モデル割り当て・`advisor-rules.md` の 3 箇所すべてに Opus 世代の分岐が生えることになり、方針文書の複雑度に対して得られるものが小さい。

### 6-2. Opus 5 を「メインセッション専用」として定義する

「戦術オーケストレーター = メインセッション = Opus 5(1M・高 effort)」と役割側で固定する案。長文脈と effort がセッション設定でしか制御できない事実(§2-2)に素直だが、方針が特定のセッション構成に依存する記述になり、サブエージェントとして Opus を使う場合の担当が書けなくなる。

### 6-3. 探索を完全に Opus 側へ戻す

`claude-only` と同形にする案。方針間の差分は減るが、`with-codex` の価値(重量作業を GPT に寄せる)を大きく削る。短命な探索実働はキャッシュ不成立の影響が小さい(§2-3)ため、全面回収する必要がない。

### 6-4. Haiku レビューを Opus に置き換える

品質を下げる。§3-4 の通り、Haiku レビューは弱い読者テストであることに価値がある。

### 6-5. Fable をアドバイザー専任にする(承認ゲートも Opus が持つ)

コスト削減は最大だが、品質のバックストップが 1 段減る。承認ゲートは 1 計画につき 1 回であり、削減効果に対して失うものが大きい。
