# agent-policy トークンコスト分析と最適化の検討メモ

- 作成日: 2026-07-20
- ステータス: **調査・分析まで完了。フル設計は後日**（オーケストレーターの文脈を軽く保つ策まで含めて別途検討する）
- 関連: `plugins/agent-policy/`（2026-07-20 に main マージ済み）, `docs/design/2026-07-19-agent-policy-design.md`, `docs/plans/2026-07-20-agent-policy-implementation.md`
- 背景セッション: agent-policy プラグインを subagent-driven-development で実装した際、GPT Agents の入力トークンが膨大化した件の原因調査

---

## 1. 観測された事象

agent-policy プラグイン実装（全16タスクをサブエージェント駆動で実行）で、GPT Agents のセッション合計トークンが以下になった:

| エージェント | 主な担当 | dispatch 回数 | input | output |
|---|---|---|---|---|
| GPT Sol | 探索(context-map)・設計書(拒否) | ~3 | 1M | 21.7k |
| GPT Terra | 通常実装(SKILL 2件・setup 等) | 5 | 5M | 21.8k |
| GPT Luna | 軽微転記(manifest・テンプレ・追記) | 8 | 11M | 24.7k |

**逆説**: 最も軽量なタスクを担う Luna が最大の 11M input、最も複雑な Sol が最小の 1M input。タスクの複雑さと input が逆相関している。

## 2. 原因（否定されたもの）

- **タスクの複雑さではない**: 上記の逆相関から棄却。
- **エージェント定義やブリーフのサイズではない**: `codex/gpt-*.md` は各 ~2.2k トークン、各タスクブリーフは平均 ~58 行と小さく、11M には桁が足りない。
- **「毎回関連ファイルを全読み」ではない（実装フェーズについて）**: 今回の実装はブリーフに完成形の全文を埋め込んだ自己完結型で、実装者はブリーフ1つを読んで1ファイルを書いただけ。プロジェクトファイルの全読みはしていない。

## 3. 真の原因: 「1ターンあたりの文脈再送 × ターン数」

LLM はツールを1回呼ぶたびに、それまでの全文脈（システムプロンプト + 全ツールのスキーマ + スキル/エージェントのカタログ + これまでの会話）を丸ごと **入力として再送** する。したがって:

```
input ≈ (1ターンあたりの文脈サイズ) × (総ターン数)
総ターン数 = (dispatch 回数) × (1 dispatch あたりの tool 呼び出し数)
```

転記タスクでも「ブリーフ読む→ディレクトリ確認→書き込み→検証 grep 数回→git add→git commit」で 9〜16 ターン。これが dispatch ごとに繰り返される。

### 概算による裏付け
- Luna: 8 dispatch × 平均 ~12 tool_uses ≈ 97 ターン。11M ÷ 97 ≈ **1ターン ~113k トークン**
- Terra: 5 dispatch × ~10 ≈ 52 ターン。5M ÷ 52 ≈ **~96k トークン**

両者とも 1ターン **~100k** で一致。この 100k の正体は、GPT エージェントの `tools: Read, Grep, Glob, Write, Edit, Bash, Skill, LSP, Agent` に含まれる:
- **`Skill`** → 全56スキルのカタログが毎ターン読み込まれる
- **`Agent`** → 全カスタムエージェント（9種、~20k）のカタログが毎ターン読み込まれる
- システムプロンプト + 許可ツールのスキーマ

転記タスクは Skill も Agent もほぼ使わないのに、そのカタログを毎ターン ~100k 運んでいた。

## 4. コストモデル（実単価反映・訂正版）

実単価: **Fable 入力 $10/1M・出力 $50/1M、Luna 入力 $1/1M・出力 $6/1M**。

> ⚠ 重要な訂正: 当初の分析では Fable 自身の1ターンコストを「相殺されるので無視」と誤って扱った。実際は Fable の文脈が巨大（~200k+）なので、**Fable の1ターン ≈ $2.0（200k × $10/1M）が支配項**。最適化の主眼は「Luna をトリムする」ことよりも「**Fable のターン数を減らし、Fable の文脈を軽く保つ**」ことにある。

### 1ターンあたりの入力コスト
| | 概算 |
|---|---|
| Fable（文脈 ~200k × $10/1M） | **≈ $2.0 / ターン** |
| Luna トリム済（~40k × $1/1M） | **≈ $0.04 / ターン** |
| Luna 未トリム（~100k × $1/1M） | ≈ $0.10 / ターン |

Fable のターンは Luna（トリム済）の **約50倍高い**。転記の出力（ファイル F≈1.5k）は両者とも小さく（$0.075 vs $0.009）、支配するのは入力=ターン数。

### 1ファイル転記の比較
| | Fable 直接 Write | トリム Luna に委譲 |
|---|---|---|
| Fable dispatch ターン | — | $2.00 |
| Fable の書込/受取ターン | $2.00 | $2.00（結果受取） |
| Luna 実行（4ターン×$0.04 + 出力） | — | $0.17 |
| 出力（ファイル本体） | $0.075 | 含む |
| **合計** | **≈ $2.08** | **≈ $4.22** |

**→ 1ファイルなら Fable 直接が安い。** 理由: Luna の $1/1M は激安だが、そこへ辿り着くのに Fable のターンを2回（dispatch と結果受取）= 約$4 払う必要があり、Fable が1ターンで直接書く（$2）を超える。

### 16ファイル転記の比較（バッチの仕方で激変）
| 方式 | Fable ターン | Luna | 概算 |
|---|---|---|---|
| Fable 直接（1ターンに複数 Write をまとめ ~2ターン） | 2 × $2 = $4 | — | **≈ $5** |
| 委譲・1回にバッチ（トリム Luna） | 2 × $2 = $4 | 64ターン×$0.04=$2.6 | **≈ $7** |
| 委譲・タスク毎に個別（今回の方式・未トリム） | ~26 × $2 = $52 | ~$10 | **≈ $60+** |

今回の膨張（$60級）の正体は「**タスク毎に個別 dispatch で Fable のターンを ~26回使い、かつ未トリムでサブも太らせた**」こと。Luna を使ったこと自体ではない。

## 5. 委譲の損益分岐（原則）

> 委譲が得なのは「**サブ側でしか消化できないターン数**」が十分多いとき。そのターンを Fable の $2 でなく Luna の $0.04 で回せる。
> - **転記**（サブのターンをほとんど要さない・完成形が全指定済み） → **オーケストレーターが直接 Write**
> - **探索・反復**（サブが自前で多数ターンを要する） → **バッチ委譲**（多数を1 dispatch に束ね、Fable の関与を ~2ターンに抑える）+ **サブをトリム**

## 6. 最適化レバー（後日フル設計する対象）

優先度順:

1. **オーケストレーターの文脈を軽く保つ / ターン数を減らす（最優先・最大のレバー）**
   - Fable の1ターン単価そのもの（$2）を下げる。文脈サイズに比例するので、不要な MCP サーバー・カタログ・過去ログを積まない。
   - dispatch/受取の Fable ターンを減らす（バッチ、並列ツールコールの活用）。
   - ※本セッションの実測（`/context`）でも、MCP tools 15k・custom agents 20k・skills 5k 等が常時ロードされていた。オーケストレーター側でも軽量化余地がある。
2. **転記は Fable が直接、複数ファイルを1ターンにまとめて Write**（並列ツールコール）。dispatch/受取の Fable ターンを丸ごと省く。
3. **委譲するなら必ずバッチ**（多数ファイルを1 dispatch に束ねる）+ **サブエージェントをトリム**（不要な `Agent`・`Skill` ツールを外し、毎ターンのカタログ ~数十k を削る）。
4. **検証・コミットをオーケストレーター側に寄せてサブのターン数を減らす**。

## 7. agent-policy への反映候補

- 委譲判断の節に「損益分岐」（§5）を明記: 完成形が全指定された転記はオーケストレーターが直接 Write、探索・反復はバッチ委譲。
- エージェント定義のツール権限を役割ごとに最小化（Luna から `Agent`/`Skill` を外す等）。ただしアドバイザー相談に `Agent` が要る点とのトレードオフを設計する。
- context-map の位置づけ強化: 探索フェーズ（Sol/Opus）でのファイル再読を圧縮し、探索ターン数と累積文脈を削る。context-map は「探索の重複」に効き、「転記の増幅」には効かない、という適用範囲を方針に明記。

## 8. 未確定・裏取り事項

- **入力トークンの内訳の実測**: プロキシ（CLIProxyAPI）のリクエストログで1リクエストの input 内訳を確認する。カタログが大半なら §3 の診断が確定。プロジェクトファイルが大半なら「全読み」仮説が主因で、対策の優先順位が変わる。
- サブエージェントが実際にどのカタログ（Skill/Agent/MCP）をロードするかの正確な挙動確認。
- Fable/Luna 以外（Terra・Sol）の実単価と、Codex 側（GPT 本体）の消費見積り。
- 「オーケストレーターの文脈を軽く保つ」具体策（MCP の遅延ロード・カタログの間引き・セッション分割など）の実現可能性調査。
