# codiel の intent-sync で領域ファイルの古い記述を改訂・削除する

- 対象: Issue #47(親 Story #44)
- 変更するプラグイン: codiel 1.1.3 → 1.1.5(1.1.4 は並行する #46 が使い、この PR は #46 の後にマージする)
- この PR は codiel のソースと hook を変えない

## 領域ファイルが積み上がる一方なので、intent-sync に改訂と削除を加える

持続層の領域ファイル(`docs/intents/domains/<領域>.md`)には、古くなった記述を直す手順が無い。`skills/syncing-intents/references/persistent-layer.md` の取り込み手順は追加だけを定めている。

| 状況 | 今の動作 |
| --- | --- |
| 既存と同じ制約が来た | 制約を増やさず、出典の行を加える |
| 既存と矛盾する制約が来た | 上書きせずユーザーへ確認する。確認後に古い側をどう書き換えるかは定めていない |
| 今回の intent が触れない既存の記述が古くなった | 何もしない |
| `## 目的`・`## 非ゴール` | 「取り込む」とだけあり、置き換えか追記かを定めていない |

設計資料(`docs/intents/design/`)は run のたびに今の姿へ書き直されるが、領域ファイルは積み上がる一方になっている。#45 で失敗の記録が領域ファイルの通常のセクションになり、解決済みの失敗も残り続ける。

この PR で、intent-sync の取り込みの中に、今回の変更で古くなった記述の洗い出しと、承認を得た改訂・削除を加える。

範囲外は次のとおりである。

- 今回の run が触れない領域の古い記述。run の外で棚卸しするコマンドは作らない。
- 改修前の `## GOTCHAS 候補` のセクション。#45 の決定どおり読まず、書き換えない。
- metatron の ADR 候補・GOTCHAS 候補の走査。#46 で消える。

## 取り込みの中で洗い出し、同じ確認で承認を得る

洗い出しを置く場所について 3 つの方式を比べ、案 1 を採る。

| 軸 | 案 1: 取り込みの中で洗い出す | 案 2: 取り込みの後に別の確認を置く | 案 3: run の外のコマンドで棚卸しする |
| --- | --- | --- | --- |
| 内容 | 取り込む内容を読んだ後、書く前に古い記述を洗い出し、矛盾の確認と同じ `mark-ask` で承認を得る | 追加を書いてから、もう一度 `mark-ask` で改訂・削除の承認を得る | 利用者が任意の時点で全領域を見直す |
| 人への確認 | 1 回 | 2 回 | run とは別 |
| コミット | 追加と同じ、ゲート通過直後のコミット | 同じ | 別のコミット |
| 判定の材料 | 今回の intent・`design.md`・run の差分 | 同じ | 材料が無い。何が古いかを決める変更が無い |
| 再開の判定 | `report.md` の有無 1 つで済む | 追加だけ済んだ状態を別に区別する必要がある | 対象外 |

案 2 は確認が 2 回になり、途中で止まったときの状態が増える。案 3 は利用者が範囲外とした。

### 「古くなった」の判定

今回の intent(`## 目的`・`## 要求`・`## 意図的な制約`・`## 非スコープ`・`## 合意済み事項`)・`design.md`・run の差分に照らして、事実でなくなった記述を古いとみなす。例を 3 つ挙げる。

- 今回の intent が、領域ファイルの `## 非ゴール` に書かれた機能を実装した。非ゴールの項目を削除する案を出す。
- 今回の差分が、失敗の記録の `cause` にある仕組みを取り除いた。`countermeasure` が要らなくなったので、エントリを削除する案を出す。
- 今回の intent が、ある制約の `reason` の前提(「外部の決済サービスが 1 つだけ」など)を変えた。制約は保ち、`reason` を今の姿へ書き換える案を出す。

今回の変更と関係の無い記述は、内容が古く見えても案にしない。

`## 意図的な制約` だけは、run の差分を判定に使わない。実装が制約を破ったときに、差分に合わせて制約を消すと、review がその違反を検出できなくなる。そのため、差分だけが食い違う制約は違反として人に示す。

## 書式の変更

`references/intent-format.md` の「持続層」セクションに次を加える。エントリのキーとセクションの構成は変えない。

- `## 目的` と `## 非ゴール` は箇条書きで書き、1 行を 1 項目とする。intent ごとに区切らず 1 つの箇条書きとして書く。新しい項目の追加と、文面が同じ重複の除去のほかに既存の項目を書き換えるときは、承認を経る。
- `## 意図的な制約` の改訂では、`constraint` と `reason` を今の姿に書き換え、`sourceIntent` の行に今回の intent を加える。
- `## 由来` の行に、その取り込みで改訂・削除した記述を添える。値は例であり、実際のパスと記述に置き換える。

```markdown
## 由来
- docs/intents/2026-10-01-add-oauth-login.md(取り込み日 2026-10-01)
- docs/intents/2026-11-27-drop-legacy-session.md(取り込み日 2026-11-27)改訂: 「## 意図的な制約 / セッションの保存先」 / 削除: 「## 非ゴール / 管理画面からの一括削除」、「## 失敗の記録 / ログアウト後にフォームが消える」
```

- 添え書きは「改訂: 」「削除: 」の後に、名指しした記述を読点で並べ、2 つあるときは ` / ` で区切る。記述は「<セクション名> / <見出し>」を「」で囲んで名指しし、`## 目的`・`## 非ゴール` の項目は見出しの代わりに先頭の語句を書く。制約と失敗の記録で見出しが同じでも、セクション名で区別できる。
- 同じ intent の行に後の try が添えるときは、` ; ` で区切って後ろに足す。
- 項目やエントリの一部だけを消したときは、改訂として添える。
- 古い文面は git の履歴で読み、領域ファイルには残さない。
- 設計資料の `## 由来` には添え書きを付けない。`skills/syncing-intents/references/design-docs.md` の手順 4 にも同じ一文を置く。
- 中身がすべて消えたセクションは、見出しを残し、本文に「なし」と書く。`## 失敗の記録` も同じで、作る時点の規則(失敗を初めて書くときに作る)は変えない。

チェックリスト(`docs/format-change-checklist.md`)の「intent 文書と intent-issue の書式」の項目のうち、`skills/syncing-intents/SKILL.md` の持続層への取り込みを同じコミットで追随させる。ほかの項目(契約凍結文書の §9・§10、`filing-followup-issues`・`preparing-design-agendas`・`capturing-intent`・gh-utility の `issue-craft`)は intent 文書と intent-issue の書式を写すもので、持続層を写さないので追随させない。

## 再開は領域ごとに report.md の行で判定する

領域ファイルを書き終えた直後に、その領域の行を `steps/intent-sync/report.md` へ追記する。全領域の後に 1 回で書くと、複数の領域の途中で止まったとき、書き終えた領域と書いていない領域を区別できない。行の形は次のとおりにする。値は例である。

```markdown
取り込み: docs/intents/domains/auth.md
改訂: docs/intents/domains/auth.md / 「## 意図的な制約 / セッションの保存先」
削除: docs/intents/domains/auth.md / 「## 非ゴール / 管理画面からの一括削除」
見送り: docs/intents/domains/auth.md / 「## 失敗の記録 / ログアウト後にフォームが消える」
書かずに終えた矛盾: docs/intents/domains/auth.md / なし
```

- report.md に `取り込み` の行がある領域は、済んだものとして飛ばす。
- 行が無い領域で、`## 由来` に今回の intent の行があり、その行が HEAD の領域ファイルに無いときは、取り込み済みとして飛ばす。領域ファイルを書き終えてから report.md に追記するまでの間に止まった場合である。行の添え書きのうちこの try で付けた部分(try-2 以降は最後の ` ; ` より後)から `取り込み`・`改訂`・`削除` の行を復元し、`見送り` と `書かずに終えた矛盾` は「なし」とする。
- 全領域の `取り込み` の行がそろったら、領域ファイルの取り込みは済んでいる。`設計資料:` の行の判定(`orchestrating-runs` の `references/resume.md`)は変えない。
- 改訂・削除・見送りが無いときは、領域ファイルのパスの後に「なし」と書く。
- 見送りは、案を示して人が書き換えないと答えた記述である。次の run では、その run の変更に照らして改めて洗い出す。

HEAD との比較を条件に加えたのは、前の try が同じ intent の行をコミット済みのときに、新しい try の取り込みを済んだものと誤って飛ばさないためである。復元では、見送りと書かずに終えた矛盾が失われる。どちらも領域ファイルを変えない答えなので、次の run で改めて洗い出される。

- `orchestrating-runs` の `references/phase-intent-sync.md` の取り込み先の分岐。

### 削除した失敗の記録が写し直される場合がある

incident の記録は、写した run の `写し先` のコミットがベースの祖先であるか、写した run が完了しているときに写し済みとみなされる。写した run が squash merge され、その run の `.codiel/runs/<slug>/` が消えた後は、どちらも確かめられず、次の intent-sync が記録を集め直す。その記録を人が領域ファイルから削除していたら、同じ記録が写し直される。写し直した記録はその intent-sync の洗い出しから除かれるので、後の run の洗い出しで改めて削除の案に出る。起きるのは、incident の記録を残した run の手元のディレクトリが残り、写した run のディレクトリだけが消えたときに限るので、対処はしない(レビューの指摘を受け、既知の制約とした)。

### 領域ファイルを書く途中で止まると、再開で記録が抜ける場合がある

`persistent-layer.md` の手順 6 の途中で止まったときに、次の 3 つが起きる場合がある。

- 手順 6 の 1〜4 で改訂・削除を書いた後、手順 6 の 5 で `## 由来` の行を書く前に止まると、再開は手順 2 からやり直す。改訂済み・削除済みの記述は洗い出しに出ないので、`## 由来` の添え書きと report.md の改訂・削除の行が抜け、今回の intent の制約の行が重複して取り込まれるかもしれない。古い文面は未コミットの差分を経てコミットに入るので、git の履歴には残る。
- 手順 6 の 5 の後、手順 6 の 6 で `## 出典` へ追記する前に止まると、再開は復元の条件に当たって手順 2〜6 を飛ばす。そのため `## 出典` の追記が抜ける。領域ファイルのほかの記述と report.md の行は失われない。
- try-2 以降で、既存の `## 由来` の行の末尾に添え書きした直後に止まると、「その行が HEAD に無い」の判定が、行の文面で比べるか intent のパスで比べるかで割れる。文面で比べると、前の try の添え書きまで今回の report.md に載る。パスで比べると、取り込みをやり直すので、今回の削除の行が抜ける。

どれも塞ぐには、承認の答えを書き込みの前に report.md へ予定として残し、再開でそれを当て直す手順が要る。中断というまれな場合のために指示書を厚くしないと判断し、この手順は採らなかった。

### #46 で metatron との間のずれは解消した

metatron の `scan-adr-candidates` と `shrink-adr-candidate` は、領域ファイルの `[ADR 候補: <ID>]` の印でエントリを特定していた。印の付いた改修前のエントリを intent-sync が改訂すると、印が外れて走査に出なくなるずれがあった。#46(PR #61)で両コマンドが消えたので、このずれは残らない。
