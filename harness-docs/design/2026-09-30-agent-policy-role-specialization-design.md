## 1. 同じ役割に複数の定義を置いても、タスクごとに選び分けられない

利用者は、同じ役割の定義を領域ごとに複数置きたい。例は `frontend-general-implementer` と `backend-general-implementer` で、どちらも `agent-policy-role: normal-impl` を宣言する。2 つの定義は description と本文だけが違い、それぞれの領域に要る観点を書いている。

現行の規律には、1 役割に 1 つの委譲先を前提にした箇所が 3 つある。

- `references/orchestration-discipline.md:46` は、委譲先を実務タスクの着手前に一度確定し、以後はタスクごとに再判定しないと定める。`:134` も同じ趣旨である。frontend の作業と backend の作業を同じセッションで振り分けられない。
- 同じ役割に複数あるときの基準は「依頼内容に近いものを選ぶ」だけである(`:42` `:120` `:167`、`src/hooks/marker-scan.ts:235`)。どの特化にも当たらない作業の行き先が決まっていない。
- モデル注入起動の役割モデル(`:137`)と合成のホスト(`:167`)は「その役割に解決された定義」を基準にする。frontend が opus、backend が gpt のように `model` が違うと、役割モデルが 1 つに決まらない。

選ぶ手がかりは、定義の description と本文に既に書かれている。オーケストレーターは Agent ツールの一覧で各定義の description を読める。欠けているのは選び方の規律である。

## 2. 確定要件(ユーザー確定済み。本設計はこれを前提とし、覆さない)

### 2.1 R1: 利用者の定義を編集せず、プラグイン側で振り分けを成立させる

- 定義の frontmatter に新しい欄を足さない。
- 特化の手がかりには、定義の description と本文をそのまま使う。

### 2.2 R2: 着手前に確定するのは「役割 → 候補集合」までとする

- 候補集合は、役割マーカーの対応表でその役割を宣言している定義の集まりである。
- 候補が 2 件以上ある役割では、委譲のたびに集合から 1 件を選ぶ。
- 候補が 1 件の役割は、これまでどおりその定義へ委譲する。特化か汎用かの判定をしない。

### 2.3 R3: 選ぶ順は 4 ステップとし、上から評価する

1. 同じ役割の特化定義のうち、description と本文が示す担当領域に作業が含まれるもの。複数当たるときは依頼内容に近いものを選ぶ。
2. 同じ役割の汎用定義。
3. `general`(その他のタスク)の役割。`general` の候補集合にステップ 1 とステップ 2 を当てる。
4. ビルトイン Agents。元の役割の種別が `readonly` なら `Explore`、`impl` なら `general-purpose` とする。

- 特化定義とは、description か本文が担当をディレクトリ・技術領域・機能領域のいずれかに限っている定義である。例は「frontend の実装」「`apps/api/` 配下の変更」「決済機能」である。
- 汎用定義とは、そうした限定が無い定義である。判定はオーケストレーターが description と本文を読んで行う。
- この順は種別を問わず全役割に当てる。`readonly` の役割もステップ 3 で `general` へ回す。
- `general` 自身の委譲ではステップ 3 を飛ばす。
- ステップ 4 に入るのは、`general` の定義が無い場合と、`general` の定義が特化定義だけでどれも作業に当たらない場合である。
- 「設計書・実装計画書のレビュー」は既存の例外を維持する。ステップ 3 とステップ 4 へ進めず、該当が無ければレビューを省略する。

### 2.4 R4: 役割モデルと合成のホストは「そのタスクで選んだ定義」を基準にする

- custom 構成では、モデル注入起動で注入する役割モデルを、R3 でそのタスクに選んだ定義の `model` とする。
- claude 構成の役割モデルは、現行どおり担当表の「Claude モデル」列とする。列は役割ごとに 1 つなので、候補が複数あっても一意に決まる。`model` を enum で宣言した定義は、どちらの構成でも宣言値で動き、列に上書きされない(`orchestration-discipline.md:137` はモデル注入の対象を `model` 未宣言・`inherit` の定義に限る)。
- 合成のホストは、R3 でそのタスクに選んだ定義とする。
- ステップ 3 で `general` へ回した作業は、以後の起動形態の判定でも「その他のタスク」の役割として扱う。「その他のタスク」は合成の対象外なので(`orchestration-discipline.md:153`)、合成しない。
- ステップ 4 のビルトインは現行どおり合成せず、モデル注入起動にする(`orchestration-discipline.md:163`)。注入する役割モデルは、担当表の「Claude モデル」列で元の役割に当たる値とする。
- 委譲のたびに委譲先を選ぶので、起動形態も委譲のたびに決める。

### 2.5 R5: 注入表の形は変えない

- 役割マーカーの対応表は、定義名と vendor だけを載せる現行の形を保つ。description は載せない。
- 変えるのは表の冒頭文だけである。「同じ役割に複数あるときは依頼内容に近いものを選ぶ」を、規律の選ぶ順を参照する文に置き換える。
- サブエージェントは再委譲しないため、表から委譲先を選ぶのはオーケストレーターだけである。オーケストレーターは Agent ツールの一覧で description を読める。

### 2.6 R6: バージョンは `0.21.1-dev` とする

- `plugin.json` と `package.json` を揃えて上げる。

## 4. 範囲外

- setup-agents で特化定義を生成する機能。特化定義は利用者が手で書く。
- 定義の frontmatter への新しい欄(担当パスの glob、特化と汎用の区別)。
- 注入表への description の追加。
- フックによる汎用定義の機械判定。

## 5. 不採用案

- 担当パスの glob を frontmatter に持たせる案。利用者の定義を編集しない要件(R1)に反する。
- setup-agents の定型 description と照合し、フックが汎用定義を判定する案。手書きの汎用定義を特化定義と誤って扱う。ユーザーはオーケストレーターの判定を選んだ。
- 既定名(`general-implementer` 等)と一致する定義を汎用とみなす案。改名した汎用定義を扱えない。
- どの特化にも当たらない作業を、最も近い特化定義へ回す案。frontend の観点が CI の修正に混ざる。ユーザーは汎用定義 → `general` の順を選んだ。
- `readonly` の役割はステップ 3 を飛ばして `Explore` へ回す案。ユーザーは種別を問わず `general` へ回す順を選んだ。
- 候補が 2 件以上の役割だけ注入表に description を添える案。オーケストレーターは Agent ツールの一覧で description を読めるため、ユーザーは不要と判断した。

## 6. 検証

- `pnpm run lint`、`pnpm run typecheck`、`pnpm run test` を通す。
- 新しいセッションで実機を確かめる。`.claude/agents/` に `normal-impl` の特化定義 2 件(frontend と backend)と汎用定義 1 件を置く。
  - frontend の作業と backend の作業が、それぞれの特化定義へ委譲されること。
  - CI 設定の修正が汎用定義へ委譲されること。
  - 汎用定義を外すと、CI 設定の修正が `general` の定義へ委譲されること。このとき合成されず、依頼文に外部定義の本文が入らないこと。
  - `general` の定義も外すと、CI 設定の修正が `general-purpose` へ委譲され、`model` に担当表の `normal-impl` の Claude モデルが入ること。
- 委譲先は、セッションの transcript で Agent 呼び出しの `subagent_type` を読んで確かめる。
- 実機の確認に使った定義は、確認の後に取り除く。
