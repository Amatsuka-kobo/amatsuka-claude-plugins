## 1. 背景・目的

### 1-1. 何を分離するか

Codiel は 2 つの恒久資産を持つ。

- **`docs/ARCHITECTURE.md`** — プロジェクトの技術的前提(概要 / 技術スタック / ディレクトリ構成 /
  ドメインマップ / コマンド定義 / テスト方針 / 保護パス / 規約)。
- **`docs/GOTCHAS.md`** — プロジェクト固有の失敗知識の台帳。

どちらも **Codiel の run に固有の情報ではない**。「このプロジェクトはどう作られているか」
「このプロジェクトで何を踏むと転ぶか」は、Codiel を使わないセッションでも、別のプラグイン
(sandalphon の ASIS 探索、レビュー、オンボーディング)でも、人間の新規参画者にとっても価値がある。
にもかかわらず現状は、**Codiel をインストールし `/codiel:init` を通した人だけ**がこの資産を持てる。

metatron はこの 2 資産を Codiel から切り出し、独立したプラグインとして「記録し、更新し、
毎セッション注入する」ことを担当する。

### 1-2. 名前の由来

天の書記天使 Metatron に由来する。神の記録を司り、人の行いを書き留める役である。
プロジェクトの前提と、そこで犯された失敗を書き留め続けるという役割そのものを表す。README に記載する。

### 1-3. 何を機械で保証するか

現行は「AI に守らせる指示」で品質を保っている。`initializing-harness` の HARD-GATE
(承認なしに書き込まない・既存記述を削除しない・検証を省略しない)と
`recording-gotchas` の HARD-GATE(追記のみ)がそれである。指示は AI が合理化して破りうる。

metatron の目的は、これらを**指示より強い形**へ移すことにある。移す先の候補は 3 つあった。

| 手段 | 強制力 |
| --- | --- |
| MCP ツール | **呼び出しは任意**。呼ばずに Write で直接書けば素通り |
| CLI | **呼び出しは任意**。同上 |
| **PreToolUse deny hook** | **Edit / Write / NotebookEdit 経由の直接編集を、hook が正常動作する限り拒否する** |

**真の強制点は deny hook だけである。** MCP ツールも CLI も、それ単体では「行儀よく使えば
安全な窓口」でしかない。したがって設計の中心を deny hook に置き、
「正本ファイルへの直接編集を拒否し、正しい窓口へ誘導する」構造にする。

**保証範囲は限定的である。** deny hook が守るのは
「**Edit / Write / NotebookEdit 経由の直接編集を、hook が正常動作する限り拒否する**」ところまでで、
Bash リダイレクトによる書き込み、人間のエディタでの編集、hook 自身が失敗したとき
(フェイルオープン)は対象外である。これらは既知の限界として §7-5 に明記し、
「破りようがない」とは主張しない。

### 1-4. なぜ MCP サーバーではないのか(C1 構成の採用理由)

当初は MCP サーバー化を計画した。独立レビューでの反証を受けて撤回し、
**C1 構成(共有ライブラリ + 決定的 CLI + deny hook + 注入 hook。常駐プロセスなし)** を採る。
撤回の根拠は 4 点である。

1. **読み経路がすべて MCP を迂回する。** SessionStart 注入はファイル直読、Codiel の hooks も
   ファイル直読、セッション中の参照は Read ツールで足りる。読みで MCP を通る経路が
   ひとつも無く、MCP の存在理由が「低頻度の書き込み検証」だけに縮退する。
   常駐プロセスを 1 つ増やす対価としては釣り合わない。
2. **MCP ツールでも強制にはならない。** §1-3 のとおり、呼び出しが任意である点で CLI と同じ。
   「MCP にすれば守られる」というのは誤りで、守らせるのは deny hook である。
   同じ強制力なら、常駐プロセスを持たない CLI のほうが軽い。
3. **検証ロジックが二重実装になる。** deny hook は MCP を呼べない実行文脈で動く
   (hook は独立プロセスであり、MCP クライアントを持たない)。検証をサーバー内に閉じると、
   hook 側にも同等の判定を書くことになり、**同じ規則の実装が 2 つ**できる。
   共有 TypeScript ライブラリに 1 本化し、CLI と hook の両方がそれを取り込む構成なら、
   規則の実装は 1 つで済む。
4. **raguel-mcp は前例にならない。** raguel-mcp は run の各フェーズで必ず通る高頻度ゲートであり、
   常駐のコストが呼び出し回数で償却される。metatron の書き込みは初回生成と時々の更新・記録だけで、
   **頻度プロファイルがまったく異なる**。同じリポジトリに MCP サーバーがある事実は、
   metatron を MCP にする根拠にはならない。

C1 構成で、当初 MCP に期待していた保証はすべて維持される。

| 保証したいこと | C1 での実現手段 |
| --- | --- |
| 壊れた `metatron:domains` を書けない | 共有ライブラリの検証を CLI の書き込みパスに置く |
| 対象セクション以外を壊さない | 共有ライブラリのセクション分解・再結合 |
| GOTCHAS を改変できない | CLI に追記系サブコマンドしか用意しない |
| 連番の採番ミスが起きない | 共有ライブラリが既存最大値 + 1 で採番 |
| diff を見せずに書けない | `stage-architecture` → `commit-architecture` の 2 段階(§7-3) |
| **正本を直接編集させない**(Edit / Write / NotebookEdit 経由に限る) | **PreToolUse deny hook**(§7-5)← C1 で新たに加わった、唯一の真の強制点 |

### 1-5. なぜ SessionStart 注入なのか

現行、ARCHITECTURE / GOTCHAS は「サブエージェントが作業前に必ず読む」という**指示**で運用されている
(`orchestrating-runs` のディスパッチプロンプトが毎回「作業前に必ず読んでください」と書く)。
これには 2 つの弱点がある。

1. **Codiel の run の中でしか効かない。** 通常のセッションで人間が「このバグ直して」と頼んだとき、
   AI は GOTCHAS を読まない。過去に記録した罠を、記録した本人(のプラグイン)以外は踏み続ける。
2. **読むかどうかが AI の判断に委ねられる。** 「今回は関係なさそう」と判断されれば読まれない。

SessionStart Hook で**決定的に注入する**ことでこの両方が解決する。注入はファイルを直読する
決定的スクリプトであり、外部プロセスにも `node_modules` にも依存しない。

さらに C1 構成では、注入がもう 1 つの役割を持つ。**CLI の存在と絶対パスを毎セッション広告する**
役割である(§8-1)。CLI は「知らなければ呼ばれない」ため、発見性の担保が要る。
注入文の**先頭**と deny hook の拒否メッセージの 2 経路で広告することで、これを解決する。

## 2. スコープ / 非スコープ

### 2-1. スコープ

- ARCHITECTURE / GOTCHAS のパース・検証・採番・追記制約・パス解決を担う**共有 TypeScript ライブラリ**。
- AI の書き込み窓口となる**決定的 CLI**(バンドル済み `.mjs`、Bash から実行)。
- 正本ファイルへの直接 Edit / Write を拒否する **PreToolUse deny hook**。
- **SessionStart Hook** による毎セッション注入(ARCHITECTURE 全文 + GOTCHAS 要約 + CLI の案内)。
- 共有設定ファイル(パス変更)の仕様定義。
- ドメインマップの汎用資産化と中立マーカーへの改称。
- `/metatron:init`(コードベース解析ドラフト + 対話ウォークスルー)と `/metatron:update`(乖離検出)。
- GOTCHAS の記録規律(追記のみ・タグ付与・記録判断フロー)の汎用化と継承。
- ARCHITECTURE への 3 節追加(システム概要 / レイヤー構造 / ADR 一覧)と ADR の採番。
- 2 文書の **AI 向け執筆規律**(`references/writing-discipline.md`)の策定(§6-5)。
- Codiel 側の改修(初期化スキルの縮小と単体動作フォールバック、`readDomains` 書き換え、
  パス参照の統一、domains の機械読主体の宣言訂正)。

### 2-2. 非スコープ

| 非スコープ | 理由 |
| --- | --- |
| **MCP サーバー** | §1-4 のとおり撤回。将来の昇格余地は §16-6 に残す |
| **常駐プロセス全般** | C1 構成に常駐要素は無い。`plugins/metatron/dist/` は作らない |
| **保護パスの汎用化** | 今回は現状維持とする。ARCHITECTURE の散文と `raguel.config.yaml` の `globs` の二重管理は残る。完全な単一情報源化は、保護パスの意味論(「触るな」か「慎重に」か)を機械可読に定義する別作業になる |
| **Codiel の enforcement 変更** | 「domains が読めなければ run を止める」という解釈は Codiel 側にそのまま残す。metatron はデータの意味を「ドメイン→パス写像」までしか定義せず、強制力を与えるのは利用側の責務(§6-2)。**guard-write への domains 配線もこのスコープ外**(§10-5、§16-5) |
| **既存生成物の移行措置** | Codiel は開発中ステータスで利用者ゼロと仮定する。旧 `codiel:domains` マーカーの互換読み、移行スクリプト、二重マーカー対応は**一切設けない** |
| **ARCHITECTURE の分割・多ファイル化** | 大規模プロジェクトで 1 ファイルが肥大する問題は認識するが、v1 は単一ファイルに固定する(§16-4) |
| **GOTCHAS の自動失効・要約圧縮** | エントリが数百件に達したときの圧縮戦略は運用データが無い状態では決められない。注入側のサイズ上限(§8-3)で当面しのぐ |
| **Raphael の抗体機構との統合** | 対象が異なる(§6-4)。相互参照もしない |
| **人間向けの閲覧 UI** | ファイルは Markdown であり、GitHub とエディタで読める |

### 2-3. 前提とする制約(プラットフォーム由来)

設計で回避せず、前提として受け入れる制約。

| 制約 | 内容 | 設計上の扱い |
| --- | --- | --- |
| **hook 出力の 10,000 文字キャップ** | SessionStart の `additionalContext` を含む hook 出力は 10,000 文字で頭打ちになる。超過分はファイルへ退避され、モデルにはプレビューと退避先パスが渡る | 予算を 10,000 文字基準に置き、既定 `maxChars = 9000` で自前に収める。CLI 案内を**先頭**に置き、退避に倒れてもプレビュー内に残す(§8-2、§8-3) |
| **注入枠は他プラグインと共有** | revelation 等も SessionStart で注入する。metatron が枠を独占できない | 既定値に余裕を持たせ、利用者が `maxChars` で下げられるようにする |
| **サブエージェントへの継承が保証されない** | `additionalContext` がサブエージェントに渡る保証は公式に無い | 効果範囲をメインセッションに限定して設計する。サブエージェントには従来どおりファイルを必読させる(§8-1、§10-4) |
| **hook は AI のツール呼び出しにのみ介在する** | Bash リダイレクト・人間のエディタ編集は捕捉できない | 「回避を止める設計」ではなく「知らずの直接編集を導く設計」と位置づける(§7-5、§16-7) |

### 3-1. 構成要素と役割分担

```

依存の向きに注意する。**deny hook は CLI を呼び出さない。** hook が行うのは、
自分自身の位置(`import.meta.url`)から同じプラグインルート配下の CLI の絶対パスを
**文字列として組み立て、拒否メッセージに載せる**ことだけである。
実際に CLI を実行するのはモデル(Bash ツール経由)であり、hook と CLI の間に
実行時の依存関係は無い。両者が共有するのは `src/lib/` のソースだけである。

### 3-2. 3 つの経路の独立性

| 経路 | 依存するもの | 壊れたときの影響 |
| --- | --- | --- |
| **注入**(SessionStart hook) | ファイルの存在のみ | 注入されないだけ。セッションは通常どおり動く(フェイルオープン) |
| **書き込み**(CLI + deny hook) | Node と バンドル済み `.mjs` のみ | CLI が失敗すれば書けない(フェイルクローズド)。deny hook が失敗した場合は §7-5 |
| **利用**(Codiel / sandalphon) | ファイルの**形式**のみ | metatron プラグインが無くても、形式さえ守られていれば動く |

常駐プロセスが無いため、「サーバーが起動していない」という故障モードが存在しない。
これは C1 構成の副次的だが実質的な利点である。

### 3-3. プラグイン間連携の手段は 2 つだけ

プラグインのインストールパス(`CLAUDE_PLUGIN_ROOT`)は**互いに不定**である。
Codiel から metatron の CLI やライブラリのパスを解決する手段は無く、
ソースレベルの共有も行わない(コピーによる二重管理を避けるため)。
したがって連携手段を次の 2 つに限定し、それ以外を設計に持ち込まない。

| # | 手段 | 内容 | 正本 |
| --- | --- | --- | --- |
| **(a)** | **ファイル契約** | `metatron.config.json` のスキーマとパス解決規則、中立マーカー `metatron:domains`、ARCHITECTURE / GOTCHAS の書式、文書パスの既定値 | metatron の `references/` |
| **(b)** | **モデルコンテキスト経由** | SessionStart 注入文と deny hook の拒否メッセージが **CLI の絶対パス**を広告する。Codiel を含む任意のスキル・エージェントは、コンテキストにその案内があればそれを使う | 注入文・拒否メッセージの文面(metatron 側で生成) |

(a) は静的な取り決めであり、両者が独立に実装する。(b) は動的で、
**metatron が導入されているときにだけコンテキストに現れる**。この性質が重要で、
Codiel は「案内があれば CLI を使い、無ければ自前で処理する」と書くだけで、
metatron のインストール検出を一切行わずに両環境へ対応できる(§10-1、§10-4)。

**`dist/` は作らない。** 常駐プロセスが無いため、リポジトリ規約の「server 起動など常駐プロセスを
伴うものは `plugins/*/dist/`」に該当しない。CLI と hook はいずれも短命プロセスであり、
「バンドル出力は `plugins/*/scripts/`」の規約に従う。

`src/lib/` は **CLI と 2 つの hook の 3 成果物すべてから使う**。esbuild が各エントリに
必要な分だけを取り込むため、共有ロジックの実装は 1 つに保たれる(§1-4 の理由 3)。

`hooks/hooks.json`:

```json
{
  "description": "metatron: SessionStart で ARCHITECTURE/GOTCHAS を注入し、PreToolUse で正本への直接編集を拒否する",
  "hooks": {

        "matcher": "Edit|Write|NotebookEdit",
        "hooks": [

        ]
      }
    ]
  }
}
```

## 5. 保存仕様と共有設定ファイル

### 5-1. 保存の原則

- **プロジェクト内のファイルに保存する。** git でコミットでき、レビューでき、GitHub 上で読める
  チーム資産であることが要件(§15-4)。
- 既定パスは現行 Codiel と同一の `docs/ARCHITECTURE.md` / `docs/GOTCHAS.md`。
- パスの変更は**リポジトリにコミットする共有設定ファイル**で行う。環境変数は採用しない(§15-5)。

### 5-2. 共有設定ファイル

| 項目 | 決定 |
| --- | --- |
| ファイル名 | `metatron.config.json` |
| 置き場 | プロジェクトルート直下 |
| 形式 | JSON |
| 存在の要否 | **任意**。無い場合は全項目が既定値。「設定ファイルが無い」はエラーではない |

**JSON を選ぶ理由**: この設定は metatron の CLI・2 つの hook に加え、
**Codiel と sandalphon がそれぞれ独立に実装するパス解決**からも読まれる(§3-3 (a))。
読み手が複数プラグインに分散し、しかもソースを共有しない以上、
**解釈の一致が言語仕様で保証される形式**でなければならない。JSON なら全員が `JSON.parse` で読む。
YAML にすると各プラグインがパーサを選ぶことになり、フロースタイルやアンカーの扱いで
静かに解釈が割れる余地が生まれる。

`raguel.config.yaml` が YAML なのは、読み手が Raguel の実装 1 つだけで、
そこに既に `yaml` 依存があるためである。読み手の構成が違うので、形式を揃える必要はない。

### 5-3. スキーマ

```json
{
  "version": 1,
  "paths": {
    "architecture": "docs/ARCHITECTURE.md",
    "gotchas": "docs/GOTCHAS.md"
  },
  "injection": {
    "enabled": true,
    "gotchasRecentCount": 5,
    "maxChars": 9000
  }
}
```

| キー | 型 | 既定値 | 意味 |
| --- | --- | --- | --- |
| `version` | number | `1` | スキーマバージョン。未知の値なら**全項目を既定値として扱い**、警告を 1 行添える(読み手を止めない) |
| `paths.architecture` | string | `docs/ARCHITECTURE.md` | ARCHITECTURE のパス |
| `paths.gotchas` | string | `docs/GOTCHAS.md` | GOTCHAS のパス |
| `injection.enabled` | boolean | `true` | SessionStart 注入の有効/無効 |
| `injection.gotchasRecentCount` | number | `5` | 全文で注入する直近エントリ数(§8-2) |
| `injection.maxChars` | number | `9000` | 注入全体の文字数上限(§8-3) |

**`$schema` キーは定義しない。** JSON Schema をエディタ補完のために参照させる案は採らない。
`./node_modules/metatron/config-schema.json` のような相対参照は、metatron が
npm パッケージとして配布されない(Claude Code プラグインである)ため**存在しないファイルを指す**。
公開 URL を置く案も、リポジトリの可搬性のためだけにネットワーク参照を持ち込むことになる。
キーが 6 個の平坦な構造であり、`references/config-schema.md` に正本があれば補完は不要と判断する。
利用者が独自に `$schema` を書いた場合は、**未知キーとして無視する**(エラーにしない)。

### 5-4. パス解決の規則(ファイル契約の中核)

全実装が**同一の規則**で解決する。規則の正本は `references/config-schema.md`。

**重要: ルート(基準ディレクトリ)の決定規則そのものがファイル契約の一部である。**
パスの相対解決だけを揃えても、基準が実装ごとに違えば同じ cwd から違うファイルに辿り着く。
したがって次の規則 1 を含めて契約とし、各実装はこれを再現する。

1. **ルート解決**。カレントディレクトリから上方向に探索し、最初に見つかったものを採る。
   1. `metatron.config.json` を持つ最も近い祖先ディレクトリ
   2. 無ければ `git rev-parse --show-toplevel`(リポジトリルート)
   3. それも無ければカレントディレクトリ
2. `paths.*` はルートからの**相対パス**として解決する。
3. **絶対パスと、ルートの外へ出るパス(`..` による脱出)は拒否する。**
   拒否した場合はその項目だけ既定値に落とし、理由を呼び出し元へ返す。
   チーム資産のパスがマシン固有の絶対パスになるとリポジトリの可搬性が失われ、
   ルート外への書き込みは CLI / hook の権限で任意の場所を書き換える経路になるため。
4. 解決結果はキャッシュしない(セッション中に設定が変わりうる。読み込みコストは無視できる)。

#### Codiel の既存ルート解決との相違(改修が必要)

Codiel の `findProjectRoot` は **`.codiel` ディレクトリを持つ祖先**を探す実装であり、
上の規則 1 とは異なる基準を使っている。同じ cwd から出発しても、
両者が異なるディレクトリをルートと判定しうる。

具体的に食い違うのは次のような構成である。

| 構成 | metatron の規則 | Codiel の `findProjectRoot` |
| --- | --- | --- |
| `repo/.codiel/` があり `repo/metatron.config.json` は無い | `repo`(git ルート) | `repo` — 一致 |
| `repo/sub/.codiel/` があり `repo/metatron.config.json` がある | `repo`(config 祖先) | `repo/sub` — **不一致** |
| `.codiel` が無く git 管理下 | `repo`(git ルート) | cwd をそのまま返す — **不一致** |

`readDomains` はルートを引数に取るため、**ルートがずれれば入力ファイルごと変わる**。
パス文字列だけを揃えても意味がない。したがって §10-3 の Codiel 改修に
**ルート解決の差し替え**を含め、文書パスの解決には規則 1 を使う。

ただし `.codiel/runs` の探索など **Codiel 固有資産の位置決め**には
既存の `findProjectRoot` をそのまま残す。用途が違うためである
(文書 = ファイル契約のルート、Codiel の run 状態 = `.codiel` のルート)。
2 つのルート概念を明示的に分け、関数名でも区別する(§10-3)。

### 5-5. 各実装の読み方

| 読み手 | 実装 | 備考 |
| --- | --- | --- |
| metatron CLI / 2 hook | `src/lib/config.ts` を各成果物にバンドル | **正本の実装** |
| Codiel | `src/hooks/lib.ts` に `resolveDocPaths(root)` を独立実装(§10-3) | 規則の写し。ソース共有はしない(§3-3) |
| sandalphon | `check-intent-env.ts` に独立実装 | 同上 |

規則を 3 実装が持つため、`references/config-schema.md` の冒頭に
「この規則を変更したら Codiel の `lib.ts` と sandalphon の `check-intent-env.ts` も更新する」
というチェックリストを置く。加えて、実装の一致は**テスト R4 と sandalphon のケース 16f**
(§13-2)で機械的に検証する。写しを持つ設計における唯一の機械的担保がこの 2 本であり、
3 者すべてを突き合わせているのはケース 16f である。

## 6. 記録フォーマット仕様

### 6-1. ARCHITECTURE のセクション構成

現行 `ARCHITECTURE.example.md` の 8 セクションを基礎に、**3 節を追加した 10 セクション構成**とする。
Codiel 由来の記述(「Codiel の各サブエージェントが読む」等)は中立な表現に書き換える。

| # | 見出し | CLI の `heading` キー | 内容 | 機械可読 |
| --- | --- | --- | --- | --- |
| 1 | **`## システム概要`** | `システム概要` | プロジェクト概要の散文 + **全体アーキテクチャ図(Mermaid)** | — |
| 2 | `## 技術スタック` | `技術スタック` | 言語 / FW / 主要ライブラリ / バージョン方針の表 | — |
| 3 | **`## レイヤー構造`** | `レイヤー構造` | レイヤーと依存方向、**禁止される依存方向** | — |
| 4 | `## ディレクトリ構成と責務` | `ディレクトリ構成と責務` | 主要ディレクトリのツリーと責務 | — |
| 5 | `## ドメインマップ` | `ドメインマップ` | ドメイン→パス写像 | **○**(§6-2) |
| 6 | `## コマンド定義` | `コマンド定義` | test / lint / typecheck / build / e2e の表 | △ |
| 7 | `## テスト方針` | `テスト方針` | E2E・ユニットの方針と配置規約 | — |
| 8 | `## 保護パス` | `保護パス` | 触ってはいけない / 慎重を要するパス | △ |
| 9 | `## 規約` | `規約` | コーディング規約 / ブランチ / DoD | — |
| 10 | **`## ADR 一覧`** | `ADR 一覧` | アーキテクチャ上の重要な設計判断の記録(§6-6) | △(採番) |

#### 見出しなし概要は「システム概要」に統合する(`overview` 疑似キーは廃止)

旧構成は冒頭に見出しを持たない概要段落を置いており、CLI から指定するために
疑似キー `overview` を定義していた。**新設する `## システム概要` にこれを統合し、疑似キーを廃止する。**

- 統合を選ぶ理由: 疑似キーは「見出しが無い区画をどう指すか」という**書式の歪みへの対処**であり、
  歪み自体を無くせるならそのほうが単純である。全セクションが `##` 見出しを持てば、
  `heading` キーは見出し名と 1 対 1 になり、例外が消える。
- 併せて Mermaid 図の置き場が要る。概要の散文と全体図は「このシステムは何で、どう組まれているか」
  という同じ問いに答えるものであり、別々の節に離すと読み手が 2 箇所を往復する。同じ節に置く。
- `# ARCHITECTURE` と最初の `##` の間に本文を置かない。既存ファイルにそこへ本文がある場合、
  `stage-architecture` は警告を返す(拒否はしない。読み取りは従来どおり成立するため)。

見出し名と順序を固定するのは、**セクション単位の更新(§7-4)を機械的に行うため**である。
ライブラリは見出し行でファイルを分割し、指定セクションだけを差し替える。
見出しが揺れると分割に失敗するため、`stage-architecture` は未知の見出しを受け付けない。

#### セクション分割の規範アルゴリズム

`## システム概要` が Mermaid 図を含むようになったため、**コードフェンス内の行を見出しと
誤認しない**ことが必須になった。Mermaid の本文には `%%` のコメントや、
説明ノードとして `##` で始まる文字列が現れうる。分割規則を規範として定める。

行を先頭から 1 行ずつ走査し、**フェンス状態を持つ状態機械**として処理する。

1. **フェンスの開始**: フェンス外で、行頭が `` ``` `` または `~~~` を **3 個以上連続**した
   同一文字で始まる行。その文字と個数を記憶する(CommonMark に準拠)。
2. **フェンスの終了**: フェンス内で、行頭が**開始と同じ文字**を**開始と同数以上**連続させ、
   かつ**その後に info string を持たない**行。
3. **フェンス内の行は本文として扱う。** 行頭が `## ` でもセクション見出しにしない。
4. **見出しの判定**: フェンス外で、行頭が `## `(`#` 2 個の直後に半角スペース)で始まる行。
   `#` 1 個(ファイルタイトル)と `###` 以下(節内の小見出し)は見出しにしない。
5. **未閉フェンス**: ファイル終端に達してもフェンスが閉じていない場合、
   パーサは `unclosed_fence` エラーを返す。

`unclosed_fence` の扱いは §12-1 の 2 層方針に従って分かれる。

- **書き込み経路(第 1 層・フェイルクローズド)**: `stage-architecture` / `stage-adr` は
  拒否し `stagingId` を発行しない。壊れた構造の上でセクションを差し替えると、
  対象外セクションを巻き込んで破壊しうる。
- **読み取り・注入経路(第 2 層・フェイルオープン)**: 処理を続け、未閉フェンス以降を
  1 セクション扱いにしたうえで、警告を 1 行添える。注入が丸ごと消えるほうが損害が大きい。

同名の見出しが複数あるときは**最初のものを採り**、`stage-architecture` は重複を警告する
(拒否はしない。読み取りは最初のセクションで一貫するため)。

**すべてのセクションは任意である。** 存在しないセクションがあってもエラーにしない。
これは Codiel 単体動作時に「`## ドメインマップ` だけを持つ最小ファイル」が生成されうるため
(§10-2)であり、metatron はそれを正当なファイルとして扱う。

**新設 3 節の位置の根拠**:

- `## システム概要` は冒頭。読み手が最初に必要とするのは全体像である。
- `## レイヤー構造` は `## 技術スタック` の直下。「何で作られているか」の次に
  「どう積まれているか」が来る並びであり、両者は合わせて読まれる。
- `## ADR 一覧` は末尾。追記され続けて伸びる節であり、途中に置くと
  後続セクションが読み手から遠ざかる。また注入では最初に縮退する対象でもある(§8-5)。

#### `## システム概要` の要件

- 散文はプロジェクトの目的・利用者・主要な技術的制約を 1 段落で書く。
- **全体アーキテクチャ図を Mermaid で置く。** 図は主要コンポーネントとその間のデータ・制御の流れを表す。
- Mermaid を選ぶのは、テキストのまま diff が取れ、GitHub でレンダリングされ、
  AI が読んで理解できるためである。画像ファイルは差分が読めず、注入にも載らない。
- 図の検証は行わない。**CLI は Mermaid の構文を解析しない**(§7-1 の責務分界)。
  壊れた図はレンダリングされないだけで、他セクションの機械処理に影響しない。

#### `## レイヤー構造` の要件

- レイヤーを上から下へ列挙し、各レイヤーの責務を 1 行で書く。
- **依存の許される方向を明記する。**
- **禁止される依存方向を明記する。** これがこの節を独立させる理由である。
  「許される方向」だけを書くと、書かれていない方向が「禁止」なのか「未定義」なのかが読み手に
  判別できない。禁止を明示すれば、実装エージェントもレビューアーも違反を指摘できる。
- 禁止は「〜しない」で終えず、**代わりに取る手段を併記する**(§6-5 の書き方の基準)。
  例:「ドメイン層は UI 層を参照しない。UI へ値を渡す必要があるときは、
  ドメイン層がインタフェースを定義し UI 側が実装する」

### 6-2. ドメインマップと中立マーカー

**マーカー名は `metatron:domains` とする。** 開始行は次の形に固定する。

````
```json metatron:domains
````

改称の理由は名前空間の中立化である。このデータは「Codiel が書き込み許可を判定するための表」
ではなく「**このプロジェクトでどのコードがどの関心事に属するかの写像**」であり、
複数の利用者がそれぞれの解釈を与える一級の汎用資産である。

| 利用者 | 与える解釈 |
| --- | --- |
| Codiel `orchestrating-runs` | 実装ステップの**ディスパッチ先の選択**(ドメインタグ→担当エージェント) |
| Codiel `initializing-harness` | run 開始の**前提条件**(読めなければ run を開始しない) |
| sandalphon `capturing-intent` | ASIS 探索の**スコープ決定** |
| 人間 | オンボーディング時の**コードベースの地図** |

**metatron はデータの意味を写像までしか定義せず、強制力を与えない。**
「読めなければ run を止める」というフェイルクローズドは Codiel 側の解釈として存続する。
metatron が enforcement を持つと、metatron を入れた全プロジェクトが
Codiel の厳格さを強制されることになる。

データ形式は現行と同一の `{ "<ドメイン名>": ["<glob>", ...] }` を維持する。

```json metatron:domains
{
  "frontend": ["src/app/**", "src/components/**"],
  "backend": ["src/server/**", "src/api/**"],
  "data": ["prisma/**", "db/**"]
}
```

- ドメイン名は任意の文字列。`frontend` / `backend` / `data` は例であって固定語彙ではない。
- 分割が馴染まないプロジェクトは `{ "generic": ["**"] }` に縮退させる(現行の縮退モードを継承)。
- 形式を変えないのは、Codiel の `readDomains` の変更を**マーカー名とパス解決だけ**に留め、
  値の構造に関する下流の前提(`Record<string, string[]>`)を壊さないためである。

**誰がこのブロックを機械的に読むか**(§10-5 で現行の宣言を訂正する):

| 読み手 | 現状 | 本設計後 |
| --- | --- | --- |
| Codiel `initializing-harness` の検証 | `node -e` で `readDomains` を呼ぶ | 継続(マーカー名のみ変更) |
| Codiel `orchestrating-runs` §0 の前提チェック | フェンスブロックの存在を確認 | 継続(マーカー名のみ変更) |
| Codiel `guard-write` hook | **読んでいない**(`readDomains` は未配線) | **今回も配線しない**(§10-5)。ドキュメントの宣言を実態に合わせて訂正する |
| sandalphon `check-intent-env` | — | 新規に読む(ファイル契約に基づく独立実装) |
| metatron CLI / hook | — | 共有ライブラリで読む |

CLI は書き込み時に次を検証し、いずれかに反する内容は**書き込まない**。

1. ブロック内が有効な JSON である。
2. トップレベルがオブジェクトで、配列でない。
3. 各値が 1 要素以上の文字列配列である。
4. キーが 1 個以上ある。

これは現行 `initializing-harness` の手順 5(検証)が `node -e` で行っていることと同じ内容だが、
実行を忘れられない位置(書き込みパス上)に移す。

### 6-3. GOTCHAS の書式(全面刷新)

**旧書式(発生フェーズ / 症状 / 根本原因 / 予防策 / 関連ファイル)は廃止し、新書式へ全面置換する。**
互換読みは設けない(既存生成物の移行措置は非スコープ。§2-2)。

#### ファイル構成

````markdown
# GOTCHAS

このプロジェクトで AI が実際にやってしまった失敗のパターンを蓄積する。
発見された失敗を、下記のフォーマットで追記していく。

## 運用ルール

- 新しいものを上に追加する。
- 同じパターンが 5 件以上蓄積されたら、スキルまたは Hook への昇格を検討する。
- 解決済みの項目は `[解決済み]` タグを付けて残す。削除しない。
- 陳腐化した項目は `[対象外]` タグを付けて残す。削除しない。

## 記入テンプレート

### [YYYY-MM-DD] GOTCHA-NNN: 失敗のタイトル

**タスク**: (何をしようとしていたか)
**失敗内容**: (具体的に何を間違えたか)
**原因 (推測)**: (なぜそうなったか)
**対策**: (今後 AI はどう振る舞うべきか)
**昇格候補**: Yes / No (スキルや Hook にするべきか)

## 失敗パターン一覧

### [2026-08-16] GOTCHA-002: 最新のエントリ

...

### [2026-08-10] GOTCHA-001: 古いエントリ

...
````

#### 解析の規約

- **エントリとして解析するのは `## 失敗パターン一覧` 配下の `###` ブロックだけ**とする。
  `## 記入テンプレート` 配下にも同じ形の見出しが存在するため、
  ファイル全体を走査すると雛形をエントリ 1 件として数えてしまう。節を限定することで防ぐ。
- エントリ見出しの形は `### [YYYY-MM-DD] GOTCHA-NNN: [タグ] タイトル`。タグは省略可。
- フィールドは `**名前**: 値` の 5 行。`タスク` / `失敗内容` / `原因 (推測)` / `対策` / `昇格候補`。
- `昇格候補` は `Yes` または `No` のみを受け付ける。

#### 新しいものを上に

**追記位置を「`## 失敗パターン一覧` の直下(先頭)」に変更する**(旧書式ではファイル末尾だった)。

- 読み手にとって新しい失敗ほど現在のコードベースに当てはまる確率が高く、
  先頭にあれば注入の縮退時にも残りやすい(§8-4)。
- **採番は全エントリを走査して最大値 + 1 とする。** 正常な並びでは先頭エントリが最大番号なので
  先頭だけ読めば足りるが、手編集で並びが崩れた場合にも番号衝突を起こさないよう全件走査する。
  走査コストは数百件規模でも無視できる。
- 原子性(ロック)の設計は §7-4 のまま適用する。挿入位置が先頭に変わっても、
  「最大値を読む → 書く」の窓を排他する必要は変わらない。

#### タグによる無効化(削除しない)

旧書式の「無効化追記」を **タグ付与**に置き換える。

| タグ | 意味 |
| --- | --- |
| `[解決済み]` | 原因が取り除かれ、この失敗はもう起きない |
| `[対象外]` | 設計変更等で前提が変わり、記述が現在のコードベースに当てはまらない |

付与の方法は次の 2 箇所への追記とする。**エントリ本文は書き換えない。**

1. 見出し行のタイトル直前にタグを挿入する
   (`### [2026-08-10] GOTCHA-001: [解決済み] 失敗のタイトル`)。
2. エントリ末尾に理由を 1 行追記する
   (`**[解決済み] (2026-08-20)**: <理由>`)。

見出しにタグを置くのは、**注入の一覧(§8-4)がタイトル行だけを読む**ためである。
末尾の理由だけでは一覧に状態が出ず、AI はタグ付きエントリを有効なものとして扱う。

#### タグの検出規則(規範)

タグを置ける位置を**1 箇所に固定する**。検出は次の規則だけで行い、他の位置は認識しない。

- 位置は **`GOTCHA-NNN:` の直後**、タイトル文字列の直前。区切りは半角スペース 1 個。
- 認識するのは **`[解決済み]` と `[対象外]` のリテラル 2 種のみ**。
- **タイトル内に現れる他の角括弧は無視する。** タイトルが
  `[Prisma] マイグレーションを二重適用した` のような角括弧を含んでも、
  それは `GOTCHA-NNN:` 直後の位置にある 2 種のリテラルではないため、タグとして扱わない。
- 先頭の `[YYYY-MM-DD]` は日付であり、タグの検出対象位置ではない。

正規化した見出しの形:

```
### [YYYY-MM-DD] GOTCHA-NNN: [解決済み] タイトル
```

位置を 1 箇所に固定するのは、複数位置を許すと「タイトルの一部なのかタグなのか」の判定が
文字列の意味に依存し、決定的でなくなるためである。`get gotchas --exclude-tagged` と
注入の一覧はこの規則だけで状態を判定する。

**既知の限界**: 人間が手編集でタグを別位置に書いたり、リテラルを変えたりした場合、
CLI と注入はそれをタグとして認識しない(タグ無しのエントリとして扱う)。
`tag-gotcha` を通せば必ず正しい位置に入るため、手編集の崩れは
「CLI を使わなかった場合の自己責任」として受け入れる。

### 6-3b. 記録の規律

`references/gotchas-format.md` を正本とする。

- **記録判断フローは 1 問。** 「**次にこのプロジェクトを触るエージェントがこれを知らないと
  同じ失敗をするか?**」が Yes のときだけ記録する。
- **`対策` に精神論を書かない。** 「気をつける」ではなく「〜する前に〜を Read して確認する」の形。
  次のエージェントがそのまま実行できる行動に落とす。
- **エントリの本文を書き換えない。削除しない。** 状態の変化はタグと理由の追記で表す。
- **`昇格候補: Yes` を付ける基準**: その対策が「このファイルを触るときだけ」ではなく
  「特定の操作をするとき常に」効くものであるとき。前者は GOTCHAS のまま、後者はスキルや Hook で
  機械的に効かせられる。
- **5 件ルール**: 同種のパターンが 5 件以上たまったら、スキルまたは Hook への昇格を検討する。
  検討の起点は人間であり、metatron が自動で昇格させることはしない
  (昇格先の設計はプロジェクトごとに異なるため)。
- **集計は機械化する。** `get gotchas --promotion-candidates` が `昇格候補: Yes` の
  エントリだけを返す(§7-2)。`[解決済み]` / `[対象外]` タグの付いたものは
  `--exclude-tagged` と併用して除ける。件数を数えるために台帳を通読しなくてよい。
  **判定(どれが「同種」か)は人間とモデルが行う。** CLI は候補を絞るところまでを担う。

### 6-4. Raphael との棲み分け

GOTCHAS と Raphael の抗体は、どちらも「失敗から学ぶ」機構だが**対象が直交する**。

| | metatron GOTCHAS | Raphael 抗体 |
| --- | --- | --- |
| 対象 | **このプロジェクト固有の技術的な罠** | **AI 一般の失敗パターン** |
| 例 | 「この ORM のこのバージョンに `softDelete()` は無い。`deletedAt` の update を使う」 | 「マルチラインシェルコマンドは改行がスペースに置換されるので `&&` で連結する」 |
| 有効範囲 | そのリポジトリの中だけ | どのプロジェクトでも成立する |
| 保存先 | プロジェクトの `docs/GOTCHAS.md` | `.raphael/antibodies/` |
| 注入 | SessionStart で常時(要約) | 発火条件に一致したときだけ |

判定に迷ったときの基準: **その知識を別のリポジトリに持っていっても成立するか。**
成立するなら Raphael、そのリポジトリでしか意味を持たないなら GOTCHAS。

#### 新書式の冒頭説明との両立

GOTCHAS の冒頭説明は「このプロジェクトで **AI が実際にやってしまった失敗**のパターンを蓄積する」
と書く。これは**記録の契機**(実際に起きたこと)を述べたものであって、
**対象範囲**(プロジェクト固有であること)を緩めるものではない。両者は次のように両立する。

- 記録するのは「実際に起きた」かつ「**このプロジェクトの文脈で再発しうる**」失敗である。
- 実際に起きても、プロジェクト固有性が無ければ GOTCHAS には書かない。Raphael が導入された
  環境ではそちらの領分であり、未導入なら記録しない(どのリポジトリでも起きる一般則を
  このリポジトリの台帳に溜めても、引く価値がないうえ注入の予算を食う)。
- 判定は 1 問で足りる: **「別のリポジトリでも同じ対策が要るか」。要るなら GOTCHAS ではない。**

境界例(一般的失敗とプロジェクト固有情報が混ざるケース)の扱いは従来どおりとする。
「型を確認せず存在しないメソッドを呼んだ」という失敗**そのもの**は一般的傾向なので記録せず、
「**このプロジェクトの ORM のこのバージョンには**そのメソッドが無い」という事実だけを
切り出して記録する。新書式では前者が `原因 (推測)` に、後者が `対策` に落ちる。

#### 5 件ルールの昇格先は Raphael ではない

運用ルールの「同じパターンが 5 件以上たまったら昇格を検討する」の昇格先は、
**そのプロジェクトのスキルまたは Hook** である。Raphael の抗体ではない。
GOTCHAS に溜まるのはプロジェクト固有の失敗であり、それをプロジェクト横断の抗体へ昇格させると
適用範囲が広がりすぎる。昇格は「同じプロジェクト内で、台帳を読ませる運用から
機械的に効かせる運用へ移す」変更である。

相互参照・自動連携は行わない(非スコープ)。

### 6-5. AI 向け執筆規律

ARCHITECTURE / GOTCHAS は**主に AI が読む文書**である。人間向けの読み物として書くと、
根拠や経緯で膨らみ、注入の予算(§8-2)を食い、肝心の指示が埋もれる。
そこで両文書に**執筆規律**を定め、`references/writing-discipline.md` を正本とする。

#### 正本を metatron 側に焼き込む

規律の内容は `prompt-smith` の「削る基準」「残す基準」「書き方の基準」を
**この 2 文書向けに特化・要約して書き写す**。prompt-smith を参照させない。
プラグイン間のファイル参照ができない(インストールパスが互いに不定。§3-3)以上、
参照は成立しないためである。`writing-discipline.md` は prompt-smith の写しではなく、
**2 文書に必要な範囲だけを抜き出した独立の規律**として書く
(評価の評点表・退避の手順など、指示書の監査に固有の内容は持ち込まない)。

#### 規律の骨子

**削る基準**

- 指示を正当化する根拠・理由は削り、指示だけを残す。根拠は設計文書に置く。
- 出典・引用・経緯は削る。
- 重複は削る。同じ内容の言い換え、要約と本文の重なりは一方だけを残す。
- 判断基準のない修飾(「適宜」「必要に応じて」「できるだけ」)は基準に置き換える。
  置き換えられないなら修飾ごと削る。
- 文書自身の構成や意図の説明は削る。
- 例は 1 つで伝わるなら 2 つ目以降を削る。

**残す基準**

- 読んだ後にエージェントの振る舞いが変わる文は残す。
- 誤読を防ぐ制約(順序・範囲・例外・優先順位)は残す。とくに `## レイヤー構造` の
  禁止される依存方向、`## 保護パス` は該当する。
- 判断基準そのものは残す。
- 削る基準と残す基準の両方に当たる文は、残す基準を優先する。

**書き方の基準**

- 望ましい動きの言い切り(「〜する」「〜しない」)で書く。命令形にしない。
- 1 文に 1 指示だけを書く。
- 禁止を書くときは、代わりに取る動きを併記する。「〜しない」だけで終えない。
- 本文は箇条書きで書く。構造体の補足・見出しの概要・1 文だけの指示は箇条書きにしない。

**図の基準**

- Mermaid 図は**全体の層と主要コンポーネントの関係が読めれば足りる**。
  ノード・エッジを網羅目的で増やさない。
- 図に載せるのは「これを知らないと全体像を誤解する」要素に限る。
  個々のクラス・関数・テーブルは載せない。それらは `## ディレクトリ構成と責務` と
  `## ドメインマップ` が担う。
- 図は常時注入される(§8-4)。ノードを 1 つ足すたびに毎セッションのコストが増える。
  網羅性が要るなら図ではなく表で書き、図は関係の把握に絞る。

#### 適用の強さをセクションで変える

| 区分 | 対象 | 適用 |
| --- | --- | --- |
| **削る基準を強く適用** | `## システム概要` / `## レイヤー構造` / `## 技術スタック` / `## ディレクトリ構成と責務` / `## コマンド定義` / `## テスト方針` / `## 保護パス` / `## 規約` | **常時注入される**節であり、1 文の冗長がそのまま毎セッションのコストになる(§8-2 の 10,000 文字予算に直結)。根拠・経緯・言い換えを残さない |
| **根拠系フィールドのみ例外** | `## ADR 一覧` の `理由` / `背景` / `検討した選択肢`、GOTCHAS の `原因 (推測)` | **削る基準のうち「根拠・理由を削る」だけを当てない。** 他の基準(重複・例・修飾・簡潔化)は全面適用する |

#### 例外の定義を取り違えない

例外とは「**根拠系フィールドを削らずに残すこと**」であって、
「**冗長に書いてよい**」ではない。ADR の `理由` と GOTCHAS の `原因 (推測)` は
prompt-smith の削る基準では「根拠」に当たるが、この 2 つは**根拠を引くために存在する**節であり、
根拠を削ると記録の目的そのものが消える。例外はそこに限られる。

例外の範囲に入っても、次はすべて適用する。

- **書き方の基準**(言い切り・1 文 1 指示・禁止に代替を併記・箇条書き)。
- **残す基準**。
- **削る基準のうち根拠以外**(重複・言い換え・例の 2 つ目以降・判断基準のない修飾)。

**GOTCHAS エントリは簡潔化を全面適用する。** 直近 N 件が**全文で注入される**(§8-4)ため、
1 エントリの冗長がそのまま毎セッションのコストになる。
「引くための記述だから通読させない」という理由は GOTCHAS には当てはまらない ——
実際に通読させているからである。各フィールドは 1〜3 文に収め、例示と重複を削る。

**ADR は相対的に自由度が高い。** 注入されるのはタイトルと状態だけで(§8-4)、
全文は `get adr` で引かれたときにしか読まれない。したがって注入予算を直撃しない。
ただし無制限ではなく、書き方の基準と「根拠以外の削る基準」は同じく当てる。

| | 注入のされ方 | 簡潔化の強さ |
| --- | --- | --- |
| GOTCHAS エントリ | **直近 N 件は全文** | **強い**(予算を直撃する) |
| ADR | タイトル + 状態のみ | 中(予算を直撃しない) |
| 常時注入の 8 節 | 全文 | **強い** |

#### 責務分界: 機械検証と文体規律

| 担当 | 範囲 |
| --- | --- |
| **CLI(共有ライブラリ)** | **構造・スキーマ・マーカーまで。** セクション見出しの妥当性、`metatron:domains` の JSON 検証、GOTCHAS のフィールド有無、ADR の採番と必須項目、`昇格候補` の値域。**文体は判定しない** |
| **生成・更新スキル** | **文体規律の適用。** `/metatron:init` のドラフト生成、`/metatron:update` の更新文面、`recording-gotchas` のエントリ本文が `writing-discipline.md` に従う |

CLI に文体判定を持ち込まない理由は 2 つある。
文体の良し悪しは決定的に判定できず、機械が却下すると正当な文章まで弾く。
そして CLI が「通した」ことを品質の保証と誤解させると、スキル側の推敲が形骸化する。
唯一の例外は `対策` / `予防` の精神論チェックで、これは警告に留め拒否しない(§7-4)。

### 6-6. ADR 一覧の書式

`## ADR 一覧` は、アーキテクチャ上の重要な設計判断を記録する。

#### エントリ書式

````markdown
### ADR-001: [判断のタイトル]

- 状態: 採用/提案/廃止
- 決定日: YYYY-MM-DD
- 決定者: [氏名またはチーム名]

#### 背景
#### 検討した選択肢
1. [選択肢A]: メリット/デメリット
#### 採用した結論
#### 理由
#### 影響範囲
````

- 見出しは `###`、内部の小見出しは `####` で固定する。
- `状態` は `採用` / `提案` / `廃止` のいずれか。CLI はこの値域を検証する。
- 採番 `ADR-NNN` は CLI が既存最大値 + 1 で行う(§7-4)。

#### 何を ADR にするか

**「本当に重要であるもののみ」を記録する。** 判断基準を次のとおり定め、
`writing-discipline.md` に置く。**3 つすべてを満たすものだけ**を ADR にする。

1. **覆すコストが大きい。** 後から変えると複数のコンポーネントに波及する、
   またはデータ移行を伴う。
2. **選択肢が実在した。** 比較した代替が具体的に挙げられる。
   「他に手が無かった」ものは判断ではなく制約であり、`## 技術スタック` や `## 規約` に書く。
3. **理由が自明でない。** コードや設定を読んだだけでは「なぜそうしたか」が分からない。

満たさない例: ライブラリのバージョン選定、命名規約、ディレクトリの分け方。
これらは他セクションに属する。ADR を「決めたこと全部の置き場」にすると、
一覧が伸びて注入が縮退し(§8-5)、本当に重要な判断が埋もれる。

#### 状態変更も承認を要する

ADR の追加と `状態` の変更は、いずれも `stage-adr` → `commit-architecture` を通す。
`状態` を `採用` から `廃止` に変えることは、過去の判断を覆す行為であり、
新しい判断を足すのと同じ重みを持つ。**エントリは削除しない**
(`廃止` の状態で残す。判断の履歴が消えると、同じ議論が再燃する)。

#### 状態変更の理由を永続化する

`状態` 行を書き換えるだけでは、**なぜ覆したのかが残らない**。
GOTCHAS のタグ付与(§6-3)が理由行を追記するのと対称に、
状態変更時は**エントリ末尾に 1 行を追記する**。

```
- 状態変更(YYYY-MM-DD): 採用 → 廃止。<理由>
```

- `stage-adr --input` の `reason` はこの行に書かれる。
- 変更のたびに追記し、**過去の行は消さない**。状態遷移の履歴が上から順に読める。
- `状態` 行そのものは最新の値に書き換える(一覧と `get adr --status` が最新状態で引けるため)。

理由を残さない状態変更は、後から見て「誰かが気分で廃止した」のと区別がつかない。
ADR は判断の記録であり、**覆した判断もまた記録すべき判断**である。

## 7. 書き込み経路の仕様(CLI + deny hook)

### 7-1. 設計方針

- **CLI は事実の提供と形式の保証を担い、文章の生成はしない。** 文章は常に会話の中でモデルが作り、
  ユーザーが承認したものを CLI が受け取る(sandalphon の `check-intent-env` が
  「判断を持たない」のと同じ思想)。
- **読み取りは自由、書き込みは 2 段階。**
- **CLI は行儀のよい窓口、deny hook が強制点。** 両者は役割が違い、どちらも欠かせない。
- **CLI の検証は構造・スキーマ・マーカーまで。文体規律は担わない**(§6-5 の責務分界)。
  見出しの妥当性・JSON の検証・フィールドの有無・値域・採番までが CLI で、
  文の書き方は生成・更新スキルが `writing-discipline.md` に従って担保する。

### 7-2. CLI のサブコマンド

```
node <metatron-plugin-root>/scripts/metatron.mjs <subcommand> [options]
```

| サブコマンド | 種別 | 概要 |
| --- | --- | --- |
| `get config` | 読 | 解決済みの絶対パス、既定値が適用された項目、拒否された設定値 |
| `get architecture [--section <見出し>]` | 読 | 全文またはセクション単位 |
| `get domains` | 読 | `metatron:domains` を構造化して返す。パースの成否と理由も返す |
| `get gotchas [--recent N \| --id <ID> \| --query <語>] [--exclude-tagged] [--promotion-candidates]` | 読 | 台帳の取得・検索。`--exclude-tagged` で `[解決済み]` `[対象外]` を除く。`--promotion-candidates` で `昇格候補: Yes` のみを抽出する(5 件ルールの集計。§6-3b) |
| `get adr [--id <ID> \| --status <状態>]` | 読 | ADR の取得・状態での絞り込み |
| `scan` | 読 | コードベース解析の**事実**を返す(§9-1)。書き込みなし |
| `diff-architecture` | 読 | `scan` の結果と現行 ARCHITECTURE を突き合わせ、乖離候補を返す(§9-3) |
| `stage-architecture --input <path>` | 段階 | セクション単位の更新案を受け取り、**書かずに** diff と `stagingId` を返す |
| `stage-adr --input <path>` | 段階 | ADR の追加、または既存 ADR の `状態` 変更を staged change にする。**採番は CLI**(§7-4) |
| `commit-architecture --staging-id <id>` | 書 | `stagingId` を消費して書き込む(`stage-architecture` / `stage-adr` の両方に使う) |
| `append-gotcha --input <path>` | 書 | エントリを**先頭に**挿入する。採番は CLI |
| `tag-gotcha --id <ID> --tag <解決済み\|対象外> --reason <理由>` | 書 | 既存エントリにタグを付与する(見出し + 末尾理由の追記。本文は不変) |

**入出力の規約**:

- 出力は**常に JSON を stdout へ**。人間向けの補足は stderr へ。
- 読み取り系は**常に exit 0**(「読めなかった」も事実として JSON で返す)。
- 書き込み系は成功で exit 0、拒否・失敗で**非 0**。理由は JSON の `error` に入れる。
- **長い入力は一時ファイルに書き、`--input <path>` で渡す。** これを正式な呼び出し規約とする。
  - 引数に直接埋めると、引数長の上限に当たるうえ、本文に含まれる引用符・バッククォート・
    `$`・改行がシェルで解釈されて壊れる。
  - stdin のヒアドキュメント(`<<'EOF'`)も、実運用では終端トークンが本文に現れたときや
    インデントの扱いで事故を起こす。AI が組み立てる長い Markdown を渡す経路としては脆い。
  - 一時ファイル経由なら、**ファイルの書き込みは Write ツールが担い、シェルを一切通らない**。
    CLI に渡るのはパス 1 個だけになり、引用の問題が構造的に消える
    (gh-utility が Issue 本文を `--body-file` で渡すのと同じ判断)。
  - stdin も補助として受け付けてよいが、**スキル・拒否メッセージ・注入の案内はすべて
    `--input <path>` 形式で書く**。示す形を 1 つに統一しないと、AI は示された方を真似るため
    経路が分岐する。
  - 一時ファイルの置き場は OS の一時ディレクトリとし、CLI は読み取り後に削除しない
    (失敗時に内容を確認できるようにするため)。

### 7-3. stage → commit の 2 段階と機械保証

承認は**対話**で行うため、CLI は「ユーザーが承認したか」を知りえない。
`--approved` のようなフラグをモデルに立てさせる設計は自己申告に過ぎず、ゲートにならない。
そこで**機械的に保証できる性質だけを担保する**。

```
stage-architecture --input <path> ──→ { stagingId, diff, warnings, valid }
                                                │
                                  [スキルが diff を全文提示し承認を得る]
                                                │
commit-architecture --staging-id <id> ──→ 書き込み実行
```

保証されるのは次の 3 点である。

1. **diff を計算せずに書き込むことはできない。** `commit-architecture` は `stagingId` 無しでは
   失敗する。「差分を見せずにいきなり書く」経路がコマンド体系上存在しない。
2. **staging は単回使用かつ有効期限つき**(既定 30 分)。使い回し・古い案の遅延適用ができない。
3. **stage 後に対象ファイルが変化していたら commit は失敗する。** stage 時のファイル内容の
   ハッシュを保持し、commit 時に照合する。ユーザーが承認した diff と実際に適用される diff の
   一致を保証する。

**staging の保存先**: OS の一時ディレクトリ配下(`<tmpdir>/metatron-staging/<プロジェクトパスのハッシュ>/<id>.json`)。
CLI はサブコマンドごとに別プロセスとして起動するため、staging はプロセス外に置く必要がある。
プロジェクト内(`.metatron/staging/`)に置かない理由は、staging が**セッション限りの一時状態**で
あってプロジェクト資産ではないためである。リポジトリ内に置くと、全利用プロジェクトで
`.gitignore` の追加が必要になり、書きかけのドラフトを誤ってコミットする事故も起こりうる。

保証**されない**のは「人間が実際に diff を見て承認したか」だけであり、そこは
スキル側の HARD-GATE(承認なしに `commit-architecture` を実行しない)が担う。
この責務分界を `references/cli-usage.md` に明記し、
「コマンドが通ったから承認済み」と誤解させない。

### 7-4. 主要サブコマンドの入出力

**`stage-architecture --input <path>`**(`<path>` は JSON ファイル)

- 入力: `{ sections: [{ heading, body }], reason? }`
  - `heading` は §6-1 の**キー列のいずれか**(`システム概要` / `技術スタック` / `レイヤー構造` /
    … / `規約` / `ADR 一覧`)。未知の見出しは**エラー**にする(新セクションの発明を防ぐ)。
  - `overview` 疑似キーは**廃止**した。冒頭概要は `システム概要` で指定する(§6-1)。
  - **`ADR 一覧` を `heading` に指定した場合はエラーにする。** `stage-adr` を使うよう
    エラーメッセージで誘導する。ADR 一覧の変更経路を `stage-adr` に**一本化**するためである。
    丸ごと差し替えを許すと、採番の一貫性・`状態` の値域・状態変更履歴の追記(§6-6)を
    すべて迂回でき、過去の ADR を無言で消す経路にもなる。
    節が肥大するほど差し替え時の取りこぼしも起きやすい。
  - `body` は当該セクションの新しい本文(見出し行を含まない)。
- 出力: `{ stagingId, diff, warnings, valid }`
  - `## ドメインマップ` を含む場合、§6-2 の 4 検証を実行する。失敗なら `valid: false` と
    具体的な理由を返し、`stagingId` を**発行しない**(壊れたブロックは stage すらできない)。
  - `warnings` の例: 「`## コマンド定義` が表形式でない」「保護パスの glob が
    `raguel.config.yaml` と不一致」。警告は stage を止めない(判断はユーザー)。
- 対象ファイルが存在しない場合は新規作成の diff(全文追加)を返す。

**`commit-architecture`**

- 出力: `{ written: true, path, bytesWritten }`、または非 0 終了で
  `{ error: "expired" | "already_used" | "file_changed" | "unknown_id" }`。
- **指定セクション以外は 1 バイトも変更しない。** 元ファイルをセクション分割して保持し、
  対象セクションだけを差し替えて再結合する。

**`stage-adr --input <path>`**(`<path>` は JSON ファイル)

- 入力(追加): `{ mode: "add", title, decidedOn?, decidedBy, background, options[], conclusion, rationale, impact }`
- 入力(状態変更): `{ mode: "status", id: "ADR-003", status: "廃止", reason }`
  - `reason` は必須。`状態` 行を最新値に書き換えたうえで、エントリ末尾へ
    `- 状態変更(YYYY-MM-DD): 旧 → 新。<reason>` を**追記**する(§6-6)。
    過去の状態変更行は消さない。
- 出力: `{ stagingId, diff, assignedId }`(追加時)
- **採番は CLI が行う。** `## ADR 一覧` 配下の `### ADR-NNN:` を全件走査し、最大値 + 1 を割り当てる。
- `status` の値域(`採用` / `提案` / `廃止`)と必須項目の有無を検証する。欠落は stage を拒否する。
- ADR は `## ADR 一覧` 節の**末尾に追加**する(GOTCHAS と逆向き)。ADR は番号順に読まれる記録であり、
  昇順に並べたほうが「この判断の後に何が決まったか」を追える。
- **書き込みは行わない。** `commit-architecture --staging-id <id>` で確定する。
  ADR の追加と状態変更が承認を要するのは、いずれも設計判断の宣言だからである(§6-6)。

**`append-gotcha --input <path>`**(`<path>` は JSON ファイル)

- 入力: `{ title, date?, task, mistake, cause, countermeasure, promotionCandidate }`
  - 新書式(§6-3)の 5 フィールドに対応する。
    `task` = **タスク**、`mistake` = **失敗内容**、`cause` = **原因 (推測)**、
    `countermeasure` = **対策**、`promotionCandidate` = **昇格候補**。
- 出力: `{ id: "GOTCHA-007", path }`
- `date` 省略時は当日日付。
- `promotionCandidate` は `Yes` / `No` のみを受け付ける。他の値は拒否する
  (値域が 2 つしかなく、揺れると 5 件ルールの集計ができなくなる)。
- **`countermeasure` が空、または「気をつける」「注意する」のみで構成される場合は警告を返す**
  (拒否はしない。判定を厳密にすると正当な対策まで弾くため)。
- 採番は `## 失敗パターン一覧` 配下の全エントリを走査して最大値 + 1。
- 書き込みは **`## 失敗パターン一覧` の直下(先頭)への挿入**。台帳が無ければ雛形ごと新規作成する
  (冒頭説明・運用ルール・記入テンプレート・空の一覧節を含む。§6-3)。

**採番と挿入の原子性**: 「既存最大値を読む」と「書く」の間に別プロセスが割り込むと、
同じ番号が 2 つ採番される。CLI はサブコマンドごとに独立プロセスとして起動するため、
プロセス内のロックでは防げない。次の方式を採る。

1. `<gotchas パス>.lock` を **`fs.open` の `wx` フラグ**(既存なら失敗)で作成してロックを取る。
   排他作成はファイルシステムのアトミックな操作であり、追加依存なしに相互排除が成立する。
2. 取得できたら「最大値の読み取り → 挿入 → ロック削除」を行う。
3. 取得できなければ **50ms 間隔で最大 20 回リトライ**(合計約 1 秒)。
   それでも取れなければ非 0 終了し、`{ error: "lock_timeout" }` を返す。
4. ロックファイルの**更新時刻が 60 秒より古ければ死んだロックとみなして奪う**
   (プロセスが異常終了してロックが残った場合の回復)。

先頭挿入は末尾追記と違い O_APPEND では実現できず、**必ず読み書き全体の排他が要る**。
挿入位置の変更(§6-3)によってロックの必要性はむしろ強まった。
**ロックは文書ファイル単位で取る。** ロックファイルは対象文書のパスに `.lock` を付けたものとし、
2 文書で別々になる。

| ロック | 取得するサブコマンド |
| --- | --- |
| `<gotchas パス>.lock` | `append-gotcha` / `tag-gotcha` |
| `<architecture パス>.lock` | `stage-adr`(採番の読み取り) / `commit-architecture`(書き込み) |

GOTCHAS への追記と ARCHITECTURE の更新は**互いをブロックしない**。別ファイルであり、
競合が起こりえないためである。

**`stage-adr` と `stage-architecture` は同一の ARCHITECTURE ファイルを対象とするため、
同一ロックと `commit` 時のハッシュ照合の 2 段で直列化される。**
`stage-adr` は採番のために現ファイルを読む必要があり、その読み取りはロック下で行う。
実際の書き込みは `commit-architecture` が行い、そこで stage 時のハッシュと照合する(§7-3)。
2 つの stage が並行しても、後から commit する側が `file_changed` で弾かれるため、
片方の変更が無言で消えることはない。

**`tag-gotcha --id <ID> --tag <解決済み|対象外> --reason <理由>`**

- 対象エントリに次の 2 箇所を追記する。**エントリ本文は書き換えない。**
  1. 見出し行のタイトル直前へタグを挿入する
     (`### [2026-08-10] GOTCHA-001: [解決済み] 失敗のタイトル`)。
  2. エントリ末尾へ `**[解決済み] (YYYY-MM-DD)**: <理由>` を 1 行追記する。
- 既にタグが付いているエントリへの再付与は、見出しのタグを差し替え、理由行を**追記**する
  (前の理由行も残す。状態遷移の履歴が読めるようにするため)。
- `--tag` の値域は `解決済み` / `対象外` の 2 つ。他は拒否する。
- **これ以外の変更を行う経路を持たない**ため、「削除・改変禁止」が指示ではなく構造として成立する。

**旧 `invalidate-gotcha` からの改名**: 新書式では状態が「無効化」の 1 種類ではなく
`[解決済み]` と `[対象外]` の 2 種類になり、前者は「無効」ではなく「解決」である。
`invalidate` という名前は実態と食い違うため `tag-gotcha` に改める。
名前が現れるのは拒否メッセージ・注入案内・スキル本文の 3 箇所だけで、改名の波及は小さい。

### 7-5. PreToolUse deny hook(強制点)

`scripts/guard-docs.mjs` が **`Edit|Write|NotebookEdit`** の PreToolUse で起動し、次を行う。

1. `tool_input.file_path`(NotebookEdit は `notebook_path`)を絶対パスへ解決する。
2. `metatron.config.json` を §5-4 の規則で解決し、ARCHITECTURE / GOTCHAS の絶対パスを得る。
3. 書き込み先がそのいずれかに**正規化のうえ一致**すれば **deny** を返す。一致しなければ**素通し**
   (`permissionDecision` を返さず「意見なし」で終える。他プラグインの判断を妨げないため)。

**`NotebookEdit` を含める理由**: `Edit|Write` だけでは、ノートブック形式のファイルを
正本パスに設定したプロジェクトで素通りする。matcher に 1 語足すだけで塞げる穴を残さない。

**パス一致は正規化して判定する。** 単純な文字列の完全一致では次のすり抜けが起きる。

| すり抜け | 対処 |
| --- | --- |
| 相対パスと絶対パスの混在 | `cwd` 基準で `path.resolve` する |
| シンボリックリンク経由 | `fs.realpathSync` で実体パスに解決する(存在しないファイルは親ディレクトリで解決し、ファイル名を付け直す) |
| 大文字小文字が異なる(macOS / Windows の非区別 FS) | 非区別 FS では小文字化して比較する |
| 区切り文字の差(`\` と `/`) | `/` に正規化する |
| 冗長な `./` や `..` を含むパス | `path.resolve` が畳む |

Codiel の `guard-write` が `state.json` の保護で同種の対策
(絶対パスでの検査・大文字小文字非区別)を既に行っており、その実装に倣う。
一方で**部分一致・前方一致はしない**。`docs/ARCHITECTURE.md.bak` や
`docs/ARCHITECTURE.md.orig` は別ファイルであり、拒否すると
バックアップを取る正当な操作まで止めてしまう。

Codiel の `lib.ts` の `emit("deny", reason)` と同じく、
`hookSpecificOutput.permissionDecision` / `permissionDecisionReason` を出力する。

**拒否メッセージの要件**(発見性の担保。§3-3 (b)):

```
docs/GOTCHAS.md は metatron の管理下にあり、直接編集できません(追記のみ・採番・書式検証のため)。
エントリの JSON を一時ファイルに書き、次のコマンドで追記してください:
  node /abs/path/plugins/metatron/scripts/metatron.mjs append-gotcha --input /tmp/gotcha.json
既存エントリへのタグ付与(解決済み / 対象外):
  node /abs/path/plugins/metatron/scripts/metatron.mjs tag-gotcha --id GOTCHA-003 --tag 解決済み --reason "..."
入力の書式: node /abs/path/plugins/metatron/scripts/metatron.mjs get config
```

- **CLI の絶対パスを必ず含める。** hook 自身の位置は `import.meta.url` から解決できるため、
  同じプラグインルート配下の `scripts/metatron.mjs` の絶対パスを機械的に組み立てられる。
  これにより、AI は「metatron がどこにインストールされているか」を知らなくても CLI を呼べる。
- 拒否対象がどちらのファイルかで案内するサブコマンドを出し分ける。
  ARCHITECTURE なら `stage-architecture --input <path>` → `commit-architecture --staging-id <id>` を示し、
  **「ADR の追加・状態変更は `stage-adr` を使う(`stage-architecture` では拒否される)」を 1 行添える**。
  これがないと、拒否された AI が `stage-architecture` に `ADR 一覧` を渡して二度目の拒否に当たる。

**この hook が C1 構成の中心である。** MCP でも CLI でも達成できなかった
「直接編集を許さない」という不変条件を、ここで初めて機械的に満たす。

**既知の限界**:

- **Bash 経由の書き込みは捕捉しない。** `echo >> docs/GOTCHAS.md` のようなリダイレクトは
  `Edit|Write|NotebookEdit` の matcher に掛からない。捕捉するにはシェルコマンドの構文解析が必要で
  (Codiel の `guard-bash` が固定の禁止パターンに対して行っている類の処理)、
  誤検知と実装コストが釣り合わない。**回避しようとする AI を止める設計ではなく、
  知らずに直接編集する AI を正しい窓口へ導く設計**である、と位置づけを明確にする。
- **人間の編集は対象外。** hook は AI のツール呼び出しにのみ介在する。
  エディタでの直接編集は自由であり、それは正しい(§15-4 のとおり、
  人間が普通に読み書きできることが Markdown 保存の目的である)。
  **ロックは CLI 同士の相互排除しか担わない**(§7-4)。人間がエディタで開いている最中に
  CLI が先頭挿入すると、人間側の保存で CLI の書き込みが消えうる。
  これは受け入れる —— 文書は git 管理下にあり、失われた変更は差分で気づけるためである。
- **hook 自身の失敗時は素通しする。** deny hook が例外で落ちた場合、
  書き込みを止めずに通す(フェイルオープン)。metatron の hook の不具合で
  ユーザーのあらゆる編集が止まる事態のほうが、直接編集 1 回を見逃すより損害が大きい。

### 7-6. 承認が要るもの・要らないもの

| 操作 | 対話での承認 | 理由 |
| --- | --- | --- |
| `commit-architecture` | **必要** | セクションの置換であり、既存記述が失われうる。プロジェクトの技術的前提の宣言でもある |
| `append-gotcha` | **不要** | 追記のみで既存を壊さない。記録の契機は多くが失敗発生時(Codiel の run 中)であり、そこで人間の承認を待つと、自律実行を売りにしたフローが失敗のたびに止まる。誤記録も `tag-gotcha` で打ち消せる |
| `tag-gotcha` | **不要** | 同じく追記のみ。タグの付け替えも追記で表現でき、本文は不変 |
| `stage-adr` → `commit-architecture` | **必要** | ADR は設計判断の宣言であり、状態変更は過去の判断を覆す行為である。`commit-architecture` を通るため承認規律は ARCHITECTURE と同じ(§6-6) |

この非対称は現行 Codiel の挙動とも一致する(`initializing-harness` は HARD-GATE で承認必須、
`recording-gotchas` は承認を求めずに追記する)。挙動を変えずに理由を明文化した。

## 8. SessionStart 注入仕様

### 8-1. 効果範囲はメインセッションに限る

**SessionStart の `additionalContext` がサブエージェントへ継承される保証は無い。**
公式に継承が保証されていない以上、設計上は「**メインセッションのオーケストレーター文脈にだけ
届く**」ものとして扱う。

この前提から重要な帰結が 2 つ出る。

1. **Codiel の各サブエージェント(`codiel-analyst` / `codiel-architect` / `codiel-implementer-*` /
   `codiel-reviewer-*` 等)は、従来どおり自分でファイルを読む設計を維持する。**
   注入を当てにして「読まなくてよい」とすると、注入が届いていないサブエージェントが
   前提を知らないまま作業することになる。これは現行より悪化する変更であり、採らない(§10-4)。
2. **「注入済みだから再読しない」という最適化は、メインセッション文脈に限って適用する。**
   sandalphon の ASIS 探索(§11 #8)や、オーケストレーター本体の判断がこれに当たる。

注入の価値は「Codiel の run の外側、通常セッションでも前提が効く」ことにある(§1-5)。
サブエージェントへの伝達は**ディスパッチプロンプトに実パスを埋めて必読させる**経路が担い、
注入とは役割を分ける。

### 8-2. プラットフォーム上限と予算

**hook 出力(`additionalContext` を含む)はプラットフォーム側で 10,000 文字にキャップされる。**
超過分はそのまま切り捨てられるのではなく、内容がファイルへ退避され、
モデルには**プレビューと退避先パスの案内**が渡る形に置き換わる。

この事実から設計を次のように改める。

- **予算はバイトではなく文字数で、上限 10,000 文字を基準に置く。**
  設計当初の `maxBytes = 32768` は**プラットフォーム上限のはるか外側**にあり、
  自前の削り込みが一度も発動しないまま退避に倒れる。上限として機能していなかった。
- **既定値は `injection.maxChars = 9000`** とする。上限ちょうどを狙わないのは、
  組み立て時の見積もりと実際の文字数に差が出うることと、次項の合算があるためである。
- **他プラグインの SessionStart 注入と同じ文脈を共有する。** revelation のトリガー表など、
  他プラグインも SessionStart で注入する。metatron が 10,000 文字を独占できる前提を置かない。
  9000 という既定は「metatron 単独ならほぼ全部使える」値であり、
  他プラグインとの併用で圧迫が観測されたら利用者が設定で下げられるようにしてある。

**退避に倒れること自体は致命的でない**(退避先パスを Read すれば全文は読める)。
ただし退避されるとモデルは「プレビューを見て、必要なら読む」という判断を挟むことになり、
§1-5 で解決したはずの「読む判断を AI に委ねる」問題が部分的に戻る。
したがって**退避に倒れないよう自前で収める**のが設計の目標である。

### 8-3. 注入内容と保持優先順

保持の優先順は次のとおり。**短いものほど優先度が高い**という並びになっている。

| 優先 | 要素 | 概算サイズ | 根拠 |
| --- | --- | --- | --- |
| **1(最優先・不可欠)** | **CLI 案内** | 約 600 文字 | これが失われると「文書は見えるが更新方法が分からない」状態になる。C1 構成では CLI の発見性が注入に依存しており(§1-5)、最も短くて最も代替が効かない |
| 2 | ARCHITECTURE | 数千文字 | 作業の前提そのもの。ただし全文性は §8-5 で段階的に譲る |
| 3 | GOTCHAS | 可変 | 目次で網羅、直近で深掘り。削る余地が最も大きい |

**CLI 案内は注入文の先頭に置く。** 末尾ではない。理由は、
万一 10,000 文字を超えて退避に倒れた場合でも、**モデルに渡るプレビューは先頭部分**であり、
先頭にあれば CLI 案内はプレビュー内に残るからである。
末尾に置くと、退避が起きた瞬間に最も重要な要素が最初に見えなくなる。

````markdown
# metatron: プロジェクトの前提と落とし穴

これらの文書は metatron の管理下にある。**直接編集は PreToolUse hook が拒否する。**
記録・更新・全文取得は次の CLI を使う(絶対パス。M = /abs/path/plugins/metatron/scripts/metatron.mjs):
  読む:   node M get gotchas --query <語> / node M get adr / node M get architecture
  記録:   node M append-gotcha --input <一時ファイル>
  タグ:   node M tag-gotcha --id GOTCHA-003 --tag 解決済み --reason "..."
  文書更新: node M stage-architecture --input <一時ファイル> → node M commit-architecture --staging-id <id>
  ADR:    node M stage-adr --input <一時ファイル> → node M commit-architecture --staging-id <id>
※この案内はメインセッション向け。サブエージェントには別途パスが渡される。

## 技術的前提(docs/ARCHITECTURE.md)

<ARCHITECTURE の全文、または目次+要約(§8-5)>

## 既知の落とし穴(docs/GOTCHAS.md: 全 12 件)

### 目次(新しい順)
- [2026-08-16] GOTCHA-012: 存在しない Prisma API を幻覚して実装した
- [2026-08-10] GOTCHA-011: ~~E2E のセレクタに data-testid 以外を使った~~([解決済み])
- ...

### 直近 5 件(全文)
<GOTCHA-012 〜 GOTCHA-008 のエントリ全文>
````

見出しの直後にファイルパスを併記するのは、縮退時に「全文はここを Read せよ」と
案内する先を、常に同じ場所に置いておくためである。

### 8-4. 要約規則

| 対象 | 規則 | 根拠 |
| --- | --- | --- |
| CLI 案内 | **常に全文**。削らない | §8-3 の優先 1 |
| ARCHITECTURE | **予算内なら全文**。超過時は §8-5 で縮退 | セクションが既に要約済みの宣言文であり、圧縮すると判断に使えない。ただし 10,000 文字の現実の前では全文を絶対視できない |
| GOTCHAS 目次 | **全エントリ**の `[日付] GOTCHA-NNN: タイトル` を**ファイル順(新しい順)**で。タグ付きは打ち消し線 + `[解決済み]` / `[対象外]` | 「そういう罠が存在する」ことさえ分かれば、必要時に `get gotchas` で全文を引ける。網羅性を担保する層 |
| GOTCHAS 直近 N 件 | **N = 5**(`injection.gotchasRecentCount`)。**ファイルの先頭から** 5 エントリを全文 | 深さを担保する層。新書式は新しいものを上に積むため(§6-3)、先頭 = 最新になる |
| タグ付きエントリ | 目次には出すが、直近 N 件の全文対象からは**除外し、除外分だけ後続の無タグエントリで埋める** | `[解決済み]` / `[対象外]` の全文は誤誘導になる。存在の告知だけで足りる |
| ADR 一覧 | **タイトル + 状態の一覧**へ縮退する(全文は載せない) | ADR は「引くための記述」(§6-5)であり、通読対象ではない。一覧があれば必要な ADR を特定でき、`get adr` で全文を引ける。全文を載せると 1 件で数百文字を消費し、予算を急速に食う |

「目次(広く浅く)+ 直近(狭く深く)」の 2 層構成は維持する。どちらか片方では失敗するためである。
全文だけでは古い罠を見落とし、目次だけでは「読みに行く」判断を AI に委ねることになり、
§1-5 で解決したはずの問題が戻る。

### 8-5. 段階縮退

組み立て後の文字数が `injection.maxChars` を超える場合、次の順に削る。
**優先順(§8-3)の逆から削る**、すなわち GOTCHAS → ARCHITECTURE の順で、
CLI 案内には決して手を付けない。

| 段階 | 削るもの | 添える案内 |
| --- | --- | --- |
| 1 | GOTCHAS 直近 N 件の全文を N-1、N-2 …と減らす(最小 0 件) | — |
| 2 | GOTCHAS 目次を直近 50 件に制限 | 「他 M 件は `get gotchas` で取得」 |
| 3 | **ADR 一覧を全廃**(既定でも全文ではなくタイトル + 状態の一覧。§8-4) | 「ADR は `get adr` で取得」 |
| 4 | **ARCHITECTURE を目次(セクション見出しの一覧)+ 各セクションの要約 1 行に縮退**。要約に採るのは**そのセクションのフェンス外の最初の散文行**(表・コードフェンス・Mermaid の中身は採らない) | **「全文は `docs/ARCHITECTURE.md` を Read すること」**(解決済みの実パスを書く) |
| 5 | GOTCHAS 目次を全廃 | 「一覧は `get gotchas` で取得」 |
| 6 | ARCHITECTURE の目次のみに縮退 | 同上 |

**ADR を ARCHITECTURE 本体より先に削る**(段階 3 < 段階 4)。ADR は
「引くための記述」であって毎セッション読ませる前提の節ではなく、
`get adr` という専用の取得経路も持つ。一方 `## レイヤー構造` や `## 保護パス` は
読んだ AI の振る舞いを直接変えるため、最後まで残す価値が高い。

**段階 4 が当初設計からの実質的な変更である。** 旧設計は「ARCHITECTURE を上限まで
切り詰める(truncate)」としていたが、これは文の途中で切れた前提をモデルに渡すことになり、
不完全な情報を完全なものとして扱う危険がある。**目次 + 要約への縮退**なら、
渡る情報は不完全でも**構造として完結**しており、「ここには続きがある」ことが明示される。
そのうえで全文パスの Read を促せば、モデルは欠けを認識したうえで補える。

段階 4 以降に到達するのは ARCHITECTURE が大きく育った場合である。
`ARCHITECTURE.example.md` の実測(コメント除去後 2,881 文字)に新設 3 節を加えても
約 4,300 文字であり(§16-2)、ADR が数件なら段階 1〜3 で収まる。
**ADR は最も伸びやすい節**であり、段階 3 の発動頻度は ADR の件数に比例する。

### 8-6. 外部依存を持たないこと

注入は次だけを行う。

1. `metatron.config.json` を探して読む(無ければ既定値)。
2. 解決したパスのファイルを `fs.readFileSync` で読む。
3. **`src/lib/architecture.ts` / `gotchas.ts` の同一パーサでセクション・エントリに分解する。**
4. 予算内に収まるよう組み立て、JSON を stdout に出す。

**注入は CLI と同じパーサを使う。** 手順 3 を素朴な文字列処理で代替しない。
別実装にすると、CLI が 1 セクションと見なす範囲と注入が切り出す範囲が食い違い、
Mermaid 図を含む節で特に壊れる(§6-1 の規範アルゴリズム)。
共有ライブラリを 3 成果物すべてが取り込む構成(§4)は、この一致のためにある。

**「ARCHITECTURE 全文」の定義**: 注入における「全文」とは、ファイルのバイト列そのものではなく、
**パーサで分解し、`## ADR 一覧` をタイトル + 状態の一覧に縮退したうえで再構成した出力**を指す
(§8-4)。ADR が全文で載ることは、予算に収まる場合でも無い。

プロセス間通信も `node_modules` への依存も持たない。C1 構成では常駐プロセスが無いため、
**「サーバーが起動していないから注入されない」という故障モードが存在しない**。

### 8-7. 失敗時の挙動(フェイルオープン)

revelation の `inject-trigger-map.ts` と同じ規律を採る。

- ファイルが存在しない・読めない・設定が壊れている → **何も出力せず exit 0**。
- 例外は握り潰す。SessionStart hook の失敗でセッション開始を妨げない。
- `injection.enabled: false` のときも同様に何も出力しない。

注入がフェイルオープンなのは、注入の失敗が**セッションを開始できない**という
不釣り合いに大きな損害に化けるためである。書き込み(CLI)がフェイルクローズドなのとは
判断が逆になるが、これは「止めたときの損害」の大きさが違うことによる(§12-1)。

## 9. 生成・更新フロー

### 9-1. `/metatron:init` — 初回生成

現行 `initializing-harness` の**インタビュー方式を廃止**し、解析ドラフト + 対話ウォークスルーに変える。

```
1. metatron.mjs scan でコードベースの事実を収集
        │
2. 事実からセクションごとのドラフトを起草(モデルの仕事)
        │
3. セクション単位の対話ウォークスルー ← ★ ファイルを直読させない
     「技術スタックはこう読み取った。合っているか」
     → 確認・修正 → 確定 → 次のセクションへ
        │
4. 全セクション確定後、stage-architecture で diff を取得
        │
5. diff を全文提示 → 承認 → commit-architecture
        │
6. GOTCHAS の台帳を初期化(空でよい。append-gotcha が必要時に作る)
```

**手順 1 が返す事実**(`scan`。すべてファイルシステムから決定的に取れるもの):

| 項目 | 収集元 |
| --- | --- |
| パッケージマネージャ | lockfile(`pnpm-lock.yaml` / `package-lock.json` / `yarn.lock`) |
| 言語・ランタイム | `package.json` / `tsconfig.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` |
| 依存ライブラリ(主要) | `package.json` の `dependencies`(devDependencies と分けて返す) |
| コマンド候補 | `package.json` の `scripts`(test / lint / build / typecheck / e2e に該当しそうなキー) |
| ディレクトリ構造 | 深さ 3 までのツリー(`node_modules` / `.git` / ビルド出力を除外) |
| テストフレームワーク | 設定ファイルとテストファイルの命名パターン |
| ドメイン候補 | トップレベルおよび `src/` 直下のディレクトリ名と、各配下のファイル数 |
| 既存ドキュメント | `README.md` / `CLAUDE.md` / 既存 `docs/*.md` の見出し一覧 |

**現行との最大の違いは「コードベース解析で回答を代替しない」という HARD-GATE の撤廃である。**
現行スキルはこれを禁じていた(出所は常にユーザーの回答であるべき、という思想)。
これを変える根拠は、**承認方式が変わったこと**にある。

- 現行: 質問 → 回答 → 生成。解析で埋めると「ユーザーが言っていないことが宣言になる」。
- 新: 解析 → **ドラフトをセクションごとに対話で確認** → 確定。
  解析結果は「たたき台」であり、**確定はすべてユーザーの明示的な確認を経る**。

出所の保証は「聞いてから書く」から「**書いたものを 1 セクションずつ承認させる**」へ移った。
後者のほうがユーザーの負担が小さく(ゼロから答えるより、提示を直すほうが速い)、
精度も高い(`package.json` の実物を見て書くため)。

**手順 3 でファイルを直読させない理由**: 「生成された ARCHITECTURE.md を読んで確認してください」と
丸投げすると、実際には斜め読みで承認される。セクションごとに「こう読み取ったが合っているか」と
問う形にすると、確認が具体的な質問への回答になり、誤りが実際に発見される。

### 9-2. ウォークスルーの粒度

- セクション 10 個を**そのままウォークスルーの単位**とする。
  ただし **`## ADR 一覧` は初回生成の対象外**とする。ADR は「これから下す判断」ではなく
  「既に下した判断」の記録であり、解析からは導けない。初回は空の節を置き、
  以後 `stage-adr` で足していく。
- **`## システム概要` の Mermaid 図は解析結果から起草する。** `scan` が返すディレクトリ構造と
  依存関係を材料に主要コンポーネントの図を書き、ウォークスルーで「この粒度で合っているか」を問う。
  図は誤りが目で見つかりやすく、対話確認の効果が最も高い節である。
- **ドラフトは §6-5 の執筆規律に従って書く。** 起草の段階から根拠・経緯を書かない。
  書いてから削るより、最初から指示だけを書くほうが対話の往復が減る。
- 1 セクションにつき「ドラフトの提示」+「確認すべき点 1〜3 個の明示」を 1 メッセージで行う。
  確認点を明示するのは、提示だけでは何を見ればいいか分からず承認が形骸化するため。
- ユーザーが「まとめて全部見る」を希望した場合は全セクションを一度に提示してよい。
  ただし `stage-architecture` → diff 提示 → `commit-architecture` の流れは省略しない。
- 情報が足りずドラフトを書けないセクション(例: `## 規約`)は**推測で埋めず**、
  そのセクションだけ質問形式に切り替える。
  ドメインマップは解析候補を提示しつつ、最終決定は必ずユーザーに確認する
  (下流の解釈が乗るため、誤りの代償が大きい)。
- **Codiel 単体で作られた最小 ARCHITECTURE(§10-2)が既にある場合**、
  `## ドメインマップ` は「既存の内容」として提示し、**残り 8 セクション**
  (10 節から `## ドメインマップ` と、初回対象外の `## ADR 一覧` を除く)を埋める流れになる。
  既存セクションを勝手に上書きしない。

### 9-3. `/metatron:update` — 乖離検出と更新

```
1. diff-architecture が乖離候補を返す
        │
2. 候補をユーザーに一覧提示(「更新する / しない」を選ばせる)
        │
3. 選ばれた分だけ stage-architecture → diff 提示 → 承認 → commit-architecture
```

**`diff-architecture` が返す乖離候補**(決定的に検出できるものに限る):

| 乖離 | 検出方法 |
| --- | --- |
| 技術スタックの追加・削除 | `package.json` の依存と `## 技術スタック` の表の突き合わせ |
| コマンドの変更 | `package.json` の `scripts` と `## コマンド定義` の表の突き合わせ |
| ドメインマップの穴 | 実在するソースディレクトリのうち、どの glob にも一致しないもの |
| ドメインマップの死んだ glob | どのファイルにも一致しない glob |
| 保護パスの不整合 | `## 保護パス` の glob と `raguel.config.yaml` の `globs` の差 |
| ディレクトリ構成の変化 | ツリーと `## ディレクトリ構成と責務` の記述の突き合わせ |
| **セクションの欠落** | §6-1 の 10 セクションのうち存在しないもの(最小ファイルからの育成を促す) |
| **ADR の状態の陳腐化** | `状態: 採用` の ADR のうち、`影響範囲` に挙げられたパスが実在しないもの |

「散文の内容が実装と食い違う」といった意味的な乖離は決定的に検出できないため候補に出さない。
実装 diff を見たモデルが気づいた点は `stage-architecture` に直接載せる経路で更新する
(検出と更新を分離しているのはこのため)。

### 9-4. GOTCHAS の記録フロー

metatron 側の `recording-gotchas` スキルは、**記録判断フロー(§6-3)を適用して
`append-gotcha` を実行する**ところまでを担う。記録の**契機**は持たない
(契機を持つのは Codiel であり、人間の明示依頼でもよい)。

## 10. Codiel 改修仕様

### 10-1. 大原則: Codiel は metatron を一切参照しない

**Codiel が参照するのはファイル契約(§3-3 (a))だけである。**

「参照しない」の定義を明確にしておく。**参照しないのは metatron の
プラグインルート・コード・コマンドである。プロジェクト内の文書ファイルとそのパスは参照する。**

| 対象 | Codiel は参照するか |
| --- | --- |
| metatron のプラグインルート(`CLAUDE_PLUGIN_ROOT`) | **しない**(解決手段が無い。§15-2) |
| metatron の TypeScript ソース・共有ライブラリ | **しない**(import もコピーもしない) |
| metatron の CLI を「パスを知っている前提で」呼ぶ | **しない**(パスは知りようがない) |
| metatron がインストール済みかの検出 | **しない**(§10-2 の判定はファイルと利用可能コマンドだけを見る) |
| `metatron.config.json` の**内容** | **する**(ファイル契約。独立実装で読む) |
| `docs/ARCHITECTURE.md` / `docs/GOTCHAS.md` の**内容** | **する**(そもそも Codiel の入力である) |
| コンテキストに現れた CLI の絶対パス | **する**(ただし「あれば使う」であって、無くても動く。§3-3 (b)) |

要するに、Codiel が知ってよいのは**プロジェクト側にあるもの**と
**その場でコンテキストに渡されたもの**だけで、metatron プラグインの中身は知らない。

この原則から次が導かれる。

- **利用者が Codiel だけを導入しても完結する。** ARCHITECTURE / GOTCHAS が無ければ
  Codiel が自前で最小限を用意する(§10-2、§10-4)。
- **metatron を併用するときは、コンテキストに現れた CLI の案内に従う**(§3-3 (b))。
  「案内があれば使い、無ければ自前で処理する」とスキルに書くだけでよく、
  条件分岐にインストール検出が入らない。
- **両者の間に依存関係の宣言が要らない。** marketplace 上でも独立したプラグインのままでいられる。

### 10-2. `/codiel:init` の縮小と単体動作フォールバック

**廃止するもの**: インタビューのテーマ 1〜6・8(ARCHITECTURE の散文全般)と、
散文セクションの生成処理。

**残すもの**: テーマ 4(ドメイン分割)と テーマ 7(保護パス)。

改修後の `/codiel:init` の流れ:

```
1. ARCHITECTURE(ファイル契約で解決したパス)を確認
   ├─ 存在し metatron:domains が読める     → 何もしない(次へ)
   ├─ 存在しない、または domains が無い
   │   ├─ /metatron:init が利用可能コマンドにある
   │   │      → /metatron:init を「推奨」として提示し、ユーザーに選ばせる
   │   │        (a) /metatron:init を実行する(推奨)  (b) 最小生成で進む
   │   └─ 無い(Codiel 単体環境)
   │          → ★ 最小 ARCHITECTURE を生成するフォールバック(下記)
2. .codiel/specs .codiel/runs .codiel/reports の作成
3. raguel.config.yaml の生成(保護パス)
4. CLAUDE.md の ## Codiel ハーネス運用ルール 節の追記
5. 検証(readDomains で読めることの確認)
6. 完了報告
```

**判定に metatron のインストール検出を使わない。** 見るのは
「ファイルが契約を満たすか」と「`/metatron:init` が自分の利用可能コマンドにあるか」の 2 点だけで、
どちらも Codiel が自力で確認できる情報である(sandalphon 設計書 §7-3 と同じ手法)。

**`/metatron:init` への誘導は「推奨」であって強制ではない。** ユーザーが
「今は run を回したいだけで、ARCHITECTURE を作り込む気は無い」という状態は正当であり、
そこで `/codiel:init` が拒否して終了すると、**Codiel を使いたいだけのユーザーが行き詰まる**。
推奨を提示したうえで、ユーザーが最小生成を選んだらそのまま進む。
最小ファイルは後から `/metatron:init` で育てられる(後述)ので、この選択は不可逆でない。

**最小 ARCHITECTURE フォールバック**:

- インタビューは**ドメイン分割テーマのみ**。散文は一切聞かない。
  **インタビューの回答はドラフトの入力であって承認ではない。** ドメイン分割を聞き取った後、
  生成する最小ファイルの**全文を提示して改めて承認を得てから**書き込む
  (回答したこと自体を承認とみなさない。現行 HARD-GATE の「承認なしに書き込まない」を維持する)。
- 生成するのは次の形の**最小ファイル**である。中立マーカーに準拠する。

````markdown
# ARCHITECTURE

## ドメインマップ

```json metatron:domains
{
  "generic": ["**"]
}
```
````

- 承認は現行どおり必須(書き込み前にドラフト全文を提示する)。
- 完了報告に「これは Codiel が run を開始するための最小構成である。
  技術スタック・規約などの記述を加えるには metatron の導入を検討するとよい」と 1 行添える。

**移行作業がゼロであること**を設計書とスキルの両方に明記する。
このファイルは §6-1 の「すべてのセクションは任意」という規定を満たす正当な ARCHITECTURE であり、
後から metatron を導入した場合、`/metatron:init` が既存の `## ドメインマップ` を
そのまま活かして残りのセクションを足す(§9-2 の最後の項)。
変換もマーカーの書き換えも要らない。

**この「移行ゼロ」は本設計以降に作られたファイルについての保証である。**
旧マーカー `codiel:domains` で書かれた既存資産は対象外であり、読み替えも変換も行わない
(非スコープ §2-2「既存生成物の移行措置」)。Codiel は開発中ステータスで利用者ゼロという
前提に立っており、旧資産が存在しないことを前提にしている。
仮に手元に旧形式のファイルがあれば、マーカー名を手で書き換えるのが唯一の対応になる。

**保護パス(テーマ 7)の扱い**: 現状維持(二重管理)。ただし入力は 1 回にする。

- ARCHITECTURE に `## 保護パス` 節が**ある**場合(metatron 管理下の典型)
  → その glob を読み取り、内容を提示して承認を得た上で `raguel.config.yaml` を生成する。
- **無い**場合(単体フォールバックの最小ファイル等)→ 従来どおりインタビューで聞く。

**削除するもの**: `install-harness.sh` からの `GOTCHAS.example.md` コピー
(GOTCHAS は §10-4 の経路で必要時に作る)。現行スキルの「修復の例外」条項のうち
ARCHITECTURE の `codiel:domains` ブロックを置換する部分は、対象マーカー名を更新して残す
(単体環境では Codiel が唯一の書き手であるため、修復手段は必要)。
ただし metatron 併用環境では deny hook が拒否するので、拒否されたら
`/metatron:update` を案内する、と手順に加える。

### 10-3. `readDomains` と `resolveDocPaths`(`src/hooks/lib.ts`)

現行:

```ts
export function readDomains(root: string): unknown {
  const p = path.join(root, "docs", "ARCHITECTURE.md")
  if (!fs.existsSync(p)) return null
  const m = fs.readFileSync(p, "utf8").match(/```json codiel:domains\n([\s\S]*?)```/)
  ...
}
```

改修後の要件:

1. **`findDocRoot(startDir)` を新設**する。§5-4 の規則 1(config 祖先 → git ルート → cwd)を
   実装する。**既存の `findProjectRoot`(`.codiel` 祖先探索)とは別関数として共存させる。**
2. **`resolveDocPaths(startDir)` を新設**する。内部で `findDocRoot` を呼び、
   `metatron.config.json` を §5-4 の規則 2〜4 で解釈して
   `{ architecture, gotchas }` の絶対パスを返す。設定が無ければ既定値。
   絶対パス・ルート脱出は拒否して既定値に落とす。
   **metatron のソースを参照せず、ファイル契約に基づいて独立に実装する**(§3-3)。
3. `readDomains` は **`root` 引数を取るのをやめ、`startDir` から `resolveDocPaths` 経由で
   解決する**。マーカーを **`metatron:domains`** に変更する。
   引数の意味を変えるのは、呼び出し側が `findProjectRoot` の結果(`.codiel` ルート)を
   渡してくると §5-4 の基準とずれるためである(§5-4 の相違表)。
   **ルートの決定を関数の内側に閉じることで、呼び出し側が基準を間違えようがなくなる。**
4. **旧マーカー `codiel:domains` は読まない。** 互換読みを入れない。
5. 戻り値の型と失敗時の `null` 返しは現行のまま(下流を変えないため)。

**2 つのルート概念を関数名で区別する。**

| 関数 | 基準 | 用途 |
| --- | --- | --- |
| `findDocRoot` | config 祖先 → git ルート → cwd(§5-4) | **文書**(ARCHITECTURE / GOTCHAS)の解決 |
| `findProjectRoot` | `.codiel` 祖先(現行のまま) | **Codiel 固有資産**(`.codiel/runs` 等)の解決 |

同じ「ルート」という語で 2 つの異なる基準を指していたことが、
今回の不整合の温床である。名前で分けたうえで、
**どちらを使うかは「探しているものが文書か Codiel 資産か」で決まる**と規約化する。
`guard-write` の `.codiel/runs/**/state.json` 判定など既存の用途は
`findProjectRoot` のままでよく、挙動は変わらない。

バンドル対象は現行の `lib` エントリのままで、新規エントリは不要。

### 10-4. `recording-gotchas` の改修

**残すもの**: 記録の契機の表(Raguel STOP / ループ上限超過 / `record_outcome(incident)` /
レビューでの設計漏れ)、run に紐づくコミット規約
(`codiel(gotchas): <要約> (issue-N try-M)`)、記録判断フロー、追記のみの HARD-GATE。

**書式の全面追随**: 旧書式のフィールド(発生フェーズ / 症状 / 根本原因 / 予防策 / 関連ファイル)を
**新書式の 5 フィールドへ全面置換する**(§6-3)。

| 旧フィールド | 新フィールド | 備考 |
| --- | --- | --- |
| 症状 | **失敗内容** | 「何を間違えたか」に視点を移す |
| 根本原因 | **原因 (推測)** | 断定しない表現に変わる。推測であることを明示する |
| 予防策 | **対策** | 「今後 AI はどう振る舞うべきか」。精神論を書かない規律は維持 |
| (なし) | **タスク** | 何をしようとしていたかの文脈。新設 |
| (なし) | **昇格候補** | `Yes` / `No`。5 件ルール(§6-3b)の集計対象。新設 |
| 発生フェーズ | (廃止) | Codiel のフェーズ名は新書式に持ち場が無い。必要なら `タスク` に書く |
| 関連ファイル | (廃止) | 必要なら `対策` の中でパスを示す |

**Codiel フェーズ名の指定は廃止する。** 新書式に `発生フェーズ` が無いためであり、
フェーズの情報が要るときは `タスク`(何をしようとしていたか)に自然文で含める。
これにより Codiel 以外からの記録と書式が完全に一致する。

**変えるもの**: 書き込み手段を次の 2 分岐にする。

```
コンテキストに metatron CLI の案内(append-gotcha の絶対パス)があるか?
  ├─ ある  → エントリの JSON を一時ファイルに書き、
  │           CLI を `append-gotcha --input <path>` で実行して追記する
  └─ ない  → 自前でファイルを作成・追記する
              └─ その書き込みが deny hook に拒否されたら
                    → ★ 拒否メッセージに載っている CLI で実行し直す
```

スキル本文には次の 2 文を書く。インストール検出も、プラグインパスの推測も行わない。

1. 「**metatron CLI の案内がコンテキストにあればそれを使い、なければ直接追記する**」
2. 「**直接追記が hook に拒否されたら、拒否メッセージに示された CLI で実行し直す**」

**2 文目が第 3 の状態への回復経路である。** 分岐は「案内があれば併用環境」という
近似に立っているが、これは常に正しいとは限らない。長い run では注入された案内が
コンテキストの圧縮で失われることがあり、そのとき Codiel は
「案内が無い = 単体環境」と誤判定して直接追記に進む。
**metatron は導入されているので deny hook が拒否し、そこで手が止まる。**

拒否メッセージ自体が CLI の絶対パスを運んでいる(§7-5)ため、回復に必要な情報は
その場で手に入る。2 文目はそれを使えと明示するだけであり、
これがないと「拒否された」で報告して終わる可能性がある。

整理すると次の 3 状態すべてで成立する。

| 状態 | 経路 |
| --- | --- |
| 併用環境・案内あり | CLI で追記(1 文目) |
| 併用環境・案内が失われた | 直接追記 → 拒否 → 拒否メッセージの CLI で再実行(2 文目) |
| 単体環境 | 直接追記(hook が無いので通る) |

#### 直接追記も新書式に従う

単体環境での直接追記は、**CLI を使わないだけで書式は同じ**でなければならない。
ここが旧書式のままだと、後から metatron を導入した時点で台帳に 2 つの書式が混在し、
パーサがどちらかを読めなくなる。Codiel 側の写し(§10-4 の書式節)に次を明記する。

- **挿入位置は `## 失敗パターン一覧` の直下(先頭)。** ファイル末尾に追記しない。
- **ファイルまたは `## 失敗パターン一覧` 節が無ければ、雛形ごと作成する。**
  雛形は冒頭説明・運用ルール・記入テンプレート・空の一覧節を含む(§6-3)。
- **エントリは新テンプレートの 5 フィールド**(タスク / 失敗内容 / 原因 (推測) / 対策 / 昇格候補)。
- **見出しは `### [YYYY-MM-DD] GOTCHA-NNN: タイトル`。** 採番は
  `## 失敗パターン一覧` 配下の既存エントリの最大値 + 1。
- **タグを付けるときは §6-3 の検出規則に従う**(`GOTCHA-NNN:` の直後、リテラル 2 種)。

写しに置くのは**書式と採番規則だけ**とし、規律の根拠・例は metatron の正本にのみ置く
(sandalphon 設計書 §6-3 と同じ正本・写し運用)。

**`docs/GOTCHAS.md` が存在しない場合**: 単体環境では Codiel が台帳ごと新規作成する
(現行は `/codiel:init` を案内していたが、記録の契機は失敗発生時であり、
そこで「初期化してください」と止めるのは学習機会の損失になる)。
併用環境では `append-gotcha` が台帳ごと作る。

**ARCHITECTURE 散文・GOTCHAS の参照は optional に統一する。** `preparing-design-agendas` の
手順 2 をはじめ、各スキルの「`docs/ARCHITECTURE.md` と `docs/GOTCHAS.md` を読む」という指示を
**「あれば読む、なければスキップする」**に変える。
最小 ARCHITECTURE には散文が無く、GOTCHAS も存在しないことがありうるため、
必須扱いのままだと単体環境で毎回「ファイルが無い」という報告が発生する。

**optional 化の意味を取り違えない。** これは「**ファイルが存在しない場合にスキップしてよい**」
という意味であって、「読むかどうかをエージェントが判断してよい」という意味ではない。
とくに次の線引きを守る。

| 対象 | 規律 |
| --- | --- |
| **Codiel のサブエージェント**(`codiel-analyst` / `codiel-architect` / `codiel-implementer-*` / `codiel-reviewer-*` 等) | **存在すれば必ず読む。** 注入を当てにして省略しない。SessionStart の注入がサブエージェントへ継承される保証は無く(§8-1)、省略すると前提を知らないまま作業することになる |
| **オーケストレーター本体**(メインセッション) | 注入で既にコンテキストにある内容は再読しなくてよい。ただし判断に必要なら読む |
| **sandalphon 等の他プラグイン** | 同上(メインセッション文脈に限る。§11 #8) |

この区別を明記しないと、「optional」を「読まなくてよい」と解釈したサブエージェントが
ARCHITECTURE を無視するようになり、**現行より悪化する**。
optional 化の目的は単体環境での空振り報告をなくすことであって、必読規律を緩めることではない。

### 10-5. domains の機械読主体の宣言訂正(事実の修正)

**現行の記述は事実と食い違っている。** `ARCHITECTURE.example.md` は
「hooks(guard-write)と implementer/reviewer のディスパッチ選択がこのブロックを機械的に読む」
と書いているが、`guard-write.ts` は `findActiveRun` / `findProjectRoot` / `emit` / `pass` /
`readStdin` しか使っておらず、**`readDomains` を呼んでいない**。
`readDomains` は `lib.ts` に実装され `scripts/lib.mjs` にバンドルされているが、
実際の消費者は `initializing-harness` の検証コマンドと、スキル本文の散文だけである。

**今回の対応: 宣言を実態に合わせて訂正する。配線はしない。**

| 選択肢 | 内容 | 判断 |
| --- | --- | --- |
| A | `guard-write` に `readDomains` を配線し、ドメイン別 implementer の書き込み境界を実際に強制する | **採らない**。これは enforcement の追加であり、非スコープ「Codiel の enforcement 変更」に真正面から当たる。今まで通っていた書き込みが弾かれるようになり、metatron 分離とは無関係な挙動変更が混入する。切り分け不能な回帰の温床になる |
| B | **ドキュメントの宣言を実態に合わせる**(採用) | 「hooks が読む」を削り、実際の読み手(§6-2 の表)を正確に書く。挙動は 1 バイトも変わらない |

具体的な修正箇所:

- `ARCHITECTURE.example.md`(metatron へ移設する版)のドメインマップ記入ガイドから

このまま配ると、**プロジェクトの CLAUDE.md が設計と食い違う指示を恒久的に持つ**ことになる。
次の 3 点を反映した文言へ改訂する。

1. **パスは固定でなく解決される**(`metatron.config.json` で変更されうる)。
2. **metatron 併用時は前提が自動注入される**(メインセッションに限る)。
3. **正本の直接編集は行わない**(併用時は hook が拒否する。CLI 経由で更新する)。

単体環境でも成立する文言にする必要がある点に注意する。
「metatron の CLI を使え」と無条件に書くと、単体利用者に存在しないコマンドを指示することになる。
「**案内があれば CLI、なければ直接編集**」という §10-4 と同じ条件付きの書き方に揃える。

不整合の危険が増えるためである。**解決はオーケストレーターで 1 回、以降は値を渡す。**

## 12. エラー・デグラデーション設計

### 12-1. 基本方針

metatron のフェイル方針は**2 層に分かれる**。層を混同しないことが重要なので、ここで一括して宣言する。

| 層 | 対象 | 方針 | 根拠 |
| --- | --- | --- | --- |
| **第 1 層: 内容の検証** | CLI の書き込み系(`stage-architecture` の検証、`commit-architecture` のハッシュ照合、採番、承認の有無) | **フェイルクローズド** | 壊れた内容を書けば正本が壊れる。書かずに止まるほうが常に安い |
| **第 2 層: 機構自身の動作** | 注入 hook・deny hook・設定の読み取り | **フェイルオープン** | ここで止めると、metatron の不具合がセッション開始やユーザーのあらゆる編集を妨げる。損害が不釣り合いに大きい |

言い換えると、**「書く内容が正しいか」は厳しく、「metatron が動いているか」は緩く**判定する。
とくに **deny hook 自身が例外で落ちた場合は素通しする**(§7-5)。
拒否できなかった結果は「直接編集が 1 回通る」ことであり、
拒否機構の故障で全編集が止まることに比べれば桁違いに小さい損害である。

### 12-2. 状況別の挙動

| 状況 | 挙動 |
| --- | --- |
| `metatron.config.json` が無い | 全項目が既定値。エラーではない。報告もしない(正常な状態) |
| 設定が壊れた JSON | 注入: 既定値で続行し「設定を読めなかったため既定値を使用」と 1 行添える。CLI: `get config` が理由つきで既定値適用を報告 |
| `version` が未知 | 全項目を既定値扱い。上と同じ 1 行を添える |
| `paths.*` が絶対パス / ルート外 | その項目だけ既定値に落とし、理由を返す(§5-4) |
| ARCHITECTURE が存在しない | 注入: GOTCHAS だけを注入。CLI: `get architecture` は「未作成」を返す。`stage-architecture` は新規作成 diff を返す |
| GOTCHAS が存在しない | 注入: ARCHITECTURE だけを注入。`append-gotcha` が台帳ごと作る |
| `metatron:domains` が無い / 壊れている | `get domains` が `{ ok: false, reason }` を返す。**注入は止めない**(散文部分には価値がある)。Codiel はこれを見て run を止める(Codiel 側の解釈) |
| ARCHITECTURE に散文セクションが無い(最小ファイル) | 正常。注入はドメインマップだけを含む。各スキルは optional 扱いでスキップする(§10-4) |
| `commit-architecture` 時にファイルが変化 | 書き込まず `file_changed`。再度 `stage-architecture` からやり直す |
| `stagingId` が期限切れ / 使用済み | 書き込まず理由を返す。stage からやり直す |
| ドメインマップの検証に失敗 | `stage-architecture` が `stagingId` を発行しない。壊れたブロックは stage すらできない |
| staging の一時ディレクトリが消えた | `unknown_id` を返す。stage からやり直す(損失はドラフト 1 回分) |
| deny hook が正本への書き込みを拒否 | 拒否理由と CLI の絶対パスを返す。AI は CLI へ切り替える(§7-5) |
| deny hook が例外で落ちた | 素通し(フェイルオープン)。直接編集が 1 回通る |
| Bash リダイレクトで正本へ書き込み | 捕捉しない(§7-5 の既知の限界) |
| 注入が予算超過 | §8-5 の順で段階縮退し、縮退したことと全文の取得方法を明示する。**CLI 案内は削らない** |
| 縮退しても 10,000 文字を超えた | プラットフォームが退避に倒す。**CLI 案内は先頭にあるためプレビュー内に残る**(§8-3)。設計上はここに到達しないことを目標とする |
| `append-gotcha` のロックが取れない | 約 1 秒リトライののち非 0 終了し `{ error: "lock_timeout" }` を返す。書き込みは行わない(§7-4) |
| GOTCHAS に `## 失敗パターン一覧` 節が無い | 節ごと作成して先頭挿入する。既存の記述は保持する |
| GOTCHAS の `## 記入テンプレート` を誤ってエントリと解析 | 起きない。解析対象を `## 失敗パターン一覧` 配下に限定している(§6-3) |
| ADR の `状態` が値域外 | `stage-adr` が拒否し `stagingId` を発行しない。書き込みなし |
| `stage-architecture` に `ADR 一覧` を指定 | エラー。`stage-adr` へ誘導する(変更経路の一本化。§7-4) |
| 未閉フェンスの ARCHITECTURE | 書き込み経路は `unclosed_fence` で拒否、読み取り・注入経路は警告つきで継続(§6-1・§12-1) |
| ARCHITECTURE に `## ADR 一覧` が無い | `stage-adr` が節ごと作成する staged change を返す |
| Mermaid の構文が壊れている | **検証しない**。レンダリングされないだけで、他セクションの機械処理に影響しない(§6-1) |
| ロックファイルが残留している | 更新時刻が 60 秒より古ければ死んだロックとみなして奪う(§7-4) |
| 文書ルートと Codiel ルートが食い違う構成 | 文書は `findDocRoot`、Codiel 資産は `findProjectRoot` で解決する。両者が別ディレクトリを指すのは正常な状態として扱う(§10-3) |
| Codiel 単体環境 | metatron の hook も CLI も存在しない。Codiel が自前で最小 ARCHITECTURE と GOTCHAS を扱う(§10-2、§10-4) |

### 12-3. 報告の書き方

畳んだ経路は 1 行で理由を報告する。ただし**「設定ファイルが無い」は報告しない**。
既定値での動作が正常な状態であり、毎セッション「設定ファイルがありません」と告げるのは
ノイズにしかならない。

## 14. 実装手順

sandalphon と合わせて 1 実装セッションで行う前提のため、依存順に並べる。

### N0. ファイル契約の凍結(実装前)

`metatron:domains` のマーカー名、`metatron.config.json` のスキーマ、パス解決規則、
ARCHITECTURE の 10 セクション(§6-1)、ADR のエントリ書式(§6-6)、
GOTCHAS の新書式とタグ(§6-3)を凍結する。
この 5 点は metatron / Codiel / sandalphon の 3 実装が独立に持つ契約であり、
実装開始後に変えると 3 箇所を追いかけることになる。

### N1. metatron 本体

1. `plugins/metatron/` の骨格(`plugin.json`、`package.json`、`build.ts`、`hooks/hooks.json`)。
2. `src/lib/config.ts` + テスト(C 系)。**最初に作る**。3 実装が依存する契約の基準となるため。
3. `src/lib/architecture.ts` / `gotchas.ts` / `adr.ts` / `staging.ts` / `scan.ts` +
   テスト(A / G / R-A / T / S 系)。
4. `src/metatron-cli.ts` + 統合テスト(S5 / S6)。`pnpm build` で `scripts/metatron.mjs` を生成。
5. `src/inject-context.ts` + テスト(I 系)。
6. `src/guard-docs.ts` + テスト(D 系)。**注入と deny hook は対で完成させる**
   (CLI の発見性と強制が両方揃って初めて §1-3 の目的が満たされる)。
7. `references/` 5 本(`writing-discipline.md` を含む)、skills 3 本、commands 2 本。
   **`writing-discipline.md` は `prompt-smith` の 3 基準を読み、2 文書向けに特化・要約して書く**
   (§6-5。prompt-smith を参照させず、metatron 側に焼き込む)。
   **skills / commands は `prompt-smith:skill-creator`、references は `prompt-smith:prompt-smith` を使う**。
8. `README.md`(名前の由来、動作要件、CLI と 2 hook の説明、Codiel / sandalphon との関係、
   常駐プロセスが無いこと)。`docs/rationale.md` に設計根拠と **MCP 撤回の経緯**を記録する。
9. `ARCHITECTURE.example.md` / `GOTCHAS.example.md` を Codiel から移設し、
   §10-5 の宣言訂正を反映する。

N1 の完了条件: M1〜M7 が通ること。特に **M4(注入された CLI パスが実際に動く)** と
**M5(deny hook が誘導し、AI が CLI へ切り替える)** を必ず確認する。
この 2 つが C1 構成の成立条件そのものである。

## 15. 不採用案・検討済み代替

### 15-1. MCP サーバー化(当初案。独立レビューを経て撤回)

ARCHITECTURE / GOTCHAS の読み書きを MCP サーバーのツールとして提供する案。
`read_architecture` / `stage_architecture` / `commit_architecture` / `append_gotcha` 等を
ツールとして定義し、`plugins/metatron/metatron-mcp/dist/server.mjs` を常駐させる。

- 利点: ツール一覧に現れるため**発見性が高い**。引数がスキーマで型付けされ、
  モデルにとって呼びやすい。同リポジトリに raguel-mcp の前例がある。
- **不採用の理由**(§1-4 の 4 点):
  1. **読み経路がすべて MCP を迂回する。** SessionStart 注入・Codiel hooks・セッション中の Read が
     いずれもファイル直読で足り、MCP を通る読み経路が存在しない。存在理由が
     低頻度の書き込み検証だけに縮退し、常駐プロセスの対価に見合わない。
  2. **MCP でも強制にならない。** ツール呼び出しは任意であり、Write で直接書けば素通りする。
     強制点は PreToolUse deny hook であって、ツールの提供形態ではない。
  3. **検証ロジックが二重実装になる。** deny hook は MCP を呼べない実行文脈で動くため、
     サーバー内に検証を閉じると hook 側にも同じ判定が必要になる。
  4. **raguel-mcp は前例にならない。** run の各フェーズで必ず通る高頻度ゲートであり、
     頻度プロファイルが根本的に違う。
- **発見性の代替**: MCP の唯一の明確な利点である発見性は、
  SessionStart 注入文の CLI 案内(§8-1)と deny hook の拒否メッセージ(§7-5)の
  2 経路で代替する。前者は毎セッション必ずコンテキストに載り、
  後者は間違えた瞬間に正しい窓口を教える。
- 将来 MCP へ昇格する余地は §16-6 に残す(サブコマンド体系はツール名に 1 対 1 で写せる)。

### 15-2. Codiel が metatron のライブラリ・CLI を直接参照する

Codiel から metatron のプラグインルートを解決し、共有ライブラリを import するか
CLI を直接叩く案。

- 利点: パス解決規則の写しが不要になり、実装が 1 つで済む。
- **不採用の理由**: **`CLAUDE_PLUGIN_ROOT` は各プラグインについて互いに不定**であり、
  Codiel から metatron のインストール位置を知る手段が無い。ハードコードは論外、
  探索は環境依存の推測になる。ソースのコピーによる共有も、
  ユーザー決定により採らない(二重管理の常態化を避けるため)。
- 代替: 連携をファイル契約(§3-3 (a))とモデルコンテキスト(§3-3 (b))の 2 手段に限定する。
  パス解決規則は 3 実装が独立に持ち、テスト R4 と sandalphon のケース 16f で
  一致を機械的に検証する(§13-2)。

### 15-3. ファイル生成インタビュー方式の継続

現行 `initializing-harness` の方式(質問 → 回答 → Write)を metatron へそのまま移す案。

- 利点: 実装が軽い。「出所は常にユーザーの回答」という現行の HARD-GATE をそのまま保てる。
- 不採用の理由: 書式の保証・部分更新・追記のみ規律・採番のすべてが
  「AI に守らせる指示」のままになる。特に**フェンス開始行を 1 文字間違えると run が
  開始できなくなる**という現行の脆さは、検証手順を AI が省略しないことに依存しており、
  不変条件として弱すぎる。
- 部分採用: **対話形式**の価値は残す。ただし「質問して埋める」から
  「解析して提示し、承認を取る」へ変える(§9-1)。

### 15-4. 内部 DB に保存する

ARCHITECTURE / GOTCHAS を SQLite 等に持ち、ファイルは出力形式の 1 つとする案。

- 利点: 構造化クエリが自然。検索・集計が速い。書式の破損が起きない。
- 不採用の理由: **チーム資産としての性質を失う。** git でコミットできず、PR でレビューできず、
  GitHub 上で読めず、metatron を入れていない人が読めない。ARCHITECTURE は
  「新しく入った人が最初に読む文書」であり、その価値は「特別なツール無しに読める」ことに
  強く依存する。DB はマシンローカルになりがちで、チーム間で内容が同期しない。
- 補足: 検索性能の懸念は、GOTCHAS が数百件規模に収まる想定では問題にならない。

### 15-5. 環境変数によるパス設定

`METATRON_ARCHITECTURE_PATH` 等でパスを指定する案。

- 利点: 実装が最も簡単。設定ファイルの探索も解析も要らない。
- 不採用の理由: **チーム内で位置が乱立する。** 環境変数は各自のシェル設定に書かれ、
  リポジトリにコミットされない。A さんの環境では `docs/ARCHITECTURE.md`、
  B さんの環境では別の場所を見る、という状態が容易に発生し、
  しかも**その食い違いは誰の目にも見えない**。
  共有資産の位置は共有された場所で宣言されなければならない。
- 補足: 設定ファイルとの併用(環境変数が優先)も採らない。優先順位を持つ設定は
  「なぜ自分の環境だけ違う挙動なのか」の調査コストを恒常的に発生させる。

### 15-6. 注入せず「CLI を呼べ」という指示だけを置く

SessionStart で「metatron の CLI で前提を確認せよ」という 1 行だけを注入する案。

- 利点: 常時のコンテキスト消費がほぼゼロ。
- 不採用の理由: **§1-5 で解決したはずの問題がそのまま残る。** 「呼ぶかどうか」が
  AI の判断に戻り、「今回は関係なさそう」で読まれない。GOTCHAS は
  「関係あると気づいていない罠」を伝えるための台帳であり、読む判断を読み手に委ねると、
  最も必要な場面(罠の存在に気づいていない場面)で読まれない。
- 部分採用: 注入の**先頭**に CLI の案内を置く(§8-3)。これは指示ではなく、
  更新経路と深掘り経路の提示である。

### 15-7. `codiel:domains` を `raguel.config.yaml` へ移設する

ドメインマップを ARCHITECTURE から出し、Codiel の設定ファイルに移す案。

- 利点: 機械可読ブロックが Markdown から消え、書式破損の危険が減る。
- 不採用の理由: ドメイン→パス写像は Codiel 固有の設定ではなく、
  sandalphon の探索スコープ、人間のオンボーディング、将来の他プラグインが等しく使う
  汎用のアーキテクチャ知識である。Codiel の設定ファイルに置くと、
  Codiel を使わないプロジェクトはこの資産を持てず、Codiel を外すと消える。
  また、ドメインマップは「ディレクトリ構成と責務」の節と表裏一体であり、
  同じファイルに置くほうが人間にとって読みやすく、乖離も起きにくい。
- 補足: 「書式破損の危険」は §6-2 の検証を CLI の書き込みパスに置くことで対処する。
  危険を避けるために資産の置き場所を歪めるのではなく、危険そのものを機械で潰す。

## 16. 未解決事項

### 16-1. GOTCHAS / ARCHITECTURE のコミット責務

- 選択肢 A: metatron は書き込むだけでコミットしない。コミットは呼び出し元
  (Codiel の `recording-gotchas` は現行どおり `git add` + コミット)。
- 選択肢 B: `append-gotcha` / `commit-architecture` にコミットまで含める。
- **推奨: A。** 対象プロジェクトのコミット粒度・メッセージ規約・ブランチ戦略は
  metatron からは見えない。Codiel は run の文脈(`issue-N try-M`)を持つのでコミットできるが、
  metatron 単体の呼び出しにはその文脈が無い。sandalphon 設計書 §14-1 と同じ判断であり、
  「ツールは書き込みまで、コミットは文脈を持つ側」で 3 プラグインの方針が揃う。
- **ただし単体利用時は放置しない。** metatron のスキル(`recording-gotchas` /
  `capturing-architecture` / `updating-architecture`)は、書き込み完了の報告に
  **「`docs/GOTCHAS.md` を更新した(未コミット)。コミットするか」の確認を 1 行添える**ことを
  規律とする。CLI がコミットしないことと、ユーザーが未コミットの変更に気づかないことは別問題で、
  後者は報告で解決できる。Codiel 経由の場合は Codiel 側のコミット規約が働くため、
  この確認は不要(重複して尋ねない)。

### 16-2. 注入予算の既定値(`maxChars = 9000`)と他プラグインとの配分

プラットフォーム上限が 10,000 文字である以上(§2-3)、予算はその内側でしか取れない。
問題は **metatron が 9000 を取ってよいか**である。他プラグインも同じ SessionStart で注入する。

- 選択肢 A: 既定 9000 で開始し、圧迫が観測されたら利用者が `maxChars` を下げる。
- 選択肢 B: 既定をもっと控えめ(5000 等)にし、必要な人が上げる。
- 選択肢 C: 他プラグインの注入量を実測して動的に配分する。
- **推奨: A。** C は実装不能に近い(自分の hook が動く時点で他プラグインの出力量を知る手段が無い)。
  B は「既定のままだと肝心の GOTCHAS がほとんど載らない」状態を作り、
  設定を触らない大多数の利用者にとって機能が目減りする。
  A の実害は「他プラグインの注入が押し出される可能性」だが、
  **押し出しはプラットフォーム側の退避で可視化される**(消えるのではなく退避先が示される)ため、
  気づける失敗である。気づけない機能低下より、気づける圧迫を選ぶ。
- **見積もり(実測ベース)**: `ARCHITECTURE.example.md` は実測 **4,348 文字**、
  記入ガイドの HTML コメントを除くと **2,881 文字**。生成される ARCHITECTURE は
  コメントをコピーしないため、後者が基準になる。
  ここに新設 3 節を加えると、`## システム概要`(散文 + Mermaid)で約 600 文字、
  `## レイヤー構造` で約 400 文字、`## ADR 一覧` は注入ではタイトル + 状態のみなので
  1 件約 40 文字。ADR 10 件で合計 **約 4,300 文字**。
- GOTCHAS は目次 1 行が約 45 文字で 100 件なら約 4,500 文字、直近 5 件全文が約 2,000 文字。
  CLI 案内が約 600 文字。**総計は約 11,400 文字**で 9,000 を超える。
- したがって **100 件規模では段階 1〜2 の縮退が通常運用で発動する**。これは想定内であり、
  縮退が「異常時のみの安全弁」ではなく「通常の調整弁」として働く点が
  当初設計(32KiB)との実質的な違いである。ARCHITECTURE 側は
  ADR を除けば 4,000 文字前後に収まり、段階 4 に到達するのは稀である。

### 16-3. ARCHITECTURE のさらなる機械可読化

`## コマンド定義` と `## 保護パス` も `metatron:commands` / `metatron:protected` として
ブロック化するか。

- 選択肢 A: v1 は `metatron:domains` のみ。
- 選択肢 B: v1 から 3 ブロックすべて。
- **推奨: A。** B にすると保護パスの二重管理を解消したくなるが、それは
  「保護パスの意味論の定義」という別の設計判断を巻き込む。コマンド定義は `scan` が
  `package.json` から候補を取れるため機械可読化の利得が小さい。
  ブロックを増やすほど書式破損の面が広がる。必要性が確認できた時点で v2 として追加する。

### 16-4. ARCHITECTURE 単一ファイルの肥大

- 選択肢 A: v1 は単一ファイル固定。肥大したら注入を段階 4(目次+要約への縮退)で凌ぐ。
- 選択肢 B: `paths.architecture` にディレクトリを許し、セクションごとにファイルを分ける。
- **推奨: A。** B は「セクション = ファイル」の対応を持ち込むため、セクション構成の固定が
  ファイル構成の固定になり、変更の影響範囲が広がる。分割が必要なほど大きいプロジェクトでは、
  そもそも「全文を毎セッション注入する」前提自体を再検討すべきで、
  ファイル分割は根本問題を先送りする対症療法にしかならない。

### 16-5. `guard-write` への domains 配線

§10-5 で「今回は宣言訂正のみ、配線はしない」と決めたが、配線自体の是非は残る。

- 選択肢 A: 配線しない(現状維持)。ドメイン別 implementer の書き込み境界は
  引き続きプロンプトの指示で運用する。
- 選択肢 B: 別スコープの独立した変更として配線する。
- **推奨: B を別途行う。** 現状は「宣言はしているが強制していない」状態であり、
  ドメイン境界を越えた書き込みが実際には通る。これは Codiel の設計意図からの逸脱であり、
  いずれ埋めるべき穴である。ただし**metatron 分離とは無関係な挙動変更**であるため、
  同じコミット範囲に混ぜない。分離完了後に単独の変更として扱えば、
  回帰が出たときの切り分けができる。
- **2026-08-17: B を採用済み。** metatron 分離の完了後に、独立した変更として配線した。
  第 1 段で `RunState.domain` と `codiel-state` の `set-domain` / `clear-domain` を追加し、
  第 2 段で `guard-write` の CODE_PHASES 分岐にドメイン境界の判定を入れた。
  違反は deny ではなく **ask**(境界の誤りは改竄と異なり人間が通せる余地を残す)。
  `domain` 未設定・ドメインマップが読めない場合は境界を課さない(従来動作)。
  これに伴い §10-5 の「配線はしない」と、そこから派生した
  「`guard-write` はドメインマップを読まない」旨の記述は**当時の記録**であって現状ではない。

### 16-6. 将来の MCP 昇格

- 選択肢 A: C1 構成を維持する。
- 選択肢 B: 発見性・引数の型付けの利点が実運用で決定的になった場合、MCP へ昇格する。
- **推奨: A で開始し、B の余地を残す。** CLI のサブコマンド体系は

  ライブラリ経由の構成も維持される。すなわち**昇格は追加であって作り直しではない**。
  判断材料は「AI が CLI の案内を見落として直接編集を試みる頻度」であり、
  deny hook のログで観測できる。

### 16-7. deny hook の対象範囲

- 選択肢 A: `Edit|Write` のみを対象とする(現設計)。
- 選択肢 B: Bash のリダイレクトも `guard-bash` 相当の構文解析で捕捉する。
- **推奨: A。** B は誤検知(正本を読むだけの `cat` や、パスを含む無関係なコマンド)と
  実装コストが釣り合わない。§7-5 のとおり、この hook は
  「回避しようとする AI を止める」ものではなく「知らずに直接編集する AI を導く」ものである。
  悪意ある回避を防ぐ必要が生じたなら、それは hook ではなく権限設計の問題として扱う。
