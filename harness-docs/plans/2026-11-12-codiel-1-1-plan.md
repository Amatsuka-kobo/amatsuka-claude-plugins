## 3. タスク間の契約

### 3-1. 作業の契約の項目(T7 が定め、T8・T9 が使う)

現行の依頼文テンプレート(`skills/orchestrating-runs/SKILL.md:343-373`)を、次の項目の「作業の契約」に置き換える(設計書 1.2 の C)。

| 項目 | 中身 | 現行との違い |
| --- | --- | --- |
| 作業内容 | この単位の作業 | 同じ |
| 任せる判断 | 作業者が材料から決めてよい判断と、その材料のパス。無ければ「なし」 | 新しい |
| 読むスキル | `<plugin-root>/skills/<スキル名>/SKILL.md` | 同じ |
| 観点ファイル | 選んだ観点ファイルのパス | 同じ |
| 入力ファイル・出力ファイル | 絶対パス | 同じ |
| 前提 | diff の範囲・ARCHITECTURE・実行モード・testsDir・担当タグ・担当範囲 | 「反論済み所見」を外す |
| 前フェーズの申し送り | findings の要約 | 同じ |
| 書いてよい範囲と使ってよい tools | 現行の `:375-381` の条項 | 「依頼文には…足す」を「契約に書く」へ |
| 完了の条件 | 単位の変更を、作業しているブランチ(並列の単位は worktree のブランチ、直列の単位は run ブランチ)にコミットしてあること。文書系フェーズでは git 操作をしないこと | 新しい。コミットを契約で指示する |
| 返し方 | 返答の 1 行目に `result: done`・`result: undecided`・`result: declined` のどれかを書く。`undecided` には理由と、判断が要るなら問いと選択肢の材料を添える。`declined` には理由を添える。修正の単位で、回帰が収束せずに修正を止めたときは `result: done` とし、残った失敗を報告に書く | 新しい |

- 削る項目は、冒頭の「あなたはサブエージェントである」と「## セッションの規律の転記」である。
- `undecided` で返す場面は、設計書 1.2 の C の箇条のうち、作業を引き受けない場面を除く 3 つである。
  - 任せない判断が要る。
  - 任せた範囲の外の判断が要る。
  - 作業を進められない。依頼文と実コードの食い違い、原因を 1 つに絞れない失敗、任せた判断の外の不明点(契約と Read・Grep で決まらないもの)、書いてよい範囲の外の変更、名指しされていないスキル、契約の必須の項目(観点ファイル・diff の範囲・testsDir など)の欠けが当たる。
- レビューの所見や NG のテストは `undecided` にしない。所見は `result: done` の報告に書き、修正のループで扱う。
- 作業を引き受けないときは `declined` で返す。
- 回帰が収束しない修正(`fixing-failures` の 3 巡の差し戻し)は `undecided` に含めない。設計書 1.3 のとおり修正のループの 1 ラウンドとして数え、次のラウンドへ進める。
- 5 スキルにある既存の「差し戻す」(`implementing/SKILL.md:35`・`reviewing-diffs/SKILL.md:19,28`・`fixing-failures/SKILL.md:13`)は、`undecided` で返す形に書き換える(T9)。
- 委譲するときは、契約を依頼文にする。運用方針が依頼文に求める項目は、契約の前後に足してよい。
- 自分で作業するときは、契約を自分への作業指示として使い、書いてよい範囲と tools も同じものを守る。

### 3-4. 計画の判断

設計書が実装計画に委ねた点と、設計書に無かった点を、次のとおり決めた。

| 番号 | 判断 | 理由 |
| --- | --- | --- |
| P1 | 標準の run で委譲先が `undecided`・`declined` を返したら、人に聞く。返答を `waits/<id>.md` に書いて `wait-done` し、同じフェーズの待ちがすべて消えてから `mark-ask <phase> --kind confirm` → AskUserQuestion → `resume` と進める。選択肢は「判断を示して続ける」「委譲先を変えて続ける」「中止」の 3 つとする。「判断を示して続ける」は問いが返ったときだけ出す。続けるときは、新しい回の待ちの `id`(`<フェーズ>-<要素>-<回>`)で単位をやり直し、示した判断を契約の「任せる判断」に足す。中止は `stop --reason ask-aborted` とする。やり直しは修正のループのラウンドに数えない。ただし理由が契約の不備(必須の項目の欠け、観点ファイルの数の誤りなど)なら、人に聞かず、オーケストレーターが契約を直して新しい回でやり直す。直した契約でも契約の不備で返ったら、上の手順で人に聞く | 設計書 §9 の未決。選択肢と止め方は 1.2 の 3.6(`harness-docs/design/2026-11-08-codiel-1-2-workflow-modes-design.md`)にそろえる。待ちが残る間に `mark-ask` すると、run が `awaiting_human` になり、guard-write の境界が外れる(`parallel-gates.md:5` と同じ理由)。返答で止まるのは委譲したときだけである。オーケストレーター自身が作業者で、任せない判断が要るときは、`mark-ask` の後に判断を人に聞き、選択肢は「判断を示して続ける」「中止」とする |
| P2 | 委譲先を変えて続けるときの選び直しは、運用方針に従う。人が委譲先を示したときはそれを使う | D1 のとおり、codiel は委譲先を書かない |
| P3 | run の中で GitHub MCP の PR 作成のツール(`create_pull_request` など)を呼んだら、guard-github-mcp がフェーズの検査の後で拒否し、`gh pr create --label codiel` を使うよう返す。`gh api` で PR を作る経路はラベルを検査しない | GitHub MCP の `create_pull_request` はラベルを受け取らない(Context7 の `/github/github-mcp-server` で確認)。設計書 3.2 の「ラベルが無ければ拒否」を当てると常に拒否になるので、拒否の理由を明示する。github モードは `gh` の認証が条件なので、`gh` の経路は常にある。指示層は `gh api` で PR を作らないので、`gh api` の経路は既知の抜け道として残す。設計書 3.2 との差として、2026-11-12 にユーザーの承認を得た |
| P4 | リポジトリに `codiel` ラベルが無いときは、init・intent(github モードで Issue を扱うとき)・pr の 3 か所で作るかを聞き、承認を得て `gh label create codiel --color 1D76DB --description "codiel が対応する Issue と PR"` で作る。有無は `gh label list --search codiel --json name` の結果に、名前が `codiel` に一致するものがあるかで確かめる | 設計書は init だけで作る。init で断られたリポジトリでは、`--label codiel` の `gh pr create` が失敗し、issue-craft は無いラベルを黙って落とす。`gh label list` は既定で 30 件しか返さないので `--search` で絞る。色と説明は設計書 8 章でビルダーに任された |
| P5 | `record-attempt` の出力から `capExceeded` のキーだけを外し、`{ statePath, state }` を返す。state の型の `limits` は省略可にし、読まない | ほかのコマンドと同じ出力の形を保つ。上限を外すと `capExceeded` は常に false になる |
